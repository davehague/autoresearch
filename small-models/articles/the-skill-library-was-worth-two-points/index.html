The skill library was worth two points

Take one open model. Freeze it. Run the same 89 terminal tasks through five different agent harnesses — the kind people actually install, not research prototypes. The worst one scores 60.1%. The best scores 71.9%.

That is PILOT in the Loop (arXiv 2608.26530), and the 11.8-point spread is measured with nothing about the model changing. On a second frozen backbone the spread is 11.7 points. Before you fine-tune anything, before you buy a bigger model, the software wrapped around it is worth about twelve points on Terminal-Bench 2.0.

Twelve points is the eye-catching number. It is also the wrong one to plan with, and the paper contains a better one.

Twelve points is the cost of choosing badly

Here is the full table, pass rate on Terminal-Bench 2.0, two runs averaged, same weights in every row:

HarnessGLM-5.1Kimi-K2.6
Terminus-264.059.6
Hermes60.164.0
OpenCode66.964.6
Pi65.766.9
PILOT71.971.3

PILOT is the authors' own system, so treat its win with the usual suspicion. But notice what the rest of the table does. The gap between PILOT and the best alternative is 5.0 points on one backbone and 4.4 on the other. The gap between the best and worst alternative — between two things a reasonable person might install — is 6.8 and 7.3.

So the twelve points is mostly the penalty for picking the wrong harness, not the reward for picking a clever one. Those are different decisions with different budgets.

Notice also that the ranking flips. Hermes is last on GLM-5.1 and third on Kimi-K2.6. OpenCode and Pi swap places. A harness recommendation does not survive a change of model, which means benchmark tables like this one are evidence that harness choice matters and not evidence about which harness to choose.

One more honest detail: on SWE-bench Multilingual, PILOT loses to Pi, 72.7 to 72.9.

The number that actually changes a build plan

The second experiment is the one worth reading twice. Run the same benchmark repeatedly. Let each harness keep what it learns — write skills into its own library, carry them into the next pass. Same frozen model, same starting library, same instruction about recording and reusing experience.

HarnessImprovement over repeated passes
PILOT+14.6
OpenCode+7.9
Pi+2.3

Identical model. Identical available experience. Six-fold difference in what gets extracted from it.

Pi's +2.3 is not an anomaly. Recuris (arXiv 2608.24876) ran the ablation that isolates it. Starting from 58.1 on a retail agent benchmark: adding a skill library alone gets you 60.1, up 2.0. Adding a component that tracks task state gets you 82.0, up 23.9. Both together, 83.6.

Two labs, two benchmarks, two different models, the same answer. A skill library, on its own, is worth about two points.

This is worth stating plainly because the skill library is the part everyone builds first. It is legible, it feels like accumulating an asset, and every agent framework ships one. Demystifying Agent Skills (arXiv 2608.14036) explains why it underdelivers: as the pool grows from 5 entries to 100, precision at retrieving the skill actually used falls from 29.6% to 3.3%. The library gets bigger and the thing you needed gets harder to find — at 3.3%, roughly thirty of every thirty-one skills pulled into context are distractors. MemTrapBench (arXiv 2608.20202) found the floor of the same effect — five memory frameworks on two models, and all ten combinations scored below having no memory at all.

What separates PILOT's +14.6 from Pi's +2.3 is not the store. It is the policy governing it: a separate supervisor process watching the run, deciding when to write something down and when to pull it back out — and, in PILOT's case, able to interrupt the worker mid-task. Recuris measured the same split from the other side, finding model-controlled skill invocation worth 7.5 points against the library's 2.0.

The build order that falls out is unglamorous and cheap: the read/write policy is the product; the library is a side effect.

Two things this evidence does not support

The headline self-improvement number is a maximum. PILOT's +14.6 is a best-so-far figure across roughly fourteen complete passes over all 89 tasks. The paper says so; downstream summaries will not. On stateful agentic work the gap between "succeeded once" and "succeeds every time" is enormous — Thinkingbox (arXiv 2608.19741) measured a top model at 65.4% pass@1, 91.1% pass@20, and 25.3% pass^20 across 507 workflows at 20 attempts each. Fourteen draws sits inside that range, and no per-pass mean is published. Two things do argue the accumulation is real rather than lucky: the skill set grows monotonically (62 to 83 skills on one backbone, 50 to 81 on the other), and mean output tokens per task fall from 28.5K to 16.3K. Something is being learned. Just not necessarily 14.6 points of it.

Uplift measured against a paper's own default is inflated. AutoSaddler (arXiv 2608.23041) is the cautionary case: it reports roughly +10 points against base harnesses on three benchmarks, and when the comparison is run against an expert-tuned harness instead, the margin is 2.5. PILOT's table has no defaults in it, which is what makes it useful — but it is also why the honest read of PILOT's own contribution is 5 points, not 12.

The one thing not to do yet

The obvious next move, once you accept that the harness is worth twelve points, is to fine-tune the model for the harness you built. There is now a measurement of what that costs.

The TaoLive technical report (arXiv 2608.15763) trained an open 35B for a production agent and published the control condition. Naive fine-tuning against a fixed harness bought 9.2 points on the target task and cost 7.7 points of instruction-following on IFEval, plus 4.6 points of prompt robustness. Reinforcement learning inside that same fixed environment then pushed prompt robustness to 66.7 — below the 72.8 of the model that was never trained at all. The authors' diagnosis is that the model learns the surface form of the harness: the literal tool names, the literal system prompt, the literal skill list.

A harness is not a fixed object. Tools get renamed. Prompts get rewritten. If the model was tuned to last month's version, every one of those edits is a regression nobody will attribute correctly.

Their fix is one extra axis of data generation, and it reverses the sign completely: present each training example under many semantically equivalent harness surfaces. Fixed-harness fine-tuning loses 4.6 points of prompt robustness; the augmented version gains 4.5, at slightly better task performance. If you tune a model to your own scaffolding, randomise the scaffolding while you do it, and hold out a harness variant the model has never seen as the acceptance test.

Everything above rests on single-lab results with two runs per configuration at best, no confidence intervals anywhere, and winning systems evaluated by the people who built them. The direction is consistent across five studies. The magnitudes are not settled.
