KV-cache quantization tolerance is a property of the training recipe — a QAT checkpoint diverges ~20× less than the same model without it

Anbeeld swept KV-cache quantization on two Gemma 4 31B Q4_0 checkpoints differing only in whether the weights were quantization-aware trained (Unsloth's standard build vs Google's QAT build), measuring KLD against a BF16-cache baseline on WikiText-2 at 32,768 context. Mean KLD, non-QAT against QAT: Q8_0 cache 0.305575 vs 0.015078 (20.3×), Q4_0 0.880436 vs 0.090504 (9.7×), Q2_0 4.176003 vs 1.058423 (3.9×); same-top-token agreement 85.1% vs 94.9%, 71.6% vs 86.3%, 26.6% vs 48.7%. The practical consequence is a free rung: QAT at Q4 cache (0.0905 / 86.3%) beats non-QAT at Q8 cache (0.3056 / 85.1%) on both metrics while using 940 MiB less cache. A 1024-token full-precision tail takes QAT Q4 to 0.025147 / 92.997%. The author's own framing: "QAT shifts the boundary; it does not remove one" — Q2 is unusable either way.

This adds the upstream variable that explains part of the scatter run 13 documented. The quant label is not a spec — Q4_K_M was non-monotonic in three of four independent GGUF builds of one model (the-quant-label-is-not-a-spec) — and run 16 forced identity by hash, quant recipe, expert count, GPU and engine version (the-same-quant-file-scores-differently-on-different-gpus). QAT-or-not joins that list, and it is the entry most likely to differ silently between an official vendor release and a community requant of the same weights.

It also unsettles an ordering we inherited. Run 13 found model precision degrading faster than cache precision at 2.6B, inverting what a 700B production operator reported, and concluded the weights-versus-cache split is a knob to sweep per model (quantization-damage-is-a-cliff-that-log-scale-metrics-hide). This says the split is not stable per model either — it moves with the training recipe of the same model at the same size. Sweep per artifact.

Why it is worth a serving-economics entry rather than a footnote: cache precision sets how much context fits, and long agentic loops are context-bound. vLLM's DCP bought 3.3× concurrency by re-laying-out the KV cache with weights and cache bit-identical (kv-cache-layout-buys-33x-throughput-with-no-quality-spent); this is the other half of the same memory budget and says a QAT checkpoint buys about one cache rung at equal fidelity — resident context up, quality flat, decided once at checkpoint selection, costing nothing.

Two cautions. KLD grades a proxy and there are no task benchmarks here at all — run 10's decomposition showed compression takes instruction-following and tool use first while closed-form reasoning stays near-intact (compression-degrades-agentic-skills-more-than-reasoning), so a 20× KLD improvement is not evidence about the capability an agent is made of. And run 16's rule applies to the method: verify the reference bit-exact (the-lossless-baseline-was-farther-from-the-original-than-a-3-bit-quant). The reference here is each checkpoint at BF16 cache, correct for the cache question — but both arms are Q4_0 weights, so neither is measured against the original model, and the QAT arm's cache advantage says nothing about where its weights already sit relative to FP16.

Grade: single-study — one independent benchmarker, one model, one RTX 3090, a custom llama.cpp fork, no task-level evaluation. The control is tight (same model, same weight quant, same hardware, one variable) and the ratio large, so the direction holds and the action it implies is free: prefer QAT checkpoints where one exists.
