An Apache-2.0 27B lands six points behind a 2.4T open checkpoint on SWE-bench Pro — eighty-nine times the parameters bought six points

Every open-vs-frontier reading this vault holds has been taken on a checkpoint we could not realistically host. Run 8's open-weight entrant at the frontier band was 2.4T (open-weight-model-ties-frontier-on-verifiable-trails-on-hard-swe); run 11's Prime Agent arm was 744B; GLM-5.3 is 743B; the endpoint study's subject was GLM-5.2 (api-endpoint-changes-an-open-models-accuracy-by-27-points). The vault's own premise — a model we train and serve on our cluster — has never had a datapoint at a size that premise permits.

Qwen3.8-27B is that datapoint. 27B parameters, Apache 2.0, 262K native context, and against the run-8 open 2.4T it reads SWE-bench Pro 61.7 vs 67.7 and Terminal-Bench 2.1 73.0 vs 86.6. Against the vendor's own Opus 4.6 Max column it wins SWE-bench Pro (61.7 vs 53.4), QwenSWEBench (79.0 vs 63.8), IFBench (79.5 vs 62.5), CoWorkBench (70.7 vs 68.2), LiveCodeBench v6 (90.3 vs 88.8) and OSWorld-Verified (84.3 vs 72.7), and loses Terminal-Bench 2.1 (73.0 vs 78.2), GPQA Diamond (89.2 vs 91.3), HLE (30.8 vs 40.0) and NL2Repo-Bench (42.3 vs 47.6).

Two readings, and the second is the one that changes a decision.

The win/loss split falls on this vault's best-performing predicate without being asked to. Wins cluster on executing a specified procedure — agentic coding against tests, instruction-following, computer use. Losses cluster on abstract reasoning and whole-repository generation — GPQA, HLE, NL2Repo-Bench. That is the procedure-versus-novel-artifact cut used prospectively for the fourth run running, now at a fourth size class.

The reading with consequences is the parameter-efficiency slope. Going from 27B to 2.4T — 89× the parameters — buys 6.0 points on SWE-bench Pro and 13.6 on Terminal-Bench 2.1. Run 12 established that base size outweighs technique on multi-turn tool use, with 1.7B → 8B worth 14.23% on BFCL and 21.4% on τ²-Bench (method-gains-favour-the-8b-over-the-4b). That slope has evidently flattened hard somewhere above 27B, which is exactly the region every serving-economics estimate on this vault's maps assumes we would have to operate in. If it holds, the memory-capacity threshold that swings self-hosting economics by ~45% (accelerator-memory-capacity-swings-self-hosting-economics) stops binding, because a 27B fits anything.

Discounts, all four binding. Vendor-reported and unreplicated. No reasoning effort stated on any row while the card ships a three-level effort dial, and run 13 measured 15.4 points from that parameter alone (reasoning-effort-moves-one-model-15-points). No harness, precision or endpoint stated. And the frontier column is Opus 4.6 Max when Opus 5 and Fable 5 exist — a vintage bias, not a tuning bias, and the second arrival this run pointing at it (the-open-frontier-gap-is-read-off-a-release-lag-not-a-capability-lag).

The cross-study comparison to the 2.4T carries its own warning: those numbers come from a different vendor's table at a different date under different unstated conditions, which is precisely the sin this map catalogues. Treat the 89×-for-six-points slope as a hypothesis worth one afternoon of our own measurement, not as a measurement.
