Tuning harness and cache settings — same models, same work — cut generated tokens by almost half in production

Databricks reports that "relatively simple tuning of our harness and caching settings led to an almost 50% reduction in the number of generated tokens" across its internal coding-agent fleet, with no accompanying quality claim in either direction. Separately it lists reducing token overhead as a 20–40% cost lever and dynamic request and task routing as 30%+.

This is a production confirmation of the vault's shipped-harness result from the customer's side of the meter rather than a vendor's or a benchmark's. Three measurements already said harness selection moves cost and not quality — a 2×+ per-task cost spread on private pull requests (harness-swap-moves-cost-not-quality-on-real-engineering-tasks), a 3.7× cost and ~6× median-token spread across six harnesses on an open model (harness-cost-spread-replicates-on-an-open-model), and a normalized-gain contrast of 0.079 against noise floors of ±0.035–0.066 (harness-optimization-gains-swing-with-task-and-seed-regime).

What this adds is a second, independent multiplier inside a single harness. Run 10 measured roughly 2× available between shipped harnesses; this measures roughly 2× more available from configuration within one. They compound, they need no model change, and neither is reported to cost quality. That makes the cheapest item on this vault's action list unchanged and now better supported: tune the harness and caching we already run, and measure the bill, before commissioning anything.

It also sharpens the design rule rather than merely confirming it. Run 11 rewrote the rule as arranging more model calls buys cost; removing model calls buys both (designed-harness-lifts-score-and-cuts-tokens-together). Cache tuning is the purest instance available: prompt caching does not change what the agent does, only what it re-reads, and it removes generated tokens without removing steps. Note the same post warns the trade is not free in one direction — cache writes have their own cost, so the setting is a knob to sweep against our real request mix rather than a switch to flip.

Limits. One company, undated, no baseline stated, no absolute figures, no quality evaluation reported alongside the token reduction — so "no quality cost" is an absence of evidence rather than evidence of absence. "Almost 50%" is generated tokens, not dollars, and the two diverge under caching because cache reads and writes price differently. Databricks sells infrastructure implementing several of these levers.
