Training through a harness you cannot see inside creates five specific places a run silently optimizes the wrong thing — and run 22 recorded the fix without knowing the failure

When the harness owns the interaction loop, the trainer observes only sequences of LLM request–response pairs. Agent Lightning enumerates what that blindness costs, and the list is short enough to act on: retokenization, sample merging, advantage calculation, loss normalization, and backend scheduling — which the authors say "can substantially affect training stability and effectiveness."

Each is a place where a run appears healthy and is not. Retokenization: the harness has already formatted the text, possibly with a chat template that differs from the trainer's, so the token sequence being optimized is not the one that was served. Sample merging: trajectories share long prefixes, and how you deduplicate them decides what gets weighted — run 22's ClawGym II used prefix trees for exactly this (black-box-rl-trains-an-open-30b-through-a-harness-it-never-reads). Advantage calculation: credit must be assigned over a structure the trainer never observed. Loss normalization: agentic sequences vary in length by orders of magnitude, and the normalizer chooses whether long trajectories dominate. Backend scheduling: the training engine now competes for GPUs with live harness execution.

This is the concrete engineering bill for a lever run 22 described as deleting an engineering effort. That reading stands — a shipped harness plus its environment is an environment already built and verified, which is the largest reduction in this map's dependency list since it was coined. But it trades environment construction for a shorter, sharper list of ways to be silently wrong, and this vault has a standing pattern of exactly that failure class: cross-teacher distillation failing silently without style residualization, rubric RL dropping signal recoverably, harness components that never fire. Run 22 read ClawGym II's headline — stability over 200–400 steps — as a claim about a fixed failure mode without knowing what the mode was. It is these five.

What is open, and what we would have to answer before running anything: none of the five has a published magnitude. "Can substantially affect" is the only quantification offered, on a framework paper written as a testbed rather than a study. We do not know which dominates, whether any is harness-specific, or whether the +14.6 on SWE-bench was obtained with or without getting them right. A cheap first check on our own stack: re-tokenize a captured trajectory with the trainer's template and diff it against what the proxy served. If those differ, everything downstream is being computed on a sequence the model never emitted.
