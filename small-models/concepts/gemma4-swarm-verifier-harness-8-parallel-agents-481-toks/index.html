A fan-out/synthesize harness — eight batched Gemma 4 E2B instances sharing one weight copy, assembled by one Gemma 4 26B-A4B verifier — hits 481.8 tok/s aggregate in ~3.5GB RAM on a 32GB Mac mini, but a same-thread critique says the sub-agents describe a template rather than write original code

Eight parallel Gemma 4 E2B-IT (QAT, 4-bit) instances, each given a distinct spec section (theme, player, enemies, pacing, power-ups, hazards, audio, HUD), run batched against one shared copy of the 2.4GB weight file via llama-server continuous batching: 60+ tok/s per agent, 481.8 tok/s aggregate, ~3.5GB total RAM for all eight slots. A Gemma 4 26B-A4B model then synthesizes the eight spec fragments into a playable browser game plugged into an existing runtime, the full cycle taking ~8 seconds. A commenter's structural objection: the sub-agents aren't writing code, only short descriptive spec sections that the larger model turns into structured JS against a fixed template — so the "coding in 8 seconds" framing overstates what varies between runs (likely palette and names, not mechanics).

This is a harness-engineering instance distinct from most entries on this map in what it's optimizing: not accuracy or agentic reliability, but memory-bandwidth economics on consumer unified-memory hardware — keep the fanned-out model tiny enough that batching stays near-free, and spend the one larger model's compute only on final synthesis. That design principle (cheap-model fan-out + single expensive-model assembly) generalizes independently of whether this specific demo (a templated game) represents real coding capability, which the in-thread critique correctly disputes.
