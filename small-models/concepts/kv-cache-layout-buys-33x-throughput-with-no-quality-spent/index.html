1,863 → 6,091 tokens/s/GPU on long-context agentic serving, at bit-identical weights and cache — the first cost lever on this map that spends nothing

vLLM's Decode Context Parallelism shards the KV cache along the sequence dimension instead of by attention head, so each GPU holds a slice of token positions rather than a duplicate of the whole cache. On 8× B200 serving Kimi K2.6 at NVFP4, against a workload of median ~67K-token inputs and ~400-token outputs: tensor parallelism plateaus at ~1,863 tok/s/GPU at concurrency 64; DCP reaches 6,091 tok/s/GPU at concurrency 512 using 82% of the KV-cache memory, and holds its frontier past 200K context.

Every other lever on this map is paid for somewhere. FP8 cache plus INT4 weights bought ~30% "within 0.8 points" (operator-quantization-cuts-cost-at-benchmark-parity) on benchmarks since shown blind to what compression takes (compression-degrades-agentic-skills-more-than-reasoning). Expert pruning takes ~10% of the domain you meant to keep (expert-pruning-is-a-second-unlabelled-shrink-axis). Buying a cheaper API hands the vendor a price dial (open-model-api-prices-are-not-a-stable-planning-input). This is ~3.3× at bit-identical weights and bit-identical cache — the shard axis changed, nothing else — so it is the rare entry a self-hosting case can bank without a hidden-capability-loss caveat.

It also corrects an omission in this vault's own arithmetic. The economics here rest on a utilization assumption (published ~70%, realistic 35–45%) formed with no KV-cache-layout term in it. The baseline plateaus at concurrency 64 because memory ran out while compute idled — which is what low realized utilization looks like from the inside, and turns out to be partly an implementation choice. Since self-hosting-savings-erased-below-engineer-scale-thresholds turns on volume, a 3.3× move in achievable concurrency moves the break-even directly, and any cost-per-completed-task estimate we build should be computed at the concurrency the stack can actually reach.

The workload shape is the other thing to keep: ~67K in, ~400 out is what an agent's bill looks like and nothing like the chat workload most serving comparisons assume. Note the asymmetry it exposes — the capability gap on long-context work is a model problem (open-weights-in-the-best-harness-still-trail-frontier-in-a-stock-sdk), but the cost of long-context work is substantially a serving problem.
