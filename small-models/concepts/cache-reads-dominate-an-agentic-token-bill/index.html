98% of the tokens in a published agentic benchmark run were cache reads — a per-token rate card prices the wrong thing by two orders of magnitude

The public Harbor job behind this run's Terminal-Bench 2.1 reproduction reports its token usage in full: roughly 3.34B total tokens — 3.28B cached, 27M prompt, 38.9M output. Cache reads are 98% of the volume. Prompt and output together are under 2%.

Run 13 accepted Databricks' internal claim that harness and cache tuning produced an almost 50% reduction in generated tokens (harness-and-cache-tuning-halved-generated-tokens-in-production), while noting it was an unaudited figure from a company selling gateway infrastructure. This is the same phenomenon from the opposite end — a published, per-trial artifact from a benchmark run rather than a production fleet — and it says the cache term does not merely matter, it dominates. Any cost-per-completed-task figure built from a headline per-token rate, without splitting cache reads from cache writes from fresh prompt tokens, is not approximately wrong; it is measuring a different quantity.

This sharpens run 10's instruction to harness-cost-spread-replicates-on-an-open-model and price in cost per completed task rather than per token. The unit was right and underspecified: cost per completed task, decomposed into cache-read, cache-write, prompt and output tokens, because those carry different prices and a harness change moves the mix rather than the total. It also explains mechanically why the same model can cost 2–3.7× more through a different harness — a scaffold that reorders context invalidates caches, and the invalidation is invisible in any metric that counts tokens without labelling them. A commenter's arithmetic on the same thread makes the point from the bill side: the newer, nominally cheaper model was listed at ~2.5× the cost per task of its predecessor, because it burned roughly twice the tokens weighted toward output.

Practical consequence: instrument our own runs to emit the four-way token split per task before we compare anything, and treat cache hit rate as a first-class harness metric alongside score.
