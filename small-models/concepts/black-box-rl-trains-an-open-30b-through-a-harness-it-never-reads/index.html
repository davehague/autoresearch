The harness does not have to be ours: an open 30B was RL-trained through OpenClaw and Claude Code as sealed black boxes, +9.98 and +14.81 Pass@1

Since run 9 this map has carried one named missing experiment: a small or open model paired with a serious harness on open-ended work, priced. The assumed shape of that experiment was always the same — we design a harness for our checkpoint, then race the pairing. Run 11's Prime Agent ran the quality half that way and lost 6 of 9. Run 19's DarwinX and run 20's AutoDesign both built harnesses, both on frontier bases.

ClawGym II runs it from the opposite end. The harness is not designed, not forked, not inspected — OpenClaw and Claude Code are executed unmodified inside per-rollout sandboxes, and the only contact point is a serving proxy at the model boundary that captures the calls the harness emits. Those captured calls are reassembled into prefix trees to recover multi-turn structure, and PPO and GRPO are adapted to optimize over the tree. Qwen3-30A3B — open weights, ~3B active, a size we can host and train — gains 9.98 Pass@1 through OpenClaw and 14.81 through Claude Code on ClawGym-Bench, stable over 200–400 optimization steps, with the gains carrying to JobBench and OfficeQA.

The consequence for this map is a change in what the pairing costs to build. Every version of the pairing considered here has priced two engineering efforts: tune the model, then build the scaffold. Run 20's headroom law made that trade explicit and unpleasant — the stronger the checkpoint, the less the scaffold buys (harness-uplift-and-base-score-are-inversely-related-across-seven-agents). ClawGym II removes the second effort entirely: take the best shipped harness, train into it. The engineering moves into an RL rig, which is a fixed cost reused across harnesses rather than a per-workflow scaffold build — and mix-harness training, optimizing one policy jointly under heterogeneous harnesses, is the paper's own answer to the obvious objection that you would be overfitting to one execution system's prompt conventions.

What it does not do is race anything. There is no frontier-plus-default-SDK arm; +14.81 is a before-and-after on one model, on the authors' own benchmark. So the pairing's central comparison is still unrun, and this is a lever added to our side of it rather than a result about it.
