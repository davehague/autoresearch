In harnessed agentic RL the GPU is not the bottleneck — 91.3% of wall-clock is the coding agent running in a sandbox

Across 3,699 OpenHands SDK trials, LEGO-RL measures where the time in a harness-native RL run actually goes. Agent execution accounts for 91.3% of mean wall-clock time — 840.5 seconds of 920.4 per trial. Sandbox setup takes 2.3% and verification 3.9%, both with substantial tail latency. The optimizer is a rounding error on the clock.

Every cost argument this map holds is about accelerators: memory ceilings, EFLOPs, A100-hours, an 87% GPU price increase, DRAM up 4–9×. That framing is correct for supervised fine-tuning and for classical RL, where the environment is cheap and the backward pass is not. It is wrong for the paradigm this vault has now ingested three times in three runs (harnessed-agentic-rl-has-a-name-and-five-implementations), because the environment is a full coding agent editing a repository in a container for fourteen minutes.

The two engineering results in the same paper are both attacks on the 91.3% rather than on the 8.7%, which is what makes them large. Asynchronous scheduling completes 7 steps against synchronous's 3 in the same 7.5 hours; correcting for the two runs' different optimizer throughput leaves 1.9 h per step synchronous against 1.0 h asynchronous. Lazy image delivery — fetching image data on demand instead of pulling the full task image first — improves median cold-start latency 1.7× and maximum latency 23× across 100 SWE-bench Verified images, cutting network traffic 21.6 GB → 1.59 GB and disk writes 65.6 GB → 5.29 GB.

What this changes for us is provisioning. The scarce resource for training a model through its harness is sandboxed CPU concurrency, container image throughput and disk, not the GPU allocation our cluster rations. Those are things we have, and things a cluster scheduler is bad at pricing. It also means the missing dollar figure in every one of these papers is less alarming than it looked: the dominant term is not accelerator-hours.
