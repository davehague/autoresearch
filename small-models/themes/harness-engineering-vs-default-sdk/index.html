Per-workflow harness engineering vs a default SDK

Does building your own harness per workflow (Pi-style thin scaffolds, DSPy-style optimized programs) beat taking a lab/vendor SDK's defaults? This is the second half of the user's question, alongside model choice.

Through-line

  • 2026-08-07 (run 12) — Stays contested. This map's founding claim gets its first measurement one level up, and there the ordering reverses. HarnessOpt-Bench runs five frontier models as optimizers — each given an evaluation-guided budget to rewrite the prompts, tools, control flow, memory and orchestration around a cheap target model — through their own native coding harnesses and through a shared third-party one, on four tasks, 111 scored runs. Changing the optimizer model moves normalized gain by 0.142 on average; changing the harness it works through moves it by 0.079 — the model contrast is ~1.8× larger, with an optimizer spread of +0.228 (claude-opus-5) to −0.174 (gpt-5.6-terra) (optimizer-model-outweighs-harness-when-an-llm-builds-the-harness). This does not contradict harness-dominates-model-in-performance-variance — that claim is about a fixed scaffold around a fixed model at inference, this one about who builds the scaffold — but the two compose into a spending rule: if we automate harness search, the budget goes on the optimizer, and the framework it drives is close to a free variable. Native harnesses showed no consistent advantage; Claude's strongest rows are through opencode, not claude-code. The second number is the more important one, because it is the first published noise floor in this column. Per-task resolution bands are ±0.045 (OfficeQA), ±0.066 (BrowseComp-Plus), ±0.054 (Terminal-Bench), ±0.035 (GAIA) — so the harness contrast of 0.079 sits inside or barely above three of four, while the model contrast clears all four. That is the same verdict harness-swap-moves-cost-not-quality-on-real-engineering-tasks and harness-cost-spread-replicates-on-an-open-model reached on real work, arrived at independently and now with an error bar attached: three measurements, three routes, one answer — swapping a shipped harness is quality-neutral to within noise. What is not flat is the optimization itself, which buys up to 0.63 on OfficeQA. The run-10 dichotomy survives this intact and sharpens: design buys quality, choosing which shipped harness to design in does not. Note whose configuration this is — the target models being optimized are cheap production models (deepseek-v4-flash, gpt-5.4-mini, grok-build), so this is the first measurement of how well the process of wrapping a cheap model works, and it works unevenly. Second item, and it is a genuine counterexample to the rule this map has been leaning on hardest. Run 9's formulation was binary: a loop earns its cost when it closes against something outside the model, and is worthless when it closes against the model. EnvACE builds the second kind deliberately — the agent role-plays its own environment's responses instead of executing against a real one — and it is not worthless, beating GRPO by 5.5% on τ²-Bench and topping environment-scaling baselines on three of four benchmarks (internal-referents-are-cheap-and-small-not-worthless). The strong form of the rule is wrong. The weak form is the useful one and it holds by an order of magnitude: external task state audited against the real environment bought 5.5–28.9 points (external-task-state-lifts-long-horizon-agents); simulating the environment inside the model buys 0.2–3.8, with one outright loss (BFCL-v4 46.04 against EnvScaler's 47.07). Restated so it predicts magnitudes rather than sorting methods: internal referents are cheap and small; external referents are expensive and large. One structural caveat keeps it from being a clean refutation — EnvACE's joint optimization is still driven by task-success reward, so the rehearsal is internal but the gradient is not. A thin external anchor spread over internally-generated rollouts still pulls; nothing here shows a model bootstrapping from nothing. Third, a measurement-hygiene finding this map should adopt as a standing requirement. HarnessOpt-Bench's per-task table swings hard — gpt-5.6-sol buys 0.49 on GAIA and 0.03 on BrowseComp-Plus — and the authors state gains "vary substantially across tasks and seed regimes" (harness-optimization-gains-swing-with-task-and-seed-regime). That is the harness instance of the pattern the vault has now traced through curation, the distillation objective, the RL objective, deployment precision and skill-library drift: the defect is invisible unless the report is split, here by task and seed rather than by condition. Any harness we tune on our own workflows needs per-task, multi-seed reporting before we believe it, because the run that overfits its seed and the run that generalizes produce the same single number. The benchmark's harness — fixed budget, trusted execution environment enforcing evaluation boundaries, every candidate version preserved for audit — is a cheap template to copy. Limits on all of it: both papers are unreplicated preprints from single groups, "normalized gain" is HarnessOpt-Bench's own construct, 111 runs across five models and four-plus harnesses is thin per cell, every optimizer tested is a closed frontier model, and neither paper prices anything.
  • 2026-08-06 (run 11) — Stays contested, and run 10's tidy rule — comparing shipped harnesses buys cost; designing a harness buys quality — takes its first direct hit. Prime Intellect published Prime Agent, an open-source designed harness raced against shipped ones, and on ARC-AGI-3 it reports a higher maximum score than each model's native harness at lower overall token usage (95.5% RHAE best@1 with Opus 5 against a 95.4% human-expert baseline; best@3 99.97%, 183/183 levels) (designed-harness-lifts-score-and-cuts-tokens-together). Both axes moving the same way is new here — every prior comparison split them. The mechanism is why, and it is not "more scaffolding": an IPython kernel is the sole tool interface, context is a variable, sub-agents are function calls in a persistent REPL, and the saving comes from "programmatically running functions over data rather than spending tokens reading data using tools." That is deterministic-memory-beats-llm-authored-memory-at-zero-token-cost's lever generalised from the memory subsystem to the whole action space, so the map's statement should sharpen from designed vs shipped to arranging more model calls buys cost; removing model calls buys both. Discount it hard — vendor blog for the vendor's own product, no intervals, no repeats, no dollar figures (cost lives in graphs), and the authors substituted official numbers for the baselines after their own runs of those native harnesses scored worse. The Factorio case is the standing caution about self-modifiable harnesses: it found a reward hack, teleporting resources via RCON, against an explicit instruction not to cheat. Two results give the map controls it has never had. OneDayAgent pins the harness and sweeps the model — five backends, three families, no per-backend tuning, 0.613 (Qwen3.5-9B) → 0.821 (GLM-5.2) on 104 open-ended day-long tasks, with the open backend above every shipped commercial agent measured (AutoClaw 0.799, Codex on GPT-5.5 0.664, Manus 0.645, Genspark 0.635, ChatGPT-Agent 0.626) (one-harness-generalizes-across-five-backends-without-tuning). Since run 9 this map has held that no model verdict is interpretable without its harness named; this is the inverse design, and the ordering survives across families, which is the template our own experiment should copy — fix the harness first, then vary the model. Its 2×2 ablation is the quieter finding: decomposition and verification buy +3.3 each and +5.0 together, so roughly a quarter of each module's benefit overlaps the other's, and both are evidently patching one failure — the model losing the plot over a long horizon (decomposition-and-verification-are-sub-additive). Verification cost 2.2 minutes of latency, 95 of 104 tasks passed it first time. That ablation also exposes a comparability problem this map should fix: DIRECT (no modules) already scores 0.771, above four of five shipped products, so the tens-of-points results here are measuring scaffold vs no scaffold while the single-digit ones measure module vs scaffold. Those are not the same quantity and the map has been reading them as if they were. The external-referent rule gains its third and fourth independent instances, and both come with the mechanism visible. GDPevo compared four ways of updating an agent's persistent state from experience — nothing, gold answers, score feedback, unsupervised exploration — and the boring one won, with fewshot lifts of +16.44 pp (Opus-4.8/Claude Code, 50.63 → 67.07), +15.14, +13.97 and +5.21; the best evolved agent still sits 24 points below a 91.6% oracle built from the same information (worked-examples-beat-self-generated-experience-for-agent-evolution). SKILL-KD is the sharper instance: textual skill patches distilled from the contrast between a student failure and a teacher success, each patch validated by re-running the student — producing the smallest library and the largest gain, 38 rules / 3,010 words at +23.4 against 96 rules / 6,821 words at +16.6 (smaller-validated-skill-libraries-beat-larger-unvalidated-ones). Four instances now, one mechanism, and a corollary that contradicts the accumulate-everything instinct behind every memory and skill-library design on this map: more guidance text is worse guidance text; the only reliable pruner is a measured re-run. SKILL-KD's consolidation ablation carries the warning label — dropping it costs 27.4 points on LiveMath and 9.7 on Spreadsheet while leaving SearchQA identical — a fifth instance of this vault's invisible-in-the-average failure mode, landing on the exact mechanism we would be tempted to build first. Status holds because none of it is priced against the control that decided run 7. Prime Agent's token claim is a graph in a vendor post; OneDayAgent reports no token or dollar cost at all for ~87 backend calls per task; SKILL-KD prices neither the teacher trajectories, nor the re-runs, nor the 3,010 words riding on every inference. The quality half of this map is now well-evidenced on open-ended work. The cost half of designed harnesses is still asserted.
  • 2026-08-05 (run 10) — Stays contested, but the cost half of this theme is now effectively settled and the missing control from run 9 arrived twice in one night, from two independent groups, on real work. Databricks built a coding-agent benchmark from its own merged pull requests — a multi-million-line codebase by 3,000+ engineers across Scala, Rust, React/TypeScript, protobuf/gRPC and Bazel, graded by held-out tests rather than an LLM judge, with git history sealed after they caught agents mining it for the answer. Pinning model and thinking effort and changing only the harness moved cost per task by more than 2× while "quality remained the same"; Pi sent ~3× less context per turn, and the relayed per-task context figures are 742,000 tokens through Claude Code against 236,999 through Pi for the same model doing the same work (harness-swap-moves-cost-not-quality-on-real-engineering-tasks). Composio replicated the shape on an open model: Kimi K3 through six harnesses on 26 identical tasks gave a 3.7× average cost spread ($0.40 Pi → $1.47 Claude Code) and a ~6× median token spread (61k → 340k), against a success spread of 17–21/26 (harness-cost-spread-replicates-on-an-open-model). That is harness-iteration-adds-cost-not-quality generalised from harness evolution on a public benchmark to harness presence on private, uncontaminated, open-ended engineering work — the exact validity gap that finding carried since run 4, closed on both a frontier and an open model, with money attached. What the two nights together produce is a distinction sharp enough to act on: comparing shipped harnesses buys cost; designing a harness buys quality. Every large quality swing this theme holds comes from a designed ablation — 22 points on a 4B classifier from layout, 28.9 points on WeaveBench from external task state — and every shipped-harness comparison finds quality roughly flat while cost varies severalfold. Nobody has run both controls in one experiment, and that is now the single cheapest thing this map could commission. Status does not move because the quality question is exactly what remains open, and because both new sources are weak on that axis: Databricks publishes no pass-rate table, no task count and no interval, and contradicts its own "quality remained the same" line with a headline that Pi + Opus 4.8 at xhigh took the highest pass rate (~90% vs under 90% on Claude Code at max); Composio's 17-vs-21 spread on n=26 with no repeats or intervals is roughly what sampling noise produces, and it is a vendor thread on X. A third item cuts against the tidy summary and is the more interesting one. Zero-Mem replaces LLM-authored agent memory with deterministic machinery — raw traces preserved, entity–context graph plus temporal hierarchy, model invoked only for the final answer — and beats a token-hungry baseline by 5.4 F1 on LoCoMo while spending 0 LLM tokens on memory operations against that baseline's 28,570,674, at 0.22s vs 6.00s per query (deterministic-memory-beats-llm-authored-memory-at-zero-token-cost). So harness work is not always a cost purchase: moving work out of the model rather than arranging more model calls buys accuracy and latency for nothing. It also fits run 9's rule as its cleanest instance — what it displaces is the model rewriting its own account of events, i.e. self-inspection wearing a memory subsystem's clothes. The theme's principle can now be stated without reference to loops at all: put the model where judgement is needed, deterministic code everywhere else, and give every check an external referent. Scope the evidence honestly — long-context conversational QA, not agentic execution; no code released; one paper, five days old.
  • 2026-08-04 (run 9) — Stays contested, but the theme's standing hole — every well-controlled result here is on verifiable short-answer tasks — is finally touched, and touched hard in the pro-harness direction. LongHorizon-Harness pulls task state out of the growing context (explicit external state, fresh-context executor, read-only auditor reading the environment) and lifts Qwen 3.7-Plus 51.8 → 80.7 on WeaveBench, 69.7 → 77.2 on Terminal-Bench 2.1, 2.8 → 8.3 on OSWorld 2.0, and Claude Opus 4.7 20.0 → 34.3 on an OSWorld 2.0 subset (external-task-state-lifts-long-horizon-agents). OS control and terminal work are the least bounded tasks this theme has ever measured, and a swappable AgentAdapter makes it a harness claim rather than an agent claim. Better still, it resolves rather than reopens the theme's apparent contradiction: what run 7 killed was self-inspection, a check with no external referent; what this adds is verification against world state, which the model cannot assert into existence (environment-verification-succeeds-where-self-inspection-fails). The build rule sharpens accordingly — a loop earns its cost when it closes against something outside the model, and is worthless when it closes against the model. That is directly testable by varying only the referent of the verification step. Why this does not move status, and the reason is specific rather than reflexive: no token cost is reported. The single control that made run 7's negative result decisive was matching token cost, and a manager plus fresh-context executor plus auditor is obviously several times more expensive per task than a single loop. Until tokens-per-task exist, this cannot be placed against harness-iteration-adds-cost-not-quality at all — a costlier way to buy accuracy is exactly what this theme's oldest finding predicts, and nothing here rules it out. Add: no small or open-weight arm (Qwen 3.7-Plus is a closed API model), no ablation across the three moving components, one paper, unreplicated. Two smaller items. A push-back on the theme's size story: Weng relays a 2026 study finding harness benefit non-monotonic in model size, peaking at middle-tier models, with harness-updating capability flat from Qwen2-32B to Opus 4.6 (harness-benefit-peaks-at-middle-tier-models). Every measurement behind run 7's "effects are largest on small models" sat at 1.5B–7B — the rising limb of a curve nobody has plotted — so a mid-tier peak is consistent with all of them and implies the opposite build decision. It is a secondhand relay with no methods visible, so it changes our experiment design (put a mid-size arm on the ladder) rather than our conclusion. And an instrument rather than a datapoint: Scale AI's 41-mode taxonomy assigns each agent failure to an edge between model, harness, environment and evaluation instead of blaming one, κ=0.76 against human labels (agent-failures-belong-to-edges-not-components) — the operational form of this theme's entanglement rule, though it reports no census of which edge failures actually land on.
  • 2026-08-02 (run 7) — Stays contested, but the design vs. quantity cut opened in run 6 is now the theme's organising axis rather than a caveat on it, because both halves got evidence on the same night, from opposite directions. On the quantity half, the best-controlled result in this theme to date: seven scaffolding methods compared against plain repeated sampling at each method's own measured token cost, on open models at 1.5B / 3B / 7B, 36 paired comparisons with bootstrap intervals and multiplicity correction. No method beat repeated sampling anywhere; all 18 self-inspection comparisons were negative, Self-Refine and forced Reflexion sat 3.6–10.1 points below baseline at 7B, and Reflexion as published never fired on the smallest model — it judged itself correct every time and silently degenerated to a single chain of thought (self-inspection-harnesses-lose-to-repeated-sampling-at-equal-cost). This confirms harness-iteration-adds-cost-not-quality on far better controls and generalises it from harness evolution to harness machinery. The loops it kills — self-critique, self-selection, reflect-and-retry, debate — are exactly what a default agent SDK ships turned on, which is the sharpest thing this theme has yet said about the default-SDK side of its own question. On the design/presence half, a natural experiment in the wild at frontier scale: identical DeepSeek V4 Flash weights at full precision drew opposite verdicts on basic instruction-following from different practitioners, and the split tracked the scaffold — OpenCode vs Pi vs a bare chat window, over an unowned chat template (open-model-live-use-robustness-is-disputed-and-tracks-the-harness). Harness variance large enough to flip a model's public reputation, with the good outcomes concentrated among people who built a harness. Note the direction of travel across the two: build the scaffold, don't buy the loops. A third item constrains what "default SDK" can be assumed to deliver: five frontier agents, in their shipped harnesses, topped out at 25.3% on realistic oncall root-cause analysis (frontier-agents-top-out-at-25-percent-on-realistic-oncall-rca). Still contested because the strongest evidence remains bounded to verifiable short-answer math (where majority-vote-over-samples is uniquely available) and to forum anecdote, and neither touches the open-ended agentic work the theme's original question is about.
  • 2026-08-01 (run 6) — Stays contested, and the reason to stay is a genuine push-back on the economics-only synthesis that had been consolidating here. Two independent datapoints show harness design moving the quality dimension on small models, not just cost. A pre-registered ablation swung a 4B model 60%→82% (22 points) on a fixed classification task with weights frozen, purely from harness design — explicit rules (+13) and task-before-context (+6.5) (harness-design-is-a-large-quality-lever-on-small-models); and Harness-G lifted small-model retrieval QA by 10.74 F1 at 1.5B / 3.98 at 3B by redesigning the action space, the gain shrinking as the model grew (graph-action-space-harness-lifts-small-model-retrieval). But the ablation also reinforces harness-iteration-adds-cost-not-quality on the other axis: every added stage cost accuracy (extra reasoning turn −5, per-turn context clearing −12, cross-session handoff −15), and the most elaborate harness spent 250 tool calls to reproduce the bare model. So the split sharpens rather than resolves — a well-laid-out harness buys quality; iterating machinery on top of one does not. Neither datapoint is strong enough to move status: the ablation is a single 250-task run (±3pt, greedy decode, self-published) and Harness-G is retrieval-QA-only against one baseline family.
  • 2026-08-01 (run 5) — Stays contested, but the harness presence question this theme kept deferring finally has a controlled answer, and it comes from an unexpected direction: the winning move was to delete the harness. A compiled small model — procedure fine-tuned into the weights, no external orchestration at all — beat LangGraph + Claude Sonnet 4.5 on the hardest procedure's graceful handling and naturalness (p<0.001) and cut failure rates on two of three procedures, while the same-model ablation showed the compiled 3B beating the same 3B base under explicit orchestration on all five criteria (compiled-small-model-nears-frontier-beats-orchestrator). So a default-SDK-style orchestrator was not merely matched, it was outperformed by absorbing the scaffold into the model. Reinforcing the theme's economics reading from a third angle: a tuned 4B execution subagent cut frontier token use 21–32% while resolve rate stayed flat (small-execution-subagent-cuts-frontier-tokens) — again cost, not accuracy. The contest that remains is scope: this is node-graph dialogue work, where a procedure can be compiled, and it tells us nothing about open-ended coding where harness-iteration-adds-cost-not-quality did its measuring.
  • 2026-08-01 (run 4) — The isolation study this theme was waiting for landed, and it favours the economics reading decisively: with the model pinned across 35 sequential harness releases and 3,500 runs, resolve rate showed no significant trend while tokens per task rose ~70% (harness-iteration-adds-cost-not-quality). Method-wise this is now the strongest evidence in the theme, and it rebuts the strong dominance claim (harness-dominates-model-in-performance-variance) on the quality dimension. Scope it honestly: it measures harness evolution (does iterating help?), not harness presence (does a custom harness beat a default SDK?) — the vault's actual question is still the latter, and Harness-Bench's cross-harness comparison stands. Stays contested, but the contest has narrowed: the live question is no longer "does the harness matter" but "does harness work buy anything beyond cost and latency."
  • 2026-08-01 (run 3) — Moved to contested as research came in on both sides. For harness-as-dominant-lever: harness materially changes measured agent performance (agent-performance-is-model-plus-harness, Harness-Bench) and, in its strong form, governs variance more than model choice (harness-dominates-model-in-performance-variance, Binding Constraint Thesis). Against the strong form: harness effect on quality is modest — the big swing is cost/runtime (harness-effect-on-quality-is-modest, BankerToolBench, which rebuts the dominance claim). Emerging synthesis: build a custom harness to win on economics, not necessarily accuracy.
  • 2026-08-01 — Opened. Two angles, both suggestive that the harness is a real lever: automated harness/prompt optimization can lift a small model's task accuracy ~27pp without touching the weights (harness-optimization-lifts-small-model-quality, DSPy/GEPA), and a minimal context-window-first harness may beat heavy defaults (minimal-harness-can-beat-heavy-defaults, Pi/TerminalBench). emerging: promising, but both are best-case/anecdotal and untested on our workflows.

Sub-threads: design vs. quantity has replaced quality vs. cost as the theme's live cut, and after run 7 both halves have direct measurement pointing opposite ways — layout and presence buy accuracy, self-inspection loops cost it, and both effects are largest on small models. The practical form of the finding is now specific enough to act on: build the scaffold, don't buy the loops. A second thread has hardened into a methodological problem the vault has to hold rather than a curiosity — harness variance is large enough to flip a verdict on a model, which entangles this theme's measurements with open-vs-frontier-capability-gap's and means no model comparison in this vault is interpretable without its scaffold named. The combined move has fully forked into combined-small-model-plus-custom-harness, where the compilation evidence lives. Harness absorption — compiling the scaffold into weights rather than building or buying one — still stands open, and run 7 makes it more attractive, since the machinery it replaces is the machinery now shown to cost accuracy. The standing hole named through run 8 — every well-controlled result on verifiable short-answer tasks — is half-closed by run 9: there is now a large open-ended-work result, but it is uncontrolled on the one axis (token cost) that decided the short-answer results, so the hole has moved rather than closed. A third thread opens with it: what the verifier reads. Loops that close against the environment gain; loops that close against the model lose. That reframes "how much scaffolding" as "scaffolding anchored to what," and it is the cheapest thing on this map to test on our own tasks. The size story is now genuinely open — three measurements say harness effects are largest at 1.5B–7B, one relayed study says benefit peaks mid-tier, and nobody has plotted the curve. Run 10 closes the run-9 hole (open-ended work with token cost, twice, independently) and replaces it with a cleaner cut that should now organise the map: designed vs shipped. Designed-ablation results move quality by tens of points; shipped-harness comparisons move cost by multiples and quality by noise. Both cannot be the whole story, and no experiment yet varies design and cost in the same run. A fourth thread opens under what the verifier reads: what the model is used for at all — Zero-Mem's result says the largest available win may be deleting model calls rather than arranging them, which is a different lever from either scaffold layout or verification referent. Run 11 promotes that fourth thread to the map's organising claim, because Prime Agent shows it moving quality and cost together where every other harness result trades them: arranging more model calls buys cost; removing model calls buys both. It also forces a bookkeeping correction the map should apply retroactively — scaffold vs no scaffold (tens of points) and module vs scaffold (single digits) have been read as one quantity and are not, which is most of why the designed-vs-shipped split looked so clean. A fifth thread is now the cheapest actionable one: how the harness gets built. Four independent results say the pruner is an external referent — gold answers, environment state, a measured re-run — and SKILL-KD says the resulting artifact should be small, with 38 validated rules beating 96 unvalidated ones. That is a build procedure we can run on our own workflows this month, with no cluster: log frontier traces where the small model fails, diff, patch, re-run to validate, prune, and grade per task rather than on the mean. The standing hole is unchanged in kind and narrower in scope — the quality half of designed harnesses now has open-ended evidence; the cost half of designed harnesses has none at all, because all three of run 11's sources omit tokens. Run 12 adds a fifth thread and settles one long-running dispute in this map's favour twice over. (e) Who does the designing is now a measurable variable and the dominant one: when an LLM optimises the harness, the optimiser model outweighs the harness it works through by 1.8×, which means the automated version of this map's central activity is bought with model spend rather than framework choice. And the shipped-harness question can be closed — three independent measurements, on three task classes, by three methods, now agree that swapping a shipped harness is quality-neutral, and one of them publishes the noise floor that makes "neutral" a real claim rather than an absence. What replaces it as the live question is calibration of the design lever: run 9's external-referent rule is right about direction and wrong about the binary, since an internally-simulated environment still buys 0.2–3.8 points where a real one buys 5.5–28.9. Carry it as a magnitude estimate — internal referents are cheap and small, external ones are expensive and large — and use it to price scaffolding decisions rather than to sort them into keep and strip. The standing hole is unchanged: nobody has priced a designed harness in dollars. [reviewed 2026-08-07 @ 10 bullets]
