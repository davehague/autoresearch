Does a small/open model plus a custom harness beat frontier plus a default SDK?

The vault's actual question, and until now it had no home. The other themes each measure one lever in isolation — parity measures the model, harness-engineering measures the scaffold, feasibility measures whether we can build it, serving-economics measures what it costs to run. This theme measures the pairing, which is the only configuration anyone would actually deploy.

It is coined deliberately thin. The index has flagged this gap as unmeasured for several runs; giving it a map makes the absence of evidence visible instead of letting it hide inside the harness theme.

Through-line

  • 2026-08-28 (run 32) — Stays contested. Two arrivals, and between them they name a step in this vault's own sentence that nobody had measured and that fails when you do it naively. Fine-tuning the model to your harness overfits your harness. TaoLive trains Qwen3.6-35B-A3B for a production live-commerce agent and publishes the control condition: naive Fixed-Harness SFT buys 9.2 points of task performance and costs 7.7 points of IFEval prompt-level, 5.3 instruction-level, and 4.6 of prompt robustness; then RL inside that same fixed environment drops prompt robustness to 66.7, six points below the untrained base model's 72.8 (fine-tuning-to-a-fixed-harness-costs-77-points-of-instruction-following). The authors' diagnosis is that the model learns "the surface form of a fixed Harness" — literal tool names, literal system prompt, literal skill list. This map has been assuming the two halves of the pairing compose. They interfere. A custom harness is not a fixed object; every rename, prompt rewrite or added skill after training is a silent regression in a model that was tuned to the previous snapshot. It is the same brittleness run 30 found when a quant and a chat template carried an entire benchmark margin (the-quant-and-template-that-carried-the-whole-margin-are-worth-nothing-here) and run 27 found in tool calls flipping on attention backend and KV dtype (the-same-weights-give-different-tool-calls-by-attention-backend) — except this time we would have generated it deliberately, during training. The fix is one extra axis of data generation and it reverses the sign completely. Harness-State Augmentation presents each training task under many semantically equivalent harness surfaces. Fixed SFT loses 4.6 on prompt robustness; HSA-SFT gains 4.5, at slightly better task performance (90.0 against 89.5). Two repair mechanisms are shown to be complementary rather than redundant: General On-Policy Distillation recovers general capability after the damage (+8.5/+5.5 IFEval), HSA prevents it, and only HSA protects the RL stage. The standing rule for anything we build: randomise the harness surface during training, and hold out a harness variant the model never saw as the acceptance test. That names what run 30's load-bearing acceptance test should vary (the-acceptance-test-outweighs-the-diagnosis-and-the-patch-combined). From the other direction, PILOT says the harness half of the pairing is worth 11.8 points before anyone trains anything — five installable harnesses, two frozen open backbones, same 89 Terminal-Bench 2.0 tasks (five-production-harnesses-span-twelve-points-on-one-frozen-open-model) — and that the accumulated-experience loop is worth +14.6 in one harness and +2.3 in another on identical weights and an identical skill library (the-same-experience-loop-pays-146-points-in-one-harness-and-23-in-another). Read with TaoLive, the pairing's build order is now specific and the order matters: harness first (11.8 points, no training), the write/read policy second (12.3 points of spread, no training), model tuning last and only with the harness surface randomised. Discounts: TaoLive's task numbers are its own unreleased rubric evals on its own traffic, its frontier comparators are zero-shot against a model that trained 10K examples on the task, and its ablation caption states the deltas exclude retraining variance; PILOT's winning harness is the authors' own and its self-improvement headline is a maximum over ~14 sweeps (the-self-improvement-headline-is-a-maximum-over-fourteen-sweeps).

The absolute levels on this map's task class remain low — a purpose-tuned Qwen3-8B lands at 16.0% on VitaBench and 36.7% on τ²-Bench (tuned-small-agents-still-fail-most-realistic-tool-tasks) — so the pairing is being optimised inside a band where nothing works well, frontier included. And the pairing's founding evidence was LLM-judged: run 12 showed a leaderboard's grader swap moving scores 3–4 points and reversing a sub-point ordering (grader-model-is-a-fourth-variable-that-has-to-be-pinned), which makes the judge a fourth variable to pin alongside model, harness and precision — retroactively, for the compilation study, and prospectively for anything we run.

  • 2026-08-06 (run 11) — Moves consolidating → contested. The map's central pairing was raced against frontier-plus-a-stock-SDK on open-ended work for the first time, and it lost. Prime Agent — the best-designed harness anyone has published, open-source, with a self-modifiable state and a REPL action space — drove GLM-5.2 (open weights) against Opus 5 in unmodified Claude Code across nine long-context and long-horizon benchmarks, and won 3 of 9, several losses wide: OOLONG 0.700 vs 0.900, OBLIQ 0.669 vs 0.795, LongBenchv2 0.680 vs 0.746, ManyIH Coding 0.424 vs 0.522. Against Codex on GPT-5.6 Sol it won 2 of 9. It beat Pi-mono with sub-agents on 8 of 9, so the harness was doing real work — the model is what ran out (open-weights-in-the-best-harness-still-trail-frontier-in-a-stock-sdk). The wins sort legibly rather than randomly: ManyIH instruction-following, LongCot-Mini, and building an emulator from scratch — long-running work where harness state and programmatic context management carry the load — while the losses cluster on long-context comprehension, where the material has to sit inside the model. That is a usable boundary for this map: a harness can supply structure, memory and verification; it cannot supply the thing that reads 128k tokens well. Status moves because both directions now have evidence on open-ended work, which is what contested means. For the pairing: an open backend in OneDayAgent's harness scores 0.821 on 104 day-long open-ended tasks, above every shipped commercial agent measured (one-harness-generalizes-across-five-backends-without-tuning); Databricks had an open model statistically tied with frontier on real pull requests (open-weight-model-ties-frontier-on-private-uncontaminated-codebase); the compilation study had a small model beating an orchestrated frontier one (compiled-small-model-nears-frontier-beats-orchestrator). Against it: this, on a third task class, in the configuration most favourable to the pairing — since the frontier arm got no harness work at all. Two scoping notes keep it from being decisive. GLM-5.2 is 744B, so "open" here means open weights, not small; the residual it shows is not a size gap and says nothing about a model we could train. And precision is unstated in every arm, making each cell a model/harness/precision confound by run 9's rule. Provenance is a vendor blog with no intervals and no repeats. Thread (c) train through the harness gains a variant that is cheaper than anything else on this map, and it needs no training run at all. SKILL-KD distils the contrast between a student failure and a teacher success into textual skill patches, validates each by re-running the student, and lifts a frozen Qwen3.5-4B from 43.5 to 66.8 average across five agent benchmarks — +56.0 pp on held-out ALFWorld — with weights untouched and cross-family transfer working (ChatGPT-5.5 teaching a Qwen student) (textual-skill-patches-lift-a-frozen-4b-by-23-points). Call it (d) teach through the harness: the teacher's advantage extracted as prompt state, where the prompt state is the harness. The size direction is the useful part — +23.3 on the 4B against +16.7 on the 35B-A3B — a fourth direct measurement putting harness effects largest at small scale, against one relayed study claiming a mid-tier peak. Two cautions before booking it as free quality: nothing prices the teacher trajectories or the repeated re-runs, and the resulting 3,010-word library rides on every inference as a standing context tax; and the baselines are other skill-induction methods, not a fine-tuned student, so this does not show text beating weights.

  • 2026-08-05 (run 10) — Stays consolidating. Two of the map's three open items move, and the harness-absorption thread gets its first general-purpose instance. Liquid AI shipped a 2.6B model whose final post-training stage is multi-turn agentic RL run through real agent harnesses (GRPO), and its strongest results against a 3.5×-larger model are exactly the harness-adjacent skills — Multi-IF 80.07 vs 62.55, IFBench 59.17 vs 56.47, ToolSandbox 77.83 vs 76.44 — while it loses on code generation, 59.41 vs 69.86 (small-model-trained-through-its-harness-leads-on-instruction-following). Until now absorption rested on one controlled study of node-graph dialogue procedures (compiled-small-model-nears-frontier-beats-orchestrator). This is a downloadable, general-purpose model from a real vendor doing the same thing on open-ended agent work, which makes the third configuration of the vault's question concrete: not small model plus custom harness, but small model trained against the harness it will run in. No ablation across four post-training stages, all numbers vendor-reported against unscaffolded comparators, so it makes the hypothesis attractive rather than demonstrating it — but it is the shape most worth copying, because we would be training against our harness on our tasks, which is precisely the arrangement this map exists to evaluate. Second, the run 9 caveat that blocked the harness half from counting is resolved, and it resolves in the map's favour on economics and against it on quality. Two independent studies on real work now pin the model and vary only the harness with cost measured: Databricks on private multi-million-line-codebase pull requests (>2× cost per task, quality unchanged; 742,000 vs 236,999 tokens of context per task) and Composio on an open model across six harnesses (3.7× cost spread, ~6× median token spread, 17–21/26 success) (harness-swap-moves-cost-not-quality-on-real-engineering-tasks, harness-cost-spread-replicates-on-an-open-model). Read against this map's founding result — the pairing wins on cost by 128–462× and loses on quality by 2–13% — the new evidence says the harness half of that split is mostly a cost lever when harnesses are compared as shipped, which means the map's open question ("how much of the 2–13% quality gap is design?") should not expect an answer from harness selection. It has to come from harness design, and that is where every large quality effect in the vault actually lives. Third, and cutting for the pairing: Databricks also found an open-weight model statistically tied with the best frontier model on those same tasks at two-thirds the cost per task (open-weight-model-ties-frontier-on-private-uncontaminated-codebase). If that holds, the model half of the pairing's quality deficit is smaller on real engineering work than the map's node-graph evidence implies. Still consolidating and not stronger, because the binding limitation is untouched: no study yet pairs a small or open model with a purpose-built harness on open-ended work and prices both. Every arm exists separately now; nobody has run them together.

  • 2026-08-04 (run 9) — Stays consolidating. The binding limitation this map has carried since run 5 — everything supporting the pairing is node-graph work; nobody has run this on open-ended coding or agentic tasks — gets its first real crack, but only on the harness half. LongHorizon-Harness lifts agents 5.5–28.9 points on WeaveBench, Terminal-Bench 2.1 and OSWorld 2.0 by moving task state outside the context and auditing it against the environment (external-task-state-lifts-long-horizon-agents). That is open-ended agentic work, and a harness lever paying off on it is the precondition for the pairing being worth attempting there at all. But there is no small or open-weight arm — Qwen 3.7-Plus is a closed API model, Opus 4.7 is frontier — so this map's actual pairing is still untested outside node graphs. What it does change is the prior: the limitation was "harness engineering may not survive contact with unbounded tasks," and on the harness side it evidently does. The mechanism carries a design instruction for the pairing specifically. Run 7 established that generic scaffolding damages the small model most (self-judgement-penalty-is-largest-on-the-smallest-models), and the new reading says why: self-referential loops have no external anchor, and the weaker the model the worse its self-judgement (environment-verification-succeeds-where-self-inspection-fails). Environment-anchored verification does not have that property — the auditor's reliability comes from the world, not from the model being audited — so it is the one class of scaffolding that should not degrade as we shrink the model. If that holds, it is a direct attack on this map's open question, how much of the 2–13% quality gap is design? One qualification pulls back: harness-benefit-peaks-at-middle-tier-models relays that harness benefit may peak at mid-size rather than rising monotonically as models shrink, which would mean the pairing's best model is not the smallest one that fits.

  • 2026-08-03 (run 8) — Stays consolidating; a light secondary touch that echoes this map's split answer on a real workflow. On enterprise document extraction, a purpose-built agent beat commercial frontier VLMs and matched general coding agents on quality while costing a fraction as much, with the frontier models failing specifically on long-document completeness (purpose-built-extraction-agent-matches-frontier-at-fraction-of-cost). Same shape as this map's founding result — the specialized-system-plus-purpose-built-scaffold wins on cost and holds quality against frontier-plus-default. It is not a clean pairing datapoint (the "small model" is a vendor agentic system, not a disclosed fine-tuned checkpoint, and there is no prompt-optimized frontier arm), and it is on extraction rather than the node-graph or coding work this map cares about — so it firms up the economics half of the pattern without touching the binding limitation, which is unchanged: still no evidence on open-ended coding.

  • 2026-08-02 (run 7) — Stays consolidating; a secondary touch that firms up what kind of harness the pairing should use, without adding a datapoint on the pairing itself. The token-cost-matched scaffolding experiment found no self-inspection method beating plain repeated sampling at equal cost on 1.5B–7B models, with all 18 self-inspection comparisons negative (self-inspection-harnesses-lose-to-repeated-sampling-at-equal-cost). Read against this map's founding result — that the winning move was to delete the harness and compile the procedure into the weights (compiled-small-model-nears-frontier-beats-orchestrator) — the two agree from opposite ends: absorbing the scaffold beats orchestrating it, and the orchestration machinery that gets absorbed is machinery independently shown to cost accuracy. That is a mildly stronger case for the harness-absorption route than this map had. One qualification pulls the other way, and it matters for the pairing specifically. The self-judgement penalty is largest at the small end — 8.0–11.3 points at 1.5B against 2.0–1.3 at 7B (self-judgement-penalty-is-largest-on-the-smallest-models) — so the small model in our pairing is the one most damaged by generic scaffolding and most dependent on getting the scaffold right. The pairing's quality deficit against frontier in-context (87–98% on the compiled study) is therefore partly a design variable rather than a fixed capability tax. Neither datapoint touches this map's binding limitation, which is unchanged: everything supporting the pairing is still node-graph work, and the new evidence is verifiable short-answer math — if anything a narrower task class, not a broader one.

  • 2026-08-01 (run 5) — Moved emerging → consolidating. The controlled study this map was created to wait for exists. A compiled Qwen2.5-3B / Qwen3-8B — the procedure fine-tuned into the weights rather than orchestrated around them — was raced against LangGraph + Claude Sonnet 4.5 and against in-context Claude Sonnet 4.5 on three procedures of increasing complexity, n=200 per condition, two judges (compiled-small-model-nears-frontier-beats-orchestrator). It beat the orchestrated frontier outright on the hardest procedure's graceful handling and naturalness (p<0.001) and cut failure rates on two of three, while costing 128–462× less (compilation-cost-advantage-grows-with-procedure-complexity). The load-bearing control is the same-model ablation — compiled 3B beat the same 3B base under explicit orchestration on all five criteria — which finally separates the compilation lever from the model-size lever, the exact confound that made the Faros datapoint unusable. A second, independent datapoint agrees from a different architecture: a tuned 4B execution subagent cut a frontier main agent's tokens 21–32% with resolve rate flat or slightly up (small-execution-subagent-cuts-frontier-tokens). Why consolidating rather than contested: the new evidence does not conflict, it converges — and on a split answer. The pairing wins decisively on economics and still loses, narrowly, on quality (frontier in-context takes every quality column on every procedure; the compiled model reaches 87–98%). That is the same shape as harness-iteration-adds-cost-not-quality found in the harness theme, arrived at independently, which is why the tension flagged in run 4 now looks resolved rather than live. Not consensus: outcomes are LLM-judged synthetic dialogue, all three procedures are node-graph workflows (the most compilable class of work), and nobody has run this on open-ended coding.

  • 2026-08-01 (run 4) — Opened with a single weak datapoint, and emerging overstates it slightly. A vendor engineering post reports that over 211 real engineering tasks, open models (GLM-5.2, Kimi K2.6) with a highly optimized harness reached the top quality band, matching or beating Opus 4.8 and GPT-5.5 (open-model-plus-optimized-harness-reaches-frontier-band). Direction is right, evidence is thin: no success rates, no cost figures, no methodology, proprietary framework, commercial interest. It also sits in tension with harness-iteration-adds-cost-not-quality, which found harness work quality-neutral under controlled conditions — plausibly because Faros varies model routing together with the harness, conflating exactly the two levers this theme exists to separate. Treat as a hypothesis to test on our own workflows.

Sub-threads: the map's founding premise — that the controlled study does not exist — is retired. Two threads replace it. (a) Where the pairing wins: a cost advantage that grows with procedure complexity, against a quality deficit that shrinks with model size but never closes. (b) The third configuration: Terminus-4B is neither pole of the vault's question but a frontier planner with tuned small specialists underneath, and it is the arrangement most like what we would actually ship. That hybrid deserves its own map if a second datapoint lands. Run 7 sharpens (a): the quality side of the split is not a fixed capability tax, since the scaffolding choices that most damage a small model are ones we control — which makes "how much of the 2–13% quality gap is design?" the map's most decision-useful open question. Run 9 gives that question a testable mechanism — environment-anchored verification should not degrade with model size the way self-referential loops do — and narrows the binding limitation from "no evidence on open-ended work" to "no evidence on open-ended work with a small model in the loop." That is now the single experiment that would move this map. Run 10 adds a third thread and it may be the most transferable: (c) train through the harness — optimise the model against the scaffold it will run in, rather than building a scaffold around a fixed model or compiling the scaffold away entirely. It sits between absorption and pairing, it is now instanced by a shipped general-purpose model, and it is the only configuration here we could reproduce end to end on our own cluster and our own tasks. Run 10 also constrains thread (a): with harness selection now measured as a cost lever on real work, the quality half of the 2–13% split has to be attacked through harness design, not by shopping for a better SDK. Run 11 moves the map to contested and reshapes (a) around a boundary rather than a magnitude: the pairing's wins are on long-running work (instruction-following under many instructions, long chain-of-thought, building an artifact over hours) and its losses are on long-context work, so the question is no longer "how big is the quality deficit" but which half of our workflows is which. That is answerable by inspection of our own tasks, before any experiment. Thread (c) gains a sibling worth tracking separately — (d) teach through the harness, the frozen-weights version, where a teacher's advantage becomes validated prompt state. It is the only configuration on this map reproducible in a week rather than a quarter, its effect is largest at the smallest size, and its costs are entirely unmeasured. The binding limitation from run 9 is now half-answered and half-worse: harness engineering does survive contact with open-ended work with an open model in the loop, and it still does not close the gap to frontier there. The one experiment that would move this map is unchanged in shape and cheaper in form — a small model, our harness, our tasks, priced per completed task, with a prompt-optimised frontier comparator rather than a stock one. Run 12 does not run it and makes it cheaper to specify. Threads (c) and (d) merge into a single build order — library → teacher → distil → ship weights with an empty prompt — which retires the question of whether text competes with weights by putting the text upstream of them. Thread (a) gains a fifth pinned variable: the founding result was LLM-judged, and a grader swap is now demonstrably worth several times the margins this map argues over, so model, harness, precision and judge all have to be fixed before a number here means anything. And the experiment's success criterion should change with it. This map has been asking which side wins; the levels say both sides fail most realistic multi-turn tool tasks, so the question worth spending a cluster run on is which configuration clears our bar on our workflows, at what cost per completed task, under a price we control — a threshold test rather than a race.
