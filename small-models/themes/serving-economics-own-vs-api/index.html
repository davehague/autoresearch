Serving economics — is running your own actually cheaper?

The half of the decision the model-quality debate ignores: even if a small model is good enough, does self-hosting it on our cluster actually beat paying per API token? Decided in the serving stack, not the leaderboard.

Through-line

  • 2026-08-13 (run 17) — Stays contested. Three arrivals, and the first one breaks the framing this map has been resting on since run 12. The build side is not the stable pole. Run 12 gave the buy side a price variance — DeepSeek warning of a "significant" increase with no figure and no date (open-model-api-prices-are-not-a-stable-planning-input) — and the structural argument we drew was that the cost of running an open checkpoint on hardware we control did not move; the cost of buying access to one moved on a vendor's unilateral notice. That argument does not survive this week. NVIDIA's RTX PRO 6000 Blackwell (96 GB GDDR7) went $8,565 (April 2025 retail listing) → $13,250 (June 2026) → $16,000 (August 2026): 87% above launch, 20.8% of it in two months, driven by memory rather than silicon — 96 GB across 32 GDDR7 modules, so every component-cost move is multiplied by 32 (the-hardware-side-of-buy-vs-build-took-an-87-percent-price-increase). Behind it, a market larger than one SKU: conventional DRAM contract prices ~93–98% QoQ in Q1 2026 (PC DRAM 105–110%, a record), 58–63% more expected in Q2, server 64 GB RDIMM $450 → $900+ in one quarter, and HBM capacity for 2026 sold out with DRAM lines redirected to it. Three consequences. (1) Amortize the cluster we have; do not model a purchase. Every self-hosting estimate on this map implicitly prices expansion at historical rates, and the capacity a frontier-class open checkpoint needs is memory — the exploding input. Run 7's ~45% tokens-per-dollar swing from whether a checkpoint fits one node (accelerator-memory-capacity-swings-self-hosting-economics) now turns on a threshold that costs 87% more per unit. (2) The planning object is a spread with two moving ends, not a break-even point — two unilateral moves in nine weeks, one on each side, neither a stable denominator. That is a direct argument for the deployment run 16 reached from the other direction: routing, where the fraction of calls on the expensive path is the dial we control (cross-model-escalation-routes-7-percent-of-calls-and-cuts-74-percent-of-cost). A fraction survives both prices moving; a build-versus-buy verdict does not. (3) Every memory-efficiency lever on this map converts to dollars at a rate that just rose 87% — DCP's 3.3× concurrency on 82% of the cache (kv-cache-layout-buys-33x-throughput-with-no-quality-spent), expert pruning at 711 GB → 478 GB (expert-pruning-is-a-second-unlabelled-shrink-axis), QAT buying a cache rung at flat quality. They stop being optimizations and become hedges. It is trade press and analyst contract estimates on a workstation SKU, not measurement on our hardware; the extension to datacenter accelerators is our inference. Thread (d), precision — an upstream variable the pin-list was missing. A KLD sweep of two Gemma 4 31B Q4_0 checkpoints differing only in quantization-aware training finds the QAT build 20.3× lower mean KLD at Q8_0 cache (0.015078 vs 0.305575), 9.7× at Q4_0, 3.9× at Q2_0 — and, practically, QAT at Q4 cache (0.0905 / 86.3% same-top) beats non-QAT at Q8 cache (0.3056 / 85.1%) using 940 MiB less cache (qat-checkpoints-tolerate-cache-quantization-twenty-times-better). So cache-quantization tolerance is a property of the training recipe, not the bit width, and QAT-or-not joins hash, quant recipe, expert count, GPU and engine version on the identity list (the-quant-label-is-not-a-spec, the-same-quant-file-scores-differently-on-different-gpus) — the entry most likely to differ silently between a vendor release and a community requant. It also unsettles run 13's ordering: the weights-versus-cache split is not stable per model, only per artifact. Two cautions carry over unchanged — no task benchmarks at all in a domain where compression takes tool use and instruction-following first (compression-degrades-agentic-skills-more-than-reasoning), and both arms are Q4_0 weights, so neither is measured against the original model (the-lossless-baseline-was-farther-from-the-original-than-a-3-bit-quant). Thread (a), the bill — a memory system's cost is generated by its own behaviour. Benchmarking Mem0, Hindsight and Mastra Observational Memory against a rolling window and full-transcript resubmission over 400-turn conversations, a fitted cost model predicts the baselines to 2.9–6.5% and the memory systems to 18–22% / 46–48% / 41–69% (memory-system-cost-is-set-by-internal-behaviour-not-conversation-length). That is run 14's cache-read finding in a subsystem: a memory system is a context-admission policy, so a cost estimate built from conversation length measures a different quantity, exactly as a per-token rate does. Note which systems are illegible — the LLM-authored ones, because the illegibility is the extra model calls; deterministic-memory-beats-llm-authored-memory-at-zero-token-cost gets a cost-side confirmation. Two riders. Break-even against no memory at all ranges from turn 0 to never across configurations of the same code (break-even-against-no-memory-at-all-ranges-from-turn-zero-to-never) — so for much of the operating range the correct memory architecture is none — and accuracy spans 21–54%, a fifth leg for the levels complaint. And the cost ranking inverts with the backbone (Mem0 is 3.1× Mastra on gpt-oss-20b, 0.63× on Gemma 4): a cross term, not a variable, which means a memory system benchmarked on one model says nothing about its cost on another. Small preprint, two open-weight backbones, one reseller, conversation-QA rather than our workload — the absolute dollars transfer nowhere and the structure transfers cleanly.

  • 2026-08-12 (run 16) — Stays contested. Three arrivals across three of this map's threads, and the sharpest one is a defect in the map's own instrument. Thread (d), precision — the yardstick was wrong. This map's cheapest screen is KL divergence against the full-precision original, at r = −0.981 against long-tail knowledge loss (quantization-erases-long-tail-knowledge-invisibly), plotted on a linear axis (quantization-damage-is-a-cliff-that-log-scale-metrics-hide). Both presume the reference is the original. A quantizer converting DeepSeek V4 Flash 0731 from the original safetensors found llama.cpp's converter hard-codes an FP8 → Q8_0 downconversion that puts the output 0.219 mean KLD from the original before any quantization begins — while their own 118 GB three-bit quant measures 0.2065 (the-lossless-baseline-was-farther-from-the-original-than-a-3-bit-quant). The default "lossless" 162 GB artifact was farther from the model than a 3-bit compression of it, and fixing it required replacing tensors with BF16 at source. Run this screen against a default-converted base and the numbers are not noisy, they are centred on the wrong point, and the worst quants look best. Verify the reference bit-exact before trusting the instrument. Published rungs against the corrected base: BF16 162.1 GB / PPL 4.5289 / KLD 0; IQ2_M 104.0 GB / 4.8822 / 0.2567; IQ1_M 70.2 GB / 6.3813 / 0.5641. A seventh pin, and it is the most mundane on the list. The same publisher abandoned cross-publisher comparison because the same GGUF file measures 4.5381 PPL on a 5090 and 4.3406 on an H100 — llama.cpp's MXFP4 fast path engages only on consumer Blackwell (the-same-quant-file-scores-differently-on-different-gpus). A 0.2 PPL swing on an identical artifact exceeds several quant rungs' separation. Record the GPU and engine version beside model, harness, precision, grader, effort, endpoint and router operating point. This also offers an alternative partial explanation for two disputes already booked to build and harness — the-quant-label-is-not-a-spec and open-model-live-use-robustness-is-disputed-and-tracks-the-harness — without overturning either. One reframing worth promoting out of the footnotes: on MI300X, decode throughput was flat at 36.92–37.75 tok/s across a 1.4× file-size range — compute-bound, not memory-bound — so a smaller quant buys VRAM headroom, not speed, which makes precision a fit decision rather than a cost-per-token one. The cost unit gets its first mechanism. cache-reads-dominate-an-agentic-token-bill measured 98% of an agentic token bill as cache reads; harness-and-cache-tuning-halved-generated-tokens-in-production reported a near-50% cut with no mechanism given. A context-pruning study now finds that which pipeline stage you prune at matters more than how you score what to cut (where-you-prune-matters-more-than-how-you-score), and the reason is the missing mechanism: context admitted early is re-read every subsequent turn, so it is the cache-read mass, and early pruning removes a term multiplied by turn count. Pruning decisions and cache hit rate are one instrument seen from two ends. The caution is real and cuts the other way — reordering or removing context invalidates caches, and cache reads are priced far below fresh input, so the instruction is prune early, append-only, and measure the four-way split per completed task before and after. Which raises the priority of the one item here that is arithmetic rather than research (three-quarters-of-enterprises-cannot-see-their-agent-bill). And the buy side gets a fourth deployment shape, treated on the harness map but priced here: escalating 7% of calls to a frontier model cut 74% of a production bill for 6% of accuracy (cross-model-escalation-routes-7-percent-of-calls-and-cuts-74-percent-of-cost). That is a better trade than any single-model swap on this ledger, better than open-model-trades-seven-points-for-61-percent-of-the-bill — and it still leaves a frontier model on someone else's API at a price they set (open-model-api-prices-are-not-a-stable-planning-input). Routing lowers exposure to the price variance; it does not remove it.

Nominal precision does not predict it — Nebius at FP4 reads 100, DeepInfra at FP4 reads 73 — and neither does price or speed. This is thread (d) precision arriving on the buy side, and it is worse there than locally because nothing is disclosed. Run 13's rule was identity by build, not by label (the-quant-label-is-not-a-spec), written for artifacts we download and can hash. Behind an endpoint there is no hash, no obligation to announce a requantization, and a quarter of the model's accuracy at stake. It also puts a real price on this map's largest named lever: 40–60% from switching to a cheaper open-model API (switching-to-cheaper-models-is-the-largest-named-coding-cost-lever) was booked as infrastructure-free money, and at the bottom of this table part of that saving is paid in accuracy — on tool calling and long-context recall, two of the three components, and the same capabilities compression takes first (compression-degrades-agentic-skills-more-than-reasoning). Cost per completed task now needs the endpoint and the date named beside the model. The quieter finding should change how this map argues. The yardstick is a self-hosted deployment, defined as 100% (self-hosting-is-the-reference-every-api-is-measured-against). This map has carried self-hosting as the expensive option that must justify itself against an API price; in the only instrument that measures both, it is the definition of correct and buying is the thing with the error bar. That changes nothing about our utilization or our marginal engineer cost — but it adds a term buy-vs-build has never had, and it is thread (g) transposed from price to quality: the model you buy is defined by a stack you cannot inspect and that can change without notice. Thread (g) asked whether running our own is cheaper at an acceptable spread; the spread turns out to exist on both axes, and only on the buy side. Alongside it, the market-scale version of this map's accounting problem. KPMG's Global AI Pulse (Q2 2026, 2,145 leaders across 20 countries) reports 49% scaled back agent deployments because cost exceeded benefit, against 79% still naming AI a top priority and flat $188M average spend — but the numbers to keep are only 26% having real-time cost visibility and 33% naming token-pricing comprehension as a barrier (three-quarters-of-enterprises-cannot-see-their-agent-bill). Set against run 14's finding that 98% of an agentic token bill is cache reads (cache-reads-dominate-an-agentic-token-bill), that third of the market is not confused about a simple thing — an agentic bill genuinely is not legible from a headline rate. It promotes run 14's action item from hygiene to prerequisite: instrument the four-way token split per completed task, which is arithmetic we can do this week and is evidently what half the market lacks before it can decide anything. Do not read the pullback as an argument for building: every cancellation here is of an API bill, and every ranked remedy needs no infrastructure. Grade it weakly — vendor survey, executive self-report, secondhand, and KPMG sells the advisory work that follows. One item arrives from the routing side and cuts toward buying. LLMRouter reports learned routers beating the strongest fixed model by ~14.6% relative by sending many queries to smaller cheaper models (routing-across-models-is-learnable-routing-a-model-across-itself-is-not), which is the independent quality half Databricks' 30%+ gateway claim never had — and unlike run 14's routing result, this one routes across a heterogeneous model pool rather than across one agent's own configurations. Cheap-model routing is a real lever on the buy side and it does not require us to own anything.

Every other entry on this map is paid for somewhere — quantization in unmeasured capability, expert pruning in the domain you kept, a cheaper API in a vendor's unilateral price dial. This is ~3.3× at bit-identical weights and bit-identical cache. It also patches a hole in our own arithmetic: this map's utilization assumption (published ~70%, realistic 35–45%) was formed with no KV-cache-layout term in it, and the baseline here idles compute because memory ran out — low realized utilization as an implementation choice rather than a property of the workload. Since self-hosting-savings-erased-below-engineer-scale-thresholds turns on volume, 3.3× in achievable concurrency moves the break-even directly. Hardware caveat is load-bearing: high-bandwidth interconnect is a stated requirement, so the honest question is what fraction survives on the cluster we have, and speculative decoding is currently unsupported so the two levers do not stack. The token bill has a term we have never entered, and it dominates. The public Harbor job behind this run's Terminal-Bench reproduction publishes its usage in full: roughly 3.34B total tokens — 3.28B cached, 27M prompt, 38.9M output. Cache reads are 98% of the volume (cache-reads-dominate-an-agentic-token-bill). Run 10's unit stands and needs specifying: cost per completed task, decomposed into cache-read, cache-write, prompt and output, because a harness change moves the mix, which is the mechanical explanation for why the same model costs 2–3.7× more through a different scaffold. Run 13's rule extends unchanged: identity by build, not by label — hash, quant recipe and expert count — and the linear-axis KLD screen applies to pruning as-is and would settle this in an afternoon.   • 2026-08-08 (run 13) — Stays contested, and for the first time the map gets a ranked ledger of levers from inside a production bill rather than a benchmark. Databricks published its coding-cost playbook with four levers and the saving each produced — directional, from an informal survey — open-source / lower-cost models 40–60%, dynamic request and task routing 30%+, reducing token overhead 20–40%, developer visibility and budgets 10–20% — plus two measured internal figures: its gateway router cuts average task cost >30% while "roughly matching the quality of the most expensive model," and simple tuning of harness and caching settings produced an almost 50% reduction in generated tokens (switching-to-cheaper-models-is-the-largest-named-coding-cost-lever). The framing is a split between an intelligence frontier and an efficiency frontier — "the set of models that have the best price point for a given level of intelligence" — with the claim that most daily coding does not need the former. Read carefully, the biggest row raises the bar on our own case rather than supporting it. 40–60% prices buying a cheaper model's API — GLM through a vendor endpoint, rolled out internally on price/performance — not running one on hardware we own. So the first half of an agentic coding bill is available with no infrastructure at all, and any self-hosting proposal has to beat the open-model API price, not the frontier one. That is a harder target than self-hosting-savings-erased-below-engineer-scale-thresholds was built against. Run 12's thread (g) is the counterweight and the two together are the actual position: switching models captures the largest immediate saving and carries the only unhedged price risk on the board (open-model-api-prices-are-not-a-stable-planning-input). One incidental item deserves promotion out of the footnotes — Databricks reports cost regressions from Opus 5.0 versus 4.8, and Stripe found Opus 4.7 no better than 4.6 and declined to deploy it. This map has been modelling the frontier as a monotonically rising bar; two production reports say a newer release can cost more for no measured quality gain, so the bar is not only lower than leaderboards imply but not reliably rising in the dimension we would pay for. Discount all of it appropriately: the Databricks table is practitioner consensus written down by a company selling the routing infrastructure it credits, and the quantization work is one author, one model, one wikitext corpus, grading distributional fidelity rather than any task.   • 2026-08-05 (run 10) — Stays contested; the precision lever opened in run 9 gets itemized, and the itemization changes what it costs us. Run 9 established that compression buys ~30% per token and charges the bill to long-tail factual recall, in a currency benchmarks do not report. Syzygy's Mach-1 Additive — Qwen3.6-35B-A3B compressed to 1.7 bits per weight with multiplication-free inference, ~7GB, up to 120 tok/s on a laptop — publishes a per-benchmark retention table rather than a mean, and the table shows the loss is not spread evenly across capabilities. It sorts almost perfectly by distance from a closed-form answer: AIME26 99.5%, MATH-500 99.4%, GSM8K 98.4%, MBPP+ 98.3%, HumanEval+ 97.4%, MMLU-Redux 96.2%, IFEval 94.0%, MuSR 92.7%, BFCL-v3 92.0%, τ²-bench 90.0%, IFBench 83.2% (compression-degrades-agentic-skills-more-than-reasoning). The headline "95.0% mean retention" is carried by competition math; the casualties are instruction-following (−10.9pp) and agentic tool use (−7.9pp, −6.0pp) — which is to say, the model's ability to be an agent. A checkpoint keeping 99.5% of its AIME score and 83.2% of its IFBench score has not lost 5% of itself; it has lost the part we would deploy. That is the same phenomenon as quantization-erases-long-tail-knowledge-invisibly extended from obscure facts to agentic skill, and it makes operator-quantization-cuts-cost-at-benchmark-parity's "within 0.8 points across benchmarks" unusable as a quality claim for our purposes — not by inference this time, but demonstrably, because this vendor happened to report agentic benchmarks in the same table as math and the gap is visible inside one artifact. Keep the absolute numbers in view too: τ²-bench 71.58 and BFCL-v3 68.97 are still usable, so the compressed model is not broken, it is systematically worse at exactly the target capability. Operational consequence, and it is the concrete output of this thread: any compression we run gets evaluated agentically, on our own tasks, before and after. A benchmark mean is now provably the wrong instrument. Alongside it, a claim worth an afternoon of verification rather than belief — under 15 GPU hours of retraining to compress a 35B, said to scale to 3T (retrofit-compression-claims-15-gpu-hours). If true, precision stops being a one-way commitment and becomes a knob we can sweep cheaply enough to evaluate each setting properly, which is precisely what the finding above demands. A second, smaller item on a different lever: Databricks priced real engineering tasks per task rather than per token — GLM 5.2 $1.28, Opus 4.8 $1.94, Sonnet 5 $2.09, with Sonnet consuming 1.9× more tokens than Opus despite a cheaper per-token rate (open-weight-model-ties-frontier-on-private-uncontaminated-codebase). That inversion is the clearest illustration this map has that per-token price ranks models wrongly, and the same study's harness result adds the other multiplier: 742,000 vs 236,999 tokens of context per task for the same model, harness alone (harness-swap-moves-cost-not-quality-on-real-engineering-tasks). Status unchanged for the sixth run running, and for the same reason: none of this touches our real utilization or our marginal engineer cost. Discount both sources as vendor material — a model card with no independent evaluation, no error bars and no ablation separating bit width from retraining recipe, and a company blog with no results table.

  • 2026-08-04 (run 9) — Stays contested; a fifth lever enters, and unlike the other four it is not a cost term at all but a quality term that every cost estimate here has been silently spending. The lever is numerical precision, and two sources landed on it the same day from opposite sides. From the operator side, Cloudflare serving Kimi and GLM in production: FP8 KV cache halves the cache, lifting Kimi K2.6's resident context from ~686k to ~1.37M tokens at +41% peak throughput and under 1% accuracy variance; INT4 weights shrink GLM 5.2 from 705 GB to 421 GB and per-GPU memory from 88 to 52 GB, at +55%/+16% throughput by concurrency and quality "within 0.8 points across benchmarks" — netting roughly 30% lower cost per token (operator-quantization-cuts-cost-at-benchmark-parity). The KV-cache half is genuinely new here and it interlocks with run 7's hardware-fit finding: that one was about squeezing weights into one node's memory, this is the cache competing for the same budget, and halving it roughly doubles resident context — the exact constraint long agentic loops hit. Two independent knobs, both converting precision into batch size. From the measurement side, the same-week result that makes the operator's quality number unsafe to reuse. Across 58 quantizations of Qwen3.6 27B against a 1,400-question probe stratified into 7 obscurity tiers, factual knowledge degrades non-linearly — flat above ~5-bit, dropping at 3-bit, sharp at 2-bit — while the same author's same ladder measured on AIME-120 and Terminal-Bench 2.1 showed no cliff above 4-bit at all (quantization-erases-long-tail-knowledge-invisibly). Reasoning survives compression; long-tail recall does not; and "within 0.8 points across benchmarks" is measured on exactly the probes that cannot see it. These two do not cancel — they compose into the theme's most actionable pairing yet: quantization buys ~30% per token and the bill is charged to factual recall, in a currency your benchmarks do not report. The payoff is a cheap instrument: knowledge loss tracks KL divergence from the BF16 original at r = −0.981, so a candidate quantization can be screened against a sample of our own traffic without running any knowledge benchmark. Status unchanged, for the same reason as the last two runs: this sharpens how cheap and at what hidden cost, and touches neither of the two numbers that would settle the theme — our real utilization (Cloudflare states none) and our marginal engineer cost. Discount both sources as vendor-adjacent: a commercially interested operator blog with an unnamed eval suite on one side, a single self-published author on one model with no replication on the other.

  • 2026-08-03 (run 8) — Stays contested; a fourth cost lever enters, and it sits one layer below the three already here — the software footprint. Every priced analysis in this theme prices GPU-hours, utilization, hardware fit; none prices the deployment stack, which is what actually decides whether a small model runs on constrained or heterogeneous hardware. A custom C++ inference engine reportedly matches vLLM throughput within ~1% at a 66 MiB binary versus a 9.1 GiB Python virtualenv, with companion ports cutting memory ~5× (inference-engine-footprint-is-a-self-hosting-lever). The throughput-parity claim is what makes it load-bearing — it removes the usual objection that a smaller engine costs tokens/sec — and it lands on the cheap-small-model self-hosting case specifically, the same case the compiled-model economics already favor. Discount for source: a vendor blog (LocalAI) with its own benchmarks and an obvious interest, so the exact ratios are illustrative; the throughput-parity-at-tiny-footprint claim is falsifiable and is the one to carry. Doesn't move status — it sharpens how cheap self-hosting a small model can get without touching the two numbers that would settle the theme (our real utilization, our marginal engineer cost).

  • 2026-08-02 (run 7) — Stays contested; a third variable enters, and it interacts with the two already here. The theme had split its dispute by which model you host; this adds which accelerator you host it on. Serving the 2.8T open-weight Kimi K3 in TP8, MI355X measured 952 tok/s/node against a B300 delivering ~1.65× more aggregate throughput — but at $2.50/GPU-hour versus $6.00, the slower part wins the economics: 48 tokens/sec per dollar-of-GPU-hour versus 33, roughly a 45% advantage (accelerator-memory-capacity-swings-self-hosting-economics). The mechanism is capacity, not compute: 288 GB VRAM lets the checkpoint fit in one node, where the comparison part needs multi-node, so the cross-node communication disappears. That makes it a threshold effect rather than a vendor result — a model 20% larger, or a long-context configuration with a bigger KV cache, pushes you back multi-node and plausibly inverts it. Planning consequence: match accelerator memory to checkpoint size and the cross-node overhead becomes margin; carry an implicit NVIDIA assumption into a cost-per-token estimate and it can be wrong by ~45% before utilization is even considered. Discount it accordingly — a single vendor-adjacent blog post with a commercial interest, author-chosen list prices (the TCO term most sensitive to contract and region), and one fixed 1,024-in/400-out shape that flatters aggregate throughput relative to long-context agentic traffic. Most tellingly it states no utilization assumption at all, which is the term run 5's four-term analysis found decisive; 48 tok/s per dollar-hour at full utilization is a different number entirely at the realistic 35–45%. The ratio is informative, the absolute is marketing. Status unchanged because this sharpens our estimate without touching the two numbers that would actually settle it — our real utilization and our marginal engineer cost.

  • 2026-08-01 (run 5) — Moved emerging → contested, and the dispute turns out to be about which model you host, not about self-hosting. For: compiling a procedure into a 3–8B model cut per-conversation cost 128–462× vs frontier in-context, with the advantage growing with procedure complexity because the compiled prompt is constant-size while an orchestrated one scales with the node graph (compilation-cost-advantage-grows-with-procedure-complexity). Against: a full four-term TCO model puts the break-even for frontier-class open weights at ~600M tok/mo (code) or ~1.2B (chat), and only with a dedicated inference engineer — below that the API wins by up to 30× (self-hosting-savings-erased-below-engineer-scale-thresholds, which rebuts the unqualified form of self-hosted-serving-throughput-cuts-cost). These reconcile rather than cancel: a compiled 3–8B and a self-hosted 70B+ are different economic objects, and the per-token gap (~65×) is only half the story next to token volume. Three numbers from the pushback side should reshape any estimate we build: realistic utilization is 35–45%, not the ~70% back-of-envelope models assume, once you size for P99 tail latency; the inference engineer is 25–30% of TCO and does not amortise; and every frontier update costs 1–2 weeks of engineering every 4–8 weeks, so the open ecosystem's pace is a recurring tax, not pure upside. Our own threshold is plausibly lower than the published one — the analysis assumes hiring an engineer, and we already staff a cluster — which makes this the one theme where the decisive number is ours to compute rather than to find.

  • 2026-08-01 — Opened. Serving throughput on open models is improving fast — speculative decoding, MoE optimizations (~2.2k tok/s/H200), low-bit quantization — which pushes self-hosting economics in our favour (self-hosted-serving-throughput-cuts-cost). emerging: one vendor-blog source; the real number can only come from a throughput/cost test on our own hardware.

Sub-threads: two, and they should not be merged. (a) Small compiled models — economics are overwhelming and get better with task complexity. (b) Frontier-class open weights at scale — economics are marginal, volume-gated, and dominated by headcount and utilization. Most published "self-hosting is cheaper" claims silently pick one and generalise to both. Run 7 adds a cross-cutting one: (c) the hardware fit, which is not a third case so much as a multiplier on the other two — a checkpoint that fits in one node's memory is a different economic object from the same checkpoint spread across two, and the boundary is a memory threshold we can design around rather than a vendor loyalty. Run 9 adds (d) precision, which is different in kind from the rest and should be tracked separately: it is the only lever here that buys cost by spending quality, and the quality it spends is invisible in the evaluations an operator would run. Every self-hosting plan on this map implicitly quantizes — that is how a frontier-class checkpoint fits affordable hardware at all — so this is a bill the theme has been running up without an entry for it. Run 10 gives (d) its shape: the quality precision spends is not uniform across capabilities, and it is spent most heavily on instruction-following and tool use — the agentic skills — while leaving math and code nearly intact, which is why a mean retention figure flatters it. Track this thread by capability, never by average. A fifth is now worth naming separately: the accounting unit. Two independent measurements this run show per-token pricing ranking things wrongly — a cheaper-per-token model costing more per task, and the same model costing 2–3.7× more per task through a different harness — so every estimate on this map should be built in cost-per-task from here. The latent thread is unchanged and still the most valuable: total cost including curation and training, which no source has yet priced end to end. Run 11 gives the accounting-unit thread its first real table — four model/harness pairings priced per completed task on the same uncontaminated enterprise work — and the shape it reveals should change what this map optimises: the quality/cost curve is convex enough that the interesting choice is between open options, not between open and frontier. It also adds a caveat the unit itself cannot fix: a cost-per-task figure is only a model measurement if the harness is pinned, and GDPevo's is not. Worth stating plainly as thread (f): quality and cost only trade off when the intervention is more model calls. Two independent results this run — a better-informed agent costing less, and a designed harness scoring higher on fewer tokens — show interventions that move both together, which means the frontier framing this map inherited is a special case rather than the rule. Run 12 opens thread (g) price risk, not price level — the variable this map has never modelled. Every number it holds is a point estimate against a rate set by someone else, and one of those rates just acquired a stated 2–10× of headroom overnight. The buy-vs-build comparison is therefore not two costs but a cost against a cost plus a variance, and the variance only appears on one side. That reframes the map's whole question: it has been asking whether running our own is cheaper, and the sharper question is whether it is cheaper at an acceptable spread, which a sunk cluster and staffed engineers answer far better than they answer the first. The one experiment that would settle it is now small enough to schedule — a week of rented GPUs, our real request mix, cost per completed task against the API bill for identical work — and it tests the rented-parity claim and the price-risk thesis in the same run. Run 15 forces one revision to thread (g) and one to thread (d), and they are the same revision seen twice. (g) was scoped to price and should be scoped to terms. A 27-point accuracy spread across endpoints serving one open checkpoint means the buy side carries a variance on quality as well as on price, undisclosed and unhashable, so the comparison is not two costs but a cost against a cost-plus-two-variances. (d) precision is no longer only a knob we turn; it is also a knob a vendor turns on our behalf without telling us, which is why nominal precision fails to predict endpoint accuracy. The operational form is one line and it should be attached to every measurement this map holds from here: pin the endpoint and the date, or the model is not identified. And the rented-GPU experiment gains a second output for free — running the official weights ourselves is, per the only published instrument, the 100% reference, so the same week of rented capacity produces both our cost baseline and our accuracy baseline.
