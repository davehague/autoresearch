Serving economics — is running your own actually cheaper?

The half of the decision the model-quality debate ignores: even if a small model is good enough, does self-hosting it on our cluster actually beat paying per API token? Decided in the serving stack, not the leaderboard.

Through-line

  • 2026-08-08 (run 13) — Stays contested, and for the first time the map gets a ranked ledger of levers from inside a production bill rather than a benchmark. Databricks published its coding-cost playbook with four levers and the saving each produced — directional, from an informal survey — open-source / lower-cost models 40–60%, dynamic request and task routing 30%+, reducing token overhead 20–40%, developer visibility and budgets 10–20% — plus two measured internal figures: its gateway router cuts average task cost >30% while "roughly matching the quality of the most expensive model," and simple tuning of harness and caching settings produced an almost 50% reduction in generated tokens (switching-to-cheaper-models-is-the-largest-named-coding-cost-lever). The framing is a split between an intelligence frontier and an efficiency frontier — "the set of models that have the best price point for a given level of intelligence" — with the claim that most daily coding does not need the former. Read carefully, the biggest row raises the bar on our own case rather than supporting it. 40–60% prices buying a cheaper model's API — GLM through a vendor endpoint, rolled out internally on price/performance — not running one on hardware we own. So the first half of an agentic coding bill is available with no infrastructure at all, and any self-hosting proposal has to beat the open-model API price, not the frontier one. That is a harder target than self-hosting-savings-erased-below-engineer-scale-thresholds was built against. Run 12's thread (g) is the counterweight and the two together are the actual position: switching models captures the largest immediate saving and carries the only unhedged price risk on the board (open-model-api-prices-are-not-a-stable-planning-input). One incidental item deserves promotion out of the footnotes — Databricks reports cost regressions from Opus 5.0 versus 4.8, and Stripe found Opus 4.7 no better than 4.6 and declined to deploy it. This map has been modelling the frontier as a monotonically rising bar; two production reports say a newer release can cost more for no measured quality gain, so the bar is not only lower than leaderboards imply but not reliably rising in the dimension we would pay for. Thread (d) precision gets an independent measurement and a correction to how its instrument is read. An outside sweep of LFM2.5-2.6B across model quants × KV-cache quants found mean KLD moving 0.0037 → 0.0114 → 0.0755 → 0.1892 down four rungs — a 51× spread concentrated in the last two — and states plainly that log-scale KLD and Top-1% accuracy convert that cliff into a slope (quantization-damage-is-a-cliff-that-log-scale-metrics-hide). Run 9's r = −0.981 screen survives intact and gains a usage note: plot it linearly, or the screen hides exactly what it exists to catch. This is the same defect class the vault has traced through curation, the distillation objective, the RL objective and skill-library drift, now appearing in a chart axis — and it is the cheapest instance to avoid on the whole ledger. Two secondary results are directly actionable. Model precision degrades faster than cache precision on this model, inverting the ordering Cloudflare reached at frontier MoE scale (operator-quantization-cuts-cost-at-benchmark-parity) — both can hold, since weights dominate memory at 700B and not at 2.6B, so the weights-versus-cache split is a knob to sweep per model rather than a rule to inherit, at a cost of one afternoon. And abliteration is a flat ~0.075 KLD tax at every rung, paid whether or not you quantize. The sharper item is a provenance requirement this map did not have. Q4_K_M was non-monotonic in three of four independent GGUF builds of the same model and clean in the fourth (the-quant-label-is-not-a-spec). Since run 9 the rule has been "name the precision alongside the harness"; that is now insufficient, because two artifacts with the same nominal bit width differ by more than the label predicts and one of them is defective. Pin precision by build — publisher, file, imatrix — the way we would pin a grader version. Retroactively it supplies a second uncontrolled variable for open-model-live-use-robustness-is-disputed-and-tracks-the-harness, where practitioners running nominally identical open weights disagreed on basic rule-following and the disagreement was attributed to harness alone. Discount all of it appropriately: the Databricks table is practitioner consensus written down by a company selling the routing infrastructure it credits, and the quantization work is one author, one model, one wikitext corpus, grading distributional fidelity rather than any task. Status unchanged for the eighth run running, and for the unchanged reason — none of this touches our real utilization or our marginal engineer cost. [reviewed 2026-08-08 @ 8 bullets]
  • 2026-08-07 (run 12) — Stays contested, and the caveat run 11 booked against its own best table became the news. DeepSeek told developers it will raise API prices "significantly", with no figure and no date; founder Jun Song's public framing is that even after a 2–10× rise it would still undercut most Western APIs. Current V4 Flash list is $0.14/M cache-miss input, $0.0028/M cache-hit, $0.28/M output; V4 Pro $0.435 / $0.003625 / $0.87. Context is capacity rather than margin — V4 Flash processed 8 trillion tokens on 2026-08-01 — and no official reason was published (open-model-api-prices-are-not-a-stable-planning-input). The direct casualty is this map's most quoted curve. GDPevo put DeepSeek-V4-Pro-Preview at 48.79% for $0.040 per completed task against Opus-4.8's 67.07% for $1.36, which is where "18.28 points buys 97% of the bill" came from (open-model-trades-seven-points-for-61-percent-of-the-bill). At the top of the announced envelope that row lands near $0.40 and the 34× convexity story flattens into something ordinary. Nothing about the model changed; the rent did. The structural reading outlasts the specific number and it is the first argument for building that does not depend on beating an API on unit cost: the cost of running an open checkpoint on hardware we control did not move this week, while the cost of buying access to one moved by an unspecified multiple on a vendor's unilateral notice. Run 10's instruction to rebuild every estimate in cost per completed task therefore needs a second axis — under a price we set, versus one we do not — and the second axis is not a number but a variance. Carry the limit honestly: "significant" is not a measurement, 2–10× is a founder's aside rather than a schedule, and the increase could land at the bottom of the range or be dropped. What is established is that this input is not a constant, and this map had been modelling it as one. Alongside it, the weakest-graded item on this map and the only outside break-even estimate it has ever held. dax of OpenCode stated his team matched DeepSeek's current API pricing using rented GPUs, reading the hike as traffic shaping on overloaded infrastructure rather than a correction to loss-making prices (rented-gpus-reportedly-match-the-cheapest-open-api-rate). If it holds it attacks the break-even from below, because rented GPUs are the cheapest possible version of running it yourself — no capex, no cluster, no procurement — and our configuration is strictly more favourable than that, with the cluster sunk and the engineers already staffed. Against self-hosting-savings-erased-below-engineer-scale-thresholds that is a direct contradiction at the bottom of the scale. But it is one person's summary in a forum thread: no model size, no hardware, no utilization, no token volume, no window, no arithmetic, and mildly self-interested. It is a lead, not evidence — and the reproduction is cheap, ours, and needs no cluster: rent one GPU class for a week, serve one open checkpoint at our real request mix, compute cost per completed task against the API bill for identical work. That single measurement would replace three of the assumptions currently propping up this map.
  • 2026-08-06 (run 11) — Stays contested, but run 10's instruction to rebuild this map in cost per completed task stops being arithmetic we have to do ourselves — GDPevo publishes the table, across four model/harness pairings, on 120 held-out enterprise-workflow tasks (CRM, ERP, finance, healthcare, legal, data) built so test-time gains are attributable rather than memorised: Opus-4.8 / Claude Code 67.07% at $1.36; GPT-5.5 / Codex 64.51% at $1.02; GLM-5.2 / Claude Code 60.09% at $0.53; DeepSeek-V4-Pro-Preview / Claude Code 48.79% at $0.040 (open-model-trades-seven-points-for-61-percent-of-the-bill). The curve is steeply convex and steeper than any per-token price sheet implies: 6.98 points buys a 61% cut, 18.28 points buys 97% — $0.040 against $1.36 is a 34× ratio. Two consequences for how this map should be read. First, the live decision is not open-vs-frontier at all; it is which open option, since the interesting trade sits between GLM-5.2 and DeepSeek-V4, not between either and Opus. Second, one row breaks the frontier framing entirely: GPT-5.5 gained 15.14 points while its cost per task fell from $1.29 to $1.02, because a better-informed agent flounders less. Spend that reduces flailing is not on the quality/cost frontier — the same non-tradeoff Prime Agent reports from the harness side (designed-harness-lifts-score-and-cuts-tokens-together), and a reminder that this map's axes are only orthogonal when the intervention is more model calls. Set against the vault's other decontaminated measurement, this cuts the other way and that is the useful part. Databricks found an open model statistically tied with frontier on real pull requests at $1.28 vs $1.94; GDPevo, also contamination-resistant and also externally graded, finds a real 7-point gap at a much larger discount. Run 10's reframed question — which reported gaps survive removing benchmark contamination — gets an early answer of some do. Discount it on the control this map cares most about: harness is not pinned across all four rows. GPT-5.5 runs in Codex, the other three in Claude Code, and given the 2–3.7× per-task cost spread harnesses alone produce (harness-cost-spread-replicates-on-an-open-model), some of the visible cost difference is scaffold rather than model. The accessible tables show a single supervision type for both open models, so their baselines must be inferred. No intervals, no repeats, n=120, precision unstated. And the prices are API list rates — this prices buying an open model, not running one, so it informs thread (b) and leaves the self-hosting question where it was.
  • 2026-08-05 (run 10) — Stays contested; the precision lever opened in run 9 gets itemized, and the itemization changes what it costs us. Run 9 established that compression buys ~30% per token and charges the bill to long-tail factual recall, in a currency benchmarks do not report. Syzygy's Mach-1 Additive — Qwen3.6-35B-A3B compressed to 1.7 bits per weight with multiplication-free inference, ~7GB, up to 120 tok/s on a laptop — publishes a per-benchmark retention table rather than a mean, and the table shows the loss is not spread evenly across capabilities. It sorts almost perfectly by distance from a closed-form answer: AIME26 99.5%, MATH-500 99.4%, GSM8K 98.4%, MBPP+ 98.3%, HumanEval+ 97.4%, MMLU-Redux 96.2%, IFEval 94.0%, MuSR 92.7%, BFCL-v3 92.0%, τ²-bench 90.0%, IFBench 83.2% (compression-degrades-agentic-skills-more-than-reasoning). The headline "95.0% mean retention" is carried by competition math; the casualties are instruction-following (−10.9pp) and agentic tool use (−7.9pp, −6.0pp) — which is to say, the model's ability to be an agent. A checkpoint keeping 99.5% of its AIME score and 83.2% of its IFBench score has not lost 5% of itself; it has lost the part we would deploy. That is the same phenomenon as quantization-erases-long-tail-knowledge-invisibly extended from obscure facts to agentic skill, and it makes operator-quantization-cuts-cost-at-benchmark-parity's "within 0.8 points across benchmarks" unusable as a quality claim for our purposes — not by inference this time, but demonstrably, because this vendor happened to report agentic benchmarks in the same table as math and the gap is visible inside one artifact. Keep the absolute numbers in view too: τ²-bench 71.58 and BFCL-v3 68.97 are still usable, so the compressed model is not broken, it is systematically worse at exactly the target capability. Operational consequence, and it is the concrete output of this thread: any compression we run gets evaluated agentically, on our own tasks, before and after. A benchmark mean is now provably the wrong instrument. Alongside it, a claim worth an afternoon of verification rather than belief — under 15 GPU hours of retraining to compress a 35B, said to scale to 3T (retrofit-compression-claims-15-gpu-hours). If true, precision stops being a one-way commitment and becomes a knob we can sweep cheaply enough to evaluate each setting properly, which is precisely what the finding above demands. A second, smaller item on a different lever: Databricks priced real engineering tasks per task rather than per token — GLM 5.2 $1.28, Opus 4.8 $1.94, Sonnet 5 $2.09, with Sonnet consuming 1.9× more tokens than Opus despite a cheaper per-token rate (open-weight-model-ties-frontier-on-private-uncontaminated-codebase). That inversion is the clearest illustration this map has that per-token price ranks models wrongly, and the same study's harness result adds the other multiplier: 742,000 vs 236,999 tokens of context per task for the same model, harness alone (harness-swap-moves-cost-not-quality-on-real-engineering-tasks). Status unchanged for the sixth run running, and for the same reason: none of this touches our real utilization or our marginal engineer cost. Discount both sources as vendor material — a model card with no independent evaluation, no error bars and no ablation separating bit width from retraining recipe, and a company blog with no results table.
  • 2026-08-04 (run 9) — Stays contested; a fifth lever enters, and unlike the other four it is not a cost term at all but a quality term that every cost estimate here has been silently spending. The lever is numerical precision, and two sources landed on it the same day from opposite sides. From the operator side, Cloudflare serving Kimi and GLM in production: FP8 KV cache halves the cache, lifting Kimi K2.6's resident context from ~686k to ~1.37M tokens at +41% peak throughput and under 1% accuracy variance; INT4 weights shrink GLM 5.2 from 705 GB to 421 GB and per-GPU memory from 88 to 52 GB, at +55%/+16% throughput by concurrency and quality "within 0.8 points across benchmarks" — netting roughly 30% lower cost per token (operator-quantization-cuts-cost-at-benchmark-parity). The KV-cache half is genuinely new here and it interlocks with run 7's hardware-fit finding: that one was about squeezing weights into one node's memory, this is the cache competing for the same budget, and halving it roughly doubles resident context — the exact constraint long agentic loops hit. Two independent knobs, both converting precision into batch size. From the measurement side, the same-week result that makes the operator's quality number unsafe to reuse. Across 58 quantizations of Qwen3.6 27B against a 1,400-question probe stratified into 7 obscurity tiers, factual knowledge degrades non-linearly — flat above ~5-bit, dropping at 3-bit, sharp at 2-bit — while the same author's same ladder measured on AIME-120 and Terminal-Bench 2.1 showed no cliff above 4-bit at all (quantization-erases-long-tail-knowledge-invisibly). Reasoning survives compression; long-tail recall does not; and "within 0.8 points across benchmarks" is measured on exactly the probes that cannot see it. These two do not cancel — they compose into the theme's most actionable pairing yet: quantization buys ~30% per token and the bill is charged to factual recall, in a currency your benchmarks do not report. The payoff is a cheap instrument: knowledge loss tracks KL divergence from the BF16 original at r = −0.981, so a candidate quantization can be screened against a sample of our own traffic without running any knowledge benchmark. Status unchanged, for the same reason as the last two runs: this sharpens how cheap and at what hidden cost, and touches neither of the two numbers that would settle the theme — our real utilization (Cloudflare states none) and our marginal engineer cost. Discount both sources as vendor-adjacent: a commercially interested operator blog with an unnamed eval suite on one side, a single self-published author on one model with no replication on the other.
  • 2026-08-03 (run 8) — Stays contested; a fourth cost lever enters, and it sits one layer below the three already here — the software footprint. Every priced analysis in this theme prices GPU-hours, utilization, hardware fit; none prices the deployment stack, which is what actually decides whether a small model runs on constrained or heterogeneous hardware. A custom C++ inference engine reportedly matches vLLM throughput within ~1% at a 66 MiB binary versus a 9.1 GiB Python virtualenv, with companion ports cutting memory ~5× (inference-engine-footprint-is-a-self-hosting-lever). The throughput-parity claim is what makes it load-bearing — it removes the usual objection that a smaller engine costs tokens/sec — and it lands on the cheap-small-model self-hosting case specifically, the same case the compiled-model economics already favor. Discount for source: a vendor blog (LocalAI) with its own benchmarks and an obvious interest, so the exact ratios are illustrative; the throughput-parity-at-tiny-footprint claim is falsifiable and is the one to carry. Doesn't move status — it sharpens how cheap self-hosting a small model can get without touching the two numbers that would settle the theme (our real utilization, our marginal engineer cost).
  • 2026-08-02 (run 7) — Stays contested; a third variable enters, and it interacts with the two already here. The theme had split its dispute by which model you host; this adds which accelerator you host it on. Serving the 2.8T open-weight Kimi K3 in TP8, MI355X measured 952 tok/s/node against a B300 delivering ~1.65× more aggregate throughput — but at $2.50/GPU-hour versus $6.00, the slower part wins the economics: 48 tokens/sec per dollar-of-GPU-hour versus 33, roughly a 45% advantage (accelerator-memory-capacity-swings-self-hosting-economics). The mechanism is capacity, not compute: 288 GB VRAM lets the checkpoint fit in one node, where the comparison part needs multi-node, so the cross-node communication disappears. That makes it a threshold effect rather than a vendor result — a model 20% larger, or a long-context configuration with a bigger KV cache, pushes you back multi-node and plausibly inverts it. Planning consequence: match accelerator memory to checkpoint size and the cross-node overhead becomes margin; carry an implicit NVIDIA assumption into a cost-per-token estimate and it can be wrong by ~45% before utilization is even considered. Discount it accordingly — a single vendor-adjacent blog post with a commercial interest, author-chosen list prices (the TCO term most sensitive to contract and region), and one fixed 1,024-in/400-out shape that flatters aggregate throughput relative to long-context agentic traffic. Most tellingly it states no utilization assumption at all, which is the term run 5's four-term analysis found decisive; 48 tok/s per dollar-hour at full utilization is a different number entirely at the realistic 35–45%. The ratio is informative, the absolute is marketing. Status unchanged because this sharpens our estimate without touching the two numbers that would actually settle it — our real utilization and our marginal engineer cost.
  • 2026-08-01 (run 5) — Moved emerging → contested, and the dispute turns out to be about which model you host, not about self-hosting. For: compiling a procedure into a 3–8B model cut per-conversation cost 128–462× vs frontier in-context, with the advantage growing with procedure complexity because the compiled prompt is constant-size while an orchestrated one scales with the node graph (compilation-cost-advantage-grows-with-procedure-complexity). Against: a full four-term TCO model puts the break-even for frontier-class open weights at ~600M tok/mo (code) or ~1.2B (chat), and only with a dedicated inference engineer — below that the API wins by up to 30× (self-hosting-savings-erased-below-engineer-scale-thresholds, which rebuts the unqualified form of self-hosted-serving-throughput-cuts-cost). These reconcile rather than cancel: a compiled 3–8B and a self-hosted 70B+ are different economic objects, and the per-token gap (~65×) is only half the story next to token volume. Three numbers from the pushback side should reshape any estimate we build: realistic utilization is 35–45%, not the ~70% back-of-envelope models assume, once you size for P99 tail latency; the inference engineer is 25–30% of TCO and does not amortise; and every frontier update costs 1–2 weeks of engineering every 4–8 weeks, so the open ecosystem's pace is a recurring tax, not pure upside. Our own threshold is plausibly lower than the published one — the analysis assumes hiring an engineer, and we already staff a cluster — which makes this the one theme where the decisive number is ours to compute rather than to find.
  • 2026-08-01 — Opened. Serving throughput on open models is improving fast — speculative decoding, MoE optimizations (~2.2k tok/s/H200), low-bit quantization — which pushes self-hosting economics in our favour (self-hosted-serving-throughput-cuts-cost). emerging: one vendor-blog source; the real number can only come from a throughput/cost test on our own hardware.

Sub-threads: two, and they should not be merged. (a) Small compiled models — economics are overwhelming and get better with task complexity. (b) Frontier-class open weights at scale — economics are marginal, volume-gated, and dominated by headcount and utilization. Most published "self-hosting is cheaper" claims silently pick one and generalise to both. Run 7 adds a cross-cutting one: (c) the hardware fit, which is not a third case so much as a multiplier on the other two — a checkpoint that fits in one node's memory is a different economic object from the same checkpoint spread across two, and the boundary is a memory threshold we can design around rather than a vendor loyalty. Run 9 adds (d) precision, which is different in kind from the rest and should be tracked separately: it is the only lever here that buys cost by spending quality, and the quality it spends is invisible in the evaluations an operator would run. Every self-hosting plan on this map implicitly quantizes — that is how a frontier-class checkpoint fits affordable hardware at all — so this is a bill the theme has been running up without an entry for it. Run 10 gives (d) its shape: the quality precision spends is not uniform across capabilities, and it is spent most heavily on instruction-following and tool use — the agentic skills — while leaving math and code nearly intact, which is why a mean retention figure flatters it. Track this thread by capability, never by average. A fifth is now worth naming separately: the accounting unit. Two independent measurements this run show per-token pricing ranking things wrongly — a cheaper-per-token model costing more per task, and the same model costing 2–3.7× more per task through a different harness — so every estimate on this map should be built in cost-per-task from here. The latent thread is unchanged and still the most valuable: total cost including curation and training, which no source has yet priced end to end. Run 11 gives the accounting-unit thread its first real table — four model/harness pairings priced per completed task on the same uncontaminated enterprise work — and the shape it reveals should change what this map optimises: the quality/cost curve is convex enough that the interesting choice is between open options, not between open and frontier. It also adds a caveat the unit itself cannot fix: a cost-per-task figure is only a model measurement if the harness is pinned, and GDPevo's is not. Worth stating plainly as thread (f): quality and cost only trade off when the intervention is more model calls. Two independent results this run — a better-informed agent costing less, and a designed harness scoring higher on fewer tokens — show interventions that move both together, which means the frontier framing this map inherited is a special case rather than the rule. Run 12 opens thread (g) price risk, not price level — the variable this map has never modelled. Every number it holds is a point estimate against a rate set by someone else, and one of those rates just acquired a stated 2–10× of headroom overnight. The buy-vs-build comparison is therefore not two costs but a cost against a cost plus a variance, and the variance only appears on one side. That reframes the map's whole question: it has been asking whether running our own is cheaper, and the sharper question is whether it is cheaper at an acceptable spread, which a sunk cluster and staffed engineers answer far better than they answer the first. The one experiment that would settle it is now small enough to schedule — a week of rented GPUs, our real request mix, cost per completed task against the API bill for identical work — and it tests the rented-parity claim and the price-risk thesis in the same run.
