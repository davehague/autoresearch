Find it before you fix it: the retrieval stage nobody was scoring

As of 2026-08, the evidence on getting repository context into a coding agent has a shape that took a month to become visible, and it is not the shape the tooling market assumes.

The assumption is that this is a ranking problem — that agents fail because the retriever surfaces the wrong files, and that a better retriever fixes it. Every measurement below says the ranking is a smaller term than it looks, that the losses are spread across four separate stages between "the repository" and "the model's working set," and that the single largest recovered gain in the whole map came from a system that did not touch retrieval at all.

This is a young map, forked out of context engineering on 2026-08-02 because the parent's discipline — persist the contract, deliver it, re-deliver it at the decision it governs — assumes the right material already arrived. Every finding here is that assumption failing.

The pipeline, and where each stage loses

Four stages sit between a repository and what the model reasons over. Each has now been measured separately, and each loses independently of the others.

1. Acquisition — does the agent ever touch the file? On a quarter to a third of tasks, no. Against repositories frozen at the pre-resolution base commit (427 samples, 25 repositories, 391,932 files, with gold-path, raw-patch, fix-commit and generated-artifact leakage all verified at zero), logged trajectories from real agents with real search and read tools never touch any required file on 35.2% of samples for one strict-context agent and 27.2–29.3% for two Codex configurations [T1] (Agent Retrieval Bench). The reassuring "median first hit at step 2" statistic is conditional on eventually hitting.

2. Ranking — which candidates come back? No family wins. Semantic embeddings take MRR, a vectorless structural repo map takes budgeted context yield, a 0.5B model takes review-comment context, and the aggregate ranking reverses when repositories rather than samples are weighted equally. A training-free rank fusion of a semantic and a structural ranker beats both of its inputs [T1] (same source). Retrieval and interaction are also two surfaces, not one: static retrieval finds files the agent never touches on 12.5–17.8% of samples, and browsing finds files the retriever misses on 7.7–22.0%. Installing a retriever does not close the second gap.

3. Selection — what survives into the input? This is the stage nobody scores, and it loses more than most of the interventions the field argues about gain. On 16,490 RepoBench tasks from 2,798 repositories, required cross-file evidence enters the retriever's top five for 64.16% of tasks and survives complete inside a 4,096-token budget for 39.59% — a 24.57-point loss located entirely after ranking [T1] (VITAL-RAG). The mechanism is authority multiplication: an index exposes the body, signature, call site and test fragment of one code object, each competes for a slot as a separate result, and the independent helper the task needed gets clipped.

4. Structure and disclosure — how is the corpus packaged? Conditionally valuable, and only above a scale threshold (below).

What is settled enough to act on

Deduplicate on provenance identity, not on text. Exact deduplication moves evidence survival by 0.02 points. Canonical grouping, per-file quotas and MMR all reach ~64% candidate recall while leaving survival pinned between 39.41% and 39.59% — a row of controls that fail identically, which is what makes selection a distinct stage rather than a diversity problem. Quotienting views by canonical code object and then allocating tokens per object raises survival to 63.67% at 35.63% fewer tokens with the candidate set held fixed [T1] (VITAL-RAG).

A bigger window is not the fix. Survival saturates by 4K; 8K adds 0.01 points [T1] (same source). Buy the quotient, not the context length.

Measure localization at span granularity, not file granularity. A file-level hit is document reachability. Median gold file: 515 lines. Median useful evidence inside it: 27 lines (4.7%). Every method's line F1 is under 0.03, and the ranking between methods changes at span granularity [T1] (Agent Retrieval Bench). A retriever comparison scored on file hits is not measuring what the agent experiences.

A structural index beats grep, and costs less. A codebase index combining vector embeddings, a graph of definitions and call edges, and BM25 lexical, built over live source, lifts localization acc@5 44.3% → 84.5% (p<0.0001) and resolve 41.9% → 50.4% (p=0.003) against index-off, at a lower dollar-per-solve ($2.30 vs $2.92) because it wastes fewer turns [T1, suggestive] (Code Isn't Memory). The payoff concentrates on multi-file changes, so the value is workload-dependent by the authors' own framing.

Compact deterministically, not with a summarization model. Materializing lexical, dense and structural views per commit, handing the agent candidates carrying re-resolvable source addresses, and compacting via a one-time deterministic history rewrite cuts trajectory tokens 50–87% across five models while preserving AnswerRecall@5 within ε = 0.05 at a 95% confidence lower bound [T1] (CodeNib). The efficiency framing matters: the saving is stated conditional on preserving localization, so it is not a quality trade wearing efficiency's label.

One level of progressive disclosure. Never two. Holding the chunk set and descriptions identical and varying only the wiring, a second routing level — every chunk its own skill with an always-loaded description plus a meta-router — never helps and sometimes destroys accuracy (En.MC 0.9126 → 0.6398; Zh.QA 0.7479 → 0.3890) [T1] (Is Progressive Disclosure All You Need?). The mechanism is self-inflicted: the always-loaded child descriptions saturate the router's context before it commits to a chunk, recreating the exact pressure disclosure exists to relieve. Package a long document as one skill with a single in-skill index, and treat the instinct to add a routing layer when retrieval underperforms as usually backwards.

Packaged structure is a scale lever, not an accuracy lever. Same study: on a single document, the pack lifts harnesses that navigate raw text poorly and adds nothing to one whose bare agent already greps for the entities a question names. At twenty documents that same agent can no longer find the right file and the pack pulls 1.7× ahead (En.QA 0.257 → 0.462) [T1, suggestive]. The harness's own search ability is a named term in every result on this map. Report it, or your numbers do not transfer.

Judge scope before gathering, not after. Every other reduction technique here is reactive — prune, summarize, compact what was already pulled in. Estimating required scope first and expanding only on verification failure is an earlier lever with a metric attached (redundancy ratio against an oracle minimum). Carried with its arms separated: −85% cost / −91% tokens at equal success in a deterministic simulator, but only −18% tokens against a read-everything agent on live gpt-4o at case-study scale [T1, suggestive]. The durable part holds in both arms and is not about tokens: over-provisioned context costs reliability — the thorough agent lost 3/3 runs on the hardest tier where the scoped one held 93%.

The result that reframes the map

Everything above optimizes what arrives. As of 2026-08-03 the largest measured gain on this map does something else: it refuses to let the agent act until it has looked.

ECLoop compiles a per-task evidence specification from the issue text plus repository structure — conditions naming what must be observed before a class of commitment action may proceed ("inspect the callers of the function you are about to edit"; "check the available tests before submitting"). Reads, searches and diagnostics run unrestricted. Edits and submissions are held while their action-specific evidence gap is non-empty, with the unmet conditions returned as guidance. All four significant under an exact McNemar test on the 500 paired outcomes (p < 0.001), and token use falls 1.4–12.1% in every cell [T1] (ECLoop). Retrieval is not improved at all.

Three details in that system generalize past it.

Satisfaction is decided deterministically, never from the model's claim. An LLM proposes candidate conditions; each is then grounded against the AST, call graph and class hierarchy, and dropped if it cannot be resolved to a checkable entity. Matching runs against recorded trajectory events — what was viewed, searched, executed. A bad specification can only lose coverage; it cannot introduce a check the system is unable to evaluate.

The structure is load-bearing, and this is the sharpest measurement of that anywhere in the vault. Replacing the machine-checkable specification with an equivalent natural-language summary of what to investigate scores 58 against the full system's 68 — and against 63 for supplying no guidance at all. Identical content, identical context window; the only difference is whether satisfaction can be mechanically decided, and that difference is ten points.

It has to sit before the commitment. The Self-Refine control — three rounds of the model reviewing and revising its own patch, comparable extra inference — goes negative on both models (−1.4, −1.8 pp). Same budget, opposite sign. A decision taken without an observation is not repairable by a review that also lacks it.

What is still open

Almost nothing here is scored on repair. This was the map's own founding complaint and it is only half-answered. VITAL-RAG, CodeNib, the structural index and the disclosure work report retrieval survival, token savings, localization and recall. ECLoop is the first source in the map to report a resolve rate on the same axis — and it is one group, one benchmark, one language, one task type, with a single run per configuration and no seed variance or intervals. Treat +11.8 as a direction, not a number to plan around.

The gate's blocking variant is unmeasured. ECLoop holds an action at most three times per commitment target, then releases it through an audited fallback. Every regression in the paper traces to that fallback. Nobody has run the version that refuses.

Issue quality is an unpriced input. The evidence specification is compiled from the issue description, and SWE-bench Verified issues are human-validated and well-specified. That is not the condition on a real tracker. The authors name a preceding clarification step as the fix and do not run it.

The gains shrink as baselines strengthen. Across the four cells, both the accuracy gain and the token saving track how weak the baseline was — 12.1% token reduction at a 56.2% baseline against 1.4% at 74.8%. Both models were chosen mid-tier to permit full-benchmark runs. What this buys on a frontier configuration is unmeasured, and the trend line does not favour it.

Contamination applies to all of it. Every resolve-rate number on this map lives on SWE-bench, where retrieval-time leakage inflates scores and this vault carries the warning as standing.

The short version

As of 2026-08:

  1. Assume the agent will not find the file. A quarter to a third of the time, it does not [T1].
  2. Make it look before it may edit. The only intervention on this map that has moved a repair outcome gates the commitment on observed evidence, and it pays for itself in tokens [T1].
  3. Decide satisfaction from the trajectory, not from the model's report. Ground every condition against real repository structure and drop what cannot be checked [T1].
  4. Structure your guidance so a machine can decide it. The same content as prose is worse than silence [T1].
  5. Deduplicate on provenance, quotient by code object, and stop buying window size [T1].
  6. Measure spans, not files — and report your harness's own search ability, because it conditions every number here [T1].
  7. Add one level of disclosure. Never two [T1].
  8. Do not read a token saving as a capability claim. Most of this map still measures cost.
