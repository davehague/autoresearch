Find it before you fix it: the retrieval stage nobody was scoring

As of 2026-09, the evidence on getting repository context into a coding agent has a shape that took over a month to become visible, and it is not the shape the tooling market assumes.

The assumption is that this is a ranking problem — that agents fail because the retriever surfaces the wrong files, and that a better retriever fixes it. Every measurement below says the ranking is a smaller term than it looks, that the losses are spread across four separate stages between "the repository" and "the model's working set," and that the single largest recovered gain in the whole map came from a system that did not touch retrieval at all.

This is a young map, forked out of context engineering on 2026-08-02 because the parent's discipline — persist the contract, deliver it, re-deliver it at the decision it governs — assumes the right material already arrived. Every finding here is that assumption failing.

The pipeline, and where each stage loses

Four stages sit between a repository and what the model reasons over. Each has now been measured separately, and each loses independently of the others.

1. Acquisition — does the agent ever touch the file? On a quarter to a third of tasks, no. Against repositories frozen at the pre-resolution base commit (427 samples, 25 repositories, 391,932 files, with gold-path, raw-patch, fix-commit and generated-artifact leakage all verified at zero), logged trajectories from real agents with real search and read tools never touch any required file on 35.2% of samples for one strict-context agent and 27.2–29.3% for two Codex configurations [T1] (Agent Retrieval Bench). The reassuring "median first hit at step 2" statistic is conditional on eventually hitting.

2. Ranking — which candidates come back? No family wins. Semantic embeddings take MRR, a vectorless structural repo map takes budgeted context yield, a 0.5B model takes review-comment context, and the aggregate ranking reverses when repositories rather than samples are weighted equally. A training-free rank fusion of a semantic and a structural ranker beats both of its inputs [T1] (same source). Retrieval and interaction are also two surfaces, not one: static retrieval finds files the agent never touches on 12.5–17.8% of samples, and browsing finds files the retriever misses on 7.7–22.0%. Installing a retriever does not close the second gap.

3. Selection — what survives into the input? This is the stage nobody scores, and it loses more than most of the interventions the field argues about gain. On 16,490 RepoBench tasks from 2,798 repositories, required cross-file evidence enters the retriever's top five for 64.16% of tasks and survives complete inside a 4,096-token budget for 39.59% — a 24.57-point loss located entirely after ranking [T1] (VITAL-RAG). The mechanism is authority multiplication: an index exposes the body, signature, call site and test fragment of one code object, each competes for a slot as a separate result, and the independent helper the task needed gets clipped.

4. Structure and disclosure — how is the corpus packaged? Conditionally valuable, and only above a scale threshold (below).

5. Navigation — what governs the next file the agent opens? Not the dependency graph, and not a pre-built index. At 341 first-visit decision points (visit history empty by construction, so nothing can be predicted by restating the agent's own past), a ranker reading only the agent's most recent tool output reaches top-3 0.326, against 0.058 for a code dependency graph deliberately strengthened to seed from the entire visited set, and 0.072 for repository frequency [T1] (What Process Evaluation of Coding Agents Actually Measures). The graph still does real work — it separates the visited file set from random same-size sets by 30.9× in edge density, and scopes a region — it just doesn't route within that region; that's the agent's own last observation. A companion result complicates stage 2's static-graph story rather than resolving it: building the dependency graph fresh, per query, rather than once for the whole repository, beats retrieving against a fully materialized static graph on code generation (CoderEval +15.2% relative, DevEval +8.9%) at 7.4× lower wall-clock cost [T1] (Effective and Efficient Context Retrieval via Partial Dependency Graph). Read together: a reused, static graph scopes a region but does not predict the next move inside it; a query-conditioned, freshly built one materializes exactly the edges one generation task needs. "The dependency graph helps" is not one claim — it depends on whether the graph is built once or built for the query at hand.

6. Freshness — is what arrived still true? A stage none of the above measures, because every retrieval benchmark above freezes the corpus at evaluation time. Once a serving layer is caching, materializing, or indexing over a live source that keeps changing — license assignments, price changes, contract renewals — an answer can be correct when its facts were retrieved and wrong by the time the agent reports it, and the earlier four stages have no vocabulary for that failure at all. See below: this is not a smaller version of stage 1-4's problem, it is a fifth stage with its own mechanism, and the mechanism is not the one the tooling market would guess either.

What is settled enough to act on

Deduplicate on provenance identity, not on text. Exact deduplication moves evidence survival by 0.02 points. Canonical grouping, per-file quotas and MMR all reach ~64% candidate recall while leaving survival pinned between 39.41% and 39.59% — a row of controls that fail identically, which is what makes selection a distinct stage rather than a diversity problem. Quotienting views by canonical code object and then allocating tokens per object raises survival to 63.67% at 35.63% fewer tokens with the candidate set held fixed [T1] (VITAL-RAG).

A bigger window is not the fix. Survival saturates by 4K; 8K adds 0.01 points [T1] (same source). Buy the quotient, not the context length.

Measure localization at span granularity, not file granularity. A file-level hit is document reachability. Median gold file: 515 lines. Median useful evidence inside it: 27 lines (4.7%). Every method's line F1 is under 0.03, and the ranking between methods changes at span granularity [T1] (Agent Retrieval Bench). A retriever comparison scored on file hits is not measuring what the agent experiences.

A structural index beats grep, and costs less. A codebase index combining vector embeddings, a graph of definitions and call edges, and BM25 lexical, built over live source, lifts localization acc@5 44.3% → 84.5% (p<0.0001) and resolve 41.9% → 50.4% (p=0.003) against index-off, at a lower dollar-per-solve ($2.30 vs $2.92) because it wastes fewer turns [T1, suggestive] (Code Isn't Memory). The payoff concentrates on multi-file changes, so the value is workload-dependent by the authors' own framing.

Compact deterministically, not with a summarization model. Materializing lexical, dense and structural views per commit, handing the agent candidates carrying re-resolvable source addresses, and compacting via a one-time deterministic history rewrite cuts trajectory tokens 50–87% across five models while preserving AnswerRecall@5 within ε = 0.05 at a 95% confidence lower bound [T1] (CodeNib). The efficiency framing matters: the saving is stated conditional on preserving localization, so it is not a quality trade wearing efficiency's label.

One level of progressive disclosure. Never two. Holding the chunk set and descriptions identical and varying only the wiring, a second routing level — every chunk its own skill with an always-loaded description plus a meta-router — never helps and sometimes destroys accuracy (En.MC 0.9126 → 0.6398; Zh.QA 0.7479 → 0.3890) [T1] (Is Progressive Disclosure All You Need?). The mechanism is self-inflicted: the always-loaded child descriptions saturate the router's context before it commits to a chunk, recreating the exact pressure disclosure exists to relieve. Package a long document as one skill with a single in-skill index, and treat the instinct to add a routing layer when retrieval underperforms as usually backwards.

Packaged structure is a scale lever, not an accuracy lever. Same study: on a single document, the pack lifts harnesses that navigate raw text poorly and adds nothing to one whose bare agent already greps for the entities a question names. At twenty documents that same agent can no longer find the right file and the pack pulls 1.7× ahead (En.QA 0.257 → 0.462) [T1, suggestive]. The harness's own search ability is a named term in every result on this map. Report it, or your numbers do not transfer.

Judge scope before gathering, not after. Every other reduction technique here is reactive — prune, summarize, compact what was already pulled in. Estimating required scope first and expanding only on verification failure is an earlier lever with a metric attached (redundancy ratio against an oracle minimum). Carried with its arms separated: −85% cost / −91% tokens at equal success in a deterministic simulator, but only −18% tokens against a read-everything agent on live gpt-4o at case-study scale [T1, suggestive]. The durable part holds in both arms and is not about tokens: over-provisioned context costs reliability — the thorough agent lost 3/3 runs on the hardest tier where the scoped one held 93%.

The result that reframes the map

Everything above optimizes what arrives. As of 2026-08-03 the largest measured gain on this map does something else: it refuses to let the agent act until it has looked.

ECLoop compiles a per-task evidence specification from the issue text plus repository structure — conditions naming what must be observed before a class of commitment action may proceed ("inspect the callers of the function you are about to edit"; "check the available tests before submitting"). Reads, searches and diagnostics run unrestricted. Edits and submissions are held while their action-specific evidence gap is non-empty, with the unmet conditions returned as guidance. All four significant under an exact McNemar test on the 500 paired outcomes (p < 0.001), and token use falls 1.4–12.1% in every cell [T1] (ECLoop). Retrieval is not improved at all.

Three details in that system generalize past it.

Satisfaction is decided deterministically, never from the model's claim. An LLM proposes candidate conditions; each is then grounded against the AST, call graph and class hierarchy, and dropped if it cannot be resolved to a checkable entity. Matching runs against recorded trajectory events — what was viewed, searched, executed. A bad specification can only lose coverage; it cannot introduce a check the system is unable to evaluate.

The structure is load-bearing, and this is the sharpest measurement of that anywhere in the vault. Replacing the machine-checkable specification with an equivalent natural-language summary of what to investigate scores 58 against the full system's 68 — and against 63 for supplying no guidance at all. Identical content, identical context window; the only difference is whether satisfaction can be mechanically decided, and that difference is ten points.

It has to sit before the commitment. The Self-Refine control — three rounds of the model reviewing and revising its own patch, comparable extra inference — goes negative on both models (−1.4, −1.8 pp). Same budget, opposite sign. A decision taken without an observation is not repairable by a review that also lacks it.

The subagent-delegation reversal

The delegated-search design — isolate exploration in its own window, return a condensed result to the main agent — was carried on efficiency evidence alone, with quality asserted. As of 2026-08 it has a quality number, and it goes the other way. On SWE-QA (720 questions × 15 Python repositories × four models, paired within model, human-validated judge): a flat agent reading a semantic vector index answers 65.2% Pass against 46.2% for the delegated-subagent design — consistent in direction across all four models, significant after FDR correction, and the smallest gap under a Pass-threshold sweep from 50 to 90 is still 3.8 points [T1] (Deep Agentic Search for Repository-Level Code Question Answering). The mechanism is a new failure class, not a redistribution of old ones: coordination breakdown at the planner-to-subagent hand-off accounts for 41.8% of the delegating design's failures and 0% of the flat design's, and it fails silently — the condensed memo the planner receives reads as a confident claim about the wrong entity, not a missing answer. Context rot is real and delegation addresses it; what this measurement refutes is that the protection is free. Bound: read-only question answering over an indexable repository, not code modification, and the margin narrows (without crossing) as the repository grows past ~861 KLoC.

Precision and success are decoupled measurements, not consecutive stages

This map's retrieval-quality metrics assumed precision predicts outcome. Exposing an entire skill library at execution time with no preselection and growing the candidate pool from 5 to 100 finds actual-use precision collapsing 29.6% → 3.3% while downstream task success holds or rises (36.4% → 39.3% pooled; one stack rises 35.4% → 42.0%) [T1] (Demystifying Agent Skills: Why They Work—Until They Don't). The agent opens the labeled artifact along with several wrong ones and does not restrict itself to the label — a related-but-unlabeled procedure is often still usable, and exact ground-truth invocation is neither sufficient nor necessary for the task to succeed. This means a retrieval score on this map should not be read as a leading indicator of a repair outcome without a matched success measurement beside it — which is exactly what the subagent-delegation reversal above independently confirms from the opposite direction (a worse-quality design still wins on efficiency numbers alone). What does degrade cleanly is offline retrieval identification against confusable (not merely more numerous) distractors — a library that is half unregistered near-duplicate copies is where a retrieval metric still tracks the real failure.

The packing policy you would rationally adopt is the one that loses the repair

Once the context budget is fixed and zero-sum, the configuration that maximizes recall@k is not the one that maximizes resolve rate — and this is now causal, execution-graded evidence rather than an index-level correlation. One production flag (one-chunk-per-file deduplication), toggled on an otherwise identical SWE-bench Verified stack with official Docker grading: dedup-ON raises the served gold-file rate (0.878 vs 0.806) and resolves less — 39.2% → 46.8% is the reversed direction, i.e. dedup-OFF resolves 7.6 points more (McNemar p=0.0003, twelve of twelve leave-one-repository-out folds positive, a pre-registered open-weights replication confirms it) [T1] (The Recall Trap: A Recall-Maximizing Retriever Configuration Reduces Issue Resolution). The trade is roughly twelve files at one chunk each against five files at several chunks, and the advantage grows with the budget (+4.80pp at K=4 to +9.20pp at K=40) rather than washing out. A companion study maps where this reverses: on a lexical BM25 retriever the effect flips sign entirely (−3.2pp), and under agents that can open any file with no fixed budget it disappears (a powered null, MDE 4.5pp) — which excludes every tool-using coding agent from the positive finding as stated. The operational rule stays the same but narrower: at a tight, fixed-budget, dense-retrieval configuration, do not hard-deduplicate by file — everywhere else, the trap does not obviously apply, and the boundary map matters more than the headline number.

What agents actually read, and when supplying more of it backfires

Two findings hit acquisition from opposite ends. Measured over 3,033 documentation interactions extracted from 557 real agentic sessions, the artifacts agents consult are overwhelmingly the ones agents themselves write — instruction files and agent-authored working notes at 60.5% combined, against 1.3% for API references and 0.4% for troubleshooting guides — and consultation is self-initiated 70.2% of the time against 7.5% failure-driven, so documentation serves the agent already making progress, not the one that's stuck [T1] (Agent Documentation Behaviour). At the other end, a paired ablation that holds the repository snapshot, environment, and hidden validators fixed and adds only curated domain knowledge — rationales, upstream repairs, expert guidance — finds Pass@1 helping the weaker of two agent configurations (16.48% → 23.08%) and hurting the stronger one (36.26% → 31.87%), with 12 tasks lost against 8 won for the frontier configuration rather than a shifted mean. This is the third finding in the vault at the same shape — injected context's value is conditional on the agent's own competence, and the conditioning can flip the sign — so the operational rule this map now carries is concrete: A/B a context pipeline on the model you will actually serve, because a win measured on a cheaper model can be a loss on the frontier one.

The fifth stage: freshness, and the benchmark-design trap it exposes

Every stage above assumes the corpus is a snapshot. Production agentic systems answer questions over data that keeps changing underneath them — licenses reassigned, prices repriced, contracts renewed — and the natural instinct, tested directly for the first time on this map, is wrong. ChurnBench builds a four-source enterprise data fabric as a timeline (an append-only ledger, gold answers resolved from the ledger rather than the live stores, so a "correct when retrieved, wrong when evaluated" answer is mechanically detectable as a freshness error distinct from a reasoning error) and sweeps cache age across 1, 14, and 28 days with scheduled per-entity TTL refresh running. The result is flat: freshness errors of 7, 4, 4 — because a scheduled refresh renews any entity before its TTL lapses, so the drift-window variable the sweep was built to move never reaches the retrieval layer at all [T1] (ChurnBench). A controlled ablation — identical code, refresh switched off as the only variable — confirms the mechanism causally rather than leaving it a plausible story: freshness errors rise 4 → 45 (11×) at 28 days and stay identical (7=7) at one day, since at one day nothing has had time to drift regardless of refresh policy. Attribution sharpens the design rule further: exposure is the product of tier width and mutation rate, not either alone — the widest, most-stale-by-construction tier produces zero errors because those entities barely change, and the fastest-refreshing tier produces zero errors under tiering specifically because its TTL never lapses; 14 of 15 errors concentrate in the one tier where width and change rate actually overlap. For this map, the actionable consequence is a fifth acquisition-pipeline design rule alongside the four above: serving-layer TTL should be set from measured per-entity mutation rate, not from an assumption that older equals staler, and a benchmark's own staleness instrumentation should record per-entity refresh timestamps rather than lapse-event counts — a lapse-count metric reads identically as zero for "this never goes stale" and for "the staleness check never ran," which is a measurement trap distinct from anything the acquisition-through-disclosure stages above have to guard against. Scope: single model, single agent framework, single domain, entirely synthetic data, and the paper makes no claim that any particular grounding architecture (staged, federated, live-only) trades staleness against cost better than another — that comparison is explicitly left open.

What is still open

"Scored on cost, not repair" was the map's founding complaint, and it is now the exception rather than the rule — but the exceptions don't agree with each other on what buys a repair. ECLoop moves a resolve rate by gating on observed evidence; the dedup-ON packing study moves one by removing the apparent recall winner; the delegated-search reversal moves the quality axis by simply measuring it for the first time. None of the three is about the same lever, and nothing has run them together on one stack. ECLoop specifically is still one group, one benchmark, one language, one task type, with a single run per configuration and no seed variance. Treat +11.8 as a direction, not a number to plan around.

The gate's blocking variant is unmeasured. ECLoop holds an action at most three times per commitment target, then releases it through an audited fallback. Every regression in the paper traces to that fallback. Nobody has run the version that refuses.

Precision-success decoupling has not been tested against a harder success bar. The skill-use result found success holding steady while precision collapsed — but the success measure there is task-level pass/fail. Whether an unlabeled, related-but-not-quite-right artifact is still safe to act on under a stricter correctness bar (security, data integrity) is untested, and this map's own commit-gate adjacent evidence (verifier independence, runtime action governance) suggests the answer is regime-dependent rather than free.

The freshness stage has no repair-outcome number yet, and no architecture comparison. ChurnBench demonstrates the mechanism (TTL beats cache age) and instruments it precisely, but explicitly ran no baseline comparison under its final design — staged, federated, and live-only grounding architectures are named as an open question, not measured. Nothing on this map yet connects a freshness error to a downstream Pass@1 the way ECLoop connects an evidence gate to one.

Issue quality is an unpriced input for the gate result specifically. The evidence specification is compiled from the issue description, and SWE-bench Verified issues are human-validated and well-specified — not the condition on a real tracker. The authors name a preceding clarification step as the fix and do not run it.

The packing-policy rule is narrower than it first reads. Do-not-deduplicate holds at a tight, fixed budget under dense retrieval; it reverses under BM25 and disappears once the agent can open any file without a budget ceiling — which is most tool-using coding agents as actually deployed. Read the boundary map, not the headline delta.

Contamination applies to all of it. Every resolve-rate number on this map lives on SWE-bench, where retrieval-time leakage inflates scores and this vault carries the warning as standing.

The short version

As of 2026-09:

  1. Assume the agent will not find the file. A quarter to a third of the time, it does not [T1].
  2. Make it look before it may edit. The only intervention on this map with a resolve-rate number gates the commitment on observed evidence, and it pays for itself in tokens [T1].
  3. Decide satisfaction from the trajectory, not from the model's report. Ground every condition against real repository structure and drop what cannot be checked [T1].
  4. Structure your guidance so a machine can decide it. The same content as prose is worse than silence [T1].
  5. Deduplicate on provenance, quotient by code object — but only hard-deduplicate by file inside a tight, fixed budget under dense retrieval. Outside that regime the rule reverses or vanishes [T1].
  6. Measure spans, not files, and grade quality, not just efficiency. A flat agent over an index beat a delegated-search design on quality by 19 points while the delegated design still won on tokens — report your harness's own search ability and its success rate, not just its cost [T1].
  7. A retrieval score is not a leading indicator of success. Precision can collapse ninefold while the task still gets done; don't gate a design decision on recall@k alone [T1].
  8. A/B your context pipeline on the model you will actually serve. A curated-knowledge or packaging win on a weaker model can be a loss on the frontier one [T1].
  9. Add one level of disclosure. Never two [T1].
  10. Set serving-layer refresh from measured per-entity mutation rate, not cache age. A scheduled TTL bounds staleness; a wider sweep window does not reveal it [T1].
  11. Do not read a token saving as a capability claim. Most of this map still measures cost, and this run adds the sharpest reminder yet: the design with the better cost number here had the worse quality number.
