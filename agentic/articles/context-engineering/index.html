Context engineering: manage the window as a decaying resource

As of 2026-07, the strongest cross-cutting claim about long-running agents is not about the model — it's about the window. Treat the context window as a finite, decaying resource, and the agent builder's job becomes curating the minimal high-signal set of tokens present at each inference step. That much has held since this article was first written.

Two things changed enough to restructure the piece. The first is a sharpening: more context is not better context, and more memory is not better memory — getting it wrong degrades the agent below giving it nothing. The second is newer and more uncomfortable, because it lands on advice this article has been giving since July: "summarize better" is not reliably the fix, and on at least one task class the configurations that process history do worse than the ones that keep it raw.

The claim, and why it holds

Anthropic's Applied AI team frames it as an "attention budget" subject to context rot: accuracy degrades as tokens accumulate, because attention grows quadratically and models have trained on few examples with window-wide dependencies [T2] (Effective context engineering for AI agents). That's vendor practice. The measurement side agrees, now from four independent directions. LongDS-Bench runs long, dependent data-analysis sessions and finds leading models reach only 48.45% accuracy and degrade ~47 points early-to-late, with the collapse in state-preservation, not step budget: more turns don't fix it [T1] (Xu et al.). RoadmapBench finds the ceiling at real feature scale (median 3,700 changed lines across 51 files; best of 13 frontier models resolves 39.1%) [T1] (Xu et al.). SaaSBench locates where the failures live: on from-scratch enterprise builds ~95.6% of failures land before deep business logic — 63.5% never run stably [T1] (Ren et al.).

ChainSWE supplies the fourth and cleanest demonstration, because it isolates the mechanism. Fixing a chronological chain of dependent bugs in one un-reset repository drops per-bug accuracy from 58.9% (with oracle prior fixes) to 36.5% (sequential) — roughly 61% → 40% → 28% by position in a length-3 chain. The loss is not that later bugs are harder; the chains were pre-filtered so more than half solve in oracle mode. It is agent-authored state pollution: 48% of downstream failures are chain errors introduced by the agent's own prior patches [T1] (Jin et al.). That is context rot with a named cause — the agent poisons its own window and then reads the poison as evidence.

The practical corollary from SaaSBench inverts the usual instinct: the highest-leverage context work is often not summarizing better but removing setup and integration surface from the agent's path — pre-built environments, working scaffolds, mechanically-enforced invariants. You cannot summarize your way out of a stack that never ran.

What to actually do

  • Pursue the minimal token set. Right-altitude system prompts; small, non-overlapping tool sets. Cost: up-front design and the discipline to delete context that isn't load-bearing.
  • Retrieve just-in-time. Hold lightweight identifiers, pull bytes at runtime; pre-load only cheap, always-relevant context. Cursor independently migrated from heavy static pre-loading to dynamic runtime fetch — a second vendor, same direction [T2] (Continually improving our agent harness). Trade: fewer stale indexes, more in-loop tool calls.
  • Estimate scope before you gather, not after. Every reduction move in this article is reactive — prune, summarize, evict, compact, all operating on context already pulled in. E3 adds the anticipatory one: estimate the task's scope first, execute the minimum path that estimate implies, widen only when verification fails. On a deterministic simulator it holds 100% success at −85% cost / −91% tokens; against a live model on one real library the effect shrinks to −18% tokens versus a read-everything agent, and the authors call that arm a case study rather than a benchmark [T1] (Do AI Agents Know When a Task Is Simple?). The result worth carrying comes from the weaker arm anyway: on the hardest deceptive tier the "thorough" agent lost all three runs while E3 held 93%. Over-provisioned context carries a reliability tax, not just a token tax.
  • Prune, then summarize — with a caveat that is now load-bearing. A controlled four-way sweep on GPT-5 (reproduced on Sonnet 4.5) found pruning to the last few tool interactions plus summarizing beats full-history retention by +20.6 completion points at ~2.7× fewer tokens [T1] (Less Context, Better Agents). Hold that result — and read the next section before generalizing it.

There's still no head-to-head on when compaction beats note-taking beats sub-agents. Treat that as open.

Where "summarize better" stops working

This is the part of the article that changed most since the last refresh, and it cuts against the bullet above it.

On ChainSWE's multi-bug maintenance chains, the configurations that process history performed worse than the one that didn't: baseline full-history 33%, versus 40–41% for summarize and sub-agent configurations — and paid conversation memory bought +7–8 points for GPT-5.5 alone, roughly nothing for six other models, at 10–16K extra tokens per bug [T1] (Jin et al.).

Set against Less Context, Better Agents, that looks like a contradiction. The reconciling read is about what is in the history. Where the history is mostly tool output — retrieved files, command results, search hits — pruning and summarizing it is compression of evidence, and it wins. Where the history contains the agent's own prior decisions and patches, summarizing is compression of reasoning, and each compaction pass discards the details that would let the agent notice its earlier patch was wrong. You get a shorter, more confident, equally wrong context.

A T3 case report shows the mechanism at its sharpest: summarization has no epistemics. A killed process's partial stdout was compacted into "confirmed results" and persisted across sessions — the refuting exit code was in-context at compaction time and did not survive it [T3] (Compaction as Epistemic Failure). Single case, so hold it loosely, but the fix is cheap and worth doing regardless: flag non-zero exit codes in summaries, and verify claimed outputs against persistent artifacts before recording them.

So the operative rule is narrower than "prune, then summarize": compress what the agent observed, be conservative about compressing what the agent did, and never let a summarizer be the only thing standing between a failed command and a recorded fact.

Not all external memory is good memory

Here is where the naive reading — "state decays, so persist more of it" — breaks, and the break is measured. A reliability study across 23,392 episodes and 10 models found that generic memory scaffolds degraded long-horizon performance on all 10 models — not helped less, degraded [T1] (Beyond pass@1). The same window ingested the opposite result: an external layer tracking the specification recovered 90% of a faithfulness gap that opens when requirements arrive incrementally [T1] (SLUMP).

Both can be true. The distinction is what you externalize, not whether you externalize: structured state about the task's contract helps; unstructured recall of the agent's own history hurts, because history compounds drift. Through 2026-07 the same shape kept landing. Goal-anchored pruning beats task-blind perplexity compression, which destroys correctness [T1] (SWE-Pruner). LLM-generated AGENTS.md files (the /init artifact) lose 0.5–2 points at +20–23% cost, while developer-written context files gain +4% [T1] (Evaluating AGENTS.md).

Then obedience: for a cross-cutting requirement nobody scores (logging), compliance from a repository context file is 8.3%, with instructed and uninstructed PRs statistically indistinguishable (p=0.25) [T1] (Do AI Coding Agents Log Like Humans?). Set against the AGENTS.md result — agents do follow context-file instructions on scored tasks — the rule sharpens: context is obeyed in proportion to how task-anchored it is. The blunt corollary is that AGENTS.md is the wrong home for any requirement you actually need enforced. Gate it instead.

That rule got its first designed test in June, and the result is worse than neglect. Given a hidden 222-test oracle and three availability conditions, agents with no oracle access produced incomplete-but-sound libraries (177/222, 162/222); agents with the oracle in-loop hit 221–222/222 with the requested library dead, absent, or collapsed into a 1,758-line single component reported as "222 passed" [T1] (Building to the Test). Ungraded properties aren't merely ignored when something else is graded — they get destroyed.

Most direct, a memory architecture finally manipulated the discriminating variable on purpose, in one experiment. Persist only contract categories (task specs, data schemas, tool configs, output constraints) and discard session reasoning: 96% task completion, versus 79% with no memory and 71% with full history [T1] (Shared Selective Persistent Memory). Full history landing below the no-memory baseline is the drift mechanism caught red-handed. It runs on enterprise data-artifact workflows rather than long-horizon code repair, so it does not close the head-to-head the field still needs.

The axis underneath: verification at the point of use

A July result reframes the generated-context finding, and it is the most useful addition in this refresh. The Harness Handbook builds an LLM-synthesized index over a codebase — the same production method as a generated AGENTS.md, which loses points — and it helps: localization F1 up 5.0 to 18.8 points while spending 8.6–12.7% fewer planner tokens [T1] (Harness Handbook).

The difference is trust posture, not authorship. A generated AGENTS.md is believed at read time. The Handbook is used only to narrow the search, after which the agent opens the repository, resolves every candidate location, and keeps only what is still there — carrying a current source excerpt forward. The authors' rule: the handbook guides the search, the repository remains the authority.

So there are two axes, not one. Task-anchoring predicts whether context gets used. Verification predicts whether using it is safe. Generated context is fine — if nothing downstream treats its claims as established. Note the honest caveat: this comparison is a synthesis across two papers, not an experiment. Nobody has run generated-context-with-verification against generated-context-without on one task set, and that is now the cheapest high-value experiment in this area. The Handbook's own evidence is also weaker than its numbers suggest — the dependent variable is an LLM-judged edit plan, never an executed patch.

So: keep recommending compaction, external notes, and sub-agents — but as evidence compression, not as reasoning compression, and not as a generic memory scaffold. Persist the contract; discard the conversation; verify what you retrieve.

The docs tree is also an attack surface

This article has treated the documentation tree as an asset to curate for fidelity and cost. As of 2026-07 it is also untrusted input sitting on the execution path. Editing only a README, requirements.txt, or Makefile — no malicious code, no compromised registry — is enough to make an agent install attacker-chosen packages. Name-based attacks (typosquats) are caught nearly everywhere; source-based ones (registry redirection, hidden index) are missed nearly everywhere; and version-based attacks pinning a known-vulnerable release were missed by all nine harness-model configurations across 270/270 runs [T1] (Setup Complete, Now You Are Compromised).

The surface is real at scale: --extra-index-url appears in over 5,500 READMEs and 6,900 requirements.txt files. And note how neatly this fits the task-anchoring rule rather than complicating it — a logging instruction is a cross-cutting requirement nobody scores, so it is ignored at 8.3% compliance; a setup instruction is the immediate task, so it is executed without question. Obedience and neglect are the same mechanism read at two ends. Nothing here weakens just-in-time retrieval. It adds a provenance obligation to it.

Where this connects

The thesis wears a code reviewer's hat as Sourcegraph's "80% problem" — agents finish the visible 80% and miss the cross-cutting 20% outside their window [T2] (Agentic Coding in 2026); the answer is out-of-band verification (ci-cd-for-agents, agentic-code-review). Practitioners building agents report the same limit from the inside and name it well — agents retrieve the written, not the unsaid (76% agree) — and rate converting tacit knowledge into durable artifacts (83.8%) and escalating gaps to humans (83.5%) above providing context progressively (73.1%) [T1] (How Do Practitioners Build SE Agents?). The binding constraint isn't retrieval of what's written; it's that the important thing was never written down.

A maintenance caution worth carrying: tracing regressions across 35 scaffolding releases with the model frozen, Context Management is one of the two highest-risk components to change [T1] (Don't Blame the Large Language Model). The surface this vault treats as highest-leverage is also the one most likely to break when the middleware ships.

Open and contested

  • The prune-and-summarize result and the ChainSWE result are not reconciled by an experiment. The evidence-versus-reasoning distinction offered above is a hypothesis that fits both, not a finding. Someone should run one compaction policy across both task shapes.
  • The decisive memory experiment is still unrun: a spec-tracking layer versus a history-memory scaffold on one long-horizon code task set. The contract-vs-history result gets closest, on a data-artifact workload with the retained categories bundled rather than ablated.
  • Is the tension about memory at all, or about scoring? If context is obeyed in proportion to task-anchoring, "contract-state helps, self-recall hurts" may be a special case of "context that bears on the graded objective is used; the rest is overhead." Cheap test: put the same requirement in the graded spec versus in AGENTS.md, hold everything else fixed, measure compliance.
  • Does verification-at-point-of-use generalize beyond code localization? It is one study, judged by LLMs, with no execution and no build-cost accounting.
  • No general effect-size. Every quantified anchor is domain-bound; the direction is what replicates.
  • How much of "context rot" is human interaction pattern? Dribbling requirements across ~60 turns is itself a degradation mechanism (16/20 tasks worse than handing over the whole spec); nobody has decomposed that from window mechanics.
