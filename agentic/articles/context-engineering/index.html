Context engineering: manage the window as a decaying resource

As of 2026-07, the strongest cross-cutting claim about long-running agents is not about the model — it's about the window. Treat the context window as a finite, decaying resource, and the agent builder's job becomes curating the minimal high-signal set of tokens present at each inference step. That much has held since this article was first written. What has changed, and what this refresh is mostly about, is a sharper and more uncomfortable finding: more context is not better context, and more memory is not better memory — and getting that wrong actively degrades the agent below giving it nothing.

The claim, and why it holds

Anthropic's Applied AI team frames it as an "attention budget" subject to context rot: accuracy degrades as tokens accumulate, because attention grows quadratically and models have trained on few examples with window-wide dependencies [T2] (Effective context engineering for AI agents). That's vendor practice. The measurement side agrees, now from three independent directions. LongDS-Bench runs long, dependent data-analysis sessions and finds leading models reach only 48.45% accuracy and degrade ~47 points early-to-late, with long-horizon errors over half of all failures — and the collapse is state-preservation, not step budget: more turns don't fix it [T1] (Xu et al.). RoadmapBench finds the ceiling at real feature scale (median 3,700 changed lines across 51 files; best of 13 frontier models resolves 39.1%) [T1] (Xu et al.). And SaaSBench locates where the failures live: on from-scratch enterprise builds ~95.6% of failures land before deep business logic — 63.5% never run stably [T1] (Ren et al.). Multiple orgs, multiple methods, same root cause. That is what moved this topic to consolidating and keeps it there.

The practical corollary from SaaSBench inverts the usual instinct: the highest-leverage context work is often not summarizing better but removing setup and integration surface from the agent's path — pre-built environments, working scaffolds, mechanically-enforced invariants. You cannot summarize your way out of a stack that never ran.

What to actually do

  • Pursue the minimal token set. Right-altitude system prompts; small, non-overlapping tool sets. Cost: up-front design and the discipline to delete context that isn't load-bearing.
  • Retrieve just-in-time. Hold lightweight identifiers, pull bytes at runtime; pre-load only cheap, always-relevant context. Cursor independently migrated from heavy static pre-loading to dynamic runtime fetch — a second vendor, same direction [T2] (Continually improving our agent harness). Trade: fewer stale indexes, more in-loop tool calls.
  • Prune, then summarize — and this one is now quantified. A controlled four-way sweep on GPT-5 (reproduced on Sonnet 4.5) found pruning to the last few tool interactions plus summarizing beats full-history retention by +20.6 completion points at ~2.7× fewer tokens — reliability and cost improving together [T1] (Less Context, Better Agents). Compaction, external notes, and sub-agent isolation (each sub-agent returns a distilled 1–2k-token summary) extend the horizon past one window. Cost: orchestration complexity and, for sub-agents, extra model calls.

There's still no head-to-head on when compaction beats note-taking beats sub-agents. Treat that as open.

The part that changed: not all external memory is good memory

Here is where the naive reading — "state decays, so persist more of it" — breaks, and the break is a measured one. A reliability study across 23,392 episodes and 10 models found that generic memory scaffolds degraded long-horizon performance on all 10 models — not helped less, degraded [T1] (Beyond pass@1). The same window ingested the opposite result: an external layer tracking the specification recovered 90% of a faithfulness gap that opens when requirements arrive incrementally [T1] (SLUMP).

Both can be true, and reconciling them gives the sharpest rule in this article. The distinction is what you externalize, not whether you externalize: structured state about the task's contract helps; unstructured recall of the agent's own history hurts, because history compounds drift — it feeds the agent its own earlier errors back as evidence. Through 2026-07 the same shape kept landing. Goal-anchored pruning (a skimmer that cuts tool output against the agent's stated need) beats task-blind perplexity compression, which destroys correctness [T1] (SWE-Pruner). LLM-generated AGENTS.md files (the /init artifact) lose 0.5–2 points at +20–23% cost, while developer-written context files gain +4% — the generated overview is a lossy README copy, task-blind self-recall about the repo [T1] (Evaluating AGENTS.md).

Two findings tightened it further. First, obedience: for a cross-cutting requirement nobody scores (logging), compliance from a repository context file is 8.3%, with instructed and uninstructed PRs statistically indistinguishable (p=0.25) [T1] (Do AI Coding Agents Log Like Humans?). Set against the AGENTS.md result (agents do follow context-file instructions on scored tasks), the rule sharpens again: context is obeyed in proportion to how task-anchored it is — and the blunt corollary is that AGENTS.md is the wrong home for any requirement you actually need enforced. Gate it instead.

Second, and most direct, a memory architecture finally manipulated the discriminating variable on purpose, in one experiment. Persist only contract categories (task specs, data schemas, tool configs, output constraints) and discard session reasoning: 96% task completion, versus 79% with no memory and 71% with full history [T1] (Shared Selective Persistent Memory). Full history landing below the no-memory baseline is the drift mechanism caught red-handed — the authors' own words are that "naive full-history persistence actively degrades completion by biasing the agent with stale traces." It runs on enterprise data-artifact workflows, not long-horizon code repair, so it does not fully close the head-to-head the field still needs — but it is the same shape, same sign, with both arms measured in one setup.

So: keep recommending compaction, external notes, and sub-agents — the supporting evidence is cross-stack and strong. Do not treat a generic memory scaffold as the same intervention. Persist the contract; discard the conversation.

Where this connects

The thesis wears a code reviewer's hat as Sourcegraph's "80% problem" — agents finish the visible 80% and miss the cross-cutting 20% outside their window [T2] (Agentic Coding in 2026); the answer is out-of-band verification (ci-cd-for-agents, agentic-code-review). It sets the bar for unattended operation, where a durable session log exists to preserve the state LongDS-Bench watches decay (unattended-operation, agent-harness-architecture). And the "obeyed in proportion to task-anchoring" finding is runtime-action-governance's instruction arriving on the quality axis: if prose doesn't govern a property, a deterministic guardrail must.

Open and contested

  • The decisive experiment is still unrun: a spec-tracking layer versus a history-memory scaffold on one long-horizon code task set. The 2026-07 contract-vs-history result gets closest, but on a data-artifact workload with the retained categories bundled rather than ablated.
  • Is the tension about memory at all, or about scoring? If context is obeyed in proportion to task-anchoring, "contract-state helps, self-recall hurts" may be a special case of "context that bears on the graded objective is used; the rest is ignored or pure overhead." Cheap test: put the same requirement in the graded spec versus in AGENTS.md, hold everything else fixed, measure compliance.
  • No general effect-size. Every quantified anchor is domain-bound; the direction is what replicates.
  • How much of "context rot" is human interaction pattern? Dribbling requirements across ~60 turns is itself a degradation mechanism (16/20 tasks worse than handing over the whole spec); nobody has decomposed that from window mechanics.
