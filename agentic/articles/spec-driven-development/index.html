Spec-driven development: the contract lives outside the agent

As of 2026-08, the standing instruction has not changed: the specification is a contract, and the contract must be held outside the agent. What has changed is how much of the job that sentence turns out to cover. Since this piece was first written in July, the evidence has added a phase for writing the contract, a second axis for checking it, a route to recovering one that was never written — and, in August, a measured limit that no amount of holding-it-outside repairs.

Start with the two results the instruction rests on. The agent cannot critique a spec: given a design proposal, the codebase, and RFC history, the best agent tested finds only 44.4% of the proposal's defects — it misses more than it finds [T1] (SpecBench). And it cannot retain a spec that arrives in pieces: holding requirements constant and varying only delivery, handing everything over upfront beats letting the spec emerge across ~60 progressive requests on 16/20 papers for Claude Code and 14/20 for Codex [T1] (SLUMP).

Neither job goes to the model. A human reviews the spec; a durable artifact tracks it.

This indicts the default workflow. The emergent condition SLUMP measures — disclosing the design request by request as you think of it — is exactly how every chat-first agent product invites you to work. That workflow has a measured cost in artifact faithfulness and structural integration, on both platforms tested. "Write the spec first" graduated from taste to effect size.

New in August: the route to the contract keeps acting after the contract is fixed

Here is the result that complicates everything below it. Hold the repository, the final contract, the verifier, the agent configuration and a 20-minute budget fixed. Defer execution until the complete requirement history is visible, from a fresh checkout, so there is no intermediate code creating inertia. Then vary only the revision path by which those requirements arrived — state them directly, or state them twice, or split them across turns, or state an old rule and explicitly override it, or introduce a temporary rule and cancel it. Every path resolves to the same contract, verified by replay and by two blind reviewers who recovered the same obligations from all 25 histories.

Aggregate accuracy notices nothing: final-contract realization is 78.8% on the direct statement and 78.7% averaged over the four equivalents. Pair the runs and 35 of 100 blocks that succeed on the direct statement fail on at least one equivalent history — a conditional path-violation rate of 36.4% (95% CI 25.6–45.1), present in all five task families and all three repeats [T1] (SpecPath).

Two things follow, and the second is stranger than the first.

A complete external contract does not make the program a function of the contract. The map's practice survives — nothing here says stop writing specs — but "hand it over whole" is now demonstrably necessary and not sufficient, for the second time and by a different mechanism than the long-context result below.

The operator that does the most damage changes no obligation at all. Plain duplication — restating the same requirements a second time — produced the largest violation rate (18.3%), ahead of explicit override (10.8%). The ordering churns across repeats and the authors mark it exploratory, so treat it as a flag rather than a finding. But the direction of the surprise matters: this is not "non-monotonic revision is hard." It is "presentation is load-bearing at all," and the two wording controls back that up by not firing — paraphrasing the direct statement costs −3.1 points and padding it with neutral turns −4.0 points, both intervals spanning zero. Longer prompts are not the problem.

The actionable step is the paper's own: before writing code, make the agent normalize the currently binding obligations — write down which requirements still count, then implement from that. Completeness in the conversation is not the same thing as having resolved it.

Also new: the notation is not the intervention

A preregistered randomized trial rendered byte-identical propositions two ways — connected prose, versus an explicit contract whose lines read HOLD FIXED, INTERVENE, REQUIRED DIRECTION — and asked whether two model snapshots then produced more similar executable programs. Both registered stages and their preregistered conjunction return not_supported; same-account identifiability sits at chance (0.469–0.523) against a registered 0.80 threshold in all four cells [T1] (SPECFORM, a preregistered renderer-format trial).

That corroborates a null this map already carried on one arm of one paper — structured Markdown, freeform prose and RFC-2119 GIVEN/WHEN/THEN performed alike in the elicitation study below. Two independent nulls now say the same thing: stop designing a spec notation. The payoff is in the phase and the delivery.

Worth reading the method even if you never care about the result. The analysis plan was compiled and sealed with an RFC 3161 timestamp before the assignment randomness existed; treatment was drawn from a specified future NIST randomness beacon pulse; inference enumerated all 65,536 possible assignments exactly; and support required all 27 criteria to pass under two differently-shaped transforms, so when the study's one interesting endpoint cleared a corrected threshold under one and shrank tenfold under the other, the pre-committed rule already called it transform-dependent. The honest counterweight is the author's own: effective N is 16 and no positive control was registered, so there is no measured floor on what this instrument could have detected.

Write the spec in its own phase — the agent is good at that part

The July framing merged two jobs the evidence has since separated. The agent is bad at judging a spec. It is productive at discovering one, when it has something to probe.

Split the loop into a spec agent that does nothing but explore and write SPEC.md, and a synthesis agent that does nothing but implement from that file — same scaffold, same model, fresh context, and the spec agent's reasoning withheld from the implementer. Average test pass rate rises +6.9% to +21.3% across all 200 benchmark instances on four models, every one significant at p < 0.01 paired, winning on 59–75% of instances [T1] (SpecFirst). The tail moves more than the mean: near-perfect reconstructions triple at the ≥90% threshold. And the mechanism is instrumented rather than asserted — exploration coverage of the target rises 9.4–18.5% on every model, with the spec agent covering far more than the synthesis agent and their union barely adding. An agent that can code stops exploring too early, every time.

The scope condition is severe and worth stating plainly: the benchmark hands the agent an execute-only binary as a behavioural oracle, which is a perfect, cheap, on-demand answer key that no real feature request has. Costs rise 48–130%. What plays the binary's role for ordinary product work is this map's sharpest open question.

Re-present the contract at each decision it governs

The other sufficiency failure, measured in July. With 24 checks mechanically extracted from a production workflow, frozen, and available to the agent throughout, strict pass still fell 8/10 → 3/10 under long context while requirement coverage stayed above 92% — the contract survived in the window and stopped governing behaviour. Changing only the completion instruction, to restate all 24 obligations rather than asking the agent to validate its own constraints, restored 10/10 against 5/10 (Fisher p = 0.0325) [T3] (long-context skill failure).

A self-generated validator inherits the omission that produced the artifact. So make the spec executable, and make re-delivery a harness responsibility rather than a hope. Note the shape this shares with SpecPath: one says the contract stops governing over time, the other says it fails to govern uniformly across presentations. Both are arguments for a normalization step the agent is made to perform rather than trusted to have performed.

Make the executable contract two checks, not one

Every external contract above is behavioural — a test suite, 24 observable checks, an output comparison — and all of it answers did the result behave correctly. A separable check asks does the intended path exist at all: are the required units present, the adjacent relations intact, the data states flowing between them — answerable statically, before anything runs, and reported as a localized violation naming the edge that broke.

Ablated against the same harness, removing the behaviour half costs −6.7 points and removing the architecture half −4.1 points; their sum exceeds the joint −8.1, so the two are partially redundant rather than additive, and they fail independently [T1, single-study] (CodeSpec). Carry it as a design, not a number — authors' own system and baselines, no preregistration, no seed variance, no intervals, gains thinning above ~4K LOC, and the checks used to steer the agent rather than to admit or reject its work.

Stress-test the contract before you spend on execution

The only case in this vault of a team paying to validate a spec first. The contract is a rulebook — lookup tables where structure is preserved, design docs where it is redesigned, a dependency map, an inventory of features with no counterpart in the target. Step two is to run a mini-migration on three files with adversarial review, discard the output, and keep the refined rules. Thereafter the rulebook is live: a recurring mistake is answered by amending the rule and regenerating the affected batch [T2] (Anthropic on large-scale migrations).

That makes the spec the unit of repair, not only of instruction. It also front-loads human effort exactly where SpecBench says a human is irreplaceable. Two case studies, no control arm, and a language port has an unusually complete pre-existing spec in the source program.

Where no spec was written, recover one from the trajectory

Everything above assumes a contract authored in advance, which leaves the ordinary case untouched: someone opens a chat, iterates, and a diff appears. Intent — defined sharply against summary, meaning why the change was made rather than what changed — is recoverable from the conversation, change metadata, agent plans and linked artifacts at F1 0.860 on 121 hand-annotated diffs, with the code change withheld from the prompt so the inference is not circular. The diff is then backtranslated into a task list using none of those sources, and the two compared on a shared five-bucket rubric: QWK 0.907 [T1] (intent drift in code critique).

The limit is in the authors' own per-bucket table: 0.889 and 0.812 at the extremes against 0.341 and 0.409 in the middle. It detects did roughly what was asked versus did nothing like it and cannot grade the interval between — the high-confidence-at-the-extremes profile this vault keeps finding in gates. And a reconstructed intent checks execution against the stated goal, never whether the goal was right.

Track the spec in external state — and only the spec

ProjectGuard, an external project-state layer maintaining what the spec so far commits the project to, recovers 90% of the faithfulness gap on the worst-degrading platform — fully faithful components 118 → 181, severe failures 72 → 49 [T1]. This is the externalize-the-durable-state rule unattended-operation reached for the run, applied to the contract.

What the tracker holds matters. Against the naive version: generic memory scaffolds degraded all 10 models tested on long horizons [T1] (Beyond pass@1). The reconciling hypothesis — structured state about the task's contract helps, unstructured recall of the agent's own history compounds drift — is stated in both maps and tested in neither. Until someone runs the head-to-head: track the spec, not the transcript.

The human spec review is a load-bearing gate

SpecBench places the agent's weakest phase precisely where teams are most tempted to skip human effort: upstream, before any code exists to react to. Without execution feedback, agents reason poorly about specs in the abstract — omissions, ambiguities, inconsistent assumptions, the things a maintainer catches in RFC review [T1]. The trade-off is real and worth naming: this is the slowest, most senior-time-expensive step in the pipeline, and the evidence says it is the wrong one to automate away.

Note what SpecFirst does not overturn. Discovery moved to the agent; judgement did not.

Under-specification is priced at the action layer too

What does the agent do under an incomplete spec? It acts anyway. Strip identifying bits of the target from a DevOps instruction and 55.8–67.8% of acted runs violate an action boundary; refusal stays at or below 2.5%, and cues about blast radius do not slow the agent down [T1] (UnderSpecBench). The damage is driven by target underspecification (wrong-target rate 9.6% → 75.1%), while weak intent wording is recoverable when the target is unique. The ticket-writing corollary is cheap and concrete: a fully qualified, unique target buys more safety than any amount of intent prose [T1]. Whether the agent asks a clarifying question instead of guessing is largely a harness affordance — a 3× ask-rate difference with the model held fixed.

What to do

  • Write the spec before the session and hand it over whole; incremental disclosure measurably corrupts the artifact [T1].
  • Before implementation, make the agent restate which requirements currently bind. A complete conversation is not a resolved contract, and a third of otherwise-competent runs get this wrong [T1].
  • Give elicitation its own phase and its own agent, then hand a written file to a fresh context. An agent that can code stops exploring too early [T1].
  • Do not invest in spec notation. Two independent nulls, one preregistered, say format is not what pays [T1].
  • Re-present the contract at the decision it governs — especially at completion — rather than asking the agent to validate its own constraints [T3].
  • Route the spec through human review before code; the agent misses most spec defects, and this gate sits exactly over its blind spot [T1].
  • Add a static structural check beside the behavioural one; they fail independently, and the structural one localizes the break [T1, single-study].
  • On a repeated migration, stress-test the rulebook on a few files, throw the output away, keep the rules — and amend the rule, not the output, when a mistake recurs [T2].
  • Maintain the spec in a durable external tracker the agent consults [T1] — and do not confuse spec tracking with memory: generic self-history scaffolds degraded every model tested [T1].
  • In every ticket, fully qualify the target (which file, which resource, which environment); target specificity outperforms intent prose at preventing wrong-target actions [T1].
  • Treat an under-specified ticket as the expensive case — route it to a clarify-first pipeline rather than the standard one [T1].

Where this connects

Downstream, the same asymmetry appears at the diff: the agent is weak at critiquing its input contract just as it is weak at certifying its output — agentic-code-review holds that side, with its own quantified self-assessment failures. Spec critique is a context-heavy task, and both ProjectGuard and the phase boundary in SpecFirst are context-engineering interventions wearing spec-tracking labels — context-engineering shares the memory-scaffold tension in full. The ticket's target specificity doubles as a governance control (runtime-action-governance). And SpecPath found a 12-point spread in path-sensitivity between two scaffolds running identical contracts and models, which puts part of this map's newest finding in harness-as-score-confound — where the 78.8-vs-78.7 result also belongs, as the cleanest demonstration the vault holds that a stable mean can conceal a third of its successes changing hands (evaluation-integrity).

Open and contested

  • Does resolving the contract first buy back path invariance? SpecPath names the missing step and measures the failure without it, but never runs the arm where the agent is required to emit a resolved contract before coding. Cheap, obvious, unrun — and it is the experiment that turns a diagnostic into a practice.
  • Is duplicate-history sensitivity real? The operator that changes no obligation produced the largest violation rate. If it replicates, the framing changes from "handle supersession" to "handle repetition," which is a much stranger claim.
  • Is the format null underpowered? Two independent nulls agree that notation is inert. Neither has demonstrated it could have detected an effect of the size it was looking for; the preregistered one says so explicitly.
  • Model failure or harness failure? Claude Code suffers severe faithfulness loss under emergent specs; Codex barely degrades, and SLUMP does not isolate why. Harnesses differ 3× in whether the same model asks instead of guessing — suggestive, not probative, and nobody has run the protocol with ask-affordance as the variable.
  • What should the tracker track? Contract-state (helps, one T1) versus self-history (hurts, one T1) has never been tested head-to-head on one task set. Still the most decision-relevant unrun experiment this map touches.
  • What plays the oracle's role outside a benchmark? SpecFirst's gains come from probing an execute-only binary. Real feature requests have no such answer key, and the authors concede pronounced degradation at repository scale.
  • Does a human-refined spec measurably improve downstream code? Every source measures the spec layer's failure; none measures the delta from fixing it.
  • Ticket decomposition — the middle of the pipeline — is unmeasured by anyone. Spec critique and spec retention are covered; spec → tickets is not, and that is exactly where loop-engineering's fleets get their work.
  • Transfer is unproven: SLUMP reimplements ML papers, a domain with unusually crisp ground truth. Messy product specs with stakeholders and no answer key are the untested case.
