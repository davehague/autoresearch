Spec-driven development: the contract lives outside the agent

As of 2026-07, two independent T1 results — approaching from opposite ends — converge on one instruction: the specification is a contract, and the contract must be held outside the agent. The agent cannot critique a spec: given a design proposal, the codebase, and RFC history, the best agent tested finds only 44.4% of the proposal's defects — it misses more than it finds [T1] (SpecBench). And the agent cannot retain a spec that arrives in pieces: holding requirements constant and varying only delivery, handing everything over upfront beats letting the spec emerge across ~60 progressive requests on 16/20 papers for Claude Code and 14/20 for Codex [T1] (SLUMP).

Neither job goes to the model. A human reviews the spec; a durable artifact tracks it.

This indicts the default workflow. The emergent condition SLUMP measures — disclosing the design request by request as you think of it — is exactly how every chat-first agent product invites you to work. That workflow now has a measured cost in artifact faithfulness and structural integration, on both platforms tested. "Write the spec first" graduated from taste to effect size.

Hand the spec over whole, and track it in external state

SLUMP's second contribution turns the negative result into a positive instruction. ProjectGuard, an external project-state layer that maintains what the spec so far commits the project to, recovers 90% of the faithfulness gap on the worst-degrading platform — fully faithful components 118 → 181, severe failures 72 → 49 [T1]. This is the same externalize-the-durable-state rule unattended-operation reached for the run, applied here to the contract.

What the tracker holds matters. The same week's evidence includes a T1 negative against the naive version: generic memory scaffolds degraded all 10 models tested on long horizons [T1] (Beyond pass@1). The reconciling hypothesis — structured state about the task's contract helps; unstructured recall of the agent's own history compounds drift — is stated in both maps and tested in neither. Until someone runs the head-to-head, track the spec, not the transcript.

The human spec review is a load-bearing gate

SpecBench places the agent's weakest phase precisely where teams are most tempted to skip human effort: upstream, before any code exists to react to. Without execution feedback, agents reason poorly about specs in the abstract — omissions, ambiguities, inconsistent assumptions, the things a maintainer catches in RFC review [T1]. So the human-in-the-loop spec review is not optional polish; it is the one gate positioned exactly over the model's measured blind spot. The trade-off is real and worth naming: this is the slowest, most senior-time-expensive step in the pipeline, and the evidence says it is the wrong one to automate away.

Under-specification is priced at the action layer too

What does the agent do under an incomplete spec? It acts anyway. Strip identifying bits of the target from a DevOps instruction and 55.8–67.8% of acted runs violate an action boundary; refusal stays at or below 2.5%, and cues about blast radius do not slow the agent down [T1] (UnderSpecBench). The damage is driven by target underspecification (wrong-target rate 9.6% → 75.1%), while weak intent wording is recoverable when the target is unique. The ticket-writing corollary is cheap and concrete: a fully qualified, unique target buys more safety than any amount of intent prose [T1]. Whether the agent asks a clarifying question instead of guessing turns out to be largely a harness affordance — a 3× ask-rate difference with the model held fixed — which feeds the open question below.

What to do

  • Write the spec before the session, and hand it over whole; incremental disclosure measurably corrupts the artifact [T1].
  • Route the spec through human review before code — the agent misses most spec defects, and this gate sits exactly where it is weakest [T1].
  • Maintain the spec in a durable external tracker the agent consults; contract-state recovers most of what emergence costs [T1].
  • Do not confuse spec tracking with memory: generic self-history scaffolds degraded every model tested [T1].
  • In every ticket, fully qualify the target (which file, which resource, which environment); target specificity outperforms intent prose at preventing wrong-target actions [T1].
  • Treat an under-specified ticket as the expensive case — route it to a clarify-first pipeline rather than the standard one [T1].

Where this connects

Downstream, the same asymmetry appears at the diff: the agent is weak at critiquing its input contract just as it is weak at certifying its output — agentic-code-review holds that side, with its own quantified self-assessment failures. Spec critique is a context-heavy task, and ProjectGuard is a context-engineering intervention wearing a spec-tracking label — context-engineering shares the memory-scaffold tension in full. The ticket's target specificity doubles as a governance control (runtime-action-governance), and if the Claude Code / Codex divergence turns out to be harness-side, part of this map's central finding migrates to agent-harness-architecture.

Open and contested

  • Model failure or harness failure? Claude Code suffers severe semantic faithfulness loss under emergent specs; Codex barely degrades, and SLUMP does not isolate why. A mechanism of the right shape exists — harnesses differ 3× in whether the same model asks instead of guessing — but nobody has run SLUMP's protocol across harnesses with the ask-affordance as the variable. If the gap is harness-side, "agents lose emergent specs" is really "some harnesses do," and the fix is a feature, not a workflow discipline.
  • What should the tracker track? Contract-state (helps, one T1) vs self-history (hurts, one T1) has never been tested head-to-head on one task set. It is the most decision-relevant unrun experiment this map touches.
  • Does a human-refined spec measurably improve downstream code? Both sources measure the spec layer's failure; neither measures the delta from fixing it.
  • Ticket decomposition — the middle of the pipeline — is unmeasured by anyone. Spec critique and spec retention are covered; spec → tickets is not, and that is exactly where loop-engineering's fleets get their work.
  • Transfer is unproven: SLUMP reimplements ML papers, a domain with unusually crisp ground truth. Messy product specs with stakeholders and no answer key are the untested case.
