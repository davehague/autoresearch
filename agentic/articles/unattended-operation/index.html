Unattended operation: the process is disposable, the state is not

As of 2026-07, three organizations running agents unattended at scale have converged on one design rule from different directions: make the durable unit of an agent its externalized run state, not the process running the loop. A crashed harness should be boring — reboot, read state, resume. Anything the process holds only in memory is something a restart destroys, and unattended systems restart constantly.

The convergence is unusually clean because each org implemented it at a different layer, and it worked at all four:

  • Infrastructure: Anthropic keeps a durable, replayable session event log outside the harness process; a restarted harness replays to exactly where it died [T2] (Scaling Managed Agents).
  • Repository: Anthropic's long-running-agent harnesses persist a progress file, a feature_list.json whose entries stay failing until verified, and descriptive git history — a fresh session (or a recovered crash) re-enters through the artifacts [T2] (Effective harnesses for long-running agents).
  • Tracker: OpenAI's Symphony daemon recovers from restarts without a persistent database by reconciling against ticket state — the issue tracker is the control plane and the recovery record [T2] (Symphony).
  • Workflow engine: Cursor moved its agent loop onto Temporal durable execution after a work-stealing design that died with its process; machine state and conversation state are decoupled so each recovers independently. This carries the pattern's first effect size: reliability ~90% → ~99% at 50M+ actions/day across 7M+ workflows [T2] (What we've learned building cloud agents).

One number, three orgs, four layers, no counterexample in the vault. This is as settled as unattended-agent practice currently gets.

The orchestrator is the first responder — and stall detection is not enough

Nobody watches an unattended fleet, so the layer above the agent must do what an on-call human would: stall detection, automatic restart, exponential-backoff retries, structured logs as the operator surface. Symphony bakes each of these into its spec — engineers file work from a phone and trust pickup [T2]. But restart-on-stall catches only the agent that stops, and the expensive failure is the agent that doesn't.

Two T1 results converge on the same missing primitive: a kill rule. Frontier models melt down on up to 19% of long runs — confident, ongoing, token-burning wrong work that a liveness check reads as healthy — and the Meltdown Onset Point names where it begins [T1] (Beyond pass@1). Argued from inside the coding trajectory, the price is concrete: when recovery fails, only 18% of runs terminate — 82% keep executing without progress, and "repairs the wrong problem" alone is 39% of all wasted computation [T1] (Failure as a Process). The agent essentially never terminates itself. So the first responder needs a no-progress detector — repeated failed repairs of one symptom, edits advancing no tracked objective, a run past its MOP — wired to kill-and-restart from durable state. Capability makes this worse, not better: stronger models attempt more ambitious strategies, and ambition is a variance source. (Relatedly, the same reliability study found generic memory scaffolds degraded all 10 models on long horizons — externalize the run's contract and verified progress, not a transcript of its own recollections; context-engineering carries that tension in full.)

The operator surface has an unexamined dependency worth stating plainly: it assumes the code being operated is instrumented, and increasingly it isn't. Agents change logging less often than humans in 58.4% of repositories, under-log precisely in the conditionals and loops where an operator needs signal, and ignore instructions to do otherwise (8.3% compliance from a context file), with humans silently backfilling 72.5% of the gap [T1] (Do AI Coding Agents Log Like Humans?). An unattended fleet operating a codebase its own agents wrote is operating one with thinner instrumentation than the practice assumes, which raises the price of every incident this map's advice exists to survive. Nobody has yet linked the gap to an MTTR or a failed recovery — the dependency is logical, not empirical — but the mitigation is already in the toolkit: gate instrumentation mechanically (observability linters, CI), because asking does not work (runtime-action-governance).

Credentials: attested once, deeply

Never let a sandbox executing model-generated code hold a reachable credential. Anthropic brokers secret-requiring actions (git push, OAuth-scoped calls) through infrastructure or an MCP proxy, and Cowork's sealed-VM pattern keeps credentials in the host keychain, outside the VM where generated code runs [T2]. Honest caveat: this is one vendor's practice described at depth. Cursor names secret redaction and credential management as cloud-agent infrastructure without comparable detail, and Symphony's spec explicitly declines to mandate a sandbox/approval posture. Treat credential isolation as strongly advised, single-source attested — not cross-org settled.

Unattended operation is arriving in the approval path, unplanned

The map's advice is to build the operator surface deliberately. The adjacent warning, now measured: if you don't, capacity pressure will build one for you in the wrong place. As agent throughput doubled at a real firm, the human review gate did not scale — automated review climbed from ~19% to ~84% of PRs and overtook human review, substantive human review fell from ~39% to ~21% [T1] (AI Writes Faster Than Humans Can Review). Unattended operation is not only a property of the agent's runtime; it spreads to the approval path by throughput alone. If you run agents at volume, the automated gate is part of your unattended system whether you designed it or not — see agentic-code-review for why its false-negative rate is the exposure.

What to do

  • Externalize run state at whatever layer you already operate well — event log, repo artifacts + git, tracker state, or a durable workflow engine. All four are attested; composition between them is unexamined [T2].
  • Mark work failing-until-verified in the durable state; a resumed session must re-derive "done" from artifacts, never from the previous process's optimism [T2].
  • Give the orchestrator restart, backoff, and stall detection — plus a no-progress / meltdown kill rule, because 82% of failed-recovery runs never terminate and liveness checks read them as healthy [T1].
  • Gate instrumentation mechanically; an unattended fleet running agent-written code inherits thinner logging than the operator surface assumes [T1].
  • Broker credentials; never place them inside the surface that executes generated code [T2].

Where this connects

Durability is this map; boundedness — what the live run may do — is runtime-action-governance, and credential isolation sits on the shared boundary. The externalized-state rule is the same instruction spec-driven-development reached for the contract (an external spec tracker recovered 90% of a faithfulness gap) and context-engineering measures as state decay. The no-progress kill rule is the operational face of observability's first-wrong-step localization. The always-on orchestrator is where this map meets loop-engineering's fleets, and the automated approval gate is where it bleeds into agentic-code-review; retry cost under failure is now a measured architectural property at the harness layer (agent-harness-architecture).

Open and contested

  • The ~90%→~99% reliability win is whole-system, one org, one stack; per-incident recovery-rate and work-lost accounting still doesn't exist anywhere.
  • Credential isolation remains single-vendor at depth; Symphony's silence on sandboxing is a deliberate spec decision, which means the field's most-adopted orchestration spec ships without a credential posture.
  • The operator surface's instrumentation dependency is unpriced — the logging gap is measured, but no one has linked it to an incident, an MTTR, or a failed recovery in an agent-operated codebase.
  • No one has published what a fleet's kill rule costs in false positives — healthy, ambitious runs terminated at the meltdown/no-progress threshold.
  • When to prefer which durability layer — or how event log, artifacts, tracker, and workflow engine compose — is unexamined; four attested layers make that question sharper, not answered.
