Durable Execution Engines Do Not Supply Barrier Semantics

Durable execution is the pattern this vault credits with the first quantified reliability win for unattended agent operation (Cursor's move to Temporal, ~90%→~99% reliability at 50M+ actions/day). It is natural to read "durable" as implying the run is also safe to pause — that an execution engine solving crash-recovery and exactly-once side effects has, along the way, made human-approval pauses trustworthy too. This paper runs its model-free sibling-leak and reject-after-effect probes directly against Temporal and separates the two properties empirically rather than by argument.

Replay is genuinely closed by construction on Temporal: a forced full-history replay after a worker shutdown returns each activity's already-recorded result rather than re-executing it, verdict- identical across repeated runs and across two checked server releases (1.31.1–1.31.2) — durable execution does exactly what it promises on the double-execution axis, and Temporal is explicitly excluded from the paper's recurrence denominator because it isn't one of the frameworks failing here. But the pause barrier the map's reliability story doesn't claim is separately absent: with a documented Signal-based human-approval wait (awaiting_decision) and a side-effecting activity as siblings under asyncio.gather, the sibling's effect commits while the workflow's queried state is still awaiting_decision, before any decision is delivered — so a subsequent rejection is powerless, the identical failure mode measured on the unrepaired frameworks. The paper is explicit that this is "behavioral only," not a documentation contradiction — nothing in Temporal's docs implies awaiting a Signal in one branch pauses its siblings. The fix travels cleanly: the same ~20-line external-gate wrapper pattern used elsewhere in the paper, applied at Temporal's activity boundary, holds the sibling's mediated effect during a live Signal pause and releases zero effects on rejection — "the pause barrier must be an admission point in any engine, and the same environment-external gate supplies it on this one unchanged."

The actionable read for an unattended-operation stack: adopting a durable-execution engine buys crash-safety and idempotent replay, and that is a real, separately-proven property worth having — but it is not evidence that an approval gate riding on top of it enforces "nothing happens until the human decides." That guarantee has to be added explicitly, the same way it does on a bespoke framework scheduler; durability and admission control are orthogonal layers that happen to be easy to conflate because both get described loosely as "safety."

Caveats: this is one contrast experiment against one durable-execution engine (Temporal), run by the probe author using the documented Signal-based HITL pattern, not an exhaustive audit of Temporal's API surface or of other durable-execution engines (AWS Step Functions, Azure Durable Functions are discussed only in the paper's related-work survey, not measured). The finding is "behavioral," per the paper's own framing — it does not allege a documentation defect, only an unstated assumption an operator could reasonably make. Single-author, unreviewed arXiv preprint.
