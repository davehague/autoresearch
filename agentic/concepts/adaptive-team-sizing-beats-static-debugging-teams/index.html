Sub-thread (1)'s multi-agent-coordination question gets an instance where the coordination decision itself -- how many agents, which roles -- is made dynamically per task rather than declared once in advance, and the resource savings it reports are exactly the overhead this map's adherence-measurement finding warns gets paid even when it doesn't need to be

This map's adherence-measurement finding (adherence-adjusted-estimate-reverses-the-sign-of-a-coordination-gain) showed that a declared multi-agent organization is realized at runtime only 47.2% of the time under unconstrained defaults, and that a fixed team topology pays coordination overhead regardless of whether the task needed it. ASAD attacks the same problem from the design side rather than the measurement side: instead of fixing agent count, roles, and interaction pattern before looking at the bug, it analyzes the fault first (AST depth, program-understanding difficulty, localization) and routes to a single agent for low-complexity cases or assembles a purpose-built team only when the analysis says the task warrants it. The headline numbers read as a direct resolution of the inefficiency this map's adherence finding implies is being paid by fixed-topology systems: 4-9% better fix precision than static multi-agent baselines while using 32% fewer agents on average — the efficiency gain is not a trade against quality, both move together, because the agents not spent on simple bugs are available (in the sense that the design choice generalizes) for the complex ones that actually need them.

The benchmark-stratified result is the more interesting shape for this map: the gain over static approaches is not uniform across difficulty — on Defects4J, the hardest of the three benchmarks tested, where static methods achieve only 6.8-13.2% fix rate, ASAD roughly triples it to 22.1-32.5%, while on the easier DebugBench and CodeFlaws benchmarks (where static methods already clear 50-65%) the relative improvement is proportionally smaller. That is the signature this map would expect if the mechanism is real: a fixed-size team is closest to correctly-sized by accident on easy bugs (where even one agent's worth of capability may suffice) and furthest from correctly-sized on hard ones (where a static team sized for the average case is under-resourced for a genuinely complex fault) — complexity-matched allocation should help most exactly where this map's existing static-coordination sources are weakest, and that is where it does.

Ablation controls (a fixed-team and an "ASAD-Max" always-maximal-team variant) isolate the adaptive routing decision from merely having specialized roles available, which rules out "more roles always helps" as the explanation. Scope: evaluated on three established research benchmarks (DebugBench, Defects4J, CodeFlaws) rather than production incident data or a live coordination-adherence measurement of ASAD's own runtime behavior — so this map's own adherence-auditing method (adherence-adjusted-estimate-reverses-the-sign-of-a-coordination-gain) has not yet been applied to check whether ASAD's declared adaptive routing is itself realized as described at runtime, which would be the natural next measurement connecting the two sources. The efficiency claim is denominated in agent-count rather than tokens or wall-clock, so it is not directly unit-comparable to this map's or model-routing-token-economics's cost findings without a conversion.
