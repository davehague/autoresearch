A second, same-night instance of the on-demand-vs-always-shown cost asymmetry, in a different task domain

This map's sub-thread (1) just gained a quantified instance of on-demand loading retaining only part of an always-shown benefit, in coding-agent Skills (skill-revisions-pay-less-under-on-demand-loading). This paper runs a structurally similar comparison — on-demand skill-loading versus an always-present playbook — in agentic ML-engineering rather than coding-agent instruction-following, and the cost side of the finding converges cleanly: a playbook that places every insight in the initial context pays token overhead for insight content the agent will never use in a given run (25.2% more input tokens than baseline), while on-demand loading pays only for what's actually read (7.7% more) — the same mechanism, "always-present costs more because it can't discriminate relevance," expressed as a token-cost ratio rather than an action-rate shortfall this time.

Where this paper differs from, rather than merely repeats, that finding: here on-demand loading does not cost effectiveness — Full-skill (123.9%) and Full-playbook (122.8%) land within a point of each other on the score that matters, with "which mode wins" varying by task rather than skills systematically underperforming. That is a genuinely different outcome from the Skills-revision paper's result that on-demand loading keeps only 51%/38% of an always-shown behavioral gain. The two results are not in tension — different injected content (static best-practice insights with trigger-action structure vs. a dynamic instruction revision tied to one specific request) and different outcome granularity (a long-horizon multi-step solution score vs. single-decision compliance) — but the map's persist-and-deliver sub-thread now has its first case where on-demand delivery matches an always-shown ceiling on effectiveness while still winning on cost, next to a case where on-demand delivery loses on effectiveness too. The open question this pair raises and neither answers alone: what property of the injected content (structure, specificity to the immediate decision, length) predicts which regime a given insight/skill falls into.

Complementary-insight-types finding is the paper's other contribution worth carrying: no single insight type (domain/competition/improvement) does most of the work alone (8-9 of 12 tasks each vs 11 combined), which is a concrete argument against collapsing a context-delivery system to one insight source — the map's existing persist-and-deliver findings have mostly compared whether to deliver content, not how many independently-useful kinds of it exist.

Single self-released benchmark and technique, one primary backend LLM for the main comparison (a second model checks generalization but is not a full replication), 12 target tasks. Does not move this map's status — confirms and sharpens sub-thread (1)'s cost/effectiveness distinction rather than resolving the live decay-vs-absence instrument dispute.
