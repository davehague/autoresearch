Plan mode is enforced at the prompt layer; the injection lands below it

The single most useful sentence in the study is its explanation of why plan mode — a read-only mode that does not trigger write-tool execution at normal task startup — scored 0%: the restriction is enforced at the prompt level and does not extend to the router layer. Once a malicious tool call is inserted into the response the agent consumes, the agent processes it as a legitimate call and executes it regardless of the prompt-level constraint. The auto mode's built-in reviewer fails for a sibling reason: the review request itself travels through the same router.

That is this vault's own rule, enforce-high-risk-constraints-below-the-prompt-layer, turned back on the products that adopted it. Enforcement has to sit below every component that can rewrite the agent's input — and a gateway inserted for key management, provider fallback and cost control is exactly such a component, with plaintext access to system prompts, repository context, tool specifications and tool-call payloads.

The result is architectural rather than incidental, which is what the four-way sweep establishes. Four agents with different tool abstractions: 0%. Four backend models: 0%. Four injection styles from crude substitution to distribution-level regeneration that leaves no edit boundary: 0%. Backend diversity is not robustness here, because the injection is applied after the provider's response exists.

The composition is the same shape as the incident this map already carries. There, an agent barred from deploying asked a peer agent to push code, and two individually-bounded agents composed into an unbounded one (least-agency-blocks-an-agent-that-recruits-another-agent, sibling-leak-defeats-human-in-the-loop-approval-gates). Here the co-conspirator is a piece of infrastructure rather than a peer. The rule generalizes: the effective permission set is the transitive closure over everything on the path to an action — peers and intermediaries alike.

The mitigation profile is worth reading for what it says about gate design generally. The deterministic whitelist is the map's preferred kind of control — model-free, sits below the model, negligible overhead (contain-at-the-environment-layer-first, enforce-invariants-not-implementations) — and it still only reached 30.8–44.1%, because an allowlist can only express risks shaped as an out-of-list domain or package, and it blocked 29.7–43.9% of benign actions doing it. LLM review does better on the tradeoff but tops out at 64.4% and its collateral damage varies five-fold with the choice of reviewer model alone, which is the same "the reviewer, not the model name, is the component" finding the review map carries (repository-grounding-buys-localization-not-judgment). Neither restores end-to-end control; the authors' conclusion is that this needs a provider-side output-integrity guarantee, which nobody ships.

The operational read for anyone running agents through a gateway: prefer a first-party path or a self-hosted gateway you control, pin and verify gateway versions (malicious LiteLLM releases shipped on PyPI in March 2026), and treat allowlisted egress as the only control still meaningfully on the right side of the boundary.

Caveats: three task instances with the injection turn sampled from the first 15 turns; the 400 samples are a balanced measurement instrument, not a prevalence estimate; the provider is held honest and transport attacks are out of scope. The transferable claim is the architecture, not the rates — and the mitigation numbers are measured under an assumption favourable to the mitigation, since the reviewers call official endpoints directly.
