Decompose into a DAG, dispatch to isolated sub-agents, forward-and-stitch

MACU's loop shape: a manager expands the task into a directed acyclic graph, dispatches sub-agents to run the independent nodes concurrently, and re-plans as results arrive. The non-obvious part is state: each sub-agent only observes its own slice (partial observability), so the manager retains and forwards the distilled output of each completed node to the downstream nodes that depend on it — an explicit stitch step, not shared memory. That's what lets parallel isolated workers cohere into one result instead of drifting.

The generalizable principle, independent of the computer-use domain it was measured in: long-horizon work wants a central manager + isolated parallel sub-agents + an explicit forward/merge step, not a single agent grinding one serial context. It is the loop-engineering analogue of context-engineering's sub-agent-isolation pattern (each sub-agent returns a distilled 1–2k-token summary) and of the harness-layer planner/generator/evaluator split (decompose the roles). See also isolate-and-merge-parallel-agent-work, which reaches the same architecture in the SWE domain but reconciles through git merge instead of manager-forwarded state.

Caveat: GUI/computer-use benchmarks; the percentages are regime-dependent. Same-orbit org (CMU) as the SWE-agent source, so this is a convergent principle, not yet cross-org replication.

Rebutted by: pre-write-admission-buys-reliability-by-serializing — the only coordination study here that ran an explicit always-serial reference arm found its best parallel arm matching that arm exactly rather than beating it (50.0% vs 50.0% pair pass, identical within every task cluster), so "beats a single serial agent" is a claim this map's parallel results have mostly not tested.
