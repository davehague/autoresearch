Harness interchangeability is asserted, not measured

Around June 2026 a product category appeared from unrelated vendors at once: a meta-harness, a layer sitting above the coding agents rather than inside one. Databricks' Omnigent is the best-documented instance — "a meta-harness that sits above the agents you already use (Claude Code, Codex, Pi, or custom agents) and makes them interoperable parts of a richer system," wrapping each in a sandboxed session behind a uniform API, with policy and sharing on top. The repo adds Cursor, OpenCode and Hermes. The generator variant mints bespoke harnesses per repository instead of orchestrating existing ones (harness-self-evolution-shipped-ahead-of-its-evidence).

The category's load-bearing promise is composition: combine or swap harnesses without rewriting. That is a claim about the world, and it is the claim this vault has the most evidence against. Holding seven models fixed across 260 tasks and varying only the harness moves scores by a mean 8.6 points, changes rank order, and moves one cell 13.5 points (the-harness-shifts-benchmark-rank-order). A security outcome reverses outright on a harness swap with the model and repository byte-identical (install-time-security-is-a-harness-model-pair-property). A progressive-disclosure context pack is worth double digits under one harness and exactly zero under another (progressive-disclosure-buys-context-not-intelligence). A byte-identical skill library is read on 99–100% of tasks under one stack and 0–1% under another (skill-invocation-rate-is-a-harness-property). Field defects exist only in the reaction between a model's output and the harness parsing it (agent-reactive-bugs-need-both-components-to-explain).

So the distinction to hold onto: a uniform API makes harnesses substitutable at the call site. It does not make them equivalent in outcome. Everything a team would need to use one of these layers well — which harness to route a given workload to, what the swap costs, what breaks when a workflow moves from Claude Code to Codex — is exactly what the pair thesis says must be measured per pair, and exactly what no product in the category publishes. The honest status is an open question, not a refutation: it is entirely possible that a mediating layer with per-harness adapters is the right place to manage the non-equivalence. The adapter tables in these projects are tacit evidence they know it exists. Nobody has measured it.

What a practitioner should do with this now: treat harness portability as a migration, not a configuration change, and re-run your own evaluation on the target pair before trusting a workflow that moved (re-examine-the-harness-when-the-model-changes, attribute-performance-to-the-stack-not-the-model). The value proposition that survives the pair thesis untouched is the governance half — policy, sandboxing and spend caps enforced at the runner, below the prompt, on the dispatch path the harness already mediates (enforce-high-risk-constraints-below-the-prompt-layer, contain-at-the-environment-layer-first). That does not depend on harnesses being equivalent, only on their being wrapped.

Caveats: this note grades a category from its two best-documented instances, and one vendor post is thin evidence for a trend. Both projects are alpha. No claim here is that the category is wrong — only that its central premise is currently unevidenced in either direction, which is why this is carried as an open question at single-study strength and moves no map status. The counter-measurement that would settle it is cheap and specific: run one workload across two harnesses through the same mediating layer and publish the delta.
