The map's oldest open question, answered on the test side

This map has asked one thing repeatedly and never got an answer: does a better specification measurably improve the downstream artifact? agents-are-weak-at-spec-critique and emergent-specs-corrupt-the-artifact measure the spec layer failing. elicit-the-spec-in-its-own-phase-before-synthesis establishes that a separate elicitation phase pays. converge-the-spec-against-the-code-before-freezing-it adds a refinement loop with n=1 behind it. None of them measures the delta from fixing the spec, because in every prior source the specification and the artifact moved together.

This one separates them, on 90 real production bugs from a monorepo, with the same model and harness on both arms and only the phase structure varying. +9.8 points of historical-bug detection at k=5, McNemar p=0.0352, and +2.5 points of branch coverage at p=0.0034 while line coverage is flat and non-significant — a decomposition that tells you what the scaffold actually does. It does not make the agent write more test; it makes it write test that reaches into branches, which is where boundary and error behaviour lives.

The mediation is the part that turns this from an effect into a mechanism, and it is the strongest single number here. A separate judge, given the bug description, the developer's commit message, the ground-truth fix diff and the generated .spec.md, decides whether the specification documented the contract the bug violated. Conditioning on that: 54.9% detection when the contract was captured against 19.4% when it was not, Fisher p = 3.62 × 10⁻¹⁴. That is what distinguishes "the contract helps" from "any intermediate reasoning step helps," because the intermediate step was performed in both halves of the split — the only difference is whether it landed on the right obligation. It also directly narrows the spec-driven practice: what pays is not the ritual of producing a document, it is coverage of the obligation that will be violated, which is the thing the-specs-format-is-not-what-pays had already ruled out being about notation.

Two design details make the result readable rather than merely favourable. The greenfield setup strips the existing test suite entirely, which removes the two cheapest shortcuts — copying established test structure and doing test repair — and forces both arms onto code understanding. And the post-execution sanity check discards, without repeating, any run in which the agent modified the source under test or any other pre-existing source file, because letting an agent alter the code it is testing turns its own injected faults into apparent detections. That check is worth stealing outright by anyone evaluating an agent that writes tests; it is the false-positive path nobody prints.

Where it breaks is a taxonomy, not a shrug. 141 runs failed at the specification layer — omitted methods (35), happy-path-only documentation missing exceptions and fallbacks (32), omitted data transformations (27), acknowledging a constant or format while abstracting away its exact value (25), and missing execution ordering, negative constraints and boundary conditions (22). A further 110 runs captured the contract and still failed downstream: inadequate input data (37), ignoring explicit specification statements (36), weak or overly broad assertions (20), flawed test logic (12). The split is directly actionable, because the two halves want different fixes — better extraction versus better synthesis — and this is the first source here that can tell them apart.

The human-in-the-loop lever is unmeasured, and the paper is explicit about why. The framework supports a curation step between the two phases, and the evaluation bypasses it, accepting every agent-generated suggestion autonomously to avoid introducing subjectivity. So the 63.2% is the fully automated floor, and the obvious next arm — a developer reviewing and amending the .spec.md before synthesis — is exactly this map's long-standing "does a human-refined spec improve downstream code quality" question with the apparatus now built to answer it.

Bounds. One model family, one organisation's monorepo with its own style guides and review culture, and only fixes touching a single production file. Historical bugs are an established regression-testing protocol and are not the same as finding new defects. Contract coverage is judged by an LLM (a stronger model judging a weaker one, five runs, strict majority) and has no precision counterpart, so over-specification and hallucinated contracts are unmeasured. The baseline already does chain-of-thought natively, so this is a comparison against a reasoning baseline — but not against other structured scaffolds like explicit test planning or execution-trace modelling, which the authors name as unrun.
