Agents pull documentation forward into the work, not backward out of a failure — and troubleshooting guides are not a recovery resource for them

Two assumptions get separated here, and they fail in opposite directions.

The first survives. This vault's acquisition model has been converging on demand-driven retrieval — just-in-time-context-retrieval as the design, condition-retrieval-on-the-phase-the-agent-is-in as the refinement, dynamic-context-beats-static-preloading as the comparison. This is the behavioural counterpart measured in the wild: 70.2% of documentation interaction is the agent's own move, not a response to a user instruction (20.4%) and emphatically not a response to a failure. The human-developer literature spent two decades trying to encourage exactly this behaviour among people; agents do it by default. Documentation interaction also occurs in more than half of sampled sessions (56.7%), so it is a routine part of the loop rather than an occasional detour.

The second does not. The framing of documentation as the thing an agent reaches for when it gets stuck has no support here. Across 2,034 failure episodes the agent reads documentation first in 5.4% — it reads code first six times as often, and it retries the identical failing action four times as often. P(read doc | tool error) is 0.020. And the genre written specifically for this moment, troubleshooting documentation, is eleven events across 94,813 extracted development events.

The methodological detail worth carrying is the authors' refusal. Documentation-based recovery has the highest point estimate of subsequent resolution — 63.6% — and they decline to report it as a finding, because only 11 of those 109 episodes have an observable outcome and the interval spans 35.4–84.8%, overlapping every other strategy. That is the same discipline this vault applies in report-a-null-as-a-bounded-interval-not-a-failed-test, applied to a positive point estimate that would have made a better headline. The open question they leave — whether documentation-based recovery is genuinely more effective — is the one worth funding, because if it is, the 5.4% is a large unexploited margin rather than a fact about what agents need.

What a practitioner does with this. Write for the agent that is making progress, not for the agent that is stuck, because the second one is going to read your code. That is a reallocation away from troubleshooting prose and toward whatever the agent is already opening — which the-documentation-agents-open-is-the-documentation-agents-wrote measures as instruction files and its own notes. It also means the recovery path is where instrumentation belongs rather than documentation: an agent that retries the identical failing action in 19.9% of episodes is not going to be rescued by a better runbook, which is the same lesson as recovery-is-a-property-of-the-fault-not-the-model and fail-loud-instrumentation-over-plausible-substitutes.

Bounds. Trigger is inferred from a fixed four-event lookback, and the authors flag that a read prompted by anything outside that window most likely lands in "agent initiative" — the largest bucket and therefore the one most exposed to the error. Purpose is not coded at all, by design, because intent is not recoverable from tool-call logs. Outcome detection uses regular expressions over tool output, and resolution rates are computed only for the 662 of 2,034 episodes with an observable outcome, so a selection effect the authors cannot quantify may bias them. Opt-in telemetry, 87% from one agent family, path-based identification only, and per-agent rates confounded with extraction coverage.
