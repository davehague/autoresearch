A provenance field that always returns the same answer looks exactly like a provenance field that works

This map's standing demand is that a governed action leave behind evidence a third party can check — claims against what was gathered (audit-agent-claims-against-trajectory-evidence), the first wrong step localized, the approval artifact actually recording that someone judged (the-approval-artifact-never-recorded-that-anyone-judged). This is a small, concrete failure of that demand, found by review rather than by design, and it is the kind that survives indefinitely because the field is populated.

The record is one line per decision and it is unusually complete: the action's context, each gate's own section with its inputs and verdict, the substitution's pre- and post-values and the buffer key it drew from, every record identifier, the final join, the winning gate, and which remediation operators fired in which order — that last field existing only because operator order turned out to be semantically load-bearing (remediation-order-is-part-of-the-control-plane). Ground-truth labels are deliberately absent and kept in a separate run log, so the audit surface cannot be scored against an answer key it was never supposed to see.

The defect. The identifier for "which governed write did this substitution draw from" was a hash of the write's key and value. Two writes of the same value for the same key are therefore the same identifier, and in a system that repeatedly substitutes a small set of governed values, that collapses almost everything: 3,478 real substitution occurrences resolving to 62 unique ids. The field was present, well-formed, and schema-valid on every line. It simply could not answer the question — which write, not which value — and nothing short of counting distinct ids against distinct events would have shown it. The repair is a durable run-scoped write-history log persisted next to the evidence lines, so each substitution resolves to exactly one write event.

The generalisable rule: an identifier derived from an artifact's content answers "what", never "when" or "which occurrence". Any audit trail that has to support "trace this decision back to the event that produced the value it used" needs an event log, not a content hash, and the cheap test for whether yours does is to compare the count of distinct identifiers against the count of distinct events.

The second half is what the record does not promise. An earlier draft claimed the line lets a reader reconstruct the original bytes. An independent review refuted it and the claim was retracted; the surviving proposition is an identity commitment and lineage binding — from the line alone you can name, by content-addressed id, every record each phase relied on including the pre-substitution evidence, and verify those identities given access to the record store and the write history. It does not establish source authenticity, semantic truth, or that the referenced bytes still exist, and it assumes collision resistance at the deployment's security level. That is a narrower guarantee than "full provenance", and stating it narrowly is what makes it usable — the same discipline as gate-lifecycle-claims-on-fresh-hash-bound-evidence, where a hash binds a claim to a moment rather than proving the claim.

Bounds. A deterministic mechanism-demonstration artifact with zero model calls, so this is an audit record for a control plane rather than for an agent trajectory; the transfer to trajectory logging is structural and untested here. The schema-level checks behind the proposition are described by the paper's own claims table as checker-adjacent unit tests rather than an exhaustive model check, and the proposition is tagged checked-scope-only.
