The gate that answers with yesterday's decision

Every layer this map recommends ends at the same place. Deterministic containment first, a contextual classifier second, human escalation last. The escalation layer is the one that is supposed to hold when the others fail, and it is the only layer whose correctness this vault has never audited at the mechanism level. Two findings here audit it, and both are failures of the plumbing rather than of the model.

Fork determinism. A one-node graph parks on an interrupt. The probe records the interrupt checkpoint's id and issues two resumes to the same (thread_id, checkpoint_id) — the address the framework's own persistence documentation presents as the branch-creating time-travel primitive — carrying True and then False. Both return value 1. The second answer is durably recorded and never consulted. Rendered into the deployment: a reviewer who approves, thinks better of it, and answers the same approval again with a different decision is served the first decision's consequences, and the gated tool fires a second time with the stale value. It reproduces on all three checkpointer backends including a live PostgreSQL server, on both invocation forms, at every release across a year, and — with a real ReAct agent and a real side-effecting tool — 40/40 on each of two Claude models, 80/80 overall, across two hosts.

Consume-once under concurrency. The same parked interrupt, answered by two OS processes from a spin-barrier start: the gated effect fires twice in 10/10 repetitions, on SQLite and on live PostgreSQL, with no error on either side. The pre-gate effect fires exactly once, so the duplicate is the gated node alone rather than a replayed prefix. Byte-identical re-delivery — the arm that is inert when the two resumes arrive sequentially — is the arm that duplicates. When the racers carry different values, both values fire and each racer is served its own. The failure crosses hosts. Distinct threads under the same contention are unaffected, which localizes it to same-thread resume rather than to the store's write path. And afterwards the durable state records one branch, so the double-fire is invisible in framework state and visible only in an external effect ledger.

This is the third distinct way this vault has watched an approval barrier fail without anyone lying to it. sibling-leak-defeats-human-in-the-loop-approval-gates found a sibling's side effect committing inside the approval wait, before any decision was delivered. durable-execution-engines-do-not-supply-barrier-semantics found the durable-execution engine that fixes replay leaving the pause barrier untouched. This finds the barrier consuming correctly on the sequential path and failing on both the revision path and the concurrent path. The generalization the map already carries — an-intermediary-on-the-response-path-voids-client-side-gates, the effective permission set being the transitive closure over everything on the path to an action — extends one hop further, and the hop is unglamorous: the persistence layer that parks the approval is on the path to the action, and nothing in any agent checks whether it kept its promise.

Two operational consequences follow, and neither requires waiting for a framework fix.

A human approval must be single-delivery by construction, not by convention. If two people can answer the same gate — an on-call pair, a Slack button and a web console, a retried webhook — the gate is not one gate. The paper's own repair is the cheap version and it ships: an opt-in read-path filter that claims consumption in the shared store and refuses the losers loudly before any node executes, taking the cell from 10/10 duplication to {1:10} on both durable backends and across hosts. Claim-then-serve at the read path, not key-then-write.

A changed decision needs a new address. Since a second resume to the same checkpoint is recorded and ignored, the operator surface must not offer "answer again." Cancel the run and re-park it, or route the revision through a distinct interrupt — because the interface that looks like editing your answer is the interface that serves the old one and fires the tool.

Bounds. One framework holds the fork violation, measured on named paths at pinned versions by a deterministic harness, with live cells confirming existence and cross-model/cross-host stability rather than prevalence (at N=40 a true rate as high as 0.09 is consistent with the zero observed in the clean cells). The concurrency failure is measured on the same framework's two durable backends. Single independent author; artifact private pending publication. What generalizes is the class of hazard and the shape of the repair; the per-framework verdicts do not transfer to frameworks nobody probed.
