Strand (2)'s fixed-substrate-cost thread gets a forecasting instrument instead of another point-in-time savings number — and it's accurate enough to spend against, not just report

This map's strand (2) has so far measured the substrate cost as a series of static savings figures — system-prompt trims, dynamic tool loading, cache breakpoints — each a one-time lever pulled and reported as a percentage cut. TokenCast is a different kind of contribution: not a lever but an instrument, a learned model of how much a task will cost before and while it runs, built on a formally derived composition identity that prices the specific mechanism this map's other cost sources have been describing qualitatively — that a token saved early compounds into tokens saved at every later call, because context growth in one segment inflates the input size of every subsequent one. That is the harness-layer mechanism strand (2)'s "strip the harness" sources (system-prompt trims, dynamic tool loading) have been exploiting empirically; this source is the first to give it a mathematical form and a forecast built on it.

The budget-control result (21.3% token savings at matched completion, from forecast-informed stopping decisions with zero added LLM calls) is the map's first instance of a free efficiency lever — every other strand-(2) saving required a harness redesign or an A/B-tested production change; this one is a downstream policy applied to an existing trajectory using a forecast that costs 32.8ms and no model calls to produce. It sits adjacent to strand (1)'s allocation-policy sources (AgentRouter, InflationAgent, SeqRoute) in spirit — all convert a cost signal into a spending decision — but operates on within-task stopping rather than between-model routing, a granularity this map's allocation strand has not previously carried.

Scope: cross-harness transfer degrades (1.04x error ratio moving between DeepSeek Harness and OpenHands), so the forecaster is not harness-agnostic out of the box; zero-shot transfer to unseen models or task types needs modest in-domain adaptation data (as few as 20 tasks, but not zero); no failure-mode analysis for partial or aborted trajectories; reasoning-token opacity for API models with hidden reasoning traces complicates cost attribution in that setting.
