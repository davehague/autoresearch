Where you write the rule is a design decision, and depth is the wrong intuition

Two intuitions die here. The first is that the system prompt outranks the repository's CLAUDE.md — it does not; system prompt, project file and user instruction tie exactly at 2.22 mean conflict rank, each with an identical model-level rank sum of 20. The second is that a rule an agent reliably follows is a rule with authority — also false, and in the most inconvenient direction: skill descriptions are the highest-compliance surface in isolation (78.6%) and dead last under conflict (4.56).

Why the two measurements come apart. Compliance in isolation asks how often is this rule followed when it is the only voice, which is a property of how easy the rule is to satisfy and how well it matches the agent's habits. Precedence asks which voice wins when two demand opposite things, which is a property of perceived authority. A skill description saying "report numbers in base-10" is trivially easy to obey and trivially easy to overrule. The paper keeps the two panels strictly separate and never pools them, and that separation is the contribution as much as either number.

What this changes about how the vault reads skills. a-skill-description-acts-without-being-invoked established that the always-resident triggering description is an unconditional intervention — it acts whether or not the body loads. This adds the boundary: it acts until something disagrees with it, and then it is the first thing dropped. So the description channel is powerful for shaping default behaviour in an uncontested context and worthless as a guardrail. Anything that must hold against a user instruction or a project file does not belong in a skill description or a tool description at all. That is the same conclusion a-standing-policy-decays-into-one-more-retrieved-source reached about long policy documents decaying over turns, arriving from the orthogonal axis — one is decay over time, this is defeat in conflict, and a rule can suffer both.

Direct consequence for David's fleet. A CLAUDE.md instruction carries the same weight as a system prompt in these conflicts, which is better news than expected for repo-level convention files — and it means a project file and a user instruction contradicting each other is a genuine coin-flip rather than a resolved hierarchy, so the two should not be allowed to disagree. Rules that are safety- or cost-critical (never push to main, never spend beyond N tokens, never touch these paths) belong on the surfaces that win, or better, outside the model entirely, which is the standing instruction from a-standing-policy-decays-into-one-more-retrieved-source.

Bounds, and they matter for how hard to lean on the ordering. E0 is a separate, older cohort — nine builds, four synthetic style conflicts, deterministic-only scoring, collected months before the main panel — and the authors interpret it as a robust pooled cross-build tendency, explicitly not a universal or build-invariant hierarchy. The main panel assigns rules to operationally admissible surfaces rather than relocating one rule across all five, so its per-surface rates are descriptive strata, not a controlled surface effect. Four conflict pairs cannot cover the space of ways two instructions can contradict.
