Removal is still the under-used edit, one layer down

This map's 2026-07-22 note was that removal is an under-used harness edit and that where a well-defined mechanical operation exists, taking the model out of the path is the reliability win. Both halves land here at once, on a component nobody had treated as a design decision.

The append-only trajectory is not a considered choice; it is what you get when a tool call and its result are appended in order. It quietly encodes an assumption — that an observation is a fact about the world rather than a reading of a mutable thing — and that assumption is false for every file an agent edits. Fixing it is a structural edit with no model in it: a registry plus a re-read before each cycle. No summarizer, no relevance judgment, no compression, nothing to be miscalibrated (harness-self-evolution-is-capped-by-its-proxy-judge).

It belongs in a sequence the vault has been assembling. Stripping over 80% of a mature system prompt with no measurable eval loss (strip-the-prompt-when-the-model-improves). Stripping 17.9–32.9% of an agent's patch by counterfactual search over its trajectory, with no model reading the trajectory (patch-minimization-is-search-not-generation). Collapsing a coding agent to one execution channel and holding pass rate at lower cost (restrict-the-tool-surface-to-cut-cost-not-capability). And now deleting the accumulated history of file contents. In each case the largest available improvement was subtracting something the harness had been accumulating by default, and in three of the four the subtraction is performed deterministically.

The complementarity result is the part that generalizes as advice: the reactive methods were not wrong, they were downstream. Compression operates on content that has already entered the trajectory, so it inherits whatever the architecture put there. Combining prevention with compression beat either alone on every strategy tested. The design question a harness author should ask first is therefore not "how do I compress this history" but "what is this history storing that it should be querying?"

One property that distinguishes it from most scaffolding this map carries: the gain is largest on the strongest model (−37.3% cycles on Sonnet 4.5 against −15.2% on the weakest), because stronger models sustain longer trajectories. That makes it durable capability rather than model compensation, which is the decision rule this map adopted on 2026-07-20 (separate-durable-scaffolding-from-model-compensation).

Caveats: one baseline (a minimum-viable agent derived from 14 production agents' tool sets) rather than a shipped harness, so this is measured against an unoptimized append-only agent rather than against Claude Code or Cursor as they ship; single run per configuration; whole-file sync only; prompt-cache interaction disclosed and unmeasured.
