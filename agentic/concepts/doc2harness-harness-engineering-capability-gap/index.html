A deterministic, vacuous-pass-controlled benchmark for the one capability this map's self-authored-harness evidence has mostly measured by proxy — can a model actually build a complete, correctly-engineered harness from documentation alone — and the answer is "barely half, even for the best model"

This map's design-lever strand (2) has repeatedly measured what a hand-engineered harness choice buys (Dev-Primitives, bash-alone tooling, typed-tool catalogues), and its pair-attribution strand (1) has measured what happens when a harness is given. Neither strand has directly measured a model's capability to construct a complete, working harness from a specification — the closest prior evidence on this vault is indirect (self-authored-harness studies on harness-self-evolution measure modifying an existing harness, not building one from a documentation-derived spec). Doc2Harness supplies that measurement directly, and does it with a methodological feature most agent benchmarks lack: positive controls that rule out a vacuous pass — a test case can pass not because the harness correctly implements a behavior, but because the implementation never reaches the channel being observed at all (e.g., a path-escape test "passes" whether the implementation blocks an out-of-bounds read or simply can't read any file). 130 of 328 test cases are gated by at least one such control.

The headline number — the strongest of nineteen frontier models passes barely half the suite (53.05%), the weakest barely a quarter (27.44%) — establishes that long-horizon harness engineering from documentation is neither saturated nor a capability every frontier model already has. More useful than the aggregate is where the gap concentrates: the top two models trade places entirely depending on scenario type (Opus 5 leads ordinary scenarios, GPT-6 Astra leads boundary/edge-case scenarios by a wider margin), and a model's rank shifts by as much as sixteen positions across the suite's six categories — harness-building capability is not a single scalar skill, and a leaderboard-style ranking on this benchmark would materially mislead depending on which category of harness work matters for a given deployment. The authors' qualitative read of failures — that higher-scoring harnesses consolidate cross-cutting functionality (features spanning multiple modules, like permission checks touching both file ops and command execution) into fewer modules, while lower-scoring ones scatter it — is a concrete, testable design principle this map does not yet carry for self-constructed harnesses specifically.

Why this is marked an open question rather than confirms/extends a specific standing claim: no existing note on this map makes a directly comparable prediction about harness-construction capability (as opposed to harness-design-lever value or harness-modification capability), so this is new territory for the map rather than a replication or a pushback. It is the clearest available instrument, going forward, for tracking whether frontier models' harness-construction capability improves as a distinct axis from their coding capability generally.

Bounds: the Stage 2 driver is a scripted mock model, not a real LLM, trading realism for determinism — whether a candidate harness performs identically under a live model is untested. The builder harness is fixed to one implementation (OpenCode), chosen specifically to avoid confounding Claude/GPT-family build models with a harness built by their own vendor; transfer to a different builder harness is untested. Single hardware/construction environment; no independent replication yet.
