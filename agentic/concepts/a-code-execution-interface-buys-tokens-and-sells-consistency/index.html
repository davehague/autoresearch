Half the token bill, and the runs stop agreeing with each other

This map has one previous controlled result on collapsing an agent's tool surface: restrict-the-tool-surface-to-cut-cost-not-capability found that reducing a coding agent to a single execute_code channel never lowered pass rate and was cheaper in three of four regime×agent cells. That finding is confirmed here at larger scale and with capability parity checked rather than assumed — 41.6% fewer steps and 56.3% fewer tokens at similar resolve rate, on all three actors. It is also qualified here in a way the earlier result could not see, because the earlier result measured pass rate and this one also measures pass^k.

The saving comes from batching, and batching is what costs the reliability. The agent writes one Python block that traverses, inspects, edits and checks, instead of a dozen round trips. Fewer round trips means fewer tokens and fewer chances to observe an intermediate result — and an error inside a bundled block surfaces later, further from its cause, with less of the trajectory available to recover from it. The pass^k numbers show the consequence at its starkest on the weakest actor: 0.020 → 0.002 at k=9, a setup where nine repeated attempts essentially never all succeed. On Sonnet-4.5 the penalty is small (−0.013 to 0.000), so this is again a defect-compensation story — the cost of losing intermediate observation scales with how often the actor needs to react to one.

How to price it. For work that is retried anyway, sampled, or verified by an independent gate, buying a 56% token cut with run-to-run variance is a good trade — the variance is absorbed downstream. For work that runs once, unattended, with no human to notice a bad run, it is the wrong trade at any discount, because the thing being sold is precisely the property unattended operation depends on. That is the routing decision this map should carry: the code-execution interface is a cost lever for supervised and resampled work, and a liability for single-shot autonomous work.

And note the asymmetry with the other efficiency lever. Atomic's cost effect reverses by actor — cheaper for the weak model, more expensive for the two strong ones, because many small calls add overhead a capable actor did not need. Python's cost effect is uniform. So of the two efficiency architectures, only one generalizes across models, and it is the one that costs consistency.

Bounds. 65 curated SWE-bench Live instances, three actors; absolute pass^k values are low throughout, so the Python consistency penalty on the weakest actor is measured near the floor. Token cost is measured, dollar cost is not, and the two diverge under differential cache behaviour (the-agent-token-bill-is-a-cache-lifecycle-problem). Resolve-rate parity is "broadly similar," not a tested equivalence.
