Judge the task's scope before gathering context, not after

The mechanism is upfront and anticipatory, not downstream and reactive. An agent forms a structured estimate — difficulty, scope (files/tools/steps), risk, confidence — from the query plus at most one cheap probe, executes the smallest path that estimate implies, and only expands scope, bounded and monotone, when a verification check fails. That's a different point in the pipeline from goal-hinted-pruning-beats-generic-compression and prune-and-summarize-beats-full-history, both of which act on context an agent has already gathered. This paper's agent never gathers the excess context in the first place — the 92% cut in inspected files against a max-context-first baseline is files never opened, not files opened and then trimmed. It's a genuinely new mechanism sitting next to an established finding, not a restatement of it: the vault's standing thesis that task-anchored, selective context beats generically-more context now has a before-the-fact instantiation alongside the after-the-fact ones, with its own formal metric — the Agent Cognitive Redundancy Ratio, realized cost in excess of an oracle minimum, normalized so waste is comparable across tasks of very different absolute size.

The paper is careful, and this note should be too, about which claim rests on what evidence. The 85/91/92% reductions are measured inside MSE-Bench, a deterministic simulator where every policy is a hand-written function against a mechanical cost model — no language model executes any trajectory there. The companion LLM-Case harness runs the same three system prompts (read-everything, ReAct, E3) over a live gpt-4o agent editing a real vendored library, graded by actually running the project's pytest suite against a measured oracle, and finds the same direction at a much smaller magnitude: gpt-4o is already frugal on its own, so the simulator's dramatic over-reading doesn't reproduce, but E3 is still the leanest and fastest of the three policies, and — a finding the simulator can't produce because it has no failure-under-load — the heaviest-reading real trajectories are also the slowest and the most likely to exhaust step budgets or trip provider rate limits and fail outright.

An ablation shows the two halves of the mechanism aren't redundant: removing the expansion stage drops success to 85.1% (every under-scoped task now goes unrecovered), while removing the estimation stage holds success at 100% but raises cost 20-36%. The estimate is what's cheap; the verified expansion is what makes an optimistic, sometimes-wrong estimate safe to act on.

Caveats: the headline numbers are a simulator property, not a deployed-agent measurement — the paper says this plainly. The real-model corroboration is one model (gpt-4o), one library (toml), five tasks, three runs each — a case study, explicitly not a powered benchmark, and which policy fails on the hardest tier is shown to move across runs. The estimator is a transparent lexical rule, not learned; MSE-Bench's hidden-dependency mechanism (aliases/re-exports) is one source of hidden complexity, not all of them (the paper names dynamic dispatch, configuration coupling, runtime reflection as unaddressed). Two-author arXiv v1, no confirmed venue acceptance despite journal formatting.
