The seventh consecutive held-out result, and the seventh consecutive run with no compute-matched arm

This map's contest has a precise shape: harness search has accumulated generalization evidence and not one compute-matched control. This arrival keeps both halves of that pattern intact, and it is the strongest generalization evidence yet — which is exactly why the missing arm is worth restating rather than waving through.

What is new is the partition, not the search. The evolution pool is stratified by baseline failure behavior — wrong_tool, context_loss, missing_evidence, premature_conclusion — computed from a baseline run before the partition exists, then split into proposer-visible search tasks and proposer-hidden selection tasks with matched score, failure-mode and verifier-pass distributions. The proposer sees search-task traces and outcomes and never sees selection-task contents, traces, verifier feedback, or per-task outcomes. Held-out tasks touch neither proposal nor acceptance. The authors name the protocol failure they are correcting: a prior meta-harness system used held-out sets for text classification and math but searched and reported final performance on the same 89-task benchmark. This is discovered-harnesses-transfer-off-the-search-distribution with the leakage surface closed by construction rather than by instruction.

Two loop mechanics are cheap and worth copying into any harness-search rig. A proposer-selected single-task test flip runs before the expensive evaluation, so a candidate that cannot move even its own chosen task is rejected without paying for a benchmark run. And promotion is deterministic — improve the hidden selection mean, with verifier rate as a tie-breaker only when available — so acceptance is never a judgement call the proposer could argue with. The guardrail list is equally explicit about what would make the result meaningless: no branching on task IDs, no verifier or assertion content in agent prompts, no ground-truth tables, no benchmark-specific answer mappings, with scope and import checks before anything runs.

The gains come with the cost going down, which is the unusual part. Turns fall, tool calls fall, cost per task falls by up to 53%, and on the diagnostic benchmark the movement is in both error directions at once — false positives roughly halve while true positives nearly double. On the finance benchmark guardrail violations fell from 33 to 4. So this is not a score bought with more sampling; the harness got cheaper and safer simultaneously, which is a different claim from the ones this map usually adjudicates.

And the gain shrinks as the model gets stronger on two of three benchmarks — ITBench +44.4 pp for the weakest model down to +27.9 for the strongest, EnterpriseOps +20.6 down to +10.7. That is the shape a model-environment-mismatch story predicts and a general-capability story does not. AutomationBench does not follow it, so the pattern is suggestive rather than established.

Bounds, and the first one is the contest. No compute-matched control anywhere — the evolution budget is never compared against spending the same budget on test-time scaling, more samples, or a stronger model, which is the objection this map has been carrying since 2026-07-18 and which remains unanswered. The comparison against prompt optimization is labelled descriptive by the authors, since the systems differ in prompts, tools, execution policies and architecture. "We cannot isolate the causal contribution of individual patches from the paired comparisons," stated twice. The exploration and exploitation modes are sequential by construction, so their comparison is not a causal head-to-head. All three benchmarks are enterprise tool-rich environments with programmatic state verifiers — the setting most favourable to interface repair and least like open-ended coding, which is the domain where this map's objection was raised. The external Claude reference scores are third-party figures explicitly outside the controlled comparison.
