A file that wins precedence over your tool descriptions, and nobody reviews it

This map's central claim is that permission has to be enforced below the prompt, in layers, and that the effective permission set is the transitive closure over everything the agent can reach — agents, tools, peers, gateways, stores, skill sources (screen-skill-files-before-they-enter-the-context, with skill-exploitability-is-an-agent-property-not-a-payload-property the sharpest recent addition). This adds the surface that closure keeps skipping: the project rule file that ships in the repository.

Three things about it, from a 65-file coding of a 12,110-file corpus.

It is a style document. Code quality and engineering practices take 30.4% of coded instances; project structure another 18.3%. Security is 4.2%, access control 1.0%, and explicit security-mechanism content roughly 2.5%. When security does appear it is mostly generic — "follow security best practices", "validate all input data" — with a minority naming a concrete control (CSRF protection, prepared statements, the checks-effects-interactions pattern against reentrancy). This is exactly the profile instructions-fail-to-govern-non-functional-requirements predicts and it is worse than that result assumed, because here the non-functional requirement is not merely ineffective, it is largely absent.

A measurable fraction of these files leak. About 1.5% of coded instances are security smells, in four named shapes: information exposure (a local path /Users/md/Dropbox/dev/.../BTC-USD-15m.csv, internal metadata), hard-coded sensitive parameters ('budget_tokens': '120790'; a SECRET_KEY for signing JWTs defaulting to 'banana'), internal resource exposure (private Notion workspace URLs), and inconsistency. That last one matters most here and is easy to miss: one sampled file instructs camelCase for component names and, later in the same file, PascalCase. A contradiction inside a single instruction surface is not something the precedence ordering can resolve — a-skill-description-loses-the-conflicts-it-wins-alone measured precedence between surfaces, and this is a conflict with no arbitrator at all.

And it outranks the surfaces that do get reviewed. a-skill-description-loses-the-conflicts-it-wins-alone puts the project file at the top of the precedence ordering, tied with the system prompt, ahead of tool descriptions and skill descriptions. So the file with the least review, the fewest maintainers (the-project-rule-file-is-written-once-and-abandoned: 95.8% single-contributor, 67.3% never edited) and the highest rate of committed secrets is the file that wins when instructions conflict. That is a governance inversion, and it is cheap to fix: make-agent-facing-rules-enforceable-not-conventional and agent-specifications-are-versioned-engineering-artifacts both argue the agent-facing markdown is a build input; a build input containing a JWT signing key belongs in the same secret-scanning path as source code.

Bounds. The smell rate is a property of a 65-file sample, not of the 12,110-file corpus — the authors say plainly that the qualitative arm is not representative and that themes reflect the coders' interpretations. Krippendorff's α starts at 0.674 (moderate) and only reaches 0.897 after the codebook is refined. Nothing here is an exploit: no measurement shows an agent acting on a leaked secret or being confused by a contradiction, so the harm is inferred from the artifact rather than observed. Public repositories only, and heavily weighted toward small hobby projects, where committed secrets are more likely than in a reviewed enterprise codebase. The .mdc comparison is 14 files, and the drop in security-awareness ranking there (9th → 41st) is partly explained by the authors as a scoping artifact rather than a real decline.
