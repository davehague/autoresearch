The map's enforcement half has assumed a sufficiently complete, externally-held spec is enough for an agent to check its own work against; this is the first measurement of that assumption, and it fails at the point where the agent is asked to write the check itself

This map's running thesis is that a specification held outside the agent is what makes a build faithful and checkable — ProjectGuard's project-state tracking, the decision-pin's execution-confirmed record, and SpecGuard's Lean certification are all mechanisms for holding or enforcing that external contract. Every one of those mechanisms assumes something downstream can tell whether the implementation actually satisfies the spec. TestSuiteBench measures that assumption directly, on the same specifications used to build the code, and finds a sharp asymmetry: an agent given a full specification writes an implementation that satisfies 82% of a reference test suite, but asked to write the verification for that same specification, produces a suite that misses most of the mutants specifically engineered to violate one of its requirements. The gap is not that the agent writes obviously broken tests — 88% of its tests are valid against the reference implementation — it is that the suite doesn't probe the input combinations a requirement actually constrains.

Why this sharpens rather than contests the map's standing instruction. Holding the contract outside the agent was always a necessary condition, not a sufficient one — the map's existing findings are about whether the document survives intact (SLUMP, SpecBench) or whether its sub-decisions are made explicit (the decision pin). This adds a third, separate failure point: even a document that survives intact and has its sub-decisions pinned can still be checked badly, because turning "what the spec requires" into "a test that would catch a violation" is itself a capability gap, independent of whether the spec was held externally. The map's enforcement mechanisms (Lean certification, decision pins) are model-free or execution-confirmed precisely because they don't trust the agent's own judgment about what counts as a check — this result is evidence for why that design choice matters.

Bounds: benchmark covers 165 applications averaging 74 mutants each, mutation targets drawn from stated requirements rather than arbitrary code locations, so it measures requirement-coverage specifically rather than general code-coverage. The paper does not report which frontier models were evaluated or at what cost, nor whether iterative tool access (running the suite against the implementation and revising) narrows the gap relative to one-shot generation — both left open by this single arrival.
