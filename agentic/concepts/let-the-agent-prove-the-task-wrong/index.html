The benchmark accepts "your task is broken" as a graded answer, if you can prove it

This map's benchmark-defect literature is entirely retrospective and external: someone scans a finished benchmark for flaws (automated-benchmark-flaw-scanners), someone re-scores it with the defective instances removed and the leaderboard reshuffles (removing-defective-instances-reshuffles-the-leaderboard), someone notices that defects suppress scores as well as inflate them (benchmark-defects-suppress-scores-not-only-inflate-them). The best signal the vault had during a run was statistical — a-unanimous-agent-failure-flags-a-broken-task, where every agent failing the same instance is a hint that the instance is wrong. A hint is all it is; it cannot distinguish a broken task from a hard one.

Vero replaces the hint with a proof. An agent that believes an instance is wrong may submit machine-checked negative evidence in three forms — the specification is unsatisfiable, the reference implementation is incorrect, or the specification set is mutually inconsistent — and that submission is graded. The property worth taking is that this is the same kind of object as a solve: kernel-checked, not argued, so accepting it costs the curator nothing in judgement. In a formal setting the asymmetry that usually makes this impossible disappears. Everywhere else in this vault, an agent's claim that the task is broken is indistinguishable from an excuse, which is why audit-agent-claims-against-trajectory-evidence and treat-agent-output-as-a-claim-not-lifecycle-state exist at all. Here the claim carries its own verification.

It worked as a curation instrument, which is the part with evidence behind it: the mechanism surfaced latent errors "that escaped manual review," with three worked corrections shown. Note what that says about manual review of formal artifacts — a specification can be read carefully by an expert and still be unsatisfiable, because unsatisfiability is not a thing human reading is good at detecting. This is the formal-methods sibling of independent-review-catches-bugs-in-the-measurement-code-itself, and it points the same direction: the measurement apparatus needs its own checker, and the cheapest available checker is often the system under test.

Where it stops is worth being blunt about, because the mechanism invites over-reading. Formal satisfiability is not semantic correctness. A specification set can be satisfiable, mutually consistent, provably closed, and still fail to describe what the library is for — which is why Vero kept manual review of every specification anyway and cross-checked the ported track against its source-language originals. The audit catches the class of defect that is formally decidable, and the class this vault worries about most — build-tasks-from-private-artifacts-not-public-issue-text, search-time-leakage-inflates-web-agent-scores, an oracle that rewards the wrong behaviour (agents-build-to-the-oracle-you-expose) — is not in it. So the honest statement of the transferable idea is narrow: where your acceptance criterion is machine-checkable, make its negation submittable too. Test suites qualify more often than people assume; a proof that a supplied test contradicts another supplied test is an ordinary program.

Bounds. The paper does not quantify the yield — "several latent errors" with three appendix case studies is the whole reporting, so there is no defect rate to compare against automated-benchmark-flaw-scanners's external-scan numbers, and no measurement of how many false defect claims the mechanism had to reject. Single benchmark, single team, and the team that built the audit is the team whose curation it audited.
