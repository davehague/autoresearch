The same metric shape, caught in a second domain, by people who went looking for it

report-current-correctness-not-only-ever-correct established this failure on coding agents: pass@k and best-of-k report whether a loop ever produced a correct artifact, not whether it retained one, so a trajectory can post monotone improvement on the reported number over exactly the interval in which its current correctness is falling — ever-correct 0.820 → 0.853 while current correctness fell to 0.673, with 16.0% of trajectories producing a correct patch and then losing it. That was one study, one artifact type, one team. This is an independent group, a different loop (generate Terraform → scan with Checkov → repair), a different failure (a security check that passed and now fails), a different scale (5,968 timelines), and the identical shape: cumulative-best climbs 73% → 83% while the raw per-iteration pass rate peaks at 83.4% on iteration 4 and falls to 82.6% on iteration 5. The metric is not merely optimistic; it is non-decreasing by construction, which means it cannot report the event, ever, in any run, for any model.

The authors' framing is the one to steal: the reason nobody had seen the per-iteration trajectory for infrastructure-as-code is that no published evaluation had plotted it. The instrument's shape determined what the field believed, which is this map's standing thesis stated as a literature observation rather than an experiment.

Three second-order results are worth as much as the headline, and two of them are cautions against over-reading it.

The regression rate is a definition, not a measurement. Counting any check that passes at iteration i and fails at i+1 gives 13.8% of scenarios. Requiring the check to pass exclusively and then fail exclusively — removing cases where the same rule passes on one resource and fails on another in the same file — gives 3.3%, a 76% reduction, and the authors nominate the conservative number as the defensible one. This vault has been assembling the same warning from the other direction (skewed-label-bases-inflate-classifier-headlines, measure-the-judge-parameter-you-stipulated); here the analyst's own detection rule moves the headline by 4×, and the paper prints both.

A definition artifact can masquerade as a model difference. Under the loose rule Mistral regresses 17.3× more often than Gemini — 32.6–41.2% against 1.9–4.7%, a gap anyone would publish as a model comparison. Under the strict rule both models show zero scenario regressions in the RAG arms. The entire effect was multi-resource ambiguity. That belongs beside harness-asymmetry-manufactures-model-differences as a second, cleanly-worked example of a large model gap that is an instrument reading, and it is the more alarming one because the instrument here is a deterministic static scanner, not a judge.

And the knob everyone tunes did nothing. Temperature across 0.1 / 0.4 / 0.7 gives Cramér's V = 0.049.

The operational reading is stop-on-the-sign-of-the-marginal-gain with a number attached: stop at iteration 3, which sits within 0.3 pp of the peak and accrues fewer regressions than running to 4 or 5. The loop-engineering half of the finding — that repair rounds actively break things rather than merely stop helping — is carried separately at a-repair-round-trades-one-check-for-another.

Bounds. Terraform and Checkov only, AWS-only scenarios, and Checkov is explicitly a proxy — the paper says real security assessment requires deployment-time evaluation. Two models, both a generation behind the frontier, and the authors concede the trajectory partly reflects their particular repair ability. One run per configuration, so run-to-run variance is unquantified; the null temperature effect is offered as indirect evidence of stability, which is weak. 13% of scenario-configuration pairs are missing to API errors and timeouts. The 4→5 decline is 0.8 pp with no confidence interval reported, so the existence of a non-monotone trajectory is the durable finding here, not its magnitude.
