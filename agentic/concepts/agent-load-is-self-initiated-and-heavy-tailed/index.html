The population this vault has been sampling, with the shape of its tail

This map's argument is that agents must be audited and governed from trajectory-level evidence rather than from outcomes (audit-agent-claims-against-trajectory-evidence, fail-loud-instrumentation-over-plausible-substitutes). What it has lacked is a field distribution to calibrate against — how much trajectory there is, how it varies, and what a typical operational unit even looks like. This supplies it at a scale no other source here approaches: 760.5M LLM calls across 3.2M users, one week.

The load is agent-generated. Each user message unfolds into an average of 6.6 autonomous LLM calls, yielding an 87% / 13% split of agent- to user-initiated calls, with LLM and tool invocations coupled nearly one-to-one (760.5M against 774.7M). The practical consequence the authors draw is a capacity one — "user request arrivals alone do not predict LLM load" — but the observability consequence is sharper: any dashboard whose primary unit is the user prompt is displaying 13% of what the system did. The unit that carries information is the turn, and the turn is a whole autonomous trajectory.

Every dimension is heavy-tailed, so averages mislead in a specific direction. The median session runs 3 user turns, 15 LLM calls, 4.2 minutes; the mean runs 6.1, 40.6 and 62.6 minutes — a 14.9× mean-to-median ratio on duration with P90 above three hours. At the turn level the median is 3 LLM calls and 160.2K prompt tokens against a P90 of ~16 calls and over 1M. Alerting or budgeting on the mean therefore describes almost no real session; the tail is where the resource consumption and, plausibly, the failure modes live. This is the same warning agent-improvement-distributions-can-be-bimodal raises about improvement distributions, restated for operational telemetry.

Populations differ 50× and are stable enough to name. Five clustered user archetypes span 23K (chat-only, no tools) to 1.1M (deep-loop) tokens per turn, with different tool mixes, idle profiles and session statefulness. A single SLO or a single retention policy over that spread is a policy tuned for nobody.

Two structural facts worth holding when reading any trajectory. Time and tokens are inverted — LLM execution takes 85.4% of session wall-clock but contributes 48% of prompt tokens, while tool calls take 4.7% of time and contribute 28% — so a latency profile and a token profile of the same session point at different components. And execution is overwhelmingly serial: 36.7% of turns strictly so, and where concurrency exists it is shallow (median 1.15, P90 1.4, concentrated mid-turn in an inverted-U as exploration fans out and the decision converges), with 93% of tool batches a single invocation. The fan-out that multi-agent architectures assume is not what production traffic mostly looks like — which is a field observation bearing on multi-agent-helps-only-decomposable-tasks and coordination-saturates-as-the-single-agent-improves without settling either.

Bounds, and they are serious for this map specifically. This is telemetry, not trajectories: no prompt text, file content, model output, tool arguments or source code was collected, so it is a census of the shape of agent activity and carries no outcomes, no correctness, and no failure labels. One vendor, one product, one sampled week, one tool surface. Archetypes are post-hoc clusters. Population statistics rather than estimates, so no intervals. Everything here calibrates expectations; none of it audits a claim.
