A destructive MCP tool needs two independent opt-ins to get confirmed, and the census shows neither one defaults to yes

This map's enforce-below-the-prompt thesis has carried a running list of surfaces where the agent's effective permission set turns out to be a transitive closure nobody enumerated — peers, gateways, stores, skill sources. mcp-annotations-cannot-express-transactional-guarantees (agent-harness-architecture) already measured one half of why: across a 98,291-tool registry census, the one annotation field that could flag a call as risky (destructiveHint) is only meaningfully applicable to 12.9% of tools in the first place, so a policy trying to gate on "is this destructive" is working from metadata that mostly doesn't say. This source measures the behavioral consequence of that thin metadata at full ecosystem scale, on both sides of the handshake MCP actually defines: ~90% of destructive tools, sampled from 1,000 real registry repositories, ship with no server-side confirmation request at all, and when a host can't relay a confirmation request, servers mostly proceed anyway rather than refuse.

The host side is no better. Of 41 popular open-source hosts and agent SDKs, 32 have no approval step enabled by default, including 16 of 25 full applications — so even a server that did ask correctly would often be talking to a host that drops the request on the floor. Composed across sampled pairs, 60.7% enforce no human approval by default, and a live test across four agent SDKs found four of five low-cost models would execute an injected deletion instruction in 479 of 960 runs — not a rare misconfiguration, a modal outcome.

The fix the authors model is a policy inversion, not a protocol feature. MCP already has an elicitation mechanism a server can use to request confirmation — but relying on it alone, with no change to which tools get marked as needing it, only closes the gap from 60.7% down to 56.7% unapproved. Flipping the default — treat anything not explicitly marked read-only or non-destructive as needing a human — gets to 5.4%. The protocol capability already exists; almost nobody has set the policy that would make it matter, which is the same shape this map keeps finding in the-instruction-file-is-an-ungoverned-security-surface and the operator-surface enumeration generally: a layer that could enforce something is present and unused, and the closure fails wherever an opt-in was assumed rather than defaulted.

Bounds. Server-side confirmation-request presence is estimated from static registry-listing analysis at the 1,000-repository scale, not confirmed against live server behavior for every sampled tool; the 41-host default audit covers popular projects, not the long tail of self-hosted or internal hosts; the live-execution injection test uses four SDKs and five low-cost models, so it says nothing directly about frontier-model or production-fleet behavior, where other guardrail layers this map tracks may already be in place.
