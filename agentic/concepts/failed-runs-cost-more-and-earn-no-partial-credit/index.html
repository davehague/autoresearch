More rounds is what losing looks like

This map already holds that spending more does not buy more in several forms — spend-the-budget-on-context-not-repair-rounds, a-repair-round-trades-one-check-for-another, charge-every-search-method-the-same-budget. This arrival supplies the within-run version, and it is a stronger statement than "extra spend has diminishing returns": across every iterative framework tested, the runs that got it wrong consumed more rounds than the runs that got it right, by up to 11.4 rounds.

The refutation of the obvious defence is what makes this usable. The natural reply is that hard cases both take longer and fail more, so the extra rounds are buying partial progress on problems that were always going to be harder. The paper tests that directly and it does not hold: incorrect runs trail correct ones on both process-quality metrics — they did not reconstruct more of the causal structure for their extra rounds. Whatever the additional search bought, it was not evidence. The authors' phrasing is the right one to carry: unproductive search inflates cost without improving outcomes.

Which turns elapsed rounds into a signal rather than a budget. If long is systematically worse rather than merely more expensive, then round count is a live, free, provider-agnostic feature for abandonment — the same role a-tiny-monitor-prices-a-doomed-trajectory gives a small monitor model, available without the monitor. It also inverts the usual reading of a timeout: a run that hits its round cap is not a run that was cut off before it would have succeeded, it is disproportionately a run that had already lost the thread.

Two cost readings sit underneath, and they point opposite directions. Budget does scale with investigative openness — the agents that requery telemetry adaptively sustain 45–54 rounds and 1,500+ ktok against under 700 ktok for the constrained designs — and those agents are also the accurate ones, so openness is worth paying for at the architecture level. But within an open architecture, more rounds on a given case is bad news. The two are consistent and the distinction is the practical one: buy the affordance, not the rounds. Note also that the stronger backbone reaches a better answer in fewer rounds (31.2 vs 44.7) while costing 22× more per case — solve-sets-are-nested-so-route-for-cost-not-accuracy and agent-cost-spans-orders-of-magnitude both apply, and the token count and the bill move in opposite directions here.

The ablation makes the same point about interventions. Adding a defense wrapper to the diagnostic core raises accuracy by 9.0 points while the two single-defense variants each gain about half that — and the gains do not track budget at all. The costliest arm gains least (343.8 ktok, $0.17, +4.1); the full stack gains most while spending less than it (318.5 ktok, $0.16, +9.0). So the cheapest configuration of the three interventions is also the best, which is only surprising if you were expecting quality to be purchased.

Related: a-task-count-budget-is-not-a-cost-budget for the map's standing caution on what a budget actually measures; retry-cost-is-an-architectural-property for the structural version; the-correction-window-is-the-first-third-of-the-trajectory for the compatible timing result — if correction happens early, then late rounds were never where the value was.

Bounds. Every characterization configuration here is a single run with no significance testing, which the authors flag themselves and which applies to the round counts as much as to the accuracy figures; the up-to-11.4-round gap is a difference of means across single runs, not an interval. One task domain (microservice root-cause analysis on one topology) and one benchmark, so the generalization to coding agents is by analogy. The correct/incorrect round comparison is observational — nothing was randomized, and a common cause (case difficulty interacting with something other than evidence quality) is not fully excluded even though the F1 result argues against the simplest version of it. Dollar figures are provider list prices at a moment in time and the 22× backbone ratio will move. And "rounds" is defined per framework, so cross-framework round counts are not strictly commensurable — the within-framework correct-versus-incorrect comparison, which is the load-bearing one, is.
