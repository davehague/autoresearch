The condition label on the run is not what the run did

This map's catalogue is mostly about numbers that describe the wrong thing — a contaminated task set, a permissive judge, a proxy that ranks something adjacent. Here is a plainer version, and it applies to a design pattern this vault sees constantly: assign an agent a tool interface, measure the arm, report the difference.

In a companion experiment with both routes reachable, the MCP server attached and confirmed connected in all 21 runs, only six used the MCP tools exclusively. Six completed the task entirely through the shell without calling an MCP tool once. Six used both. Three called no tools at all. Four bypassed both assigned interfaces and hit the service's web API directly over HTTP — a route nobody put in the design. Whatever those 21 runs measured, it was not the interface printed in the condition column.

Prompting did not fix it; configuration did. Adding an instruction to the prompt that named the available interface and directed the agent to use it "did not change this behaviour materially." Removing the credentials that made the alternative route possible did: after isolation, all 25 recorded command-line runs used only the command line. An instruction is a request; an unavailable capability is a fact. It converges from a different direction on an-obeyed-rule-may-just-be-the-default, which found compliance rates inflated by rules the agent would have followed anyway. Both are the same defect in the instrument: the treatment was not delivered, and the score does not say so.

The bias has a direction, which makes it worse than noise. An agent that quietly finishes through its shell while an unused catalogue sits in its context produces a low measurement for the arm labelled MCP. So studies that do not verify actual tool calls understate what the assigned interface costs — the error runs toward the null, which is exactly the direction that makes a real effect look absent.

Two rules follow, and both are cheap. Record which tools were called, not which were made available — the study logged the tool register per request through a single proxy, which also stopped scaffoldings from hiding sub-agent spend. And isolate the arms by removing capability rather than by instructing against it, giving each arm its own credential and pointing the other route at an empty configuration so a fallback fails visibly instead of succeeding unnoticed. The MCP arm remained untidy even so (11 of 17 pure), which is honest reporting of a limit rather than a solved problem.

Bounds. The 21-run behaviour experiment used a public fixture with credentials unseparated, which is why it was useless for cost and informative about behaviour; it is one task family, one service, and the tool registers are per-run counts with no repetition. One scaffolding's runs on one provider did not report tool calls at all and are excluded from this analysis, so coverage is partial even within the main matrix.
