Prove the grader fails before you let it pass anything

This map's catalogue of misgrading proxies is long and its remedies are mostly retrospective — read transcripts (fix-the-eval-before-trusting-the-score), find the majority-class baseline (skewed-label-bases-inflate-classifier-headlines), replay the reference patch (perf-benchmark-reference-patches-are-unstable), measure a paired floor (coordination-deltas-need-a-measured-noise-floor). Each of those is a way of discovering, after the fact, that a number described the instrument. Here is the same discipline moved upstream of the run and stated as a precondition of doing the work at all.

The protocol is small enough to copy. Categorize the existing tests into external-facing and internal-dependent; rewrite the external ones so they survive the port; then verify the judge in both directions — it must pass the original code and it must fail code you broke on purpose. Only then start migrating. On the 165,000-line port that meant seven human-written real-world scenarios plus end-to-end tests the agent designed itself, run overnight across four iterations, before a line was translated.

The direction that gets skipped is the second one. A grader that passes the original is trivially satisfying and tells you nothing; a grader that also fails a deliberate defect is the only one that has demonstrated discriminative power. That is the same property the vault keeps finding is the operative variable elsewhere: verifier discrimination decides whether a repair loop has positive value (repair-loops-have-an-interior-optimum), and a gate's catch rate is meaningless without its false-alarm rate (verifier-catch-and-false-alarm-rates-are-measurable — catch 0.20, fix 0.75, false-alarm ≈0). Validating the judge in both directions is how you measure discrimination before spending on the loop it governs.

It also composes with this map's self-improvement caution. harness-self-evolution-is-capped-by-its-proxy-judge found a selector committing a 50% program when a 64% one sat in the pool, and harness-optimizers-fabricate-failures-to-fix found a phantom guard that a suppression-only acceptance metric cannot see. Both are failures of an unvalidated judge steering generation. A migration loop that regenerates batches on rule amendments is the same structure — the judge selects what gets rewritten — and this is the practice that would have caught either.

Caveats: T2 practice narrative with no measurement of the protocol's contribution. It is one org's prerequisite on two migrations, and both had an unusually complete grader available in the first place: a working reference implementation plus a human-written suite. Where no such oracle exists — the unlabeled setting harness-self-evolution-is-capped-by-its-proxy-judge identifies — the instruction is unimplementable, and this source says nothing about that case.
