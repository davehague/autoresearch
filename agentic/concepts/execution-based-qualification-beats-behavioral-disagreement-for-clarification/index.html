A clarification question earns its interruption cost only if two plausible answers provably steer execution apart -- behavioral disagreement across independent samples measures something related but noisier (it also fires on plain bugs)

This map's standing complaint about the pre-code phase is that agents reason poorly about specs in the abstract — the best agent in SpecBench hits only 44.4% at finding design-proposal defects without execution feedback (agents-are-weak-at-spec-critique). CONTRA attacks a narrower, more tractable version of the same problem from the opposite direction: instead of asking the agent to critique a given spec, make the agent find the places where the requirement is silent, and use execution — not another layer of LLM judgment — to decide whether the silence actually matters. Generate two programs under two plausible answers to a candidate question and check whether they diverge on shared inputs. If they don't, the question's "ambiguity" was never going to change behavior and asking it would be pure interruption cost; if they do diverge stably, the question is load-bearing and worth a developer's attention before the implementation (and everything downstream of it) commits to one interpretation.

The comparison against ClarifyGPT's behavioral-disagreement baseline is the paper's sharpest methodological point for this map: disagreement across independently sampled programs from the same requirement conflates two different sources of variance — genuine requirement ambiguity, and plain implementation error/non-determinism in the sampling. CONTRA's design removes that confound by fixing the two answers as the independent variable and sampling programs conditioned on each, isolating whether the answer choice itself is what moves behavior. This is the same discipline this vault keeps re-deriving in other guises — a controlled contrast needs to vary one thing and hold the rest fixed, or the measured effect is attributable to noise in the thing you didn't mean to vary.

The harness comparison (beating Claude Code and OpenHands's own native clarification behavior under a matched model and protocol) is independent evidence that production coding harnesses under-ask: not because the underlying model can't form good questions, but because the harness's selective-clarification policy (whatever filter it uses internally) is weaker than CONTRA's execution-based filter on the same model. That lands directly on this map's open question about whether harnesses differ in their "ask-affordance" — prior evidence here found harnesses differ 3x in surfacing uncertainty as a clarifying question (clarification-is-a-harness-affordance); this source is a second, independent measurement that harness- level clarification policy is a real, swappable component with a large quality gap between implementations.

The plugin's decision-discovery result (57 of 262 decisions caught by both the agent's own self-report and an independent re-derivation pass; 116 caught only by the independent pass) is this map's most concrete number yet for a question it has been circling since the self-generated-contract work (make-the-agent-write-the-contract-before-the-test): an agent's own completion report is not a reliable inventory of the decisions it silently made. A developer reading only the final reply would miss roughly two-thirds of what an independent pass would have flagged — not because the agent is lying, but because a report optimized for "explain what I did" is a different object than a report optimized for "surface every place I guessed."

Interaction edge: context-engineering — selective clarification is a context-acquisition decision made before any code exists; CONTRA's qualification step is effectively a cheap, execution-grounded filter on which missing context is worth acquiring from the user versus assumed, which is the same sufficiency-triage question that map's retrieval sub-thread asks of documents and APIs.

Scope: the repository plugin evaluation is 40 tasks across six Python repositories with one run per task (no seeds or variance reported); the "underspecified" task labels are LLM-generated and then manually reviewed rather than independently authored from scratch; the decision-discovery overlap figures (57/116/89) compare two internal LLM passes against each other, not against an external ground-truth inventory of what decisions the diff "actually" contained, so the two-thirds-missed framing is relative to the plugin's own second pass rather than to an independently verified gold standard.
