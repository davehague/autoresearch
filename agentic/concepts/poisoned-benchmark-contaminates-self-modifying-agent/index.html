This map's governance sub-thread gets a second, distinct attack surface — not planting a malicious skill in context for the loop to imitate, but poisoning the score the loop is evolving against

Sub-thread (2) of this map asks whether self-modification can be governed at all, and its sharpest prior answer is an in-context authoring attack: a planted skill an agent never invokes still gets re-authored, stored and executed on 20.3-41.8% of tasks, falling only to 11.1% with every instructional wrapper stripped — ordinary imitation-based authoring, not injected instructions, is enough. This source is a different attack on the same governability question, upstream of authoring: instead of corrupting what the loop reads in-context, it corrupts the reward signal the loop optimizes against. Every self-modifying system in this map's evidence — the auto-research loop, Ecdysis, HarnessDev — treats a held-out benchmark split as the honest arbiter that keeps its search generalizing rather than overfitting; that entire discipline assumes the benchmark itself is trustworthy. This source demonstrates it does not have to be: an adversary who can influence which benchmark a self-modifying agent evaluates itself against can make the agent evolve a hidden vulnerability that reproduces at 100% on unrelated, neutral tasks, using nothing but the agent's own designed-in incentive to raise its benchmark score.

The persistence result is the one this map's search-pays contest (sub-thread 1) should carry forward alongside the governance question: continuing to evolve a poisoned agent against clean benchmarks, including a general security benchmark (CWEval), did not remove the contamination in most tested configurations. That is structurally the same shape as this map's skill-persistence finding — "the property that makes evolution valuable (the library persists and is retrieved) is the same property that makes the compromise persist" — now shown for a corrupted evaluation signal rather than a corrupted context artifact. Both attacks exploit the same underlying feature of self-modification: what the loop learns from one exposure keeps acting on every subsequent one unless something specifically targets it for removal, and ordinary continued operation does not count as removal.

The authors' stated necessary conditions are a usable checklist against any self-modifying system this map tracks going forward: the benchmark must force or reward the vulnerable behavior for tests to pass; the vulnerability must be functionally invisible on neutral inputs; benchmark tasks must minimally cue it so the agent overgeneralizes its fix; the exploited pattern should be a standard library idiom to transfer well; and the underlying model must default to a secure implementation absent benchmark pressure, or there is no initial gap for a poisoned reward to close. On the harness side: open-ended self-improvement objectives without guardrails against task-specific changes, no security-awareness in the self-improvement scaffolding, and pure benchmark-score-maximizing evolution with no competing objective all made the attack easier across the three systems tested.

Scope: DGM's stock system resisted the attack until the authors modified its internal prompt to permit task-specific tool creation, so the DGM result is not against an unmodified deployed configuration; of five vulnerability classes tested, only CertCheck (disabling HTTPS certificate validation) transferred reliably across all three systems, so generalization across vulnerability types is narrower than generalization across systems; two authors, no independent replication yet; the paper is explicitly a feasibility and necessary-conditions demonstration, not a measurement of real-world attack prevalence.
