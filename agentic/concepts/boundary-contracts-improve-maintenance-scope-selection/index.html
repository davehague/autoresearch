Relevance and permission are different questions, and telling an agent the answer to the second one -- not just giving it more context -- moves what it does

This map's effective-permission-set enumeration has mostly reasoned about tool-call permission; this pilot applies the identical logic to maintenance scope -- which repository artifacts a task-specific change should touch -- and finds the same shape: an agent given more context (richer retrieval, more candidate files) is not automatically an agent that acts within the right boundary. The paper's own distinction between informational relevance (useful for understanding the task) and operational role (permitted/required/forbidden to modify) is a clean, reusable vocabulary for a confusion this map's enumeration keeps running into from the tool-permission side -- an artifact an agent should read is not thereby an artifact it should write, and the inverse failure (an artifact the request never mentions but the maintenance still requires) is equally unaddressed by relevance-only retrieval.

The shared-file subset analysis is the methodologically load-bearing result: by restricting to the 21 of 40 tasks where baseline and boundary-informed conditions already overlapped on at least one touched file, the authors rule out the easy explanation ("the contract just helped localization") and the gap survives anyway -- extra edits fall from 29 to 9 and acceptable patches roughly double, on tasks where both conditions were already looking at some of the same files. That is evidence the boundary changes behavior once an agent has reached an artifact, not merely which artifacts it reaches -- directly relevant to this map's standing finding (SWE-Misbehavior) that agents routinely cross operational boundaries a task never asked them to cross, here showing one concrete, measured intervention that narrows that gap, albeit on one repository and one agent configuration. The authors' own open question 4 (should such a boundary be advisory or runtime-enforced) sits exactly on this map's recurring advisory-vs-enforced distinction and is posed, not answered, here.

[T1, single-study; explicitly framed by its authors as a pilot, not a general-effectiveness claim — one repository, one language pair (Java/XML), one agent configuration, no ablation isolating which boundary-contract field drives the gain, boundary quality and the agent's ability to use a correct boundary are conflated since the same knowledge base underlies both the contract and the gold evaluation records, no test of agent behavior under a deliberately wrong or incomplete boundary]
