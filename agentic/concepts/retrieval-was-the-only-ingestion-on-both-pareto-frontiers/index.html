The most robust way to hand an agent a specification it did not write is to not hand it the specification

The sibling note records the problem: a-specification-is-not-an-agent-neutral-artifact — the same document is worth wildly different amounts to different consumers, directionally and unpredictably. This note records what the source tried about it, and the ranking is instructive mostly because the winner did not win on any metric.

Rewriting is the strongest single fix and the least portable. Asking the consuming agent to restate the foreign specification in its own idiom first pulls Gemini back from a near-total collapse to roughly its native level. Applied to Copilot, which had no transfer problem to begin with, the same rewrite makes things worse — SQL syntax validity falls from 43.4% under direct ingestion to 14.09%. So the remedy has the same shape as the disease: it is a pair property, and applying it by default costs the agents that did not need it.

Compression is a null, and it is the expected null. If specification length were the problem, summarizing would fix it, and it does not. That is consistent with the same source's finding that an eight-times-longer specification did not produce better code, and with the broader pattern on this map that the payoff is not in the notation (the-specs-format-is-not-what-pays) nor in completeness (a-specification-buys-executability-not-agreement).

Retrieval wins by not losing. Denying the agent the whole document and giving it retrieval tools for selective access does not dominate: Gemini's SQL validity under retrieval (13.82%) is far below its rewrite result (43.62%). What it does is stay on the efficient frontier for both agents when syntax validity and structural similarity are read jointly — the only strategy that does. The authors are careful about what that licenses, and the care is worth preserving: not universally optimal, but the most robust common strategy when you do not know how the consuming agent will react. Which is the operating condition of any workflow where the agent might be swapped.

Why this belongs on this map rather than beside a retrieval note. This vault's acquisition map already holds that a retrieval score does not predict a repair outcome, and that a recall-maximizing packing flag can resolve fewer issues at a fixed budget. Nothing here contradicts that, because the quantity being managed is different: not finding the right material, but bounding what the consumer has to interpret. It is the same intuition as declare-what-each-step-reads-and-writes — reduce what the executor must select from — reached from the ingestion side rather than the authoring side, and it points at the same architecture the source proposes at the end: a structured specification of semantic blocks retrieved by declared dependency relation rather than by textual similarity, so each implementation object receives only its relevant blocks plus their dependencies.

Related: persist-the-contract-not-the-conversation and track-the-spec-in-external-state for the map's standing position on where the specification lives; selected-context-cuts-trajectory-tokens-at-equal-localization for the cost-side analogue.

Bounds. Each strategy is one run per agent on one migration task, reported as a single row with no interval and no significance test, in a study whose one repeated configuration disagreed with itself by a factor of twenty. Runnability is 0–1.80% across every strategy, so the outcome metric closest to working code does not discriminate between them at all and the entire comparison rests on lexical and structural proxies. The Pareto claim is a two-metric frontier over a handful of points, not a robustness measurement. Only two consuming agents and one specification origin were tested. And the retrieval configuration's details — chunking, relevance threshold, tool surface — are not reported in enough detail to reproduce, which for a strategy whose whole claim is robustness is the gap that matters most.
