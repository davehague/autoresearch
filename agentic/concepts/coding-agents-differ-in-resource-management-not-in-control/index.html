If every agent runs the same loop, then the loop is not where the engineering is

The vault's harness evidence keeps returning a variance that nobody has been able to localise: the-loop-implementation-is-a-larger-term-than-the-model-tier, the-harness-shifts-benchmark-rank-order, no-harness-ordering-holds-across-models. "The loop" has been the name for that variance without anyone opening the box. This is the first source in the vault that opens it on more than one agent at a time, and the finding is that there is nothing in the box — Ark, Codex CLI and OpenCode all run the same imperative while-loop over ReAct with the model picking the next tool, and if that layer is invariant it cannot be carrying the variance the benchmarks keep measuring.

Everything that does differ sits in two other layers, and they are worth naming as separate design surfaces:

  • Tool / environment. Tool count (5 / 20+ / 18+), edit mechanism, whether the tool list is static or rebuilt per turn or fully dynamic, whether retrieval has regex or only keywords, and whether execution is platform-sandboxed or a bare local shell.
  • Resource management. How history is represented (destructive truncation / flat preserved list / typed event log), how it is compacted (size truncation vs LLM summarisation), whether there is model routing and on what basis (none / safety / role), and whether anything persists across sessions (none / background pipeline / SQLite store).

That decomposition is close enough to decompose-the-harness-into-separately-liftable-layers to be worth saying carefully, because the two are doing different work. That note argues per-layer attribution is unidentifiable while the layers share one prompt loop, and prescribes lifting each into a separately callable runtime object. This one observes that in shipped agents the layers are already separated — the compaction policy, the tool registry and the routing rule are ordinary code, not prompt sections — which means the identifiability problem is not universal, it is a property of harnesses whose roles live inside the prompt. Where the layers are code, they are ablatable today, and nobody has ablated them.

Two of the eight "universal" mechanisms deserve promotion out of the list, because they are the ones this vault has evidence for and the paper treats as plumbing. Protocol validation — every model response checked against the required response shape, with a bounded retry before the run is killed — is the concrete form of fail-loud-instrumentation-over-plausible-substitutes at the harness boundary. Patch validation — auto-repair of malformed hunk headers, then git apply --check, then apply — is a deterministic gate on the one artifact that leaves the sandbox, and it is inject-determinism-at-the-dispatch-not-the-agent implemented in the smallest possible way. Containment in Ark is likewise structural rather than policy: a copied workspace, path restrictions, no arbitrary shell, a fixed test command. That is contain-at-the-environment-layer-first as an architectural default rather than a security feature, and it comes free in a prototype whose author was optimising for clarity.

Bounds, heavily. This is one author reading three codebases with no stated protocol for how the layers were identified, and two of the three agents are described from their source rather than instrumented — so the taxonomy is a plausible carve, not a measured one, and a different reader could reasonably put tool discovery under resource management or split routing out entirely. Three agents, all CLI-shaped, all open-source; nothing here covers hosted or multi-agent harnesses, where the control layer is exactly where the differences would be expected to live. And "the control layer is identical" is a claim about structure, not about behaviour: two ReAct loops with different termination conditions, retry budgets and error handling are structurally the same loop and can behave nothing alike — which is arguably where the unlocalised variance actually went, and this source does not look there. Graded T3, single-study, and useful mainly as a map of where to point the next ablation.
