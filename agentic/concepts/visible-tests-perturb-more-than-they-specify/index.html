Another task's tests work as well as yours, once the problem is hard enough

The experiment is built out of controls rather than around a proposed method, which is why it says something the many "adding tests to the prompt helps" results could not.

Where the model has room on the task, tests behave the way the TDD framing predicts. MBPP+ moves 63.8% → 71.2% with relevant tests, and the ordering underneath is exactly what semantic use would produce: shuffling the expected outputs helps less (69.0%), and swapping in another task's tests hurts badly (43.9%, a net −75 tasks). Nothing there is a prompt-length artifact — relevant tests rescue 44 tasks and break 16.

Where the task is hard the ordering disappears. On the 175 problems new to LiveCodeBench v6, the 7B model reaches 14.9% with the correct tests and 15.4% with tests borrowed from a different problem. Scaling the model does not restore it: the 27B goes to 42.3% with relevant tests and 44.6% with the outputs shuffled, and the relevant-test contrast is 17 gains against 12 losses, p = .458. Stronger synthetic tests add 1.7 points at p = .701.

So the honest statement is a scope condition rather than a debunking: tests function as a specification only where the model could nearly get there anyway, and degrade into prompt perturbation exactly in the regime where a practitioner would most want a specification to substitute for capability. The assertion-only control seals it — strip the problem statement and leave the tests, and performance drops substantially. Even where tests help, they are not carrying the intent.

For ci-cd-for-agents this sits upstream of everything the map has argued about the agent's test suite. Those arguments are about what a test checks: whether fail-to-pass constrains the fix (fail-to-pass-does-not-constrain-the-fix), whether writing the test and the fix in one trajectory couples their errors (cogenerated-tests-and-fixes-fail-together), whether coverage predicts anything when the code under test is the buggy code (coverage-stops-predicting-when-the-code-is-buggy). This is about what a test does to the model by being in the context at all, which is a separate channel and a confound for every in-prompt-test result the field has published.

The cheap discipline that follows costs one generation pass: run the irrelevant-test arm. It is the only control that separates semantic guidance from perturbation, and on the hard benchmark it is the arm that wins. The same instinct as the placebo arm this vault adopted for retry loops (a-retry-study-needs-a-placebo-arm) — there, the content-free failure notice; here, another task's assertions.

One further note the authors make and this vault should keep: their synthetic tests were selected by a complexity heuristic and did not reliably beat the originals, because a useful test is not a complex one, it is one that rules out plausible wrong programs. That is the same criterion the adversarial mutant work arrived at from the oracle side (adversarial-critic-rounds-add-kills-over-a-frozen-suite) — fault-detection strength, not surface richness.

Bounds: two checkpoints of one open-weight family, single-turn greedy generation with no execution loop, no repair round and no agent, one completion per condition. Real run-level nondeterminism exists (the 27B original and synthetic runs share prompt hashes but only 44 of 175 identical completions), so cross-run raw differences are not attributable. Difficulty stratification is post hoc and its intervals are wide, so capability-as-a-gate is a plausible necessary condition rather than an established interaction.
