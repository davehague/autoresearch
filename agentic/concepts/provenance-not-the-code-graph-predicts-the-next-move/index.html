The agent is following its own trail, not your import graph

Retrieval and localization modules rank files by dependency proximity; agent scaffolds expose repository-shaped tools. The assumption that code structure guides the next move is already built into current system designs, and it had not been tested against a null that holds the working region fixed.

Tested, it fails. Against a within-episode permutation null — which preserves the multiset of visited files and destroys only their temporal order — consecutive steps are no closer in the dependency graph than chance: one-hop lift 0.94, three-hop 1.02, same-community 1.01. The only quantity clearly above chance is immediate self-repetition (1.47), which is a temporal effect, not a graph effect. The null is the load-bearing part: the visited files do cluster in the graph, and that clustering is what a naive measurement would have reported as evidence for graph-driven navigation.

What does predict the next object is the agent's own execution provenance — the paths that just appeared in a tool output. On first-visit steps, where visit history is empty by construction and a predictor cannot score by restating the agent's past, a predictor reading only the most recent tool output reaches top-3 0.326 with 3.46 effective candidates, against 0.058 for a code graph strengthened to seed multi-source proximity from the entire visited set (at 1,719 effective candidates). 0.689 of first-visit targets had already been mentioned in an earlier tool output. The gap is quoted from the frequency-weighted provenance row rather than the best one, so the paper understates its own result.

The graph is not useless — it is useful one level up. The same graph separates the visited set from random same-size sets by 30.9× in internal edge density, and ranks unseen gold files at a leakage-controlled rank quantile of 0.049. It describes where the agent is working, not how it moves inside that region. The two panels are consistent: inside a region of density 0.269 an arbitrary pair is already likely one hop apart, and the permutation null removes exactly that region effect. So: use the dependency graph to scope the corpus; use provenance to rank the next candidate. Building next-step retrieval on graph proximity is optimizing the wrong conditioning variable.

Two operational readings that fall out of the reliability strata, and they are strata observable before the prediction, not after:

  1. Prediction is trustworthy right after a search and untrustworthy right after a read — top-3 0.469 at ECE 0.013 versus 0.160, an eight-fold spread. A prefetch or speculative-context policy keyed on the last tool type is the cheap version of this.
  2. A small candidate set is not confidence. The lowest-entropy stratum (exp(H) ≤ 5) is the worst calibrated of the three, because a narrow candidate set usually signals that the true answer is not in the set at all. Any harness gating on "the model is sure" is gating on a coverage failure.

And the aggregate hides the real difficulty distribution: handler steps are nearly determined (top-3 0.582), path steps moderate (0.185), and steps whose object is a novel free-text search query essentially unpredictable (0.029) at 21.6% of all steps. Query generation, not path selection, is the hard part of predicting what a coding agent does — which is also where a retrieval layer could most plausibly help and where nothing here suggests structure will supply the answer.

Bounds. File localization, not editing or patch synthesis. The graph conclusions are confined to the 46.2% of agent objects that resolve to a graph node — a real coverage limit the authors return to. One agent and one model family; the per-repository composition is dominated by django, which is why leave-one-repository-out is used wherever a predictor is fitted.
