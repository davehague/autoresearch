Global deduplication changes which corpus looks contaminated — and the answer is opposite for a tool-calling leaderboard than for the ecosystem it's meant to stand in for

This map's first sub-thread (benchmark & contamination validity) has so far tracked contamination as a property of tasks — memorized solutions, leaked test cases. This source measures a distinct construct-validity failure at the tool layer of a tool-calling benchmark: whether the interface surface a model is scored against resembles what a real, independently-authored population of tools looks like, or is instead an artifact of how the benchmark's task rows were assembled. The finding is not simply "BFCL v4 is more repetitive than real tools" — the decomposition matters more than the headline ratio. Real MCP's near-duplication is entirely a within-server phenomenon (the list_x/get_x/create_x naming families one project naturally produces), and vanishes to exactly 0.0% the moment you restrict to pairs from different, independent authors, at every cosine threshold tested. BFCL v4's near-duplication runs the opposite direction: 16.4 of its 16.7 points are between independently-presented task rows — the benchmark repeats itself across tasks it presents as distinct, which is a scoring-validity problem (a model that memorizes or overfits one tool definition gets credit on every row reusing it) that has nothing to do with how real deployed tools look. UltraTool, built for the same purpose as BFCL, comes out cleaner than real tools (0.3% vs 2.8%), which forecloses any claim that synthetic tool corpora as a class are unrealistically repetitive — this is a property of BFCL specifically, discovered because the paper held one method constant across all three corpora rather than auditing BFCL alone.

Interaction edges: agent-harness-architecture — the registry-level finding (37.5% of a random server draw never starts at all, nearly 3x the credential-gating rate the literature assumes) is base-rate context for any harness or evaluation pipeline treating the MCP ecosystem as a reliable tool-supply layer: curated reference frames used to vet or select MCP servers systematically overstate both startup reliability and safety-annotation completeness relative to what an agent encounters drawing from the published population at random.

Bounds: the behavioral tier (server probing, tool extraction) covers npm/stdio servers only — 30.7% of the population and falling (remote-only overtook package-only between the paper's two census snapshots) — so the 48.8% inclusion rate and the tool-corpus comparison do not characterize remote or non-npm servers. Similarity is lexical (TF-IDF cosine), not semantic, which biases all three corpora's near-duplication rates downward in the same direction and does not resolve tools that do the same thing in different words. The cross-unit near-duplication columns are not power-matched (BFCL averages 1.8 tools/task-row vs real MCP's 14.2 tools/server), which the paper identifies as partly inflating how much the BFCL cross-task figure resembles its all-pairs figure — though the real-MCP collapse to 0.0% runs the opposite direction and is not explained by this artifact. A single probe attempt with no retry means the 48.8% inclusion figure is a lower bound, not an exact rate.
