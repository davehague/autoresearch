The bottleneck a growing agent fleet finds first is not the gate policy — it is the infrastructure that decides what the gate even runs

This map's contest is about how strict a CI gate should be for agent-authored code. This source is silent on that question and instead names a prior, more mechanical failure mode: the service that decides which tests to run per PR is itself a piece of infrastructure with a scaling curve, and agent-driven code volume can outrun it well before anyone gets to argue about strictness. Three sequential capacity patches to the same single-process, stateful design each bought less time than the last (70 days -> 29 days -> under a day) — a shape that reads as an architecture problem disguised as a capacity problem, not a story capacity alone could ever fix.

The 8x-code-per-quarter figure is not new to this vault (anthropic-claude-on-call-cicd cites the same company-wide number), but this source attaches two figures that number lacked: 10x test-suite growth and 25x CI-job growth over six months specifically, plus a first concrete account of what breaks when that growth hits a system that was never designed to shard. The fix — move state off the process boundary into a store, make the listener stateless and horizontally scalable, keep the selector as a fast reader over a rolled-up history — is a standard scaling pattern, not a novel one; what is useful here is naming which CI subsystem hits the wall first under agent load (test selection, not build capacity or the merge queue) and that patching capacity without changing the architecture bought successively shorter runway each time.
