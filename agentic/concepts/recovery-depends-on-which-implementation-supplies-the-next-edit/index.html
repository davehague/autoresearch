The same failure, the same feedback, two different recovery rates -- because the editor was shown a different starting point to revise from

Retention doesn't just decide what keeps running between edits; it also decides what the next edit is made from. This paper separates those two questions cleanly, and the separation is the finding: keeping the incumbent active after rejection and choosing the incumbent as the editing parent are two different knobs that happen to default to the same value in most self-improvement loops. Holding every other variable fixed -- same 42 failed programs, same validation rule, same feedback -- redirecting the editor from "revise the thing that just failed" to "revise the last known-correct version" takes the unsafe-endpoint rate from 14/42 to 1/42 after six rounds.

This is a mechanistic complement to historical-archive-scores-preserve-unsafe-programs-refresh-fixes-it from the same source: that note is about what gets selected to run; this one is about what gets handed to the editor as a starting point for the next revision. Both sit on this map's sub-thread (2) governance question, and together they argue that a self-improving harness's safety properties are set by a short list of discrete control-plane decisions (which archive entry is deployed, which archive entry is the editing parent, what happens when nothing passes) rather than by how good the editor is. The editor-dependence result makes this concrete: Devstral recovers well regardless of which source it edits from, while Qwen recovers poorly under either source -- so "use founder editing" is not a substitute for editor capability, it is a separate lever that happens to matter more when the editor is weak at repair in general.

One caution the paper itself states plainly and this note keeps: founder editing changes where proposals come from, not what gets deployed. The incumbent still competes in the eligible set, and current-contract validation still has to clear whatever wins before it runs. Treating "edit from the founder" as a safety mechanism on its own, without the validation gate that decides deployment, would be a different and weaker claim than the one measured here.

Interaction edge: loop-engineering -- this is a within-agent repair-loop result (which starting point the repair is made from) measured on an authorization-safety outcome rather than a task-correctness one; that map's own within-agent sub-thread has asked a structurally similar question (does editing source or feedback richness change recovery) on correctness tasks, and found feedback richness alone does not reliably improve recovery either -- a second, independent domain where "give the editor more information" is not the lever that moves the outcome; "give it a different starting artifact" is.

Scope: the 42-root cohort is a recovery-from-shared-failure measurement, not a measurement of how often each editor produces a failure in the first place -- the editors were not compared on failure rate, only on repair rate once already failed. Editor-level variation is observed, not mechanistically explained.
