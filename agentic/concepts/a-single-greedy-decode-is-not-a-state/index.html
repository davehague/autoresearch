The ratio was two single-digit counts, and both of them were noise

Batching nondeterminism is widely known and almost never controlled for. This is the measurement of what it costs when a comparison is built on single greedy decodes, which is how most before/after item ledgers in this vault's source literature are built.

Take an untrained model. Evaluate it twice, greedily, on the same 200 problems. Diff the verdicts. You get 6 problems it "learned" and 9 it "corrupted" — a corruption-to-learning ratio of 1.5, which is exactly the shape of the finding the self-improvement literature reports as alarming. Nothing trained. The solve-rate estimator over the same samples reports 1 and 0.

Two things make this more than a caution.

The mechanism is tested, not cited. Run the same 200 problems greedily under 64 concurrent requests and again strictly serialised. Flips fall 16/200 → 4/200 (Fisher p = 0.005) and extracted-answer changes 25 → 5 (p < 10⁻⁴). So batching is the dominant cause — and it is not the only one. Fully serialised, the frozen model still flips 2% of its verdicts, and no discipline about one's own request pattern reaches server-side batching across tenants or nondeterminism below the API. This is not a bug you can fix from the client side of a hosted endpoint.

So the repair is not "decode more carefully." It is to stop treating a decode as a state. Draw k samples, estimate the solve rate, and discretise with hysteresis — a dead band of ½ ± z·√(1/4k) inside which the previous state is held, so a problem must move further than ordinary binomial jitter before the ledger records it as changing. At k=128 and z=2 that band is [0.41, 0.59]. On a 1,163-problem set the difference is 18.9% of problems changing state under greedy decoding against 0.8% under the estimator — a factor of twenty-four in the amount of movement the instrument reports.

This is the decode-level sibling of one-draw-per-item-recovers-none-of-the-reliable-changes, which showed that one trial per item recovers none of 457 statistically reliable changes and produces flips that are about a coin toss. That note says a single draw misses real changes; this one says it fabricates changes that are not there. The two failures point the same direction and are separately fatal: an item-level before/after comparison built on one sample per item is measuring its own inference stack.

For anyone running scheduled agents: the same property means a "did this regress?" check built on one run per task at temperature 0 is not a regression detector. It is a sampler with an unmeasured floor — see a-null-measured-once-is-a-point-estimate for what it costs to measure that floor properly.
