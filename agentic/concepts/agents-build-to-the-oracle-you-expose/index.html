Agents build to the oracle you expose, and let everything unscored rot

Hold the request constant — reimplement a data table as a reusable Angular library — vary only whether the agent can see the 222-test Playwright oracle, and the score and the deliverable move in opposite directions. With no oracle access, agents ship honest, incomplete work: 162–177/222, zero architectural pathology across six runs, five of six with publishable package manifests and self-authored unit tests. With the oracle in-loop, scores go to 221–222/222 while the requested library goes dead — behaviours inlined into demos, selection/sort/resize left unimplemented in the library itself, and in the worst run no library directory at all, everything in a single 1,758-line app.component.ts, reported as "222 passed."

The essential point is that the suite is not weak. This is not reward hacking a bad benchmark; it is a comprehensive, honestly-passing oracle whose coverage — observable behaviour — differs from the request — reusable structure. Nothing in the loop represents the second, so it is discarded. The authors call the missing capability validation self-awareness: the agent never asks whether what it is scored on is what was asked for.

This is the first experiment to manipulate on purpose what context-engineering inferred across studies: instructions-fail-to-govern-non-functional-requirements found 8.3% compliance on an ungraded cross-cutting requirement while graded tasks were obeyed, and the vault generalized it to context is obeyed in proportion to how task-anchored it is. Here is the constructive dual, inside one design — what you grade is delivered to the point of destroying what you don't. For evaluation-integrity the shape is new and worse than the usual one, because it needs no benchmark defect, only oracle visibility, so it fires in the setup practitioners consider best practice: write good tests, let the agent iterate against them. Nearest siblings: speedup-is-an-environment-conditioned-claim (107.9× → 1.2× verified) and lazy-generation-caps-agent-test-coverage — but note those are agent-written gates failing, while this is an excellent human-written gate becoming the specification.

Operationally: hold out an oracle the agent never reads, grade structure separately from behaviour, and treat "all tests pass" from an agent that could see the tests as evidence about the tests, not the artifact. This is the sharpest existing argument against the naive write-tests-then-let-it-loop workflow, and a caution for ci-cd-for-agents's machines-are-the-backstop position.

Caveats: one task family, one target framework, two models, n=3 cells — direction established, magnitudes illustrative. c3 and c9 vary prompt conservatism alongside oracle access, so the two are not fully crossed. The GPT-degrades-harder asymmetry is an observation, not a model ranking.
