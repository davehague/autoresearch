The census for the other instruction surface, and the number is the copy rate

Yesterday's arrival, the-project-rule-file-is-written-once-and-abandoned, was the population census behind three weeks of instruction-surface results: 12,110 rule files, 67.3% never edited after creation, 95.8% single-contributor, 40.7% committed within a day of the repository itself. This is the same move for the other instruction surface — the packaged, model-selected skill — and it is two and a half orders of magnitude larger. 3,797,117 SKILL.md files across 282,200 repositories and 195,841 accounts, nine months after the format was published. The vault has been reasoning about skills from controlled studies of handfuls (a-skill-buys-validation-not-efficiency, an-unguarded-skill-pool-peaks-then-degrades, a-weaker-model-writes-a-longer-skill, skills-regress-as-much-as-they-gain). This is what the population underneath those studies actually looks like.

50.5% of the collected files are verbatim copies of another file. Exact content hash, so near-duplicates — the copied skill with one line edited, which is the normal case — count as distinct, and the true copy rate is higher, not lower. That single number reorganises several things this vault already believes.

It makes the security results structural rather than hypothetical. screen-skill-files-before-they-enter-the-context and skill-contamination-survives-removing-the-skill both describe a payload that arrives through a skill file. A population where half the artifacts are copies, with no registry, no package manager and no version constraint, is a distribution channel with no revocation path: nothing tells the 200th copy of a skill that the original was withdrawn, and nothing can, because there is no edge from the copy back to the source. That is the same shape as setup-instruction-supply-chain-attacks and project-documentation-is-a-code-execution-attack-surface, now with a denominator. It also makes skill-exploitability-is-an-agent-property-not-a-payload-property more uncomfortable, not less — if exploitability is a property of the consuming agent, then 3.8 million identical payloads sit in front of a population of agents whose individual susceptibility varies.

It also gives the artifact class its own description, and the paper's framing paragraph is the most useful prose in it. A skill is not like anything the mining-software-repositories community has instruments for: written mainly in natural language, selected probabilistically by a model at run time, and no compiler or type checker verifies the selection. That is exactly why a-skill-description-acts-without-being-invoked and skill-invocation-rate-is-a-harness-property were surprising when they landed — the selection step has no static semantics, so nothing about a skill's presence predicts its effect. And it is why pool-skills-across-developers-instead-of-personalizing-them is the right operational default: a shared pool at least has one place to fix a bad skill, which a copy graph does not.

What this source does not say matters as much as what it does. It is a three-page data paper. It reports the counts, the duplication rate and the collection method, and it reports nothing else — no maintenance analysis, no front-matter conventions, no size distribution, no authorship concentration, no security findings. It should not be cited for any of those; they are explicitly the research the dataset is offered to support. The 458,548 commit-history records and 7,264,865 sibling-artifact records mean the obvious follow-up — is a skill maintained after it is copied, and does the copy diverge — is now a SQL query away rather than a crawl away, and nobody has run it. That is a concrete open question rather than a gap in the literature.

Bounds. One snapshot (July 2026), so no trend. A stated lower bound on the population: GitHub code search covers only default branches, files under 384 KB, recently-active repositories with fewer than 500,000 files, and indexes forks selectively. Public repositories only — the private and enterprise population, where an instruction surface carries the most operational weight and where an-agentic-context-file-grows-until-someone-bulldozes-it would predict the largest files, is entirely invisible. And a raw file count is a count of files, not of use: nothing here establishes that any of these 3.8 million skills was ever loaded by an agent.
