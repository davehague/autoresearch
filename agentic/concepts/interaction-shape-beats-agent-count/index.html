Four ways of adding a checker, all worth nothing, and then one that is worth ten points

The value of this result is the construction: six methods built on one benchmark with one model, each step adding exactly one design choice motivated by the measured failure of the previous one. It reads as a controlled ablation of the entire "add a verifier" family, and four of the six land in the same place.

  • Zero-shot — 77%.
  • Self-critique by the same agent — 77%. No movement, and the stated reason is this map's oldest finding: the critic and the generator are the same model making the same mistakes (an-independent-checker-beats-the-same-model-checking-itself).
  • One separate external reviewer — 77%. A lone reviewer has high variance: it approves everything or flags nits.
  • Two independent reviewers, union of findings — 75%. Independent samples do not push past the level.

Four methods, one indistinguishable cluster, and the last of them is worse than the first. Then the shape changes rather than the count. A parallel-review system with three structured reviewers and a meta-reviewer breaks out at 82% — five agents for five points, with all inter-agent interaction removed. And a three-agent loop where a critic audits the reviewer's review over a frozen artifact reaches 87%, beating it with two reviewing roles against four.

The frozen-artifact separation is the structural idea worth extracting. The inner loop exchanges review text only — the artifact is never edited while reviewer and critic are still disagreeing about what is wrong — and edits happen only in the outer loop, after the review stabilises. That prevents the agents from jointly rewriting the solution mid-argument, and it has a second benefit the paper exploits: because the inner loop never touches the artifact, it can be lifted out and evaluated separately as a code-review method, which is how the false-consensus failure was found at all (two-agents-told-to-agree-will-agree). A loop whose stages can be scored independently is a loop whose failures can be located.

This is multi-agent-helps-only-decomposable-tasks and coordination-saturates-as-the-single-agent-improves sharpened into a positive prescription: the returns are not in how many checkers, they are in whether the checkers read each other's output before the artifact moves. Adjacent evidence in this map points the same way — hierarchical-swarm-beats-flat-swarm-on-the-same-task, transfer-coverage-beats-agent-count-in-orchestration, the-quadratic-cost-of-a-team-is-mostly-a-handshake.

The protocol survives being written down as prose, which is the deployment-relevant half. On repository-level repair the same protocol is expressed as a pure-text skill document and handed to an autonomous agent that decides for itself when to invoke the reviewer and critic and when to edit — no orchestrator forcing any step. It still wins: 75.2% against 71.6% zero-shot and 72.6% for the five-agent system. So a cooperative protocol is portable across agentic systems when its roles and decision rules are simple enough to state in text, which is a real constraint on how elaborate a loop can usefully be.

The cost is real and the authors decline to universalise the win. AR uses ~4.5× zero-shot tokens and sits on the cost-quality Pareto frontier of every benchmark tested — no method is both cheaper and better — but on easy tasks the review loop is wasted computation and on narrow-scope issues extra review raises the chance of over-editing. Their own case studies show both directions: the loop moves the agent from a 45-line symptom patch at the caller to a ~20-line root-cause patch at the callee and is the only method that passes; and elsewhere it turns a reviewer's speculative "what if the user calls this separately?" into an out-of-scope 32-line patch that fails where a 24-line zero-shot patch passed. The loop helps when disagreement redirects toward the true bug and hurts when it expands the repair beyond the issue — which is an argument for intervene-on-a-trigger-not-on-a-schedule applied to the review loop itself.

Bounds. One model family across every agent and every benchmark. LiveCodeBench measures competitive-programming correctness, not repository work, and the 105/57 task counts make several of these differences small in absolute terms. SWE-bench Verified compares only three methods because a full run is estimated at over 300 hours each. The two execution modes (strict orchestrator vs autonomous skill) answer different questions and are not interchangeable.
