Restricting self-improvement to prompts only makes the governance problem small enough that a test-repair-verify loop rejects nearly everything risky — but a handwritten rule does just as well, and the runtime underneath the prompt layer has its own unguarded gaps

This is runtime-action-governance's first deployed-product evaluation of a self-improvement admission gate, and it narrows harness-self-evolution's sub-thread (2) ("can self-modification be governed at all") to a specific, tractable scope: when the editable surface is prompts only — weights and runtime code held fixed — a loop that tests the proposed and current instructions, repeats failures, temporarily reverts to localize a repair target, and gates adoption on risk and utility thresholds rejects 20 of 21 deliberately risky update attempts. That is a plumbing success, not a capability result: the authors are explicit that the gate supplies no statistical safety guarantee, only an empirical point-estimate rule, and the one successful learned repair (GPT-5.6 Luna) is matched exactly, flag-for-flag and completion-for-completion, by a broad handwritten authority rule with no learning loop at all. For this scope of problem, at least, the self-improvement machinery did not out-perform a human-written rule — a useful negative data point against reading every self-evolution result on this map's sibling harness-self-evolution as evidence that search beats hand-engineering by default.

The runtime probes are the more portable finding and a direct, concrete instance of this map's standing architectural claim: enforce permission below the prompt, not inside it. A memory-entry deletion that succeeds on inspection but is refilled from retained source content and conversation history after an idle wait, and a tool-dispatch path with no local OAuth scope check before the request reaches the external provider, both sit entirely outside what any amount of prompt-level update evaluation could ever catch — they are properties of the runtime the agent's instructions sit on top of, not properties of the instructions themselves. The product only avoided a real violation in the OAuth case because the external provider's own enforcement caught it; nothing local did.
