The loop hardens what happens, not when the agent is allowed to stop looking

This map's practice for unattended work is externalized durable state, a resume contract, and a hard boundary on authority. All of it is machinery for what the agent does. This is a failure mode in a different variable, and it is the one an operator meets first: the agent does the right things, in the right order, and never decides it has enough.

The observation is incidental to the paper's argument and the author flags it as "a current takeaway of Section 7, not a research direction", which is roughly the right weight. qwen3.8-max — a flagship reasoning model, and the largest in the replication set — failed to converge on a governed workflow in 0 of 4 clean runs, looping retrieval until the round cap, while deepseek-v4-flash, v4-pro, kimi-k3 and glm-5.3 all completed. The exclusion accounting is what makes it usable rather than an anecdote: every other excluded run in the ledger is a provider or gateway fault, and these four are recorded as model behaviour rather than being quietly dropped.

The diagnosis is structural and it generalizes past the model. "The state machine hardens what happens (retrieve, then generate) and not when the agent may advance." A workflow contract can specify the tool sequence, the state transitions and the artifact fields — and this one did, tightly enough that the same contract produced byte-comparable structural output on four other models — without specifying the sufficiency condition for moving on. That is the gap a-stop-decision-needs-a-receipt-not-a-judgement approaches from the safety side (do not stop before the evidence supports it) arriving from the opposite side: an agent that will not stop after the evidence supports it burns the budget and produces nothing, and in an unattended run there is no one to notice the difference between working and circling.

Why the capability-ranking clause is the load-bearing part. The vault has this pattern from an adversarial direction already — the-agent-authors-the-malware-so-submission-screening-cannot-see-it found vulnerability to skill self-poisoning does not track model size or capability, with the 1.6T model copying most and the 120B and 230B least, and the ordering reshuffling with the task distribution. This is the same non-monotonicity in a benign variable: whether a model commits to a terminal action is a behaviour of the model against your workflow, and nothing in a leaderboard position predicts it. For a fleet that swaps models on cost or availability, that means a model swap is not a quality decision with a known direction; it is a change that can convert a working unattended job into one that never terminates, with the failure looking like a timeout rather than a regression.

The rule is cheap and the paper states it as a rule: before adopting a model on a governed workflow, verify its advancement behaviour on that workflow — whether it commits to the contract's terminal action once evidence suffices, rather than re-evaluating indefinitely. This is harness-is-tuned-per-model-and-version narrowed to a single measurable property, and it costs four runs to check.

Bounds. One development/pilot system, one workflow, one team, operated by the author. Four clean runs on the failing configuration is a small denominator for a 0/4 — the honest reading is did not converge in the runs we had, not a rate. No mechanism is established: token and latency evidence leans toward over-evaluation, but model content was not logged, and the author labels that an inference rather than a finding. Two gateway adaptation gaps were fixed same-day during the run and third-party endpoint capacity dominated re-run cost, so the ledger is not a clean experimental design. Nothing here compares model versions, prompt variants, or round caps.
