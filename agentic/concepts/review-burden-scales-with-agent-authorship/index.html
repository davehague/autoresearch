The comprehension debt, metered at production scale

This map has carried the review-capacity argument on inference and small samples: comprehension debt outpaces review capacity (comprehension-debt-outpaces-review-capacity), automated review displaces human review as volume rises (automated-review-displaces-human-review-at-scale), humans silently repair agent code outside the review channel (humans-silently-repair-agent-code-outside-review), a third of accepted completions are deleted rather than fixed (a-third-of-ai-completions-are-abandoned-not-repaired). What it has not had is the load number from a real review queue at scale.

Here it is, over twelve months and 3.52 million changes, while the agent-authored share of the queue rose 28.99% → 68.62%: 1.92× blocking comments, 1.39× total comments, 1.24× reviewer iterations, 1.19× time to merge, 1.07× submit attempts. Every review observable moves the same direction, and the blocking comment ratio — the reviewer saying "not like this" — moves nearly twice as hard as the others. This is the capacity claim confirmed at the only scale that settles it.

Part of that is size: agent changes are 89 lines against 33 and 83% new code against 60%, and a bigger change draws more comments in any organization. The authors' adjusted models control for size and organizational slice without eliminating the gap, and the ratios that do not move with size are the informative ones — a per-function view shows agent functions are actually shorter (11 LOC against 15), so the coupling and interface findings driving blocking comments are not a mechanical consequence of bulk.

The finding that should change practice is the null. The authors report no clear correlation between standard review metrics — time, iterations — and whether the inefficient AI code survives. Reviewers are working measurably harder on this code and that effort is not what removes the defect class the code actually carries (what-escapes-the-review-gate-is-efficiency-not-correctness). That is this map's own thesis about the limits of the review channel, arriving from the direction of effort rather than of accuracy: the gate is not under-resourced, it is looking at a different axis. What did move the number was upstream and automatic — naming the defect category back to the generator, worth 11.1% of the targeted findings (name-the-defect-category-not-just-the-quality-bar) — which is an argument for spending the marginal review budget on a mechanical pre-check rather than on more human passes.

Also worth carrying beside agent-throughput-doubles-without-merge-or-revert-collapse: this organization's revert rate for agent code sits below parity at ~0.9× while build failures sit at ~1.3×. Throughput did not collapse. The bill arrived somewhere else.

Caveats: one organization with a mature centralized review culture and authoring-time provenance instrumentation — the authors say results are most transferable to "similar review-gated monorepo workflows." Observational and uncontrolled for reviewer identity or task difficulty. The comment counts are review-system events, not adjudicated defects, so a blocking comment is a proxy for reviewer friction rather than for a real fault. And developer prompting proficiency grew across the same window, which pushes the early-window ratios in an unknown direction.
