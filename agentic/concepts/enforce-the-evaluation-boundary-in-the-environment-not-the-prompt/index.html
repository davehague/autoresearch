Restrictions the agent cannot follow because it cannot see them

This map's standing problem is that an agent evaluation is a system the agent participates in. Benchmarks get gamed by retrieving the fix (benchmark-scores-inflate-when-agents-can-retrieve-the-fix), by judges with exploitable biases (llm-judges-have-exploitable-biases), by search-time leakage (search-time-leakage-inflates-web-agent-scores), and by evaluator hijacking. The usual response is a better rule, stated to the agent. This is the design that stops stating rules.

The optimizer's sandbox does not contain the test partition. It does not contain the provider credentials. It does not contain the code that enforces the budget. Every one of those lives on a trusted evaluation server or a model gateway on the other side of the boundary. As the authors put it, the restrictions are properties of the execution environment rather than instructions the optimizer is expected to follow — there is no compliance step to fail and no injection that reaches the thing being protected.

This is the runtime-governance lesson arriving inside the evaluation harness, and the convergence is worth naming explicitly because the two literatures do not cite each other. The governance map's founding claim is that high-risk constraints belong compiled into the environment rather than requested of the agent (enforce-high-risk-constraints-below-the-prompt-layer, contain-at-the-environment-layer-first), with the corollary that a gate on the agent's own dispatch path is only as strong as the transitive closure around it (an-intermediary-on-the-response-path-voids-client-side-gates). Held-out data is exactly a high-risk constraint, and an optimizer with filesystem access and a coding harness is exactly an adversary-shaped capability whether or not it is adversarially motivated. The same three-layer answer applies: environment first, metering second, audit trail last.

Graded disclosure is the part most evaluations get wrong in a subtler way. The design does not simply hide everything — it tiers what each partition emits by what that partition is for: development reveals per-case outcomes and full execution traces because its job is diagnosis; validation reveals only an aggregate score because its job is selection; test reveals nothing. That maps cleanly onto the vault's progressive-disclosure results (one-level-of-disclosure-is-enough, progressive-disclosure-buys-context-not-intelligence) but for an adversarial rather than an economic reason: a selection signal rich enough to diagnose against is a selection signal rich enough to overfit to.

And the boundary earns its keep in the numbers. Most submitted candidates score below the best validation score observed during search — the visible best is optimistic, so a system reporting its own search-time peak would be reporting an inflated number. The paper is careful that this cannot separate selection-induced overfitting from a validation–test mismatch and claims only the weaker statement, which is the right call and does not weaken the operational point: without the held-out partition you would have published the optimistic number and not known. That is the same shape as discovered-harnesses-transfer-off-the-search-distribution and the matched-budget objection (harness-evolution-underperforms-matched-budget-test-time-scaling), measured here as a routine property of the protocol rather than as a scandal.

The budget denomination deserves separate mention because it is a fairness mechanism, not a cost control: counting evaluation calls and full case passes rather than compute means a comparison cannot be won by bringing more hardware (charge-every-search-method-the-same-budget). And the meter is on the far side of the gateway, so it is a fact about the run rather than a claim in the writeup (audit-agent-claims-against-trajectory-evidence).

Bounds, and the authors state them first. The design is hack-resistant, not hackproof: the optimizer cannot reach the test partition or alter the target model, environment or verifier, but repeated development and validation feedback can still reward strategies specific to a fixed evaluation, and the named remedy — per-run jitter in cases, tool behaviour and verifier implementation — is future work. Everything here is one benchmark's infrastructure over 111 runs; the design is argued rather than ablated, since there is no arm in which the boundary was removed.
