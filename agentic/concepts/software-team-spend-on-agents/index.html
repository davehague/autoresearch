This map has priced per-request and per-trajectory routing for years; this is its first attempt at pricing team-level agent spend as a whole, and the answer is the same shape as every other allocation question here — no fixed ratio, allocate against measured capability and the cost it actually avoids

Every routing claim this map has carried prices a single increment of effort — a model, an iteration, a tool call. This paper asks the question one level up: how much of a team's budget should go to agents at all, and on what. The method is a calibrated simulation rather than production telemetry (a genuine step down in evidence strength from this map's usual T1 production studies), but the result composes cleanly with the map's standing instruction that the unit of routing is the next increment of effort, allocated against measured capability rather than a fixed schedule.

The sharpest finding is a non-obvious cost mechanism, not a ratio. A cheap, low-capability agent is not a bargain in this model, because its output drives more downstream quality-assurance cost than its cheap tokens save — capability dominates price because of where the cost actually lands (escaped bugs, audited downstream), not because capable models are intrinsically "worth it." That is the same shape as this map's other capability-over-price findings, now derived from a team-economics model rather than a per-task routing benchmark.

It directly tests, and rejects, the universal-ratio framing the paper opens against (Nvidia CEO Jensen Huang's "a $500k engineer should consume $250k in tokens" quote, March 2026) — no scenario in the 432-scenario sweep supports a fixed per-developer token budget; the optimum moves with velocity, debt dynamics, and bug cost the same way traditional team sizing always has. Useful as the first explicit counter-evidence this map has against any fixed agent-spend-per-developer heuristic a reader might otherwise adopt from vendor rhetoric.

Bounds — read as suggestive, not strong: this is a sole-author simulation with fixed (not sampled) per-feature and per-bug cost parameters, no real organizational data behind the eight-role structure or cost calibration, and simplifying assumptions the author states directly (debt-independent human effort, independent re-inspection across review passes). It is a model of the trade space, not a measurement of any real team's economics — treat the qualitative shape (capability over price, no fixed ratio, bug-finding dominates the ledger) as the transferable claim, and the specific percentages as this one model's output.
