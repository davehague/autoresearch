A guard clause preserves behaviour, which is exactly what the suite is checking

Hold the task fixed. Hold the model fixed. Hold the generated patch fixed. Change only the acceptance criterion — add a check that fails while the code the repair was supposed to remove is still present — and 21.3 points of reported resolution disappear. Every one of four frontier models declines, by 17.6 to 23.5 points. A third of the attempts the original suites accept are retaining a validated deletion target.

This map has accumulated a shelf of proxies that rank wrong. Coverage predicts real-bug detection across models and near zero within one (coverage-stops-predicting-when-the-code-is-buggy). Fail-to-pass certifies tests that impose no constraint on the fix (fail-to-pass-does-not-constrain-the-fix). Resolve-rate gains do not carry quality gains (resolve-rate-gains-do-not-carry-quality-gains). Those are calibration failures — the proxy moves, just not with the thing you wanted. This one is different in kind. It is a structural blind spot, and no amount of strengthening the proxy closes it.

The mechanism is one sentence. A behavioural suite asserts what the code does on the inputs it exercises. A patch that keeps the offending code and adds a condition routing around it does exactly what the suite requires on exactly those inputs. The retained path is unreachable for the tested case, so there is no test to write. Harden the suite, add mutants, raise coverage — every one of those operations asks a behavioural question, and the patch's answer is correct.

That has a direct consequence for this vault's newest CI advice. As of 2026-07-28 the rule is keep diff coverage as an outside-the-agent floor, stop reading it as suite quality, and grade the test against adversarial mutants of the current patch (a-passing-suite-does-not-mean-a-tested-change). Mutant grading measures whether a suite distinguishes the patch from perturbations of the patch. A Guard-and-Go patch and its mutants have the same observable behaviour, so they agree, and the criterion passes. The check that catches this is not a better test — it is an assertion about the source: this construct is absent from its enclosing scope. Different oracle, trivially cheap, and absent from every gate in this corpus.

The generalisation worth taking is not "add deletion checks." It is that the class of defect a gate can see is fixed by the class of statement the gate can make, and this corpus has one class. Every executable contract the vault carries is behavioural — a test suite, 24 observable checks, an output comparison — and the spec-driven map already separated out a second, structural family that asks whether the intended path exists at all, checkable statically before anything runs. Deletion is the smallest possible instance of that second family, and it is worth a fifth of the reported score on the tasks where it applies.

Two bounds keep this from being larger than it is, and one keeps it from being smaller. The 34 tasks are deletion-heavy by construction and are not representative of Verified as a whole, so 21.3 points is the effect on the affected slice, not on the benchmark; each task moves the number about 2.9 points, so 29 flipped attempts carry it. And the developer patch is a behavioural reference rather than the unique correct repair — an alternative fix could legitimately preserve the target, which the authors state plainly: the retrofit identifies an evaluation gap without establishing that deletion is the only valid answer. Pointing the other way: 377 of the 500 Verified tasks require at least one deletion from a non-test file. The slice where this oracle applies is not a corner.
