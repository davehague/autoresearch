The framework is under test; the agent is not

The field measures agents constantly and almost never tests them. This is the first large look at the difference, and the numbers are uniform enough to be a description of practice rather than a sample: 61.8% of agent-related tests exercise a tool or agent in isolation, 8.7% assert on anything reasoning-related — and those mostly check that reasoning happened, not that it was right — 7.5% touch a non-functional requirement, 4.1% validate an interaction with a non-deterministic non-agentic component. The median test is 14 lines with cyclomatic complexity 1 and two assertions.

The mocking pattern is the tell. 34.4% of tests mock an agent or tool, and 22.3% mock the entire agent — a hand-written test double that replaces non-deterministic LLM behaviour with scripted responses while preserving the surrounding framework execution. That test verifies the wiring. It cannot fail for any reason related to the model, the prompt, the tool descriptions, or the trajectory. A suite built this way stays green through exactly the changes that break agents in production.

This lands squarely on a map that already holds agent-written-tests-miss-the-lines-they-add, a-passing-suite-does-not-mean-a-tested-change and agents-under-instrument-the-code-they-write — all about agents writing weak tests for code. This is the other half: humans writing weak tests for agents. Same shortfall, opposite direction, and together they mean the gate on both sides of an agentic pipeline is thinner than its green checkmarks suggest.

One structural finding is actionable. Testing level correlates with framework abstraction — MCP and FastMCP applications lean on unit tests, LangChain/LangGraph balance, DSPy (where the developer owns composition and boundaries are less clear) leans hardest on integration. The framework you pick sets the default granularity of what gets tested, and the frameworks that make component boundaries crisp are the ones whose users test the components and not the composition. Anyone choosing a framework is also choosing which failure class their suite will be blind to.

Test data is the other cheap fix. 39.9% of tests feed example-style inputs (test1, test2). The paper shows a PII-redaction policy test — exactly the kind of behaviour you would want covered — validated against a single sample record. That is the same shortfall visible-tests-perturb-more-than-they-specify and agents-build-to-the-oracle-you-expose describe from the generation side: a thin oracle is not just weak evidence, it actively shapes what gets built to satisfy it.

Bounds. Python GitHub repositories on popular frameworks with a quality filter — generalization to other languages, proprietary codebases and other frameworks is untested. No standardized testing ontology exists for agentic systems, so categories are approximate and derived by the authors; multi-labeller review with Cohen's κ is the mitigation. Some corpus tests may themselves be AI-generated; heuristics found no clear evidence but it cannot be excluded. Most importantly, the study measures what is tested, never whether the tested projects are more reliable — no defect rate, incident rate or production outcome is measured anywhere, so "shallow" is a description of the tests and not a demonstrated cost.
