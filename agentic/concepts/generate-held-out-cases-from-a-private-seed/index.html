Generate the held-out split instead of shipping it

This map's contamination remedies split into two eras. The run-time ones stop the agent reaching the answer — strip .git, deny egress, pin a registry allow-list — and none of them touch the channel that survives a sealed container, the task text sitting in training data. The one upstream remedy the vault holds, build-tasks-from-private-artifacts-not-public-issue-text, reverse-engineers tasks from private artifacts so the searchable prompt never existed; the vault recorded it as a design argument, not a result, because it shipped with no leakage number and no counterfactual.

This is a second upstream mechanism with a different shape and it fixes the structural problem rather than the current instance. The held-out cases are not stored at all. In their place is a per-family generator of deterministic, physics-aware perturbations that synthesizes a case on demand from a private seed, under an acceptance rule — keep a draw only if the reference solver solves it and no small perturbation of that solution scores higher. The operator keeps the seed; anyone can read exactly how held-out cases are constructed without learning which ones a round used. The confidentiality boundary extends sensibly to run records: aggregate results are publishable, per-case held-out submissions and logs are not.

The property that matters is that it does not age. A published held-out set is a depreciating asset — every month after release it is more likely to be in the next model's training data — and this design has no artifact to leak. That is a genuinely different answer from "build this year's set from private sources," which produces a fresh depreciating asset.

The generator is validated; the contamination claim is not

The distinction the paper keeps straight, and the vault should keep straight when citing it, is between these two:

The generator works. Eight draws per family from a fixed validation seed: all 328 feasible without exhausting the redraw budget, every variant differing from its public case, 40 of 41 families producing eight distinct instances, continuous inputs varying at a coefficient of variation near 0.2. The single exception draws a fault location from a small discrete set and yields four distinct instances of eight — an inherent bound for categorical families, correctly diagnosed as such rather than as a generator fault. This is a real property of the construction.

Contamination is not thereby measured. Public and held-out scores track each other and the signature one would expect from contamination — public standing above held-out — is absent. But the leaders sit at 0.973 → 0.995 and 0.973 → 1.000: this comparison is run at ceiling, where nothing could have shown a gap, and if anything the held-out draws came out marginally easier. The author declines the inference outright, claims no intrinsic difficulty gap between splits, and states the case for the generator as prospective. That is the right call and it is the honest version of the move this map demanded in benchmark-scores-inflate-when-agents-can-retrieve-the-fix — prevalence is not inflation, only the counterfactual licenses the claim. Here the counterfactual was run and came back uninformative, which is a different and better outcome than not running it.

So: adopt the mechanism on the structural argument, and note that the field still has no measured inflation delta for any upstream contamination remedy. The experiment remains cheap and undone; it needs a benchmark with headroom.

Bounds. Single unaffiliated author, 41 compact task families, one case per family per split — the author notes a ranking over 41 points is statistically fragile while observing that the generator makes enlarging the sample inexpensive, which is itself an argument for the design. Generator validation used the reference solver for feasibility, and that solver shares code with the evaluator (an-evaluator-sharing-its-reference-solver-cannot-be-self-checked), so "feasible" here means "solvable by the component that also grades it." Electric power engineering, not software engineering.
