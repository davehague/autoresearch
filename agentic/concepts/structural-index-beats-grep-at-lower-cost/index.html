A structural index beats grep at lower cost

The map holds "retrieve just-in-time" as grep/glob-style tool calls or a lightweight table of contents (just-in-time-context-retrieval, agents-md-is-a-map-not-a-manual). This says the structure of the retriever is itself a lever: a context engine combining code-chunk embeddings, a graph of definitions and call edges, and BM25 lexical search — built over live source and queried at retrieval time — beats agentic-grep on localization (+8.1 pp) and resolve (+6.0 pp), and beats the same harness with the index off by +39.6 pp localization and +7.9 pp resolve. The graph of definitions/call edges is what buys the structural reachability that multi-file changes need, which is where the gain concentrates.

The result that changes the deployment calculus is cost: the richer retriever lands at a lower dollar-per-solve ($2.30 vs $2.92 for agentic-grep) because it finds the edit site faster and wastes fewer turns — a retrieval-design cost lever for model-routing-token-economics, not a cheaper model. The authors' framing: the deployment question is not whether the index is too expensive (it isn't) but whether the workload has the multi-file changes where structural ranking pays off.

It composes with the 2026-07-20 discriminating axis for machine-built context — verify-generated-context-against-live-source: a generated artifact the agent trusts blind (a lossy AGENTS.md, generated-context-files-cost-more-than-they-help) hurts, a generated index over ground truth queried at retrieval time helps. Same "machine-built context," opposite sign, set by whether it resolves to current source.

Caveats: 91 instances, 3 seeds; the cross-harness gains (+8.1/+6.0 pp) are marginally non-significant (p=0.080/0.087) — only "beats index-off" (+7.9 pp, p=0.003) clears p<0.05; one model (Opus 4.7); payoff is workload-dependent (multi-file); the vector/graph/BM25 combination is not ablated into parts. T1, suggestive.
