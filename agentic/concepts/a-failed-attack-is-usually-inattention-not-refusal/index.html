Nothing happened, and not because anything stopped it

The headline number of this study is that two enterprise-deployed coding agents execute hidden shell payloads from benign-looking skill files in 96% and 73% of runs. The number that changes how you read every other agent-security result is the complement.

Of the runs where the attack did not land, the agent recognized it as an attack 15.3% of the time on one agent and 13.0% on the other — 1.99% of all 5,629 runs. The rest is not defense. In 39.6% and 51.5% of failures the transcript never mentions the injected step at all; in 45.0% and 25.4% the agent references it and simply moves on to the coding task without committing either way. The agent did not decline. It was distracted.

This is the load-bearing methodological point, and it generalizes past skill files. Every agent-security evaluation reports an attack success rate and thereby implies a defense rate as its complement. That complement is only a defense rate if the failures are refusals. Here they are overwhelmingly attention failures, which means the residual is an artifact of how compelling the payload's framing was, not of a safety boundary — and a slightly better-framed payload converts it. A vendor reading "we resist 26% of these" as a security property is reading a distractibility statistic.

It fits, unhappily well, with what this map already holds. Model refusal adds little over framework guardrails (framework-guardrails-add-little-over-model-refusal); agents do not refuse a prohibited contribution (agents-do-not-refuse-a-prohibited-contribution); a model that holds the security knowledge installs the vulnerable pin anyway, 270 times out of 270 (no-configuration-refuses-a-vulnerable-version-pin); permission prompts fail open (permission-prompts-fail-open-under-fatigue). Each of those said the prompt layer is not a control surface. This says something sharper: the prompt layer is not even an observation surface. You cannot infer from an agent's behaviour that it evaluated a risk, because in 98% of these runs it never did.

One genuine defense does appear, and it is not a safety mechanism. 10.1% of one agent's failures decline the injected step because it is off-task — an initialization command unrelated to scaffolding the requested web app — a behaviour the other agent exhibits in 0 of 111 failures. Scope gating is invisible to a safety-only lens and it is the only category in the taxonomy that reflects a decision at all. It also explains the sharpest inter-agent split in the study: on exfiltration, the scope-gating agent drops to 38.5% exploitability while the other stays at 95.5%. Task-scope narrowing outperforms safety training on this surface, which is an argument for least-agency configuration (least-agency-blocks-an-agent-that-recruits-another-agent, restrict-the-tool-surface-to-cut-cost-not-capability) rather than for better refusals — and a reason to give an agent a narrow charter even when you trust it, since the charter does the work the alignment does not.

Operationally, for anyone running skills unattended. The screening point is before ingestion, because there is no later one — a skill file is merged straight into the context where it is already an effective instruction (screen-skill-files-before-they-enter-the-context, a-skill-description-acts-without-being-invoked, project-documentation-is-a-code-execution-attack-surface). Below that, the enforcement has to sit in the environment (contain-at-the-environment-layer-first, enforce-high-risk-constraints-below-the-prompt-layer) and the credentials outside the sandbox (keep-credentials-outside-the-agent-sandbox), because the agent will not be the thing that notices. And the authors' first recommendation is worth restating as written: shell execution and environment modification should require explicit approval, since a trust-by-default architecture with auto-approved actions is the precondition that makes every one of these payloads land.

Bounds. Two agents chosen because they are the industrial partner's corporate standard, not a market sample — Claude Code, Copilot and Cursor are named and untested. The configuration simulates delegated privileges with auto-approved actions, so this prices the trust-by-default setup rather than the product's most cautious one. Sandboxing means the measured event is usually declared intent to execute, with execution evidence reported separately. The three judgment-bearing categories rest on a single human annotator working from raw transcripts (labels released); only the no-acknowledgment class is deterministic.
