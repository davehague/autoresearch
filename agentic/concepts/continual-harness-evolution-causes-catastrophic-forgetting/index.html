A harness that improved at one task type can almost completely unlearn a prior one -- and the identified cause is a new submission gate, not the model forgetting anything

This map's sub-thread (1), does the search pay, has accumulated fourteen-plus consecutive arrivals without a compute-matched control, but every one of them evolves a harness against a single, fixed task type. This is the first to ask what a harness search optimizes for once the task type changes mid-lifecycle, and the answer sharpens rather than resolves the standing contest: a harness evolution method that demonstrably works single-task (AHE and Meta-Harness both post real single-dataset gains here, consistent with this map's existing positive evidence) is not thereby accumulating durable capability — continuing to evolve it on a second task type can erase nearly all of what it gained on the first. The mechanism identification is the valuable part: this is not vague "catastrophic forgetting happens" hand-waving, it is a named, isolated, ablated cause — a harness that evolves a new submission-gating rule tailored to dataset B's evidence requirements (e.g., "accept only a test-only patch") silently breaks dataset A's requirements (which needed a source-code fix) at the point of submission, not at the point of reasoning. Introducing that one conflict type alone, holding everything else about the best SWE-evolved harness fixed, drops SWE-Bench performance from 96.0% to 0.0% — the single largest lever in the paper, and a workflow-rewrite conflict (changing the harness's own problem-solving procedure) is the second-largest at roughly a third of the gain lost. This gives the map's missing-compute-matched-control objection a sharper, more actionable form for any team actually deploying a self-evolving harness across more than one recurring task type: the relevant comparator for "does the search pay" is not only "versus not evolving" but "versus evolving while retaining what the harness already does well elsewhere," and this source's evidence is that neither tested method does the latter without an explicit mechanism to prevent it.

[T1, strong; single foundation model and single starting harness, both self-evolution methods reimplemented from their papers' descriptions rather than run on the authors' own code, small per-dataset evolution pools (50/50/30 instances), conflict-type attribution is a manual qualitative-to-quantitative coding by the paper's own authors rather than independently audited, task-relatedness explanation argued from the same three datasets used throughout]
