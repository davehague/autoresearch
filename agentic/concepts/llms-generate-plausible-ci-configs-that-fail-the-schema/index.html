A config that parses is not a config the service will accept

This map has tracked what happens when agents touch CI/CD configuration in the wild — frequency, merge rates, build success on real pull requests (ci-cd-for-agents's AIDev-derived measurements). Doc2CI asks the upstream capability question directly, in a controlled setting rather than an observational one: given a prose description of what a pipeline step should do, can an LLM write the YAML that actually implements it, correctly, against the service's schema?

The gap between "looks right" and "is right" is the whole finding. 97.1% of generated configs parse as valid YAML — a low bar, easily cleared. Only 70.8% satisfy the service's own JSON schema, and essentially none (never above 3.1%) reproduce the documented reference exactly. That gap is not a model-scale story: the best cosine-similarity models (GPT-4.1, GPT-4o, two Qwen2.5-Coder variants) do not separate cleanly on schema compliance, which means bigger or more capable models are not simply solving this by being generally better — the failure mode is specific to structural/schema correctness rather than semantic understanding of the described task.

Two operational levers, and they point in opposite directions, which is the part worth carrying into practice. Schema-guided repair — deterministically re-prompting with the validator's own error message, no fine-tuning, no extra training data — recovers most of the gap (81.0% → 93.7% schema validity, zero regressions, on one representative model). Fine-tuning on the target distribution alone makes schema correctness worse (81.0% → 56.7%), even as it makes the output look more like the training examples (cosine and exact-match both rise). The mechanism reads as classic overfitting-to-surface-form: the fine-tuned model has learned what these configs tend to look like at the cost of the structural constraints that make them valid. Only stacking both — fine-tune for style, then repair against the schema — recovers both axes at once.

For this map, the actionable instruction is the same shape as several already-held claims about validation loops: do not trust a generated CI config on the strength of it parsing, and do not expect fine-tuning alone to buy structural correctness — put a deterministic schema/validator check in the loop and let the model repair against the check's own error message, which costs nothing extra in training and closed most of the gap in one round here. [T1 — single author; evaluation runs against each service's declarative JSON schema rather than the live CI validator, which assumes complete standalone files; a single zero-shot prompt template applied uniformly across models; four services, English-only documentation; open coding of failure categories on a 385-item sample rather than the full population]
