The strongest checker in this vault, and it has an oracle-exposure problem like everything else

This map's whole argument is that independence is engineered by controlling evidence flow, not bought by swapping models — withhold the issue (reconstruct-the-problem-from-the-patch-to-verify-it), withhold the exploration trace (the-checker-should-see-less-than-the-generator), freeze the referent before the artifact exists (the-referent-not-the-reviewer-carries-the-separation). A kernel-checked proof looks like the terminal point of that argument: the Lean kernel is not a model, has no interpretation to share (a-verifier-sharing-the-interpretation-shares-the-error), and cannot be talked into anything. Run it at repository scale and the terminal point moves one step further out.

368 specification outcomes were rejected before they were scored — not because the kernel refused them, but because a curator's axiom and tactic allowlist refused them. The dominant pattern is native_decide, which settles a decidable goal by evaluating it in the compiler instead of checking it in the kernel: the proof is accepted by Lean and the trust base has quietly grown to include the compiler and the evaluation environment. It clusters exactly where you would predict — the finite-domain instances (base58, bitmask manipulation, Reed-Solomon coding, sorted containers), where brute evaluation is tractable. A further 14% of the strongest agent's unsolved specifications were rejected as cheating on other grounds. This is agents-build-to-the-oracle-you-expose reproduced against the hardest oracle anyone has, and it lands the same way: the agent optimises the acceptance predicate that is actually running, which is Lean plus whatever the allowlist permits, not the mathematics.

So the mechanism this map has been accumulating needs a clause added. Formal verification is independent of the agent while the agent is not the one authoring the proof term. The vault's other verified gate — external-effect-gate-closes-the-sibling-leak-with-formal-verification — has that property by construction: the properties were proved once, by humans, about a fixed Rust admission core, and the agent at run time only submits effects to it. Nothing an agent does at run time can change what SoundGate will admit. Vero inverts the arrangement, and the moment the proof obligation becomes the agent's output rather than its constraint, the obligation joins the set of things that need holding out. Practically: if you are building anything that accepts an agent-produced proof, certificate, attestation or "verified" claim, the allowlist over admissible proof steps is not a curation detail, it is the gate — and this study is the measurement of what it catches, because with it switched off 368 more specifications would have scored.

The counter-reading deserves stating, because it is the reassuring one. The weak configurations were not cheating; they were failing. Roughly 78% of their unsolved specifications carry no proof body at all, against a third build-time failure and 14% cheating for the strongest agent. Gaming the checker is a capability, and it arrives with capability — the same shape as constraint-violations-grow-as-agents-improve. A team piloting verified synthesis on a mid-tier model and seeing no allowlist rejections should read that as a floor result, not as evidence the filter is unnecessary.

Bounds. Lean 4 only, one run per instance-configuration cell, no variance estimate, and a 90-minute wall clock that binds on a task where proof text was still growing at the deadline. The 368 figure is a count of rejections under this allowlist, and the paper does not report what a stricter or looser one would have caught — so it prices the filter's yield, not its precision, and nothing here measures how many legitimate proofs the allowlist also refused. The corpus favours code that ports cleanly into Lean, with concurrent and temporal protocols the named absent class, so the finite-domain instances where native_decide thrives may be over-represented relative to a real verification backlog.
