Both arms find the same fix. Only one of them declines to ship the one that breaks everything else.

This map's standing contest is whether a search over harness configurations beats spending the same budget on the agent. This is the strongest constructive result it has, and the reason it is worth more than its headline is that the ablation isolates which part of the search is doing the work — and it is not the searching.

The headline first, because the splits are what make it readable: +9.0 / +9.6 / +10.0 pp over base harnesses on three benchmarks, with training, development and test sets drawn from disjoint task groups (on the software benchmark, optimize on one repository, validate on two others, test on three more). It beats the strongest automated baseline in every cell, and on one benchmark it beats the hand-tuned expert harness by +2.5 pp — one cell, SD 2.5, so read that as "reached parity with expert tuning," not as a general result.

Then the ablation, which is the finding. Remove generalization-aware selection — the reflection session plus dev-set evaluation, leaving optimization to rely only on training-set outcomes — and test Pass@1 falls 62.0 → 50.6, below every automated baseline and below the manual base harness's own margin. That is by far the largest component drop (diagnosis costs 4.2, structured patching 5.1). Finer ablations locate it further: dev-set filtering alone is worth 10.7 points, and removing reflection on top costs another 5.1.

The decomposition is what makes it a claim about mechanism rather than about a number. Split dev-set performance into a fix rate (success on scenarios the base harness failed) and a regression rate (failure on scenarios it passed). Both arms achieve similar fix rates. The gap is not the ability to discover improvements. It is that the filtered arm's regression rate trends −0.24 pp/iter while the unfiltered arm's trends +0.16 pp/iter.

And the failure has a face, which is the detail worth keeping. At iteration 20 the unfiltered arm adds a new tool and rewires the hook on a widely used one to forcibly redirect to it. With nothing assessing collateral damage, the patch is retained and the regression rate spikes 8% → 22% across unrelated scenarios. The same patch shape — an over-scoped hook on a high-frequency tool acting beyond its intended scope — appears in the filtered arm at iteration 4, and is blocked. The search proposes the same dangerous edit either way. The difference is entirely in what gets refused.

This sharpens what harness-self-evolution-is-capped-by-its-proxy-judge and harness-optimizers-fabricate-failures-to-fix have been saying about the selecting signal. Those describe the selector going wrong. This one measures what a correct selector is worth and finds it is the whole intervention — the generator half of a harness optimizer is nearly free without it, and the discipline is the product. The general shape: in a system that proposes and selects, credit the selector.

Two arms that make the harness look like a portable artifact rather than a fitting. Optimization on a different training universe still yields +5.9 pp, and an independent rerun reaches 58.6% — so the result is not one lucky search. More importantly, a harness optimized under Opus 4.6 keeps +5.6 pp when the task agent's model is swapped to Haiku 4.5. The harness term transfers across a model boundary, which is the constructive counterpart to this vault's confound argument: if the apparatus term were pure per-model fitting, it would not survive the swap.

Efficiency is a secondary but real result: best dev score after 147 rollouts against ~1,400 for the strongest automated baseline, roughly 10×, because selective evaluation avoids spending rollouts on patches the filter would reject anyway.

Bounds. Three benchmarks, one optimizer model, single evolution runs (three test repeats). "Generalization" here is cross-repository within a benchmark — the dev set filtering the patches comes from the same corpus family as the test set, so nothing establishes that an optimized harness survives a change of task distribution. The cross-model transfer arm runs one direction (stronger optimizer → weaker executor) on one benchmark. Optimizer-side monetary cost is higher per patch and reported in an appendix rather than beside the gains.
