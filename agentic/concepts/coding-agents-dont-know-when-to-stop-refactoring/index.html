Coding agents don't fail to stop because they can't produce clean code — they fail because nothing in the loop recognizes "done," and the failure is universal, not model-specific

This map's sub-thread (2), the within-agent repair loop, already carries the lesson that an unvalidated loop is negative-value and that the exit decision — not the repair step — is where the loop earns or loses its budget. This source supplies a clean, deliberately isolated test of exactly that exit decision, stripped of any repair-quality confound: the task (iterative refactoring with no fixed target) has no natural stopping point a test suite can check, so any edit made after the code is already optimized is, by construction, over-compliance rather than improvement. Across two harnesses, five models, and 3,000+ turns, not one model ever stopped once it reached that optimized state — some rewrote the codebase up to 31x its original size before first stopping, and some explicitly declared the task complete and then resumed editing anyway.

Why this sharpens rather than duplicates the map's existing termination finding: the earlier arrival on this sub-thread found a validated loop stopping on the sign of the marginal gain beats stopping on votes; this source shows the harder, prior problem — in an unbounded task with no explicit verifier checking for "already optimal," nothing in any of the tested harnesses even attempts to recognize that state, so there is no marginal-gain signal to stop on in the first place. The failure mode here is upstream of validation quality: it's the absence of a termination criterion, not a flaw in how one is checked.

Interaction — spec-driven-development: an unbounded refactoring prompt is exactly the shape of task this map's "hold the contract outside the agent" argument is built for — a scope boundary stated once and re-presented at the decision point ("is this task still in scope") is a direct candidate fix for over-compliance, and nobody has tested it against this paper's six signals.

Interaction — agentic-code-review: every point past the optimum that an over-compliant agent keeps editing is additional churn a reviewer (human or agent) has to triage, directly feeding this map's review-capacity-and-throughput sub-thread with a concrete upstream cause rather than an assumed one.

Bounds: the task is deliberately unbounded, which is what makes it diagnostic but also means the universal-failure finding may not transfer to bounded tasks with an explicit pass/fail gate; two harnesses and five models is broad but not exhaustive; no human-developer baseline is reported for the same open-ended prompt.
