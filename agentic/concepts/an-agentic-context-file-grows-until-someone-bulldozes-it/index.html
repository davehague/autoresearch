The context file is a ratchet, and the median one is already past the size where instructions stop working

This vault has priced context files from several directions and never priced their trajectory. agents-md-is-a-map-not-a-manual says what belongs in one. generic-context-files-do-not-move-correctness and generated-context-files-cost-more-than-they-help say a bad one costs more than it returns. a-standing-policy-decays-into-one-more-retrieved-source and a-loaded-skill-is-not-a-retained-requirement say a good one loses force during the run. All four ask what the file contains at a moment. This asks what happens to it over 299,440 commits, and the answer is that it only goes one way.

The measurement that makes this new is the unit. File-level studies already reported that these files grow; a line diff cannot tell a deletion from a rewording, which is why "deletions are rare" has stood unexplained. This work re-derives every version of every file by walking commit history forward (anchoring on the final version and searching backwards would condition on survival, which is the quantity under study), segments each version into clause-level imperatives, and matches instructions across versions with a three-stage cascade validated at 1.000 precision / 0.933 recall on 50 hand-annotated transitions. That gives 247,694 individual instruction lifetimes rather than a size curve.

The numbers a practitioner should carry. Count more than triples over a file's lifetime (+226%) while mean instruction length moves only +10% — so this is accumulation of rules, not elaboration of existing ones. The median file ends at 39 instructions, the 90th percentile at 131. That matters because instruction-following is independently known to degrade as the constraint set grows (FollowBench, WildIFEval), so the median repository is running its agents on a prompt already inside the degradation regime. Net +4.9 instructions per commit, and only about a quarter of repositories ever shrink theirs.

The shape of the only deletion that happens. 77.3% of instruction deaths arrive in a commit that halves the file or migrates it wholesale — replacing rather than pruning. Removing one instruction needs a reason; removing all of them needs none. And the rewrite does not fix anything: aligned on their first bulldozing, files drop to 59.5% and are back to 91.5% within ten commits, growing faster afterwards (4.9%/commit vs 4.1%). Growth after later rewrites is faster still, so the ratchet is not self-limiting.

The consequence for anyone maintaining a fleet is that a context file has no steady state you can inherit. It has a slope, and unless something changes the slope you are choosing between a prompt that degrades instruction-following and a periodic rewrite that discards working rules along with dead ones. The mechanism behind the slope is deletion-hazard-falls-because-the-rationale-decayed; the intervention is write-the-rationale-beside-the-instruction.

Bounds worth stating. The rewrite threshold (50% of live instructions dying in one commit, floor of 5 at risk) and the migration rule together censor 77.3% of deaths, so the hazard in the companion note is fit on a minority of them and rewrite deaths outnumber fitted deletions 3.4 to 1 — the authors name this as their largest single exposure. The per-corpus segmentation grammar is the largest untested degree of freedom: a different grammar yields a different absolute count, though the reported ratios survive a constant rescaling. English-language files on public GitHub only. Nothing here measures whether the growth causes worse agent outcomes in those repositories — the degradation claim is imported from the instruction-following literature, not measured on this corpus.
