The loop's licence has always been the verifier; here is an instrument that measures one

This map's rule for repair loops has been the same since 2026-07-22: an unvalidated loop is negative value, so measure your verifier's discrimination before granting the loop a budget (repair-loops-have-an-interior-optimum, stop-on-the-sign-of-the-marginal-gain). The map has since accumulated three arrivals establishing the pathology and none supplying an affordable measurement — the closest, verifier-catch-and-false-alarm-rates-are-measurable, instrumented a production gate with a gold label available. This measures the verifier's inputs without labels, cheaply, from execution behaviour.

The construction is the interesting part and it is not a model call. A schema is extracted from the problem statement once, then rule-based generation instantiates ~300 valid inputs per schema in dependency order. Ten candidate reference programs — deliberately brute-force, because brute force is easier for a model to get right when efficiency does not matter — are executed across all of them, producing a ~10 × 300 output matrix. Raw outputs are projected to a binary agreement indicator against the per-input plurality, which is what makes the annotation space small enough for a Dawid–Skene EM estimator to fit per-code error rates. The projection explicitly does not assume the majority is correct: each input carries a latent consistency state, and reliable behaviour can be on the minority side when several candidates share a systematic mistake. Only the highest-scoring candidate above 0.95 is used to build tests; if none clears it, no generated reference tests enter the loop at all and self-correction proceeds on public tests only.

The measured payload is the pathology this map named, reduced eightfold. The metric to read is not Pass@1 but the count of problems where the pipeline generates correction feedback on already-correct code: 113.2 → 14.0 under GPT-5.2, 81.2 → 11.6, 50.4 → 7.4, 30.0 → 1.2 across the four models. That is the same quantity as 55% of correct plans repaired into incorrect ones, attacked at the input rather than at the stop rule — where stop-on-the-sign-of-the-marginal-gain stops the loop before it destroys value, this stops the loop from being told there is value to recover. Consistent with that framing, ExeCRE shows no early-round Pass@1 degradation on either model tested iteratively, where one baseline sits below its own base for the whole run.

Two comparisons matter more than the headline. LLM judges are precise and blind: CodeJudge, LLM-analyze and direct LLM-judge score 92–94% precision at 45–47% recall, F1 60–63 — the same profile as a-verifier-sharing-the-interpretation-shares-the-error, which was 8-of-9 precise and 8-of-76 sensitive. Execution consistency reaches F1 76.62 by recovering recall (68.75) at 86.52 precision, and it does so without the model judging its own work at all. And the estimator beats naive execution voting (70.83), so the gain is specifically from modelling per-candidate error tendencies rather than from counting agreement.

Bounds. Competitive programming problems with clean input schemas, not repository tasks — the authors name repository-level extension as future work, and its blocker is input generation plus the cost of repeatedly executing candidate programs. Reliability at 0.95 falls back on 48.55% of problems, so on roughly half the corpus the method's contribution is declining to supply a signal, which is a real contribution but a different one from supplying a good one. Contamination is uncontrolled for two of four models (GPT-5.2's cutoff postdates the whole evaluation window, DeepSeek-V3.2's is undisclosed); the two cutoff-clean models show the same direction at smaller magnitudes. Dawid–Skene assumes conditional independence and the candidates come from one model, so shared bugs are a live threat — measured in agreement-among-wrong-programs-defeats-majority-voting and bounded rather than eliminated. Schema extraction itself succeeds 81.3–96.7% depending on the generating model.
