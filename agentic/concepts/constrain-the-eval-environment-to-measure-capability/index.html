Constrain the eval environment to measure capability

Two deterministic controls, both environment-layer, neither model-layer:

  • History isolation — remove the .git directory and reinitialize the repository as a fresh single-commit repo; restore the original history only at scoring time.
  • Egress proxying — deny network access by default; a pinned proxy allows dependency resolution against an allow-list of package registries.

Cursor's stated rule for practitioners: "decide what behavior they want to measure, design the harness around that, and make the setup clear when they report results." Report the harness with the number, or the number means nothing.

The transferable insight is that evaluation integrity is an infrastructure problem, solved with the same primitives as runtime containment. Default-deny egress and filesystem isolation appear here as measurement controls and in contain-at-the-environment-layer-first as safety controls — the same mechanisms, because both are answers to the same question: what could this agent reach? An organization that has built a containment sandbox for production agents has already built most of a trustworthy eval harness, and vice versa.

Second-order: this makes audit the trajectory a measurement practice, not only a debugging one — the aggregate score cannot show you that 57% of runs went to the public web, only the transcripts can. That is audit-agent-claims-against-trajectory-evidence and grade-process-defects-not-just-outcomes applied to benchmarking.

Caveat: suggestive rather than strong — the controls are described and their effect on scores is measured, but no one has shown the constrained score is itself an unbiased estimate of capability (a strict harness could under-credit legitimate documentation lookup). The right baseline is unknown.
