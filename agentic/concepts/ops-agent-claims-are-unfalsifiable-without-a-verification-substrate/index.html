Coding agents get a free falsifiability instrument (the test suite); operations agents don't, and most of the ops-agent literature has never noticed the gap

This map has repeatedly asked what an unattended fleet needs when nobody is watching — durable state, an operator surface, credential governance. This source names a prerequisite underneath all of those: a way to know, cheaply and repeatedly, whether an autonomous ops agent actually helped, which operations does not have the way coding does. A code agent's "did it work" question resolves against a test suite — fast, falsifiable, ground truth. An ops agent's "did it work" question resolves against an observational report with no agent-disabled baseline, no pre-registered decision matrix, and samples too small for the scoring system's own noise floor. The paper's claim is that this is not a minor methodological gap but the reason most published autonomous-ops results are currently unfalsifiable in the strict sense — nobody could have shown them wrong even if they were.

agent-breakage supplies the missing instrument: inject faults into a real Kubernetes cluster, score the agent's response against ground truth on four axes, distinguish framework error (the harness broke) from reasoning error (the agent's call was wrong given working tools), and enforce a pre-registered decision matrix with a genuine off-condition control (a deterministic-embedder mechanism that removes retrieval's contribution without changing anything else about execution).

The methodological payload is sharper than the substantive result: run as a case study on whether retrieval over past postmortems compounds agent capability, the framework's own instrumentation caught three confounds mid-experiment that a less-instrumented version of the identical study would have shipped as findings — a pgvector index bug (silently degrading retrieval into what looks like a null), a +19% selection-bias artifact (inflating the apparent effect), and small-sample estimates overstating effects by roughly 3x. After correcting for all three, the substantive retrieval-compounding question resolves to a partial falsification: 1 of 3 dense-corpus scenarios clears p<0.05, pooled effect +3.9pp, not significant at n=60 — directionally positive, underpowered, and a genuinely open question rather than a clean yes or no. A secondary result narrows why: a 360-run corpus-density sweep finds mechanistic alignment of near-neighbor postmortems, not raw corpus size, is what predicts whether retrieval helps at all.

For this map, the standing question moves from "what does an unattended fleet need" to a prerequisite one level down: without an ops-domain equivalent of the test suite, how would this map know if any future autonomous-ops claim it ingests is real? This source is the first candidate answer, not yet adopted or replicated elsewhere.

Bounds

Single research group, one substantive case study (postmortem retrieval) used to demonstrate a general framework rather than settle that specific question; the K8s-fault-injection domain is one operations surface among several this map cares about (CI/CD triage, incident response, cloud cost management), and the framework's applicability beyond Kubernetes is asserted by analogy rather than tested. Carried as open-question because the paper's own headline result is an honest partial null, not a finding to extend the map's belief on — the framework itself, and the confound-catching methodology, is the part worth carrying forward.
