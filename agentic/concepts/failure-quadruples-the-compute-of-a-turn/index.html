The recovery loop is 9% of turns and four times the median compute

This map's standing position is that the loop, not the model, is where reliability is won or lost, and its sharpest results are about repair loops that keep spending past the point of return (repair-loops-have-an-interior-optimum, stop-on-the-sign-of-the-marginal-gain, failed-recoveries-burn-compute-not-terminate). Those are benchmark measurements on hundreds of tasks. This is the same phenomenon in a population of 95.1 million turns, and it has a size: 9.1% of turns are the failure-recovery archetype, and they run 36 LLM calls against a median of 3 and 34 tool batches, each call carrying 80K+ tokens of accumulated error output.

The mechanism the authors name is the one this vault keeps arriving at from the other direction: "in chat, a failed request simply returns an error, but in an agentic loop, a failure triggers an autonomous recovery attempt that can cascade into dozens of additional LLM calls with growing context windows." Failure is not a terminal state in a loop; it is an input.

The tool reliability profile is the actionable half. Failures are not uniformly distributed over the tool surface, and the tools that fail are the ones that punish failure hardest:

  • Read and search tools (get_file, code_search) complete in tens of milliseconds and succeed near 100% of the time.
  • Execution and mutation tools (run_command, run_build, edit_file) drop to roughly 73%.
  • Across nearly every tool, the failure-duration distribution sits above and wider than the success distribution; for run_cmd_in_terminal a failed invocation takes 48× longer at P95.
  • A failed run_build injects 7–8× more tokens at the median than a successful one — compilers emit verbose diagnostics — so the failing call is both slower and more context-expensive, taxing the loop twice. (run_tests inverts this: success reports richer output.)

Put together: the expensive turns are expensive because a slow, verbose failure in a low-reliability tool feeds a growing window into more calls. That composes with context-is-a-finite-decaying-resource and with the compaction economics in compaction-is-a-serving-event-not-a-context-tactic — the failure loop is a major producer of the context pressure that triggers compaction, and compaction then costs the cache.

Two engineering reads, both cheap. Tool reliability is a serving-cost lever, not just a correctness lever — the authors state it directly ("tool reliability and LLM verification are a key determinant of serving efficiency"), and a build wrapper that truncates diagnostics is a token intervention as much as a readability one. And the archetype is detectable early: 36 calls against a median of 3 is a signal any harness can act on, which is where this map's stopping results attach (learn-when-to-stop-not-just-which-model, a-tiny-monitor-prices-a-doomed-trajectory) — with the caveat that this dataset carries no outcomes, so it cannot say what fraction of those 36-call turns eventually succeeded.

Bounds. One vendor, one product, one sampled week; telemetry only, no correctness labels, so "deep-loop with failures" is a compute signature and not a failed turn. Archetypes are clustered post hoc rather than defined a priori. The tool taxonomy and success rates are Copilot's tool surface. No intervals.
