The gate most of your fleet is actually running is the one you shipped as a default

This map's prescriptions have mostly addressed the person configuring the gate. This source, from an organization operating one at a scale where that person mostly does not exist, reports the inversion as its first lesson: most service owners never touched the bootstrapped default check, so it became the most common check in production, and investments that improved the defaults dominated in aggregate over investments that helped any individual owner write a better custom one. The authors say they underweighted this for too long.

For an agent fleet the translation is immediate and slightly uncomfortable. The interesting design work goes into the bespoke gate for the workflow you are currently thinking about; the gate that determines your actual failure rate is whatever every scheduled job inherited on the day it was scaffolded and nobody has looked at since. Which is the-project-rule-file-is-written-once-and-abandoned with the stakes moved from context quality to change safety.

The architectural decision that made a mandatory universal gate tractable is separable from Meta's scale. Metric templating decouples check authorship from deployment topology: the owner writes a query against metrics they care about, and the gate — in concert with the deployment system — decides which dimensions to bind and how to draw the control cohort. The authors call this, in retrospect, the single most consequential decision in the architecture, because it is what let the same check run across heterogeneous deployment systems without every owner learning the nuances of each. And it pays a second time on failure: because templating isolates the affected slice precisely, the system rolls back only what was rolling forward. Cheap rollback is a property of the targeting, not of the rollback machinery.

Accurate targeting is named as the single largest lever for detection latency, on a plain argument: the sooner a regression appears in a slice small enough to roll back cheaply, the lower the cost of catching it. That is a different optimization target from the one this map usually reaches for — not "catch more", but "catch it while it is still cheap to undo" — and it is the argument for isolate-and-merge-parallel-agent-work restated in deployment terms.

Three of the four automated improvements are worth naming because they require nothing of the owner. Severity-aware verdicts: a check failing by a hair on a small slice is not the same risk as one failing by an order of magnitude on a regional cohort, so expose how badly and how widely a threshold was breached and let downstream policy respond proportionally rather than treating every failure as equivalent. Dependency-aware checking: owners can only write checks against their own metrics, but the regressions that hurt most cross service boundaries — and a health check on an upstream rollout can mask a regression on a request path only exercised downstream — so mine cross-service correlations offline and evaluate a deploying service's critical dependencies' checks alongside its own. That is one-hop-dependency-inspection-misses-transitive-config-impact confirmed from the operations side. SLI-based gating: for the cases where symptom metrics are not a sufficient leading indicator, let an SLI regression alone halt a rollout.

And the drift finding is this map's own concern in another vocabulary. A check tuned correctly today is miscalibrated tomorrow because the service it protects changes daily — workload composition shifts, dependencies are added, a library starts emitting a new error class — while the owner's attention has moved on. The deployed population accumulates a long tail of checks that no longer measure what they were written to measure. Same failure as a-stale-convention-file-costs-more-than-no-file and harness-model-assumptions-go-stale, on a different artifact, with the same absence of a hygiene process.

The lesson the authors rate highest is the one that is hardest to fund: documentation, a chat channel and an office-hour rotation moved more checks from low to acceptable quality than several quarters of dashboard work, because they addressed owners not knowing what good looks like — which no dashboard fixes on its own. Noise is in part a sociological problem.

Bounds. An industrial experience report with no controls and no ablations: the defaults claim, the templating claim and the targeting claim are all stated as lessons drawn from operating experience rather than measured against alternatives. The incident-prevention claim is qualitative — "a significant number", "substantial avoided revenue loss" — with no count and no denominator, so it cannot be compared against anything. No numbers are given for the defaults finding (how many services, what share of checks). Single organization, single deployment substrate. And nothing here is about agents: SHC gates human- and pipeline-authored change, and every application to an agent fleet in this note is extrapolation.
