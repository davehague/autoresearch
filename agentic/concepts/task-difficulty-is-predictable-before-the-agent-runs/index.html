The difficulty is in the task before the agent touches it, and you can compute it for free

This map's accumulated position is that a benchmark number describes the evaluation at least as much as the agent — benchmarks-conflate-model-harness-and-penalize-alternatives, removing-defective-instances-reshuffles-the-leaderboard, benchmark-misalignment-concentrates-in-the-unresolved-tail, a-compressed-leaderboard-is-an-instrument-signal. Every one of those is a claim about the composition of a task set, argued without a way to characterise a task. This arrival supplies the missing instrument, and its most important property is that it needs no model.

What it buys. A calibrated per-task probability of agent success, computed from the gold patch, the repository and the issue text. AUC 0.863 with MCC 0.549 on 9,154 held-out tasks, stable under ten-fold CV, and the authors specifically check calibration because that is what the downstream uses require: predicted probabilities usable directly as continuous difficulty scores with no post-hoc adjustment. Linear models reach only 0.750, so the structure is genuinely non-linear and a simple heuristic ("count the files changed") will not substitute.

The three uses are the ones this map has been asking for.

  1. Benchmark auditing. Score every task in an existing suite and the difficulty distribution becomes visible. A benchmark heavy in compact single-hunk patches in shallow repositories systematically under-represents multi-site coordination and broad navigation — and, as the authors put it, that is invisible in an aggregate solve rate. This is the constructive counterpart to fix-the-eval-before-trusting-the-score and gold-smoke-an-execution-benchmark-before-you-trust-a-delta: those tell you to check the instrument, this tells you what to check.
  2. Difficulty-stratified reporting. An agent that improves mainly on tasks already easy for the reference agent is a categorically different result from one that improves on structurally hard ones, and an aggregate number cannot tell them apart. See report-the-delta-inside-a-difficulty-band.
  3. Calibrated reliance. Shifting the question from "how good is this agent" to "how good is this agent on tasks like this one" — which is the question a developer deciding whether to hand over a ticket is actually asking, and the one a-raw-benchmark-score-needs-its-adjudication-band gestures at from the scoring side.

The determinism is not a footnote. The nearest prior art — Item Response Theory augmented with LLM embeddings and LLM-as-judge rubric scores — needs model inference per task, which means the difficulty score inherits every reproducibility problem this vault documents about judges (validate-the-judge-before-you-trust-the-migration, llm-judges-have-exploitable-biases, report-judge-agreement-per-condition-not-per-panel). A difficulty score you can recompute byte-for-byte, forever, on a task you did not run, is a different kind of object. The authors position it as a cheap interpretable input to an IRT predictor rather than a competitor, which is the right framing.

The irreducible part is stated, not hidden. 49.8% of tasks pass on every trajectory and 32.5% on none, leaving 17.7% mixed — and no static task-level feature can predict the stochastic component of an agent sampled at nonzero temperature. That is why the regression ceiling sits near R² 0.41 rather than higher, and it is an independent measurement of the same quantity one-run-scores-an-implementation-not-an-idea and a-multi-agent-configuration-is-a-distribution-not-a-run are about: roughly a sixth of a benchmark is a coin whose bias you can estimate but whose outcome you cannot.

Bounds. One agent, one scaffold. Every trajectory is Qwen3-Coder-480B in OpenHands, and the authors state the consequence directly: the importance of repository scale and directory breadth implicitly reflects this agent's navigation strategy, and an agent with a different localisation approach may be less sensitive to them. The difficulty landscape is therefore a per-pair object until replicated, which is the extension the paper proposes rather than claims. Contamination is unaddressed — the model was pretrained on public code and the tasks come from public GitHub, so pretrained repositories may be solved at rates unrelated to structure, a mechanism benchmark-scores-inflate-when-agents-can-retrieve-the-fix already documents. Python-centric sample. Patch features are computed from the gold patch, which is a proxy for "what a correct solution looks like" and can diverge from what the agent must actually reason through. Outcomes are estimated from nonzero-temperature trajectories, so they conflate difficulty with sampling variance.
