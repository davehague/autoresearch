A third way to make a checker independent: freeze what it checks against

This map's core claim is that independence is engineered by controlling evidence flow, and its two founding results both do it by subtraction — RETRACE withholds the issue text (reconstruct-the-problem-from-the-patch-to-verify-it), OpenCodeReview withholds the agent's exploration (the-checker-should-see-less-than-the-generator). an-independent-checker-beats-the-same-model-checking-itself does it by model swap. This case does neither. The checker is a fresh session of the same agent, running the same model that wrote the code, and it is shown everything: the full codebase and the full specification.

What is controlled instead is the referent. The specification was written, audited fourteen times against the source, and frozen before a line of the implementation existed (converge-the-spec-against-the-code-before-freezing-it). At every one of the seventeen verification passes the checker compares the code to that same unchanged document. The author states the design against Anthropic's published guidance, which recommends a second agent with no memory of the change on the grounds that fresh context is less biased: here the reviewer's identity is not the control variable, the document's fixity is.

Why this belongs on this map rather than beside it. The map's operating principle is that a checker handed the objective can restate it, so agreement becomes echo — that is what vacuous-oversight-has-a-measurable-threshold prices. A frozen prior specification is immune to that failure by construction, from the other direction: it cannot have been shaped by the artifact, because it predates it. Contamination of the referent is impossible rather than merely unlikely. That is a different mechanism from information restriction and it composes with it — nothing stops a restricted checker from also using a frozen referent.

It also speaks directly to this map's second open question — is the model boundary worth anything once the information boundary is in place? Here there is no model boundary at all, no information boundary either, and the check still did work: 116 architectural deviations found and corrected across seventeen passes. That is one uncontrolled cell of the 2×2 nobody has run, and it is the cell the map predicted would be weakest.

Bounds. n = 1, self-reported, no control arm — nobody ran the same protocol with a different-model checker, or with a specification that was allowed to drift, so "the referent carries it" is the author's attribution and not a measured contrast. Critically, the false-rejection side is entirely unmeasured: 116 corrections were applied on the checker's say-so with no accounting of how many were spurious, and this map's standing complaint is that nobody prices what a gate wrongly blocks (an-smt-gate-buys-interception-with-a-false-block-tax). The checker also has one advantage a code reviewer normally lacks and this case does not isolate — the specification was executable in the sense that matters, an explicit statement of intended units, relations and behaviour, which is close to what split-the-executable-spec-into-path-and-behavior makes mechanical. And the standing caution applies: a-verifier-sharing-the-interpretation-shares-the-error shows a checker with an external anchor still missing nine value errors in ten, and a specification written by the same agent that wrote the code is an anchor shared with the generator in exactly the way that result warns about.

Rebutted by: stop-when-two-audits-against-a-frozen-referent-come-back-empty — same case, the other half of it, and it is the half that carries the risk: a checker whose independence comes from a frozen referent still ran seventeen rounds and applied 116 corrections with no accounting of how many were spurious, which is where a loop against a noisy verifier is known to do its damage. Read the two together or the design looks safer than it has been shown to be.
