The diagnosis is a hypothesis; the file is the evidence

Strip away the pipeline and this paper contains one durable mechanism, and it is an ablation rather than a headline. Deciding whether a context source needs new content or corrected content cannot be done from the conversation. A knowledge-base entry that is absent and one that is wrong produce the same observable — the user corrects the agent. Reasoning about which it was, from the trace, is 33% accurate. Having the fixing agent open the file, search for the authoritative source that should govern it, and compare, is 83%.

That is a 50-point swing bought by a read call, and it generalizes past this system's architecture. It is the same shape as source-code-access-lifts-root-cause-analysis-the-agents-underuse-it one layer out: an agent asked to explain a failure will produce a fluent account from the evidence in front of it and will not go get the evidence that would settle it unless the loop makes it. Here the loop makes it, by structuring the fixer as a verifier of a hypothesis rather than a consumer of a conclusion — the attributor's output is explicitly treated as something to confirm, refine, expand, or override.

The division of labour is the transferable design. The attributor reads only the trajectory — chain-of-thought, tool calls, tool outputs — and never opens the raw context files, because what it is good at is localization: the agent's own reasoning names its sources ("According to the KB…", "Following the SOP for…"), so the trace alone can point at the right node 72.7% of the time. The fine-grained question of what kind of fault it is gets pushed downstream to the stage that has file access. Splitting those two questions by which evidence answers them is what lets the pipeline recover from its own attribution errors 67% of the time and post a higher end-to-end number (82%) than its attribution number.

For this map the connection is to the maintenance problem it keeps naming and not solving. Context files rot (an-agentic-context-file-grows-until-someone-bulldozes-it), generic ones do not help (generic-context-files-do-not-move-correctness), and the project rule file is written once and abandoned (the-project-rule-file-is-written-once-and-abandoned). What none of that says is who edits it, on what signal. This proposes the signal — implicit dissatisfaction already sitting unread in production trajectories — and, more usefully, the discipline for acting on it: never edit a context file from a diagnosis, only from a diagnosis plus a reading of the file.

Bounds, and they are heavy. Every number here comes from traces the authors generated, containing faults the authors injected, scored against ground truth the authors annotated — the pipeline is measured against its own simulator, so 82% "end-to-end fix effectiveness" describes that generator's fault distribution and not a deployed system. n=60 with bootstrap intervals over 20 points wide; no seeds, no repeated runs, no model named at any stage. The human-approval gate is in the architecture and never measured, so nothing reports how often a reviewer rejected a recommendation — which is the number that would say whether this is safe to run. The 33%→83% ablation is the one result whose direction does not depend on the simulator being realistic, which is why it is the claim carried here rather than the pipeline accuracies.
