Context retrieval & acquisition — map

Forked from context-engineering on 2026-08-02 (bounded auto-fork; the parent was at 51 dated bullets with three declared sub-threads). The parent governs material the agent already holds — persist the contract, deliver it, re-deliver it at the decision it governs, price the resident half, re-derive state from its source. This map governs the stage before that: finding the material, choosing what enters the window, and structuring the corpus so the choosing is possible. The split is a pipeline boundary, not a topical convenience — the parent's five-clause rule assumes the right material arrived, and every finding here is about that assumption failing. Eight claims and nine dated arrivals moved across intact; nothing was rewritten in the move.

What we believe now:

  • Build the dependency graph on demand, per query, rather than once for the whole repository — a hallucination-filtered LLM trace (pick entry points, then select/visit/expand outward) beats retrieving against a fully materialized static graph on Pass@1, at a fraction of the total wall-clock cost. (Added 2026-08-30, T1 — strong.) CoderEval: 49.48% vs 42.96% (+15.2% relative) against the strongest static-graph baseline; DevEval: 46.88% vs 43.06% (+8.9%), with larger relative margins against weaker RAG baselines (+59.73% / +98.6% / +71.5%). 7.4× faster end-to-end than the static-graph baseline (10.2× faster indexing, because there is no whole-repository graph to build up front) at 1.95–2.43× the per-query token cost. Ablation: removing the dynamic-graph mechanism costs far more (-16.0% / -51.1% relative) than removing multi-hop depth (-6.0% / -9.6%) — the load-bearing choice is querying-conditioned construction itself, not how deep the trace walks once it's built that way (a-dynamic-per-query-dependency-graph-beats-a-static-one). This is a different object from the graph the bullet below demotes. The 2026-08-25 finding is about whether a pre-existing dependency graph predicts an agent's next navigation step across a multi-turn SWE-bench trajectory — it doesn't, beyond a scoping prior. This result is about a graph built fresh for the query at hand, feeding single-function code generation (CoderEval, DevEval), not next-step prediction. Read together they narrow what "the dependency graph helps" can mean: static and reused, it scopes a region but doesn't route within it; dynamic and query-conditioned, it materializes exactly the edges one generation task needs and outperforms retrieving against the static version of the same idea.
  • The dependency graph tells you which region an agent is working in and nothing about which file it opens next; what predicts the next move is the agent's own last tool output. (Added 2026-08-25, T1 — strong.) On the 341 first-visit decision points — where visit history is empty by construction, so a predictor cannot score by restating the agent's past — a ranker reading only the most recent tool output reaches top-3 0.326 [0.276, 0.375] at 3.46 effective candidates, against 0.058 for a code dependency graph deliberately strengthened to seed multi-source proximity from the entire visited set (1,719 effective candidates) and 0.072 for repository frequency; 0.689 of first-visit targets had already appeared in an earlier tool output. The null is what makes it a finding rather than a correlation: against a within-episode permutation that preserves the visited multiset and destroys only order, one-hop lift is 0.94, three-hop 1.02, same-community 1.01 — the visited files really do cluster in the graph, and that clustering is exactly what a naive measurement would have called graph-driven navigation. The complementary half is equally load-bearing: the same graph separates the visited set from random same-size sets by 30.9× in internal edge density and ranks unseen gold files at a leakage-controlled quantile of 0.049. So: scope the corpus with structure, rank the next candidate with provenance (provenance-not-the-code-graph-predicts-the-next-move). Two operational corollaries, both keyed on strata observable before the prediction. Next-action prediction is trustworthy immediately after a search (top-3 0.469, ECE 0.013) and untrustworthy immediately after a read (0.160) — an eight-fold spread. And a small candidate set is not confidence: the lowest-entropy stratum is the worst calibrated (ECE 0.076), because a narrow candidate set usually means the answer is not in the set. The difficulty is also concentrated where a retrieval layer is least able to help — steps whose object is a novel free-text query (21.6% of all steps) are predicted at top-3 0.029, against 0.582 for handler steps. Bounded to file localization and to the 46.2% of agent objects that resolve to a graph node.
  • The surface an agent actually reads is the one agents wrote, and the genres documentation tooling targets are a rounding error — while adding correct, authoritative context on top of an already-adequate repository does not reliably help and reverses sign with the agent's own competence. (Added 2026-08-21, T1 ×2 — strong on the distribution, suggestive on the crossing.) Two arrivals hit the acquisition stage from opposite ends. Measured over 3,033 documentation interactions extracted from 557 real agentic sessions, 60.5% target agent-facing artefacts — instruction files at 35.4%, agent-authored working notes at 25.1% — against 1.3% for API references and 0.4% for troubleshooting guides, with documentation produced at 0.87× the rate it is consulted and AGENTS.md/CLAUDE.md among the most-changed files in agentic pull requests (the-documentation-agents-open-is-the-documentation-agents-wrote). The 60.5% is weighting-sensitive — under agent-reweighting the consultation half sits at 50.1% — so the load-bearing figures are the two small ones, which are stable under every weighting. Consultation is self-initiated 70.2% against 7.5% failure-driven, and documentation is the first recovery move in 5.4% of 2,034 failure episodes, so the artefact serves the agent making progress and not the agent that is stuck (documentation-consultation-is-self-initiated-not-failure-driven). At the other end, a paired ablation holding the repository snapshot, environment, entry points, hidden validators and the task-defining context fixed adds only the curated layer — rationales, upstream repairs, audit findings, paper excerpts, expert guidance — and finds Pass@1 moving 16.48% → 23.08% on the weaker configuration and 36.26% → 31.87% on the stronger, with the task-level overlap showing 8 tasks won and 12 lost for the stronger one rather than a shifted mean (supplied-domain-knowledge-helps-the-weak-agent-and-hurts-the-strong-one). Named mechanism: anchoring, scope spillover, premature reliance on a supplied explanation. Third arrival in this vault at the shape the value of injected context is conditional on the agent's own competence, and the conditioning can flip the sign — after a-skill-set-helps-the-weaker-harness-and-hurts-the-stronger and the-memory-layer-only-separates-on-a-capable-answerer. The operational rule the map now carries: A/B your context pipeline on the model you will serve, because a win on a cheaper one may be a loss on the frontier one.
  • The retrieval configuration you would rationally adopt — the one that raises recall@k — is the one that loses the repair, once the context budget is fixed and zero-sum. (Added 2026-08-18, T1, strong — the causal, execution-graded version of the clause below.) One production flag (one-chunk-per-file deduplication) toggled on an otherwise identical stack, SWE-bench Verified, 12-slot pack, single-shot with no tools, official Docker grading, empties counted as failures. Dedup-ON is the recall maximizer on the served packs, not just in the index eval (gold file present in 0.878 against 0.806). It resolves less: gpt-5.6-sol 39.2% → 46.8%, +7.6pp, McNemar exact p=0.0003, clustered CI [+0.8, +13.1], all twelve leave-one-repository-out folds positive; a pre-registered open-weights replication any reviewer can re-run gives +3.6pp (p=0.0133) and also survives clustering (the-recall-maximizing-packing-policy-loses-the-repair). The trade is ~12 files × one chunk against ~5 files × several chunks, and the gain is quality, not producibility — the correct-given-attempt channel carries 88–94% of it. Three alternatives are killed by design rather than by argument: a random-chunk control refutes argmax-selection bias (3.0% against dedup-ON's 6.6% against depth's 12.4%), a parse-apply-test funnel shows depth still wins among patches that applied, and a popularity stratification (ρ ≈ +0.12) finds no contamination dose-response. And the advantage grows with the budget rather than washing out: +4.80pp at K=4 to +9.20pp at K=40, difference-in-differences +4.40pp, CI [+2.65, +6.23]. The operational rule: at a tight fixed budget, do not hard-deduplicate by file, and A/B a packing policy against the task rather than against the metric the flag was tuned to.
  • The trap is a property of the regime, and the boundary map is worth more than the number. (Added 2026-08-18, T1, strong.) The same paper maps where its own effect stops, which is what makes it usable. It reverses on a lexical BM25 retriever (−3.2pp), with a significant cross-retriever interaction (+10.8pp, CI [+5.3, +16.4]) rather than a bare non-replication — and the mechanism co-varies: BM25's depth arm raises within-file gold-line coverage by only +0.029 against fusion's +0.089, so the quantity the effect tracks barely moves where the sign flips. It is not detected under unrestricted-Read agents (−1.4pp, p=0.45, a powered null at MDE 4.5pp), because the fixed budget stops binding once the agent can open any file — which excludes every tool-using coding agent from the positive finding. And the pre-registered multilingual test lands at +2.59pp, p=0.056, reported under the pre-committed branch as an honest boundary; its most informative cell is a null on SWE-PolyBench Python for the same model that gave +7.6pp on SWE-bench Verified Python, so language is not the moderator and whatever conditions the effect operates at the level of the instance pool (the-recall-trap-is-a-property-of-the-regime-not-of-retrieval). This map should carry the negative claim (a retrieval metric does not predict a repair) as increasingly well-supported, and every positive packing prescription as regime-bound.
  • Retrieval precision and task success are independent measurements, not consecutive stages: the share of accessed artifacts that were the annotated ground truth fell ninefold while the outcome held. (Added 2026-08-17, T1, strong — this map's first pushback, and it lands on the map's own inference rather than on its core claim.) Expose an entire skill library at execution time with no preselection, parse what the agent actually opened, and grow the pool from 5 to 100 candidates: actual-use precision 29.6% → 3.3% (one stack 16.9% → 0.7%, the other 42.3% → 5.9%) while downstream success goes 36.4% → 39.3% — flat for one stack, rising 35.4% → 42.0% for the other. Recall stays 54–74% against 0.7–8.1% precision, which says what is happening: the agent opens the right artifact along with several wrong ones and does not restrict itself to the label. It does not need to. Related-but-unlabelled procedure is still usable, and the labelled artifact is not always what unblocks the task — exact ground-truth invocation is neither sufficient nor necessary (skill-use-precision-collapses-while-success-does-not). This is proxy-metrics-rank-models-not-suites arriving at the acquisition layer, and it means this map has to stop treating a retrieval score as a leading indicator of a repair outcome, which is precisely what retrieval-benchmarks-omit-the-quality-axis was asking for on the assumption the answer would go the other way. What does degrade cleanly is offline identification, and it degrades on confusability rather than size: embedding top-1 precision 70.5% → 53.4% on semantically similar distractor pools against 97.7% → 84.1% on random ones, with explicit agent selection worse than embedding ranking throughout. So a real acquisition problem in a library looks like near-duplicates — the exact shape of the published skill population (the-skill-population-is-half-copies-with-no-registry). [T1 — one benchmark with ground-truth task–skill annotations, two agent–model pairings, one substituted for availability, so these are within-pairing comparisons not comparable with the study's other arms]
  • The delegated-subagent search design — isolate exploration in its own window, return a condensed result — now has the quality number it was always missing, and it goes the other way: on read-only questions over an indexable repository a flat agent over a vector index answered substantially more correctly, at less than half the cost per correct answer. (Added 2026-08-08, T1, strong.) The vault carried this design on efficiency evidence with quality asserted (delegate-search-to-a-specialist-loop) — the gap retrieval-benchmarks-omit-the-quality-axis named. Measured on SWE-QA (720 questions × 15 Python repositories × four models, paired within model, human-validated judge): 65.2% Pass for semantic retrieval against 46.2% for deep agentic search, with more outright Fails for every model, consistent in direction across all four and significant after FDR correction — honestly heterogeneous in size (Cliff's δ 0.137 / 0.138 / 0.760 / 0.235, large only for one model), and stable under a Pass-threshold sweep from 50 to 90 whose smallest gap anywhere is 3.8 pp. Semantic led on 14 of 15 repositories, all five quality dimensions and all four question types; the margin narrows with repository size (ρ = −0.69, p = 0.004) without crossing even at ~861 KLoC. The mechanism is a new failure class, not a redistribution of old ones. Coding every failed run on orthogonal mechanism/symptom axes: coordination breakdown at the planner-to-subagent hand-off is 41.8% of the delegating design's failures and 0% of the flat one's, and the association survives restriction to the five shared mechanisms (V = 0.35); symptom, by contrast, is only weakly architecture-associated (V = 0.16), so both designs produce similarly-shaped wrong answers by different routes. And it fails silently — coordination breakdown fans mostly to a confident answer about the wrong entity rather than to no answer, which is the-agents-final-report-is-its-least-reliable-artifact with a share attached: the condensed memo is a claim the planner adopts unverified (verify-a-handoffs-claims-before-the-next-agent-reads-them, subagent-delegation-adds-a-silent-handoff-failure-class). What this does and does not overturn: context rot is real and the design addresses it; what is refuted is that the protection is free. [T1 — read-only question answering, not code modification, over a corpus that can be indexed; framework-default harnesses (LangChain ReAct vs Deep Agents) rather than the tuned commercial implementations whose adoption motivates the study, so a vendor's hand-off contract may close the 41.8%; one benchmark, one language, 15 repositories, four models, one retrieval configuration; failure coding LLM-performed with a validated 400-failure human subsample]
  • The map's own open question is answered, and the answer is that the fix was never a better ranker: make the agent look before it may edit, and the resolve rate moves. (Added 2026-08-03, T1, strong.) As of the fork this map's closing complaint was that every source in it reports a token saving or a retrieval gain and none reports a resolve rate, so better context serving was a cost claim rather than a capability claim. An execution layer that compiles per-task evidence conditions from the issue and repository structure, then holds edits and submissions whose applicable conditions are unmet while letting reads and searches run free, raises Pass@1 by 4.8–11.8 points across two models and two scaffolds on all 500 SWE-bench Verified instances — GPT-5-mini 56.2→68.0 and MiniMax-M2.5 75.8→80.6 on mini-swe-agent v2, 40.4→50.8 and 74.8→79.8 on Codex CLI through its hooks, all p < 0.001 by exact McNemar — while token use falls 1.4–12.1% (gate-the-edit-on-evidence-observed-not-claimed). Retrieval is not improved at all. That is the point: this map's founding measurement is that agents with real search tools never touch any required file on 27–35% of tasks (context-acquisition-is-an-unmeasured-failure-surface) and that no retrieval family dominates (no-retrieval-family-wins-across-agentic-relevance-types) — and the operative gap turns out to be that nothing in the runtime required the agent to look. Two design details generalize beyond this system. Satisfaction is decided deterministically from recorded trajectory events, never from the model's claim to have investigated: an LLM proposes candidate conditions, but each is grounded against the AST, call graph and class hierarchy and dropped if it cannot be resolved to a checkable entity, so a bad specification can only lose coverage, never add an unevaluable check. And the structure is load-bearing — replacing the specification with an equivalent natural-language summary scores ten points below the full system and five points below supplying no guidance at all, the sharpest statement in this vault that identical content in identical context differs by whether its satisfaction can be mechanically decided. [T1 — one benchmark, one language, one task type; specification quality is bounded by issue quality and SWE-bench Verified issues are human-validated; mid-tier models by design and gains shrink as baselines strengthen; every regression comes from the audited fallback that releases an action after three holds, so the blocking variant is unmeasured; single run per configuration, no seed variance]
  • There is a selection stage after retrieval that nobody scores, and it loses more evidence than most of the interventions this map argues about gain. (Added 2026-08-01, T1, strong.) Between a ranked candidate list and the model input sits a renderer with its own implicit allocation policy. On 16,490 RepoBench tasks from 2,798 repositories, the required cross-file evidence enters the retriever's top five for 64.16% of tasks and survives complete inside a 4,096-token budget for only 39.59% — a 24.57-point loss located entirely after ranking (Java 26.37, Python 22.64). The mechanism is authority multiplication: a repository index exposes body, signature, call site and test fragment for one code object, each competes for a slot as a separate result, and the independent helper the task needed gets clipped. What makes this a distinct stage rather than a diversity problem is the row of controls that do not fix it — exact deduplication moves survival by 0.02 points, and canonical grouping, per-file quotas and MMR all reach ~64% candidate recall while leaving survival pinned between 39.41% and 39.59%. Quotienting views by canonical code object and then allocating tokens per object raises survival to 63.67% using 35.63% fewer tokens with the candidate set held fixed, cutting the loss to 0.49 points (retrieved-evidence-dies-again-at-the-rendering-budget). Two operational readings: deduplicate on provenance identity, not on text, and a bigger window is not the fix — survival saturates by 4K and 8K adds 0.01 points. [T1 — a fixed pre-method selection setting on completion-style tasks, not a live agent choosing its own searches; requires a provenance-tracking index, which grep-based retrieval does not have; two languages; downstream Pass@1 is one sample per task with no seed variance, and ties exactly with the strongest baseline on two of three backends]
  • Serve context from a maintained, addressable store and compact it deterministically — the token saving is large and it costs no localization. (Added 2026-07-30, T1, strong for the token result.) Materializing lexical, dense and structural views per commit, handing the agent ranked candidates that carry re-resolvable source addresses, and compacting with a one-time deterministic history rewrite rather than a summarization model cuts trajectory tokens 50–87% across five models while preserving AnswerRecall@5 within ε = 0.05 at a 95% confidence lower bound (selected-context-cuts-trajectory-tokens-at-equal-localization). It is the fifth clause as infrastructure, and its no-model compaction sidesteps the all-or-nothing summary boundary this map measured directly (compaction-selection-is-all-or-nothing). Two boundaries to keep attached: the static index reproduces a live language server on only 63% of navigation requests with no automatic fallback, so this supplements a semantic path rather than replacing it — and nothing here measures repair, so a cheaper, better-localized context is not yet shown to fix more bugs. [T1 — 7,500 trajectories, five models, only one from a frontier family; no resolve-rate arm]
  • Before any of that: the agent has to find the file, and on a quarter to a third of tasks it never does. (Added 2026-07-29, T1, strong for the miss rates.) This map has spent July arguing about what to persist and how to deliver it. The stage upstream of both — which repository files enter the model at all — turns out to be a measurable failure surface nobody reports. Against repositories frozen at the pre-resolution base commit (427 samples, 25 repositories, 391,932 files, with exact gold-path, raw-patch, fix-commit and generated-artifact leakage all at zero), logged trajectories from real agents with real search and read tools never touch any required file on 35.2% of samples for one strict-context agent and 27.2–29.3% for two Codex configurations (context-acquisition-is-an-unmeasured-failure-surface). The comforting median-first-hit-at-step-2 statistic is conditional on eventually hitting. This is the term the 2026-07-22 disclosure boundary left unmeasured: progressive disclosure buys context only once the corpus outgrows the harness's own search ability (progressive-disclosure-buys-context-not-intelligence), and that ability was never quantified. Two refinements ride along. A file-level hit is document reachability, not localization — median gold file 515 lines, median useful evidence 27 lines (4.7%), and every method's line F1 under 0.03, with the ranking changing at span granularity, the same read-the-proxy-at-the-right-granularity error as coverage (proxy-metrics-rank-models-not-suites). And no retrieval family dominates: semantic embeddings take MRR, a vectorless structural repo map takes budgeted context yield and causal trace-to-root-cause retrieval, a 0.5B model takes review-comment context, the aggregate ranking reverses when repositories rather than samples are weighted equally, and a training-free rank fusion of a semantic and a structural ranker beats both inputs (no-retrieval-family-wins-across-agentic-relevance-types). Retrieval and interaction are two failure surfaces, not one — static retrieval finds files the agent never touches on 12.5–17.8% of samples and interaction finds files the retriever misses on 7.7–22.0% — so installing a retriever does not close the second. [T1, strong for the trajectory miss rates and the file-versus-span gap, suggestive for the leaderboard, single-study for the 45-sample seed-intervention deltas — one trajectory per arm, and random non-gold context already helps by 0.0215 File F1]
  • Search is a context cost before it is a retrieval problem — and a specialist search loop is cheaper on both time and tokens than the coding agent searching for itself. (Added 2026-07-26, T2, single-study.) A vendor productizing exactly the term the map's 2026-07-22 boundary named: a narrow agent that runs its own search loop and returns file paths, line ranges and a one-line note beats the coding agent using local search by 2.19× on time, and beats the same agent calling the same MCP tools by 1.63× on cost. The stated mechanism is the map's own — "a general coding agent carries a large context window and a broad instruction set into every search" — and the pitch is turns and context window, i.e. the cost of searching badly, not finding what a grep loop cannot; so read it as evidence for progressive-disclosure-buys-context-not-intelligence's conditional, not against it. The detail to carry is the ordering inversion: local search is the slowest (2.19×) yet the cheaper of the two losers (1.32×), while the MCP-tools agent is nearly as fast (1.14×) and the most expensive (1.63×). A delegated call spends tokens to save turns; a grep loop spends turns to save tokens. Latency and token cost are not interchangeable proxies for retrieval efficiency, and a harness tuned on one picks a different winner than a harness tuned on the other (delegate-search-to-a-specialist-loop). [T2, single-study — vendor's own beta product; no task set, repo sizes, model, run count or intervals disclosed, and quality is asserted "comparable" with no number (retrieval-benchmarks-omit-the-quality-axis)]
  • Judge the scope before gathering, not after. Every other reduction technique in this map is reactive — prune, summarize, compact what was already pulled in. Estimating a task's required scope first, executing the minimum path, and expanding only on verification failure is a distinct and earlier lever, with a metric attached (redundancy ratio against an oracle minimum). Carried with its arms separated: −85% cost / −91% tokens at equal success in a deterministic simulator, but −18% tokens versus a read-everything agent on live gpt-4o over one library at case-study scale. The durable part is directional and holds in both arms — over-provisioned context costs reliability, not just tokens (the thorough agent lost 3/3 runs on the hardest tier where the scoped one held 93%). [T1, suggestive]
  • Retriever structure is a context lever, and it can be cost-negative. (Added 2026-07-21.) The map has held "retrieve just-in-time" as grep/glob-style tool calls or a lightweight table of contents. A within-harness ablation (Claude Opus 4.7, 91 instances, 3 seeds) shows the structure of the retriever matters: a structural codebase index — vector embeddings + a graph of definitions and call edges + BM25 lexical, built over live source — lifts localization acc@5 44.3% → 84.5% (p<0.0001) and resolve 41.9% → 50.4% (p=0.003) over index-off, and beats an agentic-grep baseline by +8.1 pp localization / +6.0 pp resolve (marginal, p≈0.08) at a lower dollar-per-solve ($2.30 vs $2.92) because it finds the site faster and wastes fewer turns. The payoff concentrates on multi-file changes, so the value is workload-dependent by the authors' own framing. It composes with the point-of-use-verification axis (verify-generated-context-against-live-source): a generated index over ground truth queried at retrieval time helps, where a generated artifact trusted blind (a lossy AGENTS.md, generated-context-files-cost-more-than-they-help) hurts — same machine-built context, opposite sign, set by whether it resolves to current source. [T1, suggestive]
  • Packaged retrieval structure buys context, not intelligence — its value is the gap between corpus size and the harness's own navigation ability. (Added 2026-07-22, the first controlled test of this map's founding instruction.) Three reading strategies over the same book-length text — raw navigation, a flat description-gated skill pack, a hierarchical one — across three harnesses × three model families. On a single document the pack lifts harnesses that navigate raw text poorly and adds nothing to one whose bare agent already greps for the entities a question names; at twenty documents that same agent can no longer find the right file and the pack pulls 1.7× ahead (En.QA 0.257 → 0.462), beating a hybrid BM25+dense+rerank retriever in nearly every cell. So the technique is not a universal accuracy lever — it is a scale lever, and it is redundant until the corpus outgrows native search. The economics agree: as the corpus grows the cost–accuracy frontier recedes down and to the right, so a larger corpus is strictly less efficient to read. This is the scale condition just-in-time-context-retrieval and structural-index-beats-grep-at-lower-cost both lacked, and the two agree in shape — retrieval structure pays where the search space is too big to read.   • One level of disclosure, and put the index where it is paid on activation, not always.   • 2026-07-19 — execution-scope-estimation-e3 (arXiv, "Do AI Agents Know When a Task Is Simple?", 2026-07-14, T1, suggestive): the map's context-reduction cluster is entirely reactive — prune, summarize, evict, compact, all operating on context already gathered (goal-hinted-pruning-beats-generic-compression, prune-and-summarize-beats-full-history). This adds the anticipatory move: estimate the task's scope before gathering anything, execute the minimum path that estimate implies, and widen only when verification fails. It also supplies a metric the vault lacked — the Agent Cognitive Redundancy Ratio, realized cost over an oracle minimum. Keep the two arms apart, because they differ by an order of magnitude. On MSE-Bench, a deterministic capability-controlled simulator with no LLM in the loop, E3 holds 100% success at −85% cost / −91% tokens / −92% files inspected versus max-context-first, and −16% cost versus a strong adaptive-retrieval baseline; robustness is genuinely well done (cheapest fully-successful policy under 99.8% of 4,000 cost-weightings; success holds on held-out paraphrases even as estimator accuracy falls 85.1%→66.9%). On live gpt-4o against one real library, the effect is −18% tokens versus a read-everything agent and −4% versus plain ReAct — the authors' own framing is a case study, not a benchmark, and gpt-4o simply does not over-read to the simulator's degree. The finding that most deserves to travel comes from the weaker arm anyway: on the hardest deceptive tier the "thorough" agent lost all three runs while E3 held 93%, so over-provisioned context carries a reliability tax and not merely a token tax — the same direction as less-context-better-agents and the-80-percent-problem-is-a-context-gap, arrived at from a new angle. See execution-scope-estimation-precedes-execution.

  • 2026-07-05 — less-context-better-agents (Lodha et al., Microsoft, arXiv, "Less Context, Better Agents", 2026-06-08, T1): a controlled four-way sweep measures the fix on GPT-5 (reproduced on Sonnet 4.5) — prune to the last 5 tool interactions + summarize hits 91.6% completion at 553k tokens vs full-history's 71.0% at 1.48M, reliability and cost improving together. Open questions:

  • The question this whole map is blocked on: does better-served context fix more bugs, or only cost less? CodeNib cuts trajectory tokens 50–87% at preserved localization and reports no resolve-rate arm at all; Agent Retrieval Bench measures a 27–35% acquisition miss rate and explicitly declines to connect it to repair outcomes, its own proxy-validity check putting budgeted context yield against agent gold-touch at Spearman 0.129–0.237. Two well-measured results a week apart, both stopping at the same line, and VITAL-RAG's 24.57-point survival loss stops there too. So this map has a large, quantified upstream improvement with no established downstream value. The experiment is not expensive — one agent, one SWE benchmark, the serving tier as the only variable, resolve rate reported beside the token saving. Until someone runs it, "better context engineering" is a cost claim here, not a capability claim.
  • How much of the 27–35% acquisition miss survives a good context engine? The oracle arm (+0.3115 File F1, every miss rescued) bounds the headroom for acquisition; nothing bounds the headroom for the patch. And the aggregate ranking of retrieval families reverses under repository-equal weighting, so the map cannot currently name a best method — only that a training-free fusion of a semantic and a structural ranker beat both of its parts.
  • Is the disclosure boundary a property of the corpus or of the harness? Packaged progressive disclosure adds nothing where the agent already navigates raw source well and becomes decisive (1.7× at twenty documents) once the corpus outgrows native search — which makes the harness's own search ability a named term in every result here, and means none of these numbers transfer across harnesses without re-measurement. Nobody has run the same corpus against two harnesses of known, different search strength.
  • Retrieval and interaction are two failure surfaces and nobody has composed them. Interaction finds files the retriever misses on 7.7–22.0% of samples, so an agent that searches badly and browses well is a different system from one that does the reverse. Every measurement in this map holds one of the two fixed.
