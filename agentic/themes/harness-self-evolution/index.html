Automated harness self-evolution — map

Forked from agent-harness-architecture on 2026-08-05 (bounded auto-fork; the parent was at 60 dated bullets with three declared sub-threads). The parent asks how an agent's harness should be built — which layers exist, which edits pay, and why a score belongs to the harness-model pair rather than the model. This map asks the separable question of whether the harness can build itself: automated harness search and meta-harness generation, test-time and unlabeled evolution, the observability that makes a harness editable, the judge that selects its own improvements, and the product category now selling all of it. The split is a boundary between a design claim and an optimization claim, not a topical convenience — every hand-engineered lever in the parent is evaluated by whether it improves an agent, and every claim here is evaluated by whether a search over levers beats spending the same budget elsewhere. The parent's contested status was, by its own status note, entirely on this limb, so the downgrade moves here with the evidence and the parent returns to consolidating. Seven claims and nine dated arrivals moved across intact; nothing was rewritten in the move.

Status: contested (inherited from the parent, where it was the only limb carrying the downgrade. Downgraded 2026-07-18 when two T1s landed together: automated harness evolution underperforms budget-matched test-time scaling on the domain where both were run, and scaffolding releases swing quality without improving it. Narrowed 2026-07-29 to the coding domain, where the objection was raised and remains unanswered — harness search has held-out generalization evidence everywhere else. The contest is live in both directions: the strongest positive result and the strongest negative result are on different task families and neither group has run the other's arm. Status held 2026-08-08: tonight's arrival is the map's first coding-domain evolution result whose only reported numbers are held-out — a one-project-held-out protocol across two harnesses, plus an industrial deployment — which answers the transfer half of the 2026-07-18 objection on this domain for the first time. It does not answer the other half: there is no compute-matched control anywhere in it, so by this map's own operative rule the contest stands. Status held 2026-08-09, and the pattern is now worth naming rather than repeating: tonight brings the third and fourth consecutive arrivals whose only reported numbers are held-out — a frozen gated skill pool transferring to five backbones and a second benchmark, and the first common protocol for harness optimization, which enforces its held-out partition in the execution environment rather than by instruction. Four sources in twelve days have answered the generalization half of the 2026-07-18 objection and not one has run the compute-matched control. That is no longer an omission per paper; it is a gap in the field's protocol, and the benchmark that could close it now exists — HarnessOpt-Bench meters budget in evaluation calls and case passes, so the missing arm is an entrant, not a redesign.)

What we believe now:

  • A self-evolving harness is a legible compensation layer, not an opaque scaffold. What it writes down is the correction of defects the base policy was already capable of avoiding — so the gain tracks defect mass and vanishes where that mass is near zero — and a fifth to two-fifths of what it writes is unusable outside the ecosystem it was evolved in. (Added 2026-08-12, T1, strong.) This map has had aggregate gains and no account of their content. Holding one recipe fixed across an 8-language × 3-model grid and reading the artifacts supplies one. The loop beats a minimal seed in most cells and matches or beats the hand-designed mini-SWE-agent scaffold in 14 of 24 — and the authors state the ceiling as a negative result: no recovered instance in which the evolved harness enables a repair the base policy could not otherwise express. The rules it installs are one line each (never edit test files; verify it compiles; run the failing test), and the two null regions are the mechanism's own prediction — Python, whose detector-covered defect rate is the lowest of eight at 5.6%, and GPT-5-mini, whose evolved memory contains no test-file rule at all where every other model writes one first (an-evolved-harness-compensates-defects-it-does-not-raise-the-ceiling). GPT-5-mini is also the weakest model under a static scaffold, so this is not "stronger models need less harness"; the authors' reading is that models have qualitative properties independent of capability level, which is the mechanism behind no-harness-ordering-holds-across-models and harness-asymmetry-manufactures-model-differences. Which defect binds is cell-specific — non-compiling submissions are 70% of C++ rollout defects and under 10% of Go's — so a static scaffold hard-codes one guess and is wrong most places, and the cheap planning instrument is to count your own defects first, from verifier-side and budget-side rollout evidence, with no labels (measure-the-defect-profile-before-you-engineer-the-harness). On reuse, three independent measurements agree: concept-level overlap across languages 0.55 against ecosystem-marker overlap 0.12, 20–40% of each harness ecosystem-bound, distillation retaining 1.08–1.13 of native gain on generic targets and 0.45–0.68 on ecosystem-heavy ones, transplants positive in 18 of 20 pairs and short of native in 14 (the-portable-part-of-a-harness-stops-at-the-ecosystem-margin). The failure mechanism is the transferable part: a JavaScript-evolved harness has no compile check, which is harmless on C++ and Java because running the test entails building and fatal on TypeScript where runners transpile without type-checking — the portability boundary is where a discipline stops being a free consequence of the environment's own execution chain. This does not resolve the map's standing contest (whether evolution beats matched-budget test-time scaling, or is capped by its proxy judge) — it is a different question, answered — but it does convert separate-durable-scaffolding-from-model-compensation from a design heuristic into something measurable from rollouts.
  • Three nights of this thread put the countermeasure at the door; the fourth says the door is not enough. A skill bank needs an admission gate and a removal instrument, and which one is bounded depends entirely on whether the material you are removing conditioned anything written after it. (Added 2026-08-10, T1, strong for the method, suggestive for the pushback.) SkillProx runs the familiar admission gate — a candidate is re-executed on the batch that produced it and accepted only on non-decreasing accuracy, with rollback and the failed directions fed forward — and then adds a stage this map has not had: parse the accumulated skill into auditable units, compute a frozen leave-one-out marginal utility for each against a held-out validation split, and walk the negative ones under a gate requiring structural validity, strict complexity reduction, preserved hard accuracy and bounded cell-accuracy loss. The ablation puts removal ahead of the diagnostic loop: −2.5 points without the removal stage against −1.5 without closed-loop diagnosis, on a method that beats the strongest gradient-style baseline by +3.0 pp across nine cells (deletion-needs-its-own-instrument-not-a-generic-edit). Freezing the audit before traversal is the detail worth stealing — recomputing after each removal is utility shopping with no reason to converge — and the audit over-nominates on purpose: five units flagged, one survived validation. Text identity is not utility identity: the same meta-instruction appears four times in one skill at +0.1038, +0.0119, −0.0212, −0.0337, and only the worst copy carries a hard-coded value, which is precisely what a rewrite-shaped edit operator cannot see. The pushback is the more consequential half. Last night's arrival claimed post-hoc curation is bounded below pre-commit gating no matter how good the detector gets (skill-contamination-survives-removing-the-skill). Here a batch-level admission gate of exactly the endorsed shape still admitted negative-utility material — the authors report two estimated-negative units surviving in one seed and state that such gates "can miss content harmless locally but harmful under broader validation" — while post-hoc removal recovered real points (one section moving validation hard accuracy 46% → 54% for 3.12% of the artifact). The tension resolves into a scope condition rather than a reversal: removal is bounded below gating exactly where the removed material conditioned later writes, and unbounded where it is inert reference text inside one artifact — so the operational rule is gate at admission, audit for removal, and record provenance, because provenance is what tells you which regime you are in (a-batch-level-admission-gate-is-not-a-complete-filter). One number for anyone carrying a bank: compression is nearly free to a cliff — 25.7% off for +2.0 points, still 51.0% at 74.9% compression, degrading only above ~80% — so most of what an evolution loop accumulates is inert rather than poisonous, and the loop will not shrink it (its final forward skill is +12.1% longer than its first, because an accuracy gate has no complexity term). [T1 — and the domain binds hard: spreadsheet manipulation and table QA, no repository, no patch, no test suite, so this does not touch the coding contest this map is contested on. Three backbones from one family. And the fifth consecutive arrival on this thread with no compute-matched control — the audit costs (n + M) × |V| task executions and nobody has priced that against spending the same budget on test-time sampling. The authors also decline monotonicity for their own gate: it "constrains only the current training batch"]
  • Harness optimization is now a measurable capability with a common protocol, and the first thing the protocol says is that the optimizer model is the dominant term — not the scaffold it works through, and not the search algorithm the literature has been arguing about. (Added 2026-08-09, T1, strong.) Every result on this map was produced with its author's own target agent, seed, budget, disclosure policy and scoring rule, which is exactly why the contest has been unsettleable. HarnessOpt-Bench contributes no method and fixes the problem instead: pin the invariants, grade the disclosure, and score the nominated candidate by normalized gain on a partition it never sees. Across 111 runs, swapping the optimizer model moves gain 0.142 against 0.079 for swapping its coding harness — a 1.8× ratio — and the capability tracks releases, rising monotonically +0.03 → +0.49 across five GPT versions with everything else pinned (harness-optimization-separates-models-more-than-scaffolds). Native harnesses win 9 of 20 model–task pairs against a shared harness's 11, and on the one task with four harness levels the per-model lines cross — so a claim about optimizers is itself a pair property (no-harness-ordering-holds-across-models, the-harness-shifts-benchmark-rank-order), and the paper reports tiers rather than a ranking because intermediate configurations differ by less than their round-to-round variation. Two things to steal regardless of the leaderboard. The evaluation boundary is a property of the sandbox, not an instruction: held-out data, provider credentials and the budget meter are simply absent from the optimizer's environment, which is enforce-high-risk-constraints-below-the-prompt-layer arriving inside an eval harness (enforce-the-evaluation-boundary-in-the-environment-not-the-prompt) — and it earns its keep, since most submitted candidates score below their best observed validation score. And budget is denominated in evaluation calls and case passes rather than compute, which is charge-every-search-method-the-same-budget implemented; the binding constraint turns out to be the one nobody caps, with the median optimizer using 4% of its call allowance and 82% of its case allowance. Uncomfortable rider, carried as its own claim: handed full execution traces by design, five frontier optimizers requested detailed spans 16 times across 111 runs, and time spent reading evaluation output is negatively associated with gain on all four tasks — which does not refute this map's raw-trace ablation but does refute its practical corollary (optimizers-search-broadly-and-barely-read-traces). [T1 — two replicates per configuration with ranges not intervals; resolution bands are descriptive thresholds, not significance tests; optimizer inference uncapped, so this is a ceiling rather than a cost-matched contest; Python candidates, one pinned target model per task; self-described hack-resistant, not hackproof]
  • A skill bank is not a monotone asset: unguarded accumulation peaks and then gives most of it back, and the damage cannot be rolled back afterwards — which makes admission the last point at which contamination can be stopped. (Added 2026-08-09, T1, strong.) Last night's arrival priced the regression tax as the cost of a missing rejection gate. A second group, one week later and citing none of the same work, finds the curve that tax draws. Pass@1 climbs to 62% at 105 skills and falls to 50% at 179, ending two points above its own first round — a capability–contamination tipping point, with three levels underneath it: individually harmful skills, combinatorially harmful ones (ablating the joint-selection gate grows the live pool 37 → 58 and costs 8 points, so 21 skills that each passed individual review were harmful only in company), and the systemic curve the first two produce (an-unguarded-skill-pool-peaks-then-degrades). The structural half is the more important one. Skills are distilled conditioned on the pool live at the time, so a defect admitted at round 3 is reference material for everything written after it: removing the eight culprit skills recovers 1.7 of 12.3 lost points, an oracle that also removes their full derived lineage — provenance no shipped skill library records — recovers 6.7, and 5.6 points survive perfect provenance (skill-contamination-survives-removing-the-skill). Pre-commit gating exceeds that oracle ceiling by 15.3 points, which is a stronger claim than efficiency: post-hoc curation is bounded below the intervention no matter how good the detector gets. The gate itself is the shape this vault already trusts — a conjunction of cheap heterogeneous critics (deterministic schema, no-inference held-out A–B replay, one semantic LLM call) whose ablations fail on disjoint classes of skill, plus joint subset selection — and the replay is the load-bearing component at −10 points, converging with gate-a-skill-update-on-a-replay-of-what-it-might-break from a second group and extending harness-optimizers-fabricate-failures-to-fix's warrant-aware acceptance (pre-write-admission-buys-reliability-by-serializing). It is also cheaper than what it prevents: gated per-trial tokens stay 0.77–0.94M where ungated climb to 1.30M for worse accuracy (model-routing-token-economics). Scope condition the authors supply themselves: on single-step shell tasks ungated accumulation stays net positive, because contamination chains stay shallow — it bites on long multi-step work, where the Hard tier collapses 53% → 35% ungated against 59% gated. [T1 — and the authors decline the per-round significance claim: 95% Wilson bands are ~30 points wide at n=50 and overlap at intermediate rounds, so the argument rests on trajectory shape, single-peaked against monotone, not on any one contrast. One benchmark family, one primary backbone, 50 evolution tasks, 25 test tasks behind the +8-to-+16 transfer band, and no compute-matched control]
  • The regression tax on an evolved skill bank is not intrinsic to accumulating skills — it is the price of admitting updates without replaying what they might break, and that price is now measured at 4 to 16 F1 points. (Added 2026-08-08, T1, strong.) Both caps on this limb are about acceptance: a proxy judge that prefers outputs which execute cleanly and are wrong (harness-self-evolution-is-capped-by-its-proxy-judge), and an optimizer that fabricates the failure it fixes, defeated by requiring oracle-confirmed failing-episode citations (harness-optimizers-fabricate-failures-to-fix). The vault also carries the damage empirically — an evolved skill set regresses about as much as it gains (skills-regress-as-much-as-they-gain). GSE names the cause precisely — existing frameworks treat evolution as "a sequence of local updates," so a proposal generated in isolation invalidates assumptions other skills rely on (their example: tightening a repository-exploration skill to truncate file output silently breaks the downstream analysis skills that assumed complete contents) — and answers it with an explicit skill relation graph, cluster-based consolidation, and replay-driven verification that rejects a regressing update. The ablation is the finding: removing the graph costs 4 and 11 F1 points, removing consolidation-plus-replay costs 4 and 16, on two tasks and two harnesses. That is warrant-aware acceptance generalized from "cite the failure you are fixing" to "replay the episodes you might break" — the same admission-gate shape this vault trusts everywhere else (pre-write-admission-buys-reliability-by-serializing, gate-a-skill-update-on-a-replay-of-what-it-might-break). Two riders. The evaluation is one-project-held-out — the only numbers reported are transfer numbers — which is what the 2026-07-18 downgrade demanded and had never received on a coding-adjacent domain (held-out transfer there was +0.6 points). And consolidation is a token intervention too: every skill method raises downstream execution cost over the bare agent by roughly a quarter, and the consolidated bank is the cheapest of four to carry (+21.2% against +25.4% to +26.8%). Worth stealing regardless of the result: the skill bank is versioned with a git worktree with traces and replay outcomes in SQLite, so a self-modifying artifact has a rollback story — more than the shipping products in harness-self-evolution-shipped-ahead-of-its-evidence publish. [T1 — and it does NOT un-contest this map: there is no compute-matched control, the exact comparison that produced the downgrade. Two tasks, both quality-assurance shaped (write a failing test, classify a report) rather than repository-modification, so it says nothing about resolve rates; two languages; one underlying LLM for every agent and technique; datasets of 108 and 500 cases with no seeds, variance or intervals in any cell; the strongest number (an industrial agent, F1 0.43 → 0.71) is on a proprietary dataset with an undescribed agent]
  • Harness search now has held-out generalization evidence — everywhere except the domain where it was challenged. (Added 2026-07-29, T1, strong.) The 2026-07-18 downgrade rested on a two-part objection: at matched budget, harness evolution lost to plain test-time scaling, and transferred +0.6 points to held-out tasks (harness-evolution-underperforms-matched-budget-test-time-scaling). Both parts now have answers, in two of three domains. Matched budget: a compute-matched Best-of-N control (34.0 median / 44.2 best) against a searched harness (50.0 / 56.7) — structure in the search bought what the same compute spent dumbly did not. Held-out transfer: nine unseen classification datasets at 73.1% vs 70.2% for the strongest hand-designed baseline (best on 6/9, and naively adding few-shot examples hurt on 7/9), plus a single discovered retrieval harness lifting 200 previously-unseen IMO-level problems by +4.7 points across five models never used during search — which is durable scaffolding rather than model compensation, and the first time this map has that distinction measured (separate-durable-scaffolding-from-model-compensation, discovered-harnesses-transfer-off-the-search-distribution). And on coding it answers nothing: the TerminalBench-2 arm (76.4 Opus 4.6, 37.6 Haiku 4.5 — #1 among Haiku agents) searches and scores on the same 89 tasks, framed deliberately as a "discovery problem," with leakage audited by manual inspection and regex — which catches copied strings, not a harness shaped to the task distribution. So the limb stays contested exactly where it was contested. The operative rule for reading any harness-search result, including this one: ask which distribution the number was measured on, and demand the compute-matched control. The mechanism behind the gains is separable and is the more transferable finding — see the next bullet. [T1, strong for the transfer and ablation results; the coding numbers are search-set numbers]
  • What makes harness search work is raw trace access, and summarizing the feedback is worse than not compressing it at all. (Added 2026-07-29, T1, strong.) An information ablation holding proposer, search procedure and budget fixed and varying only what the proposer may read: scores-only 34.6 median / 41.3 best, scores-plus-LLM-summary 34.9 / 38.7, full execution-trace access 50.0 / 56.7. The summarized condition is worse than raw scores on best-candidate accuracy — it spent tokens and removed signal. The enabling design is a filesystem the proposer queries with grep and cat rather than a prompt it is handed: 10.0 MTok/iteration of available diagnostics against 0.002–0.026 for every prior text optimizer, a median 82 files read per iteration, and single evaluations emitting up to 10M tokens. The mechanism is horizon — a storage or retrieval decision surfaces as a failure many steps later, so compression removes exactly the evidence needed to trace back to it. This does not contradict the vault's summarization results (prune-and-summarize-beats-full-history): those measure an agent executing, this measures an optimizer diagnosing. Compress what the actor carries forward, preserve what the diagnostician can reach back for (search-the-harness-with-raw-traces-not-summaries). Note the winner beats ACE (Agentic Context Engineering) by 7.7 points at 4.5× fewer context tokens — accuracy and cost moving together, with the Pareto frontier reported rather than one operating point. [T1, strong — one domain for the ablation, one proposer agent throughout]
  • A product category now sells harness interchangeability, which is the one thing this map has best-replicated evidence against — and it publishes no measurement. (Added 2026-07-29, T2/T3, open question, moves no status.) Mid-2026 saw a meta-harness layer arrive from unrelated vendors: an orchestration tier above Claude Code, Codex, Cursor, OpenCode, Hermes and Pi (Databricks' Omnigent, Apache 2.0, ~7.9K stars, alpha), plus a generator variant that mints bespoke per-repo harnesses across six runtimes. The load-bearing promise is composition — "combine multiple models, harnesses, and techniques without rewriting code." The pair thesis below says results do not survive a harness swap: 8.6-point mean shift with rank-order change, a security outcome reversing 10/10 → 9/30, a context pack worth double digits under one harness and zero under another, a byte-identical skill library read on 99–100% of tasks under one stack and 0–1% under another. A uniform API makes harnesses substitutable at the call site, not equivalent in outcome, and no product in the category measures the gap — their own per-runtime adapter tables (Claude Code plugins, Codex TOML, Hermes <think>-scrubbing) are tacit evidence they know it exists (harness-interchangeability-is-asserted-not-measured). Two consequences. Treat harness portability as a migration, not a config change, and re-run your evaluation on the target pair. And note the half that survives untouched: the governance tier — policy at three scopes, spend caps that pause, mandatory OS sandboxing — is enforced at the runner, below the prompt, on the dispatch path the harness already mediates, which does not require harnesses to be equivalent, only wrapped. Separately, the generator ships the self-evolution loop this map cannot validate, with no acceptance criterion, no held-out split and no mutation warrant published — so the standing ask is concrete: demand the matched-budget held-out number and the acceptance warrant before adopting one (harness-self-evolution-shipped-ahead-of-its-evidence). [T2 vendor post + T3 project README; carried as an open question, not a finding]
  • The harness-improvement limb is now contested, and only that limb. Two T1s landed together on 2026-07-18. Automated harness evolution, given the same feedback and inference budget as its baselines, does not beat plain test-time scaling on Terminal-Bench 2.1 — 67.4 average against a 68.2 direct-sampling baseline and 72.3 for parallel sampling — and transfers +0.6 points to held-out tasks (+0.0 on GPT-5.4), which says the published gains were search compute plus overfitting to the search set. Independently, the human version fares no better: 35 sequential releases of one scaffolding with the model frozen swing resolve rate 23.0%–39.0% with no improving trend (ρ=0.208, p=0.231) while tokens rise 70%. Combined with the two caps already on the books — a miscalibrated selecting judge, and an optimizer that invents the failures it fixes — the honest position is that no version of harness improvement, automated or human, has demonstrated a durable generalizing gain under controlled measurement. What survives untouched: sandbox decoupling, per-model re-tuning, the planner/generator/evaluator split, session-lifecycle re-entry, tool-surface reduction, and repo-as-harness. What survives within the limb: harness scaling still beat direct sampling (71.8 vs 68.2), so structural search is not worthless — the refuted claim is that the evolutionary loop beats a dumber use of the same compute. Practical rule until someone reruns this properly: pin your scaffolding version like you pin your model, and before adopting any self-improving harness, ask for its matched-budget held-out number. [T1, strong]
  • Behavior localization is a distinct bottleneck upstream of harness evolution, and it is weak. Modification requests describe behavior; repositories are organized by files. Unaided, a strong planner reaches 38.3% symbol-level localization F1 on a 2,267-file production harness; a generated behavior index whose every candidate is re-verified against live source lifts it to 57.1% at 12.7% fewer planner tokens. This matters for the map's contested status: an evolution loop that cannot find the edit site is not a fair test of whether evolutionary search works. Carried at single-study strength and with a heavy asterisk — the dependent variable is an LLM-judged edit plan, never an executed patch. [T1, single-study]
  • The per-model re-tuning above can be automated once the harness is made observable: represent each editable component explicitly, distill trajectories into an evidence corpus, and pair every change with a prediction verified against outcome — harness evolution becomes a falsifiable control loop, not hand-tuning (self-evolving harness beat a human-built one, Terminal-Bench 2 69.7%→77.0%, and transferred at 12% fewer tokens). Its ablation is the actionable steer: structural components (tools, middleware, memory) drive the gains; system-prompt edits contribute minimally — spend harness effort on structure, not prompt-wordsmithing. [T1] Second, apparently independent group (2026-07-14): TTHE evolves the harness at test time, from unlabeled execution traces, with the model frozen and gold used only for reporting — SWE-bench Verified 20% → 35%, LiveCodeBench 30% → 38.3%, and the same structure-not-prompts search space (candidates are arbitrary Python control programs). It never cites the Fudan work, positioning instead against Meta-Harness / MOSS / Self-Harness, so the convergence is real. The claim extends: the harness can be re-tuned not only per model but per test distribution, without labels. [T1]
  • But a self-evolving harness is bounded above by the judge that selects its own improvements, and that bound is measured. In the unlabeled setting the committed harness reaches 50.0% where an oracle over the candidates the judge inspected reaches 64.0%, and an oracle over all candidates ever generated reaches 70.0% — 14 points lost to selection, 6 more to coverage. The judge prefers outputs that execute cleanly but are wrong while "claiming near-perfect correctness," and because proposer and judge share the frozen model, extra search budget produces correlated variants repeating the same blind spots (more rounds can make it worse). The harness's usual defense against a gameable evaluator — pair it with a non-LLM ground-truth gate (llm-judges-have-exploitable-biases) — is definitionally unavailable when there is no gold. If you ship self-evolution, the proxy's false-positive profile is now a first-class engineering artifact. [T1, single-study] Second cap (2026-07-16), one step worse than bad selection: the optimizer can invent the failure it fixes. In a controlled micro-lab where the correct self-edit is no action, proposers fabricated guardrails for nonexistent failures in 15/60 runs (0/60 on featureless input) under three jointly necessary conditions — a rule-shaped pattern in the data, an under-specified rule set, and failure-presupposing instructions — and the phantom guard is a no-op the acceptance metric cannot see, so never-subtract loops retain it permanently. The procedural fix is cheap and ablation-clean: instruction hygiene (don't assert failures the evidence doesn't show), stated rule-set completeness, and warrant-aware acceptance — a self-edit lands only with oracle-confirmed failing-episode citations (fabrication 0/60). If you ship self-evolution, require warrants for every accepted change. [T1, single-study]

Through-line (newest first):

  • 2026-08-14 — interaction edge from personalized-vs-generic-agent-skills (Huang, Du & Lan, UMass Amherst / OpenRefinery.ai, arXiv, "Do Personalized Skills Help Coding Agents?", 2026-08-10, T1, suggestive, null-effect): distilling skills from execution traces is this map's central mechanism, and this runs the baseline that skill-evolution work rarely runs — a skill pooled across everyone's traces. Over 206 replayable sessions from 13 developers, a skill distilled from a developer's own history scores +0.97 over no-skill (p = .399), a skill distilled from a randomly chosen other developer scores +0.92 (p = .451), and the pooled skill scores +3.78 (p = .063) — the only condition with a win rate above half. Personalization only overtakes pooling once ≥6 task-relevant sessions exist (+5.67, n = 12), so the binding constraint on trace-distilled skills is corpus size, not distillation quality. That is a sharper version of the caution this map already carries from skills-regress-as-much-as-they-gain and a-weaker-model-writes-a-longer-skill: an evolution loop optimising against a narrow trace corpus is fitting noise, and the cheap comparison — pool the corpus — beats the sophisticated one. Status held at contested — this map's contest is over whether automated search beats spending the budget elsewhere, and a null on whose traces neither settles nor deepens it. Primary map: context-engineering. See pool-skills-across-developers-instead-of-personalizing-them.
  • 2026-08-12 — interaction edge from claude-md-catastrophic-remembering (Chakrabarti, South Park Commons, arXiv, "Why Does CLAUDE.md Keep Growing?", 2026-08-11, T1, strong for this edge): the growth law for authored instruction sets is the growth law for the memory files this map's loops write. Measured on human-maintained context files, an append-only regime is the rational response to lost rationale — deleting safely costs O(2^n) counterfactual probes, adding costs O(1) — and deletion hazard falls with age at −0.032/commit (an-agentic-context-file-grows-until-someone-bulldozes-it, deletion-hazard-falls-because-the-rationale-decayed). Two things this map should notice. Tonight's other arrival independently reaches for the same defence: TRIAGE's lessons memory is capacity-bounded and admits only rules marked cross-instance reusable, explicitly "so the cap pressures distillation rather than accumulation" — a hard cap where the CLAUDE.md work proposes provenance, and nobody has compared the two. And the capability result cuts against this map's optimism: across three maintainer tiers the uncommented arm's excess rises +67.7% → +571.9%, so a more capable evolver ratchets harder, which is a plausible unmeasured contributor to an-unguarded-skill-pool-peaks-then-degrades and skills-regress-as-much-as-they-gain. Whether catastrophic remembering reaches skill files is the paper's own stated open question. Primary map: context-engineering.
