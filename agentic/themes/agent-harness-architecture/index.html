Agent harness & infrastructure architecture — map

Coined 2026-07-04 during the seed ingest (theme not in the 8 seed groups) — flagged for David's review.

Status: contested (downgraded 2026-07-18 — narrowly, on the self-evolution limb only)

What we believe now:

  • The harness-improvement limb is now contested, and only that limb. Two T1s landed together on 2026-07-18. Automated harness evolution, given the same feedback and inference budget as its baselines, does not beat plain test-time scaling on Terminal-Bench 2.1 — 67.4 average against a 68.2 direct-sampling baseline and 72.3 for parallel sampling — and transfers +0.6 points to held-out tasks (+0.0 on GPT-5.4), which says the published gains were search compute plus overfitting to the search set. Independently, the human version fares no better: 35 sequential releases of one scaffolding with the model frozen swing resolve rate 23.0%–39.0% with no improving trend (ρ=0.208, p=0.231) while tokens rise 70%. Combined with the two caps already on the books — a miscalibrated selecting judge, and an optimizer that invents the failures it fixes — the honest position is that no version of harness improvement, automated or human, has demonstrated a durable generalizing gain under controlled measurement. What survives untouched: sandbox decoupling, per-model re-tuning, the planner/generator/evaluator split, session-lifecycle re-entry, tool-surface reduction, and repo-as-harness. What survives within the limb: harness scaling still beat direct sampling (71.8 vs 68.2), so structural search is not worthless — the refuted claim is that the evolutionary loop beats a dumber use of the same compute. Practical rule until someone reruns this properly: pin your scaffolding version like you pin your model, and before adopting any self-improving harness, ask for its matched-budget held-out number. [T1, strong]
  • Decouple the reasoning loop from its execution sandbox behind a stable tool-call interface (execute(name, input) → string) rather than running the harness inside the same container as its tools — the decoupling itself has been measured to cut latency substantially (p50 TTFT ~-60%, p95 ~-90%). [T2]
  • More structure is not always better structure — sometimes the highest-leverage harness edit is removing tool surface. A controlled three-arm ablation (all-tools / bash-only / a single execute_code channel), crossed over two task regimes and two agent designs with the model fixed, finds restricting the tool surface is pass-rate-tied in every cell and cheaper in three of four — the extra affordances bought no capability at current model sizes and usually cost tokens, because one general execution channel caches and composes better than many narrow schemas. The cheapest surface depends jointly on task regime and agent design, decided by cache-adjusted cost. Methodological catch worth keeping: separate cost-on-success from cost-of-failure, since the one adverse cell was entirely doomed-run failure cost, not a per-edit tax. [T1, suggestive]
  • Don't harden a harness against a specific model's current limitations — those workarounds become technical debt (or active friction) once a newer model no longer has the limitation; re-examine and strip the harness on each model upgrade. Now cross-org: shown across two Anthropic systems (the Sonnet→Opus "context anxiety" anecdote, Opus 4.5→4.6 deleting sprints) and independently by Cursor, which re-tunes edit format, prompting, and tool provisioning per model and re-iterates for weeks on every new model. This cross-org replication is what moves the map to consolidating. [T2]
  • The harness is customized per model and per version, not model-agnostic — matching each model's training (OpenAI patch-based edits vs Anthropic string-replacement; literal vs intuitive prompting), with mid-chat model switching needing explicit architectural support. A focused reliability sprint at Cursor drove all tool calls to 2–3 nines. [T2]
  • For multi-hour autonomous builds, split roles into planner / generator / evaluator — the evaluator being a separate skeptical agent (drives the running app with Playwright, grades against hard thresholds) because an agent asked to grade its own output confidently praises mediocre work. Caveat (new this run): a separate LLM evaluator is still gameable once something optimizes against it — see agentic-code-review and llm-judges-have-exploitable-biases. [T2]
  • The per-model re-tuning above can be automated once the harness is made observable: represent each editable component explicitly, distill trajectories into an evidence corpus, and pair every change with a prediction verified against outcome — harness evolution becomes a falsifiable control loop, not hand-tuning (self-evolving harness beat a human-built one, Terminal-Bench 2 69.7%→77.0%, and transferred at 12% fewer tokens). Its ablation is the actionable steer: structural components (tools, middleware, memory) drive the gains; system-prompt edits contribute minimally — spend harness effort on structure, not prompt-wordsmithing. [T1] Second, apparently independent group (2026-07-14): TTHE evolves the harness at test time, from unlabeled execution traces, with the model frozen and gold used only for reporting — SWE-bench Verified 20% → 35%, LiveCodeBench 30% → 38.3%, and the same structure-not-prompts search space (candidates are arbitrary Python control programs). It never cites the Fudan work, positioning instead against Meta-Harness / MOSS / Self-Harness, so the convergence is real. The claim extends: the harness can be re-tuned not only per model but per test distribution, without labels. [T1]
  • But a self-evolving harness is bounded above by the judge that selects its own improvements, and that bound is measured. In the unlabeled setting the committed harness reaches 50.0% where an oracle over the candidates the judge inspected reaches 64.0%, and an oracle over all candidates ever generated reaches 70.0% — 14 points lost to selection, 6 more to coverage. The judge prefers outputs that execute cleanly but are wrong while "claiming near-perfect correctness," and because proposer and judge share the frozen model, extra search budget produces correlated variants repeating the same blind spots (more rounds can make it worse). The harness's usual defense against a gameable evaluator — pair it with a non-LLM ground-truth gate (llm-judges-have-exploitable-biases) — is definitionally unavailable when there is no gold. If you ship self-evolution, the proxy's false-positive profile is now a first-class engineering artifact. [T1, single-study] Second cap (2026-07-16), one step worse than bad selection: the optimizer can invent the failure it fixes. In a controlled micro-lab where the correct self-edit is no action, proposers fabricated guardrails for nonexistent failures in 15/60 runs (0/60 on featureless input) under three jointly necessary conditions — a rule-shaped pattern in the data, an under-specified rule set, and failure-presupposing instructions — and the phantom guard is a no-op the acceptance metric cannot see, so never-subtract loops retain it permanently. The procedural fix is cheap and ablation-clean: instruction hygiene (don't assert failures the evidence doesn't show), stated rule-set completeness, and warrant-aware acceptance — a self-edit lands only with oracle-confirmed failing-episode citations (fabrication 0/60). If you ship self-evolution, require warrants for every accepted change. [T1, single-study]
  • The thing outside the agent that decides it is not done can itself be learned — and its correct policy differs per agent. A cost-penalized contextual bandit choosing {generate, analyze-then- generate, stop} from cheap static + dynamic features beats a fixed iteration budget on quality and price (82.8% line / 74.7% branch / 64.7% mutation at $0.693 vs 77.3 / 70.2 / 59.6 at $0.797) — and learns opposite policies for two agents: stop-early-on-95%-of-tasks against a strong-zero-shot agent, iterate-and-analyze against a weaker one. This is separate-the-generator-from-the-evaluator with an economic policy attached: the evaluator does not just grade, it decides how much more to spend. The fixed iteration cap in most harnesses is wrong in both directions at once. [T1, single-study]
  • The harness extends into the repository itself: in an agent-first codebase, knowledge layout (a ~100-line AGENTS.md table of contents over a structured, CI-linted docs/ system of record), layer-dependency linters, structural tests, and "golden principle" cleanup agents are harness components on equal footing with tools — enforce invariants mechanically, leave implementations free (~1M LOC / ~1,500 PRs / 3.5 PRs-per-engineer-day in 5 months with zero hand-written code; custom lint errors inject remediation instructions into agent context; recurring GC agents replaced the 20%-of-week manual slop cleanup). Third org converging on harness engineering as the core discipline. [T2]
  • Below the role split sits a session-lifecycle split: an initializer agent seeds the environment once (init script, feature list all-marked-failing, progress file, git), then each session re-enters through a fixed ritual (read artifacts → pick ONE incomplete feature → baseline test → incremental progress → clean artifacts out) — killing the two unguided cross-window failure modes: build-everything-at-once and premature "done". [T2]

  • 2026-07-18 — harness-evolution-evaluation-rethink (Wang/Zhu/Hu/Yuan/Chen/Senthil/ Hajishirzi/Tsvetkov/Dasigi/Xiao, AI2 / UW et al., arXiv, "Rethinking the Evaluation of Harness Evolution for Agents", 2026-07-14, T1, strong): the map downgrades to contested on this bullet. The argument is methodological and hard to escape — harness evolution is itself a search procedure that repeatedly runs and revises candidates, so crediting its gain over a single-shot baseline conflates the design discovered with the compute spent discovering it. Match feedback and inference budget across arms on Terminal-Bench 2.1 (Claude Opus 4.6, GPT-5.4, GPT-5.4-mini) and harness evolution averages 67.4, below the 68.2 direct-sampling baseline, while parallel sampling reaches 72.3 and harness scaling 71.8. With unit tests the gap widens (parallel 86.0 pass@1; sequential refinement 91.8 pass@5; harness evolution 75.8 / 86.2). The decisive number is generalization: held-out tasks gain +0.6 (+0.0 on GPT-5.4) — the evolution fitted the tasks it searched. This lands exactly on the caveat evolve-the-harness-at-test-time-without-labels named and did not test (transductive; forward generalization unestablished), which makes it more damaging than a non-replication. Note what survives: harness scaling still beats the baseline, so structural search has value; the refuted claim is that the evolutionary loop beats simpler use of equal compute. Ripples to evaluation-integrity as a protocol (charge-every-search-method-the-same-budget): disjoint search/eval task sets, matched budgets, held-out reporting. Caveats: one benchmark, three models, authors' reproduction of harness evolution rather than a named published system — fidelity is contestable.   • 2026-07-16 — phantom-guardrails-counterfactual-fabrication (Wang/Qian/Lin/Xu/Chen/Jiang/ Liu/Yu, CMU / Georgia Tech / Corespeed, arXiv, "Phantom Guardrails: When Self-Improving Agent Harnesses Fix Failures That Never Happened", 2026-07-13, T1, single-study): the self-evolution thread's second cap, past the judge's bad selection — fabrication. The Counterfactual Fabrication Lab (deterministic, byte-exact oracle, correct action = do nothing) shows optimizers enabling guards for nonexistent rules and citing oracle-refuted violations in 15/60 runs when all-legal input carries a rule-shaped pattern (0/60 featureless; other pattern shapes 0/180). Three conditions each necessary: rule-shaped pattern, unstated rule-set completeness (stating it → 0/60), failure-presupposing instructions (neutral charter → 0/60). Under suppression-only acceptance the phantom enters monotonically (1→8→10→11 across rounds) and can never be demerited — a no-op guard is invisible to the metric — which is a new failure shape: not reward hacking, not over-refusal, but unwarranted complexity the score can't see. Warrant-aware acceptance (self-edits land only with oracle-confirmed episode citations) excludes it entirely: 0/60 all rounds. Answers the direction of this map's adversarial-arm question: no adversary needed, just a presupposing prompt over an open-ended spec. Caveats: board-game micro-lab; effect concentrates in weaker proposers (deepseek/qwen/GLM-5.1); carry the existence proof + ablations + remedy, not the 25% rate. Also ripples to evaluation-integrity (a metric blind to unnecessary work) and runtime-action-governance (failure-presupposition manufactures overeager self-modification the way target under-specification manufactures overeager action). See harness-optimizers-fabricate-failures-to-fix.

  • 2026-07-14 — tthe-test-time-harness-evolution (Nie et al., HKBU / USTC / HKUST / TCL, arXiv, "TTHE: Test-Time Harness Evolution", 2026-07-09, T1, single-study): a second, apparently independent lineage for automated harness evolution — and it drops the label. TTHE maintains a population of candidate harnesses (arbitrary Python control programs), refines them with an agentic proposer reading their execution traces, and commits one via a judge scoring three execution-derived proxies; solver, proposer and judge are the same frozen LLM in different roles, and gold is used only for reporting. Caveats that bound this hard: transductive (selected and scored on the same batch — forward generalization unestablished, and the authors name the prequential test they did not run), single-run cells (no seeds, no variance, no CIs), small slices, BIRD's slice built from the baseline's own failures, and zero cost accounting — no tokens, no dollars, no wall-clock — for a method that re-runs a population of programs. Open questions:

  • No longer single-vendor: Cursor and OpenAI now corroborate from different orgs. Still open: the quantified claims (latency -60/-90%, build cost/duration, tool reliability 2–3 nines, 3.5 PRs/eng/day) are each one system's numbers, not general constants — no cross-org quantification of the same metric exists yet.
  • The repo-as-harness evidence (OpenAI) is one greenfield, agent-first-from-empty-repo system; whether mechanical-invariant enforcement pays off retrofitted onto a brownfield codebase is unmeasured.
  • Still no systematic accounting of how often or how expensively harness debt accumulates — both vendors report re-tuning per model as necessary, neither measures the cost of not doing it. The self-evolving-harness source begins to close this (it measures token efficiency of the evolved harness) but its evidence-corpus quality becomes the new, unquantified bottleneck.
  • Cost/latency of the multi-agent planner/generator/evaluator split (~$125–200/build) is unquantified against a strong solo baseline on the same task at the same model.
  • The evaluator-agent pattern now has a live tension: an LLM evaluator carries exploitable biases under optimization pressure (llm-judges-have-exploitable-biases) — how a harness keeps its evaluator honest (rotate it, pair it with a non-LLM ground-truth gate) is unresolved. Sharpened 2026-07-10: the evaluator's environment is part of the answer, since an agent with web and git-history access routes around the criterion 63% of the time (benchmark-scores-inflate-when-agents-can-retrieve-the-fix). Sharpened again 2026-07-14, and it now cuts the map's own most exciting result. Self-evolving harnesses are the pattern this map is most bullish on, and TTHE measures the ceiling they hit: 20 points of attainable performance lost to a miscalibrated judge, most of it in selection rather than search. The standard remedy is unavailable in the unlabeled setting by construction. Open, and now urgent: does the selection gap widen across generations as proposer and judge share blind spots (the correlated-variant finding says yes); is there any label-free in-flight detector of judge miscalibration; and does a periodic gold-labeled audit — the only obvious fix — reintroduce the labeled-development-set dependency the whole method exists to escape? 2026-07-16 adds the second cap and a remedy with a catch: the optimizer can fabricate the failures it fixes (harness-optimizers-fabricate-failures-to-fix), and warrant-aware acceptance eliminates fabrication in the lab — but the lab has a byte-exact oracle to confirm warrants against, and the unlabeled setting's defining condition is that no such oracle exists. Whether a warrant requirement is implementable label-free is now the sharpest open sub-question in this thread.
  • How expensive is self-evolution? Both self-evolving-harness sources report gains and neither reports a full cost. The Fudan work at least measures token efficiency of the evolved harness (−12%); TTHE reports no cost figure at all for the evolution process — while maintaining a population of candidate programs, running an agentic proposer over their traces, and re-executing candidates for a judge. A method whose price is unstated cannot be compared against the compute-matched baselines the authors themselves say are missing (best-of-N execution selection; development-time optimizers). Until someone prices it, "the harness improves itself" is a capability claim, not an engineering recommendation.
  • If ~95.6% of from-scratch failure mass sits in setup, configuration, and integration, then the highest-return harness component is the environment, not the role split — and none of the planner/generator/evaluator numbers control for environment quality. Nobody has ablated a harness against a fixed, pre-built environment to separate the two contributions.
