Problem → spec → tickets (spec-driven development) — map

Coined 2026-07-05 during the nightly radar — first evidence in the previously-empty "Problem → spec → tickets" group. Moved to consolidating 2026-07-11: a second independent T1 (SLUMP) supplies the other half of the claim — the agent can neither critique a spec nor retain one that arrives in pieces — and the two compose into a positive, quantified instruction. Flagged for David's review.

Status: consolidating

What we believe now:

  • The specification is a contract that must be held outside the agent. Two independent T1 results, approached from opposite ends, converge on this: the agent cannot critique a spec (best agent 44.4% at finding design-proposal defects) and cannot retain one that arrives incrementally (single-shot beats emergent delivery on 16/20 papers for Claude Code, 14/20 for Codex, with requirements held constant). Neither job goes to the model. [T1, two groups]
  • How the spec arrives changes what gets built — hand it over whole. SLUMP holds the content of the requirements fixed and varies only delivery: everything upfront, versus ~60 progressive requests that disclose the design as you go. The emergent condition — which is how nearly every chat-first agent product invites you to work — produces measurably less faithful artifacts, and degrades structural integration on both platforms tested. "Write the spec first" is now a measured effect, not a taste. [T1]
  • Agents are weak at critiquing a spec before coding — finding the omissions, ambiguities, inconsistencies, and bad assumptions a maintainer catches in RFC review. The best agent (GPT-5.4) reached only 44.4%; it misses more spec defects than it finds. So the human-in-the-loop spec review is a load-bearing gate, not optional polish — it sits exactly where the agent is weakest, upstream of the code phase. [T1]
  • Track the spec in external state; a tracker recovers most of what emergence costs. ProjectGuard — a project-state layer outside the agent, maintaining what the spec so far commits the project to — recovers 90% of the faithfulness gap on the worst-degrading platform (fully faithful components 118 → 181, severe failures 72 → 49). This is the same "externalize the durable state" instruction unattended-operation reached from the other direction, now applied to the contract rather than the run. [T1]
  • Practical shape, therefore: a human reviews the spec (the model can't), a durable artifact tracks it (the model won't), and an under-specified ticket should route to a different pipeline than a well-specified one (scaffold-topology-should-adapt-to-task-quality) — under-specification is the expensive case, and it is now measurably expensive. [T1]

Through-line (newest first):

  • 2026-07-20 — how-practitioners-build-se-agents (Lyu et al., SMU / UCL / Tencent / Alberta, arXiv, "How Do Practitioners Build SE Agents?", 2026-07-12, T1, suggestive): this map's central instruction, applied one level up and observed in production. track-the-spec-in-external-state established that the spec of the work must be held outside the agent. Practitioners building SE agents report that the spec of the agent — its prompts, skills, context definitions, and scaffold behavior — has become the central engineering artifact, because "an SE agent's capability is determined largely by these specifications rather than by hand-written code" (77% agree, mean 3.90). The practice is concrete and cheap to copy: written "for the agent to read… it has to be versioned together with the code — when you commit, you commit the Markdown too. It becomes a new software-engineering artifact" (P17), with system prompts under version control and tests written on top of them. Requirements now serve "a dual audience: human teams and the agents that consume them as input," pushing teams toward explicit, agent-readable specs. Two connections: this is make-agent-facing-rules-enforceable-not-conventional arriving from the authoring side rather than the enforcement side — if the Markdown is a build input it needs review, versioning, and tests like any other — and a hand-authored, reviewed, version-controlled agent spec sits squarely on the favourable side of generated-context-files-cost-more-than-they-help's line. Worth noting this is one of the study's lower-rated shifts (3.90 against 4.46 for the review-burden shift): real, not yet universal. Caveats: self-report, no inter-rater reliability, 15 of 20 interviewees at big tech, Feb–May 2026 window, and the finding describes teams building agents, which may not transfer to teams merely using them. See agent-specifications-are-versioned-engineering-artifacts.
  • 2026-07-17 — interaction edge from cheap-code-costly-judgment (Davis et al., Purdue, arXiv, "Cheap Code, Costly Judgment", 2026-07-04, T3, single-study): a live amendment to hold the spec outside the agent. The 12-week case argues part of the contract cannot be written up front — the "governance conversion" theory says controls (and the constraints they encode) are discovered from failures visible only during agentic work, then converted into durable artifacts. So the external contract this map recommends is not a static document authored before coding; it is a substrate that accretes, and the discipline is converting each surfaced gap into a durable, agent-legible artifact fast enough to sustain velocity. Complements rather than contradicts the human reviews the spec and a durable artifact tracks it: the artifact is right, the assumption that it can be complete at t=0 is what the case pushes on. Primary map: runtime-action-governance. T3, single-study. See governance-conversion-controls-discovered-from-agentic-failures.
  • 2026-07-12 — interaction edge from underspecbench-action-boundaries (Ji et al., arXiv, 2026-07-02, T1): the action-layer face of underspecification. The map knew the agent can't critique a spec and can't retain one; now measured is what it does under an incomplete one — it acts anyway (refusal ≤2.5%; 55.8–67.8% of acted runs violate a boundary), and the damage is driven by target underspecification (Wrong Target 9.6% → 75.1%), while "weak intent wording is recoverable when the target is unique." The spec-writing corollary is cheap and concrete: a fully qualified, unique target in the ticket buys more safety than any amount of intent prose. Also feeds this map's harness-or-model open question below: whether the agent asks instead of guessing is harness-determined (31.8% vs 10.5% ask rate, model fixed). Primary map: runtime-action-governance. See underspecified-targets-drive-unsafe-actions, clarification-is-a-harness-affordance.
  • 2026-07-11 — slump-emergent-specification (Yan/Chen/Zhang, Purdue, arXiv, "When the Specification Emerges: Benchmarking Faithfulness Loss in Long-Horizon Coding Agents", 2026-03-17, T1): SLUMP holds requirements fixed and varies only how they arrive — single-shot vs ~60 progressive requests. Single-shot wins 16/20 (Claude Code) and 14/20 (Codex) across 371 verifiable components from 20 ICML/NeurIPS 2025 papers; structural integration degrades on both; semantic faithfulness loss is severe for Claude Code, minimal for Codex. ProjectGuard, an external project-state tracker, recovers 90% of the gap (118 → 181 faithful components; 72 → 49 severe failures). Moves the map emerging → consolidating — the second independent T1, and the one that turns SpecBench's negative result into a positive instruction. See emergent-specs-corrupt-the-artifact, track-the-spec-in-external-state.
  • 2026-07-05 — specbench-spec-level-reasoning (Hamblin et al., arXiv, "SpecBench: Evaluating Specification-Level Reasoning for Software Engineering LLM Agents", 2026-05-28, T1): benchmarks the pre-code phase — given a design proposal, codebase, and RFC history, find the proposal's deficiencies — using tasks from real RFC review across Kubernetes, React, Rust, TVM, vLLM. Best agent (GPT-5.4) hits 44.4%; without execution feedback, agents reason poorly about specs in the abstract. Positions "planning mode" / spec-driven development as the direction. See agents-are-weak-at-spec-critique.

Open questions:

  • Is the emergent-spec penalty a model failure or a harness failure? Claude Code suffers severe semantic faithfulness loss; Codex barely degrades. SLUMP does not isolate why. If the gap is harness-side, "agents lose emergent specs" is really "some harnesses do," and the fix is a harness feature rather than a workflow discipline — a materially different instruction. A mechanism of the right shape appeared 2026-07-12: harnesses differ 3× in whether the same model surfaces uncertainty as a clarifying question (clarification-is-a-harness-affordance). Suggestive, not probative — nobody has run SLUMP's protocol across harnesses with ask-affordance as the variable.
  • What should the external tracker track? ProjectGuard (spec state) helps; generic memory scaffolds degrade all 10 models tested (memory-scaffolds-can-degrade-long-horizon-agents, same run, also T1). The reconciling hypothesis — structured contract-state helps, unstructured self-recall hurts — is stated in both maps and tested in neither. Head-to-head on one task set settles it, and it is the single most decision-relevant experiment either map is missing.
  • Does a human-refined spec measurably improve downstream code quality? Both sources measure the spec layer's failure; neither measures the downstream delta from fixing it. (Other 2026 work claims up to ~50% error reduction from human-refined specs — still not ingested; a standing sweep candidate.)
  • Ticket decomposition remains unmeasured — but the hole narrowed at the edges on 2026-07-12. SpecBench covers spec critique, SLUMP covers spec retention — nobody measures spec → tickets, which is where loop-engineering's fleets get their work. Adjacent now: retry-cost-is-an-architectural-property measures runtime decomposition (system-authored, on cost, not fidelity — decomposition as failure-isolation, not as work-breakdown), and underspecified-targets-drive-unsafe-actions prices what an under-specified ticket costs at the action layer. The center of the hole — do human-authored decompositions produce more faithful outcomes, and what makes a ticket "workable"? — is still unmeasured by anyone.
  • Transfer is unproven: SLUMP's domain (reimplementing ML papers) has an unusually crisp ground truth. Messy product specs, with stakeholders and no answer key, are the untested case.

  • context-engineering — spec critique is a context-heavy task (proposal + codebase + RFC history), and the ProjectGuard result is a context-engineering intervention wearing a spec-tracking label. The memory-scaffold tension is shared between the two maps.
  • agent-harness-architecture — if the Claude Code / Codex divergence is harness-side, this map's central finding belongs partly to that one; and adaptive scaffolding (scaffold-topology-should-adapt-to-task-quality) is the harness responding to spec quality at runtime.
  • unattended-operation — "externalize the durable state" is the same instruction; ProjectGuard is that pattern applied to the contract instead of the run.
