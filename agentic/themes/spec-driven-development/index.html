Problem → spec → tickets (spec-driven development) — map

Coined 2026-07-05 during the nightly radar — first evidence in the previously-empty "Problem → spec → tickets" group. Moved to consolidating 2026-07-11: a second independent T1 (SLUMP) supplies the other half of the claim — the agent can neither critique a spec nor retain one that arrives in pieces — and the two compose into a positive, quantified instruction. Flagged for David's review.

Status: consolidating (status held 2026-08-01 — tonight's T1 separates two capabilities this map had merged and confirms the delivery half from the opposite end, which strengthens the standing claim rather than moving it; the consensus bar here wants independently designed measurement approaches, and elicitation has been measured exactly once, on the most favourable oracle available)

What we believe now:

  • Judging a specification and discovering one are different jobs — the agent is bad at the first and productive at the second, so the spec gets written in its own phase and handed over whole. (Added 2026-08-01, T1, strong.) This map's contract-outside-the-agent claim rests on two findings about what the agent cannot do — critique a spec (agents-are-weak-at-spec-critique, 44.4% on design-proposal defects) and retain one delivered in pieces (emergent-specs-corrupt-the-artifact) — and both have been read as therefore a human writes it. That reading merges design judgement with systematic observation. Given an oracle it can probe, a dedicated spec agent that does nothing but explore and write SPEC.md, followed by a synthesis agent that does nothing but implement from it, beats the same scaffold and the same model in one interleaved loop on all 200 ProgramBench instances across four models: average test pass rate +6.9% to +21.3% (33.66→40.84, 27.51→31.40, 59.02→65.14, 39.09→41.78), every one significant at p < 0.01 paired Wilcoxon, winning on 59–75% of instances. The tail moves more than the mean — near-perfect reconstructions triple at the ≥90% threshold (5.5% → 16.5%) and quadruple at ≥95%, both with non-overlapping intervals. The mechanism is measured, not assumed: binary exploration coverage rises 9.4–18.5% on every model, and the spec agent alone (54.9–58.3%) far exceeds the synthesis agent (31.2–51.3%) with their union barely adding — an agent that can code stops exploring too early, every time (elicit-the-spec-in-its-own-phase-before-synthesis). Note the vault-shaped failure it removes: a typed signature read at turn 4 and emitted untyped at turn 57, which is a-loaded-skill-is-not-a-retained-requirement on a fifty-turn delay, answered here by writing the requirement to a durable artifact a fresh context reads rather than by restate-the-checks-externally-at-completion's re-presentation. [T1 — but the scope condition is severe: an execute-only binary is a perfect, cheap, deterministic oracle available on demand, which is exactly what a real feature request lacks, and the authors concede pronounced degradation at repository scale. One scaffold, same model both phases, no matched-budget arm (answered indirectly by 100% of runs self-terminating inside the cap), no repeated runs per instance, deterministic CLI programs only, cost up 48–130%]
  • Make the executable spec two checks, not one: does the path exist, and does the path behave. (Added 2026-07-30, T1, single-study.) Everything this vault carries as an external contract is behavioural — a test suite, a set of observable checks, an output comparison — and all of it answers did the result behave correctly. A second, separable check asks do the required units, relations and data flows exist along the functional chain, and it is answerable statically, before anything runs. Measured against the same harness, removing the behaviour half costs −6.7 pp and removing the architecture half −4.1 pp, so the two questions fail independently (split-the-executable-spec-into-path-and-behavior). The practical value is the localization: a violation names the unit, relation or data-flow edge that broke, which is the form of feedback the vault's loop evidence says is worth having and the external anchor a cheap independent check needs. [T1, single-study — authors' own system and baselines, no preregistration, no seed variance, no confidence intervals; 9/17/28 resolved tasks; gains thin out above ~4K LOC; used to steer the agent, never as an admission gate]
  • Hold the spec outside the agent and re-present it at each decision it governs — holding it outside is necessary and not sufficient. (Added 2026-07-25, T3, single-study.) With 24 checks mechanically extracted from a production workflow, frozen, and available to the agent throughout, strict pass still fell 8/10 → 3/10 under long context while requirement coverage stayed above 92%: the contract survived and stopped governing (a-loaded-skill-is-not-a-retained-requirement). Changing only the completion instruction — restating all 24 obligations rather than asking the agent to validate its own constraints — restored 10/10 against 5/10 (Fisher p = 0.0325, prompts differing by 649 characters), because a self-generated validator inherits the omission that produced the artifact (restate-the-checks-externally-at-completion). Two design consequences: make the spec executable (which is what made the failure visible here at all), and make re-delivery a harness responsibility rather than a hope. [T3, single-study — one task, one model, n = 10 per arm, non-preregistered]
  • Stress-test the contract before you spend on execution, and throw the test output away. (Added 2026-07-25, T2 practice.) The only instance in this vault of a team paying to validate a spec first: the contract is a rulebook (lookup tables where structure is preserved, design docs where it is redesigned, plus a dependency map and an inventory of features with no counterpart in the target), and step two is to run a mini-migration on three files with adversarial review, discard the output, and keep the refined rules. Thereafter the rulebook is live: a recurring mistake is answered by amending the rule and regenerating the affected batch, which makes the spec the unit of repair and not only of instruction (fix-the-loop-not-the-artifact). It pairs with the same practice's other prerequisite — build and two-way validate the judge before any work begins (validate-the-judge-before-you-trust-the-migration) — so a contract and an oracle are both established and both tested up front. Note where the human effort is front-loaded: writing and stress-testing the rulebook, which is exactly where agents-are-weak-at-spec-critique predicts a human is irreplaceable. [T2, suggestive — two case studies, no control arm; a language port has an unusually complete pre-existing spec in the source program]
  • The specification is a contract that must be held outside the agent. Two independent T1 results, approached from opposite ends, converge on this: the agent cannot critique a spec (best agent 44.4% at finding design-proposal defects) and cannot retain one that arrives incrementally (single-shot beats emergent delivery on 16/20 papers for Claude Code, 14/20 for Codex, with requirements held constant). Neither job goes to the model. [T1, two groups]
  • How the spec arrives changes what gets built — hand it over whole. SLUMP holds the content of the requirements fixed and varies only delivery: everything upfront, versus ~60 progressive requests that disclose the design as you go. The emergent condition — which is how nearly every chat-first agent product invites you to work — produces measurably less faithful artifacts, and degrades structural integration on both platforms tested. "Write the spec first" is now a measured effect, not a taste. [T1]
  • Agents are weak at critiquing a spec before coding — finding the omissions, ambiguities, inconsistencies, and bad assumptions a maintainer catches in RFC review. The best agent (GPT-5.4) reached only 44.4%; it misses more spec defects than it finds. So the human-in-the-loop spec review is a load-bearing gate, not optional polish — it sits exactly where the agent is weakest, upstream of the code phase. [T1]
  • Track the spec in external state; a tracker recovers most of what emergence costs. ProjectGuard — a project-state layer outside the agent, maintaining what the spec so far commits the project to — recovers 90% of the faithfulness gap on the worst-degrading platform (fully faithful components 118 → 181, severe failures 72 → 49). This is the same "externalize the durable state" instruction unattended-operation reached from the other direction, now applied to the contract rather than the run. [T1]
  • Practical shape, therefore: a human reviews the spec (the model can't), a durable artifact tracks it (the model won't), and an under-specified ticket should route to a different pipeline than a well-specified one (scaffold-topology-should-adapt-to-task-quality) — under-specification is the expensive case, and it is now measurably expensive. [T1]

Through-line (newest first):

  • 2026-08-01 — specfirst-behavioral-spec-elicitation (Chen, Chang, Chawa, Lin, Chen, Wang & Hassan, Huawei Canada / Queen's University / University of Manitoba / Concordia University, arXiv, "SpecFirst: Behavioral Specification Elicitation as a First-Class Step in Agent-Based Program Synthesis from Scratch", 2026-07-29, T1, strong): the first source here to ask who writes the contract rather than who holds it. The task is ProgramBench — reconstruct a command-line program given only a README and an execute-only binary as behavioural oracle, a setting so hard that the strongest baseline fully resolves 1 of 200 instances, which is why the primary metric is mean per-instance test pass rate with partial credit. The intervention is one structural change: split the agent loop into a spec agent (probes the binary, writes SPEC.md, terminates on its own judgement under a 1,000-turn and 6-hour safety net, with a deliverable gate that rejects and re-asks up to 8 times if the file is missing) and a code synthesis agent (receives documentation + binary + SPEC.md, and not the spec agent's reasoning or tool output). Same scaffold (mini-SWE-agent), same model in both phases, everything else held. Results across all 200 instances × 4 models spanning two families and an order of magnitude of capability: Qwen3.5-397B-A17B 33.66 → 40.84% (+21.3%, 130/58/12 W/L/T), Qwen3.6-35B-A3B 27.51 → 31.40% (+14.1%, 121/67/12), GPT-5.5-high 59.02 → 65.14% (+10.4%, 150/38/12), GPT-5.4-mini 39.09 → 41.78% (+6.9%, 119/69/12), all p < 0.01 on a paired two-sided Wilcoxon signed-rank test. The distribution moves at the top, not the middle: on GPT-5.5-high, instances scoring ≥90% go 5.5% [3.1, 9.6] → 16.5% [12.0, 22.3] and ≥95% go 1.5% [0.5, 4.3] → 6.5% [3.8, 10.8], non-overlapping at both. The mechanism is instrumented rather than argued — line coverage of the target binary during probing (go build -cover, gcc --coverage, cargo llvm-cov) rises 9.4–18.5% on every model (p < 0.05), the spec agent covering more behaviour than the baseline on 63.5–77.2% of instances, and decomposing to 54.9–58.3% for the spec agent against 31.2–51.3% for the synthesis agent with their union adding only marginally. Downstream, the synthesis agent starts writing code earlier and sustains it longer instead of alternating probe-and-code. Two vignettes name the disease: Seq(start, end, step int64) []int64 read at turns 4–5 and emitted as func Seq(args ...interface) []interface at turn 57; six namespaces observed once, never re-referenced, omitted from the final function map, 126 test cases failing before a line was written for them. The compute confound is priced and answered indirectly — cost is 48–130% higher ($0.25–$3.16 for the spec agent) but 100% of runs self-terminated well inside the cap, so the baseline was not budget-bound; there is still no matched-budget arm. A useful null: comparing structured Markdown, freeform and OpenSpec (RFC-2119 plus GIVEN/WHEN/THEN) on 50 sampled instances shows the formal vocabulary is not what pays — the phase is (elicit-the-spec-in-its-own-phase-before-synthesis). Status held at consolidating: this confirms emergent-specs-corrupt-the-artifact from the opposite end — SLUMP varied delivery with content fixed, this varies phase structure with model fixed — and separates elicitation from critique, which sharpens the map's practice without contradicting anything on it. The load-bearing caveat is the oracle: a probe-able binary is the most favourable possible condition for elicitation and the authors concede pronounced degradation at repository scale, so what plays the binary's role for ordinary feature work is now this map's sharpest open question. Ripples: context-engineering (the phase boundary is a context boundary; reasoning-token stripping and summarization named as the destroyers of the implicit spec), loop-engineering (a sequential two-agent handoff with no shared pool and no orchestrator — the substrate event-passing-beats-shared-context-in-agent-fleets and verified-shared-state-beats-orchestrator-routing both point at), agent-harness-architecture (the deliverable gate is compile-the-procedure-into-the-harness in miniature).
  • 2026-07-30 — codespec-dual-executable-specifications (Wang, Zhang, Liu, Li & Zhu, arXiv, "CodeSpec: Dual Executable Specifications for Agentic Long-Horizon Feature Development", 2026-07-29, T1, single-study): the first source here to take executability as the design target and then decompose it. The map noted on 2026-07-25 that the spec in the study behind its newest clause was executable — "which is what made the failure visible at all" (a-loaded-skill-is-not-a-retained-requirement). This splits the executable contract into two checks that fail independently. The architecture specification asserts path integrity before anything runs: CheckUnit (each required unit exists), CheckRelation (adjacent units hold the intended relation), CheckDataFlow (required data states present between units), with failures reported as localized violations naming the unit, relation or edge that broke. The behaviour specification asserts runtime correctness at three scopes: CheckOutput (returned values and external effects), CheckBoundary (exceptional and boundary conditions), CheckState (state transitions along the chain). The joint property is functional chain completeness — every requirement realized through an ordered sequence of connected units, grounded in repository architecture evidence rather than plan prose. On FeatureBench (30/100/200 tasks, ~4.8k words and ~800 lines of required code per problem) with DeepSeek-V4-Pro: 70.7% / 55.0% / 49.9% against RTADev's 65.3% / 49.7% / 46.1%; on NL2Repo-Bench, 70.0% / 51.7% / 20.4% by difficulty. The ablations carry the claim, not the headline: removing all specifications costs −8.1 pp, the behaviour spec alone −6.7, the architecture spec alone −4.1, evidence grounding −5.9 — both halves contribute, neither subsumes the other, and their sum exceeding the joint effect says they are partially redundant rather than additive (split-the-executable-spec-into-path-and-behavior). Why the decomposition is worth more here than the numbers: every external-contract result this vault carries is behavioural — a fail-to-pass suite, 24 observable checks, a migration rulebook's output comparison — and all of it answers did the result behave correctly. Does the intended path exist at all is a different question, checkable statically, on a repository where the units already exist to be found. It is also track-the-spec-in-external-state made checkable: ProjectGuard tracked what the spec commits the project to; this makes that commitment mechanical and localized. Caveats — read this as a design, not a result. A system paper evaluated by its own authors against baselines they configured, with no preregistration, no seed variance and no confidence intervals on any contrast, and +3.8 to +5.4 pp on 30–200 tasks sits squarely in the band this vault has measured as wrong-signed 33–44% of the time (control-the-data-draw-before-the-seed). Resolved counts are 9/17/28 and 8. One primary model plus a single-split mini-model check. Gains concentrate under ~4K LOC and thin out on Hard (20.4%), so the long-horizon claim is weakest where the horizon is longest. And the checks steer the agent here — nobody has used them to admit or reject its work. Status held at consolidating: this extends the map's clause with a design, and a single-study system paper cannot carry it further. Ripples: ci-cd-for-agents (a gate constructed from the requirement rather than inherited from the repository — a third position in that map's strictness contest, and unevaluated as a gate), loop-engineering (a localized architecture violation is the external anchor a cheap independent check needs, an-independent-checker-beats-the-same-model-checking-itself), agentic-code-review (repository-grounding-buys-localization-not-judgment — the spec supplies grounding without a repository crawl).
  • 2026-07-25 — interaction edge from anthropic-large-scale-code-migrations (Anthropic, with Jarred Sumner and Mike Krieger, "How Anthropic runs large-scale code migrations with Claude Code", 2026-07-16, T2, suggestive): this map's central instruction — hold the contract outside the agent (track-the-spec-in-external-state) — operating at 1M LOC, and the only instance in the vault of a team paying to validate a spec before spending on execution. The contract is a rulebook: lookup tables where structure is preserved, design docs where it is redesigned, plus a file dependency map and an inventory of language features with no counterpart in the target. Then step two, which is the part worth copying: run a mini-migration on three files with adversarial review, throw the output away, and keep the refined rules. The spec is stress-tested against reality and the artifact produced during testing is discarded as a by-product. Thereafter the rulebook is live: when the same mistake recurs, you amend the rule and regenerate the affected batch rather than patching instances (fix-the-loop-not-the-artifact) — which makes the spec the unit of repair, not just of instruction. It pairs with the migration's other prerequisite, building and two-way validating the judge before any translation begins (validate-the-judge-before-you-trust-the-migration): a contract plus an oracle, both established and both tested, ahead of the work. Read against agents-are-weak-at-spec-critique (the best agent finds 44.4% of design-proposal defects), the human effort the post says to front-load into the rulebook and its stress test is exactly where this map predicts a human is irreplaceable. Caveats: T2 practice narrative, two case studies, no control arm, and a language port has an unusually complete pre-existing specification — the source program. Primary map: loop-engineering. See fix-the-loop-not-the-artifact.
  • 2026-07-25 — interaction edge from agent-skills-long-context-failure (Yue Xue, independent, arXiv, "How Agent Skills Fail under Long Contexts", 2026-07-20, T3, single-study): a mechanically-extracted spec, held outside the agent, measured. Twenty-four observable checks are derived from a production audit workflow's normative text — explicit requirements, prohibitions, conditional branches, field-count limits, completion rules — each rewritten as a predicate over a visible event or saved file state, and the checker itself validated against positive and targeted negative fixtures before any model runs. Two findings for this map. Holding the spec outside is not sufficient: with the checks frozen and available, strict pass still fell 8/10 → 3/10 under long context while coverage stayed above 92% — the contract survived and stopped governing (a-loaded-skill-is-not-a-retained-requirement). And re-delivering it at the completion decision is what closes the gap: 10/10 versus 5/10 for asking the agent to validate its own constraints (restate-the-checks-externally-at-completion). So the instruction sharpens from hold the spec outside the agent to hold it outside and re-present it at each decision it governs — and note that the spec here is executable, which is what made the failure visible at all. Caveats: T3, single author, one task and model, n = 10 per arm, non-preregistered, and a second task showed no effect. Primary map: context-engineering.
  • 2026-07-20 — how-practitioners-build-se-agents (Lyu et al., SMU / UCL / Tencent / Alberta, arXiv, "How Do Practitioners Build SE Agents?", 2026-07-12, T1, suggestive): this map's central instruction, applied one level up and observed in production. track-the-spec-in-external-state established that the spec of the work must be held outside the agent. Practitioners building SE agents report that the spec of the agent — its prompts, skills, context definitions, and scaffold behavior — has become the central engineering artifact, because "an SE agent's capability is determined largely by these specifications rather than by hand-written code" (77% agree, mean 3.90). The practice is concrete and cheap to copy: written "for the agent to read… it has to be versioned together with the code — when you commit, you commit the Markdown too. It becomes a new software-engineering artifact" (P17), with system prompts under version control and tests written on top of them. Requirements now serve "a dual audience: human teams and the agents that consume them as input," pushing teams toward explicit, agent-readable specs. Two connections: this is make-agent-facing-rules-enforceable-not-conventional arriving from the authoring side rather than the enforcement side — if the Markdown is a build input it needs review, versioning, and tests like any other — and a hand-authored, reviewed, version-controlled agent spec sits squarely on the favourable side of generated-context-files-cost-more-than-they-help's line. Worth noting this is one of the study's lower-rated shifts (3.90 against 4.46 for the review-burden shift): real, not yet universal. Caveats: self-report, no inter-rater reliability, 15 of 20 interviewees at big tech, Feb–May 2026 window, and the finding describes teams building agents, which may not transfer to teams merely using them. See agent-specifications-are-versioned-engineering-artifacts.
  • 2026-07-17 — interaction edge from cheap-code-costly-judgment (Davis et al., Purdue, arXiv, "Cheap Code, Costly Judgment", 2026-07-04, T3, single-study): a live amendment to hold the spec outside the agent. The 12-week case argues part of the contract cannot be written up front — the "governance conversion" theory says controls (and the constraints they encode) are discovered from failures visible only during agentic work, then converted into durable artifacts. So the external contract this map recommends is not a static document authored before coding; it is a substrate that accretes, and the discipline is converting each surfaced gap into a durable, agent-legible artifact fast enough to sustain velocity. Complements rather than contradicts the human reviews the spec and a durable artifact tracks it: the artifact is right, the assumption that it can be complete at t=0 is what the case pushes on. Primary map: runtime-action-governance. T3, single-study. See governance-conversion-controls-discovered-from-agentic-failures.
  • 2026-07-12 — interaction edge from underspecbench-action-boundaries (Ji et al., arXiv, 2026-07-02, T1): the action-layer face of underspecification. The map knew the agent can't critique a spec and can't retain one; now measured is what it does under an incomplete one — it acts anyway (refusal ≤2.5%; 55.8–67.8% of acted runs violate a boundary), and the damage is driven by target underspecification (Wrong Target 9.6% → 75.1%), while "weak intent wording is recoverable when the target is unique." The spec-writing corollary is cheap and concrete: a fully qualified, unique target in the ticket buys more safety than any amount of intent prose. Also feeds this map's harness-or-model open question below: whether the agent asks instead of guessing is harness-determined (31.8% vs 10.5% ask rate, model fixed). Primary map: runtime-action-governance. See underspecified-targets-drive-unsafe-actions, clarification-is-a-harness-affordance.
  • 2026-07-11 — slump-emergent-specification (Yan/Chen/Zhang, Purdue, arXiv, "When the Specification Emerges: Benchmarking Faithfulness Loss in Long-Horizon Coding Agents", 2026-03-17, T1): SLUMP holds requirements fixed and varies only how they arrive — single-shot vs ~60 progressive requests. Single-shot wins 16/20 (Claude Code) and 14/20 (Codex) across 371 verifiable components from 20 ICML/NeurIPS 2025 papers; structural integration degrades on both; semantic faithfulness loss is severe for Claude Code, minimal for Codex. ProjectGuard, an external project-state tracker, recovers 90% of the gap (118 → 181 faithful components; 72 → 49 severe failures). Moves the map emerging → consolidating — the second independent T1, and the one that turns SpecBench's negative result into a positive instruction. See emergent-specs-corrupt-the-artifact, track-the-spec-in-external-state.
  • 2026-07-05 — specbench-spec-level-reasoning (Hamblin et al., arXiv, "SpecBench: Evaluating Specification-Level Reasoning for Software Engineering LLM Agents", 2026-05-28, T1): benchmarks the pre-code phase — given a design proposal, codebase, and RFC history, find the proposal's deficiencies — using tasks from real RFC review across Kubernetes, React, Rust, TVM, vLLM. Best agent (GPT-5.4) hits 44.4%; without execution feedback, agents reason poorly about specs in the abstract. Positions "planning mode" / spec-driven development as the direction. See agents-are-weak-at-spec-critique.

Open questions:

  • Is the emergent-spec penalty a model failure or a harness failure? Claude Code suffers severe semantic faithfulness loss; Codex barely degrades. SLUMP does not isolate why. If the gap is harness-side, "agents lose emergent specs" is really "some harnesses do," and the fix is a harness feature rather than a workflow discipline — a materially different instruction. A mechanism of the right shape appeared 2026-07-12: harnesses differ 3× in whether the same model surfaces uncertainty as a clarifying question (clarification-is-a-harness-affordance). Suggestive, not probative — nobody has run SLUMP's protocol across harnesses with ask-affordance as the variable.
  • What should the external tracker track? ProjectGuard (spec state) helps; generic memory scaffolds degrade all 10 models tested (memory-scaffolds-can-degrade-long-horizon-agents, same run, also T1). The reconciling hypothesis — structured contract-state helps, unstructured self-recall hurts — is stated in both maps and tested in neither. Head-to-head on one task set settles it, and it is the single most decision-relevant experiment either map is missing.
  • Does a human-refined spec measurably improve downstream code quality? Both sources measure the spec layer's failure; neither measures the downstream delta from fixing it. (Other 2026 work claims up to ~50% error reduction from human-refined specs — still not ingested; a standing sweep candidate.)
  • Ticket decomposition remains unmeasured — but the hole narrowed at the edges on 2026-07-12. SpecBench covers spec critique, SLUMP covers spec retention — nobody measures spec → tickets, which is where loop-engineering's fleets get their work. Adjacent now: retry-cost-is-an-architectural-property measures runtime decomposition (system-authored, on cost, not fidelity — decomposition as failure-isolation, not as work-breakdown), and underspecified-targets-drive-unsafe-actions prices what an under-specified ticket costs at the action layer. The center of the hole — do human-authored decompositions produce more faithful outcomes, and what makes a ticket "workable"? — is still unmeasured by anyone.
  • Transfer is unproven: SLUMP's domain (reimplementing ML papers) has an unusually crisp ground truth. Messy product specs, with stakeholders and no answer key, are the untested case.

See also:

  • agentic-code-review — downstream sibling: the agent is weak at critiquing its input contract (the spec) just as it's weak at certifying its output (the diff). Both argue for verification from outside the agent, and both now have quantified failure rates for the model's self-assessment.
  • context-engineering — spec critique is a context-heavy task (proposal + codebase + RFC history), and the ProjectGuard result is a context-engineering intervention wearing a spec-tracking label. The memory-scaffold tension is shared between the two maps.
  • agent-harness-architecture — if the Claude Code / Codex divergence is harness-side, this map's central finding belongs partly to that one; and adaptive scaffolding (scaffold-topology-should-adapt-to-task-quality) is the harness responding to spec quality at runtime.
  • unattended-operation — "externalize the durable state" is the same instruction; ProjectGuard is that pattern applied to the contract instead of the run.
  • runtime-action-governance — downstream sibling as of 2026-07-12: what the agent does under an underspecified contract is act on a guessed target. The ticket's target specificity is a governance control, priced at both layers now.
