What we believe now:

  • Spec-driven development is now a large enough population on public GitHub to census, and where it is directly observable the spec and the code move together most of the time — but the census instrument is structurally blind to everything else that could be happening to a spec. (Added 2026-08-29, T1 — strong.) 470,795 spec files, 73,030 repositories, 17 named tools, 99.7% committed 2025 or later (92% in 2026 alone). Of 5,992 pull requests that touch a spec file, 81.2% also modify implementation code in the same PR (spec-driven-development-is-now-a-population-and-mostly-invisible-to-co-change). Read against the map's 2026-08-27 arrival that 73.8% of committed AI configuration is never revised after its first commit, this is the other side of the same coin: when a spec is touched, code moves with it most of the time, but neither study can see what happens to the majority of specs that are never touched again at all. [T1, strong]
  • What changed about the spec is not that there is more of it but that it became consequential: quality propagates straight into generated code, and the model does not push back on a weak spec the way an experienced engineer would. (Added 2026-08-28, T1 — suggestive.) This is the missing half of a-stale-convention-file-costs-more-than-no-file, which measured that when a written standard and working code disagree the agent follows the standard every time, even when the standard is worse. One study measures the obedience; this supplies why it is dangerous — the loop that used to catch a bad spec was a human declining to build it, and that loop is gone (false-correctness-makes-the-spec-the-consequential-artifact). The downstream symptom practitioners name is false correctness: output that is syntactically correct and locally coherent while nobody can reconstruct why it is shaped that way — "functionally correct, but nobody understands why" — which moves the validation burden off behavioural testing and onto architectural intent, contextual consistency and maintainability. That is the uncomfortable join with this map: the spec is now load-bearing at exactly the point where the executable safety net has no coverage. Reported effort has followed — one participant estimates two thirds of task time now goes into specification refinement, another reports much longer architectural planning with correspondingly shorter coding — offered as a redistribution to budget for rather than overhead to compress. The adoption denominators keep it from being a success story and agree with the-first-configuration-a-team-commits-is-usually-its-last from a second instrument: 13 of 50 respondents use a steering file at all, 6 of 50 a structured Requirements → Design → Tasks workflow. Five interviews, convenience sample, unpiloted instrument, single-coder analysis, one participant a co-author; the two-thirds figure is one practitioner's estimate of his own time. Corroboration of a mechanism measured elsewhere, not new evidence of effect. [T1, suggestive]
  • The contract held outside the agent is, in practice, almost never amended. Across 441 repositories, 73.8% of committed AI configuration artifacts are written once and never modified again, 83.1% of adopting repositories introduce artifacts at exactly one maturity level and stop, and reversals are zero — so whatever a team writes in its first rules file governs its agents for the life of the project. (Added 2026-08-27, T1 — strong.) The map's 2026-07-25 addition credited the most disciplined team observed with treating the rulebook as the unit of repair, amended whenever a mistake recurred. This is the first measurement of how common that is, and the answer is: rare. Apparent maintenance effort at higher maturity is an artifact-count illusion — control for file count and the correlation with upkeep goes to zero (partial ρ = −0.072, p = 0.32). What does scale is authorship breadth, 3.4 contributors to AI artifacts at the highest observed level against 1.0–1.5 at the lowest. Read against a-stale-convention-file-costs-more-than-no-file — when a written standard and working code disagree the agent follows the standard every time, even when the standard is worse — the population picture is uncomfortable: the field is accumulating durable, unamended, agent-obeyed contracts written at the moment of least experience with the tool. The timing carries the intervention: reaching a first artifact takes a median 633 days of observed history, the next level takes a median 154 days, so the expensive step is going from zero to one, not climbing the ladder. See the-first-configuration-a-team-commits-is-usually-its-last.
  • The reason a prose procedure is not enforceable is not vagueness — it is that it has no variable scoping. Declare per step what it reads and what it writes. (Added 2026-08-24, T1 — strong.) A prose workflow hands each step every intermediate produced before it, which is structurally a program in which all intermediates are globals: a later operation may read any of them and the dependency is invisible at the operation boundary, so the executor must infer which one was meant from a context that also holds the ones that were not. Compiling the same procedure into a form where each step declares its read and write artifacts, with constraints gating produced artifacts and explicit control transfers — while the local action of each step stays a natural-language instruction executed by an agent — takes average task resolve rate over 11 real domain workflows and 488 instances from 62 → 85 (GLM-4.7-Flash), 46 → 82 (GPT-OSS-120B) and 60 → 85 (Qwen3-235B) (declare-what-each-step-reads-and-writes). Two negative controls carry the claim. Rewriting the prose into a clearer skill document helps one executor 16 points and another zero — the signature of a fix aimed at the wrong layer, and the third independent confirmation of this map's notation null. And decomposing the prose into subagent calls without declaring the artifact boundary does not help either: the split step still receives four unrelated inputs, so smaller contexts move the selection problem rather than removing it. The mechanism is measured — the compiled form cuts per-agent input tokens 63% — and the faithfulness validator that keeps an LLM compiler honest is priced at 16 points, with three transferable pieces: a join type check that surfaces artifacts a branch leaves unavailable, an inductive decomposition of one unverifiable global claim into local obligations, and a dry-run simulation that runs source and compiled versions on coverage-enumerated scenarios with neither given the oracle label and treats their disagreement as the defect signal. Compilation is offline: median under 5 minutes, under $3 per workflow. Scope: one harness held fixed, no significance testing, and the domains where difficulty is judgement rather than enforcement (typo versus fabricated business data) sit at 50–64% under every representation — compilation buys enforcement, not judgement. [T1, strong]
  • The human spec-review gate is load-bearing and its yield is not a constant — running it with a model beside you lowered novice detection and halved the rate at which the skill was acquired. (Added 2026-08-24, T1 — suggestive.) 34 participants, counterbalanced crossover, groups matched by Mahalanobis distance on pre-tested inspection and LLM proficiency, one Bayesian regression per outcome with the design's period, sequence and carryover terms carried explicitly. Assisted inspectors detected requirements smells at about 8% lower F1 than unassisted, took exactly as long, and were unaffected on severity classification once a smell had been found — so the loss is specific to the mechanical detection sweep and not to the judgement about what was found (model-help-lowers-a-novices-yield-on-spec-review). The authors are explicit that the credibility intervals on that main effect overlap; the effect they characterise as clear is the interaction, and it is the one that outlives the tool: everyone improved between sessions, but the group that met the task first with the model improved ~7% against ~12% for the group that met it unassisted (early-model-support-halves-the-inspection-learning-curve). The practice rule the authors give is a placement rule rather than a prohibition — keep the model out of the initial detection pass, put it in post-inspection review or justification refinement — which is elicit-the-spec-in-its-own-phase-before-synthesis applied to the human instead of the agent. Scope, and it is narrow: bachelor students with no practical inspection experience, simplified documents with at most one smell per requirement, no inter-rater agreement metric on the ground truth, and nothing at all about a model used to generate or lint a specification rather than to help a person read one. [T1, suggestive]
  • When a specification must cross to an agent that did not write it, prefer retrieval-based access over handing over the document. (Added 2026-08-24, T1 — single-study, carried as an existence proof.) Of three ingestion strategies tested on a foreign specification, rewriting it into the consumer's own idiom recovered one agent almost fully (Token F1 0.035 → 0.68) and made the other worse than direct ingestion (SQL validity 43.4% → 14.09%); length compression benefited neither universally, consistent with an eight-times-longer specification not producing better code; and retrieval-based selective access dominated on no single metric but was the only strategy on the per-agent Pareto frontier of both consuming agents (retrieval-was-the-only-ingestion-on-both-pareto-frontiers). The authors' claim is exactly the modest one: not universally optimal, but the most robust common choice when you do not know how the consuming agent will react — which is the operating condition of any workflow where the agent might be swapped. The underlying phenomenon is filed at harness-as-score-confound (a-specification-is-not-an-agent-neutral-artifact). Bounds are severe and this note should not be cited as more than an existence proof: one migration task, one run per strategy, no intervals, no significance tests, and runnability of 0–1.8% across every strategy, so the metric closest to working code does not discriminate at all. [T1, single-study]
  • A specification held outside the agent buys code that runs; measured against a no-specification control it does not buy agreement, and it does not buy correctness. (Added 2026-08-23, T1 — strong. The map's first controlled arm, and its first null.) 75 execution-verified units, two independent implementers, three arms differing only in the specification supplied, judged by execution against PostgreSQL 16 and a live Oracle instance. Clean-loading output goes 72.0% → 97.3% (+25 pp on one panel, +28 on the other), monotone across arms and comfortably above the ≈13-point run-to-run spread the same study measured on that axis. Then the nulls: aggregate cross-implementer agreement moves 83.1% → 83.8% on one panel and 83.2% → 79.7% on the other — both reported, because reporting only the favourable one "would be the exact error this paper warns about elsewhere" — and structured rows against live Oracle match on 19 of 42 probes in both arms, with four wrong-data divergences merely becoming outright missing objects (a-specification-buys-executability-not-agreement). The reason is not failure but headroom: implementers with no specification already agree ~83% of the time on shared industry defaults. And the gap between the axes is enormous — on the behavioural corpus executability is ~97% while exact behavioural match against live Oracle is 2–6 units of 20, event-level fidelity 0.15–0.26. "It loads" badly overstates "it works," which indicts every spec-driven result in this vault whose endpoint is compilation or test-pass. Two structural findings survive underneath the flat aggregate and are directly actionable: partial closure is worse than none (83.2 → 72.6 — an incomplete specification disperses implementers, which is emergent-specs-corrupt-the-artifact from the completeness side), and where the specification offers options instead of deciding it splits them (−17.8 pp). The authors do not withdraw the formal notion; what they retire is the estimator's discriminating power in this regime, and the naive reading that high convergence evidences a good specification — the fix being a coverage denominator, filed at evaluation-integrity as agreement-needs-a-coverage-denominator. Scope, and it is narrow: one specification, one migration direction, 18 documents, two implementers, one model era, and the null is explicitly a statement about implementers that already share strong defaults. [T1, strong]
  • Where a rule sits in the document changes compliance more than restating it does — and saying it twice is worse than saying it once in the right place. (Added 2026-08-23, T1 — strong.) Byte-identical rule text, only its position varying: absent 19%, trailing paragraph 23%, both places 34%, matrix row 42%. Moving the rule into the dominant decision structure — the matrix a reader is already consulting — is worth +19 points, and duplication scores eight points below the better single placement, against a pre-registration that had anticipated "≈ max, not the sum" with compounding as the only expected surprise. "A second, weaker statement does not reinforce the dominant signal; it competes with it" (put-the-rule-in-the-dominant-structure-once). The negative control on the other side makes the contrast unmissable: supplying the specification's own consumption protocol — the constraint-propagation and ambiguity-stop principles, ≈1,900 tokens, which an audit found had never actually been delivered — moved compliance −2.3 pp, left ambiguity-log precision flat to three decimals, and left executability unchanged. Relocating one sentence: +19. Explaining how to read the document: nothing. That bounds what the programme may claim — "these documents determine decision X" holds; "the SDD method determines X" does not — and it is the-specs-format-is-not-what-pays refined into something usable: the format does not pay, the position within it does. And a complied-with rule can make the output worse. One collection rule's prose is a would-agree-anyway default (15/24 vs 14/24) while its matrix example acts destructively, moving both implementers off a valid CREATE DOMAIN … AS TEXT[] they write unprompted onto an invalid CREATE TYPE … AS VARCHAR(100)[] — 0 invalid declarations in control against 10 under the rule, which on the compliance axis reads as a success. Rule efficacy has to be measured separately from rule compliance. Carried with the study's own severe scope condition: the placement effect is produced almost entirely by one implementer (38 → 78 → 47 → 64%) while the other floors at 3–6% regardless. [T1, strong]
  • The map's longest-standing open question gets an answer on the test side, and the contract — not the extra prompting — is demonstrably the causal object. (Added 2026-08-19, T1, strong.) This map has asked repeatedly whether fixing the specification measurably improves the downstream artifact, and could not answer because in every prior source the spec and the artifact moved together. agents-are-weak-at-spec-critique and emergent-specs-corrupt-the-artifact measure the spec layer failing; elicit-the-spec-in-its-own-phase-before-synthesis establishes that a separate phase pays; converge-the-spec-against-the-code-before-freezing-it adds a refinement loop with n=1 behind it. Here the two are separated on 90 real production bugs from a monorepo, same model, same harness, same tool set, greenfield (existing tests stripped) and blind to the bug, the commit message and the fix diff. Making the agent extract and document each API's pre-conditions, post-conditions and undefined behaviours before writing any test is worth +9.8 points of historical-bug detection at k=5 (63.2% against 53.4%, McNemar p=0.0352) and +2.5 points of branch coverage (p=0.0034) while line coverage is flat and non-significant — so the scaffold buys control-flow depth rather than lines executed (make-the-agent-write-the-contract-before-the-test). The mediation is what turns it from an effect into a mechanism. Conditioning on whether the generated spec documented the contract the bug actually violated: 54.9% detection when captured against 19.4% when missed, Fisher p = 3.62 × 10⁻¹⁴, φ = 0.35. The intermediate reasoning step was performed in both halves of that split; the only difference is whether it landed on the right obligation. So what pays is not the ritual of producing a document — which is the half the-specs-format-is-not-what-pays had already ruled out — it is coverage of the obligation that will be violated. Two further things to carry. The failure taxonomy separates the layers cleanly for the first time: 141 runs failed at extraction (omitted methods 35, happy-path-only documentation 32, omitted data transformations 27, constants acknowledged but abstracted 25, missing execution constraints 22) and 110 captured the contract and failed at synthesis (inadequate input data 37, ignoring the agent's own explicit spec statements 36, weak assertions 20). And the human-in-the-loop curation step the framework supports was deliberately bypassed, every suggestion accepted autonomously — so 63.2% is the fully automated floor and this map's "does a human-refined spec improve downstream quality" question now has the apparatus built to answer it. [T1 — one model family, one organisation's monorepo with its own style guides and review culture, fixes touching a single production file only; historical-bug detection is a regression protocol, not new-defect discovery; contract coverage is judged by an LLM (stronger model over weaker, five runs, strict majority) and has no precision counterpart, so over-specification and hallucinated contracts are unmeasured; and the baseline already does chain-of-thought natively, so the comparison is against a reasoning baseline and not against other structured scaffolds, which the authors name as unrun]
  • Hold the contract and free the implementation, and the agent will optimise for the checker's convenience — which is the contract working as designed, and a hazard on every axis the contract does not cover. (Added 2026-08-15, T1, strong.) This map's evidence is almost entirely about acquiring a good external contract; nobody had cleanly measured what the agent does underneath one it cannot change, because in every prior source the specification and the implementation moved together. A repository-scale verified-synthesis benchmark separates them: same 43 repositories, same 2,705 specifications, prove the reference implementation versus write your own and prove that. The aggregate barely moves (27/43 against 25/43; 87.3% of specifications against 85.8%) and hides two large opposite effects — five instance-agent pairs across three repositories close all 250 of their specifications when free to write the code, against 201 when handed the reference, because the agent substituted a simpler algorithm satisfying the same contract; seventeen pairs go the other way (freeing-the-implementation-moves-the-proof-both-ways). That is enforce-invariants-not-implementations working exactly as advertised, and it is the mirror of benchmarks-conflate-model-harness-and-penalize-alternatives: stop grading against a reference and alternatives become admissible, whereupon the agent starts choosing them for reasons that have nothing to do with the user. "Satisfies the contract and is cheapest to verify" and "is the implementation you wanted" come apart precisely on what a formal specification tends not to say — performance, memory, idiom, the shape a maintainer expects. Two operational carry-outs: difficulty attaches to the grammatical shape of the obligation, with existence-and-coverage specifications the worst band at 47.1% failure, obligations built on supplied helper definitions +14.9 pp and obligations calling one API repeatedly +11.7 pp — two of the three trivially rephrasable; and residuals are shared, not random (on one repository all eight configurations failed the same seven specifications, split by whether the obligation quantified over a state or a trace), so specification shape is a design variable rather than noise. [T1 — one run per instance-configuration cell with no variance estimate, so the mode comparison rests on the 5-versus-17 instance split and not on the totals; Lean 4 only, corpus biased toward code that ports cleanly, three of four configurations near the floor; and no independent assessment of whether the substituted implementations were acceptable code, which is exactly the axis a proof cannot see]
  • A specification is finished when re-auditing it against the code stops producing findings, not when it is written — and the audit loop is where the scope you did not know about turns up. (Added 2026-08-14, T1, single-study.) Every route to an external contract this map carries treats the writing as the work. This adds the step after: fourteen cycles, each a fresh session re-analysing the specification against the real source and rewriting it, stopping when a cycle returned zero findings. The number that argues for the loop is not the ~85 corrections but the scope — the document claimed 110 affected files when written and 160 when frozen, in a codebase whose sole author was running the protocol (converge-the-spec-against-the-code-before-freezing-it). Two properties make it copyable. The loop is systematic comparison, not judgement, so it sits on the side of the line where elicit-the-spec-in-its-own-phase-before-synthesis found the agent productive rather than the side where agents-are-weak-at-spec-critique found it weak. And freezing the output gives the downstream check a stationary referent — the code is then audited seventeen times against a document that predates it, which is a form of independence this vault had not seen (the-referent-not-the-reviewer-carries-the-separation, stop-when-two-audits-against-a-frozen-referent-come-back-empty). Read as a protocol with one existence proof behind it, not as an effect. [T1 venue, n = 1 — one task, one codebase, one operator, no control arm, self-reported by the author of both the tool and the method; 1,500+ pages of raw session logs published but the reporting is not independent; closed source, so unreplayable; the protocol ran with a ~250,000-character system prompt and a frontier model in max reasoning mode, and nothing is ablated]
  • A complete contract held outside the agent still does not make the program a function of the contract — the route by which the requirements arrived keeps acting. (Added 2026-08-13, T1, strong.) This map's whole practice assumes that once the contract is external, complete and visible, what remains is implementation. SpecPath grants exactly that and measures underneath it: repository, final contract, verifier, agent configuration and 20-minute budget held fixed, execution deferred until the complete history is visible, fresh base checkout each time, and only the revision path varies. Aggregate accuracy sees nothing — final-contract realization 78.8% direct against 78.7% averaged over four contract-equivalent histories. Paired, 35 of 100 blocks that succeed on the direct statement fail on at least one equivalent history (any-CPV 36.4%, 95% CI 25.6–45.1), in all five task families (16.0–47.4%) and all three repeats. The operator doing the most damage is duplicate — restating the same atoms, changing no obligation (19 positive blocks, 18.3%) — ahead of explicit override (8, 10.8%), so this is not a story about non-monotonic revision being hard but about presentation being load-bearing at all (an-equivalent-spec-history-builds-a-different-program). The practice this adds is the paper's own step: make the agent normalize the currently binding obligations before it writes code, because completeness in the conversation is not a substitute for resolving which requirements still count. [T1 — five curated PR families are the inferential unit, so N = 5 clusters; correctness is bounded by frozen probes (tested behaviour, not program equivalence); history operators are controlled interventions, not a sample of how real reviews revise; CPV conditions on direct success and does not estimate prevalence; wording and added-length controls both have intervals spanning zero, so the effect is not "longer prompts are worse"]
  • The notation the spec is written in is not what pays — the phase and the delivery are. (Added 2026-08-13, T1, strong.) elicit-the-spec-in-its-own-phase-before-synthesis carried this as a secondary null on 50 sampled instances (structured Markdown vs freeform vs RFC-2119 GIVEN/WHEN/THEN). SPECFORM runs it as the whole study, prospectively: byte-identical propositions rendered as connected prose or as an explicit HOLD FIXED / INTERVENE / REQUIRED DIRECTION contract, 320 calls per stage, outcomes read by a deterministic evaluator that executes the emitted programs. Both stages and their preregistered conjunction return not_supported; same-account identifiability sits at chance (0.469–0.523) against a registered 0.80 in all four cells (the-specs-format-is-not-what-pays). Two independent nulls now point the same way, so effort spent inventing a spec notation is effort not spent on the two interventions with measured effects. [T1 — effective N = 16 blocks; no positive control was registered, so there is no measured floor on what this instrument could have detected; the manipulation is the whole renderer package, so a purely lexical explanation is not excluded; the domain is verbal accounts translated into equation systems, not repository work]
  • Where no spec was written, one can be recovered from the trajectory after the fact and used to score the result. (Added 2026-08-03, T1, suggestive.) Every external contract this map carries is authored in advance — a test suite, 24 mechanically extracted checks, a migration rulebook, a completion checklist restating all 24 obligations — which leaves the ordinary case untouched: a developer opens a conversation with an agent, iterates, and a diff appears, with no contract held outside anything. Intent, defined sharply against summary (why the change was made, not what changed), is recoverable from the developer/agent conversation, change metadata, agent plans and linked artifacts at F1 0.860 on 121 hand-annotated diffs — with the code change excluded from the prompt so the inference is not circular. The diff is then backtranslated into a task list using none of the sources that produced the intent, and the two compared on a five-bucket rubric applied identically by the model and by human annotators: QWK 0.907, MAE 10.31 on a deliberately balanced 118-diff benchmark (measure-drift-from-intent-not-just-defects-in-the-diff). The separation is what makes it a measurement rather than a model comparing a diff to a summary of itself. Two limits keep this a clause and not a reversal. Per-bucket F1 is 0.889 and 0.812 at the ends against 0.341 and 0.409 in the middle — it detects did roughly what was asked versus did nothing like it, and cannot grade the interval between, which is the high-confidence-at-the-extremes profile this vault keeps finding in gates. And a reconstructed intent checks execution against stated goal, never whether the goal was right, so it does not close the gap emergent-specs-corrupt-the-artifact opened. The behavioural half is real but weak: drift falls 11.82 points between versions on its own, and 5.76 points further when the author is shown the score (one-sided p = 0.026, small effect). [T1 for the offline benchmarks — one engineering environment; every scoring layer is LLM-as-a-Judge validated against human annotation rather than ground truth; the rubric's bucket boundaries are the authors' own; the drift-reduction rollout is quasi-experimental with uncontrolled self-selection and a marginal non-parametric test at p = 0.063]
  • Judging a specification and discovering one are different jobs — the agent is bad at the first and productive at the second, so the spec gets written in its own phase and handed over whole. (Added 2026-08-01, T1, strong.) This map's contract-outside-the-agent claim rests on two findings about what the agent cannot do — critique a spec (agents-are-weak-at-spec-critique, 44.4% on design-proposal defects) and retain one delivered in pieces (emergent-specs-corrupt-the-artifact) — and both have been read as therefore a human writes it. That reading merges design judgement with systematic observation.   • Make the executable spec two checks, not one: does the path exist, and does the path behave. (Added 2026-07-30, T1, single-study.) Everything this vault carries as an external contract is behavioural — a test suite, a set of observable checks, an output comparison — and all of it answers did the result behave correctly. A second, separable check asks do the required units, relations and data flows exist along the functional chain, and it is answerable statically, before anything runs. Measured against the same harness, removing the behaviour half costs −6.7 pp and removing the architecture half −4.1 pp, so the two questions fail independently (split-the-executable-spec-into-path-and-behavior). The practical value is the localization: a violation names the unit, relation or data-flow edge that broke, which is the form of feedback the vault's loop evidence says is worth having and the external anchor a cheap independent check needs. [T1, single-study — authors' own system and baselines, no preregistration, no seed variance, no confidence intervals; 9/17/28 resolved tasks; gains thin out above ~4K LOC; used to steer the agent, never as an admission gate]
  • Hold the spec outside the agent and re-present it at each decision it governs — holding it outside is necessary and not sufficient. (Added 2026-07-25, T3, single-study.) Two design consequences: make the spec executable (which is what made the failure visible here at all), and make re-delivery a harness responsibility rather than a hope. [T3, single-study — one task, one model, n = 10 per arm, non-preregistered]
  • Stress-test the contract before you spend on execution, and throw the test output away. (Added 2026-07-25, T2 practice.) The only instance in this vault of a team paying to validate a spec first: the contract is a rulebook (lookup tables where structure is preserved, design docs where it is redesigned, plus a dependency map and an inventory of features with no counterpart in the target), and step two is to run a mini-migration on three files with adversarial review, discard the output, and keep the refined rules. Thereafter the rulebook is live: a recurring mistake is answered by amending the rule and regenerating the affected batch, which makes the spec the unit of repair and not only of instruction (fix-the-loop-not-the-artifact). It pairs with the same practice's other prerequisite — build and two-way validate the judge before any work begins (validate-the-judge-before-you-trust-the-migration) — so a contract and an oracle are both established and both tested up front. Note where the human effort is front-loaded: writing and stress-testing the rulebook, which is exactly where agents-are-weak-at-spec-critique predicts a human is irreplaceable. [T2, suggestive — two case studies, no control arm; a language port has an unusually complete pre-existing spec in the source program]
  • The specification is a contract that must be held outside the agent. Two independent T1 results, approached from opposite ends, converge on this: the agent cannot critique a spec (best agent 44.4% at finding design-proposal defects) and cannot retain one that arrives incrementally (single-shot beats emergent delivery on 16/20 papers for Claude Code, 14/20 for Codex, with requirements held constant). Neither job goes to the model. [T1, two groups]
  • How the spec arrives changes what gets built — hand it over whole. SLUMP holds the content of the requirements fixed and varies only delivery: everything upfront, versus ~60 progressive requests that disclose the design as you go. The emergent condition — which is how nearly every chat-first agent product invites you to work — produces measurably less faithful artifacts, and degrades structural integration on both platforms tested. "Write the spec first" is now a measured effect, not a taste. [T1]
  • Agents are weak at critiquing a spec before coding — finding the omissions, ambiguities, inconsistencies, and bad assumptions a maintainer catches in RFC review. The best agent (GPT-5.4) reached only 44.4%; it misses more spec defects than it finds. So the human-in-the-loop spec review is a load-bearing gate, not optional polish — it sits exactly where the agent is weakest, upstream of the code phase. [T1]
  • Track the spec in external state; a tracker recovers most of what emergence costs. ProjectGuard — a project-state layer outside the agent, maintaining what the spec so far commits the project to — recovers 90% of the faithfulness gap on the worst-degrading platform (fully faithful components 118 → 181, severe failures 72 → 49). This is the same "externalize the durable state" instruction unattended-operation reached from the other direction, now applied to the contract rather than the run. [T1]
  • Practical shape, therefore: a human reviews the spec (the model can't), a durable artifact tracks it (the model won't), and an under-specified ticket should route to a different pipeline than a well-specified one (scaffold-topology-should-adapt-to-task-quality) — under-specification is the expensive case, and it is now measurably expensive. On FeatureBench (30/100/200 tasks, ~4.8k words and ~800 lines of required code per problem) with DeepSeek-V4-Pro: 70.7% / 55.0% / 49.9% against RTADev's 65.3% / 49.7% / 46.1%; on NL2Repo-Bench, 70.0% / 51.7% / 20.4% by difficulty. The ablations carry the claim, not the headline: removing all specifications costs −8.1 pp, the behaviour spec alone −6.7, the architecture spec alone −4.1, evidence grounding −5.9 — both halves contribute, neither subsumes the other, and their sum exceeding the joint effect says they are partially redundant rather than additive (split-the-executable-spec-into-path-and-behavior). Why the decomposition is worth more here than the numbers: every external-contract result this vault carries is behavioural — a fail-to-pass suite, 24 observable checks, a migration rulebook's output comparison — and all of it answers did the result behave correctly. Does the intended path exist at all is a different question, checkable statically, on a repository where the units already exist to be found. It is also track-the-spec-in-external-state made checkable: ProjectGuard tracked what the spec commits the project to; this makes that commitment mechanical and localized. Caveats — read this as a design, not a result. A system paper evaluated by its own authors against baselines they configured, with no preregistration, no seed variance and no confidence intervals on any contrast, and +3.8 to +5.4 pp on 30–200 tasks sits squarely in the band this vault has measured as wrong-signed 33–44% of the time (control-the-data-draw-before-the-seed). Resolved counts are 9/17/28 and 8. One primary model plus a single-split mini-model check. Gains concentrate under ~4K LOC and thin out on Hard (20.4%), so the long-horizon claim is weakest where the horizon is longest. And the checks steer the agent here — nobody has used them to admit or reject its work. Status held at consolidating: this extends the map's clause with a design, and a single-study system paper cannot carry it further. Ripples: ci-cd-for-agents (a gate constructed from the requirement rather than inherited from the repository — a third position in that map's strictness contest, and unevaluated as a gate), loop-engineering (a localized architecture violation is the external anchor a cheap independent check needs, an-independent-checker-beats-the-same-model-checking-itself), agentic-code-review (repository-grounding-buys-localization-not-judgment — the spec supplies grounding without a repository crawl).

Open questions:

  • NEW 2026-08-24 — does artifact-driven compilation survive a harness swap, and can it be run against a specification that is not a procedure? The +23-point result comes from a single Codex-based harness, so the map cannot say how much of it is the representation and how much is the runner — and the runner term is exactly what harness-as-score-confound says is unreported by default. Two arms nobody has run: the same compiled workflows under a second harness, and the compiler applied to a declarative contract (behavioural obligations, non-functional requirements) rather than to a step-ordered procedure, where there is no obvious artifact-read/write structure to declare and it is not clear the technique has anything to bite on.
  • NEW 2026-08-24 — is the assisted-inspection deficit a property of novices, or of the assistance? The detection loss is argued for novices, on a mechanism (delegation, automation bias) that predicts it should shrink or invert for an experienced inspector with an established strategy. The authors call for replication with professionals and nobody has done it. The sharper unrun arm is the placement claim they derive without testing: assistance restricted to a second pass, after an unassisted sweep, against unassisted-only and assisted-throughout. If the placement rule works, it is a cheap process change; if it does not, the finding is about the tool rather than the phase.
  • Does the specification null survive a heterogeneous or weaker implementer panel? (Opened 2026-08-23.) The controlled arm's finding is that a specification buys no agreement because the implementers already agreed ~83% of the time on shared industry defaults — which is a statement about the model era, not about the artifact, and the authors say so. Their own pilot with a weaker implementer already hints the other way. The arm nobody has run: the same three specification arms against a panel spanning capability tiers, reporting agreement gain as a function of baseline agreement. If the gain is real where the defaults are not shared, the estimator is fine and the finding is about 2026's models.
  • Where does rule placement stop mattering? (Opened 2026-08-23.) Relocating one byte-identical sentence into the dominant decision structure was worth +19 points of compliance — on 31 units, from one document, with the effect carried almost entirely by one of two implementers. Nobody has varied the dominance of the structure itself (a matrix versus a checklist versus a table of contents), and nobody has tested whether the effect survives a document large enough that no single structure is dominant, which is the shape of every production specification.
  • How many refinement cycles is the loop worth, and does anyone but its inventor get fourteen? (Opened 2026-08-14.) converge-the-spec-against-the-code-before-freezing-it converged at fourteen cycles and ~85 corrections on one codebase, with the operator judging when to relaunch and when to freeze. Nothing establishes whether the count is a property of the task, the codebase, the model or the operator; whether the correction curve is monotone enough to stop on; or what a cheaper variant (three cycles? one?) gives up. The paper's own recommended next step is the right one and nobody has run it: the same protocol executed by an independent operator on a public codebase, which would remove the single-case, self-report and closed-source limitations at once.
  • Does the frozen-referent design survive a specification the agent did not write? (Opened 2026-08-14.) In the one instrumented case the agent authored the specification, audited it, implemented it and verified against it — the referent is fixed in time but not independent in origin, which is exactly the shared-anchor failure a-verifier-sharing-the-interpretation-shares-the-error warns about. Whether the protocol still converges when a human writes the contract, or when a different model does, is untested and is the cheap arm that separates fixity from independence.
  • Does making the agent write down the binding obligations first buy back path invariance? (Opened 2026-08-13.) SpecPath names the missing step — normalize the currently-binding contract before writing code — and measures the failure without it, but does not run the arm where the agent is required to emit a resolved contract first and is then scored on the same paired blocks. That is a cheap, obvious, unrun experiment, and it is the one that would turn a diagnostic into a practice. It also has a natural partner: restate-the-checks-externally-at-completion restates the contract at the end; this would restate it at the start, and nobody has tested whether the two are redundant.
  • Is duplicate-history sensitivity a real ordering or noise? (Opened 2026-08-13.) The operator that changes no obligation at all produced the largest conditional path violation (18.3%), ahead of explicit override (10.8%) — but the ordering churns across repeats and the authors mark it exploratory. If it replicates, the mechanism is not revision semantics and the map's framing needs to change from "handle supersession" to "handle repetition," which is a much stranger and more general claim.
  • Is the format null real or underpowered? (Opened 2026-08-13.) SPECFORM is the most tightly sealed null this vault holds and it registered no positive control, so it has no measured floor on what it could have detected. Two independent nulls now agree that notation is inert, and neither has demonstrated it could have seen an effect of the size it was looking for. A registered positive-control arm would settle it for almost no cost.
  • Is the emergent-spec penalty a model failure or a harness failure? Claude Code suffers severe semantic faithfulness loss; Codex barely degrades. SLUMP does not isolate why. If the gap is harness-side, "agents lose emergent specs" is really "some harnesses do," and the fix is a harness feature rather than a workflow discipline — a materially different instruction. A mechanism of the right shape appeared 2026-07-12: harnesses differ 3× in whether the same model surfaces uncertainty as a clarifying question (clarification-is-a-harness-affordance). Suggestive, not probative — nobody has run SLUMP's protocol across harnesses with ask-affordance as the variable.
  • What should the external tracker track? ProjectGuard (spec state) helps; generic memory scaffolds degrade all 10 models tested (memory-scaffolds-can-degrade-long-horizon-agents, same run, also T1). The reconciling hypothesis — structured contract-state helps, unstructured self-recall hurts — is stated in both maps and tested in neither. Head-to-head on one task set settles it, and it is the single most decision-relevant experiment either map is missing.
  • Does a human-refined spec measurably improve downstream quality? (Narrowed 2026-08-19.) The agent- refined half is now answered on one artifact type: make-the-agent-write-the-contract-before-the-test measures +9.8 points of production-bug detection from a self-generated contract, with a mediation (54.9% against 19.4%) proving the contract rather than the extra prompting carries it. The human half is not, and the same paper is one arm away from it — its framework supports a curation step between specification and synthesis, and the evaluation deliberately bypasses it, accepting every agent-generated suggestion autonomously to avoid subjectivity. So the apparatus exists, the floor is measured at 63.2% detect@5, and nobody has run the arm where a developer amends the .spec.md first. That is now the single cheapest unrun experiment on this map. (Other 2026 work claims up to ~50% error reduction from human-refined specs — still not ingested; a standing sweep candidate.)
  • Ticket decomposition remains unmeasured — but the hole narrowed at the edges on 2026-07-12. SpecBench covers spec critique, SLUMP covers spec retention — nobody measures spec → tickets, which is where loop-engineering's fleets get their work. Adjacent now: retry-cost-is-an-architectural-property measures runtime decomposition (system-authored, on cost, not fidelity — decomposition as failure-isolation, not as work-breakdown), and underspecified-targets-drive-unsafe-actions prices what an under-specified ticket costs at the action layer. The center of the hole — do human-authored decompositions produce more faithful outcomes, and what makes a ticket "workable"? — is still unmeasured by anyone.
  • Transfer is unproven: SLUMP's domain (reimplementing ML papers) has an unusually crisp ground truth. Messy product specs, with stakeholders and no answer key, are the untested case.
