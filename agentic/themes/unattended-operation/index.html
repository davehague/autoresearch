  • A durable store the agent both reads from and writes to is a transmission medium, and it has an epidemic threshold sitting in a config value nobody tunes for this. Hold the model, the attack and the library size fixed and vary only how fast the skill library turns over: a quarter turnover and a compromise decays to its seed rate and never grows, half and it amplifies to a stable plateau, three quarters and it exceeds that plateau and is still climbing after five rounds. (Added 2026-08-27, T1 — strong.) This map's practice is built on externalized durable state (make-the-project-persistent-not-the-agent); this is the first measurement of that state as a population, formalized as a branching process with a reproduction-number proxy over copy propensity and reach. The operator's instinct is backwards: more turnover feels like healthier housekeeping for a long-running system, and it is exactly what tips a decaying infection into a self-sustaining one, because it keeps opening retrieval slots the agent's own copies compete to fill. Meanwhile the parameter you would reach for first does nothing — attack rate saturates in the seed count by about eight plants (19.6% at one, 41.8% at eight, 43.1% at sixteen), and a single seed at a 0.4% poisoning rate already yields 19.6%, so hardening admission buys almost nothing. In the persistent condition the in-context rate climbs from 78% toward 100% as the store fills with the agent's own entries: the store getting better at surfacing its most-represented content is the property you built it for, operating on content you did not intend. The open form of this, for any unattended loop with a read-write durable store — memory, skills, learned rules, cached plans — is that all of them have a turnover rate and nobody has measured where the critical value sits.   • The seams an autonomous harness cannot walk back are the ones its defects land on, and every specimen kept running after the mistake instead of stopping at the boundary. (Added 2026-08-26, T1 — suggestive.) Defects reproduced or located across two harnesses of opposing philosophy and different languages fall on four recurring seams, and three of four specimens end in unrecoverable loss (the-unrecoverable-seam-is-where-agent-harness-defects-land). The two irreversible ones are worth naming because both are ordinary: a path-normalisation mismatch where //secrets compares unequal to /secrets by path component while the filesystem resolves both to one file, so a delete deny-rule, a human-approval interrupt and a backend routing check all fail open — while the adjacent read/write checks, which happen to normalise, are immune. And a transient rate-limit rethrown as a bare object, JSON- stringified past a caret-anchored regex written to catch exactly it, misclassified as context overflow, and routed into a destructive compaction that permanently replaced the session's history. Four rules follow, each one cheap: one mandatory canonicalisation point per trust boundary, with downstream accepting only the canonical form; errors carry a typed kind, with regex a last-resort fallback that must fail toward the safe side (do not compact when unsure — compacting a non-overflow is unrecoverable, declining to compact a real overflow is not); derive one async twin from the other or share a single guarded core; and at every boundary, an unrecognised shape is an error, not a default. The last is the cross-cutting one and the reason the others are expensive: a harness is long-running and autonomous, so the cost of a wrong value is not the wrong value but the ten steps of work built on top of it before anyone notices. This is fail-loud-instrumentation-over-plausible-substitutes and silent-errors-dominate-agent-bug-reports confirmed from two production harnesses' own source rather than from a benchmark — and the generalisation the author draws is a requirement none of the three harnesses meets: every automated destructive action (compaction, eviction, deletion) should be recorded and, where possible, reversible. Explicitly illustrative case reports rather than an independent test: four seams induced from a small analyst-directed sample, two specimens re-derived in a sandbox and the rest located by source reading, one seam language-specific.   • The authority boundary for an unattended agent is not "code versus infrastructure" — it is "can this be ramped back." (Added 2026-08-20, T2 — suggestive.) Anthropic's CI/CD on-call agent acts alone where the action is ramped, observable and undoable: feature-flag and canary traffic ramping (with a verification step before a flag moves), draining and cordoning cluster nodes, scaling instructions during a demand surge. It proposes where the action is not: code fixes leave as pull requests a human reviews and merges, and it never deploys directly. Notice what lands on which side. Cordoning a production node has immediate blast radius and is reversible in seconds — the agent does it. A merged patch is small and is not — the agent does not. That is keep-the-agent-interruptible-and-reversible promoted from a design goal to an authorization rule, and it is the sharpest statement of it this map has recorded. The corollary for a fleet operator: the way to widen an unattended agent's authority is not to trust it more, it is to make more of your actions ramped — which is why most deployments here sit behind feature flags in the first place (bound-agent-resolution-authority-by-reversibility). The rest is this map's own checklist instantiated in production: identity is a service account with scoped connector access; the on-call Slack channel is simultaneously the operator surface and the agent's memory, with versioned markdown skills in GitHub as the standing-instruction layer beside it; and verification closes through the same connectors used to investigate, so the agent confirms the fix landed rather than reporting that it applied one (treat-agent-output-as-a-claim-not-lifecycle-state). The limits are more informative than the capabilities. The described mode is not autonomy but "multi-player mode" — either party can steer mid-incident — the initial analysis is not always right, resolution capability varies by team, and report formatting is called out as team-specific taste, "human communication, not plumbing." That last one is the generalization boundary: the fan-out over dependencies transfers, the operator surface does not. No control arm and no rate at which a reversible action the agent took was the wrong one. [T2, suggestive]
  • The two layers that decide who is accountable for an unattended agent's code — the platform controls that gate what it may do, and the provider terms that allocate responsibility for what it produces — do not refer to each other, and disagree. (Added 2026-08-18, T1, suggestive — an open question with an empirical spine, not a settled claim.) This map has treated accountability as an engineering property: who may write (a-lease-is-not-write-authority), what the fleet may believe about its own state, which credential the action ran under. The layer above that is in worse shape. The contractual vocabulary predates the product: across eighteen documents from seven providers, output is defined as what a service returns to the user, and no term describes a service that opens a branch and authors a commit. Where "agent" appears at all — one provider's terms effective March 2026 — it means an agent the customer builds, not the agent operating in the customer's repository. And the verification duty thins where the autonomy concentrates: the same provider expressly obliges individual users to review, test and validate output and states no such duty for volume-licence customers anywhere in the agreement governing them — express verification vocabulary down by a factor of seven, and to 0.00 occurrences per thousand words in the instrument governing generative-AI services specifically, against 10.82 in a comparable-length AI-specific instrument elsewhere in the collection. The consumer-to-business transition does not explain the magnitude: a second provider makes the same transition and its commercial terms retain verification vocabulary mid-range (the-terms-allocate-consequence-to-a-party-with-no-mechanism-to-discharge-it). The sharpest instance is internally inconsistent within one vendor: its terms name the removal of manual review as a product feature and assign the user sole responsibility for the consequences, while its documentation describes an agent performing the approval those terms make the user's obligation. And across all nine workflow events, authority varies, execution varies, verification varies — the consequence column is constant. For an operator this converts unease into three configuration questions answerable today: which compelling mechanisms are actually on (the defaults are off), what identity the work is recorded under (attribution runs in opposite directions across vendors, and one posts agent output under the human's own account), and what the record will support later (very little). Carried as the paper carries it: a fact about drafting, not about legal obligation, and no claim that the gap has harmed anyone.
  • A lease says the control plane may reassign the work. It does not say the previous worker is dead, and treating it as though it does is how an unattended fleet gets two writers. (Added 2026-08-17, T3, suggestive — a design contract, not a measured effect.) This map has established that a fleet needs externalized durable state and a real resume contract (the-durable-unit-needs-a-contract-not-a-checkpoint, build-the-work-queue-from-disk-state) without ever naming the mechanism that decides who may write when two workers both believe they own the job. The near-universal implementation is a lease with renewal, and it answers liveness and allocation only: a process paused under memory pressure resumes after its lease expires, a partition heals after reassignment, a mutation issued before expiry arrives after it. The separable mechanism is a monotonic ownership epoch, incremented on each reassignment, carried on every mutation, and validated at the boundary being protected — the branch head, the work ledger, the external-effect adapter — never at the scheduler, whose belief about who is alive is exactly what the failure invalidated. Holding the current epoch confers the right to be evaluated, not a presumption of correctness (a-lease-is-not-write-authority). Two corollaries: a retry is a new attempt on the same logical work, so unless repeated execution is established idempotent or its side effects isolated, a timeout produces duplicate comments and partial writes; and a worker's self-report can move an attempt to outcome-ready and no further, with only independently observed evidence completing the work (ground-completion-in-a-rerun-not-a-self-report). The lineage is deliberately old — Chubby sequencers, ZooKeeper's premise that coordination state must outlive the processes it coordinates — transferred as principles, with the explicit note that a single durable database recording epochs transactionally suffices for a modest fleet. The scaled-down version for a personal fleet of scheduled agents is the whole point: the record of who holds authority must survive the failure of the workers it governs, and a lockfile written by the worker does not.   • Crash recovery is not environment recovery — give the agent a tool to inspect its own environment, then run a separate automation that decides which failures are worth repairing and repairs them by pull request. (Added 2026-08-01, T2, suggestive.) This map's whole durable-state thread answers "the process died, how does work resume." The more common failure in a standing fleet is that nothing crashed and the environment quietly stopped being correct: a rotated secret, a changed egress rule, a drifted base image. The shipped answer has two layers and the split is the point. Below, a dynamically discoverable tool surface (MCP) the agent uses to inspect setup failures, egress policy and changed secrets — so a broken environment is something the agent can name rather than silently absorb — with interfaces that can change without rebuilding the agent loop. Above, an automation that periodically checks for failures, remembers which errors are transient versus salient, root-causes the salient ones, and opens PRs for fixes it is confident about. The transient/salient memory is the non-obvious part: most environment noise is noise, and an automation that repairs every blip is worse than none (give-the-agent-tools-to-diagnose-its-own-environment). Alongside it, two containment properties that hold against an agent rather than asking it: secrets redacted in tool results, so the value cannot be read even if the agent tries, and a supervisor process that restarts long-running builds, taking a deterministic responsibility off the model entirely.
