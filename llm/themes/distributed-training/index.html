Status: consolidating

What we believe now:

  • There are now six distinct answers to one memory ceiling, and they are indexed by three different things (revised 2026-07-25). Five of them are indexed by parameters — shard the replicated state, split a layer's math, give each device unique experts, demote cold state down the memory hierarchy, or partition depth and recompute the rest. The sixth, sequence parallelism, is indexed by sequence length, and it is the only one that makes context a property of the cluster rather than of the model: split the input into blocks, one per host, and rotate the key/value blocks around a ring while each host computes blockwise attention on whatever it currently holds. Attention over a query block against a group of KV blocks is permutation-invariant, so the visiting order is free and the next transfer overlaps the current compute. Per-host activation memory becomes 6bch — a function of the block size, containing no s at all — so trainable context scales linearly with device count (7B: 32K → 256K on 8 A100s; 3B: 32K → 16M on TPUv4-1024, 512×) at essentially unchanged MFU. It composes with re-materialization rather than replacing it. The precondition is unusually crisp and is where it stops: c ≥ F/B, block size above the host's FLOPS-to-interconnect-bandwidth ratio, minimum per-host sequence 6c — 6.2K tokens on an A100 behind NVLink and 149.5K behind InfiniBand, a 24× swing from the wire alone. [T1]
  • The offload axis has a third tier and an efficiency formula, and the formula reorders the intuition (new 2026-07-25). NVMe is over 50× larger than GPU memory on a DGX-2-class node, and running the demotion argument down to it removes model scale as a constraint: 32 trillion parameters on 512 V100s at >25 petaFLOPS (40% of peak), and 1T fine-tuned on a single node with no model parallelism where 3D parallelism stops at 20B. Crucially, at 500B — where both still fit — offload and 3D parallelism are within a point of each other (46 vs 47 TFLOPS/GPU), so this is not a penalty you accept. What generalizes past the scale headline is the decision rule: efficiency = ait × bw / (ait × bw + peak_tp), which given each state class's arithmetic intensity yields three very different bandwidth thresholds — parameters/gradients ~70 GB/s, optimizer states up to ~1.5 TB/s (their update cannot overlap with compute), and activation checkpoints under 2 GB/s. Activations are the cheapest thing to demote and the optimizer is the most expensive, which is the inverse of the ZeRO-Offload intuition below — both are right, about different resources (compute-independence vs bandwidth demand). The enabling trick is worth stealing on its own: bandwidth-centric partitioning replaces a single owner's broadcast with an allgather across all data-parallel ranks, identical GPU-side volume but every PCIe link active at once, lifting CPU→GPU from ~12 GB/s to 48 and NVMe to 25, linear in node count. [T1]
  • There are four parameter-indexed answers requiring more GPUs, and one that does not. Sharding partitions replicated state along the data-parallel axis; tensor parallelism splits one layer's math along a model axis; expert parallelism gives each device unique experts; and offload demotes cold state down the memory hierarchy — fp32 optimizer states, fp32 parameters, and the Adam step itself run on the CPU, while fp16 params/grads and forward/backward stay on the GPU. That last one is the only answer available to someone who cannot add cards, and it is derived rather than chosen: partition mixed-precision Adam training as a data-flow graph under three constraints (orders-of-magnitude less CPU compute than GPU, minimum CPU↔GPU communication, maximal savings at that volume) and the cut is forced — 12 of the 16Ψ bytes/param go to CPU, a 4× GPU-memory reduction before any sharding, at a communication volume fixed at 2× the parameter count per step regardless of batch or sequence length. It works because of a property of the optimizer, not of CPUs: forward/backward costs O(params × batch × seq) while the Adam step costs O(params), so the optimizer is the one stage whose cost is independent of the batch — hence the one you can afford to run an order of magnitude slower. Result: 13B on a single GPU (10× PyTorch), 40 TFLOPS/GPU on one V100 for a 10B model vs 30 TFLOPS for the 1.2B largest non-offload model, near-linear to 128 GPUs, 70B+ on one DGX-2 composed with model parallelism. [T1]
  • There are two memory axes, not one, and sharding only addresses the first. Sharding (ZeRO/FSDP) partitions the replicated state — optimizer, gradients, parameters — along the data-parallel axis; it answers "the copy of the state on every GPU won't fit." Tensor (intra-layer) model parallelism answers a different question — "one layer's weights or activations won't fit on a single device" — by splitting each matmul along a model axis. Megatron shows the transformer block can be partitioned so a whole layer costs only two all-reduce collectives forward and two backward (MLP: column-split the first weight so the nonlinearity stays local, row-split the second, one all-reduce; attention: split across heads, one all-reduce on the output projection), reaching 8.3B params on 512 GPUs at 15.1 PetaFLOPs, 76% scaling efficiency. The two are orthogonal and compose (with pipeline parallelism) into 3D parallelism — but tensor parallelism's all-reduce is latency-bound, so it stays efficient only inside a high-bandwidth island (a node's NVLink); practice confines TP within a node and shards/pipelines across nodes. [T1]
  • The ceiling that makes this map necessary is memory, and it arrives early. Distributed data parallel replicates parameters, gradients, and optimizer states on every GPU, so training stops where one device's memory stops — the paper puts that near 1B parameters on a 40GB card and demonstrates DDP failing to wrap T5 above 2.28B. Below that line, sharding buys nothing and costs collectives. [T1]
  • Sharding is a dial, not a switch. FSDP decomposes the model into units, coalesces each unit's parameters into one FlatParameter, all-gathers it just before that unit computes and frees the peer shards immediately after, reduce-scattering gradients instead of all-reducing them. Peak parameter memory becomes O(Σψᵢ/F + max ψᵢ). The sharding factor F runs continuously — F=1 is plain DDP (cheapest communication, no savings), F=W is full sharding (lowest memory, most communication), and hybrid values in between are "a graduating trade-off." FSDP-unit granularity is a second knob in the same currency. [T1]
  • The dial has a knee, and the first two-thirds of it are free. ZeRO decomposes sharding into three cumulative switches with asymmetric communication prices: P_os (optimizer states, 4× memory reduction), P_os+g (+ gradients, 8×), P_os+g+p (+ parameters, N_d×, linear in data-parallel degree). Stages 1 and 2 move the same communication volume as plain data parallelism — they are close to strictly dominant. Stage 3 costs 1.5×. Concretely, a 7.5B model at N_d=64 goes 120 GB → 31.4 → 16.6 → 1.88 GB per device. This is the practitioner's answer to "how far do I turn FSDP's dial": turn on 1 and 2 unconditionally; turn on 3 when you must fit, and know you are paying bandwidth for it. [T1]
  • The waste being removed is 15/16ths of the state, and the arithmetic is simple enough to do yourself. Mixed-precision Adam costs 16Ψ bytes per parameter (2Ψ fp16 params + 2Ψ fp16 grads
    • 4Ψ fp32 params + 4Ψ momentum + 4Ψ variance), all of it replicated per GPU under plain DP. Every reduction factor above follows from that constant — which also means they change with the optimizer, since K=12 is Adam-specific. [T1]
  • Memory in a training job is two pools, not one, and they need different tools. Model states (params/grads/optimizer) are handled by partitioning; residual states (activations, temporary buffers, fragmentation) are handled by ZeRO-R — partitioned activation checkpointing, constant-size fusion buffers so all-reduce temporaries stop scaling with model size, and live defragmentation. The last one encodes a real operational lesson: OOM-from-fragmentation is a distinct failure from OOM-from-size, and they have different fixes. [T1]
  • Removing memory pressure buys throughput, not just capacity. ZeRO reports super-linear speedup from 64→400 GPUs — mechanistic, not anomalous: smaller per-device footprint permits a larger batch, which raises arithmetic intensity. This is why "it fits now" and "it's faster now" arrive together. [T1]
  • This is ZeRO stage 3, and the paper says so. FSDP is explicitly "motivated by the ZeroRedundancyOptimizer (ZeRO) technique from DeepSpeed"; the claimed difference is native co-design with PyTorch's tensor, dispatcher, and CUDA caching-allocator internals — not different sharding math. Treat FSDP and DeepSpeed ZeRO-3 as the same idea with different integration stories until a neutral comparison lands. [T1]
  • The dial has measurably wrong settings in both directions. T5-11B loses 7% per-GPU TFLOPS scaling 8→512 GPUs as communication outruns the available overlap. The CPU rate limiter that buys up to 5× on T5-11B costs 5% on DeepViT-8B and nothing on RegNet-9B, because throttling only helps when a CPU running ahead is actually causing allocator defragmentation. Tuning is workload-specific and the paper says to check num_alloc_retries before enabling it. [T1]
  • Sharded training is not guaranteed mathematically equivalent to local training — the paper's own words. Because the optimizer steps over flattened, evenly-chunked FlatParameters whose layout ignores individual parameter boundaries, anything needing a parameter's unsharded value (weight or gradient norm, hence norm-based clipping), its tensor structure (approximate second-order methods), or global state across parameters is computing over the wrong object. Fixing it is called an open research question. No quality delta is measured, which is exactly what makes it worth flagging: the failure is silent. [T1, unquantified]
  • What the engineering actually buys, in numbers: minGPT-175B at 173/186 TFLOPS per A100 (batch 1/2, ~55–60% of the 312 TFLOPS BF16 peak), linear TFLOPS scaling 128→512 GPUs, on 8–512 A100 80GB with 2Tb/s RoCE. The enabling mechanisms are deferred initialization (build on a meta device, replay init per unit — otherwise materializing the model OOMs before sharding can help), prefetched all-gathers on a separate CUDA stream to overlap communication with compute, and mixed-precision materialization of only the live unit. [T1]

  • 2026-07-25 — ingest of ring-attention-blockwise-near-infinite-context (Liu, Zaharia, Abbeel, UC Berkeley, arXiv 2023 v4, T1): closes the sequence/context parallelism gap this map has named as unsourced at every ingest since coining, and lands the sixth axis — the only one that partitions the dimension all five others are silent about. The organizing question holds: which memory term do you attack? Ring Attention attacks activations, like GPipe, but by partitioning the sequence they are indexed by rather than recomputing them, and the two compose (every experiment here runs full gradient checkpointing as well). The result is that trainable context becomes a cluster property: s on n devices becomes ns, measured at 8× on 8 A100s, 32× on 32, and 512× on TPUv4-1024 (16M tokens) with MFU moving about one point. What makes this the map's most decidable axis is the published precondition — c ≥ F/B, minimum per-host sequence 6c — which you can evaluate on paper before running anything, and which is also the bad news: the identical A100 needs 6.2K per host over NVLink and 149.5K over InfiniBand. Since F/B worsens as accelerators outpace interconnect, this axis gets harder over time on a fixed fabric — the distributed-algorithm analogue of kernel-performance-expires-with-the-gpu-generation. Honest scope for this vault's premise: sequence parallelism is a datacenter technique. Consumer hardware has the worst possible ratio (high single-device FLOPS behind PCIe), so below the threshold the communication stops overlapping entirely rather than partially — a hard floor, not a graceful degradation. Ripples to context-extension (a compute-side answer to long input, plus that map's first non-perplexity retrieval evidence) and transformer-architecture (FlashAttention's tiling, distributed across hosts instead of staged through SRAM). Caveats: no language-modeling quality comparison anywhere — every headline is capacity or MFU; full precision rather than mixed; largest model 30B and GPU results cap at 32 devices; venue-less preprint. See context-length-scales-linearly-with-device-count, overlap-requires-a-block-size-above-the-flops-to-bandwidth-ratio.
  • 2026-07-25 — ingest of zero-infinity-nvme-memory-wall (Rajbhandari, Ruwase, Rasley, Smith, He, Microsoft, SC21, T1): closes ZeRO-Infinity / NVMe as a fourth tier, named as unsourced in this map's open questions since 2026-07-22. The scale headline (32T on 512 V100s, 50× over 3D parallelism) is the least useful part; three other things are not. (a) The efficiency model ait × bw / (ait × bw + peak_tp) is the only in-vault tool for deciding whether to offload rather than how, and its per-class thresholds put activations at under 2 GB/s and optimizer states as high as 1.5 TB/s — inverting the ZeRO-Offload reading this map has carried since 2026-07-22, without contradicting it, since ZeRO-Offload's argument was about the optimizer's compute being batch-independent and this one is about its bandwidth being unhideable. (b) Bandwidth-centric partitioning (allgather over every PCIe link instead of one owner's broadcast) is a 4× win on the slow tier for identical GPU-side volume, and generalizes past offload entirely. (c) Memory-centric tiling — rewrite one oversized linear operator as a sequence of equivalent tiles — is what lets ZeRO-Infinity avoid model parallelism altogether, dissolving the Model State Working Memory pressure that otherwise forces tensor-slicing past 100B and, with it, the code refactoring tensor-parallelism-splits-a-layer-across-gpus demands. Restates this map's memory arithmetic more completely too: mixed-precision Adam is 20 bytes/param in total, of which the 16Ψ the map carries from zero-memory-optimizations is the replicated portion. For the PEFT question the map keeps asking, this sharpens rather than settles: NVMe's win is dominated by the fp32 state LoRA-on-a-4-bit-base does not have, so it should be more moot than CPU offload — but the sub-2 GB/s activation threshold means CPU activation offload is the piece worth stealing, and nobody in-vault has run it. Caveats: V100-era 2021 numbers, peak_tp from a single box, the fourth first-party DeepSpeed/FSDP source here, no PEFT experiment anywhere, weak-scaling superlinearity. See nvme-offload-removes-the-model-scale-ceiling, offload-efficiency-is-a-bandwidth-arithmetic-intensity-problem.
  • 2026-07-25 — inference-side scheduling note from orca-iteration-level-scheduling (T1, primary map local-inference): the pipeline bubble partly dissolves at inference time, for a scheduling reason rather than a partitioning one. GPipe establishes that synchronous pipelining pays O((K−1)/(M+K−1)) and needs M ≥ 4K micro-batches to amortize it (pipeline-parallelism-splits-depth-and-pays-a-bubble). Orca achieves pipeline utilization across inter-layer partitions with no micro-batching at all, because iteration-level scheduling supplies a continuous stream of independent requests — the bubble is filled by the next request instead of the next micro-batch, and the batching-efficiency-vs-bubble tradeoff micro-batching forces simply does not arise. A reminder that this map's cost models are training cost models, and that the serving regime has a different one. See scheduling-at-iteration-granularity-unblocks-generative-serving.
  • 2026-07-24 — ingest of gpipe-micro-batch-pipeline-parallelism (Huang, Cheng, Bapna et al., Google Brain, NeurIPS 2019, T1): closes the pipeline parallelism gap this map has carried at every ingest since coining, and does it in a way that fits the map's organizing question — which memory term do you attack? — rather than merely adding a name. GPipe attacks activations: partition by layer for the parameter share, and re-materialize the intermediate activations for the rest, which is worth 3.9× more parameters on one unchanged accelerator before any distribution happens at all. That makes it genuinely orthogonal to this map's other four axes, all of which fight over parameters, gradients and optimizer states. Two numbers to carry. First, the bubble — O((K−1)/(M+K−1)), negligible at M ≥ 4K — which makes this the one axis whose misconfiguration costs the entire benefit while appearing to work: at M=1, K=8 gives a 1.3× speedup, at M=32 the same partitions give 6.3×. Second, scaling is linear only when layers are uniform — Transformer 282.2M → 83.9B on 128 devices (298×), AmoebaNet 25× and sub-linear — which is a kind result for this vault, since everything it tracks is a uniform-layer transformer. The complementarity with tensor-parallelism-splits-a-layer-across-gpus is exact and stated on both sides: GPipe concedes it "assumes that a single layer fits within the memory requirements of a single accelerator" (Megatron's raison d'être) while surviving on PCIe without NVLink (3.3× at K=8), which Megatron's latency-bound all-reduces cannot. Ripples to peft-methods — activations are the one memory term LoRA does not shrink, so re-materialization is the only technique here that PEFT cannot render moot — and to transformer-architecture, whose stability thread gains a fourth instance (128-layer training required scaling FFN init by depth and clipping logits). Caveats: 2018–2019 TPUv2/v3 and P100 work on a convnet and an encoder-decoder, the fourth first-party parallelism paper here, and the PipeDream comparison is GPipe's own characterization rather than a head-to-head. See pipeline-parallelism-splits-depth-and-pays-a-bubble, rematerialization-trades-compute-for-the-activation-memory-nothing-else-shrinks.
  • 2026-07-22 — ingest of zero-offload-democratizing-billion-scale-training (Ren, Rajbhandari et al., Microsoft/UC Merced, USENIX ATC 2021, T1): closes the gap this map has named at every ingest since coining — CPU offload, "the more useful answer when you have few cards." Adds a fourth axis that is categorically unlike the other three: it does not distribute state across devices, it demotes it down the memory hierarchy, trading PCIe bandwidth and one step of staleness for 10× model size on hardware you already own. Two systems pieces make it survivable — a SIMD/OMP CPU Adam >6× faster than PyTorch's, and one-step delayed parameter update (up to 1.5× end-to-end), whose no-accuracy-cost claim is conditioned on enabling it after a few dozen iterations, since early training is where staleness destabilizes. That conditional disclosure is a better standard than sharded-optimizer-math-is-not-locally-equivalent, which names a semantic break and measures nothing. Cross-map: this is the training-side twin of post-training-quantization's move — spend a cheap resource to avoid a scarce one — and the sibling of QLoRA's 65B-on-one-card (peft-methods), which reaches the same place by shrinking what must be held rather than relocating it. Open questions:

  • The memory-wall comparison has been asking about the wrong term for a PEFT reader (revised 2026-07-25). This map now holds six answers — shard it, split the layer, demote it down the memory hierarchy, route around it with sparsity, recompute it, and partition the sequence — and the first four all attack terms that scale with the number of trainable parameters, which is why the vault suspects offload is the axis PEFT deletes. Activations do not scale that way: the forward activations of a 70B model are the same size whether you update every weight or 0.01% of them. So the two activation-indexed axes — re-materialization and sequence parallelism — are the memory techniques here that PEFT cannot make redundant, and by elimination the ones most likely to bind in the LoRA-on-one-card regime this vault's premise assumes, especially once cheap context extension (context-length-is-a-cheap-post-hoc-edit-not-a-pretraining-property) makes long sequences easy to acquire and expensive to train through. Sequence parallelism, though, is ruled out for this audience by its own precondition (c ≥ F/B, overlap-requires-a-block-size-above-the-flops-to-bandwidth-ratio) — which leaves gradient checkpointing as the single activation lever available on one or two consumer cards, and makes the standing experiment more urgent rather than less. The cheapest useful experiment across this map and peft-methods: peak memory for a 4-bit LoRA fine-tune with and without gradient checkpointing at a realistic sequence length. Nobody in-vault has run it, and it would say whether the multi-axis comparison is even the right question for this audience. Newly adjacent (2026-07-25): ZeRO-Infinity prices activation offload to CPU at under 2 GB/s (offload-efficiency-is-a-bandwidth-arithmetic-intensity-problem), i.e. trivially affordable over PCIe — so the second half of that experiment is "and with activation offload," and it is equally unrun.
  • This map's one source has nothing to say about fine-tuning. Every experiment is generic full-parameter training — no frozen layers, no adapters, no fine-tuning-specific memory profile. How FSDP composes with LoRA on a quantized base (what actually gets sharded when 99.99% of parameters are frozen and 4-bit, and whether sharding is even the right lever there) is the single most decision-relevant untested combination for this vault's premise. Unsourced.
  • NVMe offload: RESOLVED 2026-07-25 (zero-infinity-nvme-memory-wall) — and what replaces it is narrower. The tier question is answered; the contention question is not. That paper's efficiency analysis holds bandwidth infinite for every state class but the one under study, so it prices each in isolation and says nothing about what happens when parameters, optimizer states and activations are all moving over the same PCIe link at once — which is the actual configuration. A neutral FSDP-vs-DeepSpeed comparison also remains unsourced, and this is now the fourth first-party DeepSpeed/FSDP account in-vault with a shared lineage across two of them, so nothing here is a disinterested head-to-head. Still unsourced past NVMe: ZeRO++-class communication compression, and any measurement of offload under a PEFT workload.
  • Does the offload axis survive PEFT — or does PEFT delete it? ZeRO-Offload's entire win is relocating the 12Ψ bytes of fp32 optimizer state. Under LoRA on a 4-bit base there is almost no optimizer state to demote (99.99% of parameters frozen, quantized-bases-preserve-finetune-quality), which suggests offload is the one axis that parameter-efficient fine-tuning renders moot. If that is right it is a genuinely useful negative result for this vault's premise, and nobody has measured it. The optimality argument is also Adam-specific (derived from K=12 optimizer bytes) and does not transfer to a different optimizer.
  • Both sources are vendors grading their own homework. Microsoft's "10× faster than SOTA" is measured against baselines Microsoft configured; Meta's FSDP numbers are Meta's. The direction is consistent across two stacks, which is why the map moved — but no third party has audited either.
  • Does the optimizer non-equivalence bite in practice, and where? The paper states the problem and measures nothing. Which optimizers are affected, whether gradient-clipping behaviour changes a fine-tune's result, and by how much, is unanswered — and it is unanswerable from benchmark scores alone, which is the point.
  • The rest of the parallelism zoo is partly served now — tensor parallelism landed 2026-07-21 (megatron-lm-model-parallelism), the case sharding alone cannot solve, and expert parallelism landed the same day via mixture-of-experts (named by Switch, composed with the other three axes in production by DeepSeekMoE's HAI-LLM). Still unsourced: pipeline parallelism landed 2026-07-24 (gpipe-micro-batch-pipeline-parallelism) in its synchronous, micro-batched form — but its asynchronous branch (PipeDream's 1F1B schedule, weight staleness, versioned parameter copies) is known here only through GPipe's own characterization of a competitor, and the documented friction between per-micro-batch all-gathers and sharding is still unmeasured. Sequence/context parallelism landed 2026-07-25 (ring-attention-blockwise-near-infinite-context) — what remains open there is that it reports no language-modeling quality comparison at all, so "16M tokens are trainable" is a capacity claim with nothing said about whether the resulting model uses the window; and that the in-vault ring result and Megatron's sequence-parallel variant are different constructions nobody has compared. Still unsourced: the 2D/3D combinations as their own subject, plus the practitioner-scale question of which combination to pick on N cards. And the honest gap Megatron leaves: its 76% efficiency is an NVIDIA-on-NVLink number, so how tensor parallelism degrades on commodity interconnect is unsourced — a gap Ring Attention now makes sharper by showing, for a neighbouring axis, that the interconnect can swing the viability threshold by 24×.
  • No source yet on the practitioner-scale question: what actually fits on N cards. The in-vault numbers are 175B on 128–512 A100s; the vault's premise runs on far less.
