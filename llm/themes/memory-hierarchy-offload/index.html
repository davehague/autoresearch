Memory-hierarchy offload (CPU, NVMe, layer streaming) — map

Forked 2026-08-03 (auto run) from distributed-training, which reached the fork condition again (18 dated bullets, 5 declared sub-threads) one night after its first fork. The parent's remaining axes all answer the same question — the state will not fit on one device, so spread it across several. This strand answers the opposite question: what do you do when there are no more devices? Demotion is not distribution. Every other axis on the parent buys capacity with more hardware; this one buys it with slower hardware you already own — host RAM, an NVMe drive, a PCIe link — and is therefore the only axis on that map whose entire premise is a machine the reader already has. The parent itself made the argument at coining: ZeRO-Offload is "the only answer available to someone who cannot add cards." Auto-forked; flagged for David's review. The parent keeps the five distribution axes and links here as a hub.

Status: consolidating Status note (2026-08-03, at forking): consolidating, carried from the parent, and it is the honest grade rather than a generous one. The strand holds two T1 systems papers (ZeRO-Offload, ZeRO-Infinity), two independent T2 maintainer docs (torchtune, Axolotl) that price the host side and expose a PEFT-only axis, and — landing the same night as the fork — a third-party production confirmation from a 2.78T training run that stores sharded gradients in CPU memory and remotely offloads activations. What holds it below consensus is that the two systems papers are the same team at the same company, so the mechanism replicates across a lineage rather than across groups; the tool docs report capability with not one measured number; and the axis's central question for this vault — whether parameter-efficient fine-tuning deletes it — is still unanswered by anyone.

Sub-threads: none — one operation (demote state down a memory hierarchy rather than distribute it across devices) applied to three tiers (CPU, NVMe, and layer streaming) that share one cost model and one binding constraint (link bandwidth against arithmetic intensity) [reviewed 2026-08-03 @ 5 bullets]

What we believe now:

  • Demotion is a distinct axis from distribution, and it is the only one that needs no extra GPUs. Partition mixed-precision Adam training as a data-flow graph under three constraints — orders of magnitude less CPU compute than GPU, minimum CPU↔GPU communication, maximal savings at that volume — and the cut is forced: fp32 optimizer states, fp32 parameters and the Adam step itself go to the CPU (12 of the 16Ψ bytes per parameter, a 4× GPU-memory reduction before any sharding) while fp16 params/grads and forward/backward stay on the GPU, at a communication volume fixed at 2× the parameter count per step regardless of batch or sequence length. It works because of a property of the optimizer, not of CPUs: forward/backward costs O(params × batch × seq) while the Adam step costs O(params), so the optimizer is the one stage whose cost is independent of the batch — hence the one you can afford to run an order of magnitude slower. Measured: 13B on a single GPU (10× PyTorch), 40 TFLOPS/GPU on one V100 for a 10B model against 30 TFLOPS for the largest non-offload model at 1.2B, near-linear to 128 GPUs, 70B+ on one DGX-2 composed with model parallelism. Two systems pieces make it survivable: a SIMD/OMP CPU Adam over 6× faster than PyTorch's, and one-step delayed parameter update worth up to 1.5×, whose no-accuracy-cost claim is explicitly conditioned on enabling it after a few dozen iterations — early training is where staleness destabilizes. That conditional disclosure is a better standard than the parent map's silent optimizer non-equivalence. [T1] See offloading-the-optimizer-demotes-memory-instead-of-distributing-it.
  • There is a third tier, and adding it removes model scale as a constraint entirely. NVMe is over 50× larger than GPU memory on a DGX-2-class node. Running the demotion argument down to it gives 32 trillion parameters on 512 V100s at >25 petaFLOPS (40% of peak) and 1T fine-tuned on a single node with no model parallelism, where 3D parallelism stops around 20B. The number that matters more than the headline: at 500B, where both approaches still fit, offload and 3D parallelism are within a point of each other (46 vs 47 TFLOPS/GPU) — so this is not a penalty you accept for lack of hardware, it is a comparable operating point. Two enabling tricks generalize past offload. Bandwidth-centric partitioning replaces one owner's broadcast with an allgather across every data-parallel rank: identical GPU-side volume, but every PCIe link active at once, lifting CPU→GPU from ~12 GB/s to 48 and NVMe to 25, linear in node count. And memory-centric tiling rewrites one oversized linear operator as a sequence of equivalent tiles, which is what lets the system avoid model parallelism altogether and, with it, the code refactoring tensor-slicing demands. [T1] See nvme-offload-removes-the-model-scale-ceiling.
  • Whether to offload is arithmetic you can do on paper, and the answer inverts the intuition. efficiency = ait·bw/(ait·bw + peak_tp), where ait is a state class's arithmetic intensity. Fix a target efficiency and each class yields a very different required bandwidth: parameters and gradients ~70 GB/s, optimizer states up to ~1.5 TB/s, and activation checkpoints under 2 GB/s. So activations are the cheapest thing to demote and the optimizer the most expensive — the inverse of the ZeRO-Offload reading, and both are right about different resources: that argument is about the optimizer's compute being batch-independent, this one about its bandwidth being unhideable, since the optimizer step cannot overlap with compute. The practical consequence for this vault: CPU activation offload is trivially affordable over PCIe and is the piece worth stealing, and it is the piece nobody in-vault has run. [T1] See offload-efficiency-is-a-bandwidth-arithmetic-intensity-problem.
  • The host side is priced, and on a desktop it is the binding constraint. From the vault's first official tool documentation: CPUOffloadOptimizer costs 4× the model size in system RAM and forces gradient_accumulation_steps=1. On a 32–64 GB desktop an 8B model's offloaded state alone is ~32 GB — so the technique that makes the model fit simultaneously removes the mechanism that made a batch-size-1 run tolerable. Axolotl's activation_offloading: disk also puts storage into the training-memory hierarchy inside a single-GPU tool, motivated explicitly by long context, moving down-market a tier this vault had filed as datacenter-only. [T2, two independent tool docs] See cpu-optimizer-offload-costs-four-times-the-model-in-host-ram.
  • PEFT does not only delete memory axes — it opens one, and this is where it lives. The parent map's organizing inference is that axes attacking trainable-parameter-scaled terms are the ones parameter-efficient fine-tuning renders moot. Axolotl's layer_offloading is the case that argument has no slot for: it streams frozen decoder-layer parameters between CPU and GPU one layer at a time, documented as "best suited for LoRA/QLoRA where most parameters are frozen." A full fine-tune has no frozen weights to stream. So shrinking the trainable set turns the resident base into a large, read-only, sequentially accessed object — the friendliest possible pattern for a prefetcher — and creates a lever on the model term rather than the activation term. Whether it is affordable is exactly the efficiency formula's question, unanswered by the doc. This map's prediction: naive streaming is bandwidth-bound at batch size 1, and the winning implementation will look like the MoE expert-offload literature — cache plus prefetch one layer ahead — except easier, because a dense stack's access order is deterministic where a router's is not. [T2] See frozen-weights-can-be-streamed-which-is-a-peft-only-memory-axis.

Through-line (newest first):

  • 2026-08-03 — forked from distributed-training (auto run, flagged), and confirmed in production the same night. The parent hit the fork condition a second time — 18 dated bullets, 5 declared sub-threads — and strand (4) was the separable one for a reason its own coining bullet states: every other axis there answers "spread the state across more devices," while this one answers "there are no more devices." The strand carries five dated entries (2026-07-22 ZeRO-Offload, 2026-07-25 ZeRO-Infinity and the efficiency formula, 2026-07-29 the tool docs' host-side price and the PEFT-only streaming axis) and their concept notes, at consolidating — the parent's status, because the convergence that earned it is substantially inside this strand. Landing with the fork: kimi-k3-open-frontier-intelligence (T1) is the first third-party, non-DeepSpeed confirmation this map has, from a 2.78-trillion-parameter production run. It stores sharded gradients in CPU memory to cut GPU usage while keeping the double gradient buffer on the GPU, and remotely offloads activations to the memory of other pipeline-parallel ranks to balance the 1F1B skew that otherwise OOMs the early stages. Two things that adds. It is the map's first source offloading to a peer accelerator's memory rather than down to host RAM or storage — a tier between GPU and CPU that the efficiency formula covers but no in-vault source had used, and one that changes the arithmetic (a peer's HBM over a fast fabric has far better bandwidth than PCIe to a host). And it composes demotion with block-wise FP8 activation quantization, so the bytes being moved are compressed first — which is the obvious composition this map has never seen measured and which makes the sub-2 GB/s activation threshold even easier to clear. Caveat: no ablation, no before/after numbers, and it is a vendor report of a training run nobody can reproduce.
  • 2026-07-29 — the host side gets priced, and a fifth memory axis appears that this vault's premise specifically enables. From torchtune-memory-optimization-overview and axolotl-gradient-checkpointing-offloading (T2, two unrelated maintainer teams): CPUOffloadOptimizer at 4× the model in system RAM plus a forced gradient_accumulation_steps=1 is a real ceiling on a 32–64 GB desktop and strengthens the suspicion that offload is the axis PEFT renders moot — while layer_offloading on frozen decoder layers is an axis PEFT creates, on the model term, that a full fine-tune cannot have. The hard caveat on both: not one measured peak-memory figure, step time, model or GPU on either page. These are capability inventories, and they raise confidence about what is possible and what is mutually exclusive while adding nothing about magnitude.
  • 2026-07-25 — ingest of zero-infinity-nvme-memory-wall (Microsoft, SC21, T1): the third tier, and the efficiency formula, which is the only in-vault tool for deciding whether to offload rather than how. Its per-class thresholds invert the intuition — activations under 2 GB/s, optimizer states up to 1.5 TB/s — without contradicting the earlier reading, because the two arguments are about compute-independence and bandwidth demand respectively. Plus bandwidth-centric partitioning (12 → 48 GB/s for identical GPU-side volume) and memory-centric tiling, which is what removes the need for model parallelism at all. Caveats: V100-era 2021 numbers, peak_tp from a single box, no PEFT experiment anywhere, weak-scaling superlinearity.
  • 2026-07-22 — coining ingest for this strand, zero-offload-democratizing-billion-scale-training (Microsoft / UC Merced, USENIX ATC 2021, T1): the axis that is categorically unlike the parent map's others — it does not distribute state across devices, it demotes it, trading PCIe bandwidth and one step of staleness for 10× model size on hardware you already own. Cross-map at the time and still the right framing: this is the training-side twin of post-training-quantization's move — spend a cheap resource to avoid a scarce one — and the sibling of QLoRA's 65B-on-one-card in peft-methods, which reaches the same place by shrinking what must be held rather than relocating it.

Open questions:

  • Does this axis survive PEFT, or does PEFT delete it? The carried-over question and still the sharpest one on the map. ZeRO-Offload's entire win is relocating the 12Ψ bytes of fp32 optimizer state; under LoRA on a 4-bit base there is almost no optimizer state to demote (quantized-bases-preserve-finetune-quality), which suggests this is the one axis parameter- efficient fine-tuning renders moot. Against that, the tool docs supply two counter-pressures that did not exist when the question was posed: activation offload is cheap and PEFT does not shrink activations, and layer_offloading is an axis PEFT creates. So the question has become three-part — does the optimizer tier die, does the activation tier survive, and is the new model-term tier affordable — and nobody has measured any of the three. The optimality argument is also Adam-specific (derived from K=12 optimizer bytes) and does not transfer to a different optimizer.
  • The contention question, which every source ducks by construction. The efficiency analysis holds bandwidth infinite for every state class but the one under study, so it prices each in isolation and says nothing about parameters, optimizer states and activations all moving over the same PCIe link at once — which is the actual configuration on the machine this map is written for. The 2026-08-03 production confirmation does not help here either: it moves gradients to host RAM and activations to peer HBM, i.e. it avoids the contention by using two different links rather than measuring it.
  • Layer streaming has no published number anywhere. layer_offloading ships, is documented as a PEFT-oriented feature, and has no measured step time, peak memory or bandwidth utilization in any source in-vault. Given that this is the axis PEFT uniquely enables and that the streamed object is the 4-bit base every reader of this vault already holds, the cheapest useful run on this map is: step time and peak VRAM for a 4-bit LoRA fine-tune with layer_offloading on and off, at two sequence lengths, on one consumer card. Nothing about it requires a cluster.
  • The lineage problem. Both systems papers are Microsoft DeepSpeed, and the parent map counted four first-party DeepSpeed/FSDP accounts in total. What replicates here is one team's engineering across two publications, not two independent derivations, and no third party has audited either. The 2026-08-03 arrival is the first outside confirmation and it is a usage report, not a comparison.
  • Peer-accelerator offload is a tier with no cost model. Remote-offloading activations to another pipeline rank's memory sits between GPU and CPU in the hierarchy, and the efficiency formula covers it in principle — plug in the fabric's bandwidth — but no source has evaluated it as a choice against host RAM. On a two-card desktop over PCIe rather than NVLink, whether the peer's memory is worth reaching for instead of the host's is exactly the kind of question this map should be able to answer from the formula and cannot, because peak_tp and the effective link bandwidth for a consumer pair are unmeasured.
