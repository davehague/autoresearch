Memory-hierarchy offload (CPU, NVMe, layer streaming) — map

Forked 2026-08-03 (auto run) from distributed-training, which reached the fork condition again (18 dated bullets, 5 declared sub-threads) one night after its first fork. The parent's remaining axes all answer the same question — the state will not fit on one device, so spread it across several. This strand answers the opposite question: what do you do when there are no more devices? Demotion is not distribution. Every other axis on the parent buys capacity with more hardware; this one buys it with slower hardware you already own — host RAM, an NVMe drive, a PCIe link — and is therefore the only axis on that map whose entire premise is a machine the reader already has. The parent itself made the argument at coining: ZeRO-Offload is "the only answer available to someone who cannot add cards." Auto-forked; flagged for David's review. The parent keeps the five distribution axes and links here as a hub.

Status: consolidating Status note (2026-08-17): holds consolidating, and the map's 2026-07-29 prediction arrives — carrying a term its decision instrument does not have. That prediction was that layer streaming's winning implementation "will look like the MoE expert-offload literature — cache plus prefetch one layer ahead." apex-adaptive-expert-prefetching-edge-moe (T1, Wisconsin–Madison, ESWEEK/CODES 2026 → IEEE TCAD; four MoE models 1B–16B) is that literature's current state of the art and corrects the prediction twice. Coverage, not accuracy: a fixed top-k predictor at 70–85% average overlap is insufficient because per-layer overlap dips to ~79% on specific layers and one stalling layer costs the whole token, so the fix is a per-token adaptive over-fetch of top-(k + δ̂(x)) sized by a learned confidence model — >99% overlap, 26% lower per-token latency and 16–28% better energy-delay product than the fixed-k baseline. The extra budget varies 6× across models at one threshold (4.17 on Granite-1B, 0.67 on Phi-7B), which is the second independent instance in this vault of size the budget from the model's own statistics, never borrow a swept one. And waiting has a price this map's formula omits. efficiency = ait·bw/(ait·bw + peak_tp) compares transfer time against compute time and is silent about a stalled package. Here the intervention raises off-chip I/O energy (48 → 56 mJ) and reduces total energy anyway (340 → 299 mJ) because idle and leakage fall 57 → 8 mJ. Seventeen percent of baseline energy was being spent doing nothing, and on a laptop or a phone that is exactly the cost a wall-clock benchmark hides and a battery does not. The transfer term is real and bounds the trick from the other side: static over-prefetch is the worst configuration measured, I/O energy to 97 mJ and total to 377 mJ, because hiding δ requires δ·S_expert/B_eff + T_queue ≤ T_attn — the attention window is a hard ceiling, and past it the prefetch traffic becomes the bottleneck it was hiding. Status does not move, for one reason that overrides the peer review: nothing here was measured on a machine. The compute arrays are RTL-synthesized in TSMC 28 nm and characterized with PrimeTime, memory timing comes from Ramulator, the system runs in a cycle-accurate co-simulator against GPU-collected traces, and the platform is modeled as comparable to an RTX 3090. The authors state there is no hardware prototype. Simulation is the only instrument that can isolate idle leakage, so the mechanism is credible and the magnitudes describe a machine nobody can buy — which is local-inference's standing rule arriving from a new direction, with a corollary: a simulated result is a mechanism claim; its magnitudes are conditional on hardware that may never exist. One edge out, to mixture-of-experts: tolerance for inexact routing scales with k, so a k=2 model loses 4.2 average points to expert substitution where k=8 models lose 0.5. Status note (2026-08-03, at forking): consolidating, carried from the parent, and it is the honest grade rather than a generous one. The strand holds two T1 systems papers (ZeRO-Offload, ZeRO-Infinity), two independent T2 maintainer docs (torchtune, Axolotl) that price the host side and expose a PEFT-only axis, and — landing the same night as the fork — a third-party production confirmation from a 2.78T training run that stores sharded gradients in CPU memory and remotely offloads activations.   • The hierarchy this map already tracks (CPU, NVMe, layer streaming) gets a fourth rung, and this time it ships as a managed production feature rather than a research prototype (new 2026-08-31). vLLM v0.28.0 adds disk as a formal, managed KV-cache offload tier — out-of-tree secondary-tier managers, partial-load results when a demoted block can't be fully retrieved in time, dedicated tiering metrics. [T2] (vllm-adds-a-disk-tier-to-managed-kv-cache-offloading)
  • When the model genuinely will not fit, the weights the next token needs are mostly the weights you already have — and a runtime built on that difference converts an unusable configuration into a slow one (new 2026-08-28). Across autoregressive decode, 82–85% of a sparse layer's active MLP rows persist from one token to the next, so the per-token storage job is the delta, not the active set. Measured on a Jetson AGX Orin (32 GiB unified LPDDR5, Samsung 990 PRO NVMe) with Mistral-7B FP16 at 13.49 GiB and system memory capped to leave 9.0–14.8 GiB to CUDA: llama.cpp under memory-mapped demand paging sustains 0.2–0.3 tok/s with 11,453 major page faults/s, 77% CPU iowait and 3% GPU utilization; predictive delta prefetching reaches 1.7 → 3.7 tok/s (7.9–12.0×, and 3.22 vs 0.34 at a 14 GiB cap) with faults at 0.21/s, iowait at 4% and the GPU at 30%. Per-token NVMe reads run 103 MiB to just under 1 GiB against a 13.49 GiB footprint. Three riders keep this honest. The predictor is 2.86% of the base model, resident, and netted out, and picks the right centroid for ~99% of layer decisions. The dense/sparse split is a cliff, not a ceiling — past the optimum prefix length throughput drops 1.60 → 0.98 tok/s in one step, the map's second such cliff. And the technique retires at the crossover: once the model fits, llama.cpp reaches 5.9–7.7 tok/s and the advantage collapses to 1.1–1.2×. Quality is the memory dial too — at a 20-layer dense prefix, Mistral-7B keeps 95–96% of dense HellaSwag and Llama-3-8B 92–93%. Everything is FP16, so this regime is entered on this board by declining to quantize; the 4-bit composition is untested. [T1, ICPP 2026, code released — one board, two models, no seeds] (active-mlp-rows-persist-across-tokens-so-only-the-delta-must-be-fetched)
  • The bottleneck does not move when the traffic falls, so in this regime bytes-over-the-link is the whole cost model (new 2026-08-28). After an order-of-magnitude reduction in per-token storage traffic, NVMe I/O is still 80–87% of per-token latency at every memory level measured; GPU compute and the predictor are both secondary, and the paper says outright that optimizing computation alone "would have limited effect." Absolute latency runs 593 ms/token at the tightest budget to 113 ms at the loosest. The practitioner form is the same one this map's efficiency formula implies and a profile confirms: decompose the latency before optimizing anything — in the demotion regime you can predict the answer from bandwidth and bytes, and the engineering buys a constant factor on the bytes rather than an escape from the model. [T1] (storage-backed-decode-stays-io-bound-after-the-fix)
  • The concurrency remedy for a slow tier has a cliff, not a ceiling, and past it you are worse off than at batch one (new 2026-08-23). offload-efficiency-is-a-bandwidth-arithmetic-intensity-problem gives the formula and its remedy: raise arithmetic intensity so the link is hidden, which in serving means batch concurrent streams so one sweep of the slow tier amortizes. Measured on an RTX 3070 (8 GB) serving Qwen3-235B-A22B at Q4_K_M (134 GB) off an NVMe running ~2.4 GB/s against VRAM's ~448 GB/s — a 180× cliff — throughput goes 0.128 tok/s at B=1 → 0.189 at B=8 → 0.087 at B=32, a 47% regression past eight streams from OS paging thrash. The supported claim is a scope condition on an implementation (llama.cpp could not sustain concurrency above roughly B≈8 here), not a law; the amortization theory is sound and the runtime is what fails. The operational consequence is sharp anyway: tuning batch size upward until throughput stops improving walks past the optimum into a regime worse than serial. The single-stream number is the other thing to keep — 0.44 tok/s warm, matching a pure bytes-per-token ÷ bandwidth model, which is the honest floor to quote for a 235B sparse model on one 8 GB card and is roughly two orders of magnitude below reading speed. nvme-offload-removes-the-model-scale-ceiling is true; this is the bill. [T1, single-study, RTX 3070 + NVMe] batching-an-ssd-offloaded-moe-goes-backwards-past-eight-streams
  • Overlap has two payoffs and the map's cost formula prices only one: a stalled package burns static power, so fetching more data can lower total energy (new 2026-08-17). The decision instrument here has been efficiency = ait·bw/(ait·bw + peak_tp) — transfer time against compute time. It has no term for what the hardware does when the transfer fails to hide. Measured on an edge MoE decode where expert loading is 43% of latency and 29% of energy: adaptive prefetching raises off-chip I/O energy 48 → 56 mJ and cuts idle/leakage 57 → 8 mJ, netting 340 → 299 mJ. Seventeen percent of the baseline's energy was idle dissipation. The bound on the trick is the same formula written for a discrete budget — hiding δ extra fetches needs δ·S_expert/B_eff + T_queue ≤ T_attn — and past that ceiling static over-prefetch is the worst policy measured (I/O 97 mJ, total 377 mJ, worse than no prefetching). Practitioner form: prefetch adaptively, size the budget from the model's own statistics, stop at the compute window — and put an idle-power term in any offload accounting done for a battery-powered machine. [T1, fully simulated] See waiting-costs-static-power-so-overlap-pays-even-when-traffic-grows, expert-prefetching-is-governed-by-the-worst-layer-not-the-average.
  • Demotion is a distinct axis from distribution, and it is the only one that needs no extra GPUs. Partition mixed-precision Adam training as a data-flow graph under three constraints — orders of magnitude less CPU compute than GPU, minimum CPU↔GPU communication, maximal savings at that volume — and the cut is forced: fp32 optimizer states, fp32 parameters and the Adam step itself go to the CPU (12 of the 16Ψ bytes per parameter, a 4× GPU-memory reduction before any sharding) while fp16 params/grads and forward/backward stay on the GPU, at a communication volume fixed at 2× the parameter count per step regardless of batch or sequence length. It works because of a property of the optimizer, not of CPUs: forward/backward costs O(params × batch × seq) while the Adam step costs O(params), so the optimizer is the one stage whose cost is independent of the batch — hence the one you can afford to run an order of magnitude slower. Measured: 13B on a single GPU (10× PyTorch), 40 TFLOPS/GPU on one V100 for a 10B model against 30 TFLOPS for the largest non-offload model at 1.2B, near-linear to 128 GPUs, 70B+ on one DGX-2 composed with model parallelism. Two systems pieces make it survivable: a SIMD/OMP CPU Adam over 6× faster than PyTorch's, and one-step delayed parameter update worth up to 1.5×, whose no-accuracy-cost claim is explicitly conditioned on enabling it after a few dozen iterations — early training is where staleness destabilizes. That conditional disclosure is a better standard than the parent map's silent optimizer non-equivalence. [T1] See offloading-the-optimizer-demotes-memory-instead-of-distributing-it.
  • There is a third tier, and adding it removes model scale as a constraint entirely. NVMe is over 50× larger than GPU memory on a DGX-2-class node. Running the demotion argument down to it gives 32 trillion parameters on 512 V100s at >25 petaFLOPS (40% of peak) and 1T fine-tuned on a single node with no model parallelism, where 3D parallelism stops around 20B. The number that matters more than the headline: at 500B, where both approaches still fit, offload and 3D parallelism are within a point of each other (46 vs 47 TFLOPS/GPU) — so this is not a penalty you accept for lack of hardware, it is a comparable operating point. Two enabling tricks generalize past offload. Bandwidth-centric partitioning replaces one owner's broadcast with an allgather across every data-parallel rank: identical GPU-side volume, but every PCIe link active at once, lifting CPU→GPU from ~12 GB/s to 48 and NVMe to 25, linear in node count. And memory-centric tiling rewrites one oversized linear operator as a sequence of equivalent tiles, which is what lets the system avoid model parallelism altogether and, with it, the code refactoring tensor-slicing demands. [T1] See nvme-offload-removes-the-model-scale-ceiling.
  • Whether to offload is arithmetic you can do on paper, and the answer inverts the intuition. efficiency = ait·bw/(ait·bw + peak_tp), where ait is a state class's arithmetic intensity. Fix a target efficiency and each class yields a very different required bandwidth: parameters and gradients ~70 GB/s, optimizer states up to ~1.5 TB/s, and activation checkpoints under 2 GB/s. So activations are the cheapest thing to demote and the optimizer the most expensive — the inverse of the ZeRO-Offload reading, and both are right about different resources: that argument is about the optimizer's compute being batch-independent, this one about its bandwidth being unhideable, since the optimizer step cannot overlap with compute. The practical consequence for this vault: CPU activation offload is trivially affordable over PCIe and is the piece worth stealing, and it is the piece nobody in-vault has run. [T1] See offload-efficiency-is-a-bandwidth-arithmetic-intensity-problem.
  • The host side is priced, and on a desktop it is the binding constraint. From the vault's first official tool documentation: CPUOffloadOptimizer costs 4× the model size in system RAM and forces gradient_accumulation_steps=1. On a 32–64 GB desktop an 8B model's offloaded state alone is ~32 GB — so the technique that makes the model fit simultaneously removes the mechanism that made a batch-size-1 run tolerable. Axolotl's activation_offloading: disk also puts storage into the training-memory hierarchy inside a single-GPU tool, motivated explicitly by long context, moving down-market a tier this vault had filed as datacenter-only. [T2, two independent tool docs] See cpu-optimizer-offload-costs-four-times-the-model-in-host-ram.
  • PEFT does not only delete memory axes — it opens one, and this is where it lives. The parent map's organizing inference is that axes attacking trainable-parameter-scaled terms are the ones parameter-efficient fine-tuning renders moot. Axolotl's layer_offloading is the case that argument has no slot for: it streams frozen decoder-layer parameters between CPU and GPU one layer at a time, documented as "best suited for LoRA/QLoRA where most parameters are frozen." A full fine-tune has no frozen weights to stream. So shrinking the trainable set turns the resident base into a large, read-only, sequentially accessed object — the friendliest possible pattern for a prefetcher — and creates a lever on the model term rather than the activation term. Whether it is affordable is exactly the efficiency formula's question, unanswered by the doc. This map's prediction: naive streaming is bandwidth-bound at batch size 1, and the winning implementation will look like the MoE expert-offload literature — cache plus prefetch one layer ahead — except easier, because a dense stack's access order is deterministic where a router's is not. [T2] See frozen-weights-can-be-streamed-which-is-a-peft-only-memory-axis.

Every entry here treats more resident state as unambiguously better — a resident expert is one you do not fetch — and models the binding constraint as link bandwidth against arithmetic intensity. Two machines show that the offload cache and the operating system's page cache compete for one pool of RAM, and the page cache is what makes the backing-store reads fast. Past a knee, growing the cache trades a cheap hit for an expensive miss: on a 64 GB M1 Max serving a 284B MoE from SSD the knee is at a 26–28 GB expert-cache budget, and on a 125 GB i9 a 90 GiB budget decodes at 1.87 tok/s against roughly 2.2 at 24 GiB. Past the knee, reducing the budget is faster. The second contribution is a format property this map should carry as a design rule rather than as a result: making the quantized block identical on disk, in the cache slab and at the kernel's input turns a per-projection miss into a single contiguous read with no transcode, which is what converts a −10.6% bits-per-weight saving into −10.6% bytes read and +10.8% more experts pinned in the same RAM. Read with a-packed-expert-pool-turns-a-cache-miss-into-a-copy, which established the same principle one tier up (GPU, pinned host memory), the pair says the packing should be pushed as far down the hierarchy as the artifact goes — including the file. Status holds consolidating. Open questions:

  • Does the idle-power term change any of this map's existing verdicts? (new 2026-08-17.) The efficiency formula priced three state classes by required bandwidth — activation checkpoints under 2 GB/s, parameters and gradients ~70, optimizer states up to 1.5 TB/s — and concluded activations are the cheapest thing to demote. Every one of those thresholds was derived from time, with no term for the static power dissipated while the transfer fails to hide. If idle dissipation is 17% of total energy in the one system that has measured it, then the classes the formula rules out on bandwidth grounds may be affordable on energy grounds once overlap is added, and the ordering could change. Nobody has re-derived the formula with a leakage term, and it is a paper-and-pencil exercise before it is an experiment.
  • Is the 6× spread in prefetch budget predictable from the architecture? (new 2026-08-17.) The adaptive extra-fetch budget runs 0.67 to 4.17 experts across four models at one confidence threshold, and the map now holds two independent findings that MoE budgets do not transfer between models. Whether the right budget is readable from N, k and the router's entropy — the way head-function-is-readable-from-the-frozen-query-key-spectrum reads head function off frozen weights — or has to be measured per checkpoint decides whether this is a technique or a per-model engineering project.
  • Does this axis survive PEFT, or does PEFT delete it? The carried-over question and still the sharpest one on the map. ZeRO-Offload's entire win is relocating the 12Ψ bytes of fp32 optimizer state; under LoRA on a 4-bit base there is almost no optimizer state to demote (quantized-bases-preserve-finetune-quality), which suggests this is the one axis parameter- efficient fine-tuning renders moot. Against that, the tool docs supply two counter-pressures that did not exist when the question was posed: activation offload is cheap and PEFT does not shrink activations, and layer_offloading is an axis PEFT creates. So the question has become three-part — does the optimizer tier die, does the activation tier survive, and is the new model-term tier affordable — and nobody has measured any of the three. The optimality argument is also Adam-specific (derived from K=12 optimizer bytes) and does not transfer to a different optimizer.
  • The contention question, which every source ducks by construction. The efficiency analysis holds bandwidth infinite for every state class but the one under study, so it prices each in isolation and says nothing about parameters, optimizer states and activations all moving over the same PCIe link at once — which is the actual configuration on the machine this map is written for. The 2026-08-03 production confirmation does not help here either: it moves gradients to host RAM and activations to peer HBM, i.e. it avoids the contention by using two different links rather than measuring it.
  • Layer streaming has no published number anywhere. layer_offloading ships, is documented as a PEFT-oriented feature, and has no measured step time, peak memory or bandwidth utilization in any source in-vault. Given that this is the axis PEFT uniquely enables and that the streamed object is the 4-bit base every reader of this vault already holds, the cheapest useful run on this map is: step time and peak VRAM for a 4-bit LoRA fine-tune with layer_offloading on and off, at two sequence lengths, on one consumer card. Nothing about it requires a cluster.
  • The lineage problem. Both systems papers are Microsoft DeepSpeed, and the parent map counted four first-party DeepSpeed/FSDP accounts in total. What replicates here is one team's engineering across two publications, not two independent derivations, and no third party has audited either. The 2026-08-03 arrival is the first outside confirmation and it is a usage report, not a comparison.
  • Peer-accelerator offload is a tier with no cost model. Remote-offloading activations to another pipeline rank's memory sits between GPU and CPU in the hierarchy, and the efficiency formula covers it in principle — plug in the fabric's bandwidth — but no source has evaluated it as a choice against host RAM. On a two-card desktop over PCIe rather than NVLink, whether the peer's memory is worth reaching for instead of the host's is exactly the kind of question this map should be able to answer from the formula and cannot, because peak_tp and the effective link bandwidth for a consumer pair are unmeasured.
