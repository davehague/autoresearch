Local inference (formats, runtimes, on-device) — map

Coined 2026-07-16 during the seed ingest — first evidence in the "run it locally" half of the craft question. Format and kernel halves covered at seed; the runtime half started filling the same day from the GPU-serving side (vLLM); llama.cpp/Ollama as systems remain the open gap.

Status: emerging Status note (2026-07-22): this map gained a strong T1 this run (speculative-decoding-fast-inference) and deliberately did not move. Under highest-tier-wins it is not a shortage of T1s holding this map at emerging — it has five — it is that the half the map is named for is still unsourced: llama.cpp/Ollama as systems, the GGUF quant ladder measured, and any number taken on consumer or Apple silicon. Every mechanism in this map was measured on a datacenter GPU or a TPU, and the map's own rule says a throughput figure is a claim about a kernel, a card, a precision, and now a batch size. Speculative decoding is the closest fit yet — batch size 1, latency-bound, single stream — and it is still a TPU-v4 result on an 11B encoder-decoder. The status moves when someone measures the local stack, not when the vault adds another datacenter mechanism.

What we believe now:

  • Local distribution standardized on a self-describing single file. GGUF: typed key-value metadata (extensible without breaking changes), mmap loading, parseable without external libraries — built because its predecessors couldn't identify their own architecture. Its quant menu (Q4_0…Q8_0, K-quants Q2_K–Q8_K, IQ series, MXFP4) is the concrete precision-vs-quality dial local users actually turn. [T2]
  • 4-bit weights are an edge enabler, not just a VRAM discount. Generation is memory-bandwidth-bound, so 4× smaller weights are a throughput win — when kernels built for the packed format collect it: TinyChat shows >3× over HuggingFace FP16 and 70B-class models on mobile GPUs. Format and runtime are one decision, not two. [T1]
  • Practical shape of the pipeline, therefore: fine-tune → merge the adapter → convert to GGUF at a chosen quant level → run on llama.cpp/Ollama — one conversion command, because the format is self-describing. [T2]
  • Serving throughput is a memory-management problem. The KV cache — growing with context and concurrency, not model size alone — is what fills the card once weights are quantized; paging it like OS virtual memory (PagedAttention) reaches near-zero cache waste and 2–4× throughput at equal latency vs prior systems. The deploy fork is concrete: vLLM for concurrent GPU serving (mostly not GGUF), llama.cpp/Ollama for single-user on-device — runtime choice and quant-format choice are one decision, now confirmed from both sides. [T1]
  • One lever in this map costs no quality at all, and it is the only one. Every other technique here — 4-bit weights, 2-bit KV, the GGUF quant ladder — buys speed by spending accuracy, and pricing that loss is this map's job. Speculative decoding is the exception: a small draft model proposes γ tokens, the target scores all γ+1 in one parallel pass, and a modified rejection rule (accept with min(1, p/q), resample the first rejection from norm(max(0, p−q))) makes the output provably identical in distribution to ordinary decoding. It spends arithmetic and a second model's memory instead — which is affordable precisely because decode is bandwidth-bound and the ALUs are idle. 2.8–3.4× at batch size 1 on T5-XXL (TPU-v4). The counter-intuitive tuning rule: the best draft is a deliberately weak one — T5-large agrees with the target most often (α=0.82) and is the slowest option (1.7×) because its cost eats the winnings, while T5-small (α=0.75) gives 3.4×. Use this as the map's yardstick: ask any claimed speedup what currency it spends, and note that this one spends the cheapest. [T1]

Through-line (newest first):

  • 2026-07-22 — ingest of speculative-decoding-fast-inference (Leviathan, Kalman & Matias, Google Research, ICML 2023 Oral, T1): closes the "the serving field's later moves — speculative decoding/prefix caching/continuous batching — are not in-vault" gap this map opened at the vLLM ingest. Two properties make it unusual here. It is the only quality-free lever in the map (exact distribution, by construction — there is no eval to discount and no knob to tune), and it is measured at batch size 1, the single-user latency regime that is this map's actual objective and the one place paged-kv-cache-unlocks-throughput's batched wins do not apply. The two are complementary: paging manages KV placement under concurrency, speculation attacks serial depth for one stream. It also takes attention-is-memory-bound-not-compute-bound constructively — the other sources in that thread treat memory-boundness as a constraint to route around; this one treats it as a budget to spend. Ripple to distillation-small-models: a distilled student has a second use where its quality gap is priced automatically — agree with your teacher 75% of the time and you are a 3× accelerator for the teacher, with disagreement costing latency rather than correctness. Did not tip this map's status; see the status note below. See speculation-trades-arithmetic-for-latency-without-moving-the-distribution.
  • 2026-07-22 — edge-hardware edge from qwen25-vl-technical-report (T2, primary map vision-language-models): the first in-vault model sized for the edge half of the multi-modal group — Qwen2.5-VL-3B at DocVQA 93.9 / MMMU 53.1, open weights. Its encoder uses window attention in all but 4 layers to make vision cost linear rather than quadratic in patch count, which is the same play as GQA (sharing-kv-heads-buys-decode-speed-at-near-zero-quality-cost): buy back a cost curve with an architectural restriction rather than a kernel. Still unanswered here — what the GGUF/llama.cpp path does with a vision tower, and whether native-dynamic-resolution token counts (which vary per image) interact badly with a paged or preallocated KV cache. See the-vision-encoder-is-a-design-choice-not-a-frozen-import.
  • 2026-07-21 — interaction edge from the new mixture-of-experts: MoE inverts this map's budget — compute like the active count, RAM like the total count. Mixtral's own accounting (mixtral-of-experts, T1): 13B-active compute and latency, 47B-parameter serving memory, plus routing overhead — "more suitable for batched workloads," which is precisely what single-user local serving is not. Since today's strongest open weights are MoE, this map's weights-then-KV memory hierarchy needs a third line item: which experts are resident. Two graded data points exist — DeepSeekMoE 16B (≈LLaMA2-7B quality, ~2.8B active) runs on one 40GB GPU unquantized (deepseekmoe-expert-specialization, T1), and measured route locality (consecutive tokens repeat experts ~28% vs 12.5% random at depth) is the fact an expert offload/cache would exploit. What llama.cpp/Ollama actually do with routed FFNs on consumer hardware: unserved, now flagged in both maps. See moe-buys-dense-quality-at-a-fraction-of-active-params, experts-specialize-by-syntax-not-semantics.
  • 2026-07-20 — advisory edge from flashattention-3-asynchrony-low-precision (T1, primary map transformer-architecture): the expiry warning added here 2026-07-19 is now a measurement, and the stamp grows a third field. The A100-tuned FA2 kernel reaches only 35% of an H100; a Hopper-native rebuild restores 75% (740 TFLOPs/s FP16) and hits ~1.2 PFLOPs/s at FP8. Every throughput number in this map should now be read as carrying a kernel, a card, and a precision — FP8 attention is a real serving option on Hopper, and none of this map's in-vault figures were measured with it. Practical caution for the local/edge half: these are datacenter-GPU results, and consumer/Apple-silicon runtimes (local-inference's actual target) get none of this for free. See kernel-performance-expires-with-the-gpu-generation.
  • 2026-07-20 — interaction edge from yarn-context-window-extension (T1, primary map context-extension): the cheapest capability upgrade in the vault is also the one that breaks this map's memory budget. Extending a checkpoint to 128k costs a brief fine-tune — and multiplies the KV cache by the same factor the window grew. This map holds three levers on that budget (GQA architecture, KV precision, paging); a long window is what makes all three bind at once, and no in-vault source measures extension together with any of them. For local/edge deployment this is the binding constraint, not the extension technique. See context-length-is-a-cheap-post-hoc-edit-not-a-pretraining-property.
  • 2026-07-19 — advisory edge from flashattention-2-work-partitioning (T1, primary map transformer-architecture): an expiry date on every throughput number in this map. FlashAttention-2 doubles FlashAttention's speed without touching the math, purely by re-partitioning work across thread blocks and warps — and then demonstrates the limit of that achievement by running its A100-tuned kernel unmodified on an H100, where the author states Hopper's TMA, 4th-gen Tensor Cores, and fp8 leave another 1.5–2× on the table. Block sizes are hand-tuned per head dimension. The operating rule this map should adopt: a tok/s or throughput figure is a claim about a kernel-and-card pair on a date, not about a model or a format, and comparing two runtimes benchmarked on different silicon is comparing nothing. See attention-kernels-are-tuned-to-a-gpu-generation.
  • 2026-07-18 — interaction edge from gqa-grouped-query-attention (T1, primary map transformer-architecture): the KV budget this map treats as given is partly an architectural choice — GQA-8 stores a fraction of MHA's KV heads at ~equal quality, and nearly every open-weights model you would run locally already ships with it. Third lever on one resource (architecture / precision / paging), and a correction: KV-quantization gains measured on MHA models overstate what they buy on the GQA models actually deployed. See sharing-kv-heads-buys-decode-speed-at-near-zero-quality-cost.
  • 2026-07-18 — principle edge from flashattention-io-aware-attention (T1, primary map transformer-architecture): the clean statement of why every optimization in this map works — on modern accelerators arithmetic is nearly free and data movement is the bill. GGUF's mmap, 4-bit weights as a bandwidth win, PagedAttention, KV quantization are all instances. Scope note: FlashAttention itself accelerates prefill/training, not single-token decode, which is bound by weight and KV movement instead. See attention-is-memory-bound-not-compute-bound.
  • 2026-07-17 — interaction edge from kivi-2bit-kv-cache-quantization (T1, primary map post-training-quantization): the KV-cache memory wall this map places via PagedAttention can also be shrunk by 2-bit KV quantization — orthogonal levers (paging + precision) that stack; a runtime that both pages and 2-bit-quantizes the cache wins on capacity twice. See kv-cache-error-is-directionally-structured.
  • 2026-07-16 — ingest of vllm-pagedattention (Kwon et al., UC Berkeley, SOSP 2023, T1): first runtime-systems source — KV-cache paging, near-zero waste, 2–4× throughput; manages KV placement while KV quantization stays open (shared wall with post-training-quantization). See paged-kv-cache-unlocks-throughput.
  • 2026-07-16 — seed ingest of gguf-format-spec (ggml-org, tool doc, T2): the format half — why local deployment is a file copy. Deliberately silent on which quant level loses what quality; that comparison needs T1/T3 sources. See self-describing-single-files-won-local-distribution.
  • 2026-07-16 — deployment edge from awq-activation-aware-quantization (T1, primary map post-training-quantization): TinyChat's kernel-side evidence that 4-bit puts 70B-class models on mobile GPUs. See four-bit-weights-put-llms-on-device.

Open questions:

  • The runtime half is better served but still not local: vLLM's paging mechanism and speculative decoding (2026-07-22) are both in-vault, but prefix caching and continuous-batching variants are not, and llama.cpp/Ollama as systems (CPU/Metal path, the single-user objective) still have no in-vault sources at all.
  • What speculative decoding costs on the hardware this map is about, nobody has measured. Three specific unknowns, all pointing the same way: (a) batching erodes the win — concurrency already fills the arithmetic headroom speculation spends, and the crossover batch size is unreported; (b) the draft model competes for VRAM with the target's weights and KV on exactly the device where memory is the binding constraint, and no in-vault source prices that trade; (c) α is measured on full-precision pairs, so whether a quantized draft and a quantized target still agree at 0.6–0.8 — the only pairing a llama.cpp user would ever run — is unknown, and it is this map's sharpest missing datum now. A fourth, smaller constraint: draft and target must share a tokenizer.
  • KV-cache quantization — shrinking the entries PagedAttention places — now has a first source (KIVI, 2-bit KV; post-training-quantization). Unserved: whether llama.cpp/Ollama's local KV-quant options match it, and a measured paging+precision combined result on one runtime.
  • The KV budget is now known to be a product of three levers — architecture (GQA, fewer heads), precision (KV quantization, fewer bits), placement (paging, less waste) — and no in-vault source measures more than one at a time. Since the models people actually run are already GQA, the headline numbers from the other two levers are upper bounds on what they add. The combined measurement is this map's sharpest missing datum.
  • Which GGUF quant level loses what, measured — the K-quant/IQ ladder needs graded head-to-head evidence before the tutor can teach the trade as more than folklore.
  • Every in-vault throughput number needs a hardware stamp (new 2026-07-19). The kernel evidence now shows tuning does not transfer across GPU generations, yet this map's figures (2–4× from paging, >3× from 4-bit kernels, 2.35–3.47× from 2-bit KV) come from different papers on different cards and are read here as if commensurable. They are not. A single-runtime, single-card measurement of the stacked levers would fix both this and the KV-budget gap above.
  • Edge constraints beyond the mobile-GPU demo (thermals, memory bandwidth on SBCs/NPUs, the compress→convert→deploy pipeline as Track E teaches it) — future sources.
  • Note for the tutor bridge: the atlas-tutor stack itself runs on Ollama Cloud — the learner's daily tooling is this map's subject matter.
