Six answers to one memory wall: the state of distributed training

Synthesized 2026-07-22, refreshed 2026-07-26 from distributed-training (status: consolidating since 2026-07-20). The slug still says "four" because slugs are stable; the count is now six, and the trigger for this refresh was six new dated bullets on the map — pipeline parallelism, NVMe offload, sequence parallelism, an inference-side scheduling note, asynchronous pipelining, and finally a primary source for activation recomputation. Every source below is a systems paper about full-parameter training. If you are fine-tuning with adapters on one card, read the last two sections first — they are the ones that say which of this applies to you, and the answer has changed. Check the map's through-line before trusting this in 2027.

The claim

Training stops where one device's memory stops, and it stops early. Plain distributed data parallel replicates parameters, gradients, and optimizer states on every GPU, which puts the ceiling near 1B parameters on a 40GB card — the FSDP paper demonstrates DDP failing to wrap T5 above 2.28B. [T1]

The arithmetic underneath is worth memorizing, because most of what follows is a rearrangement of it. Mixed-precision Adam costs 16Ψ bytes per parameter: 2Ψ fp16 params + 2Ψ fp16 grads + 4Ψ fp32 params + 4Ψ momentum + 4Ψ variance. Twelve of those sixteen bytes are fp32 optimizer state that the forward pass never touches, replicated on every GPU. [T1]

The reason the count keeps growing is that these are not variants of each other. They cut along different axes, and — the thing that took the vault four refreshes to state cleanly — they are not all indexed by the same quantity.

That last column is the one to read. Four of the six attack terms that scale with the number of trainable parameters. Two attack activations, which do not scale that way at all — and that is the whole story for anyone fine-tuning with adapters.

What to do

  • Turn on gradient checkpointing before anything else. This is new advice in this refresh, and it comes first because it is the only lever here that is exact. Split n layers into k segments, store only the boundaries, recompute each segment's interior during backprop: O(n/k) + O(k) memory, minimized at k = sqrt(n) for exactly one extra forward pass — measured at 48 GB → under 7 GB for a 1,000-layer ResNet, and >4× below an already in-place-and-sharing-optimized plan for a 1,024-step LSTM, both at ~30% runtime. The paper states plainly that every transformation it proposes "gives equivalent weight gradient for training and can always be safely applied." Nothing else on this list can say that. [T1]
  • Treat it as a dial, not a boolean — nobody's framework does. The sqrt(n) plan is one point on a curve: apply the scheme recursively and g(n) = k·log_{k+1}(n), so k=1 gives log₂ n memory for O(n log₂ n) compute. The paper searches a memory budget and picks the plan; PyTorch and HF Transformers expose per-block checkpointing on or off, which is k = number of blocks, chosen for you. [T1]
  • Turn on ZeRO stages 1 and 2 unconditionally. ZeRO decomposes sharding into three cumulative switches with asymmetric prices: optimizer states (4× memory reduction), + gradients (8×), + parameters (N_d×, linear in data-parallel degree). Stages 1 and 2 move the same communication volume as plain data parallelism — close to strictly dominant. Stage 3 costs 1.5×. A 7.5B model at 64-way data parallelism goes 120 GB → 31.4 → 16.6 → 1.88 GB per device. So: 1 and 2 always; 3 when you must fit, knowing you are paying bandwidth for it. [T1]
  • Treat sharding as a dial too. FSDP's sharding factor runs continuously — F=1 is plain DDP (cheapest communication, no savings), F=W is full sharding (lowest memory, most communication), hybrid values a graduating trade. FSDP-unit granularity is a second knob in the same currency. [T1]
  • Expect wrong settings in both directions, and measure. T5-11B loses 7% per-GPU TFLOPS from 8 to 512 GPUs as communication outruns the available overlap. FSDP's CPU rate limiter is worth up to 5× on T5-11B, costs 5% on DeepViT-8B, and does nothing on RegNet-9B — throttling only helps when a CPU running ahead is actually causing allocator defragmentation. The paper's own advice: check num_alloc_retries first. There is no transferable configuration here. [T1]
  • Profile before you choose an axis; the right answer is a property of your deployment, not your model. PipeDream profiles 1,000 minibatches and runs a dynamic program over the stage partition, the replication factor, and the in-flight count. In all but one experiment the optimum was a mixture of data, model and pipeline parallelism — and in that one exception the search correctly returned pure data parallelism (Inception-v3, 5% communication overhead, 1.00× over BSP, 0% traffic saved). Same model on a slower network: a 7-1 pipeline worth 1.45×. [T1]
  • Reach for tensor parallelism only when a single layer won't fit — and keep it inside one node. Megatron partitions the block so a whole layer costs two all-reduces forward and two backward (MLP: column-split the first weight so the nonlinearity stays local, row-split the second; attention: split across heads so each softmax is local). That bought 8.3B parameters on 512 GPUs at 76% scaling efficiency. Those all-reduces are latency-bound, so it stays efficient only inside a high-bandwidth island. [T1]
  • Reach for pipelining for one of two different reasons, and know which. The two branches trade in opposite directions. GPipe is the memory branch: micro-batch, re-materialize, flush every step, keep the gradient exact — 3.9× more parameters on one unchanged accelerator, at a bubble of O((K−1)/(M+K−1)) that is negligible only at M ≥ 4K (get that wrong and M=1 costs the entire benefit while appearing to work: 1.3× versus 6.3× on the same partitions). PipeDream is the bandwidth branch: never flush, alternate one forward and one backward pass for different minibatches (1F1B), ship one layer's activations instead of every parameter — up to 95% less traffic, VGG16 2.99× over data-parallel BSP on Titan X and 5.12× on V100. It costs memory: one stashed weight version plus intermediate state per in-flight minibatch. [T1]
  • If you cannot add GPUs, demote instead of distribute — and know which tier each thing wants. ZeRO-Offload runs the fp32 optimizer state and the Adam step on the CPU, keeping fp16 params/grads and forward/backward on the GPU: the 12Ψ/4Ψ split, a 4× GPU-memory cut before any sharding, 13B on one GPU (10× what PyTorch fits), near-linear to 128 GPUs. ZeRO-Infinity adds NVMe and — more usefully — the decision rule efficiency = ait·bw / (ait·bw + peak_tp), whose per-class thresholds invert the intuition: activation checkpoints offload at under 2 GB/s, parameters and gradients at ~70 GB/s, and optimizer states demand up to 1.5 TB/s, because the optimizer step cannot overlap with compute. [T1]
  • Understand why offload works, because that tells you when it won't. Forward/backward costs O(params × batch × seq); the Adam step costs O(params). The optimizer is the one stage whose cost is independent of the batch — which is why you can afford to run it an order of magnitude slower, and why communication stays fixed at 2× the parameter count per step. Corollary: the larger your batch, the better this trade looks. It assumes ample CPU DRAM and PCIe bandwidth, and the optimality argument is Adam-specific. [T1]
  • Enable delayed parameter update after warm-up, not from step 1. ZeRO-Offload's one-step DPU overlaps the CPU optimizer step with GPU compute for up to 1.5×, at the cost of step i+1 being updated from step i−1's parameters. The no-accuracy-cost result is conditional on introducing it after a few dozen iterations, because early training is where staleness destabilizes. [T1]
  • Sequence parallelism is a datacenter technique, and you can rule it in or out on paper. Ring Attention makes trainable context a property of the cluster — per-host activation memory 6bch contains no sequence term, so context scales linearly with device count (7B to 256K on 8 A100s; 3B to 16M on TPUv4-1024, 512×) at essentially unchanged MFU. The precondition is crisp: c ≥ F/B, block size above the host's FLOPS-to-bandwidth ratio. The same A100 needs a 6.2K per-host sequence over NVLink and 149.5K over InfiniBand — a 24× swing from the wire alone, and a hard floor rather than graceful degradation. [T1]
  • Budget for two memory pools, not one. Model states are handled by partitioning; residual states (activations, temporaries, fragmentation) need different tools — partitioned activation checkpointing, constant-size fusion buffers, live defragmentation. The operational lesson: OOM-from-fragmentation is a distinct failure from OOM-from-size, and they have different fixes. [T1]
  • Expect "it fits now" and "it's faster now" to arrive together. ZeRO reports super-linear speedup from 64 to 400 GPUs — mechanistic, not anomalous: a smaller per-device footprint permits a larger batch, which raises arithmetic intensity. [T1]

What the numbers don't say

  • Rank these levers by exactness, because only one end of the range is safe to ignore. This is the through-line the map found on 2026-07-26 and it is the most practically useful thing here. Exact: activation recomputation — equivalent weight gradients, safe to apply always. Silently inexact: sharded training, which the FSDP paper says is "not guaranteed mathematically equivalent to local training" because the optimizer steps over flattened FlatParameters whose layout ignores parameter boundaries, so norm-based clipping and approximate second-order methods compute over the wrong object — no quality delta is measured, and the failure is silent. Deliberately inexact: asynchronous pipelining, where PipeDream states that without weight stashing "the weight update is not a valid gradient of the loss function f for any weight vector," where stashing restores only intra-stage consistency, and where the mechanism that would restore data-parallel equivalence (vertical sync) is measured as negligible and ships off by default. That is a defensible engineering call, documented better than FSDP's. It is also a model trained by an optimizer nobody would write down, whose weights get compared on a leaderboard against models that were. The training system is part of the experimental configuration, and almost no result reports it. [T1, three sources]
  • Everything here is a vendor grading its own homework. Microsoft's "10× faster than SOTA" is measured against baselines Microsoft configured; Meta's FSDP numbers are Meta's; FSDP says outright that it is ZeRO-3, so what replicates across the two is the engineering, not two independent derivations — and ZeRO-Infinity makes the fourth first-party DeepSpeed/FSDP account in-vault. Megatron's 76% efficiency is NVIDIA-on-NVLink. PipeDream's baselines are the authors' own. No third party has audited any of it. [T1, first-party]
  • The pipelining and recompute evidence predates the transformer entirely. GPipe is 2018–2019 TPU/P100 work on a convnet and an encoder-decoder; PipeDream is VGG16, Inception-v3, S2VT, ResNet-50 and AlexNet on at most 16 GPUs; the sublinear-memory paper is 2016 ResNet and LSTM on a Titan X in MXNet. Nobody has measured 1F1B staleness on a language model, and the ~30% recompute overhead does not transfer unexamined to a block whose attention op already recomputes its largest intermediate since FlashAttention — part of that win is double-counted for modern models. [T1, out-of-domain]
  • Absolute throughput figures expire with the GPU generation, and the direction is instructive. ZeRO's 38 TFlops/GPU and ZeRO-Offload's 40/30 are V100-era; the ratios survive because they follow from byte accounting. PipeDream measures the other side of the same effect: across five models, going K80 → Titan X → V100 raises communication's share of training time, and its advantage over data-parallel grows 2.99× → 5.12× on newer cards. Compute got cheaper; the interconnect did not. Optimizations about movement get more valuable as silicon improves — the same conclusion FlashAttention reaches about HBM and ZeRO-Infinity about PCIe. [T1, three literatures]
  • Nobody has priced the practitioner-scale question: what actually fits on N cards. The in-vault numbers are 175B on 128–512 A100s. This vault's premise runs on far less.

The gap that matters most here

None of these sources is about fine-tuning. Every experiment is generic full-parameter training — no frozen layers, no adapters, no fine-tuning memory profile. But the refreshes since 2026-07-22 have turned that from a shrug into a specific, testable prediction, and it is the most useful thing this article can leave you with.

Four of the six axes attack terms proportional to the number of trainable parameters. A 4-bit LoRA fine-tune has almost none of those terms: 99.99% of parameters are frozen, and there is barely any fp32 optimizer state left to shard, split, or demote. So PEFT plausibly deletes most of this list, and offload — whose entire win is relocating 12Ψ bytes of optimizer state — is the clearest candidate. [unsourced, and a genuinely useful negative result if true]

Activations do not scale that way. The forward activations of a 70B model are the same size whether you update every weight or 0.01% of them. That leaves exactly two axes standing, and one of them is already ruled out for this audience: sequence parallelism's c ≥ F/B precondition is a hard floor, and consumer PCIe has the worst possible ratio. By elimination, gradient checkpointing is the memory technique that binds in the regime this vault cares about — which is why it moved to the top of the "what to do" list in this refresh, and why the sublinear-memory paper's 2016 vintage is worth tolerating.

So the cheapest useful experiment nobody has run is now stated precisely, and it has grown a dimension since July 22:

Peak memory and step time for a 4-bit LoRA fine-tune at a realistic sequence length — with and without gradient checkpointing, with and without CPU activation offload, at more than one segment granularity.

Two facts make it more pressing than it was. ZeRO-Infinity prices CPU activation offload at under 2 GB/s, i.e. trivially affordable over PCIe, so the second knob is free to test. And cheap post-hoc context extension (context-extension) makes long sequences easy to acquire and expensive to train through, which is exactly the regime where the sublinear-memory paper's gains were largest — >4× on a 1,024-step LSTM against 2–3× for the depth case.

The honest summary as of 2026-07: the memory arithmetic is settled and replicated, the six axes are individually well-measured, no source measures any combination of them, and the combination this vault's premise actually needs — adapters, on a quantized base, at long context, across whichever of these levers still applies — is undocumented in all six.
