Slower hardware you already own: the state of memory-hierarchy offload

Synthesized 2026-09-15 from memory-hierarchy-offload (status: consolidating), forked 2026-08-03 from distributed-training and now past ten dated findings. As of 2026-09 the map's whole territory is one operation — demote state down to a slower tier rather than spread it across more devices — applied to four different objects (optimizer/gradient state, activations, frozen weight layers, and now a serving-time KV cache) across three tiers (host RAM, NVMe, and a serving engine's managed disk/object-storage layer).

The one move, and the one formula that decides whether to make it

Distributed training buys capacity with more hardware. This map's answer is the opposite: buy it with slower hardware you already have — host RAM, an NVMe drive, a PCIe link — trading bandwidth and a step (or a request) of latency for capacity that costs no additional card. ZeRO-Offload (T1) names the forced cut for Adam training: fp32 optimizer state, fp32 parameters and the optimizer step itself go to the CPU (12 of 16Ψ bytes/parameter, a 4× GPU-memory reduction before any sharding) because the optimizer step costs O(params) while forward/backward costs O(params × batch × seq) — the one stage whose cost does not grow with batch size, and therefore the one you can afford to run an order of magnitude slower on a CPU. Measured: 13B on a single GPU at 10× PyTorch's prior reach, near-linear to 128 GPUs.

ZeRO-Infinity (T1) adds NVMe as a third tier and, more usefully, supplies the only decision instrument this map has: efficiency = ait·bw/(ait·bw + peak_tp), where ait is a state class's arithmetic intensity. Fix a target efficiency and the required bandwidth per class inverts the intuition — activations under 2 GB/s, parameters/gradients ~70 GB/s, optimizer states up to 1.5 TB/s — so activations are the cheapest thing to demote and the optimizer the most expensive, the opposite of ZeRO-Offload's compute-independence framing. Both are correct about different resources: one argument is about the optimizer step's batch-independent compute, the other about its unhideable bandwidth demand, since the step cannot overlap with anything. NVMe itself is 50× larger than GPU memory on a DGX-2-class node and, combined with bandwidth-centric partitioning (an allgather across every data-parallel rank instead of one owner's broadcast, lifting CPU→GPU from ~12 to 48 GB/s) and memory-centric tiling (avoiding model parallelism entirely), reaches 32 trillion parameters on 512 V100s at 40% of peak. The number that matters more than the headline: at 500B, where both still fit, offload and 3D parallelism land within a point of each other (46 vs 47 TFLOPS/GPU) — this is a comparable operating point, not a penalty for lacking hardware.

Imperative 1 [T1]: run the formula before you run the experiment. Whether to offload a given state class is arithmetic on its arithmetic intensity, not a thing you need a GPU to discover.

Three tiers, priced

Imperative 2 [T2]: the host-side cost is real on a desktop, and it removes the exact thing that made a small-batch run tolerable. CPUOffloadOptimizer (torchtune, T2) costs 4× the model size in system RAM and forces gradient_accumulation_steps=1. On a 32–64 GB desktop, an 8B model's offloaded optimizer state alone is ~32 GB — the technique that makes the model fit simultaneously removes the mechanism that made batch-size-1 tolerable.

Imperative 3 [T2]: parameter-efficient fine-tuning does not just delete this axis, it opens a new one. Under LoRA on a 4-bit base there is almost no optimizer state to demote in the first place — the strongest argument in-vault that PEFT renders the optimizer-offload axis moot. But Axolotl (T2) ships layer_offloading, documented as "best suited for LoRA/QLoRA where most parameters are frozen": it streams frozen decoder layers between CPU and GPU one at a time, which a full fine-tune cannot do (it has no frozen weights to stream). Shrinking the trainable set turns the resident base into a large, read-only, sequentially-accessed object — the friendliest possible pattern for a prefetcher. No measured step time, peak memory, or bandwidth utilization exists anywhere in-vault for this feature; it is a capability inventory, not a benchmark.

Imperative 4 [T2]: a managed disk tier now ships in a serving engine, not just a research prototype. vLLM v0.28.0 (T2) adds disk as a formal KV-cache offload tier — out-of-tree secondary-tier managers, partial-load handling, dedicated tiering metrics. No latency number for the disk tier specifically; this map's own cost model predicts it is the slowest rung by a wide margin.

The tier gets a serving-time entrant, and a concurrency crossover

Imperative 5 [T2]: recomputing an evicted KV span and fetching it from storage cross over as concurrency rises, and the crossover does not reverse. A canonical, tensor-parallelism-independent host-memory KV layout in front of an extensible secondary-tier interface (filesystem, object storage, peer-to-peer) — with GPU memory for an offloaded block freed the instant its host copy completes — performs comparably to recompute-on-evict below ~64 concurrent multi-turn conversations, but more than doubles throughput past ~128 (tiered KV offloading in vLLM, T2, Qwen3.6-35B-A3B on 2× H100). The mechanism is an accounting fact: recompute cost scales with the prefill FLOPs of everything currently evicted across all live requests, while a storage round-trip's cost per request stays roughly constant, so the crossover is structural rather than a tuning artifact. The parallelism-independent layout is the piece with no analogue elsewhere on this map — it is what lets a KV region written under one tensor-parallel configuration be read by a node running a different one, a precondition for treating the cache as shareable across a fleet rather than pinned to its producing node. Datacenter hardware only; the single-card, batch-1 crossover this map has wanted since its first night is still nowhere in evidence.

What the formula was missing: idle power

Imperative 6 [T1, fully simulated]: overlap has two payoffs, and the formula only prices one. The bandwidth/arithmetic-intensity formula treats a stalled package as a wash — you paid the compute time either way. Measured on an edge MoE decode where expert loading is 43% of latency: adaptive prefetching raises off-chip I/O energy (48 → 56 mJ) and lowers total energy anyway (340 → 299 mJ), because idle/leakage power falls 57 → 8 mJ. Seventeen percent of the baseline's energy was being spent doing nothing. The bound on the trick is the same formula written for a discrete budget: hiding an extra fetch δ needs δ·S_expert/B_eff + T_queue ≤ T_attn, and past that ceiling static over-prefetch is the worst configuration measured — worse than no prefetching at all (APEX, T1, RTL-synthesized/simulated, no hardware prototype). The same locality pattern — 82–85% of active weight rows persisting token-to-token, so the per-token job is the delta rather than the active set — transfers to a real board serving a dense model: NeuroPrefetcher (T1, Jetson AGX Orin, ICPP 2026, code released) turns 0.2–0.3 tok/s under naive memory-mapped paging into 1.7–3.7 tok/s (7.9–12.0×), with a hard retirement condition: once the model fits in memory, the technique's advantage collapses to 1.1–1.2×, and quality costs are real (92–96% of dense HellaSwag depending on model and prefix length).

What still doesn't compose

  • Does this axis survive PEFT, or does PEFT delete it? Still the sharpest open item. The optimizer tier looks dead under LoRA-on-4-bit; the activation tier is untouched by PEFT and still cheap; the new layer_offloading tier is one PEFT creates and nobody has measured. Three separate questions where the map used to have one.
  • The contention question every source ducks by construction. Every efficiency number here holds bandwidth infinite for every state class except the one under study. Parameters, optimizer states and activations moving over the same PCIe link at once — the actual configuration on a one- or two-card desktop — has never been measured together.
  • Layer streaming has no published number anywhere. layer_offloading ships as a documented feature with zero measured step time, peak memory, or bandwidth utilization. The cheapest useful run on this map is unchanged from when it was first named: step time and peak VRAM for a 4-bit LoRA fine-tune with the feature on and off, at two sequence lengths, on one consumer card.
  • The lineage problem. ZeRO-Offload and ZeRO-Infinity are the same team at the same company; what replicates is one group's engineering across two papers, not two independent derivations. Kimi K3 (T1) is the first non-DeepSpeed confirmation — sharded gradients in CPU memory, activations offloaded to a peer pipeline-rank's memory — but it is a vendor usage report with no ablation, not a controlled comparison.
  • A cache budget and a page cache compete for the same RAM, and past a knee, growing the offload cache makes decode slower, not faster. On a 64 GB M1 Max serving a 284B MoE from SSD the knee sits at a 26–28 GB expert-cache budget; a 125 GB machine decodes faster at 24 GiB than at 90 GiB (tied trit-planes, T1, single author). The fix that turns a per-projection miss into one contiguous read — making the on-disk block format identical to the cache-slab and kernel-input format — is a design rule this map should carry generally: push the packing as far down the hierarchy as the artifact goes, including the file (router locality at the edge, T1).

If you are choosing today

Run the ZeRO-Infinity formula on your own state classes before benchmarking anything — it will tell you which tier a given tensor belongs on for free. On a single consumer card with LoRA, assume the optimizer tier has nothing left to offload and look instead at activation offload (still cheap) and layer streaming (unmeasured, but structurally the friendliest prefetch target this map has). If you are serving rather than training, and evicting a KV cache under concurrency, storage-backed offload beats recompute once load is heavy enough that the FLOPs of what you'd recompute outweigh a fetch — but nobody has yet drawn that line on a single card at batch one, which is where most of this vault's readers actually sit.
