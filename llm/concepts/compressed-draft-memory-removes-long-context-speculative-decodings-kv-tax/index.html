The draft's cache is a second memory-bound tax nobody had named

speculative-decoding and kv-cache-management have separately established that a stronger drafter buys more accepted length at a higher per-step cost, and that KV-cache read cost — not arithmetic — is what scales with context length on the target side. This source is the first in-vault evidence that the same scaling law applies to the draft: at long prefixes, a strong drafter's own cache becomes a second memory-bound cost that erodes the very speedup speculative decoding exists to buy.

The fix does not touch the target at all. A lightweight adaptor gives the draft a compressed, incrementally-updated memory — distant context compressed, recent context exact — while the target keeps its full cache and its ordinary accept/reject rule. Because the target's distribution and verification are unchanged, the scheme is lossless by the same argument that makes ordinary speculative decoding lossless: compression only ever touches the side that was already an approximation.

This is a draft-side-only compression, which makes it compose cleanly, at least in principle, with anything kv-cache-management already does to the target's cache — eviction, quantization, rotation — none of which this source touches or tests against. It also sharpens rather than answers speculative-decoding's open question about where a drafter should come from and what shape it should take: this result assumes a capable, already-well-aligned drafter and asks only how to keep its memory cheap as context grows, so it is orthogonal to the provenance question rather than an answer to it.

Bound: no acceptance-rate table in the fetched summary, no comparison against an uncompressed strong drafter at the same prefix lengths (the ablation that would isolate how much of the speedup is compression versus simply having a capable draft), and no consumer-hardware or batch>1 measurement — everything is Llama-3.1-scale, presumably on datacenter GPUs.
