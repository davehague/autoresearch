Routing is not what makes MoE slow on device

The useful half of the edge-MoE result, because it decides whether the deficit is a bug or a property.

If the gate and the dispatch were the cost, the fix would be a better kernel and every number in moe-inference-cost-tracks-total-not-active-params-on-edge would expire with the next llama.cpp release — the vault's standing warning that kernel-performance-expires-with-the-gpu-generation would apply directly. Patching llama.cpp to wall-clock each node of the decode graph rules that out: routing is under 9% of MoE-block time on the backend whose instrumentation is trustworthy, and the remaining 91% is expert FFN — the actual matmuls, reading actual weights.

So the deficit is structural. To serve 1.3B of compute you must keep 6.9B parameters reachable, and on a device whose binding constraint is memory bandwidth, reachable means resident and resident means paid for. No amount of router optimization touches that.

Methodological note worth keeping for its own sake: the same instrumentation on Metal returns 33.5% for routing, and the authors reject their own number because Metal's per-node synchronization inflates instrumented runtime 14.9× against CUDA's 1.26×. Profiling a graph node-by-node is not free, and on some backends the profiler is louder than the signal. This vault has repeatedly found that a measurement carries a kernel, a card, and a precision (attention-kernels-are-tuned-to-a-gpu-generation); this adds that on some backends it also carries the observer.

What it leaves open: the finding rules out the router but does not decompose the remaining 91% into weight traffic, expert-dispatch gather/scatter, and KV pressure — the paper names all three as contributors without separating them. Since only the first is irreducible, which of the three dominates is the question determining whether an offload-aware or locality-aware runtime (exploiting the ~28% consecutive-token expert reuse in experts-specialize-by-syntax-not-semantics) could recover the gap. Unmeasured here, on one model and two devices.
