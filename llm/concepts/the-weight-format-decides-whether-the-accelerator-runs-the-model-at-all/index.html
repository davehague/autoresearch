Quantization is the admission ticket, not the optimization

This vault has priced quantization as a memory-for-quality trade with a throughput rider (post-training-quantization's whole allocation strand) and, on constrained hardware, as the thing that makes a model fit. On Apple's Neural Engine it does something categorically different: it decides whether the accelerator is used at all.

The measurement is unusually clean because the arms are matched by construction. Quantization swaps module.__class__ rather than replacing modules, so parameter names, weight tying and save_pretrained() are byte-identical to the fp16 run; every arm loads as an ordinary causal-LM and exports through one path. The fp16 model then reads exactly zero bytes through the engine across ~5,750 consecutive inferences while the int8 sibling reads 255.6 GB and runs nearly twice as fast, and the CPU rail confirms it — 4,929 mW against 1,655 mW.

Two directions look contradictory and are not. At fp16, more parameters gets you onto the engine (25.9M off, 40.3M on). At a fixed 25.9M, fewer bytes gets you on (56.0 MB off, 28.2 MB on). Both follow from one cost expression: the engine carries a per-dispatch overhead the CPU does not (~0.23 ms on M1), so growing the model grows the work term until it amortizes, while quantization shrinks the bytes and transfer terms so the engine's total falls below the CPU's at a size where it otherwise would not. The all-attention model at 22.29M fits too — attention contributes matmuls with an expensive CPU alternative where a conv stack contributes cheap depthwise convolutions and gating multiplies.

This is a scheduler decision, not a hardware limit. The ANE is perfectly capable of the fp16 graph; CoreML simply prices it onto the CPU. That distinguishes it from the one prior instance of encoding-determines-placement (an SoC whose units physically cannot run other formats, with a per-channel decision explicit in the compiler): here the decision is whole-model and made by a cost heuristic inside a closed compiler, and the outcome is a discontinuity rather than a gradient.

Read alongside the-npu-shares-the-bandwidth-it-was-supposed-to-relieve, the pair sharpens into a rule for the vault's second-accelerator question. On an Intel AI PC the NPU is a throughput null that buys placement (a shard that fits nowhere else fits there); on Apple silicon the accelerator buys a real 1.8–2.2× decode speedup and lower power — but only if the weight format lets the scheduler admit it. Both are placement stories dressed as throughput stories.

Limits. Models are 5–50M parameters, orders of magnitude below anything deployable, and quality is deliberately not measured — the checkpoints were built so the accuracy question can be asked on the same artifacts in a companion study that does not exist yet. The size boundary was mapped only on M1 and only for conv-heavy architectures, so no parameter-count rule should be read off it; what replicated on the M3 is the encoding-gates-placement result, by energy rather than bytes, one run per cell on an 8 GB Air.
