The wrapper moved more than the machine did

The authors set out to compare a small model's accuracy on GPU, CPU and a Raspberry Pi, found a 38.85-point SQuAD gap between the first and the last, and then audited their own campaigns and discovered the two runs had used different instruction templates. Rerunning both templates on one GPU over the same hundred items reproduced 38.16 of those 38.85 points. The hardware contributed almost nothing.

Two things make this more than a caught confound.

It is bigger than the effects it was competing with. A 38-point swing from a phrasing change exceeds most compression effects in this vault: larger than the whole FP16→INT3 sweep on the trustworthiness study, larger than any single step of the GGUF quant ladder, larger than the quantization damage the same paper measures on the same task. When the nuisance term dominates the treatment term by an order of magnitude, uncontrolled comparisons do not have wide error bars — they have no information.

And the sign is not stable. Gemma's template range on the same items runs 62.42 to 48.70 and points opposite to its apparent Raspberry Pi improvement, so template variation does not merely add noise around a true platform effect; it can manufacture a platform effect of either sign. The authors flag both directions against themselves, including noting that TinyLlama's uncontrolled Pi comparison was handicapped in the pruned models' favour and the pruned models still lost.

This converts two findings evaluation-contamination already holds from properties of models into a procedure. fragility-is-a-property-of-the-rephrasing-not-the-model established that phrasing sensitivity is a property of the specific rewording rather than of the model's competence; phrasing-sensitivity-does-not-fade-with-capability-it-changes-sign established that it does not scale away. Both were arguments for reporting a distribution over phrasings. This is the narrower, cheaper corollary that this vault needs constantly, because so much of what it reads compares runtimes and devices: if the prompt path is not held byte-identical, the platform number measures the prompt.

The controlled numbers in the same study show what a clean comparison looks like and how small the real effect is. With the template fixed, GPU-versus-CPU SQuAD F1 stays within three points for all three models, and Qwen3.5 holds 87.93 on the Raspberry Pi under identical template, generation settings and items. The genuine platform effect is in latency, not accuracy: 0.13 s/sample on GPU, 0.61 on CPU, 8.91 on the Pi, at a nearly constant file size — a 70× spread that model size does not predict.

It is worth naming what "prompt path" includes, because template text is only the visible part. The chat template applied by the runtime, whether a system prompt is emitted, the generation cap, and the stop-sequence handling all differ between llama.cpp builds and Python harnesses, and each of them can move a small model's extractive-QA score. tool-calling-reliability-is-calibrated-to-a-rendering-path found the same class of dependency on the tool-calling side: the model is calibrated to a rendering, and changing the rendering changes the behaviour without touching the weights.

Bounds: sub-1.5B instruction-tuned models, one task family (extractive QA on SQuAD) plus a corroborating BoolQ signal, 100-item subsets, four templates. Whether the swing narrows at 7–8B is untested — the plausible expectation is that it does, since the models here are small enough that format compliance is itself fragile, and that expectation is exactly the kind this vault should stop assuming without a measurement.
