Greedy decoding is nondeterministic under batching

The habit is universal: set temperature=0, call it deterministic, compare two checkpoints on the same problems, and read the differences as capability change. The measurement here is that a model that did not change at all shows an 8% verdict flip rate when re-evaluated through a server running 64 concurrent requests, and 2% when the same evaluation is serialized.

The mechanism is batching. Batch composition changes reduction shapes and kernel selection inside the serving engine, floating-point reduction is not associative, and near-tied argmaxes move. The authors test this directly and attribute the dominant share to concurrency while noting that other server-side effects remain unaccounted for. "Greedy" specifies which token you take given the logits; it does not specify that you get the same logits twice.

The downstream consequence in the same audit is the reason this belongs on evaluation-contamination rather than in a footnote: a ledger built on a single greedy decode assigns a frozen model a corruption-to-learning ratio of 1.5×. Not noise around zero — a directional result, on a model that was never trained. Every problem that flips one way reads as forgetting and every problem that flips the other reads as learning, and the two do not balance.

What to do about it is not exotic, and the size of the fix matters: serialize, or average over samples, or both. Going from 64-way concurrency to serialized execution takes the flip rate from 8% to 2% — a 4× reduction for a throughput cost, which is the actual trade being made whenever an eval is run at production concurrency for speed.

The two-source convergence in this run is what makes this more than an operational gotcha. logit-margin-predicts-which-token-a-kernel-swap-flips arrives at a 4.7% per-position flip rate from an entirely different cause — swapping one INT8 GEMM kernel, holding the container digest fixed — and identifies logit margin as the variable that governs which positions move. Read together: numerical perturbations from anywhere in the stack act on the same population of near-tied decisions, and a benchmark's margin distribution determines how much of its score is available to be moved by things that are not the model. That is a stronger and more useful statement than either source makes alone.

The practical rule for this vault: before reporting that a fine-tune changed which problems a model solves, evaluate the unchanged model twice through the same pipeline and report that number first. It is one extra run and it converts an unbounded worry into a stated floor.

Bounded: one model family, one benchmark size (200 problems), one serving configuration. The direction and the mechanism are not in doubt; the exact 8% is a property of this stack at this concurrency.
