The first serving-engine-level result on this map to bring vLLM's server-grade scheduling primitives natively to Apple Silicon, rather than adapting MLX's single-request design or translating vLLM's CUDA path

This map's Apple Silicon coverage has so far measured MLX/Metal engines built around a single-request mental model (padded batching, or per-prompt calls) — good at concurrency 1, degrading as soon as several requests overlap, because none of them separates KV storage into pageable blocks the way server-grade GPU engines do. vllm-metal is the first entry here that ports vLLM's own primitives — the V1 scheduler, paged KV-cache with per-request block tables, chunked prefill — onto MLX/Metal directly, rather than writing a new Mac-native scheduler from scratch or running vLLM's CUDA kernels through a translation layer. The mechanism is concrete and matches this map's recurring padding-waste complaint: packed queries concatenate variable-length requests into one tensor with sequence-length markers instead of padding to a common length, and a custom "paged varlen" Metal attention kernel handles request boundaries inside that packed representation.

The result most directly relevant to this map's standing question (what runs well on one or two consumer cards) is the concurrency behavior: vllm-metal is not the fastest option at concurrency 1 (oMLX with SSD offload wins there), but becomes the fastest as soon as multiple requests overlap (concurrency 2 and up), holding its TTFT advantage out to 16 concurrent requests on Gemma 4 E4B. That is exactly the regime this map has flagged as unserved by the existing Mac inference stack — a single user running several agent sessions, or a small shared endpoint off one Mac, rather than the strictly single-request case most prior entries here optimize for. The packed-query padding-efficiency number (6% faster than llama.cpp, and a 143% slowdown for the padded alternative on ragged batches) is this map's cleanest quantification yet of what padding waste actually costs on Apple Silicon specifically.

Graded extends: adds a new serving-engine entry to the map's Apple Silicon coverage without contradicting any existing finding — it is complementary to, not competing with, this map's quantization-ladder and KV-cache-budget entries, which are about what to run rather than how many requests at once. Graded strong: multiple named benchmark configurations with quantified numbers, though see caveats below on independence.

Bounded hard: all numbers are vendor-published (vLLM project's own blog), with no independent replication and the benchmark suite (SiliconBench) not established as a third-party standard; concurrency-1 is not where vllm-metal wins, so a genuinely single-request local user gets no advantage from switching; no comparison against a CUDA-based vLLM baseline is given, so standing is established only within the Apple Silicon ecosystem; the project is a new announcement (v0.28.0), so no maintenance or longevity track record exists yet, unlike llama.cpp's multi-year presence on this map.

Rebutted by: none.
