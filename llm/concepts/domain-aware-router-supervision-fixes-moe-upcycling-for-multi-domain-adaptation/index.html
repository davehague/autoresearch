Sparse upcycling, which this map has so far sourced only as a from-scratch-pretraining-cost trick (convert a dense checkpoint into an MoE and keep training), gets a fine-tuning-scale instance aimed at a different problem: give a dense model several specialized domains without either diluting a shared LoRA adapter or letting irrelevant domains interfere — by making the router's domain assignment an explicit, separately-supervised training objective rather than a side effect of end-to-end fine-tuning

TL;DR: This map's upcycling thread has one open gap (per vault/index.md's Open gaps) stated exactly as: nothing tests upcycling at fine-tuning-scale extra compute, on an instruction-tuned checkpoint, or with adapters — the evidence is T5-XL on a 2020 encoder-decoder. This paper lands inside that gap on two counts: it is fine-tuning-scale (not pretraining-scale) and it is on modern decoder-only 8B checkpoints (Llama-3.1-8B, Qwen-3-8B), though it still updates a full expert rather than an adapter. Its specific contribution is a router-training recipe, not an architecture: upcycle to a small (odd-layers-only, Top-2) MoE with one expert initialized as a copy of the dense MLP ("general") plus one new expert per specialized domain, then train the router before task fine-tuning begins, on an explicit domain-classification objective using only 256 labeled examples per domain — general inputs should favor the general expert, domain inputs should favor their own expert and suppress the others. Fine-tuning then updates only the relevant domain's expert and the router, leaving everything else frozen. The router-supervision step is what the paper's own ablation credits for the result: an otherwise-identical upcycled architecture trained end-to-end without that explicit router objective reaches only 43-70% routing accuracy post-adaptation, against 90-98% with it — and DS-Upcycling also posts the best general-retention score of any baseline, meaning the domain gains are not bought by sacrificing the shared capability, the usual multi-LoRA trade-off this map's peft-methods neighbor already carries.

What it says. What problem this solves. Existing LoRA-based multi-domain methods either weight all domain adapters equally (diluting whichever one is actually relevant to a given input) or activate every adapter regardless of relevance (importing cross-domain interference), and LoRA's low-rank structure caps how much domain-specific knowledge any one adapter can hold regardless. Upcycling to a routed MoE replaces "which adapter(s) fire" with "which expert fires," at full-rank expert capacity instead of a low-rank adapter's capacity — but naive upcycling (copy the MLP into several experts, train the router end-to-end with the task loss alone) leaves the router's domain-assignment accuracy to whatever gradient descent on the task objective happens to discover, which this paper's own baseline shows is unreliable (43-70%). The fix. Supervise the router directly and separately, before task fine-tuning, on a small labeled set (256 examples/domain) whose only job is to teach "which expert should this input go to" — decoupling router correctness from downstream task performance entirely. What's untouched. Only the relevant domain's expert and the router update during fine-tuning; the general expert (a frozen copy of the original dense MLP) and the backbone are never touched for any domain, which is the mechanism behind the general-retention result — no domain's fine-tuning can degrade another domain's or the general capability, structurally, not just empirically.

Caveats. Two specialized domains tested (legal, biomedical) plus general retention — the harder, more directly relevant question to this map's own stated gap (does this still work, and does routing accuracy hold, as more domains are added to one upcycled model) is untested, and this map's own mixture-of-experts specialization thread already flags "nothing tests upcycling's symmetry-breaking at scale" as open. Both backbones are 8B; no scale sweep, and the T5-XL-era upcycling evidence this gap note already carries is an encoder-decoder at a comparable parameter count, so this paper does not yet close the "modern decoder-only base, larger scale" half of the gap either, only the "fine-tuning-scale, instruction-tuned checkpoint" half. No comparison to a from-scratch MoE at matched active-parameter count, nor to ordinary full fine-tuning without any MoE structure, so whether the architecture itself (vs. just the router-supervision trick) is doing the work is not isolated. The reported routing-accuracy range (90-98%) still implies up to 10% misrouted inputs even in the best case, and the paper does not test or discuss what happens to those misrouted inputs' outputs, nor a domain-ambiguous/mixed input at inference — a gap the headline number itself exposes. No code, model, or data release is stated.
