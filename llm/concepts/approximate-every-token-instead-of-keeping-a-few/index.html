Keep every token badly rather than a few perfectly

kv-cache-management was coined around the question given a fixed budget, what do you keep and in what form? — and until now the "what do you keep" half has done all the work. Eviction policies differ in how they score a token and agree that the losers are gone (predictable-past-tokens-are-the-redundant-ones, eviction-can-be-recoverable-instead-of-permanent). AnchorKV declines the question. It keeps all of them, at wildly uneven quality: a small set of anchors stored exactly per KV head, and every other token stored as a scalar projection onto its nearest anchor plus — for the tokens whose error would most move the attention output — a 2-bit Hadamard-rotated residual.

At matched bytes this wins, and the margin is not marginal. AnchorKV at 20× compression beats every eviction baseline at 10× — the same quality for half the memory. On needle-in-a-haystack at 5×, AnchorKV averages 0.94 against an uncompressed 0.99 while AdaKV, an eviction method that scores respectably on LongBench averages, reads 0.18.

That 0.94-against-0.18 gap is the mechanism showing itself, and it is why this is filed as pushing back rather than extending. Eviction fails hard: a discarded needle cannot be recovered by any later query, so the failure is a confidently missing fact. Approximation fails soft: an under-valued position is stored coarsely and is still there, so the failure is a slightly degraded one. Same budget, same benchmark, categorically different failure mode — and a practitioner picking a compression scheme on one card cares about the shape of the failure at least as much as about the mean.

It also lands where accuracy-is-an-asymmetric-diagnostic-for-a-compressed-cache said the money was. That source held the reasoning trace fixed across eleven methods and found eviction destroying a valid derivation in 47.9–64.8% of matched-correct cases against 4.2% for a 2-bit quantization control, with the stated mechanism being coverage of the trace, not fidelity of any part of it. AnchorKV is coverage as a design principle — closer to a quantizer with a dictionary than to a selector — so it has a specific reason to survive that check. Nobody has run it, and the protocol is released.

Two things bound this. The paper's own worry is the sharpest available criticism: a badly reconstructed key can attract attention mass its exact counterpart would not, a failure eviction avoids by removing the position outright. And code is promised on acceptance rather than released, so the result is not reproducible today — on a map whose founding status note already discounts its sources for exactly this.
