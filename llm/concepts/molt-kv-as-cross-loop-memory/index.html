A new axis for what a loop passes forward: KV-as-memory instead of the residual stream

This map's looped-architecture thread (no-free-loop, looped-transformer-loop-scaling-specialization, Accordion) has so far varied what gets looped (full stack vs a middle window) and how many times, always carrying the residual stream forward as the connection between loops. MoLT varies the connection itself: Mixture-of-Loops Attention treats keys and values from one loop as a readable memory bank for later loops, rather than something recomputed and discarded each pass. The MoLT-KV variant goes further — restarting each loop from the raw embeddings and reading only its own current-loop KV plus the previous loop's memory KV at earlier sequence positions — which removes same-position cross-loop dependence entirely. That removal is what permits "loop forcing" (parallelized training across loops, rather than one sequential pass per loop) and, at inference, single-traversal decoding that effectively runs more loop iterations than the model was trained with, without paying for one sequential forward pass per extra iteration. The U-shaped balancing variant (U-MoLT) is what the paper's headline numbers use, and it beats a non-looped OLMo3 baseline across model shapes (dense and MoE) while matching non-looped latency at small scale.

What this does and does not establish, and the open tension with LoopTitan. The same-day source looptitan-isolates-parameter-revisit-from-shape-and-optimizer argues, for looped MoE specifically, that reported gains from a loop-based architecture change must be decomposed against network shape and optimizer (AdamW vs Muon) before the loop mechanism itself can be credited — a matched non-looped control captures most or all of the apparent benefit in that paper's setting. MoLT's comparison against OLMo3 (and against an unspecified "matched baseline" for the continued-pretraining result) does not report this decomposition, so whether U-MoLT's 3B-MoE gain over OLMo3 survives a shape/optimizer-matched non-looped control, the way LoopTitan's own SMELT-family looped-MoE recipes barely do, is untested by either source. This is not a direct contradiction — MoLT's object of study (what connects loops) differs from LoopTitan's (whether revisiting parameters helps at all) — but it is exactly the kind of comparison LoopTitan's methodology would call for, and neither paper runs it. Flagged as an open interaction between the two maps' same-week sources, not resolved.
