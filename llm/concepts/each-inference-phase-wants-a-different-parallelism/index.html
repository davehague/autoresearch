The parallelism question has two answers inside one deployment

Every parallelism source in distributed-training argues one axis in isolation and asks which is best: tensor-parallelism-splits-a-layer-across-gpus cuts execution time at the price of two all-reduces per layer, pipeline-parallelism-splits-depth-and-pays-a-bubble adds rate capacity at the price of a bubble, and the-parallelism-configuration-is-searchable-not-a-dial says the combination is a search problem. This adds a dimension none of them has: in serving, the right answer differs between the two phases of the same request, and the reason is queueing rather than arithmetic.

Model a prefill instance as an M/D/1 queue — Poisson arrivals, deterministic service time, no batching, because one request already saturates the device. Then time-to-first-token decomposes into two terms:

Avg_TTFT = D + RD²/(2(1−RD))

execution time D plus queueing delay at arrival rate R. Two-way pipeline parallelism leaves D alone and roughly halves the queueing term (D + RD²/(4(2−RD))). Two-way tensor parallelism divides D by an imperfect speedup 1 < K < 2 and cuts queueing less (D/K + RD²/(2K(K−RD))). So the winner flips with load: tensor parallelism when arrivals are sparse or the latency target is tight (execution time dominates), pipeline parallelism as the rate climbs (queueing dominates). Measured on a 66B model across two A100s, the crossover is where the algebra puts it, and a smaller K — worse tensor-parallel scaling — moves it earlier.

Decode inverts the pair for a different reason. At large batch its latency is set by memory bandwidth, so tensor parallelism reduces latency with diminishing returns and degrading utilization, while pipeline parallelism scales throughput almost linearly. On a 13B model at batch 128, tensor parallelism takes latency from about 60 ms to 33 ms across 8 GPUs while its throughput curve flattens badly; pipeline parallelism tracks the linear-scaling line.

The consequence is the useful part. A system that colocates the phases has to pick one plan, so it provisions for whichever of the two SLOs is more demanding and wastes the difference on the other. The ablation isolates this cleanly: a vLLM variant that searches parallelism configurations instead of taking defaults performs the same as plain vLLM. Tuning parallelism without separating the phases buys nothing — the coupling, not the configuration, was the problem. Once separated, an automated search finds configurations described as "challenging to manually find," such as prefill at inter-op 3 / intra-op 3 against decode at inter-op 3 / intra-op 4 for a 175B model.

Two riders for this vault. The parallelism-selection argument is a cluster argument and evaporates on one or two cards, where there is no allocation to make. And the whole derivation assumes arrivals — with a single user issuing one request at a time, R is near zero, the queueing term vanishes, and only execution time is left, which is the regime where tensor parallelism wins uncontested and where speculation-trades-arithmetic-for-latency-without-moving-the-distribution is the lever that actually applies.
