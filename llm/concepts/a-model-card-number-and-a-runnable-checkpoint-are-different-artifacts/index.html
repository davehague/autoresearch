The card was probably honest and the download still did not work

local-inference's standing complaint is that a runtime comparison without its runtime configuration is uninformative, and its article is measured on your own machine. This source pushes the same rule one level earlier, to a gap the map had no evidence for: before configuration comparability, there is the question of whether the artifact executes.

Nanbeige4.2-3B shipped with a model card reporting competitive or better agentic and office-workflow results than Qwen3.5-4B and Qwen3.5-9B. The released checkpoint carries five independent bugs, each reproduced against the unmodified download and cited to a source line. Two of them are the ones to remember:

  • It could not be loaded on any device. A RoPE-config dispatch KeyError fires during model construction, before device placement and before a single forward pass. Not Apple-specific, not backend-specific. That is why the paper's before-figure on MCPMark is 0% — the original is unevaluatable.
  • Once loaded, it ran without positions. The rotary inv_freq buffer is silently zeroed on load (persistent=False, never restored after a meta-device load) and never repopulated. No exception, no warning. The model runs not knowing token order, and the failure presents as fluent-but-incoherent generation, which reads like a weak model rather than a broken one. Catching it requires inspecting buffer values after load — something nobody does before forming an impression of a model's quality.

The inference to draw is not that vendors falsify results. It is more useful and more uncomfortable than that: the benchmark number and the runnable artifact are produced by different pipelines. The card's numbers were plausibly obtained honestly on an internal stack with its own loader, its own kernels and its own harness. What ships to Hugging Face is a checkpoint plus trust_remote_code modeling files, pinned against a transformers version that moves underneath it, and the path from download to first token is tested by whoever downloads it first.

Two practitioner rules follow, and both are cheap. Verify the model runs correctly before you evaluate whether it is good — for a model with rotary positions, that means checking the position buffers are non-zero after load, because the failure is silent by construction. And treat "n bugs found by the first person to try it on non-reference hardware" as the expected state of a new open-weights release, not as an unusual event; bug 5 here means even a successfully-patched running model cannot be re-serialized.

This is the deployment-side sibling of what evaluation-contamination worries about from the data side. That map asks whether a reported number was earned on clean data. This asks whether the number was earned by the object you can download. Both are questions about whether a leaderboard row transfers, and this vault has had almost nothing on the second.
