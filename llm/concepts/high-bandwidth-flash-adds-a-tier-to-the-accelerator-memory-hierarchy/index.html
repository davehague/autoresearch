A new rung in the accelerator memory hierarchy, defined by a constraint this map hasn't had to reason about yet: write endurance, not just bandwidth

This map's existing tiers — CPU RAM, NVMe, layer streaming — share one binding constraint, link bandwidth against arithmetic intensity, and one operation: demote state down the hierarchy rather than distribute it across more devices. High-bandwidth flash (HBF) is a genuinely new tier in that same conceptual hierarchy, sitting between HBM (fast, capacity-limited) and host memory (slow, abundant), aimed at agentic serving workloads whose long-lived, reused KV state rewards extra capacity at high bandwidth. But HBF's defining complication is one this map's other tiers don't share: every write wears the medium, and endurance is finite, so a design that places and schedules data onto HBF carelessly can serve fast today and fail early.

The paper's contribution is architectural and scheduling characterization rather than new flash hardware: an HBM-HBF-host hierarchical design plus a buffered, cache-aware scheduler that avoids hammering the flash tier with write patterns that burn through endurance fastest. In trace-driven simulation, the fastest HBF-augmented configurations cut completion time 36.1-87.0% and energy up to 55.8% versus HBM-only systems (though some light workloads see HBF increase energy use), and the scheduling design alone extends estimated write lifetime from 4.77 to roughly 14.82 years.

This is accelerator/datacenter research, not consumer hardware — graded open-question rather than a direct map extension because HBF is not yet a shipping, broadly available component, and the paper's evaluation target (purpose-built accelerator memory hierarchies) sits outside this vault's standing one-or-two-consumer-cards question. Tracked as a forward signal: if HBF reaches consumer accelerators, the endurance-aware scheduling lesson here — don't just maximize hit rate, budget the writes — would transfer directly, and belongs in local-inference at that point.

Bound: entirely simulation-based, no physical HBF deployment or real hardware numbers. HBF itself is a storage class still being defined by hardware vendors — its real-world cost, availability, and bandwidth/endurance tradeoffs are not yet fixed. No comparison to simply adding more HBM or conventional NVMe at matched hardware cost.
