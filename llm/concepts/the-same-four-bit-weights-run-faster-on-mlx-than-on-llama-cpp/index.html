The runtime is worth 20% where it matters and 87% where it doesn't

This map's standing complaint is that every serving number in-vault is datacenter. Here is the serving stack — paged KV cache, continuous batching, prefix caching, OpenAI-compatible API — ported to MLX and Apple unified memory and benchmarked on one laptop-class machine against llama.cpp on eight models at 4 bits.

The raw result is a 21–87% throughput win. The useful result is the slope:

ModelSpeedup over llama.cpp
Qwen3-0.6B1.87×
Llama-3.2-1B1.39×
Qwen3-4B1.35×
Qwen3-8B1.21×
Qwen3-30B-A3B1.17×

The advantage decays monotonically with model size, and continuous batching scales 3.7× at 0.6B but only 2.6× at 8B, which the author attributes to memory-bandwidth saturation. Both curves say the same thing, and it is the mechanism this map already holds: single-stream decode on consumer hardware is bandwidth-bound, so runtime cleverness pays where the model is small enough to leave bandwidth unused. The corollary is the deflationary number worth remembering — at 7B–30B, the sizes this vault's premise concerns, swapping engines is worth about 20%, not 87%.

Note also the MoE datapoint. Qwen3-30B-A3B and Nemotron-30B-A3B are sparse models with ~3B active parameters, and they run at 109.7 and 121.8 tok/s — roughly Llama-3.2-3B territory on time-per-token while occupying 30B-scale memory. That is consistent with moe-inference-cost-tracks-total-not-active-params-on-edge on the memory axis while showing the active-parameter benefit on the speed axis, on a machine with 128 GB where everything fits — the condition moe-sparsity-becomes-a-transfer-budget-when-weights-are-offloaded identifies as the one that decides which currency sparsity pays in.

Graded suggestive rather than strong, for reasons the vault should keep attached to the number. The author is the tool's vendor benchmarking his own engine against llama.cpp, so these are not neutral deltas — the map already discounts this class of claim when a lab makes it about its own model. MLX 4-bit and Q4_K_M are not the same quantization scheme, so part of the gap may be a different bit allocation rather than a faster runtime, and the-gguf-quant-ladder-is-graded-not-a-cliff showed format choice can move GSM8K 3.4 points at constant perplexity. No quality evaluation appears anywhere — not one benchmark score — so this is throughput with the 4-bit quality taken on faith. No prefill/decode decomposition, which is the breakdown this map most needs given quantization-speeds-decode-and-can-slow-prefill. One machine, and an M4 Max with 128 GB at 546 GB/s is the top of the consumer range at roughly 4× a typical enthusiast's memory; the map's other Apple datapoint is an M2 Pro, so the two do not compare. Apple-only by construction, so none of it transfers to the 12–24 GB NVIDIA cards most of this map's results concern. And no energy measurement — named by the author as not conducted, which is a real gap for a laptop engine and the exact axis where the vault's Jetson result found MoE's true cost.
