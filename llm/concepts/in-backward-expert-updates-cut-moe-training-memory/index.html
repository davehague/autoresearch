MoE training memory has a fourth lever beyond total-vs-active-params accounting: when the optimizer touches each expert's gradient, not just how many experts exist

TL;DR: This map's memory accounting for MoE has mostly been about inference (resident vs. offloaded experts, bandwidth-bound decode) and about which experts to keep at what precision. Sonar-MoE is a training-time memory finding with a different mechanism entirely: standard training retains every expert's gradient until the whole backward pass finishes, so retained-gradient memory scales with total expert count regardless of how sparse the forward pass was. Firing the optimizer update the instant each batched expert tensor's gradient is ready, then discarding it, bounds retained gradient memory to one MoE layer's experts -- a training-time analogue of the architecture's own sparsity, applied to optimizer-state bookkeeping instead of compute.

What it says. The headline comparison (vs. a global-norm-clipping baseline, the common default) mixes two effects: the memory/speed win and the fact that Sonar-MoE cannot do global clipping at all, since clipping needs every gradient's norm known before any update fires, and this method discards gradients before the full backward completes. The authors isolate the architectural change from the clipping change with a second, apples-to-apples comparison (clipping off on both sides), which is where bitwise-identical weights is established -- the memory win is real but the speed win over an equally-unclipped baseline shrinks to near-zero on OLMoE, holding only on Granite (~11.6%), which the authors attribute to in-backward kernels filling otherwise-idle GPU time rather than to the update timing itself being faster. The method is restricted to element-wise optimizers (AdamW, SGD, Lion) and is incompatible with gradient accumulation beyond one microbatch (accumulation silently turns it into A separate optimizer updates per step, a different algorithm, and 5-35% slower). Stacked with 8-bit AdamW it fits a memory cap that 8-bit AdamW alone cannot -- the two techniques compose rather than compete, since one shrinks optimizer-state bytes and the other shrinks the window during which gradient bytes are retained.

Caveats. Single-GPU evidence only; data-parallel training (which needs the update to run after a gradient all-reduce) is untested. Models tested top out near 7B total parameters (OLMoE-1B-7B, Granite-3.1-3B-A800M), one dataset (8,000 Alpaca examples), one seed, bf16 fine-tuning only -- no pretraining-scale run, and pretraining's standard global-norm clipping has no compatible replacement in this paper (delayed updates / per-tensor clipping are named as future work, untested). The memory saving is batch-size-dependent and shrinks sharply once activations dominate peak memory (~2.2GB saved at batch size 32, vs. the headline ~10GB+ savings at batch size 2) -- so the practical win is largest exactly where MoE fine-tuning on constrained hardware already runs small batches, and smaller where it doesn't.
