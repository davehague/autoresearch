The host side of the offload bargain, stated by the people who maintain it

offloading-the-optimizer-demotes-memory-instead-of-distributing-it carries ZeRO-Offload's argument: optimizer state is the fattest term in a training step, it is touched once per step rather than once per layer, so demote it to CPU and pay a modest bandwidth bill. The paper's framing is about the bandwidth, and the vault absorbed it that way.

The shipping implementation prices the other side, and it is the side a practitioner runs into first: host RAM grows by 4× the model size, and gradient accumulation must be 1.

Both constraints land where this vault's premise lives. A 32–64 GB desktop trying to fine-tune an 8B model needs ~32 GB of system RAM for the offloaded state alone, before the dataloader, the OS, or a second process. And the accumulation constraint is worse than it looks: accumulation is the standard way to get a usable effective batch out of one card, so the technique that lets a model fit simultaneously removes the mechanism that made a small batch tolerable. total_batch_size = batch_size × gradient_accumulation_steps is documented on the same page; offload sets the second factor to 1.

This strengthens rather than weakens a suspicion distributed-training has carried since 2026-07-24 — that offload is the axis PEFT renders moot. ZeRO-Offload's entire win is relocating 12Ψ bytes of fp32 optimizer state, and LoRA on a 4-bit base has almost none of that to relocate. The docs say the same thing from the implementation side about a neighbouring technique: fusing the optimizer step into the backward pass shows "no meaningful impact when finetuning LoRA recipes." Two optimizer-term techniques, both documented as not paying under PEFT. The term is already small, and paying 4× the model in host RAM to shrink something already small is not a trade anyone should take.

What survives is offload of a different term. The same run's Axolotl ingest documents activation_offloading (the checkpointed activations, see activation-offload-is-a-rider-on-checkpointing-not-an-alternative) and layer_offloading (the frozen weights, see frozen-weights-can-be-streamed-which-is-a-peft-only-memory-axis) — neither of which is the optimizer state. So "offload" should stop being one axis in this vault and become three, of which the originally-sourced one is the least relevant to a PEFT practitioner.

Bounded: a documentation page, no measurement. The 4× figure is stated without derivation or a worked example, and it is torchtune's implementation rather than a property of the technique — a different framework could plausibly do better. Version-bound to the 0.6 docs, read 2026-07-29.
