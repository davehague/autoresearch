Rollout and training are two different policies

post-training-rl is written, entry by entry, as though "the policy" is one object. DPO, PPO, GRPO, R1-Zero-style verifiable-reward RL — each describes a loop where the model generates, the generations are scored, and the model is updated using the probabilities it assigned to what it generated. That last clause is the one that is false in practice.

The generation runs in an inference engine (vLLM). The update runs in a training engine (Megatron). They hold identical parameters and compute different probabilities, because floating-point addition is not associative and reduction order is fixed not by the mathematics but by the kernel, the batch shape and the parallelism layout — all of which differ between the two systems by design.

The magnitude is not a rounding footnote. Before alignment, on Qwen3.5-35B-A3B over DAPO-Math-17k, the rollout-versus-training logprob difference has mean ~10⁻³ and standard deviation ~2×10⁻³ — but an average per-step maximum of 5.073. Some token in a typical step carries a disagreement of about five nats. Ratios formed from that are not small perturbations of the intended update.

The failure mode when it bites is documented in the incidents this post cites rather than reproduces: ByteDance's VeXact study reporting that mismatch destabilizes algorithms, and a Fireworks GLM-5.2 run where clipping discarded roughly 45% of tokens and reward collapsed around step 20 under mismatched execution, against stable behaviour when bitwise aligned. The mechanism is legible — a large spurious importance ratio is clipped, the token contributes nothing, and if enough tokens are clipped the gradient signal degrades toward noise.

The hardest case is worth keeping because it shows the problem is not only about kernels. For gated-DeltaNet linear attention, training uses a chunkwise-parallel formulation and inference uses the recurrent one. They are algebraically the same function and numerically differ by mean ~10⁻⁵ with max ~0.25. Here the mismatch is a formulation choice, not an implementation detail, and no amount of kernel pinning would have removed it — it took an algorithm (CPR) that makes both phases execute the same arithmetic.

Graded open-question deliberately. What is measured is that the gap exists, that it is large at the tail, and that it can be removed by contract. What is not measured here is that removing it helps: the same run reports no meaningful reward improvement over 50 steps at a 25.3% throughput cost — see bitwise-alignment-costs-a-quarter-of-throughput-and-has-not-yet-bought-a-measured-gain. So this map should carry the precondition as a named risk with a documented failure mode, not as a recommended default.

The wider connection: two-int8-kernels-of-the-same-model-agree-on-no-sequence finds the same class of problem in inference alone — two kernels, one checkpoint, zero matching sequences — and greedy-decoding-is-nondeterministic-under-batching finds it in evaluation. The common statement is that reduction order is an unspecified free variable throughout this stack, and it is load-bearing in at least three places.

T2, self-reported by the maintainers of both engines, one model, one dataset, one node, 50 steps, with the motivating collapses cited rather than reproduced.

Rebutted by: bitwise-alignment-costs-a-quarter-of-throughput-and-has-not-yet-bought-a-measured-gain — from the same source: the mismatch is real and removable, but removing it cost 25.3% end-to-end throughput and produced no measurable reward improvement over the 50-step window, so the precondition is a documented risk rather than a demonstrated default.
