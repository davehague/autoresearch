The engine list on this map is much shorter than the engine list in the literature

This vault's local-inference map is built on the premise that the artifact and the hardware decide the result, not the method. This is the widest available table of that principle: twenty inference systems, one edge board, one over-budget model, and sixteen of them never generate a token.

The failure classes are more useful than the count, because each names a design assumption rather than a bug.

Six fail allocation. HF Transformers (both the plain and disk-offload paths), ZeRO-Inference, CATS, TEAL and SGLang attempt weight transfers that exceed unified-memory headroom, and once free memory drops below roughly 1 GiB the Jetson kernel cannot satisfy their contiguous allocation requests. Note who is in this list: CATS and TEAL are activation-sparsity methods — exactly the family the winning system belongs to — and they fail before their sparsity can help, because the allocator sits upstream of the algorithm. A method's memory story and a runtime's allocation path are different objects.

Six assume a memory hierarchy that does not exist here. vLLM, TensorRT-LLM, MLC-LLM, PowerInfer, Candle and DejaVu all treat GPU memory and host memory as separate capacity tiers, so "offload to host" is a real relief valve. On unified memory there is one physical pool, host offload creates no new capacity, and the pool is exhausted during initialization. Candle failing identically despite being a compiled systems implementation is the load-bearing detail: the authors read it, correctly, as architectural rather than framework-specific. Anyone porting a datacenter-designed serving stack to Apple silicon, a Jetson, a Ryzen AI Max or any other unified-memory machine is fighting this assumption and not a packaging problem.

Four have no ARM/JetPack build at all — LLM in a Flash, LMDeploy, TGI, HF Optimum + ONNX GPU — which is the least interesting class and the most common reason a technique in a paper is not a technique on a machine.

Two consequences for how this map reads its own sources.

The default engine keeps winning by being the only one present. llama.cpp survives here purely through OS demand paging of memory-mapped weights — no sparse execution policy, no plan, 0.34 tok/s — and it is still the strongest operational baseline among twenty candidates. Ollama inherits the same behaviour by wrapping the same core and is 5× slower than what it wraps. This map's standing observation that llama.cpp's ubiquity is a portability result rather than a performance one gets its cleanest support here: it is not fast, it is present.

A benchmark that only reports the systems that ran is reporting a survivor set. Sixteen exclusions is the most informative column in the table and it is the column a throughput comparison normally deletes. When this map next reads a serving comparison on edge hardware, the first question is which engines were tried and dropped, and for which of these three reasons.

Scope: one board, one JetPack version, one model family and FP16 throughout, so nothing here says how the same twenty behave on a 4-bit checkpoint that fits — and for most of them, fitting is precisely what would let them run. The claim is about the over-budget regime on unified memory, not about the engines in general.
