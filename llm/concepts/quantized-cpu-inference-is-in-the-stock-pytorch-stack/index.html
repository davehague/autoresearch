Quantized CPU inference is in the stock PyTorch stack

local-inference's most durable finding is that the runtime, not the model, decides what you can actually run — most sharply in the-runtime-shape-check-is-what-actually-forbids-structural-pruning, where a stock GGUF loader rejected a legitimately narrowed model because it shape-checks tensors at model width. This is the same lever moving in the useful direction.

Until now, INT8 CPU inference for transformer encoders meant leaving PyTorch: Intel Neural Compressor, Optimum Intel, an ONNX Runtime export, or IPEX's torch.jit path whose maintenance has since folded into upstream. Now it is torch.compile. Four pieces, all in-tree:

  1. TorchAO carries the SmoothQuant workflow — insert observers, calibrate smoothing factors offline, swap nn.Linear weights for a tensor subclass holding quantized weights, scales and smoothing factors.
  2. A TorchInductor fusion pass matches the scaled-INT8-GEMM subgraph and collapses it into one qlinear_pointwise that takes blocked-layout weights, applies both scales as in-kernel post-operations, and caches oneDNN metadata after warm-up — killing the three overheads that made the naive path slow (runtime layout conversion, separate epilogue, per-call setup). Weight layout conversion folds at constant-folding time.
  3. Compile-time kernel selection between that oneDNN operator and template-generated GEMM kernels, chosen by compiling and micro-benchmarking candidates once, because no single backend is best across matrix shapes.
  4. An AVX512_VNNI microkernel so older Xeons are covered alongside AMX, plus an s8s8 → u8s8 shift with a precomputed compensation c = (Σ_k W_{:,k})·128 for hardware with no signed×signed INT8 GEMM.

The practitioner-facing results are two. Use static quantization: it beats dynamic in all six model×platform configurations, because calibration moves the scale search offline, and the gap is large enough to matter (5.82× vs 5.02× on BERT-large). And the accuracy cost is not the interesting variable — every SQuAD and MultiNLI delta is under 1% and most are exactly 0.0%, with several slightly negative in a way the authors correctly read as evaluation variance rather than a benefit.

Why this map should care about an encoder result at all: BERT-family models still do most production classification, ranking and retrieval, they run on CPUs because that is where the cost profile is, and "no third-party tooling" is the difference between a technique existing and a technique being used. The pattern here — quantization frontend, compiler fusion pass, ISA-aware kernel selection, all upstream — is also the shape the decoder-LLM CPU path would have to take.
