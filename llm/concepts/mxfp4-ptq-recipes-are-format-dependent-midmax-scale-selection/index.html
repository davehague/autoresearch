A PTQ recipe's components don't transfer across microscaling formats — what helps MXFP4 can do little for NVFP4, because the two formats fail in different places

TL;DR: post-training-quantization already carries three separate allocation-axis sources (bit-width, group size, scale-code objective) that each vary one axis while holding the others fixed, and an open question (2026-11-13) asking whether any of them compose. This source runs the closest thing to that composition test the map has seen for microscaling formats specifically: it crosses Hadamard rotation granularity, PTQ algorithm choice, and scale-selection strategy across MXFP6/MXFP4/NVFP4 and six LLMs. The headline is not a single winning recipe but a format-dependence finding — MXFP4's coarse, power-of-two (E8M0) block scales leave a clipping-error gap that rotation and error-correcting PTQ close well; NVFP4's finer-grained scales already absorb more of that error on their own, so the same interventions buy much less there. The paper's own new method, Midmax, is a calibration-free scale-selection rule built specifically to reduce that power-of-two clipping error, and it improves accuracy across most of the MXFP4 configurations tested, without needing calibration data. A clean negative result travels with it: bolting NVFP4's per-tensor macroscale mechanism onto MXFP4 does not help on average — the fix has to match the format's actual failure mode, not just borrow a mechanism from a format that works better.

Why this matters for the map's open composability question. The map already names SoScale (a Hessian-weighted scale-search objective, also calibration-free-adjacent) as a prior scale-selection-axis result. Midmax and SoScale now target the same underlying choice — how a quantized value's scale code is chosen — by different principles (power-of-two clipping-error minimization vs. Hessian-weighted layer-reconstruction fidelity), and neither has been tested against the other. This source's format-dependence finding is itself a partial answer to the map's standing "do the allocation axes compose" question: at least for rotation and scale-selection, the honest answer so far is "it depends which format you're quantizing to," which argues against assuming any single recipe generalizes across this map's format menu.

Caveats. This read could not independently re-extract the full six-model list or Midmax's exact accuracy deltas — only Llama-3.1-8B is confirmed by name, and the quoted "matches or exceeds BF16" claim is the paper's own in-house baseline, not an external reference number. No institutional affiliation is stated on the paper itself; AMD authorship is inferred circumstantially from a document asset, not confirmed in the text. No code release found. No test on a mixture-of-experts backbone — this map's MoE bit-allocation findings (AlphaQ/GEMQ/Q-Strata) are untouched by this source. No consumer-hardware or non-datacenter throughput measurement; this is an accuracy/recipe study only.
