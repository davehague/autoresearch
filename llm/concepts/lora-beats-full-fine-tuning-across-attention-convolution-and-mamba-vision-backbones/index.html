This map's LoRA-vs-full-fine-tuning contest has so far run entirely on language models (and on vision backbones only for memory, never for accuracy); here it runs on vision classification backbones across three architecture families with both the rate and the weight decay actually tuned, and LoRA wins the capacity argument on five of six

TL;DR: This map's existing vision-backbone evidence (adaptive-checkpointing-peft-consumer-gpu, TinyViT/ViT-Small) lives entirely in strand 2 (the bill — peak memory under a fixed budget) and explicitly carries "no decoder-only model, no 4-bit base" as an open scope gap, with an untuned learning rate per method class flagged as a confound inherited from adapter-variant-gains-are-a-learning-rate-artifact. This source is the map's first vision-backbone evidence for strand 1 (the contest — does a low-rank update match or beat full fine-tuning), and it clears the confound this map keeps re-discovering: learning rate and weight decay are swept per method over an 8x8 grid, not shared. Under that protocol, LoRA beats FFT on 5 of 6 backbones spanning attention, convolution, and Mamba/SSM — a cross-architecture-family generalization of the capacity result this map has only ever measured within the Transformer family.

What it says.

The contest, on a new substrate. DTD (a 47-class, data-scarce texture-classification task) is scored under four transfer methods — Visual Prompting, Linear Probing, Full Fine-tuning, and LoRA — on six ImageNet-1k-pretrained backbones drawn from three architecture families: ViT-B/DeiT-B/Swin-B (attention), ConvNeXt-B (convolution), and VMamba-B/MambaVision-B (Mamba/state-space). LoRA (rank 2, 740,911 trainable parameters) beats FFT (87,601,967 trainable parameters) on five of the six: ConvNeXt (+3.42pp), VMamba (+1.70pp), DeiT (+1.70pp), ViT (+1.70pp), Swin (+1.70pp); MambaVision is the one loss (73.88 vs 75.16, −1.28pp). The win holds across all three architecture families, not just within Transformers, which this map had never tested — every prior rank/init/placement/learning-rate finding on this map was measured on attention-only backbones (and the map's own 2026-09-26 entry flags that even those findings have never been checked against optimizer-geometry sensitivity, let alone architecture-family sensitivity).

The confound this map keeps flagging is absent here. adapter-variant-gains-are-a-learning-rate-artifact and its several replications (frozen-factor-vs-band, IFCLoRA, etc.) have repeatedly found that apparent method differences on this map collapse once learning rate is tuned per method. This source tunes both learning rate and weight decay per method (and rank, for LoRA) over an 8x8 grid for FFT/LP, plus a rank sweep for LoRA — the exact protocol this map has been asking papers to run since 2026-07-30's lora-variants-learning-rate-confound arrival. A LoRA-vs-FFT margin that survives independent tuning on both sides is a materially stronger claim than most of what this map has graded T1, suggestive for exactly this reason.

The rank-floor question gets a second, contrasting data point. This map's only prior evidence on whether rank 1 can collapse is salt-subspace-aligned-ultra-lora-serving's Mistral-7B-v0.3 result: a plain r=1 LoRA scores 11.03% on MultiArith against 86.21% for a same-rank subspace-pinned alternative — a 75-point floor-collapse, not a small effect. Here, across all six vision backbones, r=1 LoRA never collapses: DTD accuracy at r=1 sits within 1-5 points of r=16 on every model (ViT-B: 76.70 at r=1 vs 77.02 at r=16; Swin: 80.00 at r=1 vs 80.00 at r=16; ConvNeXt: 76.22 at r=1 vs 76.12 at r=16). Neither source sweeps the learning rate independently at each rank, so this doesn't resolve whether the Mistral collapse is architecture-specific, task-specific, or itself a step-size artifact — but it is the map's first evidence that the r=1 floor the map worried about generalizing from one LLM case is not universal.

Strand 2 gets an unplanned data point too. Peak GPU memory for LoRA (67.5 GB) is only ~7% below FFT's (72.3 GB) on the same VMamba-B/DTD run, despite training ~118x fewer parameters — another instance of peft-does-not-reliably-reduce-peak-memory's finding that trainable-parameter count does not predict memory savings, this time for a LoRA-vs-FFT comparison specifically (the existing entry compared BitFit against LoRA/AdaLoRA/QLoRA on TinyViT). The two findings are independent instruments (different method pair, different backbone) converging on the same inversion.

Caveats. Single task (DTD) for the four-method comparison — not replicated across the paper's other seven tasks, which only re-run Visual Prompting. One seed for this comparison. The authors flag their own LoRA-on-Mamba implementation as "probably less optimized" than the Transformer implementation, so the one loss (MambaVision) and the Mamba-family margins generally may understate a tuned implementation's result. No quantized base is tested, so this says nothing about strand 2's QLoRA-specific bill. These are vision classification backbones, not vision-language models — vision-language-models and vlm-on-device are not implicated, and the mechanism transfer to LLMs is by argument (architecture-family generalization), not by direct test — this map's actual domain-acquisition-vs-task-adaptation contest (the thing that downgraded the map to contested on 2026-07-18) is about language models and remains untouched by this source. Workshop-reviewed (ES-FoMo III, ICML 2025), posted to arXiv 15 months after acceptance with no stated reason.
