The capability was bought by removing a behaviour

The benchmark story here is a near-tie with a model a third larger — RefCOCO 87.9 against InternVL 3.5-4B's 88.8, MMBench 81.0 against 81.1, DocVQA 91.1 against Qwen3.5-2B's 92.6 — and the generation-over-generation deltas are enormous: ScreenSpot-v2 Desktop from 6.0 to 78.7, RefCOCO +30.8, ToolSandBox +33.1. Read alone, that says a 3B model closed the gap to the 4B class.

Read with the vendor's own scoping, it says something more precise and more useful. The post states the model "answers directly instead of reasoning, so responses stay fast," recommends it for single-turn, high-throughput, low-latency work — OCR with layout analysis, object detection, on-device translation — and explicitly does not recommend it for "long-context, reasoning-intensive tasks." The near-parity is on grounding, screen understanding and document reading: tasks where the answer is located in the image rather than derived over several steps. Where multi-step behaviour is scored, the picture is duller — BFCL V4 tool use reads 32.5 against a 2B baseline's 33.2, essentially flat.

This is a design choice made legible, and this map should record it as one. The edge VLM story is usually told as compression: take a general model, shrink it, lose a little. This artifact was not built that way. It was built to be good at the class of task where perception is the whole job, and the reasoning behaviour was traded away deliberately for latency. So "a 3B model matches a 4B model" is true within a task family that was selected for, and the honest framing is that on-device VLM capability is currently purchased by narrowing the job, not by compressing a generalist.

That connects to two things already in the vault. It is the practical form of quantization-preserves-the-answer-and-changes-the-derivation — precision loss attacks multi-step derivation first — arrived at from the product side: if derivation is the fragile part, a model for constrained hardware can simply not do it. And it sits against vision-language-models's architecture contest without settling it: this is a late-fusion design (a separate SigLIP2 encoder projected into a text backbone), so it adds a shipped, measured point to the late-fusion column without anyone having run the early-fusion comparison at this size on this hardware — which is that map's own standing complaint.

The reason to hold it at single-study and to keep it out of any capability claim: every number is vendor-reported, the baselines are vendor-chosen, there is no independent replication, and the comparison this vault would actually want — the same tasks scored against a quantized general 7B–8B VLM at a matched 3 GB footprint — is exactly the comparison at-a-fixed-footprint-take-the-larger-quantized-model says usually goes the other way, and it was not run. The strong version of this claim is one experiment away and nobody has done it.
