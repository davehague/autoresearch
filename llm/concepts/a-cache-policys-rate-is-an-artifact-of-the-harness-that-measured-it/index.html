Two conflations, and both of them inflate the number in the paper's favour

kv-cache-management's founding question is "given a fixed budget, what do you keep and in what form," and its scoring rule has been quality retained against bytes retained. This is the first source to attack the denominator.

Chunked teacher-forcing. In real decode the model appends one token and issues one query per step. In chunked evaluation an implementation appends tens or hundreds of target tokens in a single call; the logits can still be masked causally, and the arithmetic is still correct — but the cache policy sees the whole chunk as a current, unquantized region. Measured on one implementation of KIVI, the resident rate moves from 5.03 bits/value at chunk 64 to 5.69 at chunk 1024. Same policy, same model, 13% different compression, decided by a harness setting that has nothing to do with the method. Any comparison run at different query lengths is not rate-matched, and almost no paper reports the chunk size.

Resident bits versus read bits. The resident cache is what must fit in device memory; the read rate is how much of it a query must touch. Query-sparse methods report the selected bytes as though they were the resident capacity. Under separated accounting, Quest keeps exact K/V resident plus min/max page summaries, so it costs more VRAM than storing the cache uncompressed (+1.6%) — its traffic efficiency buys no capacity at all. Two different resources, one reported number, and the number quoted is the flattering one.

The consequence for this map is uncomfortable and should be carried plainly: a meaningful fraction of the retention-versus-bytes comparisons already on this map were scored on one or both of these conflations, and none of them state the chunk size or separate resident from read. cache-compression-must-be-scored-query-agnostic identified a related leak from the query side — a policy tuned on the queries it will be scored against — and this is the same failure at the harness level rather than the policy level. Together they say the map's scoring rule needs three numbers, not two: resident bits, read bits, and the query length they were measured at.

The paper also enforces the causal discipline it demands, which is the reason to trust its own numbers: an EMA of attention mass (0.9/0.1) as the demotion signal so no future query leaks into policy state, GQA-shared KV heads allocated once per KV head rather than once per query head, and regression tests for both leaks. Its rate accounting checks out end to end — real packed format from real K/V measures 1.959 bits/value against a predicted 1.990, mildly conservative.

What keeps this at the methodological level rather than a method win: the baselines are local semantic ports on a shared attention path, not version-pinned original kernels, which the authors say is fine for causal comparison and no substitute for an official benchmark. So the 5.03→5.69 swing is demonstrated on their KIVI, not on KIVI. The direction of the artifact is not in doubt — a chunk the policy treats as current cannot be compressed — but the magnitude on any given implementation is untested.

Read alongside: a-per-head-mask-is-not-a-freed-byte — an independent group finds the same species of inflation one level down, in the storage layout rather than the harness: per-head selections stored as masks over one equal-slot tensor free no memory at all, and enforcing the nominal budget on the same selection costs 14.1 to 62.2 benchmark points. Three locations now, three groups. The scoring rule this note argues for needs a fourth column — materialized or masked. The same source also puts a ceiling on the numerator this note is defending the denominator of: keeping-the-largest-attention-weights-is-already-near-optimal finds top-k already within a median 2.1–4.7% of an oracle subset, so with almost no retention slack left, the whole retention-versus-bytes argument moves onto the bytes side — exactly where this note found the accounting broken.
