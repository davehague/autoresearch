The fastest way to offload an MoE too big for one card depends on the specific model-platform pair, and a cheap emulator can pick it without building and timing every candidate — including on the two consumer cards this vault's offload complaints have never had a tool for

TL;DR: This map's standing offload-economics thread (resident-vs-offloaded Mixtral on a T4, OLMoE on an M2 Pro/Jetson, ThunderEP/CoMoE's PCIe-native expert-parallel fixes) has repeatedly found that offload performance is substrate-specific and that "nothing in either result is reachable from the local stack" because the numbers depend on custom kernels or trained components nobody can run. COPE (Shanghai Jiao Tong University) doesn't add a new offload mechanism — it adds a cheap predictor for which existing policy (what stays resident, how CPU/GPU execution is scheduled) will be fastest for a given model on a given card, validated against nine actual llama.cpp implementations, including on an RTX 4090 and an RTX 5090 at varying VRAM reservations — the first in-vault instrument that measures MoE-offload policy selection on consumer hardware this map's audience could plausibly own.

What it says.

The setup. Offloading an MoE that doesn't fit resident involves two coupled choices — which experts stay resident, and whether CPU-side and GPU-side execution for a batch run serially or overlap — and this map has already established that the best static choice changes with hardware (local-inference's T4/M2 Pro/Jetson results) and that per-expert communication fixes (ThunderEP, CoMoE) are substrate-specific and untested against each other. COPE's contribution is not a new offload mechanism but a way to choose among existing ones cheaply: it factors the design space into a Policy Matrix (residency x execution strategy, exposing four combinations nobody had tried) and profiles combined-operator schedules once per platform rather than once per policy, combining that profile with offline routing-trace statistics.

The method. Ground truth comes from nine actual llama.cpp implementations across Qwen3.5-35B-A3B, Qwen3-30B-A3B, DeepSeek-Coder-V2-Lite-Instruct and DeepSeek-V2-Lite-Chat, run on an A100-SXM4-80GB (varying CPU workers, MPS share, VRAM cap), an RTX 4090 (24 GiB, dual Xeon Gold 6430), and an RTX 5090 (32 GiB, evaluated at 16/12/8 GiB VRAM reservations). Two baselines are compared: an atomic-operator-composition model (each operator's cost measured independently, composed by max/addition rules, inspired by LLMServingSim 2.0) and a hierarchical roofline model (from MoE-Lightning, bounding latency from peak compute/memory/interconnect throughput).

The result. COPE selects the measured-fastest policy in 134/150 A100 cases, 20/20 RTX 4090 cases, and 42/45 RTX 5090 cases, against the atomic-operator baseline's 5/50-36/50 per-model A100 accuracy and much lower top-3 overlap on the 4090 (59/60 for COPE vs. 24/60). Prediction error against the roofline baseline falls from 61.5-68.5% to 9.4-17.4% (RTX 4090) and 47.2-53.9% to 8.0-13.3% (RTX 5090). The engineering payoff is separate from the prediction accuracy: picking the right policy up front instead of implementing every candidate saves up to 74% of policy-specific code for a given model-platform pair.

Caveats. No code or weights release stated. Both comparison baselines are the paper's own reimplementations of ideas from other systems (LLMServingSim 2.0, MoE-Lightning), not head-to-head against those systems' own released code. All ground-truth measurements are llama.cpp-specific; no vLLM/SGLang offload path is tested. The policy space COPE searches is residency and scheduling only — it does not vary or predict the effect of quantizing the offloaded experts, so it does not itself answer this map's open "does quantizing the experts make speculative decoding profitable on an offloaded MoE?" question, though it is now the closest in-vault tool for running that question's hardware half.
