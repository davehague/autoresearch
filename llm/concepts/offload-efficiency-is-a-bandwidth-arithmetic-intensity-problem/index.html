Offload has a formula, and it says activations are cheap to move and the optimizer is expensive

Every other memory-axis source in this vault argues its case by demonstration. This one supplies a model. Define arithmetic intensity ait = total_computation / total_data_movement for a class of state, take your accelerator's achievable throughput peak_tp and the bandwidth bw of the tier you are considering, and

efficiency = ait × bw / (ait × bw + peak_tp)

Three numbers you can measure, one answer. Applied per state class it produces a ranking that inverts the intuition this vault has been carrying:

  • Activation checkpoints are the cheapest thing to offload. ait = 24 × hd × ci, so a meager 2 GB/s sustains >50% efficiency at hidden size 2K, dropping below 1 GB/s past hidden size 8K. Ordinary PCIe is an order of magnitude more than enough.
  • Parameters and gradients are moderate. ait = seq × bsz; above 70 GB/s you clear 50% efficiency even at the smallest batch.
  • Optimizer states are the most expensive. ait = seq × bsz / 4, needing 4× more bandwidth, and at batch size 2 per GPU roughly 1.5 TB/s for 90% efficiency — more than GPU memory bandwidth. The reason is structural: the optimizer step runs at the end of the iteration and has no compute to overlap with.

That last point sits in genuine tension with offloading-the-optimizer-demotes-memory-instead-of-distributing-it, and a practitioner needs both halves. ZeRO-Offload demotes the optimizer because its compute is batch-independent — the one stage you can afford to run slowly. ZeRO-Infinity warns that its bandwidth demand is the highest of any class because it cannot be hidden. Both are true; they are statements about different resources.

The engineering move that resolves it generalizes well past offload: bandwidth-centric partitioning. ZeRO-3 and ZeRO-Offload give each parameter one owning process that broadcasts it, so exactly one PCIe link is active and CPU/NVMe→GPU bandwidth caps near 12 GB/s regardless of GPU count. Partitioning every parameter across all processes and using an allgather moves identical volume on the GPU side but pulls on every PCIe link at once, reaching 48 GB/s (CPU) / 25 GB/s (NVMe) per node and growing linearly with nodes. The transferable lesson: when a resource is slow, check whether you are using one instance of it or all of them.

For this vault's premise the actionable consequence is the activation line. PEFT deletes most optimizer state, which is why offload looks moot under LoRA — but rematerialization-trades-compute-for-the-activation-memory-nothing-else-shrinks establishes that activations are the one term PEFT cannot shrink, and this source says activations offload at under 2 GB/s. CPU activation offload during a 4-bit LoRA fine-tune is therefore the piece worth stealing, and nobody in-vault has measured it.

Bound: peak_tp = 70 TFLOPS/GPU is a single empirical measurement on one V100 DGX-2 box, and every efficiency curve inherits it. The analysis holds bandwidth infinite for all classes but the one under study, so it prices each in isolation and says nothing about contention when several are offloaded at once — which is the actual configuration.

Rebutted by: batching-an-ssd-offloaded-moe-goes-backwards-past-eight-streams — the formula's remedy for a low-bandwidth tier is to raise arithmetic intensity by batching; measured on an SSD-offloaded 235B MoE, throughput rises to batch 8 and then falls 47% by batch 32 from paging thrash. Holds for the analytic efficiency, not for the runtime: the concurrency knob has a cliff, not a ceiling.
