Cache compression charges throughput and pays only under pressure

local-inference has asked for this number three times. Its 2026-07-29 open item said plainly that no speed number exists for KV quantization at all in either of the vault's KV sources, and that this matters more than for weight quantization because the KV quantizer sits on the critical path of every attention call. The number has arrived, inside an ablation the authors published to justify a different claim, and it is a 5.3× penalty.

The four cells are the whole finding. With the model resident, moving the cache from FP16 to a fused 3-bit representation takes throughput from 109.8 to 20.6 tok/s and saves 99 MB — a rounding error against a 10.6 GB footprint. With experts offloaded to disk, the same swap moves 1.01 to 1.05 tok/s. So the compression neither helps nor hurts once transfer dominates, and it is straightforwardly harmful when nothing is being transferred. The authors state the rule themselves: the method "is counterproductive when the model comfortably fits in memory."

This is the third independent instance of one pattern and it is now stateable as a rule rather than a coincidence. speculation-and-quantization-compete-for-the-same-headroom found two levers cancelling because both spend idle arithmetic. the-attention-backend-decides-whether-cache-compression-pays found the same KV method at +9.8% under eager attention and −59% under FlashAttention-2. Now a cache method's sign is decided by whether the weights fit. In every case the method's own quality number was fine and its throughput sign belonged to the configuration around it. The operating form for a reader: ask what currency a lever spends before asking what it saves, and treat a compression result with no throughput measurement as a claim about capacity only.

Two secondary effects worth carrying. Compression made decode 18× more stable — inter-run coefficient of variation 5.4% → 0.3% — which is the kind of thing that matters on a laptop sharing memory with everything else and that no other source here reports. And fusion is the whole method: run the same compression without the fused attention kernels and it costs 44% of prompt throughput against a llama.cpp baseline instead of 0.5%. A KV-quantization flag in a runtime that dequantizes before attention is a different technique from the one measured here, which is a warning about llama.cpp's and Ollama's own KV-quant options rather than an endorsement of them.

The honest limit is that this is one model, one machine, one bit-width, on Apple unified memory where the offloaded case reads a barely-usable 1 tok/s. Whether the crossover sits somewhere more interesting on a discrete card with a PCIe boundary — the configuration most of this map's readers have — is unrun.
