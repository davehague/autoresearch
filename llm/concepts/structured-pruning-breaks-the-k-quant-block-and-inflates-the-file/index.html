You pruned the checkpoint; you inflated the file

structured-pruning has been arguing about the FP16 checkpoint. Which axis to cut (the-pruning-axis-that-preserves-quality-is-not-the-one-that-buys-speed), whether the requested ratio is delivered (a-pruner-misses-the-compression-ratio-you-asked-for), what the quality costs (a-quarter-of-the-parameters-costs-an-eighth-of-the-capability). Every one of those is a statement about a model that is not yet deployable on a consumer machine, because deploying it locally means converting it to GGUF and quantizing it.

That conversion step has a constraint nobody in the pruning literature models. k-quant formats operate on 256-element super-blocks. A width pruner removes individual MLP channels, which leaves feed-forward dimensions that are not multiples of 256. The converter cannot express those tensors in the target format, so it falls back to a higher-precision encoding — 24 of 320 tensors for Qwen3.5 0.8B — and the resulting Q4_K_M file is bigger than the unpruned model's: +21%, +33%, +49% across three families.

On a GPU that is an annoyance. On the hardware pruning exists for, it is the whole ballgame. Decode is memory-bandwidth-bound and re-reads the full weight set on every generated token, so a 21–49% larger artifact is paid N_gen times, while the compute-bound prefill pays it once. The measurement follows exactly that shape: token-weighted per-token decode cost rises in all eighteen matched baseline-versus-pruned pairs, in the same cross-family order as the byte growth, while prompt evaluation moves by at most +16% — and moves up, because the higher-precision fallback tensors make prefill slightly more expensive too. Nothing about pruning got faster anywhere.

The paper separates a second, independent slowdown that would otherwise be confounded with this one. Pruning damages output discipline before it removes knowledge: pruned models get verbose and less format-compliant, and Qwen3.5's mean SQuAD answer grows from 29 to 61 characters. Gemma's slowdown is almost entirely this (+168.5% tokens against +6.1% per token); TinyLlama's is almost entirely byte traffic (+24.7% per token against +10.9% tokens); Qwen sits between. The LoRA-recovered TinyLlama variants — barely longer than baseline yet nearly twice as slow — are the clean case that isolates the byte-traffic term.

This is the first concrete instance of the composition question post-training-quantization posed on 2026-08-16, and it arrives from an unexpected side. That question anticipated a quality interaction between two compressions at four bits. This is a size and throughput interaction, and it is worse than non-composition: one lever silently reverses the other, through a format detail that appears in neither method's paper.

The practitioner form is blunt and, for the sub-1.5B GGUF case, close to a rule. If the deployment target is llama.cpp, structured width pruning is dominated by moving down the quant ladder — the ladder is graded (the-gguf-quant-ladder-is-graded-not-a-cliff), it shrinks the file monotonically, and it does not fight the block structure. The narrow exception the same source documents is vision: for segmentation models, default quantization leaves parameters and MACs untouched and cuts storage by 0.63%, so pruning is the only lever that does anything at all.

Two bounds, both material. The pruner is one method at low ratios (DepGraph-MLP, ~1–10%), which is the configuration this vault's own pruning map already flags as buying the least speed; a depth pruner removing whole blocks would keep the widths aligned and this failure mode would not arise. And the models are sub-1.5B — the arithmetic scales the same way at 7B, but nothing here measures it. The mitigation is obvious and untested here: prune to multiples of 256, or prune along depth instead of width.

Rebutted by: the-runtime-shape-check-is-what-actually-forbids-structural-pruning — narrowly, on the mitigation this note proposes. "Prune to multiples of 256" assumes the obstacle is block alignment inside the quantizer. On a depthwise-convolution model the stock GGUF loader creates the tensors at fixed model width and shape-checks them, rejecting a real narrowed artefact (check_tensor_dims: expected 3,768, got 3,640) with a full-width rebuild through the identical writer as the control. Alignment is a gate; the loader is a prior one, and it does not care what the width is a multiple of.
