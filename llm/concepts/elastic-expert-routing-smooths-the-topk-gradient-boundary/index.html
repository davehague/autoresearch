Top-k routing's hard cutoff silently zeroes the gradient for near-tied experts every step; sampling the active count around k during training fixes this without touching inference

This map's existing routing findings describe what routers learn (syntax, not topics) and how to prevent collapse (balance losses, router z-loss) — both about the router's learned policy. This paper attacks a different, more mechanical problem: top-k routing imposes a hard rank cutoff on a continuous score distribution, so an expert scoring just below the threshold gets exactly zero gradient from the task loss every single step, even when its score is statistically indistinguishable from the expert just above it. Elastic Expert Routing samples the active count kappa per token per layer from a window around k0 during training (schedules 7-9/6-10/5-11, symmetric so expected compute matches the fixed baseline exactly), leaving inference untouched — static top-k, same serving cost, same memory-tracks-total-params accounting this map already carries.

The ablations are the valuable part: this is not simply "more active experts helps." Budget-matched controls (fixed top-9, fixed top-10, top-p routing at matched average activation) all underperform the elastic 6-10 schedule, ruling out "more compute on average" as the explanation. A router-swap ablation — put the elastically-trained router into the statically-trained expert set, and vice versa — shows most of the gain requires the co-adapted pairing: the router alone recovers almost none of the improvement (30.86 vs the 30.57 baseline and 31.41 full result). And an expert-selection analysis shows the mechanism is mostly about reordering priority within a largely shared expert set (top-8 set differs only 7.08%, ~0.57 experts) rather than routing to meaningfully different experts.

Where it sits against this map's edge-deployment findings. Because inference is completely unchanged (static top-k, no architecture change), this training-time intervention does not touch the map's hard-won edge-deployment accounting (OLMoE-1B-7B's bandwidth-bound disadvantage on M2 Pro/Jetson Orin, the MoE x quantization and MoE x offload results) — it is a free quality improvement orthogonal to every serving-side finding this map carries, assuming it replicates at the scales those findings were measured at.

Caveats carried from the source. Pretraining validation is at 1.42B-total/0.365B-active only — the authors call it "a controlled validation... at a moderate scale" and explicitly defer larger pretraining to future work, so whether this holds at Mixtral/DeepSeekMoE-class scale (where this map's other pretraining findings live) is untested. No seed/variance reporting anywhere — every number is a single run. The paper's own claim of winning on "all nine" SFT tasks is contradicted by its own table (5-11 leads GPQA, 7-9 leads MBPP) — the aggregate win is real, the universal per-task claim is not. No code release stated.
