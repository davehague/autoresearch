A new axis on the allocation-unit debate: search over quantization granularity (group size) with bits fixed, rather than search over which unit gets more bits with granularity fixed -- and an LLM-driven search policy where this map has only seen analytic signals

TL;DR: This map's recurring allocation-unit debate (GEMQ's global-over-every-expert allocation, Q-Strata's bi-level reframing in mixture-of-experts, and this map's own dense-model convergent finding) has so far always fixed the search method (an analytic signal — HT-SR power-law tail exponent, Fisher information, a cheap global/local proxy) and searched over which unit (layer, block, expert) gets more bits. AutoQS inverts this: bits per se stay fixed, and the search is over group size — the granularity at which quantization scale parameters are shared — using an LLM itself as the proposal engine, in the FunSearch/AlphaEvolve lineage of LLM-driven program/heuristic search, applied here to a quantization-configuration search space. Evaluation history and a candidate repository (tracking previously-tried allocations by canonical representation) guide the LLM's coordinated edits across layers and operators; deterministic validation enforces configuration compatibility; a cheap proxy scores most candidates, with periodic actual quantization keeping the proxy calibrated against measured accuracy and checkpoint storage. On Qwen2.5-7B-Instruct at 4-bit, this beats uniform-group GPTQ by 0.70 points and uniform-group AWQ by 1.12 points (seven-task average).

What it says. Bit-width allocation and group-size allocation are formally separable axes of the same quantization-configuration space, and nothing in this vault — including AutoQS itself — has tested whether they compose: an allocation that is simultaneously bit-heterogeneous (GEMQ/AlphaQ-style) and group-size-heterogeneous (AutoQS-style) is an open, concrete, and cheap-to-pose experiment this map's allocation-unit debate has not yet reached. AutoQS's LLM-as-search-policy approach is also the map's first instance of using a general-purpose LLM, rather than a quantization-specific analytic signal, as the allocator — raising a direct, currently unanswered question against the map's existing analytic allocators (AlphaQ, the Fisher-screener): at matched evaluation budget (number of actual-quantization runs consumed), does LLM-driven search find better allocations, or just more expensive ones for a comparable result? AutoQS's own paper does not report this comparison.

Caveats. Evaluated on a single model (Qwen2.5-7B-Instruct) at a single bit-width (4-bit) — this map's own evidence says allocation choices matter most at 2-3 bits, where AutoQS is untested, and on mixture-of-experts backbones, where group-size allocation would interact with mixture-of-experts's routing-sparsity questions in ways neither map has evidence for. The absolute accuracy gain is modest (0.70-1.12 points), no code release is stated, and no latency/throughput number accompanies the accuracy and checkpoint-storage results — this map's standing "accuracy-only, no speed number" gap, named repeatedly for other allocation methods, applies here too. The search's own compute cost (LLM API calls plus periodic real-quantization validation passes, versus a brute-force or analytic-signal baseline at matched final quality) is not reported in the fetched abstract/intro text.
