A speculative-decoding drafter's own aggregate accept-rate-vs-context-length curve can be hiding the opposite trend inside any single trajectory phase -- so this map's existing "does acceptance degrade with context/temperature" measurements need to be read per-phase, not pooled, before they can be trusted for agentic workloads

TL;DR: This map's open question about what speculation costs on agentic workloads has so far been answered with aggregate numbers -- accept rate as a function of context length or temperature, pooled across however many tool calls a trajectory happens to need. This source names a confound in that practice directly: on five existing drafters (DFlash, EAGLE-3, DSpark, LongSpark, DLite), pooled accept rate rises with context length while the same drafters' accept rate falls within a matched late-stage phase of the same trajectories, because later phases disproportionately contribute the longer-context examples to the pooled statistic. That is a pushback on any claim in this map stated as "accept rate rises with context" if the underlying measurement pooled across trajectory phase without checking for this -- not a claim this map has made explicitly yet, but exactly the kind of measurement its own open question ("nobody reports the temperature, and the effect is the size of the method differences") already worried about for a different confound (sampling temperature). The fix TraceSpec builds — train on intermediate turns, allocate budget from a state-conditioned, prefix-aware acceptance-gap estimate — buys a real 12.5-22.6% replay-throughput gain over its own DSpark base, but the gain collapses to 1.4-5.5% once the agent's own feedback loop is live rather than replayed, which is itself the sharpest instance yet in this map of a result inflating under a fixed-history replay protocol relative to genuine online serving.

What it says. TraceSpec-Traj stratifies 10,000 training and 2,500 test assistant-turn states by domain (web browsing, software engineering), context-length stratum, and trajectory phase (plan/act/reflect/answer). Evaluated on this corpus, five existing speculative baselines show the described disagreement between pooled and within-phase accept-rate trends. TraceSpec itself (a DSpark-architecture drafter trained on intermediate turns, with a fixed per-step prediction budget allocated by a state-conditioned prefix-aware acceptance-gap estimate) gains 12.5-22.6% replay throughput over its own DSpark base across Qwen3-4B/8B/14B targets at two temperatures, in 15 of 18 settings (native-PyTorch runtime comparisons; LongSpark on SGLang excluded from this specific comparison). A Qwen3-4B ablation isolates the adaptive-budget-allocation contribution alone at +3.3-10.0% accepted length over fixed full-turn supervision. In live dynamic execution — 100 tasks per workload on BrowseComp-Plus and SWE-bench Verified, with the agent's own tool feedback actually running rather than replayed from a fixed saved history — greedy throughput improves only 1.4-5.5%, a gap the paper reports without obscuring it behind the larger replay number.

Caveats. The paper's own replay-vs-dynamic gap is the strongest evidence here that most of the headline 12.5-22.6% figure is a property of the fixed-history replay protocol, not of live agentic serving — which narrows rather than closes this map's standing "what does speculation cost on agentic workloads" question, since the live number is closer to what a deployed agent would see. The adaptive-allocation ablation runs only on Qwen3-4B. Dynamic evaluation is 100 tasks per workload, a modest sample for an agentic benchmark. Thinking mode is disabled throughout. Throughput comparisons exclude the SGLang-based LongSpark baseline; only episode latency is compared there. All numbers are from the authors' own harness. Code is released at github.com/Robot2050/TraceSpec, which makes the within-phase-vs-pooled confound independently checkable against other drafters in this map's provenance comparison, an open question this map already tracks.
