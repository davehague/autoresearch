The weights you need next are mostly the weights you have, and that is a scheduling fact before it is a compression one

This map has priced demotion as a bandwidth problem — offload-efficiency-is-a-bandwidth-arithmetic-intensity-problem compares transfer time against compute time and prescribes raising arithmetic intensity until the link is hidden. That framing assumes the transfer is a given quantity. This source finds it mostly is not: across tokens, 82–85% of a sparse layer's active MLP rows are the same rows, so the per-token storage job is the delta, and the fetch volume is a variable the runtime controls rather than a constant it must hide.

The consequence is measured on hardware, which matters here more than usual. The map's most recent arrival, expert-prefetching-is-governed-by-the-worst-layer-not-the-average, established the prefetch-with-a-learned-budget pattern in simulation — RTL synthesis, Ramulator, a cycle-accurate co-simulator, and an explicit statement that no hardware prototype exists. This is the same pattern on a board you can buy, against a baseline anyone can reproduce, and the mechanism survives the transfer intact.

The failure it replaces is worth naming precisely, because it is the default. When a model exceeds resident memory, llama.cpp falls back to memory-mapped weights and OS demand paging: 11,453 major page faults per second, the CPU 77% blocked on I/O, the GPU at 3%. Nothing is computing. This is what nvme-offload-removes-the-model-scale-ceiling looks like when the ceiling is removed and nothing else is done — and it is the same shape as batching-an-ssd-offloaded-moe-goes-backwards-past-eight-streams, where an 8 GB card serving a 134 GB model regressed 47% past B=8 from OS paging thrash. Both failures are the operating system moving weights reactively. Both fixes are the application deciding instead.

What makes the prediction early enough to be useful is a structural choice this map should keep. Prior sparse runtimes (DejaVu) predict a layer's active set when execution reaches that layer, which is too late to overlap I/O. Here one predictor runs after layer 0 and emits the whole plan — 62 centroid IDs covering gate and up projections for layers 1–31 — in a single forward pass, from five cheap layer-0 features. Predicting identities early rather than masks accurately is the same inversion APEX made when it swapped accuracy for coverage, and it recurs because the binding constraint is the schedule, not the classifier.

Three things are load-bearing and easy to lose in the headline.

The predictor is priced in. 206.8M parameters, 2.86% of the base model, 414 MB resident in FP16, and every speedup is net of it. Its own error contributes almost nothing to the quality loss — 99% of layer decisions pick the correct centroid, so what the quality numbers measure is the offline clustering, not the runtime prediction.

Quality is a knob, not a constant. The dense prefix length d splits GPU memory between fully resident early layers and active-row buffers for the rest, and it is simultaneously the memory dial and the quality dial: at d=20, Mistral-7B keeps 95–96% of dense HellaSwag and Llama-3-8B 92–93%, and both degrade as d shrinks to fit tighter budgets. There is also a cliff on the other side — past the optimum d* the prefix starves the suffix of buffer space, layers fall back to whole-layer reads, and throughput drops 1.60 → 0.98 tok/s at one step. d* moves with sparsity (14 at 62%, 8 at 50%, 2 at 31%) and is a one-time calibration per hardware setting. This is the second cliff-not-ceiling result on this map, and the same practitioner rule applies: tune until throughput stops improving and you have already walked past the optimum.

The technique retires at the crossover, and the paper says so. Once the model fits — 13.9 and 14.8 GiB here — llama.cpp jumps to 5.9 and 7.7 tok/s and the advantage collapses to 1.2× and 1.1×. This is a regime tool. The honest reading is that it converts an unusable configuration into a slow one, not a slow one into a fast one.

Where it does not reach, and this is the discount that matters most for this vault. Everything is FP16. There is no quantized arm anywhere; the baseline is llama.cpp on an FP16 checkpoint, not Q4_K_M. A 4-bit Mistral-7B fits inside 11.9 GiB comfortably, so on this exact board the model-exceeds-memory regime is entered by declining to quantize — which is not what a reader of this vault would do. The interesting untested question is the composition: at 4 bits the resident footprint is a quarter the size and the 82–85% locality has no reason to disappear, so the same machinery should let a much larger model into the same regime. Nobody has run it. One board, one SSD, two models, no seeds or intervals on the throughput figures.
