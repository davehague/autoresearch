The first KV-cache codec trained end-to-end against the frozen model it compresses, rather than fit offline by PCA and a reconstruction-error bit-allocation rule -- and the training-together step itself, not just the components it trains, is where part of the gain comes from

TL;DR: This map's "spending a fixed budget" sub-thread already has several trained mechanisms that decide what to keep or evict (TokenGate, AbridgeKV). DCKV (MIL Team/DAIMLD) adds a different kind of trained mechanism: not a keep/evict policy but a codec -- the transform that maps cache entries to a compressed representation, the quantizer, and the entropy model that assigns code lengths are all trained together, end-to-end, against the frozen downstream model's own output distribution. The prior best comparable method (KVTC) fixes its transform by PCA and its bit allocation by a reconstruction-error heuristic with dynamic programming -- a pipeline of independently-optimized stages rather than one model trained on the actual downstream objective. On a hybrid model (Qwen3.5-2B, 6 of 24 layers full-attention) DCKV needs 72% fewer bytes than KVTC at equal RULER-4K score.

What it says.

The setup. Hybrid models (Mamba/Gated-DeltaNet-style linear-attention layers mixed with a few full-attention layers) keep a KV cache only in the full-attention layers, but that cache is still the only part of a stored request's state that grows with context -- 12,288 bytes/token in bf16 on Qwen3.5-2B, reaching 1.5 GiB at 128K tokens, next to a fixed 9.84 MiB recurrent state. DCKV compresses this cache with a learned encoder (linear transform plus small nonlinear correction network), a learned per-component quantization step, and GPU rANS entropy coding, all optimized jointly against a rate-plus-distortion loss: bits under the entropy model, plus lambda times the KL divergence between the frozen model's next-token distributions computed from the exact vs. reconstructed cache. Two conditional entropy models shift each code's predicted distribution using information the decoder already has -- one from the prompt token's embedding, one (checkerboard-ordered) from already-decoded neighboring positions -- so the codec learns to not spend bits on what these predictors already capture.

The result. At lambda=3e5, DCKV stores 205-221 bytes/token (56-60x smaller than bf16) at 0.45-1.75 points of loss across three long-context benchmarks (RULER 4K, LongBench, RULER 32K). Against KVTC at a comparable 16x compression ratio, DCKV needs 72% fewer bytes at equal RULER-4K score and 62% fewer at equal LongBench score (Bjontegaard-delta rate); at stronger compression (113-122 bytes/token) DCKV beats KVTC's 32x operating point (304-356 bytes/token) on all three benchmarks while storing 2.5-3.1x fewer bytes. Against xKV (cross-layer low-rank sharing, counting its per-prompt basis), DCKV needs 96-97% fewer bytes while losing less. An ablation adding each component to an untrained PCA/static-entropy baseline shows training the transform's nonlinear correction and the conditional entropy models together saves more bytes at equal score (16%/13% on RULER 4K/LongBench) than either saves added independently (5.5%/8.7%) -- the paper's central mechanistic claim, that end-to-end joint training of codec and entropy model is itself load-bearing, not just the presence of each trained component.

Where the advantage matters. Because a hybrid model's fixed recurrent state dominates short-prompt memory (73-81% of a stored request's memory at 4K-11K tokens), DCKV's bytes-per-token advantage over KVTC only becomes a memory advantage past roughly 32K tokens, where the KV payload itself exceeds a third of request memory -- at that length DCKV scores 6.5 points higher than KVTC at matched memory.

Caveats. One model (Qwen3.5-2B), one hybrid architecture family (Gated DeltaNet); untested on a standard all-attention transformer or a different hybrid design (Mamba/Jamba). Each compression rate needs its own full training run (25.9-33.9 hours on two A100s per loop reported) -- no single codec serves a range of rates, and the paper's own variable-rate attempt underperforms a dedicated codec at the upper end of its range for a cause the authors could not identify. The 32K-token numbers are computed from the measured per-token rate rather than directly measured, and the paper flags this likely overstates DCKV's relative advantage there (DCKV's realized 32K payload runs 3% above its 4K rate; KVTC's runs 12-14% below). DCKV restores the full bf16 cache before decoding, so it does not reduce peak GPU memory or per-token decode latency -- no throughput or latency number is reported anywhere, only bytes-per-token and benchmark score, which this map's own evidence check (2026-08-06 downgrade) already holds to be an incomplete picture of what a compressed cache actually buys at serving time.
