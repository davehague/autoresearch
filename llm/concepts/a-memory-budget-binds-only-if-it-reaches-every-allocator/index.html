A memory budget binds only if it reaches every allocator

This is the second finding in three days on local-inference where the thing that decided a local machine's behaviour was an allocator, and the two arrived from unrelated directions.

the-cpu-inference-bottleneck-was-the-memory-allocator (2026-08-06) found that swapping the process memory allocator outweighed every kernel change on a CPU inference backend. This is one level up. Here a memory policy exists — one user-visible number, the whole point of the design — and it is silently violated by every subsystem nobody thought to route it through. The paper enumerates five it had to hunt down, and the one that stayed unbounded, a dtype conversion on the scan matrix, costs +777 MB in transient. On a 16 GB machine with a 6 GB cap, that is the difference between working and not.

The generalizable claim is uncomfortable and worth stating in the form a practitioner can act on: the memory number a local stack reports is a description of its instrumented paths, not of its behaviour. Weights are easy to count and everyone counts them. What is hard to count — and what actually overflows — is the union of transients: a compaction that doubles an index while rewriting it, a decoded video frame buffer, a precision copy of vision weights made once and never freed, a framework's own buffer cache. Every one of those is invisible in a "model needs N GB" claim.

Three details make the finding practical rather than a lament. The fix is slab-based conversion — do the transformation in bounded pieces rather than materializing the converted whole — which is what turns +777 MB unbounded into a bounded cost. The budget has to be re-propagated during compaction and transient operations, not just set at startup. And the honest residual is stated: with both model weights and the vector base resident, the compaction transient still cannot be fully bounded, so the technique buys a much smaller unaccounted region rather than none.

The scope condition matters for how far this travels. This is an encoder workload — a 1.0B multimodal embedding model run in batches — on Apple Silicon's unified memory, where CPU and GPU allocations contend for the same pool and the failure is therefore sharper than on a discrete card with its own VRAM. But the argument is about which allocators were audited, not about the memory architecture, and a llama.cpp or MLX serving stack has the same anatomy: weights, KV cache, scratch buffers, a tokenizer, an image decoder, and a framework cache underneath all of them.
