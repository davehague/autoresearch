Two characters of whitespace, and the tool calls stop parsing

The finding is small enough to state in one sentence and large enough to be worth a note. A model's chat template branches on whether the caller supplied a system message. The auto-insert branch renders the model's own trained-in tool-use prompt with no trailing separator; the caller-supplied branch appends "\n\n". Supplying byte-identical content through the second branch breaks multi-tool-call output, because the rendered strings differ by two whitespace characters.

The mechanism is straightforward once stated: the model's tool-use supervised and reinforcement data was only ever rendered through the auto-insert path, so its reliability is calibrated to that exact byte sequence. Nothing about the meaning of the prompt changed. What changed was the surface form the model was trained to condition on. The independent corroboration is what makes this more than one vendor's bug — llama.cpp PR #26324 documents a mechanically distinct failure in the same template pipeline for the same model (<tool_call> followed by a space instead of a newline, roughly a quarter of the time, breaking tag matching in that engine), found by a different party in a different runtime, and notes the template structure is shared with Qwen3-Coder and Qwen3.5-4B.

Why this belongs on evaluation-contamination rather than in a deployment note. That map's question is whether a reported capability number transfers, and its existing evidence attacks the data side — was the test set seen in training, does a benchmark measure what it claims. This is the same question from the serving side. A tool-calling score is measured through a rendering path, and the harness that produced the score and the harness that will run in production are not the same code. A benchmark run through the model's own default template measures a capability that partly evaporates the moment an application adds "You are an assistant with MCP tools" to the system slot — which every application does. The vault's wording-effect evidence is the closest neighbour — fragility-is-a-property-of-the-rephrasing-not-the-model found that benchmark drift under rephrasing is a property of the rewrite rather than of the model being tested — and this is a more extreme version of the same defect: not a paraphrase, not a rewording, but two invisible characters.

The practitioner rule is specific and testable. Render your production prompt through the model's template and diff it, byte for byte, against what the template produces with no system message. If they differ and tool calling is degrading, that difference is the first suspect, ahead of the model. And when comparing tool-use scores across models, check whether each was scored through its own default path — because the model that looks worse may simply be the one whose harness took the other branch.

Graded suggestive: the mechanism is demonstrated cleanly and corroborated independently, but on one checkpoint. Whether this generalizes across the template family it shares structure with is exactly what the llama.cpp report hints at and nobody has systematically tested. Separately, the BFCL numbers this same source reports isolate a format-level weakness that survives every fix — 1/30 on emitting two parallel calls, against 30/30 on correctly emitting none — which is a reminder that not every tool-calling failure is a template artifact.
