The disaggregation thread gets its first hybrid-linear-attention capacity-planning account, and it names a second budget axis this map's KV-focused framing doesn't have a slot for

This map's disaggregation sub-thread (DistServe, the MiniMax M3 and Kimi K3 hybrid-attention serving entries) has so far reasoned about memory in KV-cache terms: paging, quantization, and now prefill/decode separation, all sized against a token-indexed cache. Qwen3.8-2.4T's GDN layers break that framing outright — 69 of its 92 layers carry a fixed-size recurrent state per request rather than a growing KV cache, so the memory-planning question this map has treated as one problem (how big is the KV cache) is actually two problems that scale on independent axes (sequence length for attention layers, concurrency for GDN layers). The practical consequence this source reports is that prefill and decode topologies were tuned independently (different tensor-parallel splits for each) and only reconciled where KV must physically transfer between them — disaggregation here is not just "run two phases on separate GPUs" (this map's existing DistServe framing) but "run two phases whose memory bottlenecks are different resources entirely."

This sharpens rather than replaces this map's standing KV-budget framework (architecture × precision × placement): for a hybrid stack, "architecture" now has to specify which layers are attention and which are recurrent, because the other two levers (precision, placement) apply differently to a fixed-size state than to a growing cache. Cross-map: kv-cache-management (the GDN/ full-attention memory-law asymmetry directly extends that map's existing ReplaySSM/Kimi-K3-KDA recurrent-state thread with a concrete production capacity-planning number rather than a reconstruction-cost one).

Graded extends: sharpens this map's existing disaggregation and KV-budget threads with a new architectural case, rather than contesting either. Graded mixed direction: the finding is a capacity-planning cost (a single formula no longer suffices) alongside the throughput result it enables, so it is not a pure improvement claim. Graded suggestive rather than strong: this is one vendor's tuning-log account of one model on one cluster, with the CUDA-graph over-provisioning number (10-56%) reported as an acknowledged inefficiency rather than a resolved one, and no ablation isolates the disaggregation decision from the other changes (MTP, CUDA-graph tuning) made in the same post.

Bounded: every number is GB300 NVL72 datacenter hardware — nothing here is a single-consumer-card measurement, continuing this map's standing complaint about where its headline serving numbers come from; MTP concurrency figures are stated as upper bounds rather than reachable concurrency; no comparison against a non-disaggregated (colocated) baseline on the same hardware is given, so disaggregation's own contribution is not isolated from the other engineering changes; software-version- pinned (vLLM v0.26.1rc1), so reproducibility outside that exact stack is unestablished.

Rebutted by: none.
