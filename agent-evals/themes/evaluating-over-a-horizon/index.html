Evaluating over a horizon

Status: consolidating

Sub-threads: the run can lose ground · the order of the run is a variable · what the counterpart does while the agent works · what the run leaves behind for the next one · how long a horizon has to be before it shows anything · boundaries that stand in for duration · history as a hazard rather than a resource · where in the run the intervention was made · the trajectory as the score rather than the diagnostic · the length of the run as a scale factor on anything cumulative · where in the run the input arrives · the horizon as a mutable run-time setting · partial credit that refuses out-of-order progress · screening a task for horizon rather than for duration · inert steps accumulate with the horizon · reliability across repeats rather than discovery on one · the tasks a deterministic corpus declines to author · the run's end is not the outcome's end · the scaffolding forgets as well as the agent · required volume as a horizon knob independent of difficulty · the items that pass with the mechanism switched off · the stop the agent owns · the submission the agent has to declare · evidence scoped to the revision that produced it · what the agent says about having finished · the stop a second model owns · the score's time decoupled from the run's time [reviewed 2026-08-23 @ 23 bullets]

Scope

Evals that score a sustained run rather than a point. The claim collected here is that a terminal number on a long-horizon task is an average over a trajectory with structure — order effects, regressions, decay — and that the structure is where the information is. Distinct from evals-that-localize-the-fix, which asks which component a failure belongs to; this asks when in the run it happened, and whether an earlier success is still a success.

Through-line

  • 2026-08-07 — opened at emerging. Structure each task as a dependency DAG over separately testable units, release tests along the ready frontier, and retain completed nodes as standing regression obligations. 112 tasks, 8 languages, 5,300+ units with executable tests, prerequisite edges recovered from real build history rather than authored (a-dependency-dag-of-separately-testable-units-with-completed-nodes-held-as-regression-obligations-scores-a-long-run-continuously, loopsbench-loop-engineering-benchmark). The finding that only this design can produce: regression events stayed visible across every loop implementation evaluated. Best configuration resolves 25.00%.

  • 2026-08-07 — the same mechanism from a different task family, and this is the reason the theme exists rather than living as a bullet elsewhere. For an agent with persistent memory, tasks are not independent and the order of accumulated experience moves the score, so one run sequence measures a path rather than an agent (the-order-of-accumulated-experience-changes-a-lifelong-agents-score-so-one-run-sequence-measures-a-path-rather-than-an-agent, path-bench-path-dependent-evaluation).

  • 2026-08-07 — and the decomposition that follows from it: report transfer and forgetting separately, because the agent that gains most from helpful history is not the one that keeps the gain (strong-forward-transfer-does-not-imply-retention-so-transfer-and-forgetting-need-separate-metrics). Two teams, two task families, one design principle — a long run needs previously-passed checks to stay live, or the scoring is monotone by construction and cannot represent damage.

  • 2026-08-07 — the third arrival extends the horizon from a run to a relationship, and pays for it. An agent tutor in a continuous 30-day relationship with a simulated learner across 55 scenarios, and almost no model-plus-adapter combination sustained good tutoring across the full 30 days (educlaw-bench-pedagogical-agents-simulated-learners, where-ground-truth-is-contested-the-construction-move-is-a-simulated-counterpart-fit-to-real-data-plus-a-cross-family-judge-panel-on-the-soft-axes). Whatever a single-session eval certifies, it is not durability.

  • 2026-08-09 — the cheap way to keep a multi-turn run comparable without freezing it. Each persona carries a hidden gate that branches on the agent's own behaviour — whether deeper disclosure was earned — so the interaction state space stays enumerable while the path through it is not assigned (a-hidden-gate-branching-the-trajectory-on-the-agents-own-behaviour-controls-a-multi-turn-eval-state-space-without-scripting-dialogue, companionbench-judge-severity-separated-from-agent-quality). This is the third way the vault has seen a counterpart handled and by far the cheapest: EduClaw-Bench fits a simulated learner to real student data with a knowledge-tracing model, PATH-Bench constructs and permutes history sequences, and this writes one decision rule per persona. It also produces a metric with no judge in it — reaching the branch is a deterministic property of the run — which is rare in a domain with no crisp success condition. Generalizes to any eval with a counterpart whose cooperation must be earned: support escalation, sales qualification, negotiation, clinical elicitation. Untested against the obvious failure: an agent that satisfies the disclosure condition without doing the underlying work, which is the shortcut-certification problem in a new place.

  • 2026-08-10 — the horizon extends past the end of the run, and this is the version the theme's machinery cannot reach. 328 cases whose two halves live in different sessions: content enters through memory, a skill, a tool result, a session summary, a shared artifact, a subagent delegation or a memory-to-skill transformation, then fires later on a request that is itself benign (a-failure-that-enters-in-one-session-and-fires-in-a-later-one-is-invisible-to-any-eval-whose-unit-is-a-single-run, harnesssafe-persistent-carriers-across-agent-harnesses). Matched controls confirm the boundary is doing the work — remove any critical lifecycle element and attack success falls from 25.8% to at most 2.5%. Every practice this vault relies on fails here: outcome grading passes the poisoning session, a transcript audit would have to audit the session where nothing happened, and staged scoring only works because the benchmark authored the pairing, which cannot be recovered afterwards from two independent runs. Note what the seven carrier families have in common — memory, reusable skills, session summaries, shared artifacts are the features that make an agent useful across sessions, so the exposure grows exactly as the product improves. A long task is expensive to evaluate; this is expensive to represent, and the minimum test nobody here reports running is whether their harness can express a two-session case at all. Adversarial construction throughout, so 25.8% is an attack success rate and not a base rate for anything benign.

  • 2026-08-12 — the first source to vary the horizon and report what changes, which is the question this theme has been asking since it opened. One loop harness, one backbone, one execution backend, three benchmarks of increasing length: Terminal-Bench 2.1 (closest to a single bounded task) +7.5, WeaveBench (GUI and CLI across a longer run) +28.9, OSWorld 2.0 binary completion 2.8% → 8.3% (the-harness-gain-is-largest-on-the-longest-horizon-benchmark-which-is-the-first-quantitative-support-for-checkpoint-and-recover, longhorizon-harness-loop-engineering). Checkpoint-and-recover should do nothing on a task that fits in one round and everything on a task that needs thirty, and that is roughly the shape observed — a factor of four in effect size with everything else held fixed. Three points is not a curve, but it is the first evidence the relationship is monotone and steep enough to be worth mapping, and it makes the experiment this theme wants cheap and obvious: run one intervention at 5, 10, 20 and 30 rounds and find where the gain stops growing. That is the shortest-horizon question asked about an intervention rather than about a regression, and nobody has to build a new benchmark to answer it. Two caveats, both real. The three benchmarks differ in surface as well as horizon — Terminal-Bench is CLI, OSWorld is desktop GUI, WeaveBench is both — so "longer" and "more GUI" move together and the horizon reading is plausible rather than isolated. And OSWorld's 2.8% baseline is a warning attached to the finding: a binary metric on a long-horizon task saturates at the floor and ranks nothing, while the partial-credit row on the same runs moves 13.7 points. Partial credit is not a nicety in horizon evaluation, it is the only thing carrying signal — subtask-partial-credit-recovers-the-signal-binary-grading-throws-away-and-matters-most-when-every-model-scores-near-zero observed in the wild, under exactly the condition it named. Weakest evidence class here: the harness authors' own README, one week old, no repeated runs.

  • 2026-08-13 — a horizon failure with a one-restart price tag, which reframes this theme's affordability problem. InfraBench's per-check scoring names non-durable changes as a distinct failure class: the agent satisfies the objective now and the change does not persist (a-change-that-passes-now-and-does-not-survive-a-restart-is-the-cheapest-durability-check-the-horizon-theme-has-been-asking-for, infrabench-durability-and-per-check-scoring). That is a-failure-that-enters-in-one-session-and-fires-in-a-later-one-is-invisible-to-any-eval-whose-unit-is-a-single-run made concrete, and every instrument this theme has collected for catching it is expensive — 112-node DAGs, constructed history sequences, 30 simulated days, path-ordered task streams. This one costs a restart. The standing gap has been finding the shortest horizon that still surfaces a regression, and this suggests the question is mis-shaped for a whole class of failures: some horizon effects are not about duration at all, they are about whether state was written somewhere that survives a boundary — a restart, a new session, a cache clear, a fresh context. Crossing the boundary is the test, and every one of those boundaries is cheap. The generalisation worth chasing, and unrun by anyone here: for any agent that modifies persistent state, re-run the success check after the cheapest available reset. That covers config changes, migrations, file edits, installed dependencies, and most relevantly for this vault's readers, anything an agent writes to memory that a later session is supposed to find. Limits: only one of the four named classes is durability, the abstract does not size it, and infrastructure has an unusually crisp notion of persistence that prose output does not.

  • 2026-08-14 — the theme's founding claim extends in the direction that hurts: accumulated experience has an uncontrolled sign. Controlled comparisons of experience reuse within and across tasks, over seven frontier models and 36 long-horizon tasks, report reuse "that can help or mislead subsequent decisions" (experience-reuse-can-help-or-mislead-later-decisions-so-carrying-history-between-tasks-is-a-parameter-with-an-uncontrolled-sign, beyond-final-scores-long-horizon-rd-agents). the-order-of-accumulated-experience-changes-a-lifelong-agents-score-so-one-run-sequence-measures-a-path-rather-than-an-agent established that history moves the score, and everything built on it since — including the transfer/forgetting split — quietly assumed history is a resource whose value runs from zero upward, with the risk being that it decays. "Can mislead" says it is not bounded below. Carrying context between tasks becomes a hazard, not a benefit that fades. Two consequences. First, whether the agent sees prior tasks is a setting in every multi-task harness, usually set once by whoever wrote the runner, and it belongs on the unwritten-variable list in evals-that-localize-the-fix — it is also cheaper to test than most of them: run the suite with and without history carried, one extra pass, no new tasks and no new grader. Second, it complicates this theme's most useful open question. The standing ask is for the shortest horizon that still surfaces a regression, on the assumption that a shorter run sees less of the same thing. If reuse can mislead as well as help, a truncated horizon may see a different sign, because the misleading stretch and the helping stretch need not be the same length. Nobody here has reported the effect's trajectory over run length. One clause from an abstract, no magnitude, no statement of how often reuse helped versus misled, and no description of the controlled comparison beyond its scope.

  • 2026-08-15 — the theme's mechanisms so far are about state accumulating; this one is about a single change destroying everything after it. Forking live SWE-bench trajectories and continuing each fork with a different model, swaps exceed matched control floors by +0.25 to +0.66 normalized edit distance, "rewriting 61-94% of post-fork actions," and "divergence decreases with fork depth in both directions" (one-substituted-step-rewrites-61-to-94-percent-of-later-actions-and-the-effect-shrinks-with-fork-depth, the-replay-gap-static-evaluation-of-model-switching). Together with the order effects and cross-session carry already here, it says a long run has no interior points interchangeable with the same point in another run. The depth gradient is the new and actionable half: an intervention early in a horizon has to be measured by re-running the whole thing, one late in it can be approximated locally, and the crossover is measurable per task family by forking at a few depths. Nobody in this vault has stated where in a run they intervened, because until now there was no reason to think it mattered. It also prices the honest version — ~900 rollouts to characterise one substitution policy on one benchmark.

  • 2026-08-16 — the instrument degrades with the horizon, which is a worse problem than the agent degrading with it. In coding trajectories the error responsible for the final failure "frequently appear[s] in the middle or toward the trajectory's end rather than at the beginning," and past 61 steps attribution accuracy falls for every method tested (critical-errors-sit-mid-run-or-late-and-attribution-accuracy-collapses-past-61-steps, trajdebug-error-lifecycle-critical-failure-attribution). This theme has collected findings that long runs are harder to pass; this is a measured finding that they are harder to diagnose, and it is the first length effect here with a threshold attached rather than an adjective. The first half also kills the cheapest attribution heuristic there is — blame the first thing that looks wrong — which fails in the exact shape this vault's free-metric rule predicts: a cheap signal (position of first anomaly) asked to stand in for an expensive one (which error the outcome actually depended on). It joins step counts, tool calls, tokens, context volume, the recorded plan and tool-call count in the graveyard. The design consequence is a real fork for anyone building a long-horizon eval: either keep the horizon short enough that post-hoc attribution still works, or instrument checkpoints during the run so responsibility never has to be reconstructed — which is a fresh argument for a-dependency-dag-of-separately-testable-units-with-completed-nodes-held-as-regression-obligations-scores-a-long-run-continuously, on diagnosability rather than on scoring resolution. Limits: two benchmarks, the position claim stated for coding specifically, and 61 steps is a property of these task distributions rather than a general number.

  • 2026-08-17 — the learning curve stops being something a benchmark noticed and becomes the metric. "We score a harness by how much its student converges toward the teacher over time," where the student runs a continual learning harness that improves from feedback without retraining (making-convergence-over-time-the-score-rather-than-a-diagnostic-is-the-learning-curve-this-vault-asked-for-as-a-metric, label-free-harness-evaluation-teacher-relative-lift). a-harness-that-rewrites-itself-from-rollout-feedback-removes-harness-held-fixed-as-an-available-control concluded that a self-improving harness destroys the fixed-harness control every comparison in this vault rests on, and had only "report a learning curve" to offer; early-saturation-in-a-self-evolving-harness-is-the-learning-curve-the-vault-asked-for-and-it-caps-the-rollout-bill then found one, as an anomaly a benchmark happened to log. This is the first method here whose output is a trajectory by construction, and it makes this theme's founding claim apply to the evaluating apparatus rather than to the agent: a system whose purpose is to improve from feedback has no meaningful terminal number at all, because its score is a function of where you stopped. The open question it inherits is this theme's oldest, in the sharpest form it has taken: how many correction rounds before the convergence ranking of two harnesses stabilises, and can a short run invert it? That is not merely a resolution question — experience-reuse-can-help-or-mislead-later-decisions-so-carrying-history-between-tasks-is-a-parameter-with-an-uncontrolled-sign establishes that a truncated horizon can see a different sign, and "sparsely sampled" corrections are simultaneously what makes the method affordable and what makes an early reading noisy. Nobody reports the ranking's trajectory, only that the endpoint correlates with a held-out gold standard. One domain, no coefficient, no round count, and no statement of how sparse the sampling was — so what is recorded here is a metric shape rather than a result.

  • 2026-08-18 — a normalization rule for any cumulative measure over a run, arriving as an aside in a study about something else. "A trajectory is thrashing when uncovered edit-time debt survives repeated read–edit–test cycles because no new evidence retires it. A long successful trajectory may accumulate more raw debt than a short failure", so the reported quantity is normalized to the final quarter of a trajectory rather than being an unnormalized cumulative sum (working-set-of-a-coding-agent-coherence-debt, a-five-event-trace-schema-with-a-pre-write-edit-intent-separates-four-failure-causes-that-otherwise-arrive-as-one-failed-test). This is the horizon version of the class-balance problem: any metric that counts events over a run rewards short runs, so a cumulative error count, a cumulative retrieval measure, or a cumulative cost figure compares run lengths unless something normalizes it. This theme has recorded that the order of a run is a variable and that the run can lose ground; it has not recorded that the run's length silently scales most of the quantities anyone would measure across it. The proposed schema's revert event is the same concern instrumented — an explicit compensating write rather than a reversal inferred from a later diff, so ground lost mid-run is a recorded event rather than a reconstruction.

  • 2026-08-19 — held at emerging, with a horizon design nobody else here uses: put the adversarial content in the middle of the run. Each of 128 cases pairs "a benign user objective with an adversarial instruction embedded in an untrusted workflow artifact," delivered across three owner turns so the artifact arrives after the agent has committed to a plan (harnessrisk-lifecycle-agent-harness-safety). Every other injection study in this vault puts the hostile content in the opening prompt, which measures whether an agent can be redirected before it starts — a different and easier question than whether it can be redirected mid-commitment. The design also makes State Persistence scoreable as its own label rather than as a side effect of the final answer: whether "transient adversarial content is written into trusted state and later reused" is measured directly, which is this theme's what-the-run-leaves-behind sub-thread with an instrument attached for the first time. The label is also the least reliable of the four (84.3% agreement, κ=0.65), which is the honest caveat on it.

  • 2026-08-19 — and the run's length becomes editable while the run is happening. "inspect ctl config can retune per-sample time/token/message limits mid-flight," with unsupported knobs rejected atomically and a --now flag that holds in-flight samples at the next model call (retuning-per-sample-time-token-and-message-limits-mid-run-makes-the-limit-a-property-of-when-a-sample-ran, inspect-ai-changelog-unreleased-after-0-3-259). Message and token limits are precisely what set the horizon this theme argues scales every cumulative measure taken across it, so a single eval log can now contain samples scored under different horizons and any aggregate over it mixes them. Whether that is an operations convenience or an unrecorded variable turns on one unstated fact: are the effective limits recorded per sample, or only the change event? This runner already ships an audit trail for mid-run config changes, which makes it likely survivable here and is exactly the part a hand-rolled harness copying the feature would omit. The incentive is not going away — long agent runs are slow and expensive, and an operator watching a stall will reach for the knob — so the question is not whether limits get changed but whether the change is legible afterwards.

  • 2026-08-20 — partial credit finally gets an opinion, and the opinion is that order is part of the score. Every partial-credit result this vault holds counts what was achieved — subtask credit, process reward, per-check scoring. A 82-task long-horizon benchmark counts something else: let ℓ be "the length of the longest prefix (g₁, …, g_ℓ) such that gᵢ(s_T) = 1 for all i ≤ ℓ"; progress is ρ = ℓ / n (longest-satisfied-prefix-rather-than-fraction-of-criteria-refuses-to-credit-out-of-order-progress, agentrewind-mettlebench-recoverable-execution). An agent satisfying criteria 1, 3 and 5 of five scores 0.2, not 0.6. That is defensible here because the corpus was screened to make it so — later deliverables must quote run-time values earlier stages produced, "digests, counts, or identifiers, in at least two places," so skipping a stage genuinely cannot be built on. And the paper shows the metric's eligibility condition by failing it: transferring to Terminal-Bench 2.0, where criteria "are not semantically ordered," it reverts to plain fraction-of-criteria. So prefix progress is not a better rule in general — it is the rule you become entitled to once your checklist is genuinely ordered, which is the same eligibility framing this vault reached for cheap subsetting. What it measures that success cannot: two models at similar task success whose unsuccessful runs average 50.8% and 38.1% prefix progress — 12.7 points apart on how far they get before collapsing, which is exactly the distinction a team choosing for long-running work needs and which binary success destroys. The feedback design is the other half and is deliberately narrow: the backend "returns natural-language feedback identifying only the first unsatisfied checklist item," full checklist hidden, all criteria sharing one environment state so "subsequent actions may invalidate previously satisfied criteria." A prefix can shorten — this theme's "previously-passed checks must stay live" enforced by construction rather than by policy, and the fourth independent arrival at it.

  • 2026-08-20 — and the theme's oldest open question — how short can a horizon be and still show these effects — gets its first empirical handle. Grouping the same 82 tasks by median baseline trace length into tertiles, a runtime-recovery intervention's "advantage over the strongest baseline is modest in the short-horizon group but becomes substantially larger in the medium- and long-horizon groups." That is the shape this theme has been predicting without evidence: long-horizon machinery pays in proportion to horizon, so a benchmark truncated for cost will under-report it. Two more things from the same table are worth keeping. Trace length is not capability — the best-performing model has the shortest mean trace (50.5 events) while three models exceeding 300 events do not do better, so run length is a property of the configuration and not a difficulty measure. And the horizon screen itself is now specified rather than asserted: at least four strictly sequential stages, run-time values quoted forward in at least two places, either two defects where fixing the first exposes the second or a 30-entry log to reconstruct, at least five acceptance criteria — plus explicit anti-padding rules ("may not stretch a run out by forcing the agent to wait, or to work one item at a time when it could work in batches"). The first stated defence in this vault against horizon being confused with duration.

  • 2026-08-21 — the theme just adopted an opinionated partial-credit rule; here is the reason to be careful with every other per-step score over a long run. Audited against an executed-replay causal ground truth, only 30.5% of decision points carry measurable effect on the outcome, and the share of points where the instrument has no verdict at all differs by a factor of two between two similar-scale policies — 13.1% against 26.8% (only-30-5-percent-of-decision-points-carry-measurable-causal-effect-and-the-unmeasurable-share-doubles-between-two-similar-policies, credit-without-ground-truth-executed-replay-audit). Longest-satisfied-prefix survives this — it scores against explicit, ordered acceptance criteria evaluated on the final state, not against a model's opinion of individual steps. What does not survive is the family of scores that walk a trajectory assigning per-step credit: over a long run, most of the steps being weighted did not matter, and the fraction the instrument can even adjudicate is a property of the agent being measured. Longer horizon, more inert steps, more of the score determined by an instrument whose coverage nobody reports.

  • 2026-08-22 — the discovery/reliability gap gets its cleanest measurement, on one corpus with one grader. The strongest model on 507 stateful business workflows scores 65.36% pass@1 and 25.25% pass^20 — pass^20 being the fraction of tasks completed on all twenty attempts (pass-at-one-of-65-percent-and-pass-of-all-twenty-at-25-percent-on-the-same-tasks, thinkingbox-reliability-over-repeats). A factor of 2.6, same tasks, same executable checks, same model. Everything published as a benchmark number is a discovery rate; what a business buys from an agent with write access is closer to the all-of-k rate, because those failures are not retried by a human who noticed, they are wrong rows in a database. There is no arithmetic that gets a reader from the first number to the second, and the first is the one that gets published. Two things keep this from being just another aggregation complaint. It is cheap to fix — no new authoring, no new graders, twenty runs and a second column, and per-test repeat options now shipping in mainstream runners let you pay the 20x on a chosen subset. And it is not a noise floor: a noise floor tells you whether a delta between two configurations is real, pass^k tells you whether one configuration is dependable. This vault has a 6-to-12-point standard error for the first quantity and now a 40-point gap for the second. A benchmark can report both; almost none report either. The honest extension is that k=20 is arbitrary — the right k is how many times the workflow runs before a human looks, and reporting pass^k as a curve costs nothing once the twenty runs exist.

  • 2026-08-22 — and the same corpus writes down what determinism cost it, which is rarer than the finding. Tasks admit a single golden state, and workflows with several defensible resolutions are excluded by construction (excluding-workflows-with-more-than-one-defensible-resolution-is-how-this-benchmark-buys-determinism). This vault has reconstructed that trade from the outside repeatedly — a deterministic grader is usually possible because the ambiguous items were quietly never authored — and a reader cannot distinguish a corpus that had no ambiguous cases from one that dropped them. Here it is an explicit exclusion criterion. What it removes is exactly the class where judgement is required, and in refund policy, insurance adjudication, IT triage and HR support that class is not a corner case; it is much of the work. Which makes the reliability finding worse, not better — 65% discovery and 25% all-of-twenty are scores on the procedural subset, and whatever the excluded class would score, it is not higher. The general rule for anyone building a corpus: determinism is paid for at authoring time in items you decline to write, and the way to stay honest is to count the exclusions and keep the dropped pile, because it is both the best available estimate of what your deterministic evals cannot see and a ready-made corpus for the rubric-scored tier.

  • 2026-08-23 — moved emerging → consolidating, on one sub-thread and not on the theme as a whole: the order of the run is a variable. The theme opened on this claim from a benchmark built to demonstrate it — PATH-Bench constructed and permuted history sequences and found that the order of accumulated experience moves the score (the-order-of-accumulated-experience-changes-a-lifelong-agents-score-so-one-run-sequence-measures-a-path-rather-than-an-agent). A designed result is the kind a reader is entitled to discount. Tonight it turns up uninvited: a re-evaluation of two published memory-based self-improving agents, changing nothing but the protocol, finds that "the agent's improvement is highly dependent on task order" and that "prior works often adopt default orderings that impose an implicit curriculum, acting as a hidden prerequisite for success" (default-task-orderings-impose-an-implicit-curriculum-that-acts-as-a-hidden-prerequisite-for-success, fragility-of-self-improving-agents-variance-task-order-underspecification). Neither author team was studying sequencing. That is now three independent arrivals — a benchmark that constructed the effect, a re-evaluation that found it inside other people's results, and the transfer-versus-retention decomposition that predicted it (strong-forward-transfer-does-not-imply-retention-so-transfer-and-forgetting-need-separate-metrics) — converging on one operational rule: shuffle the stream, run it more than once, publish the spread. The rule costs nothing, no long-horizon corpus tracked here except the one built to study it applies it, and any sequential result that has not been shuffled is quoted at the wrong precision. What is emphatically not consolidating: the rest of the theme. How long a horizon has to be, whether prefix progress or fraction-of-criteria is the right partial-credit rule, and where in the run an intervention pays are all still open on one or two studies each.

  • 2026-08-23 — and the theme's outer boundary moves for the first time: the run's end is not the outcome's end. Everything collected here so far concerns structure along the trajectory and still assumes the score can be read off the state at the stop. A position paper with a controlled experiment attached says both conditions needed for that reading are unestablished: outcome finality and cross-unit separation, which fail independently (outcome-finality-and-cross-unit-separation-are-independent-conditions-that-an-endpoint-does-not-establish). Holding the agent's actions fixed and varying only whether operations had settled, the endpoint label and the terminal label differed for every delayed operation tested (the-label-at-the-stop-and-the-label-at-settlement-differed-for-every-delayed-operation, when-is-an-agent-evaluation-over). This lands hardest on the part of the theme that is currently most confident: prefix progress, per-check scoring and every partial-credit rule here evaluates predicates against a final state, and longest-satisfied-prefix-rather-than-fraction-of-criteria-refuses-to-credit-out-of-order-progress already concedes that later actions can invalidate earlier ones — pending actions can too, after scoring, in both directions. The proposed disclosure is an open-effects record: list what was still in flight when you stopped. It costs a list, and the same night supplies a live example of the condition — a grader that verifies records by refetching cited pages is verifying after the run against a resource that can change (a-judge-that-refetches-cited-pages-trades-a-gold-set-that-expires-for-a-dependency-that-drifts).

  • 2026-08-23 — the scaffolding forgets too, and the theme's oldest open question finally gets a knob instead of a tertile split. First: "a harness update can disrupt previously reliable behavior even when the model is frozen," measured in controlled retention sweeps and named harness-level forgetting (harness-level-forgetting-makes-the-harness-a-variable-across-time-rather-than-only-across-configurations, harness-continual-learning-guarded-evolution). Every harness result in this vault is cross-sectional — 8.6 points between harnesses, 4.3x on behaviour, five nested provisioning levels — and all of it holds time fixed. This is the longitudinal version, which is the one that hits teams who never run a comparison: nobody swapped harnesses, somebody added a skill. It is the exact symmetry of transfer-versus-retention, applied to the scaffolding rather than the agent. Second: WANDR specifies each task as a qualification key hierarchy where "n companies, m employees per company, and k sources per employee requires n x m x k records," targets running "from dozens to thousands" (a-required-record-count-set-by-an-n-by-m-by-k-hierarchy-scales-run-length-without-scaling-per-item-difficulty, wandr-refetching-judges-and-hierarchical-completeness). Required volume is a stated parameter, roughly independent of per-item difficulty — the first dial here suitable for the controlled horizon experiment this theme has only ever approximated by grouping an existing corpus into tertiles after the fact. The reported trend is the expected one, performance degrading with volume and depth, and two of the three named bottlenecks — incomplete discovery, missing enrichment, incomplete evidence construction — describe runs that stopped short rather than got things wrong.

  • 2026-08-24 — held at consolidating, and the theme gets a control that comes before the shuffle it has been asking for. Among CMB's disclosed defects: "Qwen2.5-7B answers every transfer and preservation item without revision state, exposing zero-state reconstruction" (a-model-answered-every-transfer-and-preservation-item-with-no-state-at-all-so-the-items-were-passable-by-reconstruction, cmb-criterion-revision-trace-anchored-protocol). Two of the benchmark's five conditions — the two that are specifically about carrying something across an episode boundary — turned out to be answerable by a 7B model with no carried state at all. The items were well-formed, the scoring was correct, and the construct was simply absent: what they measured was whether the answer could be reconstructed from what sat in front of the model at the time. Every corpus in this theme that claims to measure memory, persistence, accumulated context or cross-episode learning has this exposure and none of them reports the control, which is one line of protocol — run the items with the mechanism removed and see who still passes. Whatever the no-state arm scores is the floor; only the difference is about horizon. It is the same ablation logic as the night's paired-trial arrivals (paired-with-and-without-trials-make-the-skill-rather-than-the-agent-the-unit-that-gets-a-score) pointed at the items rather than at the effect, and it is the cheaper and more neglected of the two directions. It also reorders this theme's own open gap: the standing question is whether published long-horizon results survive a shuffle of task order, and this adds a prior one — do they survive the state being deleted? If a corpus scores the same with memory switched off, the shuffle question is moot, because there was no horizon in the measurement to begin with. The proposed repair, concealed transfer with repeated hidden items, requires authoring against an adversary rather than against a plausible use case, which is more work than most corpus construction does and is the difference between a horizon benchmark and a long prompt.

  • 2026-08-25 — held at consolidating; the stopping variable stops being a design observation and moves a headline by 9.9 points. Prime Agent names three stopping mechanisms as recorded configuration — an explicit budget with a task-specified end-condition test, heartbeats on a schedule, and goals ending "through agentic completion, when the agent marks the goal complete" (an-agentic-completion-gate-lets-the-thing-under-test-decide-when-the-measurement-ends, prime-agent-self-improving-rlm-harness). The third hands the stop to the system under test, which makes the amount of effort endogenous: two agents scored under agentic completion have not been run for the same amount of work, and the score does not say so. The corroboration arrived the same night from an unrelated benchmark and carries a number. Enabling thinking mode raised the test-case score for three of four models and lowered it 9.9 points for the strongest (0.961 → 0.862, pass rate 0.852 → 0.738), with the cause identified as early submission rising from 0% to 7.9% (enabling-thinking-cost-the-strongest-model-9-9-points-by-making-it-submit-early, netconfarena-closed-loop-network-configuration). The knob under test was a decoding setting; what moved was when the agent declared itself finished. Attributing that to reasoning quality sends a team to the wrong fix, and it was only separable because a submission-mode process metric sat beside the score. The cheap standing instruction this theme can now issue: record why every run ended — agent submitted, limit fired, error terminated — because a regression that appears as a shift in that distribution is a control-flow problem, not a capability one. Inspect AI has begun recording exactly that, a reason on limit-halted samples distinguishing operator termination, which suggests independent convergence rather than one team's idea.

  • 2026-08-26 — held at consolidating; the multi-revision run gets two mechanisms, and one of them is the well-behaved twin of a move this theme was sceptical of last night. In Pufibara, submission is an explicit agent action — not implied by compiling, not implied by simulating, not implied by being the newest edit — and the harness freezes "the exact candidate identity and the exact artifact set or parameter assignment selected by the agent" (making-submission-an-explicit-agent-action-freezes-which-candidate-is-being-scored, pufibara-modelica-agent-workflow-benchmark). Over a long run "the final state of the workspace" is not a well-defined answer; grading the last write scores an experiment. Note the contrast with an-agentic-completion-gate-lets-the-thing-under-test-decide-when-the-measurement-ends: declaring when to stop lets the agent shorten its own exam, declaring what it submits removes an ambiguity the grader would otherwise resolve by guessing. The second mechanism handles the same problem backwards — every evidence record carries the candidate identity that produced it, so a superseded revision's simulation stays as auditable history and stops discharging the current candidate's readiness (binding-every-evidence-record-to-the-candidate-that-produced-it-stops-an-agent-citing-a-superseded-revision). Staleness represented rather than remembered. Both are unablated, and neither reports the counter that would size the hazard — how often a stale citation or a suboptimal submission actually occurred.

  • 2026-08-27 — held at consolidating, and the agent's own account of whether it finished turns out to be anti-diagnostic. Across 970 Claude Code trajectories on 97 end-to-end scientific workflows, 641 of the 849 non-passing runs (75.5%) ended with a final message containing lexical completion language, and only 13 (1.5%) said anything was still running or in progress (75-5-percent-of-non-passing-agent-runs-ended-by-claiming-completion-and-the-rate-rose-with-the-score, frontierchallenge-scientific-workflow-completion). The banding is what makes it a finding: completion language appeared in 61.2% of runs scoring under 50, stayed above 78% in every non-passing band above 50, and reached 90.1% among passing runs. The frequency rises with the score, so the self-report is most misleading exactly where the decision is closest — an agent that did most of the work and missed one deliverable is nearly as likely to declare victory as one that succeeded.

  • 2026-08-27 — which constrains, rather than overturns, the two stopping-related mechanisms this theme adopted this week. making-submission-an-explicit-agent-action-freezes-which-candidate-is-being-scored and enabling-thinking-cost-the-strongest-model-9-9-points-by-making-it-submit-early are both about when the agent stopped, and both survive. What does not survive is anything the agent asserts about having finished. The horizon framing is where this bites hardest and the incentive runs the wrong way: the longer the run, the more expensive it is to check the artifacts and the more tempting it is to take the agent's word — while the longer the run, the more ways a conjunctive contract has to be missed. Any unattended pipeline gating on "the agent said it was done" is gating on a signal with a measured 75.5% false-positive rate, and this is a design requirement for the system, not only for the eval. The paper's own prescription is the constructive half: explicit contract tracking, cross-artifact validation, and evidence-based completion checks — with the same contract grading the run and gating the pipeline.

  • 2026-08-27 — and the third cheap horizon signal fails alongside the other two. On the same suite the mean rubric score does not predict completion (an-average-rubric-score-of-87-9-and-a-pass-rate-of-20-6-percent-came-from-the-same-graders), the agent's claim of completion does not predict completion, and the presence of tool errors does not either — errors appeared in 94.2% of passing runs against 80.7% of failing ones (tool-errors-appeared-in-more-passing-runs-than-failing-ones-so-error-presence-is-not-a-triage-signal). Three of the cheapest ways to tell whether a long run delivered, and all three fail on one suite. What remains is an executable check over the artifacts, which is the expensive thing, and which this theme's cost sub-thread now prices at six million input tokens and 22–113 minutes per task.

  • 2026-08-28 — held at consolidating, and a fourth owner of the run's end arrives — the only one that is itself a scored component. PILOT's supervisor observes the active worker and can redirect or abort it when "continuing that worker session is no longer useful"; the abort criteria are not published and the abort counts are not reported (a-supervisor-that-can-abort-the-active-worker-moves-the-run-s-stopping-decision-inside-the-system-under-test, pilot-live-steering-supervisor-worker). The theme's existing owners — the operator's cap, the agent's declared submission, the outcome's settlement time — are all either config or transcript. This one is a second model's live judgment, recorded nowhere, and it means two arms that both use a supervisor are not matched on run length even when matched on every declared budget. There is a benign reading (aborting a doomed run early is exactly the token efficiency the paper reports) and a hazardous one (aborting a run that would have succeeded is a self-inflicted failure indistinguishable from task difficulty in the results table), and the experiment that separates them — rerun the aborted subset with steering disabled — is not in the paper.

  • 2026-08-28 — and the seam from the other side: the score's time is no longer the run's time. inspect ctl task score scores a running eval's in-flight samples, each briefly held, "without ending any sample" (scoring-a-running-eval-s-in-flight-samples-produces-an-interim-metric-that-mixes-two-populations, inspect-ai-changelog-score-reason-and-in-flight-scoring). This theme has argued that the run's end is not the outcome's end; here a measurement detaches from the end entirely, and partial-progress measurement stops requiring a rerun. The hazard is stated in the entry and not flagged: the interim metric folds "completed samples' final scores" together with provisional scores of samples still running, so it is a mean over two populations with a mixing ratio that changes every second and is not part of the number. Its trajectory over a run confounds real progress with the shifting mix. Usable as an operational signal for deciding whether to kill a run; not usable as a measurement to record or compare, because comparing two arms' interim metrics compares two mixtures and nothing in the log says what they were.

  • 2026-09-02 — held at consolidating, and a fifth cheap horizon signal fails on the same shape as the third. On deep-research tasks, verbal confidence separates eventually-failing from eventually-succeeding trajectories at a mean AUROC of 0.85 once the run has finished, and at no better than 0.60 for any tested signal read at 50% progress on the identical trajectories (verbal-confidence-predicts-agent-failure-at-completion-auroc-0-85-but-no-signal-exceeds-0-60-at-halfway, last-step-matters-early-uncertainty-fails-in-long-horizon-agents). Unlike the mean-rubric-score and agent-completion-claim failures on 2026-08-27, this is a same-signal, two-timepoint design — not a worse signal tried early, but the identical signal losing almost all its power between halfway and the end. The paper names why: agents "frequently abandon their current search direction in-trajectory," so a reading taken against one direction is compared to an outcome produced along another (path-switching-breaks-the-link-between-early-uncertainty-and-final-outcome) — the first named behavioral mechanism for a horizon-signal failure this theme holds, rather than another restated null. The paper's own recommendation, restart on final-step confidence rather than intervene mid-run (restarting-on-final-step-confidence-outperformed-in-trajectory-intervention), sits in tension with a-supervisor-that-can-abort-the-active-worker-moves-the-run-s-stopping-decision-inside-the-system-under-test's mid-run abort design: one recommends acting as late as possible, the other is built to act early, and the theme has not yet reconciled who holds a stopping decision with when that decision can be trusted.

Status note, 2026-08-23 — moved emerging → consolidating, on the order sub-thread only

The theme has held at emerging since it opened on 2026-08-07, across sixteen reviews, because the evidence kept arriving as single studies pointing in compatible but non-overlapping directions. One sub-thread has now cleared that bar and the rest have not.

What consolidated. The order of the run is a variable, and the fix is a protocol change with no cost. Three independent arrivals, one of them a re-evaluation that found the effect inside published results whose authors were not looking for it, and a fourth adjacent finding — a self-improving loop compounding the environment's existing noise down the stream (a-self-improving-loop-amplifies-the-environments-existing-run-to-run-noise) — which supplies the mechanism. The operational consequence is a two-line change: randomize the sequence, repeat, report the spread.

What did not. The horizon-length question, the partial-credit rule, the counterpart design, and the where-in-the-run-does-the-intervention-pay question all still rest on one or two studies each. Nothing in this move should be read as the theme settling; it is one bullet's worth of a large theme reaching the point where a practitioner can act on it without waiting for the next arrival.

What would move it back. A published shuffle sweep showing order effects are small on a modern long-horizon corpus, or a demonstration that the effect is confined to memory-carrying agents and absent in stateless ones.

Why this is its own theme

It does not fit the existing four. evals-that-localize-the-fix is about routing a failure to a component; the phenomena here — a passed test later broken, a gain later eroded, a history that helps or interferes — are about position in time, and they are invisible to any scoring that runs to completion and then grades. design-for-verifiability is adjacent and genuinely overlaps at the DAG bullet, since restructuring work into checkable units is that theme's move; what it does not cover is keeping those checks live afterwards. And this is not a cost question, though it is an expensive one.

Three sources arriving on the same day is a weak reason to coin a theme and is not the reason. The reason is that all three independently converge on a single design decision — previously-passed checks must stay live — reached from long-horizon coding, from lifelong memory, and from sustained tutoring, none of which cite each other's problem framing. A fourth source already in the vault sits squarely here too: verifying-and-repairing-the-deliverable-inside-the-harness-raises-the-floor-and-hides-the-variance-from-the-eval is a long-horizon harness absorbing failures before the eval can see them, which is the same seam viewed from the harness side.

Held at emerging and not higher. All three sources are first-of-kind benchmarks from single teams with no replication, and no one has reported what any of this machinery costs against what it catches.

Open questions

  • When the score is a trajectory, at what point does the ranking of two configurations stop changing? This is the shortest-horizon question with the stakes raised: a truncated run of a feedback-driven harness can report a different sign, not just a smaller effect, and the one method here whose output is a curve reports only its endpoint.

  • Run one intervention at 5, 10, 20 and 30 rounds and report where the gain stops growing. This is the theme's shortest-horizon question in its cheapest form, it needs no new benchmark, and as of 2026-08-12 there is a released harness with a max_rounds setting that makes it a config sweep.

  • How often did the in-harness Auditor reject, and what did it never catch? A harness that verifies its own work before the eval sees anything is measuring the repair loop as much as the agent, and the rejection rate is the one number that would separate them.

  • Can your eval harness express a test case whose setup and assertion are in different sessions? Nobody here reports trying, and every source in this vault scores a single run.

  • Does benign state corruption happen at a rate worth measuring? The cross-session evidence is entirely adversarial, and the interesting question for a product team is whether an ordinary memory entry or session summary degrades a later run without anyone attacking anything.

  • What fraction of long-horizon failures are regressions of earlier work rather than failures to progress? Every source here shows regressions exist; none reports the share.

  • Is path dependence larger than sampling variance? If re-running the same history twice moves the score as much as reordering it, the finding is real and not worth the second run.

  • How short can a horizon be and still show these effects? The sources use 112-node DAGs, constructed history sequences, and 30 simulated days — all expensive. Nobody has looked for the cheapest run length that surfaces a regression. A behaviour-branched gate is the first mechanism here cheap enough to test that question with, since it costs a decision rule rather than a fitted counterpart.

  • What fraction of agents clear a behavioural gate? If nearly all of them do, it is scenario colour; if it separates them, it is a judge-free instrument in a domain that has none. Nobody reports the branch-reach rate.

  • Does this collapse into design-for-verifiability once someone builds an artifact designed for continuous re-checking, or does keeping checks live stay a separate discipline from making them possible?

  • Final-quarter normalization is one team's choice on one workload family. Is there a principled window, or is every cumulative long-horizon measure carrying an arbitrary constant?

  • Does the eval log record the effective time, token and message limit per sample, or only per run? One field check against a real log, and it decides whether mid-flight retuning is an operations feature or an unrecorded variable in every result produced under it.

  • How much does injection position matter? Turn-one and mid-workflow injection are now both in the literature and nobody has run the same cases both ways, so the vault cannot say whether the harder design finds more or merely different failures.

  • Is your checklist actually ordered? Prefix progress and fraction-of-criteria give very different scores for the same run, and which you are entitled to is a property of your corpus that most teams have never asked about. The one benchmark that checked proved its ordering by running a deliberately out-of-order solution and confirming it failed at the right criterion.

  • How often does prefix progress under-credit? An agent failing criterion 2 and completing 3 through 8 scores 0.125. The metric's designers do not report the frequency, and it is the number that decides whether the rule is strict or punitive.

  • Does the horizon screen reproduce? Four sequential stages, forward-quoted run-time values, cascading defects, five criteria — the first written-down definition of what makes a task long-horizon rather than merely long. Nobody has applied it to an existing benchmark to see how many of its tasks survive.
