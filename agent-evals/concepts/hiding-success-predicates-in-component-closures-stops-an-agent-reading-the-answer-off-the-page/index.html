Hiding success predicates in component closures stops an agent reading the answer off the page it is scored on

Grounded in componentbench-component-level-failures-in-computer-use-agents; belongs to design-for-verifiability.

Across 2,910 programmatically verified UI tasks: "target values and success predicates reside in React component closures and are never exposed as DOM attributes, accessible-tree labels, or page text." Success is signalled only by a banner the verifier reveals (#cb-success-banner), and where a control requires an explicit commit — Apply, Save, OK, Confirm — "success requires an explicit local control" rather than an inferred state change.

This is a leak the observation channel creates and the grader has to close. An agent evaluated on a GUI reads the accessibility tree or the DOM. If the success predicate is in the DOM — a data-expected attribute, a hidden label, a target value in page text — then the richest observation channel is also the answer key, and the score measures reading rather than acting. Nothing in this vault's grader-design collection names that hazard, because everything here grades text or files, where the artifact and the criterion are naturally separate. In an interactive environment they are separate only if someone keeps them separate.

It generalizes past GUIs. The rule is: the criterion must live somewhere the agent's observation channel does not reach. Any eval where the agent observes the environment it is graded on has the same exposure — a test file in the repository the coding agent can read, an expected-response fixture in a mocked API the tool-use agent can list, an oracle row in a database the analytics agent can query. The check is mechanical: enumerate what your observation channel returns, and grep it for your criterion.

Cost: nothing. This is a build-time placement decision, not a procedure. It is the cheapest item in design-for-verifiability and among the few that cannot be retrofitted — once the predicate is in the DOM, every score collected under it is suspect, and there is no post-hoc correction.

The commit requirement is the second half and does independent work. Requiring an explicit Apply or Confirm rather than accepting the underlying state change means a task cannot be passed by a side effect. It is the interactive version of design-for-verifiability's standing preference for checking the committed artifact rather than the intent, and the failure histogram shows it bites: "missing commit or confirmation" is 11.6% of failures by trace features and 20.0% by LLM reading.

Bounds. One benchmark, asserted as a design property with no ablation — nobody measured what scores would have been had the predicates been visible, so the size of the leak this prevents is unknown. React-specific in implementation, though the principle is not. The tasks were generated with GPT-5.2 Pro and the pages implemented with Claude Code, and the paper warns the benchmark "may contain generator-specific regularities," which is a different leak the closure trick does not address.
