A runner separating scan footprint from incurred token usage shipped with seven fixes for cached, duplicate and unmetered charges, so the single token number it replaced was wrong in a knowable direction

Grounded in promptfoo-0-122-1-tracing-and-token-accounting; belongs to what-an-eval-costs-to-run.

One release added eval: distinguish scan footprint from incurred token usage (#10497) — two numbers where there had been one — and, in the same release, fixed seven separate ways the old single number was wrong:

  • prevent cached and duplicate token charges (#10417)
  • preserve cached generation and retry accounting (#10507)
  • count cached and thinking tokens for Claude on Bedrock (#10492)
  • count Claude Agent SDK subagent tokens (#10455)
  • account for all scan-time model calls (#10479)
  • account for remote strategy generation usage (#10445)
  • count unmetered generation requests (#10429)

Plus a four-way split of red-team spend into generation, target, attacker and grading tokens (#10407, #10408), and preserve cumulative grading token usage (#10406).

"Footprint" and "bill" diverge, and the divergence is structural rather than incidental. Caching means tokens processed ≠ tokens charged. Retries mean calls made ≠ calls billed. Subagents mean the tokens a run consumed are not all attributable to the top-level call. Unmetered generation requests mean some model calls did not appear in either number. A single "token usage" figure is an average over at least four different accounting questions, and the fixes tell you it was undercounting — six of the seven add tokens that were previously missed.

This is the cost-side version of the un-averaging argument, and it arrives the same night a benchmark independently demands the same distinction. one-benchmark-task-cost-between-2-2-and-13-7-million-input-tokens-and-between-22-and-113-minutes reports cache shares of 75.3% to 98.8% across configurations and declines to normalise its token counts because "provider-specific tokenizers, caching, and reporting conventions preclude a hardware-normalized efficiency interpretation." A runner and a benchmark, unrelated, arriving in the same week at the same conclusion: a token count without a cache share is not a cost.

The reporting norm this makes available is small and nobody in this vault has been observed doing it. Report two numbers per eval run — tokens processed and tokens charged — and the ratio between them. The ratio is the thing that makes two runs comparable: a 98.8%-cached run and a 75.3%-cached run with the same footprint have wildly different bills, and every cost comparison in this vault has quietly assumed they do not.

And it lands directly on a standing gap. This vault has repeatedly asked what a quality intervention costs and been given a score without a price — decomposed judging on two sources with no token count, panels with no bill, step-attribution with no rollout cost. Part of the reason is that the runner did not produce a number worth quoting. It now produces two, with the judge's share separable (grading-execution-is-now-its-own-span-class-so-judge-latency-and-judge-spend-come-out-separated). That is the fifth reporting norm in a fortnight to arrive as a runner feature rather than as adoption, after un-averaging, inter-rater agreement, confidence intervals and separable judge spend — and like the other four, availability is not use.

Single release, single vendor, changelog-level evidence. No magnitudes: the changelog does not say how far off the old number was, and "prevent cached and duplicate token charges" could be a rounding error or a doubling. The direction is inferable from the fixes — six of seven add previously-uncounted tokens — and the size is not. Anyone who quoted a promptfoo token figure before 2026-08-26 was quoting an undercount of unknown magnitude.
