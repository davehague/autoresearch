Eight named verdicts give a graded task suite the defect taxonomy a grader audit has never had

Grounded in river-verifier-quality-over-environment-quantity; belongs to build-vs-adopt-eval-tooling.

The rubric reads three artifacts that "must be mutually consistent" — the instruction shown to the agent, the verifier that scores the rollout, and the environment (Dockerfile plus data) — and asks one question: "would a competent agent that faithfully follows the instruction be able to (a) understand the task unambiguously and (b) actually pass the verifier?" Then one of eight verdicts:

  • CLEAN — the verifier "recomputes/decodes the true answer from the input (or exact-compares against a correct hardcoded answer) rather than merely checking output shape. A hard-but-fair task is still CLEAN."
  • VERIFIER-TOO-WEAK — "checks only output shape/format/types/count, trusts a self-reported value, greps the source for keywords, checks a hardcoded subset, or tests only fixed inputs so the answer can be hardcoded. A fabricated, plausibly-shaped output would pass."
  • INSTR-VERIFIER-MISMATCH — "a solution that faithfully follows the instruction still fails."
  • INSTR-ENV-MISMATCH — the task references files, dependencies or services the container does not provide.
  • ANSWER-LEAK — the instruction or a shipped file reveals the expected answer.
  • INSTR-AMBIGUOUS — a necessary specification is missing, so two reasonable readings diverge and the verifier accepts one.
  • TASK-TRIVIAL — no meaningful work regardless of verifier strength.
  • OTHER — buggy or crashing verifier code.

Why this belongs on the build-vs-adopt ledger rather than only in the verifiability theme. This vault has priced the build side in labels, hours and label ladders — four-weeks-to-a-working-eval-harness-is-the-first-build-figure-covering-criteria-labels-judge-alignment-and-runner-as-one-number, twenty-to-fifty-tasks-drawn-from-real-failures-is-the-first-stated-starting-size-for-an-eval-suite-and-it-is-an-order-of-magnitude-below-the-benchmark-corpora — and priced the adopt side in features. Neither column has ever contained a defect rate for the items themselves. Adopting a public task suite has been treated as free. Under this rubric the three suites audited are 64%, 90% and 97% defective, so "adopt someone's benchmark" carries an item-quality bill that nobody was itemising, and the bill is one model call per task to find out.

The taxonomy is the transferable part, not the numbers. Every one of the eight verdicts describes something a team building its own suite will do: hand-writing a checker that greps for a keyword, pasting the expected output into the prompt as an example, writing an instruction that assumes a file the image does not ship. Three of them — VERIFIER-TOO-WEAK, ANSWER-LEAK, INSTR-VERIFIER-MISMATCH — are undetectable from scores alone, because all three produce results that look normal: the first inflates, the second inflates, the third deflates.

It also names the boundary the vault keeps blurring. "A hard-but-fair task is still CLEAN" separates broken from difficult, which is the distinction the-residual-between-observed-and-predicted-difficulty-audits-a-whole-corpus-for-broken-items-without-reading-any-of-them reaches statistically. This gets there by reading, and unlike the residual method it works on a corpus with no response history at all.

Bounds. One rubric, authored by one team, applied by one model with a single-model blind re-judge as its only external check. No published inter-rubric comparison, no maintainer response, and the second filtering pass — dropping pass@k=0 environments as "excessively difficult or incompatible with our training infrastructure" — discards exactly the hard-but-fair category the rubric was careful to protect.
