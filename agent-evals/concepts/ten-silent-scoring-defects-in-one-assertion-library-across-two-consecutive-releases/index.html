Ten silent scoring defects in one assertion library across two consecutive releases, so the adopted grader has a per-release item-defect rate and the disclosure is the whole of the adopt case

Grounded in promptfoo-0-122-1-tracing-and-token-accounting; belongs to build-vs-adopt-eval-tooling.

promptfoo-0-121-14-to-0-122-0 disclosed six assertion types silently scoring wrong in one release window. Five days later, four more scoring-correctness fixes:

  • assertions: score tokenless GLEU inputs as zero (#9850) — a GLEU assertion given input with no tokens returned something other than zero.
  • assertions: reject out-of-range trace-span-duration percentile (#10089) — an out-of-range percentile was accepted and graded against rather than refused.
  • assertions: correct inverse JSON failure messages (#9824).
  • assertions: avoid regex backtracking in GLEU and SQL parsing (#10373) — a hang rather than a wrong score.

Plus, one layer over: providers: raise max_tokens above a manual thinking budget on every Claude route (#10491), where a configured thinking budget exceeding max_tokens was silently unachievable.

Ten silent scoring defects across two consecutive releases of a mature, widely used assertion library is a per-release item-defect rate on the graders themselves. This vault has an item-defect rate for adopted task pools — 35.8%, 10.1% and 3.3% clean across three published suites. This is the same measurement one layer down, on the code that decides whether an item passed. Both halves of an adopted eval have a defect rate, and neither is normally reported.

The first two are the same shape as the previous six and it is the dangerous shape. The assertion returned a number, the number was wrong, and nothing raised. A tokenless GLEU input is an empty or degenerate model output — exactly the case an eval most needs to catch — scoring as something other than zero. An out-of-range percentile being accepted means a misconfigured assertion graded silently instead of failing loudly. This is the four-seam rule from every-reproduced-harness-defect-landed-on-one-of-four-seams-and-all-four-default-to-running-on-rather-than-stopping arriving in an eval library: the unrecognised shape defaults and runs on instead of stopping.

The double-edged read from 2026-08-22 survives, and sharpens. The adopt case is that these were found, fixed and published, where a hand-rolled similarity > 0.8 gets none of the three — the vault's own a-shipped-similarity-gate-caught-zero-of-fifty-six-meaning-breaking-edits-and-never-exceeded-0-700-balanced-accuracy-across-ninety-cells is what an unmaintained one looks like after a year. The cost is that anyone who ran GLEU or trace-span-duration assertions before 2026-08-26 has scores that were quietly wrong, and had no way to know. A maintained runner discloses; it does not retroactively correct your numbers or tell you which of your past runs were affected.

The practical rule this vault has been circling now has a second data point behind it. Pin your runner version, record it beside every score, and re-read the changelog for assertion fixes before comparing a new run to an old one. Two consecutive releases with scoring fixes means "same suite, same items, different runner version" is not a controlled comparison — which is the config-provenance problem eval-level-limits-persisting-on-a-reused-task-object-let-one-eval-inherit-anothers-overrides raised, at the level of the grader rather than the run config.

And it constrains what the disclosure actually tells you. Ten defects found is not ten defects existing. The rate says something about how hard this vendor is looking, not about how many remain — and a vendor that stopped fixing assertions would publish a cleaner changelog. The number of things a maintained runner discloses only tells you what it found, which is the strongest argument here for validating an adopted assertion against your own labelled examples rather than trusting its name.

Single release read against one prior release, single vendor, changelog-level evidence with no severity or blast-radius information. "Ten defects" counts the previous six as disclosed and adds four here; the classification of what counts as a scoring defect versus an ergonomic one is ours, and a stricter reading gives eight. No claim is made that this library is worse than alternatives — no competitor publishes a comparable list, which is itself the point.
