Checking the end state rather than the path is the verifiability argument arriving from the eval side instead of the product side

Grounded in anthropic-demystifying-evals-for-ai-agents; belongs to design-for-verifiability.

The guidance: prefer outcome and state checks wherever they exist — the tests pass, the record changed correctly, the reservation exists, the browser is in the right state, the tool side effects match. Grade what the agent produced, not the path it took, because agents find valid approaches nobody anticipated and path assertions turn those into failures. The example given: Claude Opus 4.5 found a flight-booking loophole that failed the written eval while delivering more user value.

Why this extends. This theme's argument has run in one direction — product first. An artifact that is hard for you to verify is hard for a user to verify, so restructure the artifact into units someone can accept or reject (eval-difficulty-is-a-product-design-signal-so-the-first-move-is-restructuring-outputs-into-units-a-user-can-accept-or-reject). Every source here so far reached that conclusion from the product side. This reaches the same place from the eval side, and it is the first independent route: if you are choosing what to assert on, assert on state, which means your product needs state worth asserting on.

The two directions meet at a design question rather than a measurement one. "Does the reservation exist" is only available as a check because booking produces a row somewhere. A product whose output is a paragraph has no equivalent, and no amount of grader engineering creates one — which is the theme's whole claim, now with the eval-side consequence attached: the check you wish you could write is a feature request, not a grader task.

The loophole example is the sharper half. It is usually told as an argument against brittle assertions, and it is also a small demonstration that the eval was wrong and the agent was right. Only an outcome check could tell the difference, because a path check has already encoded the assumption that the intended path is the good one. That puts a boundary on the transcript-audit obligation this vault carries from outcome-based-grading-requires-transcript-auditing-as-its-counterweight-or-it-certifies-shortcuts-as-successes: an audit catches the run that reached the outcome by cheating, and it also flags the run that reached a better outcome by a route nobody wrote down. Those look identical in a trace, and telling them apart is a judgment call about what the product is for, not a scoring rule.

The decision it changes. When writing a grader, spend the effort on finding a state to inspect before writing assertions about behaviour. If no state exists, that is information about the product, and it belongs in a design conversation rather than in a rubric.

Why suggestive. A vendor guide's prescription with no data behind it and one illustrative anecdote. The underlying claim — that path grading is more brittle than outcome grading — is asserted rather than measured, and nothing here reports how often a path assertion produced a false failure. It earns suggestive because it converges with a conclusion this theme reached independently and because it is standard practitioner advice rather than one team's idiosyncrasy.

What would move this. Any team reporting how many of its eval failures turned out to be the eval's fault rather than the agent's. That rate is the direct measurement of what this claim is about, it is knowable from work teams already do when triaging failures, and nobody publishes it.
