Pass@1 of 65 percent and pass-all-of-20 of 25 percent on the same tasks and the same grader

Grounded in thinkingbox-reliability-over-repeats; belongs to what-the-headline-number-averages-away and evaluating-over-a-horizon.

The strongest model on a 507-task stateful business-workflow benchmark scores 65.36% pass@1 and 25.25% pass^20. pass^20 is the all-of-twenty measure: the fraction of tasks completed successfully on every one of twenty attempts. Same tasks, same executable checks, same model. The two numbers differ by a factor of 2.6.

This is the strongest instance this vault has of compounding across trials rather than averaging across items. A published benchmark number is a discovery rate — the probability that a single sample lands. What anyone deploying an agent into a workflow with persistent side effects buys is closer to the all-of-k rate, because the failures are not retried by a human who noticed; they are wrong records in a database. Between "it works two thirds of the time" and "one task in four works every time" there is no arithmetic relationship a reader can reconstruct from the first number alone, and the first number is the one that gets published.

The fix is unusually cheap, which is the useful part. It requires zero new authoring, zero new graders, zero new tasks. It requires running the suite twenty times instead of once and printing a second column. The compute cost is real and it is 20×, but it is 20× of a number that is already small relative to building the corpus, and the per-test repeat options now shipping in mainstream runners (see a-per-test-repeat-option-lets-you-buy-a-noise-floor-for-the-items-you-care-about) make it possible to pay that 20× on a chosen subset rather than the whole suite.

Note what this is not. It is not a noise-floor measurement and it does not compete with one. A noise floor tells you whether a delta between two configurations is real. pass^k tells you whether a single configuration is dependable. This vault has recorded a 6–12 point standard error on three runs of one agent configuration, which is the first quantity; a 40-point gap between discovery and reliability is the second. A benchmark can and should report both, and almost none report either.

The threshold is a product decision, not a statistical one. k=20 is arbitrary. The right k is set by how many times the workflow runs before someone looks at it, and for a back-office process that is a large number. Reporting pass^k as a curve over k would be strictly more informative than either endpoint and costs nothing extra once the twenty runs exist.

Bounds. One benchmark, five business domains, single-golden-state tasks with multi-resolution workflows excluded by construction — so the corpus is biased toward tasks with a crisp right answer, which if anything should raise reliability. pass^20 is reported for the leading model; the paper does not give the pass^20 column across all twelve models, so whether the discovery/reliability ratio is stable across capability levels is unknown. Every trajectory uses one fixed user simulator, so some of the variance across the twenty attempts is the simulator's and is not separated.
