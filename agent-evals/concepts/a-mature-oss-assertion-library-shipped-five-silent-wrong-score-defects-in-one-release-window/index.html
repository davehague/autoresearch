A mature OSS assertion library shipped five silent wrong-score defects in one release window

Grounded in promptfoo-0-121-14-to-0-122-0; belongs to build-vs-adopt-eval-tooling and design-for-verifiability.

Fixed in a single release (0.121.18, 7 July 2026) and its immediate neighbours:

  • is-refusal ignored the inverse flag when output was missing
  • the inverse flag was not honoured for cost, latency, perplexity, levenshtein and moderation assertions
  • BLEU threw an error on empty output instead of returning pass: false
  • is-sql false-rejected SELECT DISTINCT
  • is-xml accepted XML that is not well-formed
  • ROUGE was case-sensitive where it should not have been
  • contains-sql failed to extract fenced SQL containing backtick identifiers
  • conversation-relevance had no principled default threshold until one was set at 0.5 in 0.121.20

Every one of those is a silent wrong score, not a crash. An ignored inverse flag is the worst of them: it inverts the meaning of the assertion and reports a clean pass. A case-sensitive ROUGE quietly deflates every score in a suite. An is-xml that accepts malformed XML passes the exact input it exists to reject. None of these announce themselves — the suite runs green and the number is wrong.

This vault's grader-audit line has been aimed in one direction and needs a second barrel. The finding recorded under "nobody checked the grader" has been about hand-rolled graders going unaudited: randomness, network calls, UUIDs and wall clock in a grader suite, four grader-parsing defects in ten days in another runner, a drift guard catching zero of 56 reversals. The implicit consolation has been that adopting a maintained library moves this problem to someone who tests. Here is the other case: a widely used, heavily tested OSS assertion library, shipping wrong scores on eight named assertion types in a sixty-day window.

The honest read is not that adopting is worse. It is that adopting relocates grader bugs from your repo, where you might trip over them, to someone else's changelog, where you will find them only if you read it. That is a genuinely better position — someone else is finding and fixing them, and the fixes arrive whether or not you noticed — but it is better conditional on reading the changelog, and this theme has been treating "the maintained runner discloses what you would not" as an unconditional win. Disclosure only helps a reader. A team that upgrades without reading has silently changed the meaning of its assertions between two runs and has no record of it.

And there is a version problem this vault has not raised. If is-xml accepted malformed XML until 0.121.18, then every score produced by that assertion before that release is wrong in a specific, now-known way. Scores are already recorded here as perishable knowledge claims because models change. This adds a second decay source: the grader changed under you, and unlike a model change it is not something anyone thinks to record. A benchmark result without a runner version is missing a variable.

Practice. Pin the runner version in the same place you record the model version, and read the assertion-related section of the changelog on every upgrade. If you can, re-run last quarter's headline suite on the new version before upgrading and diff the scores — a non-zero diff with no config change is a grader fix, and you want to know which of your published numbers it invalidates.

Bounds. Changelog reading, not use, and release notes are a self-report — they systematically undercount defects nobody noticed. This is a defect list, not a defect rate: there is no denominator of assertion types or lines of grader code, and a project that publishes fixes in detail will always look worse than one that does not. Two release windows in a sixty-day span, one project. No comparison against the defect disclosure rate of the other runners tracked here, which would be the number that makes this a real comparison.
