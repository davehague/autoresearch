Batch and non-batch prediction paths in one runner scored the same input differently

Grounded in deepeval-4-2-0-benchmark-scoring-defects; belongs to evals-that-localize-the-fix.

On BigBenchHard, batch_predict applied free-text trimming to every prediction, including clean schema-constrained outputs. With enable_cot=True — the default — a schema answer "(A)" became "(A" and scored 0. The non-batch predict used str(res.answer) directly and scored the same answer 1. Reproduced in the PR:

predict(...) → prediction "(A)", score 1 batch_predict(...) → prediction "(A", score 0 — silently wrong

A configuration flag that nobody thinks of as an experimental variable moved the score. Batching is an efficiency choice. It is not a treatment, it is not recorded in results tables, and two runs of the same eval differing only in whether batching was on would have produced different numbers with no way to tell from the output. That is the same failure class as harness-configurations-that-all-pass-every-test-differ-12-8-times-in-tokens-so-at-ceiling-the-only-remaining-question-is-the-bill inverted — there the invisible variable moved cost, here it moves correctness — and the direct sibling of the config-leak defect where "eval-level limits and retry options were persisting on reused Task objects," recorded in the Inspect changelog.

Two code paths for one semantic operation is the shape to look for. Sync and async, batched and unbatched, streaming and buffered, cached and uncached. The same release fixes another instance of it — "honor include_reason and align sync/async reason generation" — so this runner had at least two divergent-path defects live simultaneously. Anywhere a runner offers a performance mode, the question is whether the mode is scored identically, and the check is one line: run the same fixture through both paths and assert equality.

It localises cleanly, which is why it belongs here. The failure has a repair address — one function, one branch — and the diagnosis distinguishes "the model got it wrong" from "the harness truncated the answer before comparing." Without the two-path comparison it is indistinguishable from a capability result, which is the same confusion a-failing-sandbox-was-handing-its-error-to-the-agent-as-command-output-so-infrastructure-failures-entered-the-log-as-capability-failures describes at the sandbox layer.

Bounds. One PR, one benchmark, one library. No statement of how many runs used the batch path, and the fix also resolves a latent crash on integer schema answers, so the batch path was untested against typed outputs generally.
