Item-response-theory subsetting has a cold-start cost in historical response logs that a single-product team cannot pay, so the cheapest recommendation in this vault is unavailable to its intended reader

Grounded in cot-core-coreset-selection-for-eval-cost; belongs to what-an-eval-costs-to-run.

CoT-Core's stated motivation is that existing coreset methods fail in two ways, and the first is IRT's: a "severe cold start bottleneck requiring massive historical logs." Item parameters — how discriminating each item is, how difficult — are estimated from a response matrix over many models and many items. No matrix, no selection.

Why this pushes back. what-an-eval-costs-to-run opened on item selection and immediately recommended the boring version: extract a fixed informative subset once, offline, then run it like a normal suite (a-fixed-informative-item-subset-extracted-once-captures-most-of-the-savings-without-adaptive-machinery-in-the-loop). The whole argument for that variant was that it moves the machinery out of the run loop and leaves you with a plain eval job. "Once, offline" was treated as a one-time inconvenience. It is a data requirement, and it is one an application team does not meet: to extract the subset you must first have run the full suite against a fleet of models, which is precisely the expense the subset exists to avoid.

So the recommendation splits by who is reading it. A benchmark maintainer with a public leaderboard already has the response matrix as a byproduct and should absolutely extract a subset. A team with one product, one suite, and two or three model candidates has nothing to fit, and for them the finding is currently advice they cannot take.

This does not contradict the cost result — it agrees that eval set size is a dial and offers a different way to turn it. What it rebuts is the claim that the fixed-subset variant is the cheap and general one.

The decision it changes. It adds a prerequisite check before anyone reaches for item selection: do you have full-suite responses from enough distinct models to fit item parameters? If not, the choice is between random-n and a selection rule that needs no history, and discrimination-selected-items-beat-random-subsets-of-the-same-size-which-settles-half-of-the-comparison-between-the-two-cheap-subsetting-rules does not apply to you, because you cannot run the selected arm.

Why single-study. One paper, and the critique is made in a related-work framing to motivate the authors' own method, which is the least disinterested place a criticism can come from. Nobody states how many models × items an adequate fit actually needs — "massive" is doing all the work, and the difference between twenty models and two hundred decides whether a mid-sized team is excluded. That number is the thing to go looking for.

What would move this. A stated minimum: the smallest response matrix from which item parameters recover the full-suite ranking. If it turns out to be ten models, the objection mostly dissolves.
