Swapping among three agent frameworks moved the score by 1.79 points, so harness choice is a small capability variable on rubric-graded work

Grounded in startupbench-market-validated-rubric-graded-workflows; belongs to build-vs-adopt-eval-tooling and evals-that-localize-the-fix.

Robustness was checked across Nanobot, Hermes and Claude Code on 97 rubric-graded professional workflow tasks: "only minor performance differences," average variation 1.79 points.

This is the first direct counter-measurement to the figure this theme has been built on. harness-choice-moved-agent-accuracy-15-points-with-the-model-backbone-held-fixed recorded a 15.36-point spread with the backbone held fixed, across five harnesses on 410 deterministically graded tabular analytics tasks. Same experimental shape, one order of magnitude apart. Both are single studies and neither is obviously wrong, which is what makes it a contest rather than a correction — and it is why build-vs-adopt-eval-tooling moves to contested.

The available reconciliation, and it is testable. The two task families differ in how much of the work is execution plumbing. DataSpace tasks are 7,439 heterogeneous artifacts across CSV, JSON, SQLite, Markdown, PDF and video, graded on returning a complete table — file handling, tool sequencing, format wrangling, all of it the harness's job. StartupBench tasks are long professional deliverables graded mostly on calculation precision, structure and domain compliance — work the model does inside a single sustained generation, with comparatively little for a scaffold to get wrong. The harness's leverage would then scale with the plumbing fraction of the task, which predicts something checkable: run both benchmarks under both harness sets and the spread should track the artifact-handling load, not the difficulty.

The third measurement in the same week decides how to read all of this. the-same-model-was-4-3-times-less-safe-under-a-different-harness-so-a-safety-number-names-a-configuration-rather-than-a-model swapped two of these same three harnesses and found a 4.3x spread — on the safety axis. So the harness is a small capability variable and a large behavioural one, and "what is the harness worth" is not answerable without naming the axis. Any adoption decision made on a capability number alone is being made on the axis where the harness matters least.

What it does to the build-vs-adopt ledger. The theme has been treating harness adoption as an accuracy decision on the strength of the 15-point figure. On rubric-graded professional work that argument collapses to noise — 1.79 points is inside anything anyone would call meaningful — and the argument that survives is a safety-and-containment one, which is a different purchase with different criteria. Neither figure is retired; the ledger now needs both, tagged by axis and by task family.

Bounds. Framework robustness is a side check in this paper, not its subject: no per-framework table is given, "average variation" is not defined precisely, and no run-to-run variance is reported, so nothing establishes that 1.79 is distinguishable from noise in either direction. Three frameworks, not five, and a different three. The specialization gap in the same paper — general-purpose agents 64.26 against purpose-built agents 83.50, surviving oracle conditions at 71.75 vs 83.50 — says scaffolding does matter a great deal when it is task-specific, which suggests the finding is about generic harnesses being interchangeable rather than about scaffolding being unimportant.
