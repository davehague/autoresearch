A failing sandbox was handing its error to the agent as command output, so infrastructure failures entered the log as capability failures

Grounded in inspect-ai-changelog-unreleased-after-0-3-259; belongs to evals-that-localize-the-fix.

From the unreleased window on main: "Docker failures now surface as sandbox_unavailable tool errors instead of command output."

Read what the old behaviour was. A Docker daemon that was down, out of disk, rate-limited or slow to start produced an error string. That string went into the agent's tool-result channel — the same channel a legitimate command result arrives on. The agent then reasoned about it as though the command had run and returned that, usually failed the task, and the run was scored as a failure. Nothing in the eval log marked it as anything else.

This is the failure this theme keeps finding, in its purest form. evals-that-localize-the-fix is contested because the vault keeps discovering that its diagnostic instruments are unaudited. Here the instrument was worse than unaudited: it was actively assigning one failure class to another, in the direction that makes the agent look worse than it is. The taxonomy had a bucket — "infrastructure did not work" — that could not be populated, because the evidence for it was indistinguishable from evidence for a different bucket.

The consequence for existing numbers is not recoverable. Any score produced against a flaky sandbox carries an unknown fraction of infrastructure failures counted as capability failures, and you cannot go back and separate them from the logs unless the error text happened to be distinctive. Nothing says how large that fraction is on any real run, and this vault has no source that reports a sandbox failure rate at all — which is itself the finding. The number is unmeasured everywhere, not just here.

The general check, and it needs no run. Does your harness have a channel where an infrastructure error and a legitimate tool result are indistinguishable to both the agent and the grader? Tool timeouts, provider errors, rate limits, container startup, network egress denials, filesystem exhaustion. If any of them lands as ordinary output, your failure taxonomy has a bucket that cannot be populated and your capability numbers are biased low by an amount you cannot estimate. The repair is the one shipped here: a distinct error type that the runner, the log and the scorer can all see.

It composes with the trace-schema argument. a-five-event-trace-schema-with-a-pre-write-edit-intent-separates-four-failure-causes-that-otherwise-arrive-as-one-failed-test made the case that separating failure causes is a logging problem rather than a statistical one. This is the same claim demonstrated as a shipped defect fix: the separation was impossible not because the causes are entangled in reality but because two of them were written to the same field.

Bounds. A one-line changelog entry on an unreleased branch, with no severity, no affected-version range, no statement of how long the behaviour shipped, and no measurement of how often Docker actually failed in practice. One runner. The inference that published scores were affected is a structural argument, not an observation — nobody has reported re-running an eval under both behaviours.
