The math scorer was executing model output on the evaluator host, so the grader is an untrusted-input surface

Grounded in inspect-ai-changelog-0-3-256-to-0-3-257; belongs to build-vs-adopt-eval-tooling.

Inspect AI 0.3.256, filed under Security: math() scorer answers are now parsed with a non-evaluating grammar inside a bounded worker thread, "preventing model output from executing Python on the evaluator host." Two releases later the changelog also discloses that unseeded dataset shuffles had assigned irreproducible ids, which "silently corrupted eval_set retries on affected datasets."

Why this extends. fixing-grading-bugs-moved-one-model-from-42-to-95-percent-so-the-measuring-instrument-can-own-more-of-a-score-than-anything-it-measures established that the grader can be wrong by more than everything it measures, and that nobody checks. This is the same organ failing in a way that gap did not anticipate. A grader that parses free-form model output is running untrusted input, and the source of that input is the system under evaluation — which, in an agentic eval, is a thing selected for its ability to find unanticipated routes through an environment. Every sandbox argument in this vault has been about containing what the agent does. Nobody has asked what the scoring code does with what the agent writes.

A math scorer that evaluates expressions is the obvious instance and almost certainly not the only one. The general shape is any grader that turns model text into something executable or interpretable: expression evaluation, regex compiled from output, deserialization of a claimed structured answer, a SQL comparison that runs the model's query, a rubric prompt that concatenates output into an instruction. The last of those is every LLM judge in this vault, and prompt injection through the graded artifact into the grading prompt is the same vulnerability with no memory-safety story at all.

The two disclosures together are an argument about where to put the trust boundary. An eval harness is usually drawn as a trusted supervisor around an untrusted agent. Both entries say the supervisor is downstream of the agent's output and inherits its untrustworthiness — once by execution, once by the harness's own defect silently mis-scoring retried runs. Neither failure produces an error; both produce a plausible number.

The practical addition to the grader-validation checklist. holding-out-25-percent-and-reporting-precision-recall-and-kappa-is-the-first-stated-acceptance-procedure-for-a-judge checks whether the judge agrees with a person. Scoring a known-good output checks whether the grading logic works. Neither catches this. The third check is structural and takes a reading rather than a run: does anything in the scoring path evaluate, compile, deserialize or interpolate model output, and is it isolated when it does.

Adopt-side note, and it cuts in the adopt direction. This is the strongest single argument for adopting a maintained runner that this vault has recorded. The vulnerability was found, fixed, and written down in public; a hand-rolled eval(answer) in a team's own scorer has none of those three.
