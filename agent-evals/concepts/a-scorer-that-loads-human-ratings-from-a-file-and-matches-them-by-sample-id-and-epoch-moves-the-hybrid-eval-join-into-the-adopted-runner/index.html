A scorer that loads human ratings from a file and matches them by sample id and epoch moves the hybrid eval join into the adopted runner

Grounded in inspect-ai-changelog-0-3-258-to-0-3-259; belongs to build-vs-adopt-eval-tooling.

"New precomputed_scores() scorer applies scores computed outside of Inspect (e.g. human ratings) from a JSON or JSON Lines file, matched to samples by id and epoch."

This lands on the exact seam the build side of this vault keeps reporting. two-independent-practitioners-adopt-the-platform-as-a-store-and-build-the-annotation-layer-themselves recorded two practitioners independently arriving at the same split: adopt the runner and the trace store, hand-build the labelling layer. custom-annotation-tooling-is-claimed-to-iterate-ten-times-faster-and-the-crossover-to-off-the-shelf-is-annotator-coordination puts the crossover at annotator coordination rather than at features. In both accounts the labels end up outside the eval framework, and getting them back in is a join somebody wrote and now maintains.

Matching by sample id and epoch is the non-obvious half. A single sample run five times is five things to score, and a human label attached to "that item" rather than "that run of that item" is ambiguous exactly where the run-to-run variance lives. Any hand-rolled version of this join gets the id right and gets the epoch wrong on the first attempt, which silently applies one human's judgment of one rollout to all of them.

What it changes about the build-vs-adopt call is small and real. It does not close the annotation-tooling gap — nothing here labels anything, and the interface where a human looks at a trajectory and decides is still yours to build or buy. It removes one integration that had no interesting content, and it does so in the direction the ledger has been pointing: the adopt column keeps absorbing the plumbing while the judgment layer stays on the build side.

It also makes one comparison affordable that mostly is not. With human scores and model-graded scores expressible as scorers over the same samples, running both and reading their disagreement is a configuration rather than a script — which is the operation raw-agreement-is-only-admissible-near-balanced-classes-so-an-imbalanced-eval-has-to-report-judge-precision-and-recall-separately says every judge owes and few evals report.

Bounds. A changelog entry with no usage behind it. Nobody has reported building a judge-validation loop this way, no figure on what the hand-rolled join cost, and the feature assumes labels already exist in a file with stable sample ids — which is the part that is actually hard when the labelling tool is separate from the runner.
