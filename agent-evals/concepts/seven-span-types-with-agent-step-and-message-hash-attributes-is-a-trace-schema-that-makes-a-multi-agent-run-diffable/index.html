Seven span types carrying agent id, step index and a message hash is the trace schema that makes two multi-agent runs diffable

Grounded in llmmas-otel-tracing-and-fault-injection; belongs to evals-that-localize-the-fix.

llmmas-otel instruments a multi-agent run with seven OpenTelemetry span types: session (the whole task run), segment (workflow phase, with segment.order), agent-step (agent.id, step.index), A2A send and receive (inter-agent messages, with message.sha256), tool call (invocation and arguments), LLM call (provider and request), and injected (where a fault was applied).

The schema is the diagnostic, and the specific keys are what make it one. This vault has held "the trace schema as the diagnostic" as a sub-thread for weeks without a concrete schema attached to it. Three fields here do most of the work. segment.order makes two runs alignable even when they take different numbers of steps, so a diff has a coordinate system. agent.id plus step.index gives every action an address, which is the difference between "the run failed" and "agent 2 failed at turn 5". And message.sha256 lets you verify that what one agent sent is what the next received — the boundary where a multi-agent system silently corrupts itself and the one place a plain transcript cannot tell you anything, because it shows one copy of the message.

Distributed tracing is the right borrowed abstraction and the borrowing is the point. Nothing here is novel as observability; OpenTelemetry has had this shape for years. What is new is applying it to the object an eval scores, so that a failure has a span address rather than a paragraph of narrative. That is the same move as indexing failures by lifecycle stage or assigning them to a component edge, but arriving from the infrastructure side and therefore free — the spans exist whether or not anyone reads them, and they are emitted by instrumentation rather than by a labelling pass.

Where it stops, which the authors state. The tool produces the artifacts and explicitly does not do paired-run differencing, trace summarisation, root-cause ranking or automated reports. So this is the substrate for localisation, not localisation. A team gets a diffable trace and still has to write the diff — and the vault has separately found that automated failure labelling over traces disagrees with itself by 20 points (two-automated-labelings-of-the-same-failed-traces-put-the-leading-cause-20-points-apart), so the missing layer is the hard one rather than the omitted one.

Evidence is thin: a demo plus one real system, five runs per condition, and no measurement of whether the schema helped anyone find a fix faster. The schema is worth copying on its structure, not on its results.
