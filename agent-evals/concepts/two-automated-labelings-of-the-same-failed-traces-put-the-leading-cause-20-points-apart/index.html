Two automated labelings of the same failed traces put the leading cause 20 points apart

Grounded in componentbench-component-level-failures-in-computer-use-agents; belongs to evals-that-localize-the-fix.

The same failed runs, labelled two ways. A deterministic taxonomy parses 8,864 failed traces on extracted features — drag presence, target interaction, coordinate repetition, value entry. An LLM reads 2,752 failed runs into structured JSON categories. They do not agree on what went wrong:

Categorytrace featuresLLM reading
Target acquisition / wrong instance11.2%31.6%
Widget-specific procedure missing9.6%24.1%
Missing commit or confirmation11.6%20.0%
Transient state loss19.9%15.0%
Repetition / no-progress loop11.2%5.6%

The deterministic method's top cause is continuous calibration error at 20.2%, a category the LLM labeling does not produce at all. The LLM's top cause is target acquisition at 31.6%, which the deterministic method ranks fourth at 11.2%.

This is a cheaper version of a warning this vault already holds, and it is available to anyone. the-best-automated-critical-error-attribution-reaches-34-percent-accuracy-so-a-machine-audit-is-triage-rather-than-measurement measured an automated attributor against human labels and found it weak — which requires human labels, which is why nobody runs it. ComponentBench needs no ground truth at all. Run two independent automated labelings over the same traces and compare the histograms; where they diverge, neither number is a measurement. It is the same logic as design-for-verifiability's matched-pair and known-good-output audits — check the instrument with something you already have — applied to failure attribution, which is the one instrument in this vault nobody checks.

The divergence has a readable shape and it is not noise. The rule-based method sees mechanics: coordinates repeated, a drag that did not fire, a value never entered. The LLM sees intent: the agent went after the wrong instance, the agent did not know the widget's procedure. Both are true of the same trace. A run where the agent repeatedly clicks 4 pixels off is a calibration failure to a feature parser and a target-acquisition failure to a reader, and which one you write in the postmortem decides whether the fix is grounding or procedure knowledge. The taxonomy is doing causal work that neither labeling justifies.

What survives is the cross-cutting statistic. "55.8% of failed traces end in a repeated-action loop, but it is distributed across every mechanism." A terminal symptom that appears in over half of failures and belongs to no single cause is exactly the kind of signal a one-method histogram converts into a spurious leading category. It is also the most actionable line in the paper — a loop detector is a cheap runtime guard regardless of which underlying mechanism produced the loop.

Practice. Treat any failure-category breakdown produced by one automated method as a hypothesis. If you publish one, publish it twice by different methods, or publish it with the method named and no causal language attached.

Bounds. The two labelings cover different trace populations — 8,864 across five models against 2,752 — so some of the gap is composition rather than disagreement, and the paper does not report a per-trace paired comparison, which is the analysis that would settle it. Neither method is validated against human labels, so this establishes that at least one is wrong without saying which. Categories are not identically defined across the two schemes (the deterministic one has "continuous calibration error" and "drag execution failure" with no LLM counterparts), so part of the 20-point gap is definitional. Single benchmark, single domain.
