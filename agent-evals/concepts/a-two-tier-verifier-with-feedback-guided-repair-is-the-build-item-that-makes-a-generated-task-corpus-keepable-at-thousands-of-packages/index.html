A two-tier verifier with feedback-guided repair is the build item that makes a generated task corpus keepable, which extends generation to domains that cannot compute their own answers

Grounded in skt-verified-synthetic-task-generation; belongs to build-vs-adopt-eval-tooling.

SKT turns 2,000 public agent skills into 4,000 task packages and 27,164 verified trajectories. Retention is the mechanism: rule-based checks plus agent-based checks, with failures fed back for repair rather than discarded, and a coverage criterion that keeps only trajectories which substantially exercise every skill the task requires.

Why this extends. GABench established that build cost is not linear in corpus size when the domain has an executable substrate: build 84 tools once, generate 10,400 tasks, and let execution state the ground truth (building-the-executable-tool-layer-first-lets-a-generator-produce-ten-thousand-tasks-whose-ground-truth-comes-from-execution). That is the substrate fork's easy branch, and most domains are not on it. SKT is a structurally different instance of the same non-linearity: it never computes a right answer. It generates candidates and then decides which ones are well-formed enough to keep.

The distinction is the useful part. Execution answers what is correct. A verifier answers is this instance worth having — well-formed, non-degenerate, and actually exercising what it claims to. The second question is answerable in far more domains than the first, because checking an artifact is easier than computing it. So the transferable rule sharpens: for a generated corpus, the expensive build item is the acceptance test, not the generator.

The coverage criterion is the specific thing worth stealing. "Retain only if the trajectory substantially exercises every required skill" is a directly checkable statement of what a task is for, and almost no hand-built corpus has an equivalent — which is why hand-built suites accumulate cases that pass and prove nothing.

The decision it changes. It gives the substrate fork a third branch that is not "give up and hand-author." A team whose domain will not compute its answers can still generate, provided it can write down what makes an instance acceptable. That is a smaller and much more tractable authoring job than writing the instances, and it is reusable across every future batch.

Why single-study. One team, one pipeline, no ablation of the verifier's contribution — nothing here separates what the rule-based tier caught from what the agent-based tier caught, so "two-tier" is a description rather than a demonstrated design. And the volumes are outputs, not costs: the paper does not state what fraction of generated candidates were rejected, which is the number that would say whether the verifier is doing real work or rubber-stamping a generator that was already fine. It is also, still, no price in hours — the twenty-eighth source in a row that is not.

What would move this. The rejection rate, and a comparison of models' scores on a verified corpus against the same corpus unverified. If the two rank models identically, the verifier is expensive decoration.
