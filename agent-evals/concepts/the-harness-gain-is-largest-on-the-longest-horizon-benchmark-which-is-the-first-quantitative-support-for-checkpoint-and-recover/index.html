The harness gain is largest on the longest-horizon benchmark, the first quantitative support for checkpoint-and-recover

Grounded in longhorizon-harness-loop-engineering; belongs to evaluating-over-a-horizon.

The same loop harness, the same backbone and backend, three benchmarks, and the gain scales with how many rounds the task needs. Terminal-Bench 2.1 — closest to a single bounded coding task — moves +7.5. WeaveBench, mixing GUI and CLI across a longer run, moves +28.9. OSWorld 2.0's binary completion sits at 2.8% for the bare agent and reaches 8.3% with the loop. The harness caps runs at 30 rounds by default, with per-role episode timeouts of 600–1800 seconds, restarting each round from the original goal plus the last verified checkpoint.

Why this extends. This theme opened on designs that measure over a horizon — DAGs with regression obligations, constructed experience sequences, 30 simulated days — and its standing complaint is that every one of them picked its run length by intuition, with nobody looking for the shortest horizon that still surfaces the effect. This is the first source to vary the horizon and report what changes: hold the intervention constant, run it against task families of increasing length, and the effect size moves by a factor of four in the direction the theory predicts. Checkpoint-and-recover should do nothing on a task that fits in one round and everything on a task that needs thirty, and that is roughly the shape observed.

It gives the affordability question a first handle. The reason this theme's designs are expensive is that a horizon multiplies run length, and the reason nobody trims them is that nobody knows where the signal starts. Three points is not a curve, but it is the first evidence that the relationship is monotone and steep enough to be worth mapping — which makes the practical experiment cheap and obvious: run the same intervention at 5, 10, 20 and 30 rounds and find where the gain stops growing. That is the shortest-horizon question this theme has been asking, asked about an intervention rather than about a regression.

The OSWorld floor is a warning attached to the same finding. A 2.8% baseline binary completion rate means the headline metric was measuring almost nothing before the intervention; tripling it still only reaches 8.3%, and the partial-credit row moves 13.7 points on the same runs. A long-horizon benchmark whose binary metric sits near zero cannot rank anything, and this theme should expect that condition to be common — the longer the horizon, the more likely an all-or-nothing metric saturates at the floor. Partial credit is not a nicety in horizon evaluation; it is the only thing carrying signal.

Confounded, and worth stating plainly. The three benchmarks differ in horizon and in surface — Terminal-Bench is CLI, OSWorld is desktop GUI, WeaveBench is both — so "longer horizon" and "more GUI" move together across the table. The horizon reading is the more plausible one given what the harness does, and it is not isolated by this evidence.

Weakest evidence class. Self-reported gains from the harness's own README, one week old, no repeated runs.
