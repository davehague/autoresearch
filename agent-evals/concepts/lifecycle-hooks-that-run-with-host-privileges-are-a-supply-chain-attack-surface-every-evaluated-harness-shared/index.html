Lifecycle hooks that run with host privileges are a supply-chain attack surface every evaluated harness shared

Grounded in hookpry-attacker-controlled-lifecycle-hooks-agent-harnesses; belongs to design-for-verifiability.

Lifecycle hooks — shell commands a harness binds to runtime events like session start, tool call, or file edit — run with host privileges and may fire at times the LLM never observes or authorizes. Under a threat model where the attacker controls only plugin metadata and lifecycle-hook configuration (the ordinary plugin-update channel), a benign already-installed plugin can be trojanized silently. HookPry, the authors' open-source attack framework, compromises all seven evaluated harnesses across 1,000 end-to-end runs, per-harness success up to 92.5%. Representative defenses do not currently look here: Microsoft Defender recall is 0%, and the union of three static defenses still misses 47.5% of malicious artifacts.

Every disclosed-defect instance this vault has tracked in its trust-boundary sub-thread so far is a bug in one maintained runner — Inspect AI's bridged-tool approval-policy gap, the sandboxed-party file-substitution and shell-injection pair, the tool renamed under an approval policy. Each was found, disclosed, and fixed by a single maintainer inside a single codebase. HookPry is a different shape: a structural attack surface present across seven independently built harnesses at once, exploiting a feature (the plugin/hook update path) that is not a bug in any one of them — it is the normal, intended update mechanism, trusted the same blind way everywhere the authors looked. That generalizes the vault's disclosed-defect finding from "maintained runners have bugs, keep reading their changelogs" to "an entire class of harness architecture has an unaudited trust assumption, and pinning one runner's version does not touch it."

The defense numbers are the actionable part. A 0% recall from a mainstream commercial AV product against these artifacts, and a 47.5% miss rate from stacking three static defenses, both say the standard supply-chain tooling most teams already rely on is not currently positioned to catch this. The cheap, available response named directly by the mechanism is narrow: treat a lifecycle-hook configuration change with the same review weight given to a change touching the host-privileged parts of the harness itself, because — per this paper — nothing else downstream currently notices an unreviewed one. This vault's own operating environment runs lifecycle hooks of exactly the described shape (commands bound to session-start and tool-call events), which is the concrete reason to flag this rather than file it as abstract security research.

Bounds. Single paper, one research group, seven harnesses selected and configured by the authors rather than a random or exhaustive sample of what teams actually deploy — "all seven" is a fact about this sample, not a universal claim. No adversary-cost analysis: the paper reports attack success given the threat model holds, not how visible an unusual plugin update would be to a team already reviewing its supply chain by hand. No harness in the evaluated set is reported as using signed or pinned hook configuration, so the paper does not establish whether that specific mitigation would close the silent-update leg of the attack, only that none of the seven evaluated harnesses currently have an equivalent in place.
