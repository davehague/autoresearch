A validator that audits the evaluation route and inserts evidence gates before execution is grader validation running per case

Grounded in harnesseval-w-agentified-world-model-evaluation; belongs to design-for-verifiability.

In an agentified evaluation pipeline, a planner "interprets the case context… routes it to the appropriate skills," and then — before anything is scored — a separate validator "audits the proposed route and adds the required evidence gates before execution." The resulting evidence tree records "exactly what was tested, which specific tool supplied the visual grounding, and the complete logical chain that justifies the final score," including "the selected evaluation route with evidence-grounded reasons for each skill."

All five grader-validation procedures this vault holds run beside the instrument, at build time, once. A known-good output check, a holdout against human labels, letting the agent argue an item is unsatisfiable, a difficulty residual, a matched-pair audit against a nuisance variable — each of them validates the grader as a whole, before or after a campaign. This runs per case, at evaluation time, and validates a different object: not "is this grader sound" but "is this grader about to ask the right question of this item."

That object only exists once the grader stops being fixed. A static rubric has no route to audit — every item gets the same questions, so the questions are validated once. The moment the evaluation plan is chosen per case, the plan becomes a new failure surface, and the vault's existing procedures do not cover it: a grader can be well-validated in aggregate and still route a particular case to the wrong skill. So this is less a sixth technique than the cost of adopting decomposition — dynamic routing buys the discrimination in decomposing-one-global-judgment-into-grounded-sub-questions-took-pairwise-accuracy-from-31-9-to-71-7-percent-and-the-draw-rate-from-52-2-to-1-8 and owes a route check in return.

Filed as open-question because the paper offers no evidence it works. There is no ablation of the validator, no measurement of how often it rejects or amends a route, and no report of what a bad route costs when it slips through. That rejection rate is exactly the number this vault has demanded twice before in the same shape — of an in-harness Auditor, and of a synthetic-task verifier — on the grounds that a gate with no reported rejection rate is indistinguishable from a rubber stamp. The demand applies here unchanged.

What is independently keepable is the evidence tree. Recording which tool supplied the grounding for each sub-verdict makes a score auditable after the fact by someone who was not there — the practical form of this theme's argument that a check is worth what it lets you re-derive. It is also the mechanism that would let a reviewer catch a bad route without the validator existing at all, which raises the fair question of whether the validator is doing work the tree already does.

Bounds. Single study, no dedicated limitations section, no ablation of any component. The validator is described in one sentence and never evaluated. No cost is reported for the pipeline at all, so an extra audit pass per case is unpriced. The system's out-of-distribution behaviour is conceded only obliquely — "this failure is a measurement of the evaluator's own limitation" — which is a graceful way of saying the route can be wrong and the tree will not necessarily say so.
