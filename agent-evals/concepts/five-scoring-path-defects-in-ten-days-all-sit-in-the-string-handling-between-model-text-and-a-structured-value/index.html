Five scoring-path defects in ten days all sit in the string handling between model text and a structured value

Grounded in inspect-ai-changelog-unreleased-after-0-3-259; belongs to build-vs-adopt-eval-tooling and design-for-verifiability.

This window adds four more: "single-choice answers with trailing commas now score instead of being rejected"; "CSV/JSON choices fields no longer produce empty strings from trailing/doubled commas"; "numeric string metrics treated as scalars rather than sequences in eval results"; "tool calls with stray trailing quotes now parse correctly instead of failing back to the model." The preceding ten days produced: a grader scoring an off-menu verdict lifted from an earlier mention in its own reasoning, a math() scorer executing model output on the evaluator host, unseeded dataset shuffles corrupting eval_set retries, ragged CSV rows failing silently, and multiple-choice answers with Oxford commas not scoring.

The pattern is now stable enough to state as a rule. In a maintained eval runner the disclosed defects cluster in one place: the string handling between a model's free text and a structured value. Answer parsing, choice parsing, tool-argument parsing, metric typing. Not in the metrics themselves, not in the orchestration, not in the scheduling. That is a specific place to look in anything you built yourself, and it is exactly the code nobody writes tests for because it looks trivial.

The defects have a direction, and it is the dangerous one. A valid answer rejected for a trailing comma is a false negative — it depresses the score. And whether a model appends a comma, an Oxford comma, or a stray quote is a stylistic property that varies by model and by prompt format. So a parser defect does not shave points evenly off everyone: it shaves points off the models with the wrong punctuation habits, which can reorder a leaderboard while looking exactly like a capability difference. Three separate instances of this shape have now shipped in this one runner in under two weeks.

What it does to the build-vs-adopt ledger. It cuts both ways and the vault should hold both. The adopt side gets worse in absolute terms — the runner you bought has grader bugs, repeatedly. The adopt side gets better in relative terms, because these are being found and published, and a hand-rolled scorer has the same class of defect with nobody looking for it. The asymmetry is not in defect rate, which is unknown for hand-rolled code. It is that one side has a changelog.

Practice. Before trusting any scorer you did not write a parser test for: feed it known-good outputs in three or four punctuation styles and confirm they all score identically. That is a twenty-minute check that would have caught three of the five defects listed above.

Bounds. One project's disclosures, on an unreleased branch, over a two-week window — a small sample, and a project that discloses less would produce a different-looking distribution for reasons unrelated to its code. No severity, no affected-version ranges, no statement of how long any defect shipped, so the claim that published numbers moved is structural rather than observed. The vendor concentration in this vault's changelog evidence is now five sources from one runner in twelve days.
