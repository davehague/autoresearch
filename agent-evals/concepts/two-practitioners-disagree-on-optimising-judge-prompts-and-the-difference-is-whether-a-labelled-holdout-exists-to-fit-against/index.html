Two practitioners disagree on optimising judge prompts and the difference is whether a labelled holdout exists to fit against

Grounded in eugeneyan-aligneval-building-an-eval-app; belongs to build-vs-adopt-eval-tooling.

An automated trial loop over a dev/test split: "F1 starts at 0.571, increases to 0.722 at trial 5 on dev, then gets F1=0.727 on test." Reported against his own result: "With the small sample size (25 per split, 50 in total), this likely stems from the dev" split being unrepresentative.

Against it, from the same night: "I usually adjust the prompts by hand. I haven't had much luck with prompt optimizers like DSPy" (hamel-using-llm-as-a-judge-complete-guide).

A genuine disagreement between the two most-cited voices in this vault, on a technique that decides whether a build item can be automated. This vault corrected itself on 2026-08-13 for treating multiple sources from one practitioner as corroboration; the mirror-image value is that when the two independent names actually collide, the collision is informative. Both are describing the same job — get a judge prompt to agree with expert labels — and reporting opposite outcomes from opposite methods.

The reconciling variable is visible in the reports themselves: whether there are enough labels to fit against. An optimiser needs a dev set to search on and a holdout to check that the search did not memorise it. The AlignEval run had both and still flagged 25-per-split as too thin, with the dev-to-test gain of 0.005 amounting to noise. Hand-tuning is what you do below that threshold, because there is nothing to fit. So the question this theme should carry is not whether judge-prompt optimisers work but at what label count optimising the prompt beats editing it by hand, and that is answerable with labels teams already have: run both procedures on one label set and report holdout F1.

It bears directly on where the build/adopt line falls. The line here runs at the human interface, and a prompt optimiser is an attempt to move a step from the human side to the machine side — the same move as the generated annotation UI in an-agent-generated-annotation-interface-attacks-the-reason-teams-build-their-own-rather-than-the-boundary and the skipped judge pipeline in a-simple-sampled-screenshot-baseline-matches-five-purpose-built-judge-pipelines-and-the-backbone-is-the-primary-driver. Two of those three attempts came out in favour of automation. This one is unresolved, and unlike the others it has a stated eligibility condition attached rather than a verdict.

Bounds. One optimisation run on 50 labels of one public dataset against one practitioner's unquantified impression, two-year-old models on both sides, and neither report describes the other's setup. The 0.571 → 0.727 figures are a single trajectory with no repeats and the author says the gain may be a split artifact. Recorded as an open question, not a finding.
