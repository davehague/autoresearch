A finalization retry for budget-exhausted outputs belongs in the shared harness primitive rather than in each method being compared

Grounded in recursive-agentic-reasoning-paired-scoring; belongs to build-vs-adopt-eval-tooling.

The three operators under comparison — GROW, PRUNE, BRANCH — all call one solve primitive with identical prompts, an identical 16,000-token budget and identical grading code. That primitive carries an explicit finalization retry for budget-exhausted outputs: when a model burns its budget mid-deliberation and returns empty content, the harness asks it to finalise rather than recording a blank.

Where a recovery behaviour lives determines what the comparison measures. Put finalisation retry inside each method and the method that implements it better wins partly on plumbing. Put it in the shared primitive and every arm inherits the same recovery, so the residual differences are about the thing under test. This is the general principle the vault has been assembling piecewise — the interchange format that makes a paired trial comparable, the requirement that both arms be represented identically — stated for behaviour rather than for data format: anything that is not the treatment must be identical across arms, including the error handling.

It is also a direct argument for the adopt column. Retry-and-finalise on truncated output is unglamorous, easy to get subtly wrong, and exactly the kind of thing a maintained runner should own. This vault has repeatedly found the adopt case concentrating in that layer rather than in metrics: trace schema and integrations rather than the analytics, the interchange format rather than the six runtime metrics. A shared solve with budget accounting and finalisation is the same category of asset, and a team hand-rolling a test-time-compute comparison will write it three times, differently, once per arm.

With a limit that the same paper supplies. The retry did not close the gap: 172 items still timed out in one arm against 131 in another, and the winning operator's margin correlated r = 0.72 with the baseline's residual empty rate (the-winning-operators-gain-correlated-with-the-baselines-empty-output-rate). So the primitive reduced the contamination without removing it, and the scoring-level control — pairing — was still required on top. That ordering is worth keeping: harness-level mitigation first, then a scoring protocol that assumes the mitigation was incomplete.

The vault should note the awkward inverse too. A runner that ships a good finalisation retry makes some published gains smaller, because part of what those methods were being credited for was recovering from the runner's absence of one. Adopting better tooling can lower your measured improvements, which is a correct outcome and an unpopular one.
