Grading execution is now instrumented as its own span class, so judge latency and judge spend come out of the runner already separated from system spend

Grounded in promptfoo-0-122-1-tracing-and-token-accounting; belongs to the-judge-as-a-maintained-dependency.

One release added tracing: instrument grading and red-team execution (#10362) — the grader gets its own spans, distinct from the spans of the system being graded — alongside preserve cumulative grading token usage (#10406) and a four-way red-team token split into generation, target, attacker and grading (#10408).

This closes a two-release arc. promptfoo-0-121-14-to-0-122-0 made judge spend separable — you could tell the judge's tokens from the system's if you looked. This makes it separated by construction: the grader is a distinct execution class in the trace, so its cost and its latency come out of the runner already split, no wrapper required.

The reason this theme cares about latency and not only spend is that a judge is a running dependency. The theme's founding claim is that an LLM judge is not a thing you build but a thing you run — it drifts, it costs, it needs re-validation, and its bill recurs. Every one of those is a per-run measurement, and none of them was previously available without instrumenting around the runner. A judge whose latency doubles after a provider-side model update is a production incident in a CI gate, and until now the runner reported one wall-clock number for the whole eval.

What it makes newly answerable is the question this vault has asked and been refused four times. Decomposed judging is the most actionable judge-design finding here, on two independent sources, and neither quoted a token count, a latency or a dollar figure. Panels, moderators, verifier-first stopping rules, judge-with-run-directory — same gap. The obstacle was partly that nobody could get the number cleanly out of a run where the judge and the system share a token counter. The number is now a field rather than an experiment, which removes the excuse without producing the measurement.

And it composes with the external-trace ingestion in the same release. If the runner can read spans from Langfuse or Tempo (an-eval-runner-now-reads-traces-from-three-observability-backends-it-did-not-produce) and emits grading as its own OTel-conformant span class, then judge spend becomes a line item on the same dashboard as everything else, comparable across runs and across time. That is what a maintained dependency's cost is supposed to look like: a series, not a footnote in a paper.

The gap that stays open is the one instrumentation cannot close. Cost and latency are now cheap to observe; agreement is not, and agreement is what tells you the judge still works. krippendorff_alpha() in one runner and a per-criterion three-pass average in one benchmark (a-full-completion-indicator-at-99-9-of-100-is-what-turns-a-rubric-into-a-contract) are the only two mechanisms tracked here that touch it, and both require labels or repeats that a normal run does not produce. So a team adopting this gets a precise, continuous read on what the judge costs and no read at all on whether it is right — which is the wrong pair of numbers to have if only one is going to be watched.

Single release, single vendor, changelog-level evidence, and no magnitudes: nothing here says what fraction of a typical eval's spend the judge accounts for, which is the number that would actually settle whether decomposed judging is affordable. The feature makes that number obtainable by anyone running the tool; it does not report it.
