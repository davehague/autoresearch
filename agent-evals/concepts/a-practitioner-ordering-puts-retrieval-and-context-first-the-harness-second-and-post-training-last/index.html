A practitioner ordering puts retrieval and context first the harness second and post-training last

Grounded in hamel-ai-product-engineering-notes; belongs to build-vs-adopt-eval-tooling.

"The lowest hanging fruit is to optimize retrieval and context. Once that's done, you should improve your systems and harness. Finally, consider post-training only after the other approaches are exhausted." And underneath all three: "nearly every improvement in these notes starts with good evals."

This vault holds a stack of measurements of how big the harness variable is and not one recommendation about when to pull it. Harness-only changes moved a fixed model 13.7 points (harness-only-changes-moved-a-fixed-model-13-7-points-on-a-public-coding-benchmark-which-is-an-upper-bound-on-tuning-rather-than-an-apportionment); a third measurement landed at 8.6; a behavioural axis swung 4.3x. Every one of those answers "how much can the harness move things," which is a question about magnitude. A team with a fixed budget needs the answer to a different question — which lever first — and magnitude does not settle it, because the largest available effect is not the cheapest one to obtain.

The ordering is consistent with the mechanism this vault already recorded, which is the reason to take it seriously rather than as opinion. Harness gains track recoverable execution defect mass — where there is no defect there is no gain (harness-gains-track-recoverable-execution-defect-mass-so-where-there-is-no-defect-there-is-no-gain). A system failing because the right document never reached the model has no recoverable execution defect to harvest; it has a retrieval defect, and harness work on top of it buys the 92.9% reduction in a failure mode that was not the binding one. Fix context first is what that mechanism predicts, arrived at independently by someone watching teams rather than benchmarks.

Post-training last is the part with the most agreement and the least controversy, and it is worth stating anyway because it is where the money goes when a team has run out of ideas. The corpus includes a session specifically on when eval results actually justify post-training, which is the correct framing: training is a lever you earn by having measurements good enough to know what to train on.

Evals as the precondition for the whole ordering is an assertion doing a lot of load-bearing work. It is also the one claim in this vault that every source agrees with and nobody has costed at the level a team decides on. The ordering only functions if you can tell which layer is currently binding, and telling that apart is a diagnostic problem — the theme where automated attribution tops out near a third accuracy and step-level credit signals fail against their own shuffles.

Bounds. This is practitioner judgement from a consultancy that advises on these choices, published as an index of session notes with no corpus and no numbers. Nobody has run the experiment where matched teams fix context first versus harness first. Treat it as a well-informed prior worth testing — the same status this vault gave the same author's claim that a judge costs a hundred labels plus weekly maintenance (an-llm-judge-costs-a-hundred-labels-plus-weekly-maintenance-so-it-is-a-dependency-rather-than-an-artifact), which a production programme has since corroborated.
