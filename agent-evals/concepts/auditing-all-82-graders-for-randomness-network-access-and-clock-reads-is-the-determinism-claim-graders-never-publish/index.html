Auditing all 82 graders for randomness, network access and clock reads is the determinism claim graders never publish

Grounded in agentrewind-mettlebench-recoverable-execution; belongs to design-for-verifiability.

"The evaluator is a program, not a model. Each task's evaluator is plain Python that inspects the final workspace state (mean 379 non-empty lines, range 222 to 637; 31,056 lines in total). No LLM takes part in judging. We audited the source of all 82 evaluators: none draws a random number anywhere in a judgment, none reaches the network, and none generates a UUID (the one uuid reference parses a fixed constant). Two evaluators read the wall clock. One sets file modification times by a fixed relative offset, which leaves the verdict deterministic. The other waits, with a timeout, for a locally started gRPC service to come up, and that is the only point in the benchmark where timing can affect a result."

"Deterministic grader" is an unaudited adjective everywhere else in this vault. Papers assert it; nobody demonstrates it. And this theme has already collected what happens when the assertion goes unchecked — a grader whose bugs owned more of the score than the models did, moving one system from 42% to 95%; an embedding-cosine gate that scored 0.96 on a meaning reversal. The gap between "we wrote a program, so it is deterministic" and "we read all 31,056 lines of it looking for the four things that break determinism" is the whole difference between a claim and a check.

The audit is a named checklist, which is what makes it copyable. Randomness, network access, UUID generation, wall-clock reads. Four greps over a grader suite, and any team with executable checks can run them this week. It is the cheapest item added to this theme in weeks and the one with the least judgment in it.

Crucially, the audit did not come back empty. Two evaluators read the clock. One is benign by construction; the other waits on a service and is identified as "the only point in the benchmark where timing can affect a result." That is a known, localized, single point of nondeterminism in a benchmark that would otherwise have been described as fully deterministic — and it is exactly the sort of thing an unaudited suite carries invisibly. An audit that finds one real thing in eighty-two files is an audit doing its job, and it is the reason to believe the other three findings.

It also licenses a separate claim that would otherwise be unsupportable. The same paper reports 74.7% three-run verdict agreement and attributes the disagreement to the agent, the tools and filesystem timing rather than to grading (three-run-verdict-agreement-of-74-7-percent-published-beside-a-harness-comparison-is-the-noise-floor-this-vault-has-been-asking-for). That attribution rests entirely on this audit. Without it, 25.3% disagreement has no owner, and the noise floor could be measuring the grader. The determinism audit is what converts a variance number into an interpretable one — which is a good argument for running the audit even if you never intend to publish it.

Practice. If your grader is code, state in your eval's README what you checked it for and what you found. If it is a model, this procedure does not apply and you owe the theme's other five instead.

Bounds. Single study, 82 evaluators, one benchmark. The audit checks four specific sources of nondeterminism and cannot certify absence of others — dictionary or filesystem iteration order, locale, floating-point summation order, and dependency version drift all survive it. Determinism is not correctness: an evaluator that reliably checks the wrong predicate passes this audit cleanly, which is why the paper's separate forward-only reference-solution check (every-task-shipping-an-executable-forward-only-reference-solution-is-the-known-good-output-check-run-at-corpus-scale) is doing independent work. The audit is self-reported by the authors of the code, with no external replication and no released audit script.
