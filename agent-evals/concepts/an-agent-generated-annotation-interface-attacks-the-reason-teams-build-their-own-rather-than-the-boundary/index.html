An agent-generated annotation interface attacks the reason teams build their own rather than the boundary

Grounded in hamel-evals-skills-for-coding-agents; belongs to build-vs-adopt-eval-tooling.

One of the six shipped skills is build-review-interface, which generates a tool for human annotation of traces. The same author, five months earlier, wrote that he uses eval platforms "as a backend data store" and builds "my own custom built annotation interfaces for most of my needs."

This is not a contradiction of the boundary — it is a change in what the expensive side of it costs. two-independent-practitioners-adopt-the-platform-as-a-store-and-build-the-annotation-layer-themselves put the build/adopt line at the human interface, and gave the reason: annotation UIs are not domain-specific in any technical sense, but the friction of an ill-fitting one is paid on every trace, so teams build anyway. A generator that emits a fitted interface on demand does not move the line. It attacks the reason, which is friction, and leaves the line where it is.

Why that distinction is the useful part. Every mechanism this theme has recorded for shrinking the build column worked by making something generic — a shared trace schema, a framework adapter, a maintained runner. This one works the opposite way: it makes the bespoke thing cheap to produce, so the artifact stays yours and the labour does not. If it works, the practical form of build-vs-adopt stops being "which side of the line is this on" and becomes "is there a generator for my side of it." That is a genuinely different question and this vault has not been asking it.

Single source, no evaluation, and one live objection. Nothing reports how a generated review interface compares to a hand-built one, how long it survives before a team rewrites it, or whether the generated UI encodes the same taste the hand-built one did. The objection worth holding: the friction being described is not only rendering, it is knowing which fields to surface and which comparisons to put side by side, and that knowledge is exactly the domain-specific input a generic skill cannot supply — see a-packaged-eval-skill-is-labelled-a-floor-by-its-own-author-and-names-six-things-that-generalize-across-projects. The counter-caution from do-automated-evals-work applies: expect the mechanical parts generated well and the taste-bearing parts generated plausibly and wrong.
