Is it the model or the scaffold? The first study to report both sides says it depends what you measure

When an agent underperforms, the money question is where to spend: swap in a better model, or fix the scaffolding around it — the prompts, tools, control flow, memory, and orchestration. Seven benchmarks published within about two weeks of each other in mid-2026 measured this. One says the model dominates. Five say the scaffold moves things a lot, and two of those say the question is malformed.

For most of that run, every study reported one side of the comparison and left the other implicit. In August one finally reported both — how far the number moves when you swap the harness with the model pinned, and how far it moves when you swap the model with the harness pinned, in the same units on the same grid. It came out on the model's side, and the most likely explanation is not that the earlier studies were wrong. It is that it was measuring something else: not whether the agent finished the task, but whether it got compromised.

The case that the model dominates

HarnessOpt-Bench: Evaluating LLMs at Harness Optimization (arXiv 2608.06301) hands a frontier model a target agent's starting harness, graded evaluation feedback, and a fixed budget, and asks it to improve the harness. Five models did this across four downstream tasks, both inside a shared coding harness and inside their own native ones — 111 scored runs, with each final candidate judged by its gain over the starting point on a held-out partition the optimizer never touched.

The result: the choice of optimizer model separated outcomes more than the coding harness that model worked inside. A second finding cut the same way — a model's own purpose-built harness was not reliably better than the shared one.

The paper also supplies its own strongest caveat. Gains swung substantially depending on which downstream task was in play and on how good the starting harness already was. A harness improvement carries an implicit "on this task, from this baseline," and neither travels.

The case that the scaffold moves the number

DataSpace: Benchmarking Data Agents for Verifiable Analytics over Heterogeneous Workspaces (arXiv 2608.03451) is a different kind of test: 410 analytics tasks over 7,439 artifacts — CSV, JSON, SQLite, Markdown, PDF, and video, 15 GB in all — where the agent gets a question and a workspace and must return a complete table. Grading is deterministic, with no model judging the answer.

Six recently released frontier multimodal models were run against five widely used agent harnesses. Best accuracy overall was 66.34%. And with the model backbone held fixed, swapping the harness moved accuracy by 15.36 points.

That is not a rounding error, and it is not the scaffold being a convenience.

The case that got worse

Skill-Use: Can LLMs Actually Use Skills in Agentic Harnesses? (arXiv 2608.04828) tests something narrower and finds something more damaging. It pairs 79 real skills with 177 executable tasks across nine domains, each in an isolated Docker sandbox, and puts the agent under progressive disclosure: it sees only a skill's name and one-line description and must retrieve the full procedure before following it. Scoring splits into whether the agent invoked the right skill at all, how faithfully it followed the procedure, and whether it stayed inside the skill's forbidden-operation boundary.

Eight LLMs, two harnesses. The best configuration scored 0.613 on the combined measure, so reliable skill use is not close. But the finding that matters here is a different one: both the scores and the ordering of the models changed with the harness.

A score shift and a rank shift are not the same problem. If a harness makes every model 8 points worse, you can read someone else's leaderboard and mentally subtract. If the harness reorders the models, that leaderboard tells you nothing usable about which model to pick for your stack — the winner under their scaffold may lose under yours. This was measured across nine domains, which is a wider base than either result above.

The case that the question is malformed

EduClaw-Bench: A Long-Horizon Benchmark for Pedagogical LLM Agents with Simulated Learners (arXiv 2608.03206) is the only one of the four built as a grid. It places an agent tutor in a continuous 30-day relationship with a simulated learner across 55 scenarios, where the learner's concept mastery comes from a knowledge-tracing model trained on real student data. Ten agent adapters were run over three base-model tiers.

Its first headline finding is that tutoring quality belongs to the base model and the agent harness together rather than to either alone — an interaction the authors say single-tier, single-session evaluation cannot reach. That is the right claim about the design: a study with one model tier would have credited every difference to the adapters, and a study with one adapter would have credited it all to the tiers.

Its second finding is worth carrying separately. Almost no combination sustained good tutoring across the full 30 days. Whatever a single-session evaluation certifies, it is not durability.

A fourth agreement, and the weakest one

GABench: A Comprehensive Benchmark for Evaluating LLM Agents on Graph Analysis Tasks (arXiv 2608.01684) is the largest of the five by task count and the least informative on this particular question. It builds 84 executable tools for operating on graph data, generates 10,400 tasks against them with ground truth that comes from executing the reference tool sequence, and runs frontier models across multiple harnesses over three graph types.

One of its three headline findings is that harness choice significantly affects performance, and that existing harnesses remain limited on the hardest tier. That adds a fourth unrelated task family — graph analysis, alongside tabular analytics, skill use, and tutoring — to the side saying the scaffold matters.

But the word doing the work is "significantly," and the paper does not say by how much, across how many harnesses, or against what baseline. Set that against DataSpace's 15.36 points and Skill-Use's reordered rankings and it is a different quality of evidence entirely. It counts as agreement on direction. It is not a measurement.

Worth stealing from it regardless, on an unrelated axis: building the executable tool layer first and generating tasks against it is why 10,400 tasks was affordable. Every other benchmark here sits between 50 and 410 tasks, and the entire difference is whether a human has to write down the right answer.

The grid everyone wanted, and the sentence it produced

AgentS4D: Benchmarking Runtime Risks across the Execution Lifecycle of LLM-Based Workspace Agents (arXiv 2607.27294) is the one that should have settled this, and it is the reason to stop expecting anyone to.

It runs 328 cases against all twenty combinations of four agent harnesses — Hermes, OpenClaw, Claude Code, Codex — and five model backends: GPT-5.5, Gemini 3.1 Pro, DeepSeek-V4-Pro, MiniMax-M3, Qwen3.7-Plus. That is 6,560 runs and a complete factorial, roughly an order of magnitude more configuration sweeping than anything else described here. What it measures is not task accuracy but runtime safety: whether an agent's actions, side effects, and state changes trip a prespecified unsafe signal at any point during execution. 68.0% of runs did.

The finding on this question, in full: observed safety varies with both the harness-backend pairing and with how the risk was introduced. No apportionment. No per-factor variance. Twenty cells, 6,560 runs, one clause.

The unrelated result in the same paper is more immediately useful to anyone shipping an agent. 4,344 runs — 66.22% of the total — were unsafe and completed their task anyway. Two thirds of that dataset would read as wins on a completion dashboard. Whatever a task-success rate summarizes, it is not whether the run was acceptable.

The study that reported both sides

HarnessSafe: Evaluating Safety Across Persistent Carriers in Agent Harnesses (arXiv 2608.06984) is the first to give a number for each margin instead of one.

It is not about task accuracy. It tests what happens when something an agent stores in one session — a memory entry, a reusable skill, a tool result, a session summary, a shared artifact — carries adversarial content that fires during a later, ordinary request. 328 executable cases across seven such carrier families, run natively on seven agent harnesses, with each run assigned the furthest point a chain reached before something stopped it, summarized as a Chain-Stage Score.

The two numbers:

  • Backend pinned to GPT-5.6-Sol, harness varied: 39.4 under Claude Code, 62.3 under Codex CLI. A spread of 22.9.
  • Harness pinned to Claude Code, backend varied: 22.7 to 58.7. A spread of 36.0.

Be careful with what that licenses. Two ranges are not a variance decomposition — there is no interaction term, no repeated runs, and a range depends entirely on which harnesses and which models happened to be in the grid. Include one badly-matched backend and the backend margin widens for reasons that have nothing to do with the factor. What it does establish is that on this grid, on this metric, the models were further apart than the harnesses.

Which cuts against everything above. So either the earlier results were task-specific, or — more plausibly — the answer depends on which property is being scored. Refusing to act on a poisoned memory entry is a behaviour that comes out of training. Finding the right file in a workspace is a behaviour that comes out of the scaffold. If that is what is going on, "is it the model or the harness" does not have an answer; it has one answer per thing you measure, and every result in the previous sections is quietly conditioned on measuring task success without saying so.

The paper is also worth reading for a reporting practice unrelated to any of this. Configurations with nearly identical attack-success rates stopped at different stages — one blocked at the door, another blocked at the final check. An endpoint rate treats those as identical. The stage a run reached is already sitting in the trace, and reporting the distribution costs nothing.

What a team gets by tuning rather than swapping

Every benchmark above compares scaffolds built for other purposes. LangChain's engineering write-up, Improving Deep Agents with harness engineering (February 2026), does something different and more practical: it takes one scaffold and tunes it.

Model pinned to GPT-5.2-Codex, no fine-tuning, no model swap. Terminal Bench 2.0 score goes from 52.8% to 66.5% — roughly rank 30 to top 5. Four changes, reported as a bundle:

  1. A forced build-and-verify loop, with middleware that will not let the agent declare itself done until a verification pass runs.
  2. Context injection at startup — a directory map, available tooling, environment constraints, and the evaluation criteria.
  3. Loop detection that counts edits per file and interrupts the agent after N iterations.
  4. Reasoning effort concentrated at the planning and verification phases rather than held at maximum throughout.

They found what to fix by pulling traces out of their eval store and running parallel error-analysis agents over them, which produced three failure classes — reasoning errors, missed testing, timeouts — that map onto three of the four changes.

Two large caveats, and the post states one of them itself. This is a framework vendor reporting a favourable benchmark result about its own framework, with no ablation, no repeated runs, and no variance. And the harness was tuned using traces from the benchmark it is scored on, with no held-out split mentioned, so some unknown share of the 13.7 points is fitting to the test rather than a better agent.

What the number is, read carefully, is not how much variance the harness owns. It is how much a competent team could extract by trying — which is the more useful quantity if you are deciding whether to spend a quarter on scaffolding, and which cannot be turned into an apportionment.

The most valuable sentence in the post is a throwaway. The same harness scored differently under Claude Opus 4.6 and needed its own separate optimization. A harness ports; a harness's tuning does not. So scaffolding work is a recurring cost that lands again on every model upgrade, and the upgrade decision is not "is the new model better" but "is it better after redoing the tuning I already paid for."

A wrinkle: there may be a third factor

MDArena: Evaluating Coding Agents on Realistic Molecular Dynamics Workflows (arXiv 2608.02642) was not built to weigh in on this. It is 50 containerized tasks taken from active biomolecular simulation projects, run across six model/harness configurations, and its own headline is that agents make substantial partial progress and fail on the details that make a scientific workflow reproducible.

Three of its configurations, in order:

  • Codex with GPT-5.5 at extra-high reasoning effort: 24/50
  • Codex with GPT-5.5 at medium reasoning effort: 21/50
  • OpenCode with Gemini Flash 3.5: 20/50

The first two differ in one setting — same model, same harness, effort dialled down. The third differs in both harness and model family. A decoding-time knob did about as much as swapping the model and the scaffold together.

Do not over-read this. Three tasks out of fifty is inside binomial noise, the paper reports no repeated runs or variance, and the six configurations are not a factorial design. It is a flag, not a result.

The flag is worth raising anyway, because reasoning effort is neither the model nor the harness under the definitions everyone is using. It is a setting on the boundary, it defaults differently across vendors, and it is almost never reported. If it carries real signal, then every "the model matters more" result is potentially an effort result wearing a model's name — and the decomposition this whole literature owes us is a three-way one, not a two-way one.

And a fourth factor, which is worse because it is boring

SimpleWikiSearch: A Clean Offline Wikipedia Environment for Agentic Search (arXiv 2607.26070) is not a benchmark result at all. It is a released environment — a full English Wikipedia dump, cleaned and chunked, with keyword and dense indexes and a three-tool contract of search, open_url, and submit_answer — published because its authors think the field cannot currently compare its own numbers.

Their list of what sits underneath a reported agentic-search score and usually goes unstated: the Wikipedia snapshot, the preprocessing pipeline, the chunking policy, the retrieval backend, the tool schema, the observation format, and the answer submission rule.

Read that list against the debate above. A chunking policy is not the model. Under any normal definition it is not the harness either — it is a property of the environment the harness reaches into. And unlike a model version or a harness name, nobody thinks of it as a variable. It gets picked in an afternoon by whoever wired up the retriever and never written down.

AgentS4D found the same thing from a different direction: the carrier through which adverse content reached an agent changed its behaviour independently of both the harness and the backend. So the environment shows up twice, in two unrelated task families, as something that moves the number and is not one of the two factors anyone is arguing about.

The honest caveat: SimpleWikiSearch asserts these seven parameters matter and does not measure how much any one of them is worth. It builds the apparatus for that measurement and leaves it to somebody else. Nobody should quote a magnitude from it.

Why they can all be right

The setups measure different jobs.

HarnessOpt-Bench measures a model in the editor role: reading a harness, reasoning about it, writing a better one. That is a hard coding-and-judgment task, and it is unsurprising that the model doing it matters more than the environment it does it in.

The other five measure the harness in the carrying role: an ordinary agent doing its actual work, with the scaffold supplying the tools, retrieval, control flow, and skill surfacing it needs. That is the situation almost everyone deploying an agent is actually in — and it has now been measured five times, by five teams, on five unrelated task families: tabular analytics, skill use across nine domains, tutoring, graph analysis, and workspace runtime safety. On task performance, it has not once come out on the model's side.

HarnessSafe is the exception and it is a different axis rather than a sixth vote. It measures containment — whether a risk planted in one session survives into a later one and fires — and there the model margin was larger. Two axes, two answers, and no reason to expect one to predict the other.

So the results do not contradict each other. What does not survive is the one-line summary — "the model matters more than the scaffold, so upgrade the model" — because the case people apply that advice to is the second one.

A fifth data point, weaker

OneDayAgent: Towards a Long-Horizon Harness for Autonomous Agents (arXiv 2608.05013) reports a harness that decomposes long tasks, maintains execution memory under context pressure, and verifies and repairs its own final deliverable. It scores 0.821 on a 104-task benchmark with a GLM-5.2 backend, and the authors say the same harness runs across five backends from three model families with no per-model tuning.

If that holds, a harness is a portable asset rather than something you re-tune every model release. But treat it carefully. This is a system paper reporting its own system winning on its own chosen benchmark, and "generalizes across backends" is reported as the harness running with different execution styles, not as a per-backend score table. Without those numbers, you cannot tell whether the gains held or merely whether nothing crashed.

What is still missing

Nobody has published the actual apportionment: how much of the outcome variance belongs to the model, how much to the harness, and how much to the interaction between them, stated as numbers with repeated runs behind them.

Look at what each one reports instead. DataSpace gives a spread in points. Skill-Use gives reordered rankings. EduClaw-Bench gives a joint attribution. GABench gives the word "significantly." AgentS4D gives "varies with both." HarnessSafe gives two ranges, which is the closest anyone has come and is still a comparison of spreads rather than of variance components. Both EduClaw-Bench's 3 × 10 grid and AgentS4D's 4 × 5 grid are precisely the designs that would support the real analysis.

For most of these there is a charitable explanation: the harness sweep is a robustness check, not the result being sold. The contribution is the benchmark. The comparison is the paragraph showing the benchmark is not an artifact of one scaffold, and a paragraph like that gets one qualitative sentence.

AgentS4D strains that explanation. Its cross product is not incidental — running every harness against every backend is one of the paper's stated contributions, it cost 6,560 runs, and the analysis that would apportion the variance across those cells is standard. It still is not there.

But HarnessSafe reported both margins in a table without making anything of it, so the pessimistic reading — that no benchmark author will ever report a two-sided comparison — is wrong. What is missing is narrower than it looked: a factorial over model tier, harness, reasoning effort, and environment configuration, with repeated runs and variance reported per factor and per interaction. And now there is a second thing missing that is cheaper to get: both margins on a task-success axis, which would say whether the model-versus-harness answer really does flip depending on what is being scored. That one needs no new runs at all — several of the grids above already contain the data.

Before any of this, check the grader

One number belongs in this discussion and does not fit anywhere in it.

Anthropic's engineering guide Demystifying evals for AI agents (January 2026) mentions in passing that on CORE-Bench, Claude Opus 4.5 scored 42% — and 95% after grading bugs were fixed.

Fifty-three points. Larger than the 15.36-point harness effect, larger than either HarnessSafe margin, larger than every model-versus-scaffold difference described above put together, and caused by nothing except defects in the scoring code.

It is a single anecdote in a vendor guide with no description of the bugs, so nobody should take 53 points as typical. What it establishes is that the error bar on a badly-built grader is unbounded, and the failure mode is nasty: a broken grader produces a plausible-looking low score, and a low score on a new benchmark is exactly what everyone expects to see. Nobody investigates it.

None of the papers here reports validating its grader. If you are running any of this yourself, score a known-good output first — a reference solution, a human transcript, a run you already believe — and confirm it comes back right. It takes an afternoon and it gates the value of everything downstream of it.

There is also a case that the two-factor question has aged out. Between MDArena's reasoning-effort flag, SimpleWikiSearch's seven environment parameters, and AgentS4D's risk carriers, there are now at least five candidate factors in play, and three of them are things teams do not currently write down. A clean model-versus-harness split would be answering a question that no longer describes the problem. The better version: how much of an agent's performance is owned by configuration nobody records? On present evidence the answer is "enough to matter," and not one of the five candidates has an effect size against it.

Every result here is also a single unreplicated study on its own task family, in a literature whose own papers warn that results do not transfer between task families.

What to do with this

Three things follow, in descending order of confidence.

Evaluate the model and the harness as a pair, not in sequence. Picking a model from public standings and then dropping it into your scaffold is the exact procedure the rank-instability result invalidates. A harness comparison belongs inside your evaluation rather than downstream of it — on one realistic workload it was worth 15 points.

Do not generalize a scaffold win. HarnessOpt-Bench's own caveat is the most portable finding across all four papers: improvements swing by task and by how good your starting point was. LangChain's tuned harness needed re-tuning for a different model, which adds the axis that costs the most — scaffolding gains do not survive a model upgrade, so budget harness work as recurring rather than capital.

Say which property you measured. A harness comparison run on task accuracy and one run on containment gave opposite answers. Whatever you conclude about where your own variance sits is conditional on the axis you scored, and that condition is worth one sentence in whatever you write down.

Check the grader before you compare anything. Fifty-three points on CORE-Bench came from scoring bugs. Nothing else on this list matters if the instrument is broken, and a broken instrument looks like a hard problem.

If you have persistent state or a long horizon, one run is one sample. EduClaw-Bench's second finding — almost nothing held up over 30 days — says a point-in-time score has a shelf life, and it does not tell you what that shelf life is.

Write down your inference-time settings, and your environment. Reasoning effort, thinking budget, temperature — and the corpus snapshot, chunking policy, tool schema, and observation format. MDArena's numbers are too noisy to prove the first group matters and SimpleWikiSearch does not quantify the second, but all of them are cheap to record and all of them are currently invisible in almost every comparison anyone publishes, including the ones above. A comparison that does not state them is not reproducible, whatever else it is.

Do not let a completion rate stand in for whether the run was acceptable. Two thirds of AgentS4D's runs finished the task and tripped a safety signal. If your agent has side effects, that is two measurements, not one — and averaging them into a single score puts an agent that finishes everything badly level with one that refuses everything. Name the constraint, score violations as their own rate, and gate on it rather than folding it in.

There is a useful piece of scaffolding for the diagnostic work. Model or Harness? An Interaction-Centric Taxonomy for Localizing Agent Failures (arXiv 2607.28802) assigns each of 41 observed failure modes to a component boundary and a side, so a failure routes to post-training, to harness engineering, or to environment redesign. It asserts the model/harness seam is real and worth labelling along. The benchmarks above are the first attempts to measure which side of that seam the variance sits on — and the honest current answer is that it depends on what you are asking the agent to do, that for the job most people have it is not mostly the model, that the seam has more sides than two, and that nobody has yet put a number on any of them.
