Your benchmark score is not a property of the model

Take a model's reply to a coding task — the exact bytes it produced, unchanged — and send it to the shell two different ways. One path hands the command over directly. The other wraps it in a template that escapes nothing before reparsing it.

Success falls by 55.4 to 73.2 percentage points.

That result comes from QuoteBench: How Matched Scores Can Hide Command-Path Failures (arXiv 2608.13547), and the isolation is unusually clean: escaping at the interpolation point reproduces the direct-path outcome exactly, so the parser is provably the only difference. The model was not consulted. Nothing about its reasoning changed. What changed was the plumbing between the model and the thing it acts on.

For comparison, the biggest harness effects anyone has published on agent benchmarks run 7.5 to 15.4 points — the upper end being DataSpace (arXiv 2608.03451), which held six model backbones fixed across 410 deterministically graded tasks and found harness choice worth 15.36 points. A study of infrastructure agents that ran every task three times found per-configuration standard errors of 6 to 12 points — the noise floor is roughly the size of a typical harness effect. Against that, the parser is in a different weight class entirely.

The transport is not the only thing nobody writes down

QuoteBench's authors call this the execution transport: the layer that serializes, wraps, templates and reparses model output before it takes effect. It exists in every agent product — tool-call arguments, SQL, structured-output schemas, file writes, every MCP or RPC hop — and it is documented in almost none of them.

It differs in kind from the usual list of unreported settings. Reasoning effort, network access, whether the agent was told it was being evaluated: those are choices someone made and failed to mention. The transport is code that exists whether or not anyone decided it should.

The honest caveat, and QuoteBench states it: the parser in the experiment was deliberately unescaped. The 55-to-73-point figure prices a constructed fault, not a survey of what real transports do. It also ran on 56 one-shot tasks, which is the harsher case — a real agent loop sees the error and retries. What survives the caveats is narrower and still uncomfortable: a benchmark number obtained through one execution path does not predict behaviour through another, and nobody reports which path they used.

A small number can be two enormous numbers cancelling

The same study found something worse than a large hidden effect: a small one.

One configuration showed a matched score gap of −3.6 points between the two execution paths. Underneath, the transport did −64.3 points of damage, and the model compensated by +60.7 — adapting its generation to survive the parser. The reader sees −3.6 and concludes the execution path did not matter. The true reading is that it mattered enormously twice, and this particular model happens to be good at absorbing it.

Nothing was averaged here. No mean over items, no majority over judges, no aggregation operator to blame. Two large opposed effects simply landed in the same number.

The generalisation is uncomfortable because it applies to any A/B test whose arms differ in more than one respect: a small delta is evidence of no effect only if you know nothing offsetting was bundled into it. Nobody reports that. And the check was cheap here — it needed no new model calls at all, only replaying stored replies through both paths.

Splicing a change into a stored run does not work

If the pipeline matters that much, the obvious response is to test pipeline changes cheaply: take a logged trajectory, substitute one step, and read off what would have happened. This is how agentic routers get evaluated, how prompt variants get compared, how cost-driven model downgrades get justified — because live re-runs are expensive.

The Replay Gap: Static Evaluation of Model Switching in LLM Agents Scores the Wrong World (arXiv 2608.08239) forked live SWE-bench trajectories instead of replaying them — six paired runs, roughly 900 rollouts, with 359 same-model control forks to establish a floor. Replaying with one model's output substituted leaves only 3% of replayed states valid. The replay evaluator mispredicts every success-relevant outcome call, and predicts patches with 0.00–0.11 similarity to what actually happened.

The mechanism is locality, and it does not hold: one substituted step rewrites 61–94% of subsequent actions. The effect shrinks the later in the run you intervene, which is the practically useful part — an early intervention has to be measured by re-running the whole thing, a late one can be approximated.

The reason this is worth knowing about even if you never build a router: any method that splices a per-step change into a stored run makes the same assumption. Prompt variants, tool-description edits, memory policies, model downgrades. And a replay evaluator returns a perfectly ordinary-looking score, so nothing about the output tells you it is meaningless.

"We ran at temperature 0" is not an error bar

The Replay Gap also has a control arm, which almost nothing in this literature does — 359 forks that changed nothing, run to establish how much two identical configurations diverge on their own.

They found that temperature-0 determinism is a property of the serving stack, not of the temperature setting. FP8-served controls diverged on over 90% of forks. AWQ-served ones stayed near-identical.

This is the sentence every evaluation uses in place of repeated runs. It now depends on a serving detail no methods section states, which means two teams running the same weights at the same temperature can sit on opposite sides of over-90%-divergence and near-identical without either one knowing.

It compounds a problem rather than duplicating it. InfraBench (arXiv 2608.11234) established that nobody measures the noise floor and that it can be 6–12 points. This says the standard excuse for not measuring it is unsound.

What the pipeline is worth when someone tunes it

None of this is an argument that models do not matter. It is an argument about what a leaderboard row is measuring.

Two studies put numbers on the scaffold with the model pinned. LangChain, tuning a harness against a benchmark with GPT-5.2-Codex fixed, went from 52.8% to 66.5% on Terminal Bench 2.0 — Top 30 to Top 5 (Improving Deep Agents with harness engineering). LongHorizon-Harness (GitHub), holding both the model and the execution backend fixed and changing only the loop, reports +7.5 points on Terminal-Bench 2.1 and +28.9 on WeaveBench. Both are self-reported by the people who built the harness, with no repeated runs, and should be read as upper bounds rather than measurements.

The spread between those two figures is the more interesting number than either one. A factor of four apart, with model, backend and harness all fixed, means "the harness is worth X" is not a property of the harness — it is a property of the harness and the task together.

And when the scaffold changes, rankings move, not just scores. Skill-Use (arXiv 2608.04828) ran eight models over 177 tasks in nine domains under two harnesses and found the ordering of the models changed with the harness. A score shift you can mentally subtract. A rank shift means a leaderboard built on someone else's stack cannot pick a model for yours, even directionally.

The measuring instrument gets a vote too

One more term, and it is the largest single effect in any of this. Anthropic's Demystifying evals for AI agents reports that on CORE-Bench, one model scored 42%, then 95% once grading bugs were fixed. Fifty-three points owned by the scoring code.

That is a vendor engineering post with no methodology attached, which is weak evidence for the specific number. The failure mode it describes is not weak at all, and it is worth stating plainly: a broken grader produces a plausible low score, and nobody investigates a low score on a new benchmark.

What to do about it

Five things, in rough order of cost:

  1. Score a known-good output before trusting any comparison. An afternoon. It catches the 53-point case.
  2. Write down the execution path. QuoteBench proposes reporting the model configuration, generation contract, execution path, operating point and final-state validator. Three of those five are things essentially nobody reports today. You can adopt the list unilaterally.
  3. Run it three times and report the spread, not just the mean. The repeated runs cost 3× and they are the only way to know whether your delta cleared the noise.
  4. Do not read a small gap as no effect unless you have checked what could have cancelled inside it. Where the intermediate condition can be replayed, this costs nothing.
  5. Do not evaluate a per-step change by splicing it into a stored run. If you must, report same-configuration control forks alongside it, so a reader can see the floor rather than assume it away.

The through-line: a benchmark number is a joint measurement of a model, a scaffold, an execution path, a serving configuration and a grader. Reading it as a property of the model alone is an unstated conditioning, and every one of the other four has now been shown to move the number by more than the model differences people use these scores to decide between.

Honest limits on all of this. The transport result is one study on 56 tasks with a deliberately broken parser. The replay result is one study on one benchmark. The serving-quantization finding is a control arm inside that same study. None of them has been replicated. What makes them worth acting on anyway is that every recommendation above is cheap, and every one of them fails safe: if the effects turn out smaller than reported, you have lost an afternoon and gained a methods section.
