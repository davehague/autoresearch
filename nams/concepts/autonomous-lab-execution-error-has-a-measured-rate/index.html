Two plates in 480 — and neither failure was a hallucinated fact

The number the vault has been missing

On 2026-07-22 the vault logged a schema gap: loop_readiness grades whether a machine could make the call and has never asked whether a machine can reliably run the plate. The only datapoint then was the Pipette benchmark's 37–72% task success in simulation, from which the vault computed that at a generous 95% per step, a 20-step protocol completes 36% of the time.

Here is a number from the other end — production, six months, real hardware:

"less than 1% of the executed designs were flawed (just two of 480 total 384-well plates designed by GPT-5 across Steps 0–5)."

What the two failures actually were, because the shape matters more than the rate

Failure 1 — constraint override. The model needed room for more reagents inside a fixed 20 µL total, so it overwrote the required 2 µL of base buffer, producing an out-of-spec reaction volume. Fixed by tightening the Pydantic validation schema. This is the classic optimiser failure: a hard constraint treated as a soft one because relaxing it improved the objective.

Failure 2 — a unit-conversion bug. The model "wrote code that had a minor bug (converting nL to μL by dividing by 10⁶)", producing a plate where "each well contained only glucose and ribose". No nucleic acids, no protein, one plate wasted.

Neither is a hallucination in the sense the field usually worries about. Nothing was invented; no fake citation, no fabricated mechanism. Failure 1 is a specification violation. Failure 2 is an off-by-a-thousand in a script. Both are the kind of defect that any working software engineer recognises immediately, and neither is addressed by making the model know more chemistry.

The part that should worry a tox-loop builder

Both were found after execution. The paper says so: "we only discovered 2 plates with fundamental design flaws post execution."

They were findable at all because the failure was loud. A plate containing only sugars produces no protein. The objective function screams. In the vault's terms, the loop's readout carried its own alarm.

A hazard-testing loop does not have that property. The equivalent unit error — a dilution off by a factor of a thousand — does not produce an obviously blank plate. It produces a plausible negative: a chemical tested a thousandfold below its active range, returning "no effect," passing the assay's acceptance criteria (the controls are unaffected by the test compound's concentration), and entering the record as a non-hit. A wrong answer that looks exactly like a right one.

This is the loop-specific version of the vault's correlated-blind-spot rail. The rail says an automated system reads concordance as confirmation and iterates fast into systematic error. This says the same thing one layer down: an automated system reads a silent failure as data. Speed converts a caught mistake into an uncaught one, whenever the mistake happens to be quiet.

What the vault takes from it

  1. A first real number: <1% fundamental design error, in production, on a well-instrumented loop with a hand-written validation schema. That is genuinely good, and better than the simulation benchmark suggested.
  2. The number is conditional on a loud objective. It measures how often errors happened, in a system where the errors announced themselves. It does not measure how often errors would be missed.
  3. The schema gap stays open. The vault still has no execution-reliability dimension on the loop_readiness axis, and adding a fourth sub-axis remains a human decision. Logged again in docs/open-gaps-log.md.
