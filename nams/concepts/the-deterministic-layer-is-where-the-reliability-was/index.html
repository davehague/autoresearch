The deterministic layer is where the reliability was — and it was faster too

The result

Two ways to get from a parsed protocol to robot commands. One: let the language model do it. Two: hand the parsed structure to ordinary deterministic code that knows the machine's physical constraints — tip-collision avoidance, plate positions, volume limits — and let it emit the commands.

The deterministic code won on accuracy and on speed simultaneously, which is unusual enough to be worth stating plainly: this is not the familiar reliability-versus-capability trade. There was no trade.

The failure mode it removed has a name in the paper: execution hallucination — the model inventing tip usage or coordinates that do not match what the machine actually is, and getting steps out of order. A rule cannot invent a coordinate the machine does not have. That is the entire mechanism.

The consequence the authors draw is the useful part: because the rule layer adds essentially no error, "essentially all final errors therefore originate at the Parser Agent's structuring stage." The whole system's reliability reduces to one question — did the model correctly understand the English?

Why this vault has been saying this in different words

The loop_readiness ladder in shared/evidence-model.md turns on a single question, and the contract for every ingest says so outright: "does the guideline publish a fixed, deterministic data-interpretation procedure … This is the single most decisive question on the axis."

Not "is the readout digital." Not "is there a robot." Is there a written-down rule. OECD Test Guideline 493 — the estrogen-receptor binding assay — is fully quantitative, entirely instrument-read, and sits a rung below closed-loop-ready for exactly one reason: the guideline itself states no agreed interpretation method exists. The vault has 23 maps whose blocker is no rule.

This paper is the same claim from the software side, with a measurement attached. The reliable part of an automated system is the part where somebody wrote down what to do. The model's job is to get to that written rule from something unstructured — and that is where all the remaining error lives.

It is also the empirical complement to a-model-checking-its-own-work-is-not-a-check from the same paper: the way to reduce a model's error is to give it less to be wrong about, and then to have a different model check the part that is left.

The caution that has to travel with it

A deterministic rule is only as good as the specification behind it, and this vault has a map about exactly that. nam-data-processing-pipeline tracks the software chain between an instrument's output and a hazard call, and its blocker is not capability but disclosure — the pipeline is outcome-changing, treated as an implementation detail rather than part of the method, and largely undocumented. "A loop cannot verify it is running the method it thinks it is running."

So "move it into deterministic code" relocates the risk; it does not delete it. A hard-coded rule that is wrong is wrong silently and consistently, forever, and it will never flag itself. That is arguably a worse failure mode than a model's — a model at least varies. The version of this finding worth carrying is narrower and holds: where a physical constraint is knowable in advance, encoding it beats asking a model to remember it. Tip collisions and plate geometry are knowable in advance. What counts as a positive result frequently is not.

Limits

Preprint, not peer reviewed. Directional result read off a figure. Developers measuring their own architecture against their own ground truth on 30 protocols of one assay family — enzyme-linked immunosorbent assays, dilution and dispensing. The authors state that cell culture, thermal cycling and centrifugation require separate validation. No toxicology and no Test Guideline appears anywhere in the paper.
