A second, independent group proposes the same fix from the opposite direction: architecture, not control theory

Ingested the same run as zhang-2026-safe-sdl-safety-boundaries, and worth reading against it directly. Safe-SDL names a failure mode (an AI's syntactically-valid lab command can be physically unsafe) and proposes control-theory mechanisms — formally verified operating boundaries and real-time state monitoring — to catch it at the moment of execution. Yang et al.'s Experiment-as-Code (EaC) proposes a systems-architecture separation instead: an AI agent expresses what it wants to happen (a declarative experiment specification) rather than how to make it happen (device-specific imperative commands), and a systems layer underneath — explicitly including a "safety checks" stage — compiles the declarative intent down to actual device calls.

The two papers do not cite each other and neither cites toxicology. That is itself a small, useful data point: two groups, arriving from different disciplines (control theory vs. cloud/systems infrastructure), in the same few months of 2026, independently concluded that an AI agent's stated intent and a lab instrument's physical action need a gate between them — a systems-layer checkpoint, not a smarter model. Read against automation-self-driving-labs's running observation (first logged 2026-09-11, repeated 2026-09-14 and 2026-09-17) that the materials/chemistry side of the SDL literature keeps re-deriving the same infrastructure problems in isolation from each other and from this vault's own vocabulary, this is a fourth instance of that pattern — and the first pair to converge on safety specifically, rather than on coordination/management.

What EaC adds beyond Safe-SDL, concretely. Safe-SDL proposes what the safety mechanisms should verify (ODDs, Control Barrier Functions); EaC proposes where in the system such a check would live — as one stage ("safety checks") inside a compiler-like pipeline between a declarative experiment spec and device-level actuation, alongside program analysis, resource assignment (contention over shared instruments — this map's "system entropy" problem), and job orchestration. Neither paper builds a working safety-gated system with a measured result; EaC's own evidence is a single case-study transformation of an existing ad-hoc workflow into its declarative form, with no accuracy, throughput, or incident numbers reported.

Why this stays off any method's tier. Nothing here is toxicology-specific, and both sources are explicit that the stack is domain-independent. evidence_tier: in-silico-mechanistic — architecture proposal plus one case study, not a wet-lab or regulatory-tox result; strength: suggestive. funding_flag: none — an academic systems-research proposal, not a vendor's claim about a shipped platform.
